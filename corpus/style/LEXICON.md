## 1. 起句与视角词

| 词条 | 强度 | 用法 | 例句（S1） |
|---|---|---|---|
| 这里我… | ★★★ | 引出自己的具体动作，替代"我接下来" | 「这里我选择了我们一个相对比较成熟完整的项目」 |
| 这里我简单提一下 | ★★★ | 从铺垫转入干货前的降调 | 「这里我简单提一下此次Vibe coding过程中的一些小经验」 |
| 从…方面来看 / 从…上来看 | ★★★ | 给出一层分析视角后再展开 | 「从适用场景上来看」「从提效方面来看」 |
| 另 / 另因 | ★★ | 段末追加补充说明 | 「另因录屏帧数低展示较为卡顿」 |
| 同时 | ★★ | 并列递进，不换段 | 「同时，对于程序员的技能也有了新的要求」 |
| 作为一名… | ★★ | 开场自我定位（非炫耀式） | 「作为一名后端工程师」 |

## 2. 转折、让步与限定

| 词条 | 强度 | 用法 | 例句（S1） |
|---|---|---|---|
| 然而受限于… | ★★★ | 承认现实约束，承接"惊艳"之后 | 「然而受限于AI上下文窗口的长度，在大型项目中的使用并不尽如人意」 |
| 当然，这并不意味着… | ★★★ | 主动划边界，防过度承诺 | 「当然，这并不意味着B端没有复杂度」 |
| 貌似…但实际上手就会发现 | ★★★ | 打掉读者幻想 | 「貌似不需要…，但实际上手就会发现」 |
| 并不尽如人意 / 并不 | ★★ | 克制的否定，比"不"更书面 | 同上 |
| 与其…不如… | ★★★ | 提出替代方案的核心句式 | 「与其让后端和前端…来回拉扯，不如让AI…直接生成出来」 |
| 只是 / 只不过 | ★★ | 缩小主张范围 | 「PFC 只是最后防线」（课程语料） |

## 3. 判断与定义句

| 词条 | 强度 | 用法 | 例句（S1） |
|---|---|---|---|
| X 天然就是 Y | ★★★ | 一句话定性，常用在破题处 | 「这份…文档天然就是一份AI行动指南」 |
| 以…为核心 / 为… | ★★ | 结构化的中心判断 | 「以数据管理为核心」「以API文档为核心的生成范式」 |
| 从 A 升级为 / 转向 B | ★★★ | 谈角色演化必用 | 「从"闷头CURD"升级为"按业务实现接口和合约"」 |
| 在…的前提下，… | ★★ | 给结论加前置条件 | 「在文档规范清晰的前提下」 |
| 总结： | ★★★ | 段末收口，单起一行 | 「总结：在文档规范清晰的前提下，AI生成页面可直接覆盖80%-90%的标准需求」 |

## 4. 比喻与俗语（签名级）

| 词条 | 强度 | 指代 | 例句（S1） |
|---|---|---|---|
| 抽盲盒 | ★★★ | 结果不可预期、风格不稳定 | 「避免每次生成的代码像"抽盲盒"一样」 |
| 屎山 | ★★★ | 代码/系统腐化 | 「防止代码堆砌逐渐腐化为"屎山"」 |
| 来回拉扯 | ★★★ | 跨角色协作摩擦 | 「在需求、接口与页面之间来回拉扯」 |
| 闷头 + 动宾 | ★★★ | 埋头做低价值重复劳动 | 「闷头CURD」 |
| 上来就… | ★★ | 坏习惯的起手动作 | 「智能体有时会忘记查看文档，上来就自由发挥」 |
| 驾驭 AI / AI 驾驭者 | ★★★ | 人与 AI 的关系定位 | 「为了更好的驾驭AI」；「程序员从代码实现者升级为AI驾驭者」 |

## 6. 程度与评价词

| 词条 | 强度 | 语感 |
|---|---|---|
| 惊艳 | ★★ | 正向评价的最高档，用得很克制 |
| 基本达到 / 已经基本 | ★★ | 谨慎肯定的固定搭配：「已经基本达到了生产可用」 |
| 相对比较 | ★★ | 口头冗余型限定：「相对比较成熟完整」 |
| 显著 | ★ | 谈量化收益时用：「AI可显著降低开发成本」 |
| 可复制 / 可拓展 / 可上线 | ★★★ | 评价成果的标准四字：「可上线内部使用」「更加通用可拓展」 |

## 8. 并列与列举格式

- **三连列举 + "等"字收尾**：`表格/分页/筛选/表单/校验/弹窗等重复劳动`、`审批流、动态权限、嵌套关联等场景`
- **斜杠密集列举**（同一层级的名词用 `/` 挤在一起）：`用户/角色/权限`、`字典/枚举`
- **冒号并置短句**（提纲式结论）：
  > 文档为王：字段含义、枚举、校验、错误码完整定义，版本化与变更记录
  > 统一规范：稳定的React组件库与模板规范，给AI明确着陆面
- **编号**：`1. 2. 3.` 或 `•`，**不用**「首先/其次/再次/最后」
- **加粗小标题可带问号**：`**为什么选择后台管理系统？**`

## 9. 标点与排版习惯

| 项 | 习惯 |
|---|---|
| 引号 | 中文双引号 `""`，用于自造概念或需要距离感的词 |
| 破折号 | 高频使用 `——`，后接同位语或解释：「早已成为规范的契约——API文档」 |
| 括号 | 全角 `（）`，内嵌补充信息或举例：「（如Swagger）」「（这是一个面向网络运维同事的监控平台…）」 |
| 分号 | 几乎不用 |
| 感叹号 | 不用 |
| emoji | 不用 |
| 列表符号 | 文档开头偶用 `•`（复制自笔记软件），正式稿改 Markdown 列表 |
| 图表引用 | 图片后常跟一句「注意图中数据来自…，非真实线上数据」的免责说明——**可信度习惯** |
| 落款 | `Lerix` 换行 `2026.2.27 于 北京` |

## 10. 课程语料补充（site/ 现有 MDX，供对照）

> 迁移后的课程稿经过他人重写，只能作为"可接受的相近语体"参考，**不能**当成本人口癖来源。可迁移的三点：

- 因果链推进法：「RDMA 不能丢包 → 以太网默认会丢包 → 必须有机制兜底」（与 S1 的"痛点→限制→切入"同源）
- 比喻降维：`PFC = 消息队列的消费者反压搬到交换机链路`
- 自检收口：每节「本节目标」+「参考答案与评分维度」（对应 S1 的验证表）
