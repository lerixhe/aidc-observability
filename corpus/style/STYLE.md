## 一、一句话画像

**一个有一线后端/运维经验的工程师，用第一人称讲自己刚做完的一件事：先摆痛点，再给真实项目里的做法和数据，然后把做法抬成方法论，最后留一个下期钩子。**

语气自信但不吹，习惯自谦；爱打日常比方，成语与网络俗语混着用；技术判断落在可验证的证据上（效果图、验证表、局限说明），而不是形容词上。

三个稳定的底层偏好：

1. **反重复劳动**——「表格/分页/筛选/表单/校验/弹窗等重复劳动高、改动同步成本大」
2. **反屎山**——「防止代码堆砌逐渐腐化为"屎山"」
3. **挺规范与契约**——「文档为王」「让文档成为AI的行动指南」

## 二、篇章骨架（默认五段式）

| 段 | 中文序号标题 | 功能 | 写法要点 |
|---|---|---|---|
| 摘要 | `摘要：` 顶格一段 | 一句话说清「在什么前提下，用什么手段，拿到什么结果」 | 只有一个长句，含条件、手段、量化结果 |
| 一 | 缘起 | 痛点 → 转折 → 为什么是这件事 | 先讲自己的体验（"已经感受到了…"），再讲限制（"然而受限于…"），最后给出切入点的由来 |
| 二 | 实践 | 真实项目 + 工具版本 + 目标 + 成果 + 验证 | 一定要有：项目背景一句话、工具与模型版本、"实践目标"、效果截图、验证表 |
| 三 | 经验 | 3 条以内可复制做法 | 每条「问题 → 做法 → 截图或规则示例」，编号列表 |
| 四 | 思考 | 角色再定义 / 适用与局限 / 实施建议 | 三块固定，每块都用「A：… B：…」的并置短句 |
| 五 | 结语 | 一句判断 + 一句技能要求 + 下期预告 | 升华半段、拉回个人半段，末句常是"…这个问题我们下期接着聊" |
| 落款 | `Lerix` / `2026.2.27 于 北京` | 签名 + 日期 + 地点 | 日期不加"日"字，格式 `YYYY.M.D 于 城市` |

**节奏共识**：每一段内部都是「总 → 分（分点）→ 小结」，且小结句常单独成行、加粗或冠以"总结："。

## 三、句子与段落

### 3.1 长句 + 逗号链

典型句长 30–60 字，靠逗号串起 2–4 个分句，**很少用分号和冒号做结构分层**；一个句子里可以塞进"条件 + 手段 + 结果"三层。

> 在AI助力下，后端工程师在开发API时只需要维护高质量的API说明文档（如Swagger），即可利用智能体生成覆盖80%-90%需求的后台管理系统。

> 在日常使用AI编程时已经感受到了AI生成完整的小型项目时的惊艳效果，然而受限于AI上下文窗口的长度，在大型项目中的使用并不尽如人意，为了能更好的驾驭AI，让我开始琢磨如何在大型项目中找准它的定位。

注意第二句的链路：**体验 → 然而限制 → 为了……让我开始琢磨**。他的长句不是堆形容词，是堆**因果动作**。

### 3.2 短段

2–4 句一段，一个意思一段。转换话题直接另起一段，不写过渡句。

### 3.3 先口语、后术语

先用大白话说现象，再补术语或规范名词。

> 为了避免每次生成的代码像"抽盲盒"一样，风格不固定，技术栈不统一，这里我使用了〈某智能体插件的〉自定义智能体功能。

> ⚠️ 引用例句已脱敏：原文中的内部工具名、平台名、内网链接一律替换为 `〈内部…〉` 占位，句式与口气保持原样。

> 智能体有时会忘记查看文档，上来就自由发挥，导致生成效果不稳定。

### 3.4 三个起句习惯

- **"这里"开头引出自己的动作**：「这里我选择了…」「这里我用了…」「这里我简单提一下…」
- **"从…来看/方面来看"开头给出视角**：「从适用场景上来看」「从提效方面来看」
- **"另"/"另因"开头做补充**：「另因录屏帧数低展示较为卡顿」

### 3.5 转折与让步的四件套

| 用法 | 例句 |
|---|---|
| `然而 + 限制` | 然而受限于AI上下文窗口的长度，在大型项目中的使用并不尽如人意 |
| `当然，这并不意味着…` | 当然，这并不意味着B端没有复杂度——审批流、动态权限、嵌套关联等场景仍需人工介入。 |
| `貌似…但实际上…` | 貌似不需要在学习和掌握很多技术栈细节，但实际上手就会发现… |
| `与其…不如…` | 与其让后端和前端在需求、接口与页面之间来回拉扯，不如让AI把"后台管理系统"直接从API文档中生成出来。 |

### 3.6 「并不」句式

他偏爱用"并不"表达克制的否定，而不是"不"：**并不尽如人意**、**并不意味着**、**并不复杂**。

## 四、口癖清单（可检索的指纹）

> 完整词表见 [`LEXICON.md`](./LEXICON.md)。此处只列最像"他"的十个。

1. **驾驭 AI**——他描述人与 AI 关系的核心动词，反复出现：「更好的驾驭AI」「AI驾驭者」。
2. **找我/找准定位**——「如何在大型项目中找准它的定位」。
3. **"天然就是"**——一句顶三句的判断句式：「这份…文档天然就是一份AI行动指南」。
4. **自谦三连**——「老生常谈」「班门弄斧」「不再赘述」类词组，用于开头降低姿态：「相关工具也是五花八门，我就不再班门弄斧了」。
5. **抽盲盒**——形容结果不可预期的固定比喻。
6. **屎山**——形容代码腐化，带自嘲与警示双重意味。
7. **来回拉扯**——形容协作摩擦。
8. **上来就…**——形容坏习惯的动作起手式：「上来就自由发挥」。
9. **闷头 + 动宾**——形容埋头做低级劳动：「闷头CURD」。
10. **下期接着聊**——收尾钩子，明示这是连载。

另有口头冗余习惯（是风格的一部分，但正式稿建议适度收敛）：
- 数量词后带"一个"：「我们**一个**相对比较成熟完整的项目」「**一个**长句」
- "在学习和掌握"这类同义叠加
- 序列词只用「1. 2. 3.」或「•」，不用「首先/其次/再次」

## 五、修辞偏好

| 手法 | 说明 | 例 |
|---|---|---|
| 日常喻体解释技术不确定性 | 喻体都来自生活或工地，不用科幻/战争比喻 | 抽盲盒、屎山、来回拉扯 |
| 概念降维 | 把新概念挂到读者熟悉的对象上 | 文档 = AI 的行动指南 |
| 名词化压缩 | 四字或「X + Y」造复合词当结论用 | 文档为王、验证闭环、人工兜底、人机循环、规范驱动 |
| 加号并列 | 三个短词用 `+` 串成方法论公式 | 规范驱动 + 智能生成 + 人工兜底 |
| 引号加冕 | 用中文双引号 "" 标记自造概念或需要距离感的词 | "后台管理系统"、"抽盲盒"、"屎山" |
| 破折号补充定义 | `——` 后面跟同位语或解释 | 早已成为规范的契约——API文档 |
| 三连/四连排比 | 同类短句并列，多为动宾结构，收在"等"字上 | 表格/分页/筛选/表单/校验/弹窗**等**重复劳动；审批流、动态权限、嵌套关联**等**场景 |
| 角色转变句式 | 「从 A 升级为/转向 B」几乎必用于谈分工 | 从"闷头CURD"升级为"按业务实现接口和合约" |

## 六、标题与小标题

- **一级标题 = 中文数字 + 两字文言词**：`一、缘起` `二、实践` `三、经验` `四、思考` `五、结语`。这份"八字"是他文章的骨架签名。
- **小标题加粗成句，可以带问号或判断**：`**为什么选择后台管理系统？**`、`**AI时代，分工角色再定义**`、`**适用场景与局限**`。
- 段落内的并列项也用加粗短语打头：`适用：… 局限：…`、`文档为王：… 统一规范：… 验证闭环：… 增量部署：…`
- **零 emoji、零感叹号**。强调靠加粗和引号，不靠标点和表情。

## 七、技术写作约定

- 中文全角标点；**英文技术词保留原形**（Swagger、OpenAPI、CRUD、RBAC/ABAC、react、ant）。
- 中英混排不加空格，甚至用中文逗号连接英文词：`技术栈选型： react，ant`——是他的真实习惯，但在课程/正式稿中建议改为规范写法。
- 代码、文件名、字段名用反引号：`doc.json`、`page_size`、`ReqBodyBatchIDs`。
- 代码块带语言标记，且**注释用中文**。
- 指标写法：区间用半角连字符不带空格（`80%-90%`、`10%-20%`）；阈值、版本号原样保留（`〈插件名〉 3.8.15`、`〈模型名〉-K0905`）。
- 允许少量笔误与口语冗余（`闷头CURD`、"传统前后端模式开发模式"）——是真实感来源，但**正式课程稿要校对掉**。

## 八、立场与价值观（决定"写什么"）

- **方法必须可复制**：给规则文件示例、给设置截图，不给"多思考、多练习"。
- **效果必须可验证**：用「验证项 / 结论」表格收口，明确说"经测试存在部分bug，经人机循环处理解决"——不回避缺陷。
- **主动划边界**：讲完能力立刻讲局限（"这并不意味着B端没有复杂度"），可信度来自承认不适用处。
- **对 AI 工具理性**：既说"惊艳"，也说"受限于上下文窗口"；不神化，不唱衰。
- **技术收益落到工程量纲**：缺陷率、改动量、时长、覆盖百分比。
- **对读者的姿态是同行，不是老师**：说"我就不再班门弄斧了"，不说"大家一定要记住"。

## 九、不要写什么（失真警戒线）

写出下面这些，就不像他了：

- ❌ 空洞口号与宏大预测（"AI 将彻底颠覆一切"）
- ❌ 网络亲昵语（家人们、宝子们、绝绝子）与 emoji、感叹号连用
- ❌ 无证据的效果承诺（"效率提升十倍"却不给场景和度量）
- ❌ 三段形容词堆砌（"强大、高效、智能的解决方案"）
- ❌ 自我介绍式权威背书（"作为深耕十年的专家"）
- ❌ 每段都排比、每句都加粗的用力过猛——他的排比是**局部**的，密度约每节一处

## 十、用于课程材料时的适配规则

课程稿与博客稿不是同一语体，移植时按下面处理：

| 博客里的 | 课程里改成 |
|---|---|
| 第一人称履历（"这里我选择了我们一个项目"） | 第二人称 + 场景化（"设想你手上有一份 Swagger 文档"）——遵循 `docs/MIGRATION.md` 第二节 |
| 内部平台名 / 厂商名 / 截图 | 泛化描述或删除，遵守脱敏红线 |
| 自谦套话（班门弄斧、老生常谈） | 每课最多留 1 处，否则发腻 |
| 「验证表」 | **保留并强化**：课程每节末尾给"自检维度 + 参考答案" |
| 「下期接着聊」 | 保留为"下一课"钩子 |
| 日常比喻 | **优先保留**，这是最值得迁移的部分（把 PFC 比作消息队列反压，正是同一种手法） |
| 长逗号链 | 课程里可拆成两句，但保留"因果动作"链，不要写成定义式短句堆 |

一句话原则：**移植他的"节奏、比喻、验证癖"，去掉他的"履历、内部信息、自谦"**。
