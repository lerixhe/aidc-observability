# 01-traffic-model · 同平均负载，不同到达形态

> **教学级模型，非硬件行为等价。** 它生成的是到达率序列，不是报文。
> 用来建立「平均负载骗人」的直觉，不能替代真机抓包。

## 1. 这个 lab 做什么

锁住一个变量：**平均负载都是 20 GB/s**。然后换掉到达形态：

- 传统 IDC：泊松到达 + 对数正态流大小，每条流受端口线速约束
- AllReduce：周期性同步突发，通信期四条链路全速汇聚

同样 20 GB/s，两种流量的瞬时形态差 5 倍。你要亲手算一遍「分钟级轮询能看见什么」。

对应课程：[02 为什么 AI 训练网络和 IDC 网络不一样](../../site/docs/01-paradigm/02-why-different.md)。

## 2. 跑起来

需要 Go 1.22 以上，无第三方依赖。

```bash
cd labs/01-traffic-model
make run    # 打印统计、轮询失真表、时序火花线，写 out/traffic.csv
make test   # 7 个单测
```

## 3. 默认场景

| 参数 | 值 | 意思 |
|---|---|---|
| 观测时长 | 20 s | 够看清 100 个训练步 |
| 平均负载 | 20 GB/s | 两种模型都对齐到这个值 |
| 单端口线速 | 25 GB/s | 200 Gbps |
| worker 数 | 4 | 四条链路汇聚到一个出端口 |
| 训练步周期 | 200 ms | 其中 40 ms 在通信，占 20% |
| IDC 流大小 | 中位数 64 KB，sigma 1.5 | 对数正态长尾 |

AllReduce 的通信阶段长度不是拍脑袋写的，是从平均负载反推的：
`40 ms = 200 ms × 20 GB/s ÷ (4 × 25 GB/s)`。想改平均负载，通信时长会跟着变。

## 4. 看什么

```
统计量（GB/s）                  idc 小流 AllReduce 同步突发
平均负载                         20.1       20.0
P50                          20.2        0.0
P90                          25.0      100.0
峰值                           25.0      100.0
峰值 / 均值                       1.2        5.0
空闲时间占比                         0%        80%
```

四个数字，每个都能对应课程里一句话：

1. **平均负载一样**（20 vs 20）：老面板的第一个数字永远是绿的。
2. **P50 一个 20、一个 0**：AllReduce 一半以上的时间网络是空的，因为 GPU 在算梯度。
3. **峰值 / 均值 1.2 vs 5.0**：IDC 的峰值被端口线速封顶，智算的峰值是线速的 4 倍。
4. **空闲 0% vs 80%**：同步性。一个摊平，一个齐步走。

## 5. 轮询失真表

```
采样窗口               idc 小流     AllReduce 同步突发 对 AllReduce 的判断
1 ms                25.0             100.0   看得见突发
10 ms               25.0             100.0   看得见突发
100 ms              22.1              40.0   看得见突发
1 s                 20.5              20.0   峰值被低估
10 s                20.1              20.0   峰值被低估
```

一张表说明为什么分钟级 SNMP 轮询在智算网络里失效：

- 1 ms 窗口看到 100 GB/s，是线速的 4 倍，你立刻知道出事了
- 100 ms 窗口看到 40 GB/s，已经吃掉一半峰值
- **1 s 窗口看到 20 GB/s，比端口线速 25 GB/s 还低，面板判定"不拥塞"**

而 1 s 是很多 SNMP 采集的乐观值，实际常见 30 s 到 5 min。那时的读数就是一条水平线，
永远等于平均负载。

这就是课程里那句话的机器版：**"轮询看到的只是平均值永远正常"**。

想自己验证：

```bash
go run . -step-ms 500   # 拉长训练步，1 s 窗口反而能看见突发
go run . -mean 12       # 降低平均负载，看 P99 的变化
go run . -flow-sigma 2.5  # 加重 IDC 的长尾，看排队效应
```

## 6. 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-duration-ms` | 20000 | 观测时长 |
| `-mean` | 20 | 目标平均负载 GB/s，两种模型对齐 |
| `-port` | 25 | 单端口线速 GB/s |
| `-workers` | 4 | AllReduce 并发 worker 数 |
| `-step-ms` | 200 | 训练步周期 |
| `-flow-median-kb` | 64 | IDC 流大小的中位数 |
| `-flow-sigma` | 1.5 | 对数正态 sigma，控制长尾 |
| `-seed` | 42 | 随机种子，固定种子结果可复现 |

## 7. 思考题

1. 把 `-step-ms` 设成 60，`-workers` 设成 8，重算通信阶段长度和峰值倍数。
   AllReduce 的峰值能超过端口线速多少倍？
2. 如果把轮询窗口固定成 1 s，什么样的训练步周期才能让突发重新可见？
   算一下这个周期的物理含义（一次 AllReduce 要跑多久）。
3. IDC 那一列 P90 打到了 25 GB/s，也就是端口满速。这算不算「偶发拥塞」？
   它和 incast 的区别在哪里？
4. 这张表里没有「时延」。加上时延维度后，1 s 窗口的失真会不会更严重？

## 8. 模型边界

- **没有报文**：只算到达率，看不到包大小、乱序、ECN 标记
- **单端口视角**：AllReduce 的「四条链路汇聚到一个出端口」是聚合后的视角，
  真实 incast 里每条链路各自也有细节
- **排队模型很粗**：IDC 只做「到达 → 按线速摊平」，没有真实队列调度
- **AllReduce 太规整**：真实训练的通信阶段有 Ring / Tree 之分，还有 straggler 导致的不齐步
- **没有光层、没有拥塞控制**：这里只问「来了多少」，不问「怎么挤」

## 9. 一条坑

IDC 模型的单位换算踩过一次：`MeanGBps / 1000` 换成 GB/ms 忘了，
lambda 直接放大 1000 倍，端口被 11 万条流一秒灌满，曲线看起来"很真实"，
其实全错。

改模型时先对着这一行算一遍：`110 流/ms × 182 KB/流 = 20 MB/ms = 20 GB/s`。
数字对得上，量纲才对得。
