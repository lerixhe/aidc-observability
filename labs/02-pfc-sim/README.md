# 02-pfc-sim · 参数化队列模型

> **教学级模型，非硬件行为等价。** 它把 PFC / ECN / DCQCN 的判定逻辑跑成时序，
> 用来建立指标直觉和参数敏感度，不能替代真机验证。真机路径见第 8 节。

## 1. 这个 lab 做什么

搭一台交换机、四条上游链路，让它们一起往一个出端口灌流量。你能看到：

- PFC 的水线判定怎么把「丢包」换成「堆积」
- ECN 三段水线与 DCQCN 闭环怎么把 PFC 触发次数压下去
- 队头阻塞怎么让无辜流陪绑
- pause 帧传播延迟怎么吃掉缓冲余量

对应课程：[05 PFC](../../site/docs/02-lossless/05-pfc.md)、
[06 ECN + DCQCN](../../site/docs/02-lossless/06-ecn-dcqcn.md)、
[07 四大典型故障](../../site/docs/02-lossless/07-fault-modes.md)。

## 2. 跑起来

需要 Go 1.22 以上，无第三方依赖。

```bash
cd labs/02-pfc-sim
make run       # 默认场景：incast + PFC，打印摘要 + 火花线 + 写 out/timeseries.csv
make compare   # 六种配置横向对比，一张表看完
make test      # 7 个单测，覆盖水线判定、反压解除、DCQCN 效果、HoL
```

## 3. 模型怎么建的

单位统一：时间 μs，数据量 KB（十进制），速率 KB/μs。**1 KB/μs = 1 GB/s = 8 Gbps**，
所以 200 Gbps 端口 = 25 KB/μs。

| 模型里的东西 | 真实世界里对应什么 |
|---|---|
| `ingress[i]` 缓冲 | 交换机入方向 per-priority 缓冲，PFC 水线就看它 |
| `egress` 共享缓冲 | 出端口队列，ECN 水线看它 |
| `events` 事件队列 | pause 帧的传播延迟，`-pause-delay` 控制 |
| `srcBacklog[i]` | 源端网卡里待发但被反压挡住的数据 |
| `srcRate[i]` | DCQCN 的 RP 角色：收到 CNP 就降速 |

时间步长固定 1 μs，流量按 KB 连续计数，即**流体近似**：不逐包模拟。
代价是看不到包边界效应，收益是参数含义一目了然。

三种流量模式：

| 模式 | 像什么 | 平均负载 | 关键观察点 |
|---|---|---|---|
| `incast` | AllReduce 同步突发，每周期集中发一小段 | 出端口的 80% | PFC 帧数与反压覆盖率 |
| `idc` | 传统 IDC 大量小流随机到达 | 出端口的 80% | 队列几乎不堆，PFC 零触发 |
| `hol` | 一半流量去慢目的地，一半去健康目的地 | 超出出端口 4 倍 | 无辜流的达成率 |

## 4. 五个实验

### 实验一：把 IDC 面板搬到智算网络

```bash
make compare
```

看第 1 行和第 3 行。两者平均负载都是出端口的 80%，结果完全不同：

```
idc 小流 · 无 PFC             丢弃 0 KB   pause 0 帧   覆盖率 0%    利用率 78%
incast · PFC                  丢弃 0 KB   pause 360 帧 覆盖率 53%   利用率 80%
```

小流被排队统计摊平，队列涨不到反压水线。同步突发每周期把队列顶到 XOFF，
反压覆盖率一半以上。**同样的平均负载，指标形态差一个量级**：这就是老面板测不出
PFC 风暴的原因。

### 实验二：PFC 把丢包换成了堆积

```bash
go run . -mode incast -pfc=false -duration 1000
go run . -mode incast -pfc=true  -duration 1000
```

关掉 PFC 丢 9170 KB，打开丢 0 KB。代价是反压覆盖率从 0 变成 53%，`ingress` 水位
长期贴在 XOFF 之上。丢包率是 0，但网络很慢：出口利用率还是 80%，等待都在缓冲里。

课程里那句话在这里能看见：**"无损"不是没代价，是把丢弃成本换成了排队成本。**

### 实验三：ECN 是主防线，PFC 是最后防线

```bash
go run . -mode incast -pfc=true -dcqcn=true -duration 1000
```

开 DCQCN 后，pause 帧从 360 掉到 60，反压覆盖率从 53% 掉到 7%，ECN 标记率从 98%
降到 32%。三件事同时发生：队列在 Kmin 附近就被压住，没走到 XOFF，丢包仍然为零。

**判读顺序**：ECN 标记率先动（领先指标）→ PFC pause 帧次动（滞后）→ 丢包是事故确认。
这个三级分级是第 6 课的核心结论。

### 实验四：队头阻塞

```bash
go run . -mode hol -duration 500
```

两条流共享一个无损队列。F1 去慢目的地（只吃得下 20% 带宽），F2 去健康目的地。
出口总带宽 25 KB/μs，F2 自己就能用满 20 KB/μs。

```
F1 慢目的地   需求 25000 KB   送出 2490 KB   达成率 10.0%
F2 无辜流     需求 25000 KB   送出 2672 KB   达成率 10.7%
```

F2 拿到 10.7%，和真正的罪魁祸首一样惨。原因不是 F2 自己的路径有问题，是
**共享队列 + 逐跳反压**：F1 顶起水位触发 pause，上游整条优先级队列被冻，F2 一起停。
出口利用率只剩 41%，一半以上带宽被白白闲置。

这就是「症状现场 ≠ 根因现场」的机器版演示：`F2 收不到数据` 的真凶在 `F1 的目的地`。

### 实验五：pause 延迟吃掉缓冲余量

```bash
go run . -pause-delay 40 -duration 1000
```

pause 帧要 40 μs 才传到上游，这 40 μs 里四条链路还在全速发，在途 4000 KB 撞进
只有 1024 KB 的缓冲，丢 7170 KB。延迟从 2 μs 拉到 40 μs，一个看似无害的参数把
无损网络变成了有损网络。

工程推论：**缓冲要按 pause 传播延迟 × 线速来配**，不是按业务平均 BDP 配。
XOFF 水线同理，要留出在途流量的余量，否则每次反压都会先丢一包。

### 实验六：watchdog 介入，无损网络变有损

```bash
go run . -mode hol -ignore-pause -quota 500 -watchdog 200 -duration 2000
```

`-ignore-pause` 模拟一种真实事故：上游网卡的 PFC 配置跟交换机对不上，**收到 pause 帧不当回事**，
继续满速发。队列于是永远满，switch 反复续期暂停，卡在那里。

```
溢出丢弃                      178622 KB
PFC pause 帧                      40
反压覆盖率                        95.9%
最长连续暂停                       201 μs
watchdog 触发                      36
```

watchdog 每 200 μs 强制解除一次，顺手把该队列积压丢掉。36 次触发，丢掉 178 MB。
**"无损"在工程上是概率承诺，不是绝对保证**：配置错了，watchdog 会用丢包保住整网活性。

对照第 7 课的四类故障，这条路径属于「配置不一致导致的 PFC 死锁」，
处置动作就是修配置 + 接受 watchdog 兜底期间的那点丢包。

## 5. 调参速查

| 参数 | 真实世界对应 | 调大之后 |
|---|---|---|
| `-xoff` | 交换机 XOFF 高水线 | 反压更晚触发，缓冲吃更多突发，丢包风险上升 |
| `-xon` | XON 低水线 | 解冻更早，反压震荡变频繁 |
| `-quota` | pause 帧时间配额 | 单次冻结更久，帧数下降但延迟上升 |
| `-pause-delay` | pause 帧传播与生效延迟 | 在途流量变多，缓冲余量被吃 |
| `-kmin/-kmax` | ECN 标记水线 | 标记更晚，PFC 承担更多 |
| `-ingress-buf` | 交换机入方向缓冲 | 突发吸收能力变强，PFC 更少，时延更大 |
| `-slow` | 慢目的地能吃的带宽比例 | 队头阻塞更严重 |
| `-watchdog` | PFC watchdog 阈值 μs | 更早强制解除暂停，丢包换活性 |
| `-ignore-pause` | 上游忽略 pause 帧（配置错误） | 队列永满，watchdog 反复介入 |

## 6. 思考题

1. `-ingress-buf` 从 256 KB 调到 2048 KB，PFC 帧数会掉到接近 0，丢包也是 0。
   网络变健康了吗？如果没有，代价记在谁的账上？
2. 实验三里 ECN 标记率还有 32%。能不能压到 0？压到 0 意味着什么？
3. `-ignore-pause` 下把 `-watchdog 0` 关掉跑一遍。最长连续暂停变成多少？
   此时网络还算「通」吗？watchdog 丢掉的流量该记在谁的账上？
4. 实验六里 `-quota` 设成 500 μs，watchdog 阈值 200 μs。如果反过来
   （quota 100、watchdog 500），watchdog 还会触发吗？为什么？
5. 模型里 pause 帧只发给直连上游一跳。如果真实拓扑是三跳（网卡 → leaf → spine → leaf），
   延迟该按几倍算？

## 7. 模型边界

跑出来的数字能说明机制方向，不能用来定参数。刻意简化的地方：

- **流体近似**：没有包边界、没有逐包排队、没有 PFC 帧的 per-quantum 位图语义
- **单优先级**：只有一条无损队列，演示不了 8 个队列间的调度与互相挤占
- **单跳**：PFC 逐跳传播简化成「上游一跳」，多跳的暂停波累积效应看不到
- **DCQCN 是简化版**：只有「收 CNP 降速 + 定时恢复」，没有 alpha 平滑、
  没有 RP 的 timer 状态机、没有 NP 的控制频率
- **ECN 是确定性比例**：按水位算概率直接乘字节数，不是逐包随机标记
- **交换机内部无阻塞**：fabric 带宽设成端口数 × 线速，永远不是瓶颈
- **单交换机，无环形依赖**：真实的 PFC 死锁需要多跳成环，本模型只能用 `-ignore-pause`
  模拟「上游不听话」这一种触发条件，watchdog 的环路打断逻辑没有实现

## 8. 真机怎么验

主机侧：

```bash
# pause 与丢弃计数，重点看按优先级的 pause 计数
ethtool -S <ifname> | grep -Ei 'pause|prio.*pause|discard|out_of_buffer'
# 当前哪些优先级开了 pause
mlnx_qos -i <ifname> --show
```

交换机侧（CLI 语义随平台不同，看指标不看命令）：

```text
show priority-flow-control interface <intf>
show queue-monitor
```

对照验证路径：

1. 多打一复现 incast：`ib_write_bw` 或 `iperf3`，四条上游同时打到一条下游
2. 逐步调低 XOFF 水线，观察 pause 帧计数增长与吞吐下降的关系，和 `-xoff` 的曲线对照
3. 打开 ECN 与 DCQCN，重跑第 1 步，pause 帧数应显著下降，和实验三对照
4. 给慢目的地挂一个 tc/netem 限速，复现队头阻塞，看同队列其他流的吞吐

## 9. 一条坑

pause 配额到期必须续期。模型早期版本让 quota 自然到期，每次到期都相当于给上游开了
一个小窗口，在途流量正好把缓冲顶爆，于是你会看到「有 PFC 却仍在丢包」这种假故障。

真实设备会周期性重发 pause 帧，只要水位没降到 XON 就不松口。改模型时，
`checkPause` 里那个 `pauseUntil-t < 2*PauseDelay` 的分支就是干这个的，别删。
