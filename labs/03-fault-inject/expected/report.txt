== storm · 注入计划 ==
PFC 风暴：反压沿拓扑向上游蔓延，零丢包但区域性变慢

窗口 240 秒 · 采样 8.0 秒 · 劣化起点 25% 处（第 60 秒）

拓扑：h1 h2 ── leaf1 ── spine1 ── leaf2 ── h3(慢) h4(健康)

次序  节点     动作                                                  命令
----  -------  ----------------------------------------------------  ----
 1    leaf2    上行口做成大缓冲 + 低于需求的带宽：丢包被换成堆积，等效 PFC 的反压效果               tc qdisc replace dev eth1 root tbf rate 40mbit burst 256kb latency 400ms
 2    h3       接收端起服务                                                iperf3 -s -1 -D
 3    h1       两条大象流合起来超过上行带宽，队列开始常驻高位                               iperf3 -c 10.0.3.2 -t 240 -b 30M -l 64K -D
 4    h2       第二条流，把过载推过阈值                                          iperf3 -c 10.0.3.2 -t 240 -b 30M -l 64K -D
 5    leaf2    看 backlog 与 drops：无 drops、backlog 常驻高位就是「丢包被换成堆积」     tc -s qdisc show dev eth1
 6    leaf1    上游侧看到的是出口排队引起的时延抬升                                    tc -s qdisc show dev eth3

判读要点（真机上该看到什么）：
  - 丢包率全程为 0，这是 PFC 家族的第一指纹
  - pause 时长在多个端口同时抬到 5% 以上，且方向沿拓扑向上游扩散
  - 时延台阶式抬升后不回落到基线，说明根因没消除
  - 队列水线常驻 80% 以上，与 pause 同步而非滞后

真机等价做法（容器里造不出来的部分）：
  - 上游交换机按优先级开 PFC，XOFF 阈值设 40–50% 缓冲
  - `show priority-flow-control interface <intf> counters` 看 per-priority pause 帧数与时长
  - 把 pause 时长换算成占空比：10 分钟窗口里超过 10 秒即为严重

清理：make destroy   # 或 docker exec <节点> tc qdisc del dev <if> root

leaf2:eth1    culprit      0.24      0.28    0   0.00     8.5   3.72     102
leaf2:eth2    victim       0.23      1.23    0   0.00     7.4   3.00      88
leaf1:eth3    victim       0.23      1.13    0   0.00     6.6   2.51      73
leaf1:eth1    healthy      0.22      0.23    0   0.00     0.1   0.10       8

== 判读结论：PFC 风暴（置信度高）==
特征：端口 4 个 · 劣化 3 个 · 超时占比 0% · loss 峰值 0.00% · pause 峰值 8% · ECN 峰值 3.7% · 时延 5.5 倍
劣化端口：leaf2:eth1、leaf2:eth2、leaf1:eth3

依据：
  - 丢包率峰值 0.00%：全程不丢包
  - pause 占空比峰值 8%，平均 3.9%
  - 时延抬到基线 5.5 倍，劣化端口 3/4，成片蔓延

下一步：
  - 逐跳拉 per-priority pause 计数，找第一个「pause 涨但入流量正常」的设备
  - 核对这几跳的 PFC 水线与优先级配置是否一致
  - 确认源头那个消费不动的端口，而不是拥塞端口

== deadlock · 注入计划 ==
PFC 死锁：双向互等，报文卡在队列里永远出不去

窗口 120 秒 · 采样 4.0 秒 · 劣化起点 25% 处（第 30 秒）

拓扑：h1 h2 ── leaf1 ── spine1 ── leaf2 ── h3(慢) h4(健康)

次序  节点     动作                                                  命令
----  -------  ----------------------------------------------------  ----
 1    leaf2    上行限到极低带宽，逼出持久反压                                       tc qdisc replace dev eth1 root tbf rate 2mbit burst 32kb latency 10s
 2    leaf1    反方向也压，形成互相等待的环                                        tc qdisc replace dev eth3 root tbf rate 2mbit burst 32kb latency 10s
 3    h3       接收端起服务                                                iperf3 -s -1 -D
 4    h1       正向流与被压的反向流同时占着缓冲                                      iperf3 -c 10.0.3.2 -t 120 -b 20M -l 64K -D || true
 5    h3       反向流：谁也不让，谁也不走                                         iperf3 -c 10.0.1.2 -t 120 -b 20M -l 64K -D || true
 6    leaf2    看队列是否卡死在满水位、drops 是否为 0                               tc -s qdisc show dev eth1
 7    h1       应用侧表现是全部超时，不是部分丢包                                     ping -c 5 -W 2 10.0.3.2 || true

判读要点（真机上该看到什么）：
  - 时延直接超时，报文根本没被丢，而是排队排到永远
  - 丢包率为 0 与超时并存，这是无损网络特有的矛盾组合
  - pause 占空比顶到 90% 以上，ECN 归零（流已经不动了，没人再被标记）
  - 下游还没死，健康端口照常工作：故障范围由环决定，不是由流量决定

真机等价做法（容器里造不出来的部分）：
  - `show priority-flow-control watchdog` 确认死锁检测是否开启
  - 交换机上查 stuck 队列与永久 XOFF 的端口
  - 环检测：把「暂停方向」画成有向图，找强连通分量

清理：make destroy   # 或 docker exec <节点> tc qdisc del dev <if> root

端口          角色      基线p99  峰值p99   超时  loss%   pause%  ecn%   队列KB
leaf2:eth1    culprit      0.23        超时   22   0.00   100.0   0.10     104
leaf2:eth2    victim       0.22        超时   22   0.00   100.0   0.10     104
leaf1:eth3    victim       0.22        超时   22   0.00   100.0   0.10     100
leaf1:eth1    healthy      0.23      0.23    0   0.00     0.1   0.10       8

== 判读结论：PFC 死锁（置信度高）==
特征：端口 4 个 · 劣化 3 个 · 超时占比 55% · loss 峰值 0.00% · pause 峰值 100% · ECN 峰值 0.1% · 时延 1.1 倍
劣化端口：leaf2:eth1、leaf2:eth2、leaf1:eth3

依据：
  - 超时样本占比 55%，但丢包率峰值只有 0.00%
  - pause 占空比峰值 100%，队列顶到 104 KB
  - 报文没被丢，而是排队排到出不去 —— 无损网络特有的矛盾组合

下一步：
  - 查 PFC watchdog 是否开启，有无 stuck 队列事件
  - 把暂停方向画成有向图，找强连通分量定位环
  - 先做端口隔离止血，再改 PFC 水线与拓扑

== incast · 注入计划 ==
incast：多打一，汇聚口周期性冲高，丢包与 ECN 同时出现

窗口 40 秒 · 采样 0.5 秒 · 劣化起点 10% 处（第 4 秒）

拓扑：h1 h2 ── leaf1 ── spine1 ── leaf2 ── h3(慢) h4(健康)

次序  节点     动作                                                  命令
----  -------  ----------------------------------------------------  ----
 1    leaf2    汇聚口限速：多打一时这里必然溢出                                      tc qdisc replace dev eth2 root tbf rate 25mbit burst 32kb latency 20ms
 2    h3       接收端起服务                                                iperf3 -s -1 -D
 3    h1       两个发送端同一时刻打同一个目的地                                      iperf3 -c 10.0.3.2 -t 40 -b 20M -l 4K -D
 4    h2       第二条汇聚流                                                iperf3 -c 10.0.3.2 -t 40 -b 20M -l 4K -D
 5    leaf2    看 dropped 与 backlog 的周期性：与 iperf3 的突发节奏同步             tc -s qdisc show dev eth2
 6    h1       从发送端看：重传与 RTT 的周期性尖刺                                  ss -tin dst 10.0.3.2

判读要点（真机上该看到什么）：
  - 丢包率非零，只在尖刺窗口里非零，这是与 PFC 家族的分水岭
  - 队列与 ECN 尖刺的周期等于训练步的周期，可用日志对齐验证
  - 受影响路径集合随时间稳定，指向少数汇聚点，不是成片蔓延
  - 汇聚点上游的全部发送端都被波及，但各自的问题程度不同

真机等价做法（容器里造不出来的部分）：
  - 汇聚设备上按队列看 ECN 标记率、PFC 触发次数、discard
  - 与训练 step 时间线对齐：能对齐的是 incast，不能的是风暴
  - 调小上行突发：`-l 4K` 改小、增加并发数，观察尖刺是否变陡

清理：make destroy   # 或 docker exec <节点> tc qdisc del dev <if> root

== 判读结论：incast（多打一）（置信度高）==

劣化端口：leaf2:eth2、leaf1:eth1、leaf1:eth3

依据：
  - 丢包率峰值 1.49%，出现在周期性尖刺里，间隔约 4.0 秒
  - ECN 标记率峰值 5.5%，队列峰值 104 KB
  - 劣化端口 3/4，方向指向汇聚点而非成片蔓延

下一步：
  - 拿尖刺时间点与训练 step 日志对齐，确认是同步突发
  - 查汇聚设备的 ECN / PFC / discard 三级指标，确认机制是否在工作
  - 考虑增大汇聚口缓冲、打开 ECN 并把 Kmin 调低

== hol · 注入计划 ==
队头阻塞：共享瓶颈上的无辜流被大象流拖慢

窗口 240 秒 · 采样 8.0 秒 · 劣化起点 10% 处（第 24 秒）

拓扑：h1 h2 ── leaf1 ── spine1 ── leaf2 ── h3(慢) h4(健康)

次序  节点     动作                                                  命令
----  -------  ----------------------------------------------------  ----
 1    leaf2    共享上行做成瓶颈，队列只有一个                                       tc qdisc replace dev eth1 root tbf rate 40mbit burst 128kb latency 200ms
 2    h3       慢目的地起服务                                               iperf3 -s -1 -D
 3    h4       健康目的地起服务                                              iperf3 -s -1 -D
 4    h1       肇事大象流：吃满共享队列                                          iperf3 -c 10.0.3.2 -t 240 -b 38M -l 64K -D
 5    h2       无辜小流：目的地健康，却和肇事流排同一个队列                                iperf3 -c 10.0.4.2 -t 240 -b 1M -l 4K
 6    leaf2    看共享口的 backlog：两条流的水都在这里                               tc -s qdisc show dev eth1
 7    h2       无辜流的 RTT 与重传，是它「清白」的证据                                ss -tin dst 10.0.4.2

判读要点（真机上该看到什么）：
  - 丢包率接近 0，时延只是温和抬升（1.5–2.5 倍），不像风暴那样成片
  - 受害端口与肇事端口共享同一段，其余各段全部正常
  - pause 与 ECN 都低：机制没有失效，只是队列在排队
  - 设备级均值看不出问题，只有路径级数据能证明「这条路径除了共享段以外都干净」

真机等价做法（容器里造不出来的部分）：
  - 端口上开 INT，看逐跳时延：集中在共享段那一跳
  - 按流的路径做时间相关性分析，确认受害流与肇事流同时进出同一队列
  - 考虑 per-flow 队列或更大 hash 熵，减少共享

清理：make destroy   # 或 docker exec <节点> tc qdisc del dev <if> root

劣化端口：leaf2:eth1、leaf2:eth3、leaf2:eth2

依据：

  - pause 与 ECN 都低（3.2% / 1.0%）：机制没失效，只是队列在排队
