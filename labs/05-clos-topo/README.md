# 05-clos-topo · ECMP 极化

> **教学级实验，非硬件行为等价。** 这里的散列复刻是 Jenkins lookup3 加内核同款选择方式，
> 输入拼装顺序与内核版本有关，绝对值不必对齐。要看的不是某个具体数字，
> 而是「哪种口径、多少条流，会让两条等价上行一条吃满、一条闲着」。

## 1. 这个 lab 做什么

Clos 上联做到 1:1 无收拢，不代表两条上行会各吃一半。
数据面按 5 元组算 hash，再对链路数取模。取模天生不公平，流少的时候尤其明显。

这个 lab 量三件事：

| 实验 | 变量 | 结论一句话 |
|---|---|---|
| 一 | 流数 8 → 2048 | 流越少，极化越重。两千条流才贴近均分 |
| 二 | hash 口径 L3 vs L4 | 三层口径下同一对主机的连接全撞一条路 |
| 三 | 同质大象流 | 5 元组一模一样时，任何口径都救不了，得靠拓扑结构 |

对应课程：[09 万卡集群拓扑](../../site/docs/03-traffic-topo/09-topology.md)。
那一课讲 rail-optimized 拓扑为什么这样设计，这个 lab 给出量化理由。

## 3. 三个实验怎么读

### 实验一：流数决定均匀度

```text
流数    leaf1     leaf2     leaf3     leaf4     最差极化度  CV     判定
8       2:0       0:2       0:1       1:1       2.00        0.87   严重不均
2048    222:198   249:220   213:205   230:230   1.06        0.04   可接受
```

极化度 = 最忙那条上行的占比 ÷ 均分时应有的占比。1.0 完美，2.0 是「两条只用一条」。

八条流时 2.00 不奇怪：你在用八次抽样去逼近 50%。这是样本量问题，不是算法问题。
**把这条记住，能省掉一次误判：少流的集群里看到 70/30，先数流，别先怀疑交换机。**

### 实验二：口径决定有没有得选

```text
口径               最差极化度  CV     最大链路占比
L3（src/dst IP）     2.00        1.00   100%
L4（五元组）         1.09        0.09   54.7%
```

三层口径下，端口根本不参与散列。同一对主机的一百条连接，全部走同一条上行。
不是「散得不好」，是**只有一维输入，等价于只有一条路**。

开关在 `net.ipv4.fib_multipath_hash_policy`：0 走三层，1 走四层。
默认值随发行版变，接手集群第一件事是确认它，不要猜。

### 实验三：hash 救不了的场合

```text
口径               最差极化度  CV     最大链路占比
L3（src/dst IP）     2.00        1.00   100%
L4（五元组）         2.00        1.00   100%
```

5 元组完全相同的流，两种口径都判同一条路。输入没有新信息，算法无从选择。

训练流量恰好长这样：rail 对齐的 AllReduce，5 元组在整个训练周期不变。
所以智算网络靠结构而不是靠 hash：**rail-optimized 拓扑把流量预先分到不同轨道**。
hash 能做的是「多流之间摊平」，做不了「一条流自己分叉」。
后者要靠 flowlet 交换或自适应路由，那是另一层机制。

## 4. 拓扑

```text
        spine1        spine2
          │ │           │ │
   ┌──────┴─┴───────────┴─┴──────┐
 leaf1  leaf2  leaf3  leaf4
   │      │      │      │
 h1 h2  h3 h4  h5 h6  h7 h8
```

每台 leaf 两条等价上行，各自 /30 直连一台 spine。
下挂的两台主机做二层桥（br0），上行做三层 ECMP。

地址表：

| 段 | 用途 |
|---|---|
| `10.11.N.0/24` | leafN 的下行，leaf 侧 .1，主机 .10 / .11 |
| `10.12.N.0/30` | leafN 到 spine1，leaf .1，spine .2 |
| `10.13.N.0/30` | leafN 到 spine2，leaf .1，spine .2 |

接口与地址的对照表在 [topo.clab.yml](topo.clab.yml) 开头，与 [flows.go](flows.go)
里的 `Uplinks()` 保持同步，改一处必改另一处。

## 5. 真机上怎么确认

`make collect` 干的事情，人工版只有三步：

```bash
# 1. 看散列到底开了哪一维
sysctl net.ipv4.fib_multipath_hash_policy
ip route show 10.11.4.0/24        # 确认是 multipath，不是单路径

# 2. 采两条上行的字节计数，看增量
cat /sys/class/net/eth3/statistics/tx_bytes
cat /sys/class/net/eth4/statistics/tx_bytes

# 3. 起流量，重复第 2 步
```

交换机上对应的观测量是每条 uplink 的出口利用率。
用 ECMP 的设备还有个更直接的办法：看各下一跳的报文计数。

Linux 6.2 以后多了 `net.ipv4.fib_multipath_hash_seed`。
换种子能把极化重排，但流数不变时不会变均匀 —— 这本身就是个有用的实验。

## 6. 代码怎么读

| 文件 | 内容 | 值得看的地方 |
|---|---|---|
| [hash.go](hash.go) | lookup3 与 `fib_multipath_hash` 的复刻 | 两条口径的差别只有几行 |
| [ecmp.go](ecmp.go) | 分配与统计 | 极化度与变异系数怎么算 |
| [flows.go](flows.go) | 拓扑与工作负载 | 三种流形态的定义 |
| [report.go](report.go) | 三个实验的输出 | 每个表格后面的「读法」 |

核心只有一句：`PickLink(hash, n)` 就是 `hash % n`。
不公平的来源不在取模，在输入——**流少、或者流的 5 元组一样，取模当然会撞。**

## 7. 思考题

1. 把 `-scan` 设成 `1,2,3,4`，看极化度。一条流时极化度是多少？
   这个数字要不要当成「网络有问题」？为什么不能。
2. 实验二里，把 `-flows` 从 64 加到 4096，L3 口径的极化度会变吗？
   为什么这个数字对 L3 是常数，对 L4 才随流数变化？
3. 同一个 seed 下，改 `net.ipv4.fib_multipath_hash_seed` 会怎样？
   如果集群里所有交换机种子相同，两个方向的流量会不会撞同一对链路？这属于哪一类问题？
4. 训练任务跑 rail-aligned 的 AllReduce。链条上每台 leaf 的两条上行为什么本来就该闲着？
   换成 rail 错位的通信，同一个 hash 又会怎么表现？

## 8. 模型边界

明确不做的事：

- 不模拟逐包转发与队列。要看队列与反压去 [03-fault-inject](../03-fault-inject/README.md)
- 不模拟 flowlet 与自适应路由。那是另一套机制，本 lab 只给一句结论
- 不模拟不对称路径与乱序。真实环境中 hash 换路会带来乱序，这个模型看不见
- 不追求与某个内核版本逐值对齐。改内核版本后，绝对值会变，分布特性不会

一句话：**这里练的是「看到分布不均，先问几维输入、几条流」，不是「复刻某个内核的 hash」。**
