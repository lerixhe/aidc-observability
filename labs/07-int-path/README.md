# 07-int-path · INT 逐跳元数据的编码与判读

> **教学级模型，非硬件行为等价。** 路径与元数据是构造的，编码格式按「每跳 24 字节固定步长」
> 这个真实实现里最常见的形态做简化。它练的是**判读逻辑**，不能替代真机 INT 验证。
> 真机路径见第 7 节。

## 1. 这个 lab 做什么

把课 12 的两件事变成可跑的代码：

1. **编码与解析**：把 5 跳元数据打包成线格式，再按固定步长解回来，含截断载荷的边界处理
2. **逐跳判读**：用「出口利用率 × 队列占用 × 停留时长」三个量组合出归因，区分四种形态

它要回答的问题是现场那句抱怨：**设备指标都正常，这条任务为什么慢。**

答案通常在这四种形态里：

| 场景 | 形态 | 结论 |
|---|---|---|
| `healthy` | 队列低、利用率中、停留短 | 全跳健康，别在这里找原因 |
| `egress` | 利用率 97% + 队列 780 KB | 这一跳的出口在排队 |
| `upstream` | 队列 640 KB + 利用率 55% | 多股流在抢出口，问题在上游分布 |
| `forwarding` | 队列 16 KB + 利用率 40% + 停留 40 µs | 开销在转发面，调水线没用 |

对应课程：[12 INT 带内遥测](../../site/src/content/docs/04-telemetry/12-int.mdx)。

## 3. 模型怎么建的

### 线格式

固定 24 字节，按大端编码，按固定步长滑窗解析。

| 偏移 | 字段 | 宽度 | 说明 |
|---|---|---|---|
| 0 | switch id | 4 | 设备标识，报告里显示成 `sw-003f` |
| 4 | ingress port | 2 | 入口端口号 |
| 6 | egress port | 2 | 出口端口号，用来还原实际路径 |
| 8 | hop latency | 4 | 该跳停留，纳秒 |
| 12 | queue depth | 4 | 出口队列占用，KB |
| 16 | tx util | 4 | 出口利用率，基点（10000 = 100%） |
| 20 | reserved | 4 | 时间戳低位，本 lab 未使用 |

固定步长换来的是**零歧义解析**：不需要长度前缀，也不会因为某个可选字段缺失而错位。
代价是字段宽度写死，扩展要改版本号。真实实现里这叫「定长 trace option」。

### 判读阈值

| 量 | 阈值 | 口径 |
|---|---|---|
| 出口利用率 | ≥ 85% | 视为接近打满 |
| 队列占用 | ≥ 500 KB | 按 1000 KB 端口缓冲口径 |
| 停留时长 | ≥ 20 µs | 视为该跳偏慢 |

三量组合的逻辑在 `analyze.go` 的 `ClassifyHop`，六条分支，全部有单测。

**判读顺序不能反。** 先看停留时长筛出可疑跳，再看队列与利用率区分归因。
反过来做会得到「所有队列高的跳都有问题」这种结论，而实际上多数排在队列里的流量不是这一跳造成的。

## 4. 观察什么

跑 `make run` 后重点看三处。

### 编解码往返

```text
  healthy      ✅ 5 跳，120 字节，往返一致
  truncated     ✅ 截断载荷被拒绝，不会读出垃圾字段
```

第二行比第一行重要。截断载荷若不报错，解析器会把残字节读成 switch id 与队列深度，
产出一份看起来完全正常、实际全是垃圾的记录。**这类 bug 在现场极难查，因为它不报错。**

### 逐跳判读

```text
定位到第 3 跳（sw-003f）：本跳出口拥塞
  #   设备       入    出        停留(µs)     队列KB      利用%       占比  归因
  *3  sw-003f  7    2          42.0      780     97.0    92.4%  本跳出口拥塞
```

`占比` 这一列是判读的核心。第 3 跳吃掉 92% 的全程时延，其余四跳合计 8%。
如果五跳各占 20%，那就不是单点问题，而是全程都在排队。

### 采样对照

```text
  采样       突发报文     解析捕获       实测捕获       连续 60 次全错过
  1:256    48       17.1%      17.3%      0.0%
  1:1024   48       4.6%       4.8%       6.0%
  1:4096   48       1.2%       1.1%       49.5%
```

最后一行是全 lab 最有价值的一张表。1:4096 采样下，一次 200 µs 的微突发单次捕获率只有 1.2%。
一分钟来 60 次，**有一半概率一次都抓不到。**

这不是采样实现得不好，这是采样率的算术后果。要抓这类事件，得靠队列水线触发的快照，
不能靠调采样率硬扛。

## 5. 三个可以自己改的实验

**实验一：把阈值调松，看误报怎么涨。** 把 `analyze.go` 里的 `QueueHighKB` 从 500 改成 100，
`healthy` 场景立刻出现可疑跳 —— 因为 22 KB 的队列仍然低于 100。改回来。

**实验二：加一跳。** 在 `path.go` 里给每条路径插一跳，观察 `占比` 与总时延怎么变。
五跳变六跳，元数据从 120 字节涨到 144 字节，相对 1450 字节报文的开销从 8.3% 涨到 9.9%。

**实验三：让采样率与事件时长联动。** 把 `-burst-us` 从 200 改到 2000，再看采样表。
捕获率会上升一个数量级 —— 说明**采样率够不够，取决于你要抓多短的事件**，而不是取决于某个推荐值。

## 6. 与真机的差距

| 模型 | 真机 |
|---|---|
| 固定 24 字节、字段自造 | 各厂商的 trace option 字段集不同，长度可变 |
| 判读用全局固定阈值 | 阈值要按端口缓冲、基线、业务类型分别定 |
| 五跳固定路径 | 实际路径由 ECMP hash 决定，同一流可能走不同路径 |
| 采样是独立同分布 | 哈希采样有偏，同一流反复采到或反复采不到 |
| 元数据保证准确 | 芯片在高负载下会裁剪元数据或直接不采 |

模型能练的是「拿到记录怎么读」。它练不了的是「怎么让芯片把记录写对」。

## 7. 真机验证路径

按这个顺序，每一步都能独立验证。

1. **确认芯片能力**：查设备手册的 INT / IOAM 支持章节。关键问一句：能插进业务报文，还是只能旁路导出。
2. **单点验证**：在一条已知路径上开 INT，用同一个流反复打，确认每次拿到的跳序列一致。
3. **交叉验证**：把 INT 的逐跳时延与端口计数器（队列水线、PFC）对齐，两条独立数据源对得上才算准。
4. **压力验证**：满载时再看元数据完整率。芯片过载会静默丢元数据，这是最容易被忽略的一项。

## 8. 思考题

1. 为什么判读顺序是「先筛停留时长，再看队列与利用率」，反过来会出什么错？
2. `upstream` 场景里，队列堆在第 3 跳，但结论说问题在上游。上游指的是哪一级，为什么这一跳调水线没用？
3. 采样表里「连续 60 次全错过」在 1:4096 下是 49.5%。如果业务能容忍一个月漏一次，采样率最多能放到多少？
4. 定长 24 字节的格式换成变长（带长度前缀）后，解析代码要改哪几处，会引入什么新的错误类型？

## 9. 一条坑

`Decode` 的越界检查最容易写错。常见写法是 `if len(payload) < HopSize { return error }`，
然后按 `len(payload)/HopSize` 循环。这种写法对 `len = 25` 的载荷不报错，
最后一跳会读出 1 个真实字节加 23 个零。

单测里的 `TestDecodeRejectsTruncated` 就是为这个而写的。**截断不报错的解析器，
会在事故复盘时给你一份看起来正常的假记录。**
