# 08-pipeline · 秒级遥测落盘与查询保真度对比

> **教学级模型，非生产管道。** 信号是构造的，采集器只模拟「生产者 1 Hz、消费者会降档、缓冲有限」
> 这三种行为，落盘用内存切片代替真实存储。它练的是**保真度取舍与容量估算**，
> 不能替代 Kafka / Flink / ClickHouse 的部署验证。真机路径见第 7 节。

## 1. 这个 lab 做什么

把课 14 的三笔账算成可跑的数字：

1. **容量账**：同一份 1 小时秒级数据，四档落盘的体积差多少
2. **保真账**：同一段事故窗口，四档数据能不能查出「峰值」与「告警」
3. **背压账**：采集器缓冲有限、消费速率会掉档，丢点会落在什么位置

它要回答的问题是课 14 那句判断：**降采样不是压缩，是丢弃。**

## 2. 跑起来

需要 Go 1.22 以上，无第三方依赖。

```bash
cd labs/08-pipeline
make run     # 四档体积 + 窗口查询对照 + 背压丢点
make csv     # 额外写 out/*.csv，各档数据可画图
make test    # 14 个单测
```

调参数对照：

```bash
go run . -buffer 5000          # 缓冲足够大，丢点消失
go run . -window 1800          # 半小时窗口
go run . -from 0 -to 10        # 查健康窗口，四档都正常
```

## 3. 模型怎么建的

### 信号

1 小时、1 秒采样，三个成分叠加：

| 成分 | 形态 | 目的 |
|---|---|---|
| 基线 | 20 KB 上下，5 分钟周期起伏 | 制造「正常波动」的底噪 |
| 微突发 | 每 5 分钟一次，持续 2 秒，冲到 180 KB | 秒级可见、分钟聚合会被摊平 |
| 劣化窗口 | 第 40–50 分钟，每 30 秒有 3 秒冲到 520 KB | 制造「均值正常、峰值超阈值」的双峰分布 |

阈值取 400 KB。这个数字是设计的：健康期峰值 180 KB 不触发，劣化期峰值 520 KB 触发，
而劣化期的**均值只有 213 KB**，同样不触发。

### 四档落盘

| 档位 | 桶宽 | 保留 | 说明 |
|---|---|---|---|
| `raw` | 1 s | 每点 | 完整信息，体积最大 |
| `1m(max)` | 60 s | 均值 + 峰值 + P99 | **正确做法** |
| `1m(mean)` | 60 s | 只留均值 | 最常见的错误配置 |
| `1d(max)` | 86400 s | 均值 + 峰值 + P99 | 长期归档 |

`1m(mean)` 这一档是故意放进来做反例的。它在代码里就是一个 `keepPeak bool` 参数，
配置项写成 `aggregate(mean)` 还是 `aggregate(mean,max,p99)`，后果差在这里。

### 采集器背压

规则只有三行：每 tick 入队（满则丢）、按当前消费速率出队、缓冲容量固定。

| 时段 | 消费速率 | 现象 |
|---|---|---|
| t < 2400 | 1.0 | 生产 1 Hz、消费 1 Hz，缓冲几乎不涨 |
| 2400 ≤ t < 2700 | 0.1 | 每秒积压 0.9 点，缓冲 200 点被填满 |
| t ≥ 2700 | 1.5 | 扩容消费者追赶，净排空 0.5 点/秒 |

## 4. 观察什么

### 体积对比

```text
  raw        桶 3600 个 · 每桶     1 点 · 落盘  201600 字节
  1m(max)    桶   60 个 · 每桶    60 点 · 落盘    3360 字节
  1d(max)    桶    1 个 · 每桶 86400 点 · 落盘      56 字节
```

压缩比正好是 60 与 3600。**注意字节数是按「每桶 32 字节头 + 3 个 8 字节值」粗估的**，
真实存储还有索引、标签、副本开销，实际比例更接近 5 到 10 倍压缩而不是 60 倍。

### 窗口查询对照

```text
  档位             桶数     点数      峰值KB    P99KB     均值KB 告警
  raw           600    600     520.0    520.0    213.6 是
  1m(max)        10    600     520.0    520.0    213.6 是
  1m(mean)       10    600     213.6    213.6    213.6 否
  1d(max)         1   3600     520.0    520.0     53.2 是
```

三行读法。

1. `1m(mean)` 的峰值等于均值。520 KB 的冲顶被摊平成 213 KB，**告警直接灭掉**。
2. `1m(max)` 峰值与原始档一致，代价是时间分辨率从秒降到分钟。P99 列只能当下界看。
3. `1d(max)` 峰值也在，但答不出「哪一分钟冲顶」。做容量规划够用，做事故复盘不够。

第四行还藏着一件事：`1d(max)` 的均值是 53.2 KB，因为桶里包含了 59 分钟的健康数据。
**聚合粒度越粗，均值越没有意义。** 这正是课 15 说「均值几乎没有诊断价值」的量化版本。

### 背压与静默丢弃

```text
  缓冲容量 200 点 · 消费速率 1 降档到 0.1（t=2400..2700 期间）
  峰值缓冲占用 200 点
  投递 3528 / 期望 3600 · 整体完整率 98.0%
  丢弃 72 点 · 首次丢弃 t=2622 s
  事故窗口（t=2400..3000）完整率 88.0% · 窗口内丢弃 72 点
  健康窗口（t=0..2400）完整率 100.0%
```

这段是本 lab 最值得看一眼的地方。**丢弃全部落在事故窗口内，健康窗口 100% 完整。**
如果只看「整体完整率 98%」或者只看健康时段的面板，一切正常。

而事故期间你少了 12% 的样本，且丢的恰好是积压最严重、信息量最大的那段。

## 5. 三个可以自己改的实验

**实验一：把 `1m(mean)` 改成 `1m(max)`。** 只改一行（`keepPeak` 传 true），
告警列从「否」变「是」。这就是一次口径修复的全部工作量，也是它最容易被漏掉的原因。

**实验二：缓冲从 200 调到 5000。** 丢点归零，但代价是采集器内存涨 25 倍、恢复时延变长。
缓冲不是越大越好，它换来的是「延迟换完整率」。

**实验三：把消费速率正常值从 1.0 调到 0.95。** 稳态就开始缓慢积压，两小时后缓冲爆掉。
这解释了为什么「不留余量」的采集器在业务增长半年后会突然开始丢数据。

## 6. 与真机的差距

| 模型 | 真实管道 |
|---|---|
| 内存切片当存储 | Kafka + Flink + 列存，每段有各自的缓冲与超时 |
| 丢弃是确定性的 | 丢弃与超时、重试、分区倾斜交织，多数时候无日志 |
| 消费速率按时间分档 | 背压是动态反馈，积压会反向拖慢生产端 |
| 单序列 | 上万序列共享管道，热点序列会挤掉长尾序列 |
| 时间戳单调递增 | 事件时间乱序、迟到，需要水位线与 allowed lateness |

模型能练的是「哪一档会丢什么信息」。它练不了的是「生产端超时配置怎么选」，
那需要在真实 Kafka 上压测。

## 7. 真机验证路径

1. **量级验证**：按课 14 的公式算自己集群的点速率，与实测写入速率对照，偏差超过 2 倍就回去查维度设计。
2. **保真验证**：同一段时间，用原始数据与聚合数据分别查峰值。两者不一致，说明聚合配置错了。
3. **丢弃验证**：给采集器加丢弃计数并告警，故意压测触发一次，确认告警能响。
4. **迟到验证**：制造一次时钟跳变或消费者重启，看窗口结果是否偏乐观。这一项只有真机才能做。

## 8. 思考题

1. `1m(mean)` 那行峰值等于均值。如果把这个档位接上告警，故障期间会出现什么现象？
2. `1d(max)` 的均值 53.2 KB 与窗口均值 213.6 KB 差 4 倍。这两个数字各自适合回答什么问题？
3. 缓冲从 200 加到 5000 能让丢点归零。这个改动引入了什么新代价，怎么在先验上判断加多少够用？
4. 如果丢弃只有 12% 但全部落在事故窗口，你的完整率 SLI 该按什么维度统计才能暴露它？

## 9. 一条坑

`1m(mean)` 这一档在代码里只是一个布尔参数，配置项写成 `aggregate(mean)` 还是
`aggregate(mean,max,p99)`，面板上看起来都是「分钟级队列水线」。

差别要到事故那天才显形。**容错的做法不是加告警阈值，是在指标定义里强制写明保留字段**，
让它进评审、进 diff。课 15 的口径表就是干这个的。

另一个容易踩的是分位数：`1m(max)` 的 P99 只能取各桶 P99 的最大值当下界，
跨桶求平均会得到没有统计意义的数。想拿准确的 P99，就得存直方图，聚合时用 `histogram_quantile` 重算。
