# 09-slo · 三种 SLO 口径与错误预算

> **教学级模型，非生产 SLI。** 指标流是生成的，四种口径都是简化实现（真实系统还要处理缺失点、
> 时钟漂移、多副本去重）。它练的是**口径选择的后果**，不能替代你们自己业务上的 SLI 定义。
> 真机路径见第 7 节。

## 1. 这个 lab 做什么

同一份 30 天的指标流，用三种口径算可用率，会得到一个达标、两个未达标。

| 口径 | 分母 | 本次结果 | 判定 |
|---|---|---|---|
| 时间口径 | 分钟数 | 99.780% | 未达标（预算用掉 220%） |
| 事件口径 | 请求数 | 99.924% | 达标（预算用掉 76%） |
| 分位口径 | P95 达标的分钟数 | 99.803% | 未达标 |

三个数都叫「可用率」。**不说口径就报可用率，等于没说。**

对应课程：[15 指标体系与口径](../../site/docs/05-analysis/15-metrics-slo.md)。

## 2. 跑起来

需要 Go 1.22 以上，无第三方依赖。

```bash
cd labs/09-slo
make run     # 三种口径 + 错误预算 + 多窗口燃烧率 + 事故清单

```

调目标：

```bash
go run . -slo 0.9995     # 目标抬到 99.95%，看三种口径的判定怎么变

```

## 3. 模型怎么建的

### 指标流

30 天、1 分钟一条，字段三个：请求数、失败数、P95 时延。

| 成分 | 形态 | 作用 |
|---|---|---|
| 昼夜流量 | 白天约 800 req/s，夜间约 100 req/s | 让「时间」与「请求」两个分母分化 |
| 基线 | 失败率 0.05%，P95 8 ms | 制造底噪，让预算不是满的 |
| 五次事故 | 夜间一小时 30% 失败、白天 15 分钟 25% 失败、两次小抖动、窗口末尾一次正在发生 | 制造不同形状的损失 |

**事故分布是设计过的。** 夜间事故流量只有白天的八分之一，所以它在时间口径上很重、在事件口径上很轻。
这就是三种口径分歧的唯一来源。

### 判坏规则

一分钟判坏，满足其一即可：

- 失败率 > 1%
- P95 时延 > 50 ms

规则写死在 `stream.go` 的 `Sample.BadMinute`，改它会让所有口径一起变。

### 三种口径

| 口径 | 分子 | 分母 | `sli.go` 里的分支 |
|---|---|---|---|
| 时间 | 坏分钟数 | 总分钟数 | `CaliberTime` |
| 事件 | 坏请求数 | 总请求数 | `CaliberEvent` |
| 分位 | P95 超线的分钟数 | 总分钟数 | `CaliberLatency` |

第三种最容易误导。它完全忽略失败率，**失败得快也算达标**。单测里有一条专门钉这个行为。

### 燃烧率

```text
burn = (1 - 窗口可用率) / (1 - SLO)
```

1 表示按这个速度刚好在窗口末用完预算。14.4 表示按这个速度一小时烧掉 2% 的月度预算。

多窗口成对判定，来自 SRE Workbook 的推荐配置：

| 窗口对 | 阈值 | 含义 |
|---|---|---|
| 5 分钟 + 1 小时 | 14.4 | 快烧，立刻 page |
| 30 分钟 + 6 小时 | 6 | 慢烧，开单排期 |

## 4. 观察什么

### 三种口径的分歧

```text
  口径                可用率      差目标 判定
  时间口径          99.780%   -12.0bp 未达标
  事件口径          99.924%     2.4bp 达标
  分位口径          99.803%    -9.7bp 未达标
  最宽 事件口径 99.924% 与最严 时间口径 99.780% 相差 14 个基点
```

14 个基点听起来不多，但落在判定上就是截然相反的两个结论。同样的数据，
按时间口径要发事故复盘，按事件口径可以发「本季度达标」的周报。

### 错误预算

```text
  口径                   允许          已消耗           剩余       已用
  时间口径             43.2 分       95.0 分      -51.8 分   127%+
  事件口径          1166379 条     887511 条     278868 条    76.1%
```

时间口径的预算已经超支两倍多。这个结论对运维有用：**一个月里 95 分钟的服务受损，就是不可接受。**

事件口径还剩 24%。这个结论对业务有用：**绝大多数请求其实没受影响。**

两个都对，用途不同。要对外报 SLA 用事件口径，要驱动可靠性投入用时间口径。

### 多窗口燃烧率

```text
  窗口              燃烧率         阈值 状态
  5m           200.0×      14.4× 超阈值
  60m           29.6×      14.4× 超阈值
  30m           63.5×       6.0× 超阈值
  360m           3.0×       6.0× 正常
  判定：快烧两窗口同时超阈值 → page
```

短窗口灵敏但吵，长窗口稳但慢。成对看的意义就在这里：5 分钟窗口说「现在很糟」，
1 小时窗口说「这不是一次抖动」，两个一起才值得叫人起床。6 小时窗口没超线，
说明这不是长期缓慢劣化。

## 5. 三个可以自己改的实验

**实验一：把 `-slo` 从 0.999 改到 0.9995。** 事件口径的预算从 116 万条降到 58 万条，
已用比例直接翻倍到 152%，达标变未达标。**SLO 抬高一个 9，预算砍半。**

**实验二：把夜间事故从 60 分钟改成 360 分钟。** 时间口径掉得更快（多 300 个坏分钟），
事件口径几乎不动（夜间流量占比低）。这是「时间与事件」两个口径的极端分化。

**实验三：把 `BadLatencyMs` 从 50 改成 30。** 分位口径立刻掉下去，而事件口径与时间口径
只在事故期间受影响。这说明分位口径对阈值极度敏感，**报它的时候必须连阈值一起报**。

## 6. 与真机的差距

| 模型 | 真实系统 |
|---|---|
| 指标流完整无缺失 | 采集本身会丢点，缺失点算好还是算坏要先定义 |
| 单一集群 | 多集群、多云要分别定 SLO，再定组合口径 |
| 失败率与流量关系稳定 | 真实流量有促销、训练任务潮汐，事件权重会剧烈变化 |
| 事故边界清晰 | 真实事故的起止时刻需要人工裁定，裁定差异能差出几个基点 |
| 燃烧率阈值用推荐值 | 现实要按团队响应成本调，14.4 不是圣经 |

模型能练的是「口径怎么选、预算怎么算」。它练不了的是「SLO 该订多少」，
那件事只能由业务与成本的对话决定。

## 7. 真机验证路径

1. **同期对比**：拿你们真实的一个月数据，用三种口径各算一遍。三个数差多少，就是口径风险有多大。
2. **预算回溯**：把这一个月的错误预算消耗画成曲线，看你当初的可靠性投入是否匹配。
3. **阈值标定**：把分位口径的阈值从推荐值上下各调 20%，看达标结论会不会翻转。会翻转就说明阈值没有工程依据。
4. **告警演练**：主动触发一次燃烧率告警，确认从告警到有人响应的链路是通的。这一项只能真机做。

## 8. 思考题

1. 时间口径与事件口径差了 14 个基点，一个达标一个未达标。对外报 SLA 时你选哪个，为什么？
2. 分位口径「失败得快也算达标」，这个缺陷在什么业务场景下是灾难，在什么场景下可以接受？
3. 5 分钟窗口的燃烧率是 200×，6 小时窗口只有 3×。这两个数字同时成立说明事故是什么形状？
4. `-slo` 从 99.9% 抬到 99.95%，事件口径的预算减半。如果团队不打算加投入，这个动作的实质是什么？

## 9. 一条坑

`CaliberLatency` 里的一个顺序错误值得单独提。原始实现先算 `Availability` 再 `return`，
但把 `r.Met = ...` 写在 `return` 之后，结果所有分位口径的结论都是「未达标」。

这类 bug 不会报错，也不会让数字看着奇怪（可用率是对的），**只会让判定永远是同一个值。**
单测 `TestComputeLatencyIgnoresErrors` 就是为它写的：全失败但时延很低时，
分位口径必须判「达标」。这条断言看起来反直觉，正是它的价值。
