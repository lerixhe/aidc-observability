# 10-rca · 告警收敛与图打分根因定位

> **教学级模型，非生产算法。** 拓扑与告警是生成的，图打分是「共同上游祖先 + 传播路径评分」的最小实现。
> 换成你们的真实拓扑与告警，机制不变、参数全变。

## 1. 这个 lab 做什么

走完 AIOps 四层里的第 ②③ 层：

1. **注入故障**：在 2 spine × 4 leaf × 2 host 的图上随机造一个故障，让告警沿拓扑向下流
2. **收敛**：把几百条告警压成几个 incident
3. **RCA**：用图打分找根因，和两个朴素基线对比 200 轮

对应课程：[16 告警收敛与根因定位](../../site/docs/05-analysis/16-aiops.md)。

## 2. 跑起来

需要 Go 1.22 以上，无第三方依赖。

```bash
cd labs/10-rca
make run     # 200 轮评估 + 一轮完整明细
make topo    # 只看拓扑与下游集合
make test    # 9 个单测
```

## 3. 结果长什么样

```
方法                        Top-1      Top-3         平均排名
按告警条数排序                     56%        88%        2.75
按最早时间排序                     82%       100%        1.18
图打分（本 lab）                  93%       100%        1.07

告警收敛：4013 条告警 → 661 个 incident，压缩比 6.1×
```

三个结论：

1. **按告警条数排序最差（56%）**。一个故障的派生告警最多，根因往往不是告警最多的那个。
   这是最反直觉的一条：值班新人第一反应就是「谁报警最多谁有问题」。
2. **按最早时间排序能到 82%，但不稳**。它会被上游反向告警带偏 —— 下面明细里就有一例。
3. **图打分 93%**。靠 `precision` 压住「覆盖面最大的顶层节点」，
   这才是共同祖先搜索真正在做的事。

## 4. 一轮明细

```
真值：leaf1（leaf 层）· optics-degrade · t0=1543ms
告警 17 条 → 3 个 incident；取包含真值的那个，含 4 个实体

  告警流（前 8 条）
       1545ms  spine1   neighbor-down            warning
  *    1573ms  leaf1    pfc-pause-high           critical
  *    1594ms  leaf1    queue-watermark-high     critical
       1652ms  host2    path-latency-high        warning
       1656ms  host2    nccl-timeout             warning
       1659ms  host3    path-latency-high        warning
```

注意第一条：`spine1` 的 `neighbor-down` 比真值的 critical 告警还早 28 ms。
这是上游反向告警 —— 下游出事，上游的邻居检查先失败。**按最早时间排序就栽在这里。**

候选排序：

```
#   实体         score  coverage  precision      时间
1   leaf1      0.876       94%       100%    0.84  ← 命中真值
2   spine1     0.471      100%        31%    1.00
3   host3      0.293       31%       100%    0.36
```

`spine1` 的 coverage 是满的（它下游含所有 leaf 和 host），但 precision 只有 31% ——
14 个下游里只有 4 个真的报了警。图打分因此把它压到第二。

## 5. 打分公式

```
score = F1(coverage, precision) × (0.4 + 0.6 × 时间先验)
```

| 分量 | 含义 | 为什么要它 |
|---|---|---|
| `coverage` | 加权解释的告警量占比 | 根因应该能解释绝大多数告警 |
| `precision` | 下游实体里有多少真的报了警 | **惩罚「什么都覆盖」的顶层节点**。没有这一项，spine 永远第一 |
| 时间先验 | 它自己的告警是不是比下游早 | 「故障向下流」的机器表达 |

`coverage` 按**严重度加权**，这一项很关键：

```go
critical → 3 分，warning → 1 分
```

不加权的话，一台设备产生的十几条 warning 会把根因那两条 critical 淹掉，
host 层故障几乎全被判错。实测差别：host 根因的 Top-1 从 60% 出头升到 93%，
整体从 82% 拉到 93%。

## 6. 三个方法为什么差这么多

| 方法 | 隐含假设 | 什么情况下会错 |
|---|---|---|
| 按告警条数 | 故障越大声，越像根因 | 派生告警最多的总是下游 host（任务侧重复告警） |
| 按最早时间 | 因果 = 时间先后 | 上游反向告警、早到的噪声、采集延迟抖动 |
| 图打分 | 故障沿拓扑向下流，且 root 的告警更严重 | 拓扑不准、告警没有分级、时间窗配错 |

三条都能在明细里找到实例。这也是课程里那句「难点不在算法，在数据质量」的意思：
三种方法用的是同一份数据，差别全在**怎么用拓扑和严重度**。

## 7. 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-trials` | 200 | 随机故障轮数 |
| `-seed` | 42 | 随机种子，固定后结果可复现 |
| `-gap` | 150ms | 告警收敛的时间窗口 |
| `-window` | 10s | 告警流的时间跨度 |
| `-topo` | false | 只打印拓扑与下游集合 |

调 `-gap` 能直接看到收敛的两难：

```bash
go run . -gap 10ms    # 压缩比 3.6×，三种方法都 94% 以上
go run . -gap 500ms   # 压缩比 6.4×，按告警条数掉到 53%
```

窗口收紧，主 incident 变得干净，**连朴素基线都能跑到 94%** —— 此时图算法的优势从 37 个点
缩到 3 个点。反过来窗口放开，压缩比上去了，过度合并又把无关告警卷进来，所有方法一起变差。

这就是课程里「依赖顺序不可跳」的具体数字：**收敛质量决定 RCA 的上限**，
算法只是在干净数据上多榨出几个百分点。窗口不是越大越好，也不是越小越好。

## 8. 思考题

1. 把 `-gap` 从 150ms 调到 20ms，压缩比和命中率各怎么变？为什么两者会朝反方向走？
2. `precision` 的分母是 `len(Down[c])`，也就是「候选的下游节点数」。
   如果改成「下游**有监控**的节点数」，哪个节点最受益？为什么？
3. 现在的拓扑里每个 leaf 双上行到所有 spine，所以两台 spine 的下游集合完全一样。
   换成「每个 leaf 只上行一台 spine」，哪台 spine 的下游更大？对打分公平吗？
4. host 根因的 Top-1 明显低于 leaf 根因。这是算法的缺陷，还是数据的极限？
   （提示：host 故障和它所属 leaf 故障，产生的告警集合差多少）

## 9. 模型边界

- **拓扑是静态生成的**：没有配置漂移，没有 LLDP 发现误差。而真实环境里图不准是老大难
- **告警是语法生成的**：kind 与层级的对应写死在代码里，真实告警的语义要脏得多
- **没有时钟漂移**：所有告警时间来自同一个时钟。真实环境里时钟没对齐会把传播方向判反
- **故障沿拓扑严格向下**：不考虑「跨 leaf 的路径故障」（那需要路径级拓扑，不是节点图）
- **单故障假设**：每轮只有一个根因。真实场景里两个故障叠加时，本算法会把它们当成一个
- **不做处置层**：第 ④ 层的自动化处置、验证、回滚都不在本 lab 里

## 10. 一条坑

一开始 `precision` 也用加权量算：

```go
precision = 加权解释量 / len(Down[c])   // 错
```

对 leaf 来说，下游 3 个节点但解释量能到 7 分，precision 算出 2.3 —— 大于 1 的比例，
F1 直接失真，spine 反而因为分母大而显得「谦虚」。

分母是**实体个数**，分子就得是**实体个数**。要么都加权，要么都不加权。
这次是 coverage 加权（严重度有意义）、precision 不加权（只问下游有没有无辜分支），
所以代码里两者用了不同的分子。

量纲不齐的错误，在打分函数里特别难看出来 —— 因为输出永远是 0 到 1 之间的数，
只是排序悄悄变了。
