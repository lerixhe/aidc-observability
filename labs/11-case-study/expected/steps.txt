== 剧本：十步，四把刀 ==
任务层 → 主机层 → 网络层 → 光层，每一层只做一件事：把候选压一个数量级。

[ 1] 发现 · 全体还是个别的慢（1.0 分钟）
     看：训练日志的步耗时分布
     见：步耗时 380 → 520 ms；512 个 rank 同步抬升，无掉队者；P50 与 P99 同向
     判：全体同步 → 共享资源（网络 / 存储 / 调度）优先；个别慢 → 先查那台主机 → 全体同步，网络层优先

[ 2] 定界 · 时间被谁吃掉了（1.5 分钟）
     看：日志里 allreduce 耗时与占比
     见：allreduce 90 → 190 ms；通信占比 24% → 36%
     判：占比上升 → 通信问题；占比不变而总时长涨 → 算力侧 → 通信吃掉了增量，GPU 侧先排除

[ 3] 定界 · GPU 与域内网络是否干净（2.0 分钟）
     看：nvidia-smi 降频原因、dmesg 的 XID、DCGM 的 NVLink 重放
     见：三项全干净：无降频、无 XID、NVLink 无重放
     判：干净 → 排除算力与域内；有 XID 或重放 → 先处理主机侧 → 排除单机与 NVLink

[ 4] 定界 · 通信环还在原路线上吗（1.5 分钟）
     看：NCCL_DEBUG=INFO SUBSYS=INIT,GRAPH 的 ring 组成
     见：ring 与基线一致，未跨 rail 重组
     判：ring 变了 → 环重组会带来全体变慢，而网络计数器正常 → 环没变，网络指标对得上号

[ 5] 缩小 · 哪台设备的哪个端口在冒烟（4.0 分钟）
     看：gNMI 订阅的 per-priority pause 时长，10 分钟窗口
     见：只有 rail-3 的 leaf-7 上行口异常：累计 pause 42 秒，占 7%
     判：> 10 秒 / 10 分钟为严重；只看时长不看帧数 → 候选从全网压到单个端口

[ 6] 缩小 · 拥塞是被压制还是在恶化（2.0 分钟）
     看：同一端口的 ECN 标记率斜率与队列峰值
     见：ECN 0.4% → 3.8%，十倍级上升；队列峰值未顶满
     判：ECN 持续 > 3% 即异常；队列未顶满说明还没到风暴 → 机制在工作，但压力在持续上升

[ 7] 缩小 · 逐跳看，卡在哪一跳（6.0 分钟）
     看：INT 逐跳时延与队列元数据
     见：时延集中在 leaf-7 上行口的出口队列，其余各跳正常
     判：集中在某一跳的出口 → 该跳下游能力不足，而不是上游打得太猛 → 问题在该端口往外的那一段

[ 8] 确认 · 链路底层有没有出错（4.0 分钟）
     看：端口 CRC 计数与 pre-FEC BER 的一阶差分
     见：CRC 0 → 12 次/分钟；FEC 纠正率 1e-9 → 4e-6
     判：绝对值不重要，趋势重要：从 0 起涨就是第一阶段证据 → 链路在硬扛，纠错压力上升

[ 9] 确认 · 哪个 lane 出了问题（5.0 分钟）
     看：模块 DOM 的逐 lane 接收光功率
     见：lane 2 为 -8.9 dBm，其余 lane 在 -2.4 dBm 附近
     判：单 lane 偏离 > 3 dB 即劣化；偏离 6 dB 不是抖动 → lane 级劣化，四个证据指向同一处

[10] 恢复 · 止血、验证、根治、回切（13.0 分钟）
     看：drain 端口后的步耗时、ring 重组、回切结果
     见：drain 后步耗时回到 390 ms；流量绕开；换模块后回切并登记根因
     判：步耗时回到基线 ±10% 才算恢复；不回切就没确认修复 → 业务恢复，根因入库
