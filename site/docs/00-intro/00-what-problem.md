智算中心（AIDC，也有人叫 AI Fabric、AI 网络、高性能网络）是这两年网络圈子里被提得最多的话题。它用一张以太网把成千上万张 GPU 连成一台「训练机器」，用 RoCEv2 把 RDMA 语义压到普通以太网卡上，再用 PFC 和 ECN 把这套本来随时会丢包的协议勉强捏成不丢包的。国内外头部公司都在建这种集群，Meta 公开过两万四千卡规模的 RoCE 训练集群，NVIDIA 把 DGX SuperPOD 直接做成参考架构卖给客户，国内几家做模型的公司也都在自建千卡、万卡级别的环境。也可以说，会不会看智算网络的指标，正在从网络工程师的加分项，慢慢变成绕不开的必备技能。

这门课讲的就是「看指标」这件事，而它跟传统 IDC 的差别，远比多数人预想的大。如果要用一句话来描述这门课，我想应该是：**它教你在满屏正常数字里，找出那个真正让训练变慢的东西。**

## 从面试到现场

在面试网络工程师的时候，我习惯先问一个问题：「智算网络的可观测，主要是看什么？」

第一个回答往往都是「看丢包率」。丢包确实是网络监控里最核心的那个指标，它直观、好解释，还能一路换算成重传和时延，一套静态阈值告警就能管起来，省事得很。

可是如果再进一步问「还有呢？」，大多数同学就会开始皱眉头，只有一小部分人会补上一句「看 PFC」。如果你顺着 PFC 再往下问一句「为什么 pause 计数比丢包更值得盯？」，基本就要摇头了：我们集群的面板是平台组搭好的，图都是现成的，PFC 那张我天天看，但背后的机制没研究过，工作里也用不上。

对类似的场景，我深有体会。这些年相关的面试题我攒了不少，真正能一路聊下去的人却不多。当面试的同学频繁回复「不知道、没接触过」的时候，再继续深入追问已经毫无意义，这时候就得换话题了。偶尔遇上几个能持续很多回合、还能顺手说清「哪一类指标早动、哪一类指标晚动」的同学，他们总能让人眼前一亮。如果再往周边知识点上拓展一下，会发现这些人往往也有涉猎，这时候我在心里已经暗暗给这位同学伸出了大拇指。

这样的面试经历事后也让我深刻反思：把观测能力封装成一个平台，对提升团队研发效率是实打实的好处，我们自己也该羡慕。但普通工程师如果只习惯于在别人搭好的面板上读现成的数字，只专注于用现成的图回答现成的问题，久而久之，在技术理解和故障判断上就会变得迟钝甚至麻木。从这个角度看，那套做得很漂亮的监控平台也可能成为工程师的「敌人」，它把大家养成「温室的花朵」，一旦碰上一张面板上没有的故障，就会不知所措。

真正吃亏的地方在现场。

先说一个现场，这类事我见过不止一次。集群的监控面板全绿，训练任务却从每步 380 毫秒掉到 520 毫秒。两个小时后有人发现，是一颗光模块的单 lane 在劣化。这时候你去看端口计数器，CRC 只是从 0 涨到 12。

0 到 12，在阈值告警体系里连个水花都算不上。

同一件事，两种读法，两个结论。这就是这门课存在的理由：看待的对象从「平均值」换成了「尾部与瞬时值」，从「端口」换成了「队列 × 优先级 × 路径」。后来我自己养成一个习惯，看数之前先问三句话：这个数是多长窗口聚合出来的，它拆到哪一层粒度，它在这个网络里到底代表什么语义。三句话问完，多数「指标正常所以没问题」的判断就站不住了。这三句话后面会反复出现，第 03 讲专门拆它们。

其实很多场景，会用一个工具、会读一张面板，那是再简单不过的事情。但集群规模一涨、训练一跑几十个小时之后，现有监控的问题就会层出不穷地暴露出来。如果不能理解这些数字背后的机制——为什么 PFC 会逐跳反压、为什么 ECN 标记率总比丢包先动、为什么一分钟聚合能把微突发抹得一点不剩——那么现场那些「指标全绿但任务变慢」的问题，你根本理解不到本质，更谈不上解决，临时抱佛脚也于事无补。

所谓「授人以鱼不若授人以渔」，本课程的初衷和目标，就是帮你把这套机制和判读经验练成自己的东西，做到知其然也知其所以然，为将来独立带一次故障复盘、接手一个更大的集群做好准备。

## 哪些讲，哪些不讲

本课程主要讲解笔者从实战中摸索总结的智算网络可观测最常用最核心的几个知识点，限于篇幅和精力，并没有涵盖相关的全部内容，比如交换机芯片内部的 buffer 分配与共享阈值就完全没有提到。之所以不讲，是因为这部分内容普通工程师根本碰不到，讲深了就成了厂商的培训手册，读者读完除了多记几个名词，对现场判断没有半分帮助。

第二类没有讲的，是选型结论。到底该用哪家的遥测方案、要不要上带内遥测、控制器选商业的还是开源的，这些问题跟预算、存量设备、团队习惯强相关，任何脱离具体场景的结论都是在耍流氓。本课程只给判断框架和判读口径，不给采购建议。

第三类没有多讲的是调参。PFC 的水线该设多少、ECN 的标记门限要不要随速率缩放，这类问题需要真机压测，本课程的实验也替代不了。这里只教你先把问题看见、把方向判对，至于拧哪个旋钮，得回到你自己的机房里试。

课名也交代一句。这门课每一讲都写成「第NN讲 · 名词条目」，开篇写成「开篇 · 指标全绿，任务却慢」。标题只承担两件事：检索和记忆。所以课名尽量落在一件具体的事上，不写「智算网络可观测概述」这类正确的废话。你要是发现哪一讲的标题跟内容对不上，那是内容问题，直接开 issue，改起来不费事。

下面进入正题。

## 你需要什么基础

这门课不要求你会调交换机，也不要求你写过控制面配置模板。下面四项能力，你至少占三样，剩下的一样边做实验边补也来得及。

| 前置能力 | 具体到什么程度 | 缺了怎么办 |
|---|---|---|
| TCP/IP 与以太网基础 | 能读懂 MTU、VLAN、ECMP hash、队列调度这几个词的实际含义 | 先补任意一本网络基础教材的以太网与拥塞控制章节 |
| Linux 与抓包 | 会用 `ip`、`tc`、`ethtool`、`tcpdump`，能看懂一次 netem 注入的效果 | 在容器里练一遍，代价约一天 |
| 指标与时序系统 | 知道 label 基数、聚合窗口、分位数估算的坑 | 先把第 17 讲的时序存储那节读完，再回头 |
| 一门脚本语言 | Go 或 Python 能跑通一个读 CSV 算统计的脚本 | 实验都可以只读输出，不影响理解 |

如果你的底子是传统 IDC 那一套，那恭喜，你其实占了先手。链路探测、时序管道、口径设计这些活在老环境里你都干过，搬过来几乎不费劲，要换掉的只是四个默认假设，第一篇会讲透。反过来，有三类读者会被这门课卡住，笔者先说在前面：只想看协议综述的，这里每一讲讲的都是「坏掉之后你会看到什么信号」；想要厂商选型结论的，这里只给判断框架；指望读完就会调参的，这门课讲的是先看见，再谈调优。这三类读者建议先绕道，省得读到最后来骂人。

## 一个千卡集群，你要盯的十件事

可观测的业务范围看上去很宽，落到实处其实就那么几类动作。我们以一次千卡集群的长跑训练为实例，梳理一下你都要盯哪些地方：

1. 判断一条链路是不是在悄悄劣化（CRC、FEC 纠正计数，按小时算一阶差分）。
2. 找出拥塞压在哪个队列、哪个优先级上（PFC pause 收发计数、队列水线）。
3. 分清「训练慢了」是网络的原因还是框架的原因（集合通信耗时分解）。
4. 看拥塞控制到底有没有在工作（ECN 标记率，以及标记之后速率有没有真的降下来）。
5. 把一次异常落到具体路径上（拓扑、ECMP hash、rail 归属）。
6. 建立基线，让「比上周慢了 3%」这句话可算（周同比、分位数、固定窗口）。
7. 复盘事故的时间线（秒级订阅，把 PFC 暴涨和任务抖动对齐到毫秒）。
8. 判断容量与均衡（rail 之间的流量偏不偏、上行口利用率分布是不是长尾）。
9. 收敛告警（阈值、斜率、趋势三套规则，替代一屏平铺的静态阈值）。
10. 评估一次变更的代价（固件升级、路由调整前后，用同一套口径对比）。

当然，实际情况下需求可能也没这么多，因为在集群规模不大、训练步长宽松的时候，很多数靠人肉看几张图就够了。但规模一涨、训练一长，以前靠人盯的那几个数字就必须要挪进采集管道里来，靠人记是记不住的。

以上提到的只是智算网络可观测的基础应用，也是日常值守里最常见的动作（如果读者的基础和经验不足，可能需要读完下一讲、跑完第一个实验之后，再回过头来重看这一节，那时候这些条目才算真的落地）。除了基础应用，还有不少高级一点的玩法，比如把 PFC 与 ECN 的时序对齐做因果推断、用 telemetry 流按路径还原一次 incast 的完整现场，大多数同学可能从未接触过，这部分我会在后续的章节里陆续讲解。

## 三条断层：IDC 那套经验会在这里翻车

断层一，时标对不上。PFC 风暴、incast 尖刺、微突发，这些都发生在微秒到毫秒的量级上。SNMP 一分钟轮询一次，相当于拿望远镜找细菌，找不到才是正常。

断层二，粒度对不上。你盯着端口的聚合丢包数，真正出事的是 8 个队列里的第 3 个，是优先级为 4 的那条流。计数器不区分这些维度，你就永远看不见它。

这里打个好记、但不太精确的比方。银行大厅取号，VIP 窗口和普通窗口分开排队。你只统计「今天办了多少笔业务」，既看不出 VIP 窗口排了三个人，也看不出普通窗口已经等了两小时。

断层三，语义对不上。无损网络里丢包为 0 是设计出来的结果，不是健康证明。真正的前兆是 PFC pause 在悄悄变多、ECN 标记率开始往上爬、队列水线贴着顶走。这几个数字，全都在「正常范围」里面。

::: warning 三条断层会一起发作

现场最常见的误判，是拿断层三去解释断层一。「丢包是 0，说明链路没问题」，这句话在智算网络里几乎必然错。

判断依据得换成趋势和分位数：CRC 的一阶差分、ECN 标记率的斜率、P99 时延的漂移。阈值告警在这三个量上基本不说话。
:::

## 六篇不是并列的，是一条因果链

| 篇章 | 回答的问题 | 上一步的结论怎么变成下一步的前提 |
|---|---|---|
| 第一篇 两套世界观 | 为什么智算网络不能用 IDC 的那套看法 | 同步训练要求微秒级稳定 → 需要 RDMA → RDMA 不能丢包 |
| 第二篇 不丢包的代价 | 不丢包靠什么做到，代价是什么 | PFC 与 ECN 的分工决定了要看哪些计数器 |
| 第三篇 流量与连线 | 流量长什么样，路径长什么样 | 流量矩阵已知、拓扑固定，才可能做路径级归因 |
| 第四篇 把现场变成数据 | 数据从哪采，采多细 | 有了秒级订阅与路径级元数据，才谈得上判读 |
| 第五篇 从数据到结论 | 指标怎么定口径，告警怎么收敛 | 口径统一、根因可算，才谈得上缩短 MTTR |
| 第六篇 路线与收口 | 路线怎么选，能力怎么自评 | 前五篇的判据汇总成决策依据 |

跳读的代价很具体。直接从第四篇开始，你会记住「用 gNMI 订阅」，但答不出为什么非得秒级、为什么 PFC 计数比丢包计数更要紧。这部分知识，在排障现场用不出来，那时候再回来补，成本已经付出去了。

这里先不展开 PFC 的具体机制，第 05 讲会详细讲。为什么不放在这里讲？因为你要先知道自己缺的是哪一类观测，机制才记得住。等你读完第 05 讲、手上有一份真实的 pause 计数，再回来重看这三条断层，那时候它们才从说法变成检查清单。

::: info 经验映射（IDC → AIDC）

我一开始也以为丢包率就是命根子。后来把一台交换机的 pause 计数按端口和优先级拆开看，才发现真正的拥塞压根不进丢包计数器。

如果你做过微服务，这套结构并不陌生。IDC 的监控相当于看服务的平均 RT，智算网络要看的是 P99 尾延迟，以及单条 RPC 链路上每一跳各自花了多久。

你手上的分位数思维、链路追踪、根因收敛，全都能直接搬过来。缺的只是设备侧语义，也就是交换机上那些计数器到底在说什么。
:::

## 三种读法，按处境选

| 读法 | 适合谁 | 怎么做 | 代价 |
|---|---|---|---|
| **顺序通读** | 刚接手集群，还没有具体事故要处理 | 六篇顺着读，每课做完练习题 | 约 15 到 20 小时 |
| **按故障查** | 手上正压着一个具体问题 | 直接从第 07 讲的故障指纹表进入，遇到不熟的机制再回跳 | 快，但知识会留缺口 |
| **只跑实验** | 已有网络背景，想验证判断 | 从 `labs/` 目录挑实验跑，课只当参考手册 | 容易停在「跑通了」这一步 |

第三种读法有个隐性成本。实验输出得有背景知识才读得懂，「PFC pause 帧数 12 万」这个数字本身不会告诉你，它是灾难还是日常。

笔者的建议是：手上没事故就先顺序通读，压着问题就先按故障查，两者都通顺了，再回去补机制。反过来做，容易读成背书。

这一讲到这里，该交出的东西也就清楚了。读完它，你不需要记住任何技术细节，只要能做到四件事：判断自己该不该读这门课、还缺哪一块基础；用自己的话说清为什么「指标正常」和「系统健康」在智算网络里是两件事；说出六篇为什么必须按这个顺序读、跳读会亏在哪里；以及从上面三种读法里挑出适合自己当下处境的那一种。

## 三条使用约定

**实验都是教学级模型。** 每个 L1 实验的开头都有一句声明，说的是同一件事：非硬件行为等价。模型能复现因果链与量级关系，替代不了真机验证。别拿实验输出当验收依据，拿它当理解工具。

**数字都要带单位与量级。** 课程里出现的带宽、时延、比例，都是公开资料或构造示例的量级值。看到「秒级」就去想它对应哪个数量级，看到「千卡小时」就去想它等于多少钱的电费。

**术语首现给英文对照。** 智算网络的术语中文译名极不统一，PFC 有人叫基于优先级的流量控制，有人直接说 PFC，还有人写成 PFC/802.1Qbb。所以每个术语第一次出现时带一次英文全称，后面只用缩写，省得来回解释。

## 上机：看一眼轮询失真

课可以慢慢读，实验建议现在就跑一个，成本是两分钟。第一个实验是个纯 Go 的小程序，不需要 Docker，也不需要真交换机。

```bash
# 进到第一个实验
cd labs/01-traffic-model
# 跑一遍，出一张「轮询失真」表
make run
```

看那张「轮询失真」表。1 ms 采样看得见 100 GB/s 的峰，1 s 采样只剩 20 GB/s，平均值一分没变。默认参数是 4 条链路汇聚到一个 200 Gbps 端口、训练步 200 ms，你把这几个数换掉，表里的读数跟着变。这一眼大概比读三段文字管用，因为它让你亲眼看见：平均值的世界和峰值的世界，是两个世界。

## 习题

**必答 Q1**：某同事说「我们集群的丢包率是 0，链路肯定是健康的」。这句话在智算网络里错在哪，正确的判断要看什么。

::: details 参考答案与评分维度

丢包为 0 是无损网络的设计结果，并非健康证据。PFC 逐跳反压让队列不满就不丢，代价是上游被暂停。所以丢包率是「失效之后的记分牌」，不是「劣化之中的仪表」。

正确的判断看三类过程信号。一是 PFC pause 的收发趋势，按优先级与端口拆开看。二是 ECN 标记率与队列水线，代表拥塞在多大范围内被压制。三是业务侧证据：训练的每步耗时，加上集合通信耗时的分解。

再加一条方法论：看一阶差分与分位数，少看均值。CRC 从 0 到 12，在阈值体系里是正常的，在趋势上已经是光模块劣化的第一步。

**评分维度**：指出丢包 0 是无损设计而非健康证明（必需）。给出至少两个过程信号并说明为什么它们更早（必需）。提到趋势与分位数的判断方法（加分）。
:::

**必答 Q2**：你刚接手一个千卡集群，手上没有任何历史数据。给出第一周该采集什么、该建什么口径的最小方案。

::: details 参考答案与评分维度

第一周的目标是建立基线，不是建大屏。

采集层分三档。端口级：CRC、FEC 纠正、丢包、流量，10 到 30 秒一次，覆盖全部上行口。队列级：队列水线、PFC pause 收发、ECN 标记，1 到 5 秒一次，按端口与优先级拆维度。业务级：训练每步耗时、集合通信耗时分解，直接从训练框架日志拿。

口径层先定三条。CRC 增长率按小时窗口算一阶差分。ECN 标记率的分母明确写成「该端口该优先级发出的包数」。P99 时延用固定窗口，不用滑动均值。

存储上原始秒级数据只保留 7 天，聚合结果长期保留。第一周结束时导出一次全量快照，作为后续所有异常判断的对照基线。

**评分维度**：采集分档且频率与事件时标匹配（必需）。口径定义明确到分母（必需）。提出保存基线快照（加分）。只列指标名不给频率与口径（不通过）。
:::

**自测 Q3**：为什么这门课把第四篇（把现场变成数据）排在第二篇（不丢包的代价）后面，而不是先教你怎么用工具。

::: details 参考答案与评分维度

工具是手段，选什么来采是判断。第二篇讲清 PFC 与 ECN 的分工之后，你才知道队列水线比端口丢包更早、PFC pause 要按优先级拆。

先学工具的顺序会让你采一堆无用数据。数据量爆炸之后再回头质疑采集策略，成本远高于一开始就想清楚。

**评分维度**：说清「采什么由机制决定」（必需）。提到采错数据的返工成本（加分）。
:::

**思考题**：留一道不给答案的。

在你能碰到的任意一台交换机或网卡上，把一个上行口按 1 分钟、1 秒、1 毫秒三种粒度各取一次流量。你第一次看见突发，是在哪一层粒度上。

这道题没有标准答案，也不打算给。要求只有一条：交一个证据，命令加输出，或者图上的时间轴，写清端口、时间段、当时的负载。数字和别人对不上没关系，现象讲清楚就行。写完可以扔进评论区，笔者看到了会回。

## 小结

这一节的内容可以压成一句话：**指标全绿、任务变慢，这门课就是把这段黑箱缩短。**

三条断层是这门课的起点。时标、粒度、语义，三样错位的根源是同一个：同步训练把「最慢的那一份」抬到了台面上，而计数器只会告诉你平均值。

六篇顺着同一条因果链铺开。同步训练要微秒级稳定，于是上 RDMA。RDMA 丢不起包，于是要无损网络。无损网络的机制决定了该采什么数据，采到的数据决定了口径与告警。最后这些判据汇总成选型与自评。跳读不是不行，但你得知道自己在哪个环节上留了口子。

练习只给评分维度，不给对错判定。材料这么设计是有原因的：现场没有标准答案，只有能不能解释现象。

如果只能带走一条结论离开这门课，我希望是这条：**在同步训练的集群里，性能指标要按最慢的那一份来读，不能按平均来读。** 它能从网络带进存储，带进调度，带进任何一个有同步屏障的系统。

另，在阅读课程的过程中，如果你被某一讲卡住了，先别急着回头补课，跳过它继续往后读。判断力这东西，是在看过一次真实的故障之后才长出来的，讲得再细也不如你自己跑一遍。要是跑完还有疑问，来仓库开 issue，我基本都回。

## 掌故：一个躺了二十年的开关

ECN 在 RFC 3168 里出现的时候还是个「实验性选项」，之后十几年几乎没人真开。不是标准写得不好，而是开了没好处：端到端那套拥塞控制用不上它，中间设备还得为它多写一段标记逻辑，谁愿意动。

转机来自数据中心。DCTCP 和 DCQCN 把 ECN 当成信号源来用，交换机在队列快满时先打个标记，端点按标记比例降速，丢包就不用发生了。这个躺了快二十年的开关，一夜之间变成无损网络的必需品。

同样的事在 Geneve 上也有一次。它本是给网络虚拟化做封装头的，结果在带内遥测里被借去装元数据，一份为「多租户隔离」写的标准，最后在「路径可观测」上用得最多。

标准写得好不好，跟它什么时候被用起来，是两件事。你手上那套面板里的每个计数器，背后差不多都有这么一段历史。

## 出处与延伸

#### 1. [Congestion Control for Large-Scale RDMA Deployments（SIGCOMM 2015）](https://doi.org/10.1145/2785956.2787484)

DCQCN 的原论文，也是本课程第二篇几乎所有判断的出处。它的可贵之处在于把「为什么无损网络也必须有拥塞控制」讲成了一个完整的工程故事，而不是丢几个公式了事。想搞清楚 ECN 标记率和降速动作之间的对应关系，读这一篇比读十篇二手总结强。

#### 2. [Google SRE Workbook — Implementing SLOs](https://sre.google/workbook/implementing-slos/)

第五篇关于口径的写法，源头在这里。它的核心思想说出来平淡无奇：先把分母定死，再谈指标。可惜国内太多面板连分母都没写清楚，「错误率 3%」到底是按请求数还是按字节数算的，只有做图的人知道。

#### 3. [OpenConfig — public models](https://github.com/openconfig/public)

本课程里 `interfaces` 和 `qos` 两类指标的命名，基本都对着这份模型来。它的好处是把「一个计数器叫什么名、在哪个层级、有没有按队列拆开」写成了机器可读的 schema，你跟厂商、跟平台组对齐口径的时候，有它就有了共同的参照物。

#### 4. [RFC 8926 — Geneve](https://www.rfc-editor.org/rfc/rfc8926.html)

带内遥测（INT）要在报文里塞元数据，塞的地方就是封装头。读它的交换机压力与元数据 TLV 定义就够了，不必通读全文。

#### 5. [NVIDIA DGX SuperPOD Reference Architecture](https://docs.nvidia.com/dgx-superpod/reference-architecture-scalable-infrastructure-h100/latest/index.html)

千卡级 fabric 的公开设计参考。读它的时候别只看拓扑图，重点看它对「每张网卡走哪个 rail、哪一层用光、哪一层用铜」的取舍，那些取舍里藏着可观测的坑。

#### 6. 其余几篇

- [NCCL Documentation — Collective Operations](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)（同步集合通信的语义，AllReduce 的等待关系）

这一份不必现在读，等你要把面板口径和设备侧字段对齐的时候再翻回来。
