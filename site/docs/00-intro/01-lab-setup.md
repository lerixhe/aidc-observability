工欲善其事，必先利其器。本节的学习目标只有一个：把这门课的实验在你这台机器上跑起来，跑通一个就够。

本节的内容是这门课里最简单最容易上手的部分。如果你手上已经有一台装好 Go 的机器，从珍惜生命的角度出发，你可以略过安装那几段，直接跳到 `labs/00-setup` 跑一次自检。要是连 Go 也没有，往下看，装一个就好，别的事情先不用管。

要跑实验，我们先从环境说起。

## 交付

- 从三条环境路线里选一条并跑通，其中本机路线只需要 Go
- 读懂 `labs/00-setup` 的体检报告：哪些实验能跑、缺什么工具、缺了会怎样
- 跑出第一个实验结果，并解释 `expected/` 目录为什么是这套实验能长期维护的关键
- 说清 L1 与 L2 的分界，以及为什么 L2 的实验排在后面

## 三层依赖

这门课的环境分三层。只读层什么都不用装，L1 层只依赖 Go，`go run .` 直接出结果，五分钟够。L2 层要真拓扑，得有 Docker、Linux 和 containerlab。**真正卡住人的是准备顺序，技术本身不难。**

| 层 | 依赖 | 覆盖的实验 | 缺了会怎样 |
|---|---|---|---|
| **只读层** | 无 | 全部课程的机制讲解 | 照样能读完，判读部分会缺手感 |
| **L1 计算层** | Go ≥ 1.22 | `00-setup`、`01-traffic-model`、`02-pfc-sim`、`04-nccl-trace`、`06-gnmi-mock`、`07-int-path`、`08-pipeline`、`09-slo`、`10-rca`、`11-case-study` | 十个实验全部跳过 |
| **L2 拓扑层** | Docker、Linux、containerlab | `03-fault-inject`、`05-clos-topo` | 只是注入与真散列跑不了，两个 lab 的剧本与模型仍可跑 |

两层一起准备的坏处，见过的人都记得。装 Docker、配特权、找 Linux 内核，报一个错查半天，最后实验没跑起来，课也没读下去，赔进去的是整门课。

分层的道理很实在。PFC 与 ECN 是硬件行为，软件仿真做不到行为等价。硬要把这一层做全，读者会在第一条 `docker` 命令处流失，流失的方式还挺安静：装到一半，报个错，然后关掉页面，课也就此放下了。

所以 L1 走「数据面模型」路线，用参数化的队列模型复现因果链和量级关系。L2 走「真拓扑」路线，容器里的交换机和真网卡，代价是特权与虚拟机。

L2 那两个 lab 都做成了双模式。默认模式只生成剧本与模型结论，不需要 Docker：`make run` 照常出结果，`make deploy` 才需要 containerlab。缺 Docker 时是降级体验，不是全有或全无。

## 实验环境怎么装

体验这门课的实验，L1 需要一个 Go；想跑 L2，再加 Docker 与 Linux 环境。主要方式有三种：

1. 本机直跑，装一个 Go。
2. devcontainer，仓库自带配置，Go、Docker、Python 都在镜像里。
3. 在浏览器里直接开 Codespaces，连仓库都不必克隆。

具体操作如下。下面的命令块不带提示符，它是照抄就能粘进终端的形态，不是交互会话记录。

**本机直跑方式**

```bash
# 确认版本，需要 1.22 或更高
go version
# 进到环境自检实验
cd labs/00-setup
# 跑一次，打印本机能跑的实验清单
make run
```

macOS、Linux、Windows 都可以。这条路线最省事，代价是没有 L2。笔者在三个操作系统上分别装过一遍，最省事的永远是这条最朴素的路。

**devcontainer 方式**

仓库自带 `.devcontainer/`，镜像基于 `go:1.22-bookworm`，装了 docker-in-docker 与 python3。

```bash
# 拉起容器，工作区挂到当前目录
devcontainer up --workspace-folder .
```

容器起来后会自动跑一次环境自检，也就是 `postCreateCommand` 里那句 `go run .`。VS Code 里选 "Reopen in Container" 效果一样。

**Codespaces 方式**

网页打开仓库，点 Code → Codespaces。代价是消耗免费额度，好处是 L2 实验在云端跑，不用折腾虚拟机。

::: info 经验映射（IDC → AIDC）

这套环境设计对应你很熟的「本地跑单测，CI 跑集成」。

L1 是本地单测：快、零依赖、随时跑。L2 是集成测试环境：慢、要外围系统、按需启动。把两者混成一条命令，等于要求每个开发者在本地装齐生产依赖。

对后端来说这个判断几乎不用想，但换成网络实验，很多人第一反应是「要装 Docker 才算完整」。

:::

## 只读层：什么都不用装

这一层没有实验，只有课件。全部课程的机制讲解都在这里，打开浏览器就能读。

别小看这一层。三层依赖里它覆盖的读者最多，大多数人是先读课件、后跑实验，也有相当一部分读者跑完一两个实验就够了。判读的手感要靠实验养，读的门槛却可以压到零。

## L1 计算层：一个 Go 就够

这一层是本课程的主体，十个实验全部只依赖 Go 标准库，没有 npm，没有 pip，没有绘图依赖。跑法统一是 `cd` 进目录再 `make run`。

一开始值得按顺序跑的两个：

- `01-traffic-model`，小流随机到达与同步突发的队列差异。第 02 讲《智算网络的范式差异》里那张「轮询失真」表就是它出的。
- `02-pfc-sim`，水线阈值、pause 反压、ECN 降速三者的因果。它是本课程的核心实验，覆盖第 05 讲与第 06 讲两讲。

关于 PFC 的机制细节，请阅读第 05 讲《PFC 逐跳反压》。关于 ECN 标记率怎么换算成降速，请阅读第 06 讲《ECN 与 DCQCN》。这两个 lab 的模型参数就照着那两讲的公式来的，参数含义在课件里能一一对上。

剩下的八个实验按课的顺序排：`04-nccl-trace` 配第 08 讲，`06-gnmi-mock` 配第 11 讲，`07-int-path` 配第 12 讲，`08-pipeline` 配第 14 讲，`09-slo` 配第 15 讲，`10-rca` 配第 16 讲，`11-case-study` 配第 21 讲。哪一讲读着顺手，就跑它对应的那个。

## L2 拓扑层：Docker 加 Linux

这一层只有两个实验，都要真拓扑：`03-fault-inject` 做四类故障的注入与指纹判读，`05-clos-topo` 做流数与 hash 口径的极化对照。

代价写在依赖里：Docker、Linux 内核、containerlab，还有特权容器与网络命名空间。Apple Silicon 上还要多一层镜像架构的判断。这部分折腾起来没有上限，理由前面说过了，别为它卡住整门课。

## 环境自检

`labs/00-setup` 不模拟网络，它只回答一个问题：这台机器能跑哪些实验。输出三段。

```text
工具               版本           状态     说明
go               1.22.5       ✅
Docker           —            ❌      未安装，或不在 PATH 里
python3          3.12.3       ✅

lab 盘点（12 个已落地 / 共登记 12 个）
  目录                 层    需要工具                 对应课   可跑   说明
  00-setup           L1   go                   01      ✅    环境自检
  02-pfc-sim         L1   go                   05,06   ✅    PFC / ECN / DCQCN 参数化队列模型
  03-fault-inject    L2   go+docker+clab       07      ❌    缺 docker+containerlab · 四大故障的注入剧本与遥测指纹判读
```

上面这段是脚本原样输出，符号照抄，没做改写。

三个字段各有分工。**可跑**列里能跑、缺工具、还没落地是三种状态。**层**列告诉你缺的是哪一层。**说明**列在缺工具那行会写清缺哪个，不用自己猜。

加上 `-try` 会多跑一轮冒烟检查，对每个可跑的 L1 实验执行 `go vet` 与 `go test`。CI 用的就是这个开关，有失败则退出码为 1。

```bash
# 进到自检实验
cd labs/00-setup
# 冒烟检查全部 L1 实验
make try
```

## 跑出第一个结果

队列模型实验是本课程的核心实验，覆盖第 5、6 两讲。

```bash
# 进到 PFC / ECN 模型实验
cd labs/02-pfc-sim
# 默认场景，打印时序与汇总
```

## 为什么每个实验都有 expected/

`expected/` 里放的是上一次人工确认过的输出样本。CI 拿当前输出和它逐字比对。

这个设计解决一个长期的维护问题。模型参数一改，行为就变，而这种变化通常悄无声息。

有了对照样本，改动会在 diff 里显式出现。要么你承认这是有意的行为变化，并更新样本。要么你发现这是个 bug。

```bash
# 进到核心实验
cd labs/02-pfc-sim
# 重新生成对照样本
make expected
# 先看差异，再决定提不提交
git diff
```

顺序不能反。**先 diff 再提交，先提交再 diff，等于把 bug 锁进标准答案。**

::: warning 自校验失败先看 diff，别急着重生成

CI 报 `expected/` 不一致时，正确的第一反应是看差异内容，判断模型改动是不是预期的。

直接 `make expected` 覆盖，会让「标准答案」跟着当前实现走。对照样本就退化成了快照，失去发现回归的能力。

:::

## 实验的通用规则

L1 和 L2 这两层，共享下面三条通用规则。记住这三条，出问题的时候不用去翻代码。

1. 没有目录就自己建。

    `out/` 不存在时，`make run` 会先建好再写文件。跟 Redis 里 `rpush` 一个不存在的列表会顺手创建是一样的道理，你不用先 `mkdir`。

2. 缺工具就降级，不报错退出。

    缺 Docker 时 `03-fault-inject` 只出剧本与模型结论，`make run` 照常给你结果，只是不动真拓扑。降级方式写在输出末尾，一眼能看见。

3. 跑完就销毁。

    L2 的容器是一次性的，`make deploy` 起来，`make clean` 拆掉，不留残骸。占着内存和端口不定时清理，最后一定会有一台机器被 `clab` 的残留容器拖垮。

| 本地单测 + CI 集成 | L1 与 L2 分层 |
| 快照测试（snapshot test） | `expected/` 目录与 `make expected` |

## 思考 & 作业

**必答 Q1**：某同事在 macOS 上装了 Docker Desktop，`docker --version` 正常，跑到 L2 实验时报错。给出你的排查顺序。

::: details 参考答案与评分维度

第一步分清楚 `--version` 和 `info` 的区别。前者只读二进制，后者要连 daemon。macOS 上常见情况是二进制装了、Docker Desktop 或 OrbStack 没启动。

排查顺序如下。

1. 跑 `docker info` 确认 daemon 活着。
2. 确认容器能拿到特权与网络命名空间，`docker run --rm --privileged alpine ip link` 是个快速验证。
3. 看 containerlab 版本与内核要求。
4. 才轮到实验本身。

如果这台机器是 Apple Silicon，还要多一层判断：镜像架构是否匹配。架构不对时，错误信息通常指向二进制无法执行，而不是网络配置。

**评分维度**：区分 `--version` 与 `info`（必需）。有分层排查顺序而不是直接改配置（必需）。提到架构问题（加分）。
:::

**必答 Q2**：`expected/` 对照样本和「每次改动都更新样本」这两种做法，差别在哪。给出一个反例。

::: details 参考答案与评分维度

差别在样本的地位。对照样本是外部契约，改了要解释。每次跟着实现更新，样本就退化成了当前行为的快照，只能反映「现在是什么」，不能反映「应该是什么」。

反例很具体。队列模型的阈值判断里有一个差一错误，某次改动让 pause 提前一个时间单位触发。如果样本跟着实现更新，diff 里只有一堆数字变化，没人会追问。如果先看 diff 再看改动意图，就会发现「时序整体左移了一个单位」这种不该出现的变化。

**评分维度**：说出样本是契约而非快照（必需）。给出具体反例且能指认 diff 里该看什么（必需）。提到评审流程的配合（加分）。
:::

**自测 Q3**：为什么 L1 实验要求零第三方依赖，只用 Go 标准库。

::: details 参考答案与评分维度

核心原因是流失率。第三方依赖意味着代理、版本、校验和、平台差异，每一样都能挡掉一批读者。

另一个原因是可审查性。零依赖的代码读者能一行行读完，模型的假设、参数的来源、公式的边界都在明处。引入绘图库或统计库之后，关键计算会藏进黑箱，教学价值反而下降。

**评分维度**：给出可复现性与流失率的理由（必需）。提到可审查性（加分）。
:::

**自测 Q4**：如果只在 L1 层做实验，你会漏掉哪一类认知。

::: details 参考答案与评分维度

会漏掉「真实的随机性」。L1 是有确定性的模型，参数一样，输出一样。真机上有抖动、有芯片排队实现的差异、有驱动与固件的怪癖。

也会漏掉「配置的肉身」。PFC 水线怎么设、ECN 门限怎么配、DCB 三件套怎么落到设备上，这些都是 L2 才能碰到的手感。

**评分维度**：指出模型与真机在随机性与实现细节上的差异（必需）。举出至少一个 L2 才能练到的动作（加分）。
:::

**思考题**：留一道不给答案的。如果让你删掉一个 L1 实验以减少维护成本，你删哪个，怎么保证被判读能力的缺口不扩大。

## 小结

依赖分三层。只读层什么都不用装，L1 只要一个 Go，L2 要 Docker 加 Linux 加 containerlab。环境三条路，本机直跑最省事，devcontainer 和 Codespaces 是给需要 L2 又不想折腾虚拟机的人。

体检报告看三个字段就够了：可跑、层、说明。冒烟检查加 `-try`，CI 用的就是这个开关。

实验能不能长期维护，全在 `expected/` 那份人工确认过的输出样本上。参数的改动一定会在 diff 里显形，顺序是先 diff 再提交，反了就等于把 bug 锁进标准答案。

跑通一个实验之后，别急着往下读。把 `out/` 里的 CSV 拉出来画一张图，横轴时间，纵轴队列深度，你会先看见自己之前没注意过的东西。这一眼比读三段文字值。

另，如果这一讲你只跑通了 `00-setup`，就已经可以往下走了。实验是配菜，读机制才是主食，缺了手感可以后补，别在安装环节把耐心耗光。**大家加油**！⛽️
