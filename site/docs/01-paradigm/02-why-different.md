**智算网络是一张不许丢包的网**！这点必须铭记。

也许你会怀疑，以太网天生就丢包，怎么可能有一张不许丢包的网。很抱歉，训练集群里它就是不许丢，而且它不许丢的办法不是把重传做得更好，是让发送端在队列撑破之前自己减速，你的怀疑暴露了你还在用 IDC 的直觉。莫要瞧不起有损网络那一套。TCP 在有损的土壤上跑了三十年，QUIC 也是从同一片土里长出来的，它们都是高性能传输的典范，只是它们默认的那几个前提，在训练集群里一个都不成立。

**智算网络靠什么做到不丢包？**

靠链路自己带着反压。交换机的出口队列一涨，它就往上游打 pause 帧，上游停一下，队列退回去；队列涨得没那么急的时候，它先在报文头上盖一个 ECN 标记，接收端把这条通知回给发送端，发送端自己把速率降下来。正因为这套机制是配置出来的，所以要小心规划无损域的范围，范围画大了，一处打嗝能顺着链路传出去很远。

**那上万个源同时发的时候呢？**

这个问题，很多做了十几年 IDC 的人都答不上来，因为他们没听过 incast 这个词，没见过 AllReduce 的同步屏障，也没算过一条路径在面板上的分母是多少。

大象流
--
传统 IDC 里跑的流量是碎的。用户请求从南北向进来，服务之间的调用在东西向转一圈，这批流很小，多数在 KB 到 MB 之间，数量多到没法逐条看，到达时间随机，偶尔把某个队列顶满，几毫秒内自己就排空了，所以你看聚合、看趋势就够用，从来不需要知道某一条流现在在哪条路上。

AI 训练集群里没有用户请求。一台八卡机器训练的时候，主要工作是和另外几百台到上千台机器交换**梯度数据**，单条流能持续一整个训练周期，中间不降速，一张 400 Gbps 的网卡被它一条流压满，这就是大象流（elephant flow）。比大象流更难办的是它们不约而同，每算完一轮，所有参与方都要在同一时刻把结果往同一个方向汇聚，上万个源同时朝一组端口发送，出口队列在几毫秒里被打满，这就是 incast，它不是偶发事故，是每个训练步都重复一次的固定节奏。

那么静态 hash 还够用吗？小流时代够用，hash 落空只是让一条小流多走一跳，几毫秒就散了。大象流时代它变成了一次赌博，两条梯度流被 hash 到同一条上联上，那条上联直接压满，同一侧另外三十一条空着，可是面板上看不见。

看一台 64 端口的交换机，上下联各 32。丢包率贴着零走，端口利用率 40% 出头，时延和抖动的曲线上看不出台阶，阈值告警一条没响，训练任务每步从 380 毫秒掉到 520 毫秒，掉了整整一周，没人能从面板上说出原因。查到最后就是一把 hash 摇得不巧：两条梯度流压在了同一条上联上，那条上联跑满，对面那 31 条空着。面板没算错，指标也没采错，错在分母，单条上联的流量摊到整机 64 个端口上只占 1.5%，而那条路径上，它自己是 100%。

逐跳反压
--
PFC 是逐跳的，一跳管一跳。1 号口往 2 号口发，2 号口的出口队列涨到阈值，它回头给 1 号口打 pause，1 号口把这条优先级上的发送停住，队列就退回去了，等水位降下来再撤掉 pause，这叫逐跳反压，也叫无损队列。它只保证这一跳不丢，不保证这条流不慢，前面排着的包该等还是得等。

ECN 则是软的。出口队列越过 Kmin 还没到 Kmax，交换机不给上游打 pause，只在报文头的 ECN 两位上盖一个「拥塞经历」的标记，接收端的网卡把这条标记随 ACK 回给发送端，发送端按 DCQCN 的规则把速率往下调，越接近 Kmax 调得越狠。软的那一半先把速率收一收，硬的那一半才轮到 pause 出手，这套次序配不好，pause 帧就会被当成人人都有的日常开销，天天在打，谁都不觉得是故障。

回到上面那台交换机。面板上那条利用率是这么来的：

```py
# 整机 64 个端口取平均，这是曲线上的一个点
port_rate = sum(rx_bytes[p] for p in all_ports) * 8 / 64
# 17 号上联自己是 100%，进到这个式子里是 1.5%
# 另外 31 条上联是 0，它们把 17 号摊平了
```

**所谓丢包为零，其实是整张网在替你排队**

那条贴在 0 上的丢包率曲线，说明的是反压正在工作，不是链路通畅。机制彻底失效的那一刻，这条线往往还在 0 上待着，因为包已经不走到能丢的那一步了，它们卡在队列里，或者卡在 pause 里。

丢包语义
--
这一条最要紧，后面几乎所有口径调整都从这里派生。

有损网络里，丢包率 0.01% 属于正常波动，内核静默重传，应用层根本不感知，所以丢包在面板上是一个统计数字，趋势抬头才需要看一眼，作用是给你一条排障线索。

无损网络里，重传的责任已经从内核协议栈挪走了（见 [RDMA：AI 训练为什么绕过内核](./03-rdma.md)），数据面跑在网卡上，内核连丢没丢都不知道，也没有协议栈那套按字节补洞的精细恢复，RDMA 的重传是窗口级的重发，一次丢包往往连带几十个包重来一遍，恢复期间这次内存操作整体挂起，所以工程上普遍把丢包率压到 `1e-5` 量级。在这里，丢包是机制故障已经发生的证据，PFC 没配上、拥塞参数算错了、死锁的前兆，从统计量变成了信号量，日常要盯的主指标也跟着换成 PFC pause 次数、ECN 标记率、队列水线。

同步屏障
--
IDC 里网络抖一下，影响的是一批请求，切个流、重试一次，用户那边多半察觉不到。

万卡集群不是这样。训练是**高度同步**的，一条链路卡住几个 Rank，其余上万张卡一起停在屏障上等，谁都走不了。恢复手段基本只有一条，从上一个存档点重跑，两次 checkpoint 之间通常隔十几分钟到几十分钟，这段时间的计算全部作废。损失可以直接按卡时算：卡数乘回退时长乘单卡时成本，一万张卡退一次，账面上是万卡时。

所以智算网络对 MTTR 的要求从小时级压到**分钟级**，这个数字几乎出现在每一份智算网络 SRE 的岗位描述里，来源就是上面这笔账。

采样周期
--
传统设备采集走 SNMP 那一路，分钟级轮询端口计数器，这个粒度放在无损网络里几乎是不堪用的。

PFC pause 是微秒级的事件，一次风暴可以在几秒内把队列打满，再顺着链路往外扩散，分钟级采样只看见风暴前后的平静。incast 是亚秒级的事，轮询取回来的是平均值，而平均值在 incast 场合永远是正常的。于是设备侧改用 **gNMI 流式订阅**（见 [gNMI + OpenConfig 遥测](../04-telemetry/11-gnmi.md)），交换机按秒级、亚秒级把队列、ECN、pause 推给采集端。对采集侧来说，变化只是数据源从「我去拉」换成了「它推给我」，后面的管道（消息队列、流处理、时序库）与既有体系同构，能直接复用。

**从 IDC 转过来的人，能力不是负担**

不过得逐项判断能不能搬。链路级主动探测、五元组 hash 路径覆盖更值钱，因为 hash 极化是智算集群里高频的事故模式，只有路径级观测能看见；时序管道直接复用，缺的只是数据源；告警收敛与根因分析要重做，指标口径变了，阈值和关联规则一条都用不上；以丢包率、时延、抖动为主的面板必须替换，主指标换成 PFC pause、ECN 标记率、队列水线、逐路径丢包；「网络故障就切流兜底」这套处置习惯不成立，训练流量没法切，只能定位然后尽快恢复。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：AI 训练网络为什么要把丢包率压到 `1e-5` 量级以下？「TCP 反正会重传」这句话错在哪？

::: details 参考答案与评分维度

「TCP 会重传」在有损网络里成立，因为重传由**内核协议栈**完成，代价是一个 RTT，业务几乎无感。RDMA 绕过了内核，数据面跑在网卡上，没有协议栈兜底，重传粒度是窗口级的，一次丢包连带几十个包重发。

更要紧的是**同步放大**。AllReduce 每一轮都要等所有 Rank 到齐，一个包的重传延迟会传导成整个训练步的等待，一万张卡一起等。丢包吃掉的是全局同步的时间，不是一点带宽。这是必须从机制上避免丢包的根因。

**评分维度**

- 说出 RDMA 绕过内核，丢失了协议栈的重传兜底（必需）
- 说出重传代价在同步训练里被放大到全局（必需）
- 提到 PFC / ECN 是「避免丢包」而非「丢了再补」（加分）
- 只回答「RDMA 快、TCP 慢」而没有触及重传语义（不通过）

:::

**必答 Q2**：把维护中的 IDC 监控系统原样搬到万卡智算集群，先不管能不能采到设备数据。**能立刻发现哪类问题，又会漏掉哪类？** 各举两个以上并说明理由。

::: details 参考答案与评分维度

能发现的：

1. **链路彻底中断**。探测器到不了、端口 down，任何监控体系都看得见。
2. **带宽利用率异常 / 长期饱和**。端口计数器级别的现象，老体系看得见，只是粒度和阈值不一定合适。
3. **端到端时延劣化**。基于探测包的方案能感知到某条路径变慢。

会漏掉的：

1. **PFC 风暴与 PFC 死锁**。老体系没有 pause 帧计数与持续时长指标，风暴发生时端口利用率甚至可能是「正常」的。
2. **incast 造成的微突发与 ECN 标记**。分钟级轮询取平均，亚秒级突发被抹平。
3. **hash 极化 / 单条大象流打满某条路径**。设备级聚合指标被稀释，只有逐路径观测看得见。
4. **单个光模块的渐进劣化**，比如 FEC 纠错计数上升、误码增加。不在老指标集里。

**评分维度**

- 能区分「现象层面能看见」与「有指标能定位」（必需）
- 漏掉项至少覆盖 PFC / ECN / 微突发 / 光模块中的两项（必需）
- 说明「为什么漏」是无指标口径还是粒度不够，而不是只说「没做过」（必需）
- 能主动提出补救方向，比如新增 pause / ECN 指标、路径级探测、秒级订阅（加分）

:::

**自测 Q3**：AllReduce 的同步突发和电商大促的流量洪峰，最本质的两个区别是什么？

::: details 参考答案与评分维度

① **周期性**。大促洪峰是事件驱动的偶发流量，incast 是每个训练步都发生的固定节奏。正因为可预测，才有可能通过拓扑与参数预调优，比如 rail-optimized 拓扑、拥塞控制参数。

② **同步性与木桶效应**。大促流量从大量随机入口汇聚，压力在时间和空间上被摊薄。incast 是上万个源在**同一时刻**朝同一目的地倾泻，瞬时压力远超平均负载，任何一个 Rank 慢都会拖住全体。

**评分维度**：两点各 1 分。额外指出「可预测 → 可预调优」或「木桶效应 → 单个慢节点即全局慢」加 1 分。

:::

**自测 Q4**：为什么说路径级覆盖在智算网络里比在传统 IDC 里更值钱？

::: details 参考答案与评分维度

大象流加 hash 分担的组合，让「某一条路径劣化」既高频又隐蔽。单条大象流哈希到某条路径把它打满，或者一个坏光模块只影响个别链路。设备级聚合指标会把这类局部劣化稀释到看不见：一台 64 端口的交换机上，1 条路径只占 1.5%，聚合指标永远显示正常。

只有逐路径观测能把「某条 ECMP 路径被单流打满」这类问题暴露出来。路径级探测观测的是**流量实际走过的那条路**，而不是设备的平均表现。

**评分维度**

- 说出聚合指标会稀释局部劣化（必需）
- 说出大象流使单路径饱和成为高频模式（必需）
- 能给出数量级直觉（1 条路径 / 64 端口约 1.5%）或具体观测手段（加分）

:::

## 小结

四条假设换下来，工具清单没变，判断依据全换了。流量从南北向的小流变成了东西向的大象流，上面还叠着一层 AllReduce 的同步突发；丢包从背景噪声、排障线索，变成机制性故障的信号，主指标换成 PFC pause、ECN 标记率、队列水线；故障代价从「一批请求变慢」变成「全体停摆外加 checkpoint 回退」，MTTR 压到分钟级；采集从 SNMP 分钟轮询换成 gNMI 秒级订阅，管道能直接复用，缺的只是数据源。

::: tip 本课要点

**同一张网，四个默认假设全得换。**

- **流量模型**：南北向小流 → **东西向大象流 + AllReduce 周期性同步突发（incast）**
- **丢包语义**：丢包从「背景噪声 / 排障线索」变成「**机制性故障的信号**」。日常主指标换成 PFC pause、ECN 标记率、队列水线
- **故障代价**：网络故障等于全体训练停摆加 checkpoint 回退，MTTR 要求**分钟级**
- **遥测粒度**：SNMP 分钟轮询 → **gNMI 秒级流式订阅**。数据管道可直接复用，缺的只是数据源
- **能力映射**：路径级覆盖在智算网络**更值钱**。发现环节你已有积累，定位与恢复是学习方向

:::

::: info 关于文中那几个数字

`1e-5` 量级的丢包率要求是业界工程实践的常见目标，任何 RFC 都没有强制规定。同一个集群里，不同业务、不同厂商的口径可能有差异。遇到具体数字，以所在环境的设计文档为准。

:::

**六十分钟聚合出来的图，永远不会有尖刺。** 看到一条平线先别松手，先问它是什么窗口算出来的，这一问能救掉大半次误判。留一个思考题：手上那张老面板，如果只允许保留一个指标带到智算网络里，留哪个，为什么。
