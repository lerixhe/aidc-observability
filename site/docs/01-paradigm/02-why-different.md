**智算中心里丢包为零，不能说明网络健康！** 这点必须铭记。

也许你会怀疑，丢包为零不就是最健康的状态。很抱歉，无损网络里那个零是机制配置出来的结果，它的意思是「反压正在工作」，不是「一切正常」，而机制彻底失效的那一刻，面板上那个零往往还在。

莫要瞧不起有损网络那一套。小流、随机到达、丢一点交给 TCP 补回来，这套设计在 IDC 里被验证了二十多年，它在这里不够用，是因为它假设的几个前提在训练集群里一个都不成立。

说一个案子。一台 64 端口的交换机，上下联各 32；丢包率贴着零走，端口利用率 40% 出头，时延与抖动的曲线看不出台阶，阈值告警一条没响；可训练任务每步从 380 毫秒掉到 520 毫秒，掉了整整一周，没人能从面板上说出原因。

查到最后是两条梯度流被 hash 到了同一条上联上，那条上联跑满，同一侧另外 31 条空着。面板没出错，指标也没出错，错在分母：单条上联的流量在整机分母里只占 1.5%，那条路径上的问题是它自己的 100%，落到面板上就是 1.5%。

这一篇不引入新工具，只把这四条假设逐条拆开，后面每一篇讲什么、为什么讲，都建立在这四条之上。

## 交付

- 说出两边的四个差异：流量模型、丢包语义、故障代价、遥测粒度，并讲清每个差异的成因
- 解释「TCP 反正会重传」这句话在 AI 训练网络上为什么站不住
- 把手上已有的 IDC 监控能力逐项过一遍，分清哪些能直接搬、哪些必须换口径
- 建立最基本的指标直觉：无损网络里丢包是故障信号，日常主指标换成 PFC pause、ECN 标记率、队列水线

## 流量模型：从随机小流到大象流

传统 IDC 跑的是线上业务，用户请求从南北向进出，服务之间的调用在东西向流动，这批流量流很小，多数在 KB 到 MB 级，数量极多，到达时间随机，偶尔把某个队列顶满，几毫秒内自行排空，所以看聚合、看趋势就够用。

AI 训练集群里没有用户请求。一台 GPU 服务器（通常 8 张加速卡）训练时的主要工作，是和另外几百台到上千台机器交换**梯度数据**，单条流的量级完全不同：一次 AllReduce 里，参与方之间可以把 200 Gbps 甚至 400 Gbps 的端口用满，一条流持续一整个训练周期，中间不降速，这是典型的大象流（elephant flow）。

比大象流更难处理的是同步性。分布式训练每算完一轮就往同一个目的地汇聚数据，所有 worker 在同一时刻发起，上万个源同时朝一组端口发送，出口队列在几毫秒内被打满，这就是 incast，它是每个训练步都重复一次的固定节奏，不是偶发事件。

| 维度 | 有损 IDC（小流为主） | 智算中心（大象流为主） |
|---|---|---|
| 流向 | 南北向为主 | 东西向为主 |
| 单流特征 | KB～MB，数量极多、随机 | 单流打满端口，持续整个训练周期 |
| 负载分担 | 静态 hash 大致够用 | hash 一旦失衡，某条路径直接被单流打满 |
| 拥塞形态 | 偶发，队列很快排空 | AllReduce 周期性同步突发（incast） |

那么静态 hash 还够用吗？小流时代够用，因为哈希落空只是让一条小流走了远路，几毫秒就散掉了。大象流时代它变成赌博：哈希结果一旦把两条大象流压在同一条路径上，那条路径直接被单流打满，而在设备级聚合指标里，一台 64 端口交换机的分母是整机流量，单条路径的异常占不到 2%，看不出任何异常。

上面那个案子就是这么来的：链路上什么都没坏，只是这一把 hash 摇得不巧。另外 31 条上联空着，也不会有人报警。

## 丢包语义：从统计量到信号量

四个差异里这一条最要紧，后面几乎所有口径调整都从这里来。

有损网络里，丢包率 0.01% 属于正常波动，TCP 静默重传，应用层不会感知，所以丢包在面板上是一个统计数字，趋势抬头才需要看一眼，作用是提供排障线索。

无损网络里，重传的责任已经从内核协议栈移走了（见 [RDMA：AI 训练为什么绕过内核](./03-rdma.md)），数据面跑在网卡上，内核不知道丢了包，也没有协议栈那套按字节补洞的精细恢复，RDMA 的重传是 Go-Back-N 式的窗口重发，一次丢包往往触发几十个包的重发，恢复期间这次内存操作整体挂起，于是整张网必须靠 PFC / ECN 从机制上避免丢包（见 [PFC](../02-lossless/05-pfc.md) 与 [ECN + DCQCN](../02-lossless/06-ecn-dcqcn.md)），工程上普遍要求丢包率低到 `1e-5` 量级。

::: warning 关键推论

无损网络里，**丢包意味着机制性故障已经发生**：PFC 失效、配置错误、死锁前兆。它从统计量变成了信号量。

日常要盯的主指标也跟着换了一组：**PFC pause 次数、ECN 标记率、队列水线**。老面板的阈值调紧没有用，口径本身不对。
:::

## 故障代价：从一批请求到全体停摆

传统 IDC 里网络抖一下，影响的是一批请求，切个流、重试一次，用户那边多半察觉不到。

万卡集群的约束完全不同，训练是**高度同步**的，一条链路出问题卡住几个 Rank，其余上万张卡一起停在屏障上等，谁都走不了。

恢复手段基本只有一条：**checkpoint 回退**，从上一个存档点重跑。两次 checkpoint 之间通常间隔十几分钟到几十分钟，这段时间的计算全部作废。一次网络故障的损失可以直接按卡时算：卡数 × 回退时长 × 单卡时成本，一万张卡回退一次，损失以万卡时计。

所以智算网络对 MTTR 的要求从小时级压到**分钟级**，这个要求几乎出现在每一份智算网络 SRE 的岗位描述里，原因就是上面这笔账。

## 遥测粒度：从分钟到毫秒

传统设备采集多走 SNMP 那一路，分钟级轮询端口计数器，这个粒度放在无损网络里不够用。

PFC pause 是微秒级的事件，一次风暴可以在几秒内把队列打满并沿链路扩散开，分钟级采样只看到风暴前后的平静。incast 是亚秒级事件，轮询取到的是平均值，而平均值在 incast 场景里永远正常。

那要采多密才算够？智算网络于是改用 **gNMI 流式订阅**（见 [gNMI + OpenConfig 遥测](../04-telemetry/11-gnmi.md)），交换机按秒级甚至亚秒级把队列、ECN、pause 指标推给采集端。对采集侧来说，变化只在于数据源从「我去拉」变成「它推给我」，后面的管道（消息队列 → 流处理 → 时序库）与既有体系同构，可以直接复用。

## 经验映射：哪些能搬

从 IDC 转过来的人，能力不是负担，逐项判断能不能搬：

| 已有能力 | 价值 | 说明 |
|---|---|---|
| 链路级主动探测 / 五元组 hash 路径覆盖 | **更值钱** | 大象流时代，hash 极化（多条大象流哈希到同一路径）是高频事故模式，只有路径级观测能发现 |
| 时序数据管道（采集 → 消息队列 → 存储 → 查询） | 直接复用 | 与设备侧 gNMI 订阅只是数据源不同 |
| 告警收敛 / 根因分析（RCA） | 需改造 | 指标口径变了，阈值与关联规则要重做 |
| 丢包率 / 时延 / 抖动为主的面板 | 必须替换 | 主指标应为 PFC pause、ECN 标记率、队列水线、逐路径丢包 |
| 「网络故障 → 切流兜底」的处置习惯 | 不成立 | 训练流量无法切流，只能定位并快速恢复 |

::: info 经验映射（IDC → AIDC）

需要校正的是发现环节的定位。你熟悉的「30 分钟发现」只覆盖 MTTR 的三个阶段之一，智算场景要求发现、定位、恢复全链路分钟级。发现这块你已有积累，要补的是定位（设备遥测关联）与自愈（自动化处置），第五、六篇展开。
:::

## 值班台那张表

| 观测项 | 有损 IDC 的典型做法 | 智算网络的典型做法 |
|---|---|---|
| 采集方式 | SNMP 轮询，分钟级 | gNMI 流式订阅，秒级 / 亚秒级 |
| 主指标 | 丢包率、时延、抖动、带宽利用率 | PFC pause 帧数与时长的分布、ECN 标记率、队列水线、逐路径丢包 |
| 丢包的解读 | 背景噪声，先看趋势 | 故障信号，要立刻定位到端口 / 路径 |
| 视角 | 设备级聚合 + 抽样探测 | 设备级 + 路径级 + 作业级（按训练任务归因） |
| 排障目标 | 恢复业务可用性 | 缩短停机（MTTR）并保住训练进度 |

翻一遍你现在维护的监控面板，逐个卡片标注「可直接复用 / 需改口径 / 需要新建」。

标不出结论的卡片，说明这个指标的语义还没搞清楚，那正是下一步要补的功课。

**六十分钟聚合出来的图，永远不会有尖刺。** 看到一条平线先别松手，先问它是什么窗口算出来的，这一问能救掉大半次误判。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：AI 训练网络为什么要把丢包率压到 `1e-5` 量级以下？「TCP 反正会重传」这句话错在哪？

::: details 参考答案与评分维度

「TCP 会重传」在有损网络里成立，因为重传由**内核协议栈**完成，代价是一个 RTT，业务几乎无感。RDMA 绕过了内核，数据面跑在网卡上，没有协议栈兜底，重传粒度是窗口级的，一次丢包连带几十个包重发。

更要紧的是**同步放大**。AllReduce 每一轮都要等所有 Rank 到齐，一个包的重传延迟会传导成整个训练步的等待，一万张卡一起等。丢包吃掉的是全局同步的时间，不是一点带宽。这是必须从机制上避免丢包的根因。

**评分维度**

- 说出 RDMA 绕过内核，丢失了协议栈的重传兜底（必需）
- 说出重传代价在同步训练里被放大到全局（必需）
- 提到 PFC / ECN 是「避免丢包」而非「丢了再补」（加分）
- 只回答「RDMA 快、TCP 慢」而没有触及重传语义（不通过）

:::

**必答 Q2**：把维护中的 IDC 监控系统原样搬到万卡智算集群，先不管能不能采到设备数据。**能立刻发现哪类问题，又会漏掉哪类？** 各举两个以上并说明理由。

::: details 参考答案与评分维度

能发现的：

1. **链路彻底中断**。探测器到不了、端口 down，任何监控体系都看得见。
2. **带宽利用率异常 / 长期饱和**。端口计数器级别的现象，老体系看得见，只是粒度和阈值不一定合适。
3. **端到端时延劣化**。基于探测包的方案能感知到某条路径变慢。

会漏掉的：

1. **PFC 风暴与 PFC 死锁**。老体系没有 pause 帧计数与持续时长指标，风暴发生时端口利用率甚至可能是「正常」的。
2. **incast 造成的微突发与 ECN 标记**。分钟级轮询取平均，亚秒级突发被抹平。
3. **hash 极化 / 单条大象流打满某条路径**。设备级聚合指标被稀释，只有逐路径观测看得见。
4. **单个光模块的渐进劣化**，比如 FEC 纠错计数上升、误码增加。不在老指标集里。

**评分维度**

- 能区分「现象层面能看见」与「有指标能定位」（必需）
- 漏掉项至少覆盖 PFC / ECN / 微突发 / 光模块中的两项（必需）
- 说明「为什么漏」是无指标口径还是粒度不够，而不是只说「没做过」（必需）
- 能主动提出补救方向，比如新增 pause / ECN 指标、路径级探测、秒级订阅（加分）

:::

**自测 Q3**：AllReduce 的同步突发和电商大促的流量洪峰，最本质的两个区别是什么？

::: details 参考答案与评分维度

① **周期性**。大促洪峰是事件驱动的偶发流量，incast 是每个训练步都发生的固定节奏。正因为可预测，才有可能通过拓扑与参数预调优，比如 rail-optimized 拓扑、拥塞控制参数。

② **同步性与木桶效应**。大促流量从大量随机入口汇聚，压力在时间和空间上被摊薄。incast 是上万个源在**同一时刻**朝同一目的地倾泻，瞬时压力远超平均负载，任何一个 Rank 慢都会拖住全体。

**评分维度**：两点各 1 分。额外指出「可预测 → 可预调优」或「木桶效应 → 单个慢节点即全局慢」加 1 分。

:::

**自测 Q4**：为什么说路径级覆盖在智算网络里比在传统 IDC 里更值钱？

::: details 参考答案与评分维度

大象流加 hash 分担的组合，让「某一条路径劣化」既高频又隐蔽。单条大象流哈希到某条路径把它打满，或者一个坏光模块只影响个别链路。设备级聚合指标会把这类局部劣化稀释到看不见：一台 64 端口的交换机上，1 条路径只占 1.5%，聚合指标永远显示正常。

只有逐路径观测能把「某条 ECMP 路径被单流打满」这类问题暴露出来。路径级探测观测的是**流量实际走过的那条路**，而不是设备的平均表现。

**评分维度**

- 说出聚合指标会稀释局部劣化（必需）
- 说出大象流使单路径饱和成为高频模式（必需）
- 能给出数量级直觉（1 条路径 / 64 端口约 1.5%）或具体观测手段（加分）

:::

## 小结

四条假设换下来，工具清单没变，判断依据全换了。

**流量模型**从南北向小流换成东西向大象流，上面再叠一层 AllReduce 周期性同步突发。**丢包语义**从背景噪声、排障线索，变成机制性故障的信号，主指标跟着换成 PFC pause、ECN 标记率、队列水线。**故障代价**从「一批请求变慢」变成「全体停摆加 checkpoint 回退」，MTTR 的要求压到分钟级。**遥测粒度**从 SNMP 分钟轮询换成 gNMI 秒级订阅，数据管道能直接复用，缺的只是数据源。

::: tip 本课要点

**同一张网，四个默认假设全得换。**

- **流量模型**：南北向小流 → **东西向大象流 + AllReduce 周期性同步突发（incast）**
- **丢包语义**：丢包从「背景噪声 / 排障线索」变成「**机制性故障的信号**」。日常主指标换成 PFC pause、ECN 标记率、队列水线
- **故障代价**：网络故障等于全体训练停摆加 checkpoint 回退，MTTR 要求**分钟级**
- **遥测粒度**：SNMP 分钟轮询 → **gNMI 秒级流式订阅**。数据管道可直接复用，缺的只是数据源
- **能力映射**：路径级覆盖在智算网络**更值钱**。发现环节你已有积累，定位与恢复是学习方向

:::

::: info 关于文中那几个数字

`1e-5` 量级的丢包率要求是业界工程实践的常见目标，任何 RFC 都没有强制规定。同一个集群里，不同业务、不同厂商的口径可能有差异。遇到具体数字，以所在环境的设计文档为准。

:::
