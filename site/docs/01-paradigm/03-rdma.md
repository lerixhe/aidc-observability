上一讲收了四条假设，其中一条是：无损网络里，丢包从背景噪声变成了事故信号。

这条假设的来源在时延稳定性上：AI 训练不用 TCP，卡在时延的稳定性，不在带宽。

## 交付

- 说清一个包走完内核协议栈要付的三笔开销，以及它们在什么条件下开始致命
- 用尾延迟解释：同步训练为什么只认最慢的那条流
- RDMA 的三项能力：内核旁路、零拷贝、CPU 卸载，各自消掉哪一笔开销
- 在一台机器上用命令确认它在用 RDMA，看计数器，不看网卡型号

## 一个包要走多远

先看一次普通的 `send()` 里实际发生了什么。我们通常以为 `send()` 是把数据送出去了，并非如此。

`send()` 只负责把数据写进内核给这个套接字准备的发送缓冲区，写完就返回，剩下的活归操作系统。完整路径是这样：

```text
1. 应用调用 send()，数据进入内核发送缓冲区
2. 内核协议栈接手：分片、加 IP 头与 TCP 头、算校验和、走拥塞控制
3. 数据下到网卡驱动，网卡 DMA 读走内存，发到线上
4. 对面网卡收到，硬件校验，触发中断
5. 硬中断交给软中断（ksoftirqd），内核协议栈重新组包、按序、校验、回 ACK
6. 数据放进接收缓冲区，唤醒阻塞在这个套接字上的应用
7. 应用调用 recv()，把数据从内核缓冲区拷到自己的缓冲区
8. 应用开始处理
```

八步里只有第一步和第七步属于应用，中间六步全在 CPU 上完成。收发一轮要进出内核两次，用户态与内核态切换两次，内存搬三遍：网卡到内核缓冲区，内核缓冲区到应用缓冲区，发送方向再重复一遍。

### 三笔开销

把这条路径上的损耗归归类，三笔：

| 开销 | 具体表现 | 什么时候开始致命 |
|---|---|---|
| **时延与抖动** | 单次收发包几十微秒起步，尾延迟不可控 | 软中断排队、CPU 调度、socket 锁竞争，个别包能慢出两个数量级 |
| **CPU 消耗** | 协议栈每包都要 CPU 处理一遍 | 200Gbps 线速下单核算不过来，得拆到多核，而 GPU 机器上的核是留给计算的 |
| **内存拷贝** | 内核缓冲区与应用缓冲区之间来回搬 | 每秒几十 GB 的梯度收发，拷贝既费时又占内存带宽 |

这三笔在日常业务里被摊薄了。一次查询等 5 毫秒，中间夹杂 40 微秒的抖动不会有人注意。同步训练是另一种情形。

::: info 经验映射（IDC → AIDC）

有损网络里排障时见过这样的现场：业务进程 CPU 飙高、某个核的软中断打满、接口时延立刻抖起来。问题出在主机协议栈路径上，跟网络设备没关系。

变的只是严重度。业务网络里，这类抖动被大量并发请求和重试摊平了。同步训练里，同一个抖动会被同步机制放大成全局停顿。

:::

## 尾延迟

上一讲说过，AllReduce 是上万张卡同步推进，每一轮的完成时间由最慢的那个 Rank 决定。

一次 AllReduce 里同时跑着几千条流，各自经过不同的交换机和队列。只要有一小部分包慢下来，整轮通信就卡在那条最慢的流上。

设每个包有千分之一的概率遇到调度抖动，一轮里跑 4096 条流，那么至少一条流被拖住的概率是

```text
1 - 0.999^4096 ≈ 98%
```

几乎每轮都会中。把平均时延从 60 微秒压到 10 微秒，只要尾巴上另有千分之一的包慢出 1 毫秒，整轮照样被拖住。这就是尾延迟在同步训练里的分量。

另一个约束是 CPU。训练机器配高核数 CPU 是要喂 GPU，做数据预处理、dataloader、任务编排。每秒几十 GB 的梯度收发走内核，几十个核全部搭进去，加卡就撞上 CPU 瓶颈。

两条约束合起来，需要的传输路径是：时延低且稳，不吃 CPU，不做多余拷贝。这就是 RDMA（Remote Direct Memory Access）。

## RDMA 消掉的三样

RDMA 这个全称容易理解错，听起来像一种内存接口。它描述的是路径：网卡直接读写对端内存，中间不经过任何软件。

对照上面那八步，RDMA 消掉的是三处：

| 维度 | TCP 路径 | RDMA 路径 |
|---|---|---|
| 调用方式 | 系统调用陷进内核 | **内核旁路**：用户态直接操作网卡队列对（QP），零系统调用 |
| 数据移动 | 内核缓冲区与应用缓冲区来回拷 | **零拷贝**：网卡 DMA 直接读写应用注册过的内存 |
| 传输层处理 | CPU 跑协议栈 | **CPU 卸载**：可靠传输、乱序、回 ACK 全在网卡硬件里 |
| 单包时延 | 几十微秒，抖得厉害 | 1～2 微秒量级，稳定 |
| CPU 参与度 | 重，每包都要过一遍 | 只负责发起，不负责搬运 |

应用侧的变化只有一句：声明「把这段内存写到对面那台机器的那段内存」，投递一个 Work Request 进网卡队列，剩下交给硬件。

::: info 经验映射（IDC → AIDC）

与 TCP 相比，RDMA 把控制路径上的中间层全部去掉：用户态引擎直接驱动网卡发包，数据面直达硬件。

以前优化序列化格式，省的是每一比特。RDMA 省的是每一个包的必经之路。前者是常数优化，后者是量级优化。

:::

## 代价：重传变成窗口重发

RDMA 拿到微秒级时延的办法是消掉中间层，而中间层里包含 TCP 那套丢包恢复。

TCP 丢了包，收到三个重复 ACK 就从丢失点重传那一段，SACK 还能标出丢了哪几块，补得又准又快。这是它几十年打磨出来的核心能力。

RDMA 的可靠传输做在网卡里，没有这么细的确认粒度，走的是 **Go-Back-N 那一路：丢一个包，从窗口早期开始整段重发**。SIGCOMM 2018 那篇 *Revisiting Network Support for RDMA* 对这一点做过量化分析，一次丢包可能触发几十个包的重发，恢复期间这次内存操作整体挂起。

窗口重发和选择重传的代价差一个数量级。所以 RDMA 用微秒级时延换来了一个前提：**网络不能丢包**。

::: warning 完整因果链

把两讲连起来：

**同步训练要求微秒级且稳定的时延**（尾延迟）→ 内核协议栈给不了 → **上 RDMA** → RDMA 的丢包恢复代价大。

再往下推：**网络必须从机制上保证不丢包** → 「无损网络」由此而来 → 于是有了 PFC 与 ECN（见 [PFC](../02-lossless/05-pfc.md)、[ECN + DCQCN](../02-lossless/06-ecn-dcqcn.md)）。

顺序不能颠倒。先选了 RDMA，丢包才变得不可接受；反过来先做无损再挑传输，逻辑就散了。
:::

## 三条命令

机制课也要有能验证的动作。一台装了 RDMA 网卡的机器，三条命令足够确认它是不是真的在跑 RDMA：

```bash
# 1. 设备和端口状态，看到 ACTIVE 才说明链路与协议都起来了
ibv_devices
ibv_devinfo | grep -E 'hca_id|state|link_layer|active_speed'

# 2. 实测带宽与时延，需两端一起跑（服务端起，客户端指过去）
ib_write_bw -d mlx5_0 --report_gbits
ib_write_lat -d mlx5_0

# 3. 网卡侧的拥塞与丢包计数，RoCE 场景的关键看板
ethtool -S <ifname> | grep -Ei 'pause|ecn|discard|out_of_buffer'
```

`ib_write_lat` 跑 64 字节小消息，典型输出是这样：

```text
 #bytes #iterations    t_min[usec]    t_max[usec]  t_typical[usec]
     64        1000          1.32          4.87            1.41
```

典型值 1.4 微秒，最差 4.9 微秒。同样 64 字节的小消息走内核 TCP，单程通常落在几十微秒，抖动还要大一个量级。

判读三点：

- **先看时延，再看带宽**。100Gbps 和 200Gbps 的差别是加卡的事，1.4 微秒和 40 微秒的差别是架构的事。
- **`out_of_buffer` / `discard` 开始增长，是丢包的前兆**。接收侧缓冲不够了，它比端口丢包率更早出现，也更容易定位到具体哪台机器。
- **`pause` 计数在涨，说明上游在反压**。网络已经进入无损机制的工作区间，这时要拿到按优先级、按端口拆开的分布才能定位，那是第二篇的主题。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：AI 训练直接用 TCP 不行吗？TCP 也能跑通。至少给两个理由，并说明它们和尾延迟的关系。

::: details 参考答案与评分维度

两条主线。

① **时延与抖动**。TCP 跑得通，峰值带宽也不差。问题在协议栈那条路径上：中断、软中断、调度、加锁、拷贝，几十微秒起步，尾巴上不可控。同步训练里几千条流并行，最慢那条决定整轮 AllReduce 何时收工。

② **CPU 与内存带宽**。线速收发梯度走协议栈，要吃掉大量 CPU 核与内存带宽，这些资源本该喂 GPU。高吞吐下那几趟拷贝还会自己变成瓶颈。

TCP 的「跑得通」建立在一个前提上：异步，能容忍抖动。同步训练把这个前提推翻了。

**评分维度**

- 明确指出「跑得通」和「满足同步训练的时延 / 抖动要求」是两件事（必需）
- 说出尾延迟放大机制（必需）
- 提到 CPU / 内存拷贝成本（必要但不充分）
- 只答「TCP 慢、RDMA 快」，没解释为何在同步训练里致命（不通过）

:::

**必答 Q2**：补全这条链：同步训练要求（ ① ）稳定 → 内核协议栈做不到 → 上（ ② ）。它的丢包恢复代价大，所以网络必须（ ③ ）→ 于是有了 PFC / ECN。

::: details 参考答案与评分维度

① 微秒级低时延，含尾延迟；② RDMA；③ 从机制上避免丢包，也就是无损。

重点是**顺序不可颠倒**。丢包被压到极低，是因为选了 RDMA，丢包代价被放大到了不可接受。PFC、ECN、水线阈值这些机制，本质上都是**在丢包发生之前介入**，做的是预防，不是恢复。

**评分维度**：三空全对给基本分。讲清顺序与因果给满分。再指出「无损机制是预防不是恢复」加 1 分。

:::

**自测 Q3**：RDMA 的三项能力，各自消掉了内核路径上的哪一笔开销？

::: details 参考答案与评分维度

**内核旁路**消掉系统调用与上下文切换，那是时延抖动的主要来源。**零拷贝**消掉内核到应用缓冲区那一趟搬运，省时延也省内存带宽。**CPU 卸载**消掉协议栈的 CPU 消耗，把核还给计算。

三样合起来，才把单包时延压到 1～2 微秒且稳得住。少一样都不成：只做旁路不做零拷贝，内存还得搬；只做零拷贝不做卸载，CPU 还得跑协议。

**评分维度**：三条各 1 分。能对应到「时延 / 带宽 / CPU」三类资源给满分。

:::

**自测 Q4**：某个训练任务变慢了，还能像以前一样登录机器看 CPU 和软中断吗？为什么？

::: details 参考答案与评分维度

基本失效。RDMA 的数据面不过 CPU，主机侧的 CPU 与软中断指标跟传输性能几乎解耦。看到的「一切正常」，可能正是一个队列在交换机里憋着。

慢的根因大概率在网络设备侧：队列堆积、PFC pause、ECN 降速，或者在对端、在中间链路。

所以智算网络的可观测必须自建**设备侧遥测 + 路径级观测**两类能力，gNMI 秒级订阅是前者的入口（见 [gNMI + OpenConfig 遥测](../04-telemetry/11-gnmi.md)）。把「按训练任务归因」做成常规能力，是第五、六篇的内容。

**评分维度**：答出「主机侧排障失效」给基础分。能给出替代观测手段（设备遥测 / 路径级 / 按任务归因）给满分。

:::

## 小结

内核路径上的三笔开销，时延抖动、CPU 消耗、内存拷贝，在日常业务里被并发摊薄，在同步训练里被同步机制放大成全局停顿。平均时延压低不起作用，尾巴上那千分之一的包才决定训练进度。

RDMA 用内核旁路、零拷贝、CPU 卸载消掉这三笔，单包时延压到 1～2 微秒且稳定。代价是 TCP 那套按字节补洞的恢复机制一起消失了，重传变成窗口级重发。

代价换来的是一个要求：网络必须从机制上不丢包。第二篇讲的就是这套机制，以及它们自己带来的故障模式。

::: tip 本课要点

**RDMA 消掉中间层，换来微秒级稳定时延，代价是丢包从常态变成事故。**

- 内核路径三笔开销：**时延抖动（尾延迟）、CPU 消耗、内存拷贝**
- 尾延迟的分量：千分之一的抖动概率，4096 条流下**每轮几乎必中**
- RDMA 三项能力：**内核旁路、零拷贝、CPU 卸载**，时延 1～2 微秒且稳定
- 因果链：同步训练 → 微秒级稳定时延 → RDMA → 丢包恢复代价大 → **必须无损网络** → PFC / ECN
- 可观测语义：数据面不过 CPU，主机侧排障失效，重心转向**设备侧遥测 + 路径级观测**
- 动手验证：`ibv_devinfo` 看状态、`ib_write_lat` 看时延、`ethtool -S` 看 pause / discard

:::

::: info 一个容易混的概念

RDMA 是一种传输能力，跟跑在什么介质上无关。它能跑在 InfiniBand 上，也能跑在以太网上（RoCE / RoCEv2）。

把它搬到以太网上（RoCEv2），多出来的是一整套工程问题，第 04 讲接着讲。

:::

留一个思考题：假如 RDMA 的重传也能做到按字节补洞，无损网络还有没有必要。
