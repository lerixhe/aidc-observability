上一讲收了四条假设，第一条是丢包从背景噪声变成事故。

这一讲回答那个「为什么」：AI 训练连 TCP 都不要了，到底嫌弃它什么。

先把结论摆出来：**TCP 输在「不稳」两个字上，不在峰值带宽**。它的时延抖得厉害，抖动在同步训练里会被放大成全局停顿。

## 交付

这一讲的验收动作有四条，做到了就算过关：

- 说清一个包走完内核协议栈要付的三笔账，以及这三笔账在什么条件下才开始要命
- 用木桶效应讲明白：同步训练只认尾延迟，平均延迟快多少都不算数
- 记住 RDMA 的三样东西，内核旁路、零拷贝、CPU 卸载，每样对应砍掉哪一笔
- 在一台机器上用命令确认它真的在用 RDMA，别看网卡型号，看计数器

还有一条是心法：把因果链自己推一遍，推得出来，后面的 PFC 和 ECN 就不用背了。

## 一个包要走多远

先看一次普通的 `send()` 里到底发生了什么。很多人以为 `send()` 是把数据送出去了，不是这样。

`send()` 只负责把数据塞进内核为这个套接字准备的发送缓冲区，塞完就返回。剩下的活全归操作系统。真正的旅程是这样：

```text
1. 应用调用 send()，数据进入内核发送缓冲区
2. 内核协议栈接手：分片、加 IP 头与 TCP 头、算校验和、走拥塞控制
3. 数据下到网卡驱动，网卡 DMA 读走内存，发到线上
4. 对面网卡收到，硬件校验，触发中断
5. 硬中断交给软中断（ksoftirqd），内核协议栈重新组包、按序、校验、回 ACK
6. 数据放进接收缓冲区，唤醒阻塞在这个套接字上的应用
7. 应用调用 recv()，把数据从内核缓冲区拷到自己的缓冲区
8. 应用开始处理
```

八步里，只有第一步和第七步是应用自己的事。中间六步，全靠 CPU 一寸一寸搬。

收发一个包要进出内核两次，跨用户态和内核态两次，内存要搬三遍：网卡 → 内核缓冲区 → 应用缓冲区，发的时候再来一遍。管道那篇讲过的道理在这里照样成立：你以为的「发一个包」，内核做的是一整套搬家。

### 三笔账

把这条路径上的损耗归归类，三笔，跑不掉：

| 代价 | 具体表现 | 什么时候才要命 |
|---|---|---|
| **时延与抖动** | 单次收发包几十微秒起步，尾延迟完全不可控 | 软中断排队、CPU 调度、socket 锁竞争，个别包能慢出两个数量级 |
| **CPU 消耗** | 协议栈每包都要 CPU 处理一遍 | 200Gbps 线速下单核算不过来，得拆到多核，而 GPU 机器上的核是留给计算的 |
| **内存拷贝** | 内核缓冲区 ↔ 应用缓冲区来回搬 | 每秒几十 GB 的梯度收发，拷贝既费时又占内存带宽 |

这三笔账在日常业务里被摊薄了。一条查询等 5 毫秒，中间那 40 微秒的抖谁也不会注意。换成同步训练就是另一回事。

::: info 经验映射（IDC → AIDC）

你在有损网络里排障时见过这样的现场：业务进程 CPU 飙高、某个核的软中断打满、接口时延立刻抖起来。这问题出在主机协议栈路径上，跟网络设备没关系。

区别只在严重度。业务网络里，这类抖动被大量并发请求和重试摊平了。同步训练里，它会被木桶效应放大成全局停顿。同一个现象，两种命。

:::

## 平均快没用

上一讲说过，上万张卡齐步走，**最慢的那个 Rank 决定所有人的节奏**。这句话往后推一步，就是这一节。

一次 AllReduce 里同时跑着几千条流。每条流都在自己的转发路径上排着队，各自经过不同的交换机、不同的队列。只要有一小部分包慢下来，整轮集合通信就卡在那条最慢的流上。

算一下：假设每个包有千分之一的概率被调度抖动咬一口，一轮里跑 4096 条流，那么至少一条流被咬中的概率是

```text
1 - 0.999^4096 ≈ 98%
```

几乎每一轮都会中。这就是尾延迟在同步训练里的真实分量：你花大价钱把平均时延从 60 微秒压到 10 微秒，只要尾巴上还有千分之一的包慢 1 毫秒，整轮照样被拖住。

木桶效应说的就是这个：装多少水看最短的板，跑多快看最慢的包。平均水位好看，板短的那一处照样漏水。

再往下还有一个约束。**CPU 核要留给计算**。训练机器配高核数 CPU，是要喂 GPU：数据预处理、dataloader、任务编排。每秒几十 GB 的梯度收发要是走内核，几十个核全搭进去，加卡就成了加瓶颈。

两条约束合起来，需要的是这样一条传输路径：**时延低且稳，不吃 CPU，不做多余拷贝**。

它就是 RDMA。

## 砍掉三样东西

RDMA 全称 Remote Direct Memory Access，远程直接内存访问。这个名字有点误导，听起来像是个内存接口，它其实是一套做法：让网卡直接读写对端内存，中间不经过任何软件。

对照着上面那八步，RDMA 做的事情就是删：

| 维度 | TCP 路径 | RDMA 路径 |
|---|---|---|
| 调用方式 | 系统调用陷进内核 | **内核旁路**：用户态直接操作网卡队列对（QP），零系统调用 |
| 数据移动 | 内核缓冲区 ↔ 应用缓冲区来回拷 | **零拷贝**：网卡 DMA 直接读写应用注册过的内存 |
| 传输层处理 | CPU 跑协议栈 | **CPU 卸载**：可靠传输、乱序、回 ACK 全在网卡硬件里 |
| 单包时延 | 几十微秒，抖得厉害 | 1～2 微秒量级，稳定 |
| CPU 参与度 | 重，每包都要过一遍 | 只负责发起，不负责搬 |

编程视角的变化只有一句：应用声明「把这段内存写到对面那台机器的那段内存」，投递一个 Work Request 进网卡队列，剩下的交给硬件。CPU 只负责扣扳机，不搬货。

::: info 经验映射（IDC → AIDC）

用一个你已经很熟的东西类比：RDMA 之于 TCP，等于把「每个包都过三层代理」改成「用户态引擎直接驱动网卡发包」。**控制路径上的中间层全砍掉，数据面直达硬件**。

你以前优化序列化格式，省的是每一比特。RDMA 省的是每一个包的必经之路。前者是常数优化，后者是量级优化，别把两者混着算。

:::

## 天下没有免费的午餐

RDMA 拿到微秒级时延的办法，是把中间层全砍掉。中间层里就包含 TCP 那套精细的丢包恢复。

TCP 丢了包，收到三个重复 ACK 就从丢失点重传那一段，SACK 还能告诉你丢了哪几块，补得又准又快。这是它几十年打磨出来的核心能力。

RDMA 的可靠传输做在网卡里，没有这么细的账本。它走的是 **Go-Back-N 那一路：丢一个包，从很早就开始整段重传**。据 SIGCOMM 2018 那篇 *Revisiting Network Support for RDMA* 的实测，一次丢包可能触发几十个包的重发，恢复期间这次内存操作整体挂起。

说白了：TCP 丢包像补牙，哪颗坏补哪颗。RDMA 丢包像重贴一整面墙的墙纸。代价差一个量级。

所以说 RDMA 用微秒级时延换来了一个前提：**网络不能丢包**。

::: warning 完整因果链

把两讲连起来，这条链子要能一口气说完：

**同步训练要求微秒级且稳定的时延**（木桶效应）→ 内核协议栈给不了 → **上 RDMA** → RDMA 的丢包恢复代价大。

再往下一步：**网络必须从机制上保证不丢包** → 「无损网络」就是这么来的 → 于是有了 PFC 与 ECN（见 [PFC](../02-lossless/05-pfc.md)、[ECN + DCQCN](../02-lossless/06-ecn-dcqcn.md)）。

面试问到「AI 网络为什么要无损」，答这条链，别背定义。顺序也不能颠倒：先选了 RDMA，丢包才变得不可接受；反过来先做无损再挑传输，逻辑就散了。
:::

## 三条命令

机制课也得有能上手动的动作。找一台装了 RDMA 网卡的机器，三条命令足够确认它是不是真的在跑 RDMA。

```bash
# 1. 设备和端口状态，看到 ACTIVE 才说明链路与协议都起来了
ibv_devices
ibv_devinfo | grep -E 'hca_id|state|link_layer|active_speed'

# 2. 实测带宽与时延，需两端一起跑（服务端起，客户端指过去）
ib_write_bw -d mlx5_0 --report_gbits
ib_write_lat -d mlx5_0

# 3. 网卡侧的拥塞与丢包计数，RoCE 场景的关键看板
ethtool -S <ifname> | grep -Ei 'pause|ecn|discard|out_of_buffer'
```

`ib_write_lat` 的典型输出长这样，64 字节小消息：

```text
 #bytes #iterations    t_min[usec]    t_max[usec]  t_typical[usec]
     64        1000          1.32          4.87            1.41
```

这组数字比什么都直接：**典型 1.4 微秒，尾巴上到 4.9 微秒**。同样 64 字节的小消息走内核 TCP，单程通常落在几十微秒，抖动还要大一个量级。

判读看三点：

- **先看时延，别看带宽**。100Gbps 和 200Gbps 的差别是加卡的事，1.4 微秒和 40 微秒的差别是架构的事。
- **`out_of_buffer` / `discard` 开始涨，就是丢包的前兆**。接收侧缓冲不够了，它比端口丢包率更早出现，也更容易定位到具体哪台机器。
- **`pause` 计数在涨，说明上游在反压**。网络已经进入无损机制的工作区间，这时候要拿到按优先级、按端口拆开的分布才能定位，这是第二篇的主题。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条给自己打分。跳过自评最省事，也最没用。

:::

**必答 Q1**：用你自己的话说：「AI 训练直接用 TCP 不行吗？TCP 又不是跑不通。」至少给两个理由，并说明它们和木桶效应的关系。

::: details 参考答案与评分维度

两条主线。

① **时延与抖动**。TCP 跑得通，峰值带宽也不差。问题在协议栈那条路径上：中断、软中断、调度、加锁、拷贝，几十微秒起步，尾巴上还不可控。同步训练里几千条流并行，最慢那条决定整轮 AllReduce 何时收工，尾延迟被木桶效应放大成全局停顿。

② **CPU 与内存带宽**。线速收发梯度走协议栈，要吃掉大量 CPU 核与内存带宽，这些资源本该喂 GPU。高吞吐下那几趟拷贝还会自己变成瓶颈。

换句话说，TCP 的「跑得通」建立在一个前提上：**异步，能容忍抖动**。同步训练把这个前提直接推翻了。

**评分维度**

- 明确指出「跑得通」和「满足同步训练的时延 / 抖动要求」是两件事（必需）
- 说出木桶效应或尾延迟放大机制（必需）
- 提到 CPU / 内存拷贝成本（必要但不充分）
- 只答「TCP 慢、RDMA 快」，没解释为何在同步训练里致命（不通过）

:::

**必答 Q2**：补全这条链：同步训练要求（ ① ）稳定 → 内核协议栈做不到 → 上（ ② ）。它的丢包恢复代价大，所以网络必须（ ③ ）→ 于是有了 PFC / ECN。

::: details 参考答案与评分维度

① 微秒级低时延，含尾延迟；② RDMA；③ 从机制上避免丢包，也就是无损。

重点是**顺序不可颠倒**。丢包被压到极低，是因为选了 RDMA，丢包代价被放大到了不可接受。所以 PFC、ECN、水线阈值这些机制，本质上都是**在丢包发生之前介入**，做的是预防，不是恢复。

**评分维度**：三空全对给基本分。讲清「顺序与因果」给满分。再指出「无损机制是预防不是恢复」加 1 分。

:::

**自测 Q3**：RDMA 的三样东西，各自砍掉了内核路径上的哪一笔账？

::: details 参考答案与评分维度

**内核旁路**砍掉系统调用与上下文切换，那是时延抖动的主要来源。**零拷贝**砍掉内核到应用缓冲区那一趟搬运，省时延也省内存带宽。**CPU 卸载**砍掉协议栈的 CPU 消耗，把核还给计算。

三样合起来，才把单包时延压到 1～2 微秒且稳得住。少一样都不成：只做旁路不做零拷贝，内存还得搬；只做零拷贝不做卸载，CPU 还得跑协议。

**评分维度**：三条各 1 分。能对应到「时延 / 带宽 / CPU」三类资源给满分。

:::

**自测 Q4**：某个训练任务变慢了，你还能像以前一样登录机器看 CPU 和软中断吗？为什么？

::: details 参考答案与评分维度

基本失效。RDMA 的数据面不过 CPU，主机侧的 CPU 与软中断指标跟传输性能几乎解耦。你看到的一切「正常」，很可能正是一个队列在交换机里憋着。

慢的根因大概率在网络设备侧：队列堆积、PFC pause、ECN 降速，或者在对端、在中间链路。

所以智算网络的可观测，必须自建**设备侧遥测 + 路径级观测**两类能力。gNMI 秒级订阅是前者的入口（见 [gNMI + OpenConfig 遥测](../04-telemetry/11-gnmi.md)）。把「按训练任务归因」当一等公民，也是第五、六篇的主题。

**评分维度**：答出「主机侧排障失效」给基础分。能给出替代观测手段（设备遥测 / 路径级 / 按任务归因）给满分。

:::

## 小结

内核路径上那三笔账，时延抖动、CPU 消耗、内存拷贝，在日常业务里被并发摊薄了，在同步训练里被木桶效应放大成全局停顿。平均时延压低没用，尾巴上那千分之一的包才是真正决定训练进度的东西。

RDMA 拿内核旁路、零拷贝、CPU 卸载把这三笔账砍掉，单包时延压到 1～2 微秒且稳。代价是 TCP 那套按字节补洞的恢复机制一起没了，重传变成整段重来。

砍到这一步，「网络必须从机制上不丢包」就不是一句口号了，它是前提。

::: tip 本课要点

**RDMA 用砍掉中间层换来微秒级稳定时延，代价是把丢包从常态变成了事故。**

- 内核路径三笔账：**时延抖动（尾延迟）、CPU 消耗、内存拷贝**
- 尾延迟的分量：千分之一的抖动概率，4096 条流下**每轮几乎必中**。平均快没用
- RDMA 三样东西：**内核旁路、零拷贝、CPU 卸载**，时延 1～2 微秒量级且稳定
- 因果链：同步训练 → 微秒级稳定 → RDMA → 丢包恢复代价大 → **必须无损网络** → PFC / ECN
- 可观测语义：数据面不过 CPU，主机侧排障失效，重心转向**设备侧遥测 + 路径级观测**
- 动手验证：`ibv_devinfo` 看状态、`ib_write_lat` 看时延、`ethtool -S` 看 pause / discard

:::

::: info 一个容易混的概念

RDMA 是**一种传输能力**，跟跑在什么介质上无关。它能跑在 InfiniBand 上，也能跑在以太网上（RoCE / RoCEv2）。

下一讲讲的就是把它搬到以太网之后，多出来的那些工程问题。

:::

留一个思考题：假如 RDMA 的重传也能做到按字节补洞，无损网络还有没有必要。
