AI 训练不用 TCP，不是因为带宽不够。TCP 的峰值带宽一直是够的，200Gbps 的线它照样能打满，跟同价位的 RDMA 网卡比也不难看。

TCP 的问题出在它每次收发的那条路上。我们平时以为 `send()` 就是把数据送出去了，其实不是，`send()` 只负责把数据塞进内核替这个套接字准备的发送缓冲区，塞完就返回，剩下的活全归操作系统，而这一整条路对同步训练来说太长了。

一次 `send()` 到对面 `recv()` 返回，完整路径是这样：

```text
1. 应用调用 send()，数据进入内核发送缓冲区
2. 内核协议栈接手：分片、加 IP 头与 TCP 头、算校验和、走拥塞控制
3. 数据下到网卡驱动，网卡 DMA 读走内存，发到线上
4. 对面网卡收到，硬件校验，触发中断
5. 硬中断交给软中断（ksoftirqd），内核协议栈重新组包、按序、校验、回 ACK
6. 数据放进接收缓冲区，唤醒阻塞在这个套接字上的应用
7. 应用调用 recv()，把数据从内核缓冲区拷到自己的缓冲区
8. 应用开始处理
```

八步里只有第一步和第七步属于应用，中间六步全在 CPU 上走一遍，一轮收发要进出内核两次、切换用户态与内核态两次、把内存搬三遍：网卡到内核缓冲区一遍，内核缓冲区到应用缓冲区一遍，发送方向再重复一遍。单包时延落在几十微秒，尾巴上还能再慢出两个数量级，因为软中断会排队、CPU 会被调度走、socket 锁会撞上。这笔开销归归类是三样：**时延与抖动**，单次收发包几十微秒起步，尾延迟不可控，软中断排队、CPU 调度、socket 锁竞争，个别包能慢出两个数量级；**CPU 消耗**，协议栈每包都要 CPU 处理一遍，200Gbps 线速下单核算不过来，得拆到多核，而 GPU 机器上的核是留给计算的；**内存拷贝**，每秒几十 GB 的梯度收发，拷贝既费时又占内存带宽。

三样在日常业务里被摊薄了，一次查询等 5 毫秒，中间夹着 40 微秒的抖动没人会注意；同步训练里同样的抖动会被同步机制放大成全局停顿，这就受不了了。

于是有了另一个东西，**RDMA**，也就是 `Remote Direct Memory Access`。这名字容易理解错，听起来像一种内存接口，其实它描述的是一条路径：网卡直接读写对端的内存，中间不经过任何软件。

RDMA 的请求是应用填好一个结构体，投进队列对里，硬件自己搬：

```c
struct ibv_send_wr {
    uint64_t            wr_id;      // 应用自己写的标签，完成时原样带回
    struct ibv_sge     *sg_list;    // 数据在哪：本地地址 + 长度 + lkey
    int                 num_sge;
    enum ibv_wr_opcode  opcode;     // RDMA_WRITE / RDMA_READ / SEND / ATOMIC
    struct {
        uint64_t        remote_addr; // 对端地址
        uint32_t        rkey;        // 对端在内存注册时给出的钥匙
    } rdma;
};
```

如代码所示，`sg_list` 指向的是本地内存，`rdma` 里装的是对端的地址和钥匙，那投出去之后谁来搬？没人，网卡自己按这两样去搬。对端 CPU 全程不参与，这是它和 socket 最本质的区别：地址与权限都提前换好了，运行时只剩下搬运本身。

投递的动作就一行：

```c
struct ibv_send_wr wr = {0};
wr.wr_id      = (uint64_t)ctx;
wr.opcode     = IBV_WR_RDMA_WRITE;
wr.sg_list    = &sge;
wr.num_sge    = 1;
wr.rdma.remote_addr = remote_addr;
wr.rdma.rkey        = rkey;

struct ibv_send_wr *bad = NULL;
ibv_post_send(qp, &wr, &bad);   // 交给网卡，函数立刻返回，不等结果
```

`ibv_post_send` 把描述符塞进发送队列的门铃，塞完就返回，一发一收里没有任何一次系统调用。

## 单边与双边

RDMA 的投递有两种用法，用的方式不同，省下来的东西也不一样。

一种是**双边**，`SEND` 对 `RECV`：发送方投 SEND，接收方必须提前把 RECV 缓冲投好，两边 WQE 一对一配上，数据落到哪个位置由接收方决定，所以接收侧的 CPU 得预先知道有多少东西要来，控制消息、短小的元数据走这条路。

另一种是**单边**，`WRITE` 和 `READ`：发送方直接指定对端的 `remote_addr` 与 `rkey`，往那段内存里写，或者从里面读，接收方 CPU 全程不知道也不需要知道，事后去查自己的数据就行了，梯度搬运这种大批量、地址事先说好的场景走这条路。

两者的区别在这儿：单边省掉了接收侧的准备动作，不用预投缓冲，不用对端 CPU 参与，代价是地址与钥匙必须提前换好，属于拿前期配置换运行时开销。用反了会把便宜全丢掉，用单边去送一条必须先被读走的控制消息，对端只能轮询自己的内存等它到。

小消息还有一条更便宜的走法，内联（inline）：几十个字节的数据不按 `sg_list` 去读，直接塞在 WQE 后面，网卡读 WQE 的时候顺手就拿到了，省掉一次 DMA。

那么多大的消息才值得内联呢？这就要看分界线在哪儿。

```bash
$ ibv_devinfo -v | grep -E 'max_inline_data|max_qp_wr|max_mr_size'
        max_inline_data:                64
        max_qp_wr:                      32768
        max_mr_size:                    0xffffffffffffffff
```

多数卡给 `max_inline_data` 64 字节，也有给到 128、256 的，具体看卡和驱动。为什么常见的这个数偏偏是 64 呢？

网卡读一个 WQE 是按段读的，一段 64 字节，正好一个 cache line。数据塞在这一段里，网卡读一次 WQE 就把头和载荷一起拿到手；塞不下，网卡就得按 `sg_list` 里的地址再发起一次读，那这一次 DMA 的便宜就白占了。所以 64 不是一个拍脑袋的配置值，它等于一次搬运本身的粒度，超过这个粒度，内联就不再是「顺手」，而变成「多占一段空间还得再读一遍」。

这也解释了为什么内联只在内核旁路的路径上才算一笔账。走内核协议栈的时候，一次多的 DMA 淹没在几十微秒的抖动里，看不出来；在 RDMA 这条路上，一次 DMA 的时间跟整次收发的时延是同一个量级，省下来就是实打实的。

写完还得知道成没成。完成事件从另一条队列里出来，元素长这样：

```c
struct ibv_wc {                     // 完成队列里的一个元素，即 CQE
    uint64_t            wr_id;      // 对应你投递时写的那个标签
    enum ibv_wc_status  status;     // IBV_WC_SUCCESS 才算成
    enum ibv_wc_opcode  opcode;
    uint32_t            byte_len;   // 实际搬了多少字节
    uint32_t            qp_num;
};
```

这里有个新手最容易踩的坑：**单边的 WRITE 默认不在接收侧产生完成事件**，除非投递时带了 immediate。所以排障的时候，「对面没收到」和「对面收到了但没人去看」是两个完全不同的现场，别搅在一起。

## 内存注册

对端肯把钥匙交给你，前提是那段内存注册过：

```c
struct ibv_mr {
    void    *addr;      // 注册的起始地址
    size_t   length;
    uint32_t lkey;      // 本地钥匙，填进 sge
    uint32_t rkey;      // 对端钥匙，交给通信对端
};
```

网卡要读写内存，先得知道这段虚拟地址对应的物理页在哪，还得保证这段页不被换出去，`ibv_reg_mr` 做的就是这件事：钉页、建表、把页表交给网卡。没有这一步，DMA 落不下去，钥匙也无从谈起。

`ibv_reg_mr` 的代价随内存大小一路上涨，一次几毫秒到几十毫秒都是正常数，所以这块内存应该注册一次、长期复用，不该在收发路径上反复注册注销。把注册写进循环里的程序不少见，带宽只剩个零头，问题不在网上，在自己的代码里。

## 队列深度

QP 有发送队列与接收队列，CQ 有完成队列，三者都是定长环形缓冲，深度决定了能同时挂着多少笔未完成请求。

给小了，应用投几下就得停下来等 CQE，网络明明闲着，自己先卡住，吞吐上不去而链路利用率只有两成；给大了，环太大，网卡和应用的缓存都会 miss，反而更慢。压测时把这三个深度扫一遍，吞吐曲线的拐点就在那里，这一点跟调别的缓冲没有任何区别。

## 尾延迟

上一讲讲过的同步机制，在这里开始收账：AllReduce 是上万张卡同步推进，每一轮的完成时间由最慢的那个 Rank 决定。一次 AllReduce 里同时跑着几千条流，各自经过不同的交换机和队列，只要有一小部分包慢下来，整轮通信就卡在那条最慢的流上。

那么平均时延还有意义吗？把它从 60 微秒压到 10 微秒，只要尾巴上另有千分之一的包慢出 1 毫秒，整轮照样被拖住。设每个包有千分之一的概率遇到调度抖动，一轮里跑 4096 条流，至少一条流被拖住的概率是

```text
1 - 0.999^4096 ≈ 98%
```

几乎每轮都会中。

另一个约束是 CPU。训练机器配高核数 CPU 是要喂 GPU 的，做数据预处理、dataloader、任务编排，每秒几十 GB 的梯度收发走内核，几十个核全搭进去，加卡就撞上 CPU 瓶颈。

两条约束合起来，需要的路径是：时延低且稳、不吃 CPU、不做多余拷贝。

## 代价：重传变成窗口重发

RDMA 拿到微秒级时延的办法是消掉中间层，而中间层里正包含着 TCP 那套丢包恢复。

TCP 丢了包，收到三个重复 ACK 就从丢失点重传那一段，SACK 还能标出丢了哪几块，补得又准又快，这是它几十年打磨出来的核心能力。RDMA 的可靠传输做在网卡里，账本上只有一笔粗账，它不记「哪一块缺了」，只记「窗口从哪里开始还没确认」，所以重传走的是 Go-Back-N 那一路：丢一个包，从窗口早期开始整段重发。SIGCOMM 2018 那篇 *Revisiting Network Support for RDMA* 对这一点做过量化，一次丢包可能触发几十个包的重发，恢复期间这次内存操作整体挂起。

窗口重发和选择重传的代价差一个数量级，所以 RDMA 用微秒级时延换来了一个前提：**网络不能丢包**。

把两讲连起来看，顺序是这样的：同步训练要求微秒级且稳定的时延，内核协议栈给不了，于是上 RDMA；RDMA 的丢包恢复代价大，于是网络必须从机制上不丢包；「无损网络」由此而来，PFC 与 ECN 是它的两条腿（见 [PFC](../02-lossless/05-pfc.md)、[ECN + DCQCN](../02-lossless/06-ecn-dcqcn.md)）。这个顺序不能颠倒，先选了 RDMA，丢包才变得不可接受，反过来先做无损再挑传输，逻辑就散了。

## 用命令验证

机制课也得有能验证的动作。一台装了 RDMA 网卡的机器，两条命令足够确认它是不是真的在跑 RDMA：

```bash
# 1. 设备和端口状态，看到 ACTIVE 才说明链路与协议都起来了
ibv_devinfo | grep -E 'hca_id|state|link_layer|active_speed'

# 2. 实测带宽与时延，需两端一起跑（服务端起，客户端指过去）
ib_write_lat -d mlx5_0
```

`ib_write_lat` 跑 64 字节小消息，典型输出是这样：

```text
 #bytes #iterations    t_min[usec]    t_max[usec]  t_typical[usec]
     64        1000          1.32          4.87            1.41
```

典型值 1.4 微秒，最差 4.9 微秒。同样 64 字节的小消息走内核 TCP，单程通常落在几十微秒，抖动还要大一个量级。

然后是看板这一侧，网卡侧的拥塞与丢包计数：

```bash
ethtool -S <ifname> | grep -Ei 'pause|ecn|discard|out_of_buffer'
```

判读三点：先看时延再看带宽，100Gbps 和 200Gbps 的差别是加卡的事，1.4 微秒和 40 微秒的差别是架构的事；`out_of_buffer` 和 `discard` 开始增长是丢包的前兆，接收侧缓冲不够了，它比端口丢包率更早出现，也更容易定位到具体哪台机器；`pause` 计数在涨，说明上游正在反压，网络已经进入无损机制的工作区间，要拿到按优先级、按端口拆开的分布才能定位，那是第五讲的主题。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：AI 训练直接用 TCP 不行吗？TCP 也能跑通。至少给两个理由，并说明它们和尾延迟的关系。

::: details 参考答案与评分维度

两条主线。

① **时延与抖动**。TCP 跑得通，峰值带宽也不差。问题在协议栈那条路径上：中断、软中断、调度、加锁、拷贝，几十微秒起步，尾巴上不可控。同步训练里几千条流并行，最慢那条决定整轮 AllReduce 何时收工。

② **CPU 与内存带宽**。线速收发梯度走协议栈，要吃掉大量 CPU 核与内存带宽，这些资源本该喂 GPU。高吞吐下那几趟拷贝还会自己变成瓶颈。

TCP 的「跑得通」建立在一个前提上：异步，能容忍抖动。同步训练把这个前提推翻了。

**评分维度**

- 明确指出「跑得通」和「满足同步训练的时延 / 抖动要求」是两件事（必需）
- 说出尾延迟放大机制（必需）
- 提到 CPU / 内存拷贝成本（必要但不充分）
- 只答「TCP 慢、RDMA 快」，没解释为何在同步训练里致命（不通过）

:::

**必答 Q2**：补全这条链：同步训练要求（ ① ）稳定 → 内核协议栈做不到 → 上（ ② ）。它的丢包恢复代价大，所以网络必须（ ③ ）→ 于是有了 PFC / ECN。

::: details 参考答案与评分维度

① 微秒级低时延，含尾延迟；② RDMA；③ 从机制上避免丢包，也就是无损。

重点是**顺序不可颠倒**。丢包被压到极低，是因为选了 RDMA，丢包代价被放大到了不可接受。PFC、ECN、水线阈值这些机制，本质上都是**在丢包发生之前介入**，做的是预防，不是恢复。

**评分维度**：三空全对给基本分。讲清顺序与因果给满分。再指出「无损机制是预防不是恢复」加 1 分。

:::

**自测 Q3**：RDMA 的三项能力，各自消掉了内核路径上的哪一笔开销？

::: details 参考答案与评分维度

**内核旁路**消掉系统调用与上下文切换，那是时延抖动的主要来源。**零拷贝**消掉内核到应用缓冲区那一趟搬运，省时延也省内存带宽。**CPU 卸载**消掉协议栈的 CPU 消耗，把核还给计算。

三样合起来，才把单包时延压到 1～2 微秒且稳得住。少一样都不成：只做旁路不做零拷贝，内存还得搬；只做零拷贝不做卸载，CPU 还得跑协议。

**评分维度**：三条各 1 分。能对应到「时延 / 带宽 / CPU」三类资源给满分。

:::

**自测 Q4**：某个训练任务变慢了，还能像以前一样登录机器看 CPU 和软中断吗？为什么？

::: details 参考答案与评分维度

基本失效。RDMA 的数据面不过 CPU，主机侧的 CPU 与软中断指标跟传输性能几乎解耦。看到的「一切正常」，可能正是一个队列在交换机里憋着。

慢的根因大概率在网络设备侧：队列堆积、PFC pause、ECN 降速，或者在对端、在中间链路。

所以智算网络的可观测必须自建**设备侧遥测 + 路径级观测**两类能力，gNMI 秒级订阅是前者的入口（见 [gNMI + OpenConfig 遥测](../04-telemetry/11-gnmi.md)）。把「按训练任务归因」做成常规能力，是第五、六篇的内容。

**评分维度**：答出「主机侧排障失效」给基础分。能给出替代观测手段（设备遥测 / 路径级 / 按任务归因）给满分。

:::

## 小结

内核路径上的三笔开销，时延抖动、CPU 消耗、内存拷贝，在日常业务里被并发摊薄，在同步训练里被同步机制放大成全局停顿。平均时延压低不起作用，尾巴上那千分之一的包才决定训练进度。

RDMA 用内核旁路、零拷贝、CPU 卸载消掉这三笔，单包时延压到 1～2 微秒且稳定。机制落到代码上是三个结构：WQE 描述「往哪写多少」，CQE 告诉你「写成了没有」，MR 把内存钉住并把钥匙交给两边。小包用内联与双边，大包用单边，队列深度与注册成本是两处不改架构但能拖垮链路的参数。

代价换来的是一个要求：网络必须从机制上不丢包。第五、六讲说的就是这套机制，以及它们自己带来的故障模式。

::: tip 本课要点

**RDMA 消掉中间层，换来微秒级稳定时延，代价是丢包从常态变成事故。**

- 内核路径三笔开销：**时延抖动（尾延迟）、CPU 消耗、内存拷贝**
- 尾延迟的分量：千分之一的抖动概率，4096 条流下**每轮几乎必中**
- RDMA 三项能力：**内核旁路、零拷贝、CPU 卸载**，时延 1～2 微秒且稳定
- 因果链：同步训练 → 微秒级稳定时延 → RDMA → 丢包恢复代价大 → **必须无损网络** → PFC / ECN
- 可观测语义：数据面不过 CPU，主机侧排障失效，重心转向**设备侧遥测 + 路径级观测**
- 动手验证：`ibv_devinfo` 看状态、`ib_write_lat` 看时延、`ethtool -S` 看 pause / discard

:::

::: info 一个容易混的概念

RDMA 是一种传输能力，跟跑在什么介质上无关。它能跑在 InfiniBand 上，也能跑在以太网上（RoCE / RoCEv2）。

把它搬到以太网上（RoCEv2），多出来的是一整套工程问题，第 04 讲接着讲。

:::

留一个思考题：假如 RDMA 的重传也能做到按字节补洞，无损网络还有没有必要。
