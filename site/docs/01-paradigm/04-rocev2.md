RDMA 最初是为 InfiniBand 设计的。网卡、交换机、线缆、管理软件都出自同一个体系，链路层用信用（credit）机制做流控，天生不丢包，上层应用不用为丢包写任何兜底逻辑。这套东西部署起来省心，缺点同样明显：设备只能从一家买，价格、带宽迭代、运维工具全跟着供应商走。

以太网是另一套逻辑。设备便宜，供应商多，带宽一年一档，但协议的前提就是网络会丢包，可靠性交给上层补。

以太网这边想拿到 RDMA 的时延，做法很直接：把 IB 传输层原样搬过来，外面套一层以太网封装。这就是 RoCE（RDMA over Converged Ethernet）。协议栈的核心逻辑没变，变的是传输介质，从自带流控的专用网络，换成一张尽力而为的以太网。

上一讲讲完 RDMA 为什么依赖无损网络。以太网天生没有这个能力，只能靠交换机上的一组额外配置把它补出来。这篇看这套配置怎么拼，以及它带来的复杂度和副作用。

## 交付

- 说清 InfiniBand 与 RoCE 的关系：RoCE 是把 RDMA 移植到以太网，不是另起一套协议
- 解释 RoCE v1 与 v2 的差别，以及这个差别为什么决定集群能长到多大
- 逐层说出 RoCEv2 报文里每个字段归谁管，对应到后面的 PFC、ECN 两讲
- 理解 DCB 三件套里为什么"配置一致性"比协议本身更容易出事故
- 在主机和交换机上各跑几条命令，确认 RoCEv2 真的按预期工作

## 从 IB 到以太网，中间隔着一个二层边界

InfiniBand 的定位很明确：它是为高性能计算做的一整套系统。链路层自己保证不丢包，端到端不需要重传兜底，配置基本是上电即用。代价是封闭，设备只有那几家能做。

以太网生态的相反面是便宜、开放、迭代快，正反面都认，问题只剩一个：怎么把 IB 的传输层塞进这个生态。

v1 的做法是把 IB 传输头直接塞进以太网帧，EtherType `0x8915`。它没有 IP 层，是个纯二层协议，出了这个二层域就转发不出去。一个 RoCE 集群的规模上限，等于一个二层域的上限。

v2 在中间加了 UDP 和 IP 两层，目的端口固定 **4791**。报文变成标准三层可路由格式，能跨 spine 多级转发，能参与 ECMP 哈希。今天说 RoCE 基本都指 v2。

两代的差别就这一处，但在工程上是一条死线。几百卡的集群，v1 也许能凑；上万卡必须跨 spine 多级转发、跨多个二层域，v1 在这条路上走不通。v2 是 RoCE 能进 Clos 架构的前提。

## 报文里每一层归谁管

一个 RoCEv2 报文从发起端网卡出去，封装顺序是这样：

```text
1. 网卡 DMA 读走应用注册过的内存，前面加 IB 传输头 BTH：QP 号、PSN 序号
2. 套 UDP 头，目的端口写死 4791
3. 套 IP 头，写入 DSCP 和 ECN 两位
4. 套以太网头，写入 802.1p 优先级（PCP）
5. 交换机按 PCP 决定进哪个队列，按 ECN 阈值决定要不要打 CE 标记
6. 对端网卡剥壳，按 BTH / PSN 检查顺序，回 ACK
7. 数据落进对端应用注册过的内存
```

四层壳，每一层都得有人负责。分工是这样的：

| 层 | 关键字段 | 它是给谁用的 | 后续课程 |
|---|---|---|---|
| 以太网头 | 802.1p / PCP 优先级（或由 DSCP 映射而来） | **PFC 按它暂停**，优先级是流量隔离的抓手 | [05 PFC](../02-lossless/05-pfc.md) |
| IP 头 | **ECN 两位**（ECT / CE） | 交换机拥塞时改写，源端据此降速 | [06 ECN + DCQCN](../02-lossless/06-ecn-dcqcn.md) |
| UDP 头 | 目的端口 **4791** | 只提供"可路由"这个身份，不做可靠性 | — |
| IB 传输头 | BTH、PSN | 可靠传输、乱序重排、重传，全在网卡硬件里 | [03 RDMA](./03-rdma.md) |
| Payload | 应用内存数据 | DMA 直读直写 | — |

UDP 在这里只提供可路由的身份，不做握手、不排序、不重传。可靠传输全部由网卡硬件里的 IB 传输层完成：PSN 检查顺序，ACK / NAK 反馈，丢包触发重传。所以这条流丢了包没有协议栈兜底，硬件兜底也很贵，03 讲的结论在这里落地。

优先级靠报文标记。报文带着 PCP（或者由 DSCP 映射成队列），通行做法是划出专用优先级跑 RoCE，业务流量走有损队列。同一根线、同一个交换口，逻辑上分成两条互不影响的路径。

ECN 两位在 IP 头里。交换机拥塞时直接改这两个 bit，这是以太网上"流经的设备能留下痕迹"的唯一手段，也是拥塞控制闭环能成立的基础。

## 哪些能力可以直接搬

RoCEv2 流量就是标准五元组的 UDP 流，这一点对 IDC 背景的人很重要：

| 已有的能力 | 在 RoCEv2 场景下的状态 |
|---|---|
| 五元组哈希 / ECMP | 完全适用 |
| 抓包分析（tcpdump / Wireshark） | 能用，但只看得见外层，队列级语义得靠设备遥测 |
| VLAN / 优先级 / QoS 配置经验 | 直接迁移，DCB 就是 QoS 的无损加强版 |
| "链路通就算健康"的判断习惯 | 必须改，无损机制失效时链路完全正常 |
| 逐台设备的配置管理 | 要升级为配置一致性对账，否则一跳配错全网抖 |

抓包能看到 UDP 4791，IB 传输头用 Wireshark 的 RoCE 解析器就能读。看懂流量的能力不缺，缺的是设备侧的队列、PFC、ECN 状态，那是第四篇（把现场变成数据）的内容。

## DCB：无损要在以太网上重新配一遍

IB 的无损是设备属性，上电就有。以太网的无损是配置出来的，管这套配置的标准叫 **DCB（Data Center Bridging）**，核心三件：

| 机制 | 什么时候起作用 | 干什么 | 详见 |
|---|---|---|---|
| **PFC**（优先级流控） | 队列快满 | 反向暂停上游，从机制上阻止该优先级丢包 | [05 PFC](../02-lossless/05-pfc.md) |
| **ECN**（显式拥塞通知） | 拥塞初期 | 给报文打标记，让源端网卡先降速，尽量别走到"必须暂停" | [06 ECN + DCQCN](../02-lossless/06-ecn-dcqcn.md) |
| **一致性配置** | 部署与每次变更 | 整张 Fabric 每一跳的 PFC / ECN 参数、DSCP 映射严格一致 | [07 四大故障](../02-lossless/07-fault-modes.md) |

前两件是协议，第三件是一致性要求，也是最容易出事故的一件。

具体到故障场景：A 交换机给某优先级配了 PFC，B 交换机没配。A 往 B 方向打流，A 的出口队列快满了，发暂停帧给上游，这对 A、B 之间的链路是有效的。但只要链路上有一台设备不认这个优先级，无损保障就在那一跳断掉，后面的流量照丢。PFC 死锁则更麻烦，暂停帧沿着环路互相传递，整条环上的端口一起停摆。

这里有个常见疑问：ECN 已经能让源端主动降速，PFC 是不是可以省掉？

省不掉，两者的时间尺度差一个量级。ECN 是闭环：交换机打标记，接收端回 CNP 给发送端，发送端降速，这一圈走完队列可能已经涨满了。PFC 是开环、逐跳、就地生效，快得多，代价是暂停压力会往上游传播。分工是：**ECN 负责常态降速，PFC 兜住最后一道不丢包**。只留 ECN，微突发下会漏；只留 PFC，暂停帧会把整张网串成一条链。

## 配置错误为什么难发现

传统 IDC 的配置错误，后果多半是显性的：链路不通、端口 down、路由没有，监控一眼抓到。

RoCE 的配置错误是隐性的。某一跳 PFC 没开、水线配错、DSCP 映射与别处不同，后果是"无损机制在那一跳失效"或者"无意义的暂停风暴"。链路上一切正常：端口 up，带宽跑满，光功率正常，训练在变慢。

所以观测系统得看得见**设备队列级状态**：pause 收发计数、队列水线、ECN 标记数。端口级计数器覆盖不到这些，这也是第四篇要解决的问题。

## 四讲串成一条链

```text
同步训练要求微秒级稳定时延（02 讲）
  → 内核协议栈做不到 → 上 RDMA（03 讲）
    → RDMA 丢包恢复代价极大 → 网络必须无损
      → IB 天生无损但封闭昂贵 → RoCEv2 = RDMA over 以太网（本讲）
        → 以太网默认会丢包 → 需要 PFC + ECN 从机制上补齐
          → 这些机制自带新的故障模式 → 可观测成为刚需（07 讲起）
```

这条链是篇末自测卷的主线，也是"为什么 AI 网络要无损"这类开放题的答题骨架。

## 代价

一笔一笔算。

**配置量从"改一台"变成"改全网"。** IB 那边上电即无损，参数不用管。以太网上，每一跳都要配 PFC 开关、xoff / xon 水线、ECN 的 min / max 阈值、DSCP 到队列的映射，全网还得完全一致。一次变更是全 Fabric 的动作，做完还得对账。

**交换机从纯转发设备变成故障源。** 队列水线、PFC 阈值、ECN 阈值都成了要盯的配置面，配错就是事故。设备侧原来只看端口计数器的那套监控，覆盖不了这些。

**抓包只能看到外层。** 在主机上抓到的止于 UDP 头，丢了哪个 PSN、哪个队列憋住了，tcpdump 一个字都看不出来。定位必须靠设备遥测。

**水线和阈值靠手工算。** PFC 的 xoff / xon 要按端口速率和线缆时延算，ECN 的 min / max 靠经验。水线设得松，队列先溢出；设得紧，暂停帧满天飞。这套参数没有自动收敛的机制，不同厂商的默认值还不一样。

RoCE 换来的东西也实在：标准以太网加白盒交换机，管控面能自研；供应链多元，不必锁死一家；既有的 IDC 工具链和人才储备能接着用；带宽演进跟以太网节奏走，每年上一档。

IB 那边的优势也认：天生无损、免调优、SHARP 在网计算成熟、大规模部署经验厚。这笔路线账在 [IB vs RoCE 路线之争](../06-selection/20-ib-vs-roce.md) 里正式算，这里不下结论。

## 主机侧和交换机侧各看什么

主机侧三条命令，确认它在按 RoCEv2 跑：

```bash
# 1. 看设备与协议模式，link_layer 是 Ethernet 说明走的是 RoCE 而非原生 IB
ibv_devinfo | grep -E 'hca_id|link_layer|state'
cma_roce_mode -d mlx5_0 -p 1          # 查看当前版本，加 -m 2 可设为 v2

# 2. 看优先级、PFC 与 DSCP 映射，确认 RoCE 流量进了无损队列
mlnx_qos -i <ifname>

# 3. 抓五个包，确认外层是 UDP 4791
sudo tcpdump -i <ifname> -c 5 'udp port 4791'
```

一台配好的机器，前两条命令的典型输出：

```text
$ cma_roce_mode -d mlx5_0 -p 1
RoCE mode: RoCE v2

$ mlnx_qos -i ens1f0
DCBX mode: OS controlled
PFC configuration:
        priority:    0     1     2     3     4     5     6     7
        enabled:     0     0     0     1     0     0     0     0
        buffer:      0     0     0     0     0     0     0     0
```

优先级 3 上是 `enabled: 1`，其余全 0。意思是只有 3 号队列走无损，RoCE 流量应该落在 3 号上。

交换机侧核对三件事，缺一不可：

```text
1) 优先级映射一致：DSCP → traffic-class → queue，所有跳相同
2) 无损队列一致：开了 PFC 的队列号、xoff / xon 水线相同
3) 拥塞标记一致：ECN 的 min / max 阈值与标记概率相同
```

判读看三点：

- **抓不到 4791 报文**。流量没走 RoCE，先查 `ibv_devices`，再看对端是不是同一套 RDMA 栈。
- **`mlnx_qos` 里 RoCE 队列的 PFC 是 0**。无损机制形同虚设。链路一切正常，一拥塞就丢包。
- **两跳的 DSCP 映射不同**。流量在中间某一跳被塞进有损队列，链路上没有任何告警，表现出来就是偶发变慢、查不出原因。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按"评分维度"逐条自评。

:::

**必答 Q1**：RoCEv2 的「v2」相对 v1 改了什么？为什么这一改很关键？

::: details 参考答案与评分维度

v1 把 RDMA 直接封进以太网帧（EtherType `0x8915`），只能在单个二层域内转发，出不了三层网关。v2 在中间加 UDP / IP，目的端口 4791，报文变成标准可路由格式，能跑在多级 Clos Fabric 上。

关键在集群规模。从几百卡到上万卡，必然要跨 spine 多级转发、跨多个二层域，v1 的二层边界在这条路上走不通。

**评分维度**

- 说出 v1 不可路由、v2 套 UDP/IP 后可路由（必需）
- 说出"规模化的前提是跨三层"（必需）
- 提到端口 4791 或 EtherType（加分）

:::

**必答 Q2**：RoCEv2 报文里的 UDP 头承担什么职责？这条流丢了一个包，谁来兜底？兜得住吗？

::: details 参考答案与评分维度

UDP 头只提供可路由的身份，端口号顺带给 ECMP 哈希用。它不做握手、不排序、不重传。

可靠性在网卡硬件里的 IB 传输层，靠 BTH / PSN 与 ACK / NAK 实现，重传是粗粒度的 Go-Back-N 式：丢一个包，可能整段重来。

所以兜底有，但很贵。这是 PFC / ECN 必须在丢包发生之前介入的原因。

**评分维度**

- 说出 UDP 只提供可路由身份、不负责可靠性（必需）
- 说出可靠性在网卡硬件（必需）
- 指出硬件重传代价大，因此要走"预防"而非"恢复"（必需，缺这条只算背书）

:::

**自测 Q3**：为什么国内主流厂商在以太系 RoCE 与 InfiniBand 之间普遍选前者？

::: details 参考答案与评分维度

生态开放：标准以太网加白盒交换机（如 SONiC），管控面能自研，不被单一供应商锁死。供应链与成本多元。既有 IDC 的工具链、运维体系、人才储备能延续。带宽演进跟以太网节奏走，规模弹性大。

反面也要说清：IB 天生无损、免调优、SHARP 在网计算成熟。只站一边的答案不及格。

**评分维度**：两条以上正面理由给基础分。能同时讲清 IB 的优势给满分。

:::

**自测 Q4**：RoCE 流量和普通业务流量在同一张物理网上怎么共存？这套共存最脆弱的地方在哪？

::: details 参考答案与评分维度

逻辑隔离。RoCE 走专用优先级（PCP 或 DSCP 映射到无损队列），该队列开 PFC 加 ECN；业务流量走有损队列，照常丢包重传。同一块网卡、同一根线，队列分开。

脆弱处在映射一致性。任何一跳把 RoCE 流量映进有损队列，无损保障在那一跳断掉，链路不会有告警，端口不会 down。

**评分维度**：说出优先级 / 队列隔离（必需）。说出映射不一致的后果（必需，这是本讲的落点）。

:::

## 小结

RoCE 的由来不复杂：以太网要 RDMA 的时延，把 IB 传输层原样搬了过来。v1 封在二层，出了二层域走不通；v2 加了 UDP / IP，能跨三层，这才有上万卡的余地。报文里分工也清楚：L2 优先级给 PFC 用，IP 头 ECN 两位给 DCQCN 用，UDP 只提供可路由身份，可靠性在网卡硬件里。

麻烦出在无损这件事上。IB 的无损是设备属性，以太网的无损得靠配置补出来：PFC、ECN，外加全 Fabric 的一致性。前两件是协议，第三件不是协议，却是最容易出事故的地方。整张网跳错一个，链路照样通、端口照样 up、带宽照样满，训练在变慢。

::: tip 本课要点

**RoCE 是把 IB 传输层搬到以太网上，无损要靠配置补，代价在一致性。**

- RDMA 原生在 **InfiniBand**（信用机制天生无损），RoCE 是移植。**v1 出不了二层域，v2 套 UDP/IP 后可路由**（端口 4791）
- 报文分工：**L2 优先级给 PFC · IP 头 ECN 位给 DCQCN · UDP 只提供可路由身份 · 可靠性在网卡硬件**
- 无损靠 DCB 三件套：PFC + ECN + **全 Fabric 配置严格一致**
- 代价：配置变成全网动作、交换机成故障源、抓包只见外层、水线与阈值靠手工算
- RoCEv2 就是五元组 UDP 流，**哈希 / ECMP / 抓包原样适用**，缺的是设备侧队列遥测

:::

留一个思考题：PFC 与 ECN 都配对，唯独某一跳的 DSCP 映射与别处不同。你会先在哪类指标上看到异常，为什么。
