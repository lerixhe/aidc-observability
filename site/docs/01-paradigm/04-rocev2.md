以太网这边想拿到 RDMA 的时延，做法很直接：把 IB 传输层原样搬过来，外面套一层以太网封装，这就是 **RoCE**（RDMA over Converged Ethernet）。协议栈的核心逻辑一整块没动，动的是脚下那张网，从自带流控的专用网络，换成一张尽力而为的以太网。

这么搬是有代价的，报文外面多套了三层壳，一个本来十二字节的头，放大到七八十字节才出得去门；可它照样能跑满线速，小消息的单次往返也就三微秒上下，比内核协议栈快一个数量级。所以说协议本身不是难点，难点全在「以太网默认会丢包」这件事上，而 RDMA 恰恰假定网络不丢包。

## RoCEv2 报文

RoCEv2 的报文是把四种壳一层层套起来的，从里到外是 IB 传输头、UDP 头、IP 头、以太网头，每一层都有人管，各自管一件事。

1. 以太网头，管优先级，PFC 就认这个。
2. IP 头，管拥塞标记，ECN 两位在这儿。
3. UDP 头，管可路由，端口固定 4791。
4. IB 传输头，管可靠传输，PSN 与 ACK 都在这儿。

**以太网头** 优先级 3

```
| Dst MAC 6B | Src MAC 6B | 0x0800 | PCP=3 | DEI=0 | VID |
```

以太网头本身不关心这是不是 RDMA，它只关心这个帧属于哪个优先级。PCP 三个 bit，也就是当年 802.1p 留下的那三个 bit，交换机拿它决定这个帧进哪个队列，PFC 暂停的也是这个优先级。通行做法是划一个专用优先级给 RoCE，业务流量走有损队列，同一根线、同一个交换口，逻辑上分成两条互不影响的路径。

**IP 头** DSCP 26、ECN 两位

```
| Ver=4 | IHL=5 | DSCP=26 | ECN=01 | Len | ID | TTL | Proto=17 | Cksum | Src IP | Dst IP |
```

ECN 那两位是唯一一个「流经的设备能在报文上留痕」的地方，交换机拥塞时直接把 `01` 改成 `11`，收端网卡看见了就回一条拥塞通知给发送端。这个位置只有两个 bit 宽，却是整套拥塞控制闭环的入口。

**UDP 头** 目的端口 4791

```
| Src Port | Dst Port = 0x12B7 | Len | Cksum |
```

UDP 在这里只提供一个身份：让这个报文能按普通三层流量被路由、被哈希、被转发。它不握手、不排序、不重传，可靠传输跟它没有半点关系。0x12B7 就是 4791，写死在规范里。

**IB 传输头** BTH 十二字节

每个包都带，长度固定十二字节：

```
| opcode 8bit | SE 1 | M 1 | pad 2 | TVer 4 | P_Key 16bit |
| F/B 1 | 保留 7bit | Dest QP 24bit |
| AckReq 1 | 保留 7bit | PSN 24bit |
```

从线上抓下来的一个 RC 上的 RDMA WRITE Only 首包，BTH 那十二个字节是这样：

```
0a  00  4b 00  00  00 00 12  00  00 00 3a
│   │   └P_Key┘ │  └Dest QP┘ │   └─PSN──┘
│   └TVer=0    └ F/B=0       └ AckReq=0
└ opcode 0x0a：RC 上的 RDMA WRITE Only
```

opcode 说这个包是什么，PSN 说它在流的哪个位置，两个字段足够网卡自己把乱序、丢包、重传全部办完，不用主机插一手。

**RETH** 十六字节

WRITE 与 READ 的首包还多带一个 RETH，装的是地址与钥匙：

```
00 00 00 7f 5c 30 00 00   00 00 1a 2b   00 00 10 00
└────── VA = 0x7f5c300000 ┘ └ rkey ┘    └len=4KB┘
```

上一讲那三个结构落在线上就是这三个位置：VA 与 R_Key 来自 MR，DMALen 来自 WQE，而 PSN 对应你后来从 CQ 里取走的那条 CQE。抓包看到 R_Key 对不上，基本就是两端注册的内存不一致，不用再往下查了。

这里有三个容易看错的地方。`P_Key` 写 `0xffff` 是默认分区，不是错误值，绝大多数集群里它一直是这个数，看到就别当异常；`Dest QP` 是 24 位，所以一台机器的 QP 数量上限是 1677 万而不是无限，建连建爆了要想到这一层；`PSN` 也是 24 位，回绕之后从零开始，抓包看到 PSN 突然跳回小数字，那不是丢包，是绕了一圈。

## 发起侧

发起方投出去的报文只有一种骨架：BTH 打头，后面跟载荷，或者跟 RETH 与载荷。一个「把本地四 KB 写到对端某个地址」的请求，序列化出来是这样：

```
| BTH 12B (opcode=0x0a) | RETH 16B{VA, rkey, 4KB} | payload 4096B |
```

在 Wireshark 里把 RoCE 解析器打开，同一个包读起来是这样，比原始字节好认得多：

```
InfiniBand BTH
    OpCode: RDMA WRITE Only (0x0a)
    Destination QP: 0x000012
    Packet Sequence Number: 0x00003a
    Acknowledge Request: 0
InfiniBand RETH
    Virtual Address: 0x0000007f5c300000
    Remote Key: 0x0000001a2b
    DMA Length: 4096
```

投递的动作在上一讲已经写过一遍，这里只提醒一件事：写出去的包和你投的那个 WQE 是同构的，`sg_list` 里填的地址长度会变成 DMALen 与载荷，`remote_addr` 与 `rkey` 会落进 RETH，`wr_id` 不出去，它只是留给你自己认领 CQE 用的。

## 响应侧

响应比请求复杂一些，因为它要能带数据、带状态、带错误原因，不过再复杂的响应也是 BTH 加一小段的组合。

**ACK**

```
0x11 + AckReq=0 + PSN=0x3a
```

一条 ACK 的 BTH 和别的包长得一模一样，只靠 opcode 区分。这不是设计洁癖，是因为交换机只认 UDP 4791，网卡只认 BTH，任何包都得能在这条路上裸奔，所以它必须有个共同的帽子。

**NAK**

```
0x12 + syndrome: PSN Sequence Error (0x60)
0x12 + syndrome: RNR (0x61)
```

这两种 NAK 的处置完全相反：PSN 错误意味着包丢了或者乱了，发送端要从窗口早期整段重发，也就是上一讲说的 Go-Back-N；RNR 意味着对端接收队列里没有可用的 RECV，不是网络的错，是两边的节奏没对上，重发再多次也没用，得回头看双边的缓冲投递。把这两种混成一个「对面没收到」去查，方向会一路错到天亮。

**READ Response**

```
0x10 + AETH + 载荷
```

读请求的回来路径上带的是一条 AETH 加数据，AETH 里有 credit 与 ACK 信息，所以一次 RDMA READ 完成时，你既拿到了数据，也顺带把发送窗口推进了。

## 无损从哪儿来

以太网默认会丢包，RoCE 的假定是不许丢，中间这段差口要拿配置补，管这套配置的标准叫 **DCB（Data Center Bridging）**，掰开是两件协议加一件苦力。

第一件是 **PFC**，优先级流控。队列快满的时候，交换机往上游打一个暂停帧，只暂停这个优先级，别的优先级照走。

第二件是 **ECN**，显式拥塞通知。队列越过下限还没到上限，交换机不给上游打暂停，只在 IP 头里改那两个 bit，让发送端自己先收一收。

第三件不是协议，是**一致性**：整张 Fabric 每一跳的 PFC 开关、xoff / xon 水线、ECN 阈值、DSCP 到队列的映射，必须严丝合缝地对上。

那能不能只留 ECN，把 PFC 省掉？省不掉。两者的时间尺度差一个量级：ECN 是闭环，交换机打标记、接收端回通知、发送端降速，这一圈走完队列可能已经涨满了；PFC 是开环、逐跳、就地生效，快得多，代价是暂停的压力会往上游传播。分工是交换价：ECN 负责常态降速，PFC 兜住最后一道不丢包。只留 ECN，微突发下会漏；只留 PFC，暂停帧会把整张网串成一条链。

## 一跳没配会怎样

传统 IDC 的配置错误，后果多半是显性的，链路不通、端口 down、路由没有，监控一眼抓到。

RoCE 的配置错误是隐性的，某一跳 PFC 没开、水线配歪、DSCP 映射跟别处不一样，后果是「无损机制在那一跳失效」或者「毫无意义的暂停风暴」，而链路上一切正常：端口 up，带宽跑满，光功率正常，训练在变慢。

所以观测系统得看得见**设备队列级状态**：pause 收发计数、队列水线、ECN 标记数，端口级计数器覆盖不到这些。

主机侧三条命令，确认它是不是真在按 RoCEv2 跑：

```bash
# 1. 看设备与协议模式，link_layer 是 Ethernet 说明走的是 RoCE 而非原生 IB
ibv_devinfo | grep -E 'hca_id|link_layer|state'
cma_roce_mode -d mlx5_0 -p 1          # 查看当前版本，加 -m 2 可设为 v2

# 2. 看优先级、PFC 与 DSCP 映射，确认 RoCE 流量进了无损队列
mlnx_qos -i <ifname>

# 3. 抓五个包，确认外层是 UDP 4791
sudo tcpdump -i <ifname> -c 5 'udp port 4791'
```

一台配好的机器，前两条命令的典型输出：

```text
$ cma_roce_mode -d mlx5_0 -p 1
RoCE mode: RoCE v2

$ mlnx_qos -i ens1f0
DCBX mode: OS controlled
PFC configuration:
        priority:    0     1     2     3     4     5     6     7
        enabled:     0     0     0     1     0     0     0     0
        buffer:      0     0     0     0     0     0     0     0
```

优先级 3 上是 `enabled: 1`，其余全 0，意思是只有 3 号队列走无损，RoCE 流量应该落在 3 号上。

交换机侧核对三件事，缺一不可：优先级映射一致，DSCP 到 traffic-class 到 queue 所有跳相同；无损队列一致，开了 PFC 的队列号、xoff / xon 水线相同；拥塞标记一致，ECN 的 min / max 阈值与标记概率相同。

判读看三点：抓不到 4791 报文，说明流量没走 RoCE，先查 `ibv_devices`，再看对端是不是同一套 RDMA 栈；`mlnx_qos` 里 RoCE 队列的 PFC 是 0，无损机制形同虚设，链路一切正常，一拥塞就丢包；两跳的 DSCP 映射不同，流量在中间某一跳被塞进有损队列，链路上没有任何告警，表现出来就是偶发变慢、查不出原因。

## 小结

RoCE 的由来不复杂：以太网要 RDMA 的时延，把 IB 传输层原样搬了过来，v1 封在二层出不了二层域，v2 加了 UDP 与 IP 才能跨三层，这个人字形的分岔决定了集群能长到多大。报文里分工也清楚，L2 优先级给 PFC 用，IP 头的 ECN 两位给 DCQCN 用，UDP 只提供可路由身份，可靠性在网卡硬件里。

麻烦全落在无损这件事上。IB 的无损是设备属性，上电就有；以太网的无损是要配出来的，PFC、ECN 加全 Fabric 一致性，前两件是协议，第三件不是协议，却是最容易出事故的地方。整张网跳错一个，链路照样通、端口照样 up、带宽照样满，训练在变慢。

RoCEv2 报文里头套了三层壳，浪费的字节数按比例算不低，可它还是成了这一行的主流，因为底下那张网的生态、价格和迭代节奏都摆在那儿。技术领域性能并不总是一切，还有开放、简单、可维护这些东西，都要权衡。这条路线跟 IB 的账在 [IB vs RoCE 路线之争](../06-selection/20-ib-vs-roce.md) 里正式算，这里不下结论。

::: tip 本课要点

**RoCE 是把 IB 传输层搬到以太网上，无损要靠配置补，代价在一致性。**

- RDMA 原生在 **InfiniBand**（信用机制天生无损），RoCE 是移植。**v1 出不了二层域，v2 套 UDP/IP 后可路由**（端口 4791）
- 报文分工：**L2 优先级给 PFC · IP 头 ECN 位给 DCQCN · UDP 只提供可路由身份 · 可靠性在网卡硬件**
- 无损靠 DCB 三件套：PFC + ECN + **全 Fabric 配置严格一致**
- 代价：配置变成全网动作、交换机成故障源、抓包只见外层、水线与阈值靠手工算
- RoCEv2 就是五元组 UDP 流，**哈希 / ECMP / 抓包原样适用**，缺的是设备侧队列遥测

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按"评分维度"逐条自评。

:::

**必答 Q1**：RoCEv2 的「v2」相对 v1 改了什么？为什么这一改很关键？

::: details 参考答案与评分维度

v1 把 RDMA 直接封进以太网帧（EtherType `0x8915`），只能在单个二层域内转发，出不了三层网关。v2 在中间加 UDP / IP，目的端口 4791，报文变成标准可路由格式，能跑在多级 Clos Fabric 上。

关键在集群规模。从几百卡到上万卡，必然要跨 spine 多级转发、跨多个二层域，v1 的二层边界在这条路上走不通。

**评分维度**

- 说出 v1 不可路由、v2 套 UDP/IP 后可路由（必需）
- 说出"规模化的前提是跨三层"（必需）
- 提到端口 4791 或 EtherType（加分）

:::

**必答 Q2**：RoCEv2 报文里的 UDP 头承担什么职责？这条流丢了一个包，谁来兜底？兜得住吗？

::: details 参考答案与评分维度

UDP 头只提供可路由的身份，端口号顺带给 ECMP 哈希用。它不做握手、不排序、不重传。

可靠性在网卡硬件里的 IB 传输层，靠 BTH / PSN 与 ACK / NAK 实现，重传是粗粒度的 Go-Back-N 式：丢一个包，可能整段重来。

所以兜底有，但很贵。这是 PFC / ECN 必须在丢包发生之前介入的原因。

**评分维度**

- 说出 UDP 只提供可路由身份、不负责可靠性（必需）
- 说出可靠性在网卡硬件（必需）
- 指出硬件重传代价大，因此要走"预防"而非"恢复"（必需，缺这条只算背书）

:::

**自测 Q3**：为什么国内主流厂商在以太系 RoCE 与 InfiniBand 之间普遍选前者？

::: details 参考答案与评分维度

生态开放：标准以太网加白盒交换机（如 SONiC），管控面能自研，不被单一供应商锁死。供应链与成本多元。既有 IDC 的工具链、运维体系、人才储备能延续。带宽演进跟以太网节奏走，规模弹性大。

反面也要说清：IB 天生无损、免调优、SHARP 在网计算成熟。只站一边的答案不及格。

**评分维度**：两条以上正面理由给基础分。能同时讲清 IB 的优势给满分。

:::

**自测 Q4**：RoCE 流量和普通业务流量在同一张物理网上怎么共存？这套共存最脆弱的地方在哪？

::: details 参考答案与评分维度

逻辑隔离。RoCE 走专用优先级（PCP 或 DSCP 映射到无损队列），该队列开 PFC 加 ECN；业务流量走有损队列，照常丢包重传。同一块网卡、同一根线，队列分开。

脆弱处在映射一致性。任何一跳把 RoCE 流量映进有损队列，无损保障在那一跳断掉，链路不会有告警，端口不会 down。

**评分维度**：说出优先级 / 队列隔离（必需）。说出映射不一致的后果（必需，这是本讲的落点）。

:::

留一个思考题：PFC 与 ECN 都配对，唯独某一跳的 DSCP 映射与别处不同。你会先在哪类指标上看到异常，为什么。

## 补一句：PFC 为什么必须逐跳

有人问过，PFC 能不能只在两端做，中间设备不管。不能。

流控是链路层的动作，暂停帧只对相邻一跳有效。A 让 B 停，B 只能把压力再传给 C，如此一传到底；中间哪一跳不认这个优先级，无损就在这一跳断了，而端到端重传是靠不住的。所以 PFC 的配置必须全网逐跳一致，第 05 讲把这条链路一步步走一遍。
