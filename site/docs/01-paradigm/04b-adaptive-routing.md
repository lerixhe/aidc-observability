前面几讲立了两个事实：RoCEv2 跑在以太网上，必须走 ECMP；训练通信全是同质大象流，五元组完全一样。

那换个哈希行不行？换盐、换算法、把内层五元组也混进去，试到天黑也没用。参与哈希的那几个字段本身一模一样，怎么算都是同一个数。**哈希不负责公平，它只负责可重复。**

那让交换机别提前拍板，走一步看一步呢？这就是自适应路由。先把盲区看清楚，后面的话才有落点。

两件事合起来，实验里给出一个明确结论：**静态散列在这种流量面前不均分。** 两条等价上行，八条流时常有一条打满、一条闲着。改五元组没用，得让交换机在转发时刻自己看路。

先在一条能跑的命令上把盲区看清楚：

```bash
cd labs/05-clos-topo
go run . -exp 3        # 64 条流，源目 IP 与端口全部相同
```

```text
口径                最差极化度  CV     最大链路占比
L3（src/dst IP）      2.00        1.00   100%
L4（五元组）          2.00        1.00   100%
```

五元组一模一样时，三层的哈希和五元的哈希判出同一条路，最大链路占比 100%：全部流量压在一条上行，另一条一条流都没有。

实验一还能补一个量级：八条随机流时最差极化度 2.00，两千零四十八条流才降到 1.07。哈希能做的是多条流之间摊平，做不了一条流自己分叉。训练流量恰好是后者。

## 交付

- 静态 ECMP 与自适应路由的分界：选路权交给了谁
- 流级分流、Flowlet 切片、逐包喷洒三种粒度的优劣与代价
- 打散流量之后，接收端网卡在缓存、重组、重传上付出的硬件代价
- 开启自适应路由时，交换机与网卡各看哪三个指标，以及重组失效的现场形态

## 病因：静态散列不看队列

传统 ECMP 是静态的，也是盲目的。报文进交换机，硬件拿五元组做哈希，模上链路数，算出来是几就走几号端口。

这个过程不管出端口此刻在排队的是谁，某个端口的水位已经贴着 XOFF 水线，只要新来报文的哈希值落在这里，硬件照样把它塞进去。

于是出现一种局面：一条上行顶着 XOFF 反复暂停，另一条上行一条流都没有。链路是等价的，流量不是。

## 三种选路粒度

自适应路由（Adaptive Routing，AR）只有一句：**选路依据从报文的静态身份，换成出端口的实时拥塞。** 交换芯片转发时直接查几条等价上行的队列深度，谁的队列浅、时延小，报文就给谁。

切分粒度有三种：

| 选路粒度 | 怎么切 | 保序 | 链路利用率 | 硬件开销 |
|---|---|---|---|---|
| Per-Flow（流级） | 完整五元组绑定一条路 | 完美保序 | 差，同质大象流照样极化 | 极低，传统芯片标配 |
| Flowlet（流突发切片） | 利用静默间隙换路 | 大体保序，依赖间隔时长 | 中等，间隔必须大于多径时延差 | 中等，要记录每条流的时间戳 |
| Packet Spraying（逐包喷洒） | 同一条流逐包轮流分发 | 彻底破坏顺序，必然乱序 | 高，利用率可贴近 95% | 高，压力全落在网卡 |

Flowlet 在 Web 流量里表现不错，HTTP 请求发完，TCP 连接往往安静几毫秒，这段时间足够前一个包到达，换路不会造成报文倒挂。训练流量没有静默期，NCCL 的 Ring AllReduce 一旦启动，端口就是持续数十秒的线速打满，流里找不到足够宽的间隔安全换路。

所以万卡集群上 AR 的方案普遍直接拉满到第三档：**逐包喷洒**。同一个 QP 的报文，前一个走 Spine1，后一个走 Spine2。

这就像一队人从同一个门出发，路上哪个路口空就往哪拐。人是都到齐了，队形从出门那一刻就没了，想重新排好只能在终点门口等。

## 代价落在网卡

带宽打满了，排队也跟着换了地方：**网络侧的排队减少，主机侧的乱序重组增加。**

多条路径的光纤长度不会完全相等，交换芯片的处理抖动也不会绝对对称，差几十纳秒，后发的报文就可能先到。

几十纳秒听上去不严重，算一下就明白了：一条 400Gbps 的流，把 4KB 的包推上线只要 80 纳秒，两条路径的时延差一旦超过一个包的发送时间，乱序就成了必然事件，不是概率事件。

网卡按传统方式处理，遇到 PSN 不连续的报文直接丢弃，逐包喷洒会把网络打瘫，所以开 AR 的前提是**网卡硬件原生支持乱序重组（OOO Reorder）**：网卡内部划出一块片内 SRAM 作乱序接收缓冲，硬件按报文头的 PSN 暂存、重排，再通过 DMA 直写应用显存。

和 TCP 的差别在实现位置，TCP 由主机 CPU 在内存里重排，耗时微秒级；RDMA 的重排全在网卡芯片逻辑里完成，纳秒级。

## 重组失效的现场

网卡的重组队列不是无限大，常见 400G 网卡的片内重组缓冲只有几兆字节。

几兆字节听着不小，换算一下就知道它多不经用：4MB 的缓冲按 400Gbps 的到达速率折算，只装得下 80 微秒。某条路径只要比同伴落后 80 微秒以上，缓冲就见了底。下文判读表里那条 10 微秒的告警线比这保守得多，它留的是余量，不是容量边界。

某条路径隐性故障或丢包，关键报文迟迟不来，后续报文持续涌入，重组缓冲就被占满，一旦 OOO Buffer 溢出，网卡只能强行丢包。

现场于是出现一个反直觉的画面：**交换机端口水线平稳、无丢包，网卡侧却突然报出大面积 RDMA 重传与任务超时。**

## 经验映射

| 你熟悉的机制 | 对应到自适应路由 |
|---|---|
| Nginx 轮询 upstream | 逐包喷洒（Packet Spraying） |
| 基于响应时间的动态选路 | 交换芯片按出端口队列深度自适应分流 |
| TCP 接收窗口的乱序重排 | RDMA 网卡片上 OOO 缓冲区与硬件重组 |
| 客户端缓冲打满后丢弃 | 网卡片内 SRAM 耗尽导致的序列错误丢弃 |

以前看网络只盯交换机、端口、队列。开 AR 之后，观测重心要往网卡片内状态、重组队列、多径时延偏差倾斜。

## 判读与实操

开启 AR 的集群，观测要覆盖交换机与网卡两端：

| 观察点 | 关键指标 | 采集方式 | 判读基准 |
|---|---|---|---|
| 交换机端口 | 动态选路偏转比率 | gNMI 订阅私有计数器 | 偏转率突增，说明直连链路有隐性丢包 |
| Fabric | 等价路径时延差（Path Skew） | INT 或高频探针 | 最大时延差超过重组容限（常见 > 10 µs）要告警 |
| 网卡端侧 | 乱序到达计数（`rx_out_of_order`） | `ethtool -S` | 高速增长属正常，说明喷洒生效 |
| 网卡端侧 | 乱序重组丢弃（`packet_seq_err`） | `ethtool -S <ifname>` | 必须为 0，非零即硬件重组失效 |

```bash
# 网卡侧与乱序、重排、重传相关的底层计数器
ethtool -S <ifname> | grep -Ei 'out_of_order|reorder|seq_err|out_of_buffer'

# 盯接收端重排错误的增量
watch -d -n 1 "ethtool -S <ifname> | grep -E 'packet_seq_err|out_of_buffer'"
```

判读两条：`rx_out_of_order` 上涨是常态，证明 AR 起效了；`packet_seq_err` 出现非零增长要立刻介入，说明网络时延抖动已经超过网卡硬件的重排能力。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：为什么说自适应路由把网络侧的排队压力换成了主机侧的乱序压力？

::: details 参考答案与评分维度

网络侧的变化：交换机把报文打散到所有上联，不再在单端口排队，队列水线保持低位，单端口微突发与 PFC 暂停随之减少。

主机侧的代价：多路径存在微小时延差，逐包分发让原本连续的报文乱序到达。

压力转移：接收端网卡必须动用片内高速缓冲，把报文暂存、比对、重排后再写显存。交换机里的排队行为，换成了网卡里的重组队列。

**评分维度**：答出两端行为差异（必需）。指出网络排队与网卡重组的对消关系（加分）。

:::

**必答 Q2**：某集群开启逐包 AR 后，交换机监控全绿无水线告警，训练任务频繁掉速超时。网卡侧 `rx_out_of_order` 巨大，`packet_seq_err` 每秒增加数千。指出根因与排查路径。

::: details 参考答案与评分维度

根因：某条等价路径存在物理劣化，光纤脏污或局部降速。慢路径上的报文时延极大，形成严重的 Path Skew。

失效链条：时延倾斜超过网卡重组容限，超期的乱序包被当作序列错误丢弃，引发 RDMA 重传风暴，拖垮通信。

排查路径：一是巡检所有上联光模块的收发光功率与 FEC 纠错计数，抓出误码慢链路；二是检查交换芯片的容忍时延差配置，确认链路劣化时芯片能不能自动剔除慢路径。

**评分维度**：指出慢链路引发 Path Skew 击穿重组窗口（必需）。给出从光模块与 FEC 找慢路径的落地步骤（必需）。

:::

**自测 Q3**：Flowlet 为什么不适用于训练流量，哪怕它保序性好、开销也低？

::: details 参考答案与评分维度

Flowlet 靠流内的静默间隙换路，要求间隙大于多径时延差。训练流量在 AllReduce 期间持续线速，流里没有静默期，找不到安全的换路点。硬换就会乱序，等于把 Flowlet 降级成逐包喷洒还多付了记录时间戳的开销。

**评分维度**：点出「需要静默间隙」这个前提（必需）。指出训练流持续线速（必需）。

:::

## 小结

静态 ECMP 的死穴是盲目哈希，同质流面前无路可选。自适应路由把选路权交给交换芯片的出端口队列状态，用逐包喷洒把整网带宽打满。

代价换了个地方付。网络甩掉了排队，接收端网卡就得用片内 SRAM 承接乱序重组、报文校验、序列维护。

一旦路径时延倾斜打穿网卡重组队列，现场就是三个「无」：没有 PFC 告警、没有交换机丢包、没有端口报错，任务却在超时。

哈希面前，谁跟谁同路全看运气，不看你这条流有多要紧。逐包喷洒把这份运气匀开了，账却记到了网卡上。

::: tip 本课要点

**选路权从静态五元组交给出端口队列深度，代价从交换机移到网卡。**

- 静态 ECMP 盲区：同质大象流五元组相同，哈希结果唯一，等价上行必然极化
- 三档粒度：**Per-Flow 保序但极化、Flowlet 依赖静默间隙不适用训练、逐包喷洒能打满**
- 代价换位：**网络侧队列水线下降，接收端网卡承担乱序重组**
- 失效模式：单链路劣化引发 Path Skew，打爆网卡重组缓冲后丢包
- 口径更替：交换机只看利用率不够，必须同时盯网卡的 `rx_out_of_order` 与 `packet_seq_err`

:::

留一个思考题：网络硬件已经支持逐包喷洒，为什么还要在应用层设计 Rail-Optimized 拓扑。
