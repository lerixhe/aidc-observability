前面两讲立了两个事实：RoCEv2 是标准 UDP 流，转发全靠 ECMP；训练通信全是同质大象流，五元组一模一样。

那换个哈希行不行？换盐、换算法、把内层五元组也混进去，试到天黑也没用，参与哈希的那几个字段本身长得一样，怎么算都是同一个数。**哈希不负责公平，它只负责可重复。**

那让交换机别提前拍板，走一步看一步呢？这就是自适应路由，它把选路权从报文的静态身份挪到了出端口的实时状态上。本节我们来讲自适应路由与它带来的乱序重组，后者比较复杂，读者要有心理准备。

## 基本结构

静态 ECMP 的过程是：报文进交换机，硬件拿五元组做哈希，模上链路数，算出来是几就走几号端口。这个过程有个盲区，它不管出端口此刻在排队的是谁，哪怕某个端口的水位已经贴着 XOFF 水线，只要新来报文的哈希值落在这里，硬件照样把它塞进去。

于是出现一种局面：一条上行顶着 XOFF 反复暂停，另一条上行一条流都没有。链路是等价的，流量不是。

```
上行 1  ████████████████████████  100%
上行 2  0%
```

自适应路由（Adaptive Routing，AR）只有一句：**选路依据从报文的静态身份，换成出端口的实时拥塞。** 交换芯片转发时看几条等价上行的队列深度，谁的浅、时延小，报文就给谁。

芯片里为此要维护一张状态表，大致长这样：

```c
struct egress_group {          // 一组等价上行
  port_t   ports[];            // 出端口
  uint32_t qdepth[];           // 每个端口此刻的队列深度，AR 的选路依据
  uint32_t last_update;        // 上次刷新时间，纳秒
  uint32_t base_hash;          // 静态哈希会选中的那一条，ECMP 的答案
}
```

`qdepth` 是关键，一次选路只读它，不读别的。芯片不可能每来一个包就去问所有出端口的真实水位，那太慢，它维护一份队列深度的副本，按固定周期刷新，选路时看副本。副本的刷新周期决定了 AR 的反应速度，也决定了它会不会把两个包同时指向一个其实已经满了的口。

## 查找过程

设想如果只有一条上行会怎样？选路这件事根本不存在，哈希算出来的那个端口就是唯一解，链路闲它走，链路堵它也得走。集群规模一涨，等价上行从两条变成八条、十六条，静态哈希的问题才浮出来，而且不是变慢，是直接把某一条打满。

先在一条能跑的命令上把盲区看清楚：

```bash
cd labs/05-clos-topo
go run . -exp 3        # 64 条流，源目 IP 与端口全部相同
```

```text
口径                最差极化度  CV     最大链路占比
L3（src/dst IP）      2.00        1.00   100%
L4（五元组）          2.00        1.00   100%
```

五元组一模一样时，三层的哈希和五元的哈希判出同一条路，最大链路占比 100%：全部流量压在一条上行，另一条一条流都没有。实验一还能补一个量级，八条随机流时最差极化度 2.00，两千零四十八条流才降到 1.07。哈希能做的是在**多条流之间**摊平，做不了一条流自己分叉，而训练流量恰好是后者。

那么把选路权交出去之后，一条流凭什么在几条路径之间分？这就得给它定一个分配算法。

## 选路粒度

切分粒度有三种，粗到细一路加码。

**Per-Flow**，完整五元组绑定一条路，保序，开销极低，是传统芯片的标配，代价是同质大象流照样极化。

**Flowlet**，利用流内的静默间隙换路，间隙必须大于多径时延差，才不至于让后发的包先到。它在 Web 流量里表现不错，HTTP 请求发完，TCP 连接往往安静几毫秒，这段时间足够前一个包落地，换路不会造成报文倒挂。训练流量没有静默期，NCCL 的 Ring AllReduce 一旦启动，端口就是持续数十秒的线速打满，流里找不到足够宽的间隔安全换路。

**Packet Spraying**，逐包喷洒，同一个 QP 的报文，前一个走 Spine1，后一个走 Spine2，顺序彻底不管了，利用率可以贴近 95%。

所以万卡集群上 AR 的方案普遍直接拉满到第三档。这就像一队人从同一个门出发，路上哪个路口空就往哪拐，人是都到齐了，队形从出门那一刻就没了，想重新排好只能在终点门口等。

芯片这边还有一个跟跳跃列表同构的细节：它不会每次都从最忙的那条路径开始比，那样太浪费，它记得上一次选中的端口，从那儿开始往后扫，第一个低于水线的就用，扫描的起点就是这份记忆。代价是低编号端口在均衡时更容易被选中，所以有的芯片还要在表里加一个轮转指针，扫一遍就往前挪一格。

## 乱序是怎么产生的

带宽打满了，排队也跟着换了地方：**网络侧的排队减少，主机侧的乱序重组增加。**

多条路径的光纤长度不会完全相等，交换芯片的处理抖动也不会绝对对称，差几十纳秒，后发的报文就可能先到。

几十纳秒听上去不严重，算一下就明白了：一条 400Gbps 的流，把一个 4KB 的包推上线只要 80 纳秒，两条路径的时延差一旦超过一个包的发送时间，乱序就成了必然事件，不是概率事件。

网卡按传统方式处理，遇到 PSN 不连续的报文直接丢弃，逐包喷洒会把网络打瘫，所以开 AR 的前提是**网卡硬件原生支持乱序重组**（OOO Reorder）：网卡内部划出一块片内 SRAM 作乱序接收缓冲，硬件按报文头的 PSN 暂存、重排，再通过 DMA 直写应用显存。

和 TCP 的差别在实现位置，TCP 由主机 CPU 在内存里重排，耗时微秒级；RDMA 的重排全在网卡芯片逻辑里完成，纳秒级。

## 重组过程

网卡的重组队列不是无限大，常见 400G 网卡的片内重组缓冲只有几兆字节。

几兆字节听着不小，换算一下就知道它多不经用：4MB 的缓冲按 400Gbps 的到达速率折算，只装得下 80 微秒。某条路径只要比同伴落后 80 微秒以上，缓冲就见了底。下文那条 10 微秒的告警线比这保守得多，它留的是余量，不是容量边界。

## 路径劣化时

某条路径隐性故障或者丢包，关键报文迟迟不来，后续报文持续涌入，重组缓冲就被占满，一旦 OOO Buffer 溢出，网卡只能强行丢包。

现场于是出现一个反直觉的画面：**交换机端口水线平稳、无丢包，网卡侧却突然报出大面积 RDMA 重传与任务超时。**

开启 AR 的集群，观测要覆盖两端。交换机侧看两个：动态选路偏转比率，偏转率突增说明直连链路有隐性丢包；Fabric 的等价路径时延差（Path Skew），用 INT 或高频探针取，最大时延差超过重组容限就要告警。网卡侧看 `ethtool -S` 里的计数器：

```bash
# 网卡侧与乱序、重排、重传相关的底层计数器
ethtool -S <ifname> | grep -Ei 'out_of_order|reorder|seq_err|out_of_buffer'

# 盯接收端重排错误的增量
watch -d -n 1 "ethtool -S <ifname> | grep -E 'packet_seq_err|out_of_buffer'"
```

判读两条：`rx_out_of_order` 上涨是常态，证明 AR 起效了；`packet_seq_err` 出现非零增长要立刻介入，说明网络时延抖动已经超过网卡硬件的重排能力。

## 如果所有路径都一样快呢

在一个极端的情况下，所有等价路径的时延完全相同，逐包喷洒还会不会乱序？答案是会，只是概率低了。

原因有三层，任何一层都不能假设为零：光纤长度差、芯片内部流水线的抖动、队列本身的排队差异。排队这一层最容易被忽略，同一个包走进两个不同深度的队列，出来的时刻就不可能一样，而 AR 恰恰是奔着「选浅的队列」去的，它保证的是均衡，不是等时。

那能不能让网卡的重组缓冲开得足够大，把这点差异全咽下去？可以，代价是那片 SRAM 是有限的，扩容等于把成本从交换机搬到网卡，而且治不了某条路径突然慢出 100 微秒的那种情况。

## 极化度是怎么算出来的

前面啰嗦了一堆，但是有一个数没有交代，就是「最大链路占比」，也就是极化度。这个数是怎么出来的？

如果只看总吞吐，极化是看不出来的：整机利用率照样能到 80%，只是那 80% 全压在一条路上。把每个出端口的字节计数按采样周期做差，除以这组端口的总量，取最大的一份，就是这个数。想要更稳的口径，再算一个变异系数 CV，它不关心最大值，关心的是这组数的分散程度，八条路径里一条满七条空，CV 正好是 1.00。

```py
# 采样周期内的增量，比绝对值有用
delta = [rx_bytes[p] - last[p] for p in egress_ports]
polar = max(delta) / sum(delta)        # 最大链路占比
mean  = sum(delta) / len(delta)
cv    = (sum((d - mean) ** 2 for d in delta) / len(delta)) ** 0.5 / mean
```

这样当我们要判断一次变更有没有把均衡改好，就把变更前后两个周期的极化度一对比，用不着看曲线。

## 思考

文中提到，静态 ECMP 的极化问题靠换哈希算法解决不了。那你手上那些以五元组为粒度的路径探测，在开了 AR 的集群里还有没有用？

如果确实还有用，那它探的是哪一段路，这一段跟报文实际走的那一段，还是不是一回事？

写作时也遇到一样的情况：一开始我把 `packet_seq_err` 当成链路误码，查了两天才明白它是序列错误的记账处，来源基本都在重组窗口里，跟光路没有关系。

## 小结

静态 ECMP 的死穴是盲目哈希，同质流面前无路可选。自适应路由把选路权交给交换芯片的出端口队列状态，用逐包喷洒把整网带宽打满。

代价换了个地方付。网络甩掉了排队，接收端网卡就得用片内 SRAM 承接乱序重组、报文校验、序列维护。一旦路径时延倾斜打穿网卡重组队列，现场就是三个「无」：没有 PFC 告警、没有交换机丢包、没有端口报错，任务却在超时。

这也改写了 IDC 那套经验。以前看 Nginx 轮询 upstream 就懂逐包喷洒，看响应时间选路就懂队列深度选路，看 TCP 的乱序重排就懂网卡的 OOO 缓冲；可监控的重心得从交换机、端口、队列往网卡片内状态、重组队列、多径时延偏差上挪。

哈希面前，谁跟谁同路全看运气，不看你这条流有多要紧。逐包喷洒把这份运气匀开了，账却记到了网卡上。

::: tip 本课要点

**选路权从静态五元组交给出端口队列深度，代价从交换机移到网卡。**

- 静态 ECMP 盲区：同质大象流五元组相同，哈希结果唯一，等价上行必然极化
- 三档粒度：**Per-Flow 保序但极化、Flowlet 依赖静默间隙不适用训练、逐包喷洒能打满**
- 代价换位：**网络侧队列水线下降，接收端网卡承担乱序重组**
- 失效模式：单链路劣化引发 Path Skew，打爆网卡重组缓冲后丢包
- 口径更替：交换机只看利用率不够，必须同时盯网卡的 `rx_out_of_order` 与 `packet_seq_err`

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：为什么说自适应路由把网络侧的排队压力换成了主机侧的乱序压力？

::: details 参考答案与评分维度

网络侧的变化：交换机把报文打散到所有上联，不再在单端口排队，队列水线保持低位，单端口微突发与 PFC 暂停随之减少。

主机侧的代价：多路径存在微小时延差，逐包分发让原本连续的报文乱序到达。

压力转移：接收端网卡必须动用片内高速缓冲，把报文暂存、比对、重排后再写显存。交换机里的排队行为，换成了网卡里的重组队列。

**评分维度**：答出两端行为差异（必需）。指出网络排队与网卡重组的对消关系（加分）。

:::

**必答 Q2**：某集群开启逐包 AR 后，交换机监控全绿无水线告警，训练任务频繁掉速超时。网卡侧 `rx_out_of_order` 巨大，`packet_seq_err` 每秒增加数千。指出根因与排查路径。

::: details 参考答案与评分维度

根因：某条等价路径存在物理劣化，光纤脏污或局部降速。慢路径上的报文时延极大，形成严重的 Path Skew。

失效链条：时延倾斜超过网卡重组容限，超期的乱序包被当作序列错误丢弃，引发 RDMA 重传风暴，拖垮通信。

排查路径：一是巡检所有上联光模块的收发光功率与 FEC 纠错计数，抓出误码慢链路；二是检查交换芯片的容忍时延差配置，确认链路劣化时芯片能不能自动剔除慢路径。

**评分维度**：指出慢链路引发 Path Skew 击穿重组窗口（必需）。给出从光模块与 FEC 找慢路径的落地步骤（必需）。

:::

**自测 Q3**：Flowlet 为什么不适用于训练流量，哪怕它保序性好、开销也低？

::: details 参考答案与评分维度

Flowlet 靠流内的静默间隙换路，要求间隙大于多径时延差。训练流量在 AllReduce 期间持续线速，流里没有静默期，找不到安全的换路点。硬换就会乱序，等于把 Flowlet 降级成逐包喷洒还多付了记录时间戳的开销。

**评分维度**：点出「需要静默间隙」这个前提（必需）。指出训练流持续线速（必需）。

:::
