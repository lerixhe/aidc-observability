RDMA 不能丢包，以太网默认会丢包，两者之间得有个东西把丢包挡在发生之前，这个东西是 PFC（Priority-based Flow Control），标准写在 IEEE 802.1Qbb。

PFC 的做法不复杂：队列快满了，让上游先别发。翻标准原文，一页纸就能读完，实现也就是一组水线加一帧报文。丢包确实被挡在了外面，代价是堆积，而堆积会顺着链路传染给本来无关的流量。

正因为简单，很多人看一眼就以为懂了。机制确实只有这么点，麻烦全在它的边界上，以及那几条边界在真实拓扑里怎么连锁发作。

## 交付

- 交换机丢包的成因，以及无损网络为什么不能靠重传补救
- 一次 PFC 暂停的完整生命周期：XOFF 水线、pause 帧、上游冻结、XON 恢复
- 三个属性（按优先级、逐跳、接收方驱动）各自解决什么，各自管不了什么
- 队头阻塞与拥塞上游化怎么让症状现场和根因现场分家
- 交换机与网卡上该看的 pause 计数、队列水线、无损队列丢弃

## 交换机为什么会丢包

交换机每个出端口挂着一组队列，常见 8 个，报文按优先级映射进去排队，出端口按线速往外发。

丢包的原因只有一个：**出端口的发送速率低于入队速率，队列涨满**，后到的报文被扔掉。跟设备好坏没关系，跟配置精不精细也没关系，队列满了就是满了。

有损网络对此的处理是照丢不误，TCP 自己重传。无损网络不能这么办，03 讲的因果链决定了重传代价太高。所以思路要反过来：**在队列涨满之前，让上游停手**。

那么为什么不让发送端自己减速？因为发送端看不见接收端的队列，它只知道自己的发送窗口，等它猜出来（TCP 就是靠丢包猜的），队列早就溢出了。PFC 把「停手」这个动作标准化了：暂停帧里带一个 8 位的优先级开关，加每个优先级的暂停时间值，单位是 512 bit time 的倍数，收帧的一方按这个时间把对应优先级的发送队列冻住。

## PFC 怎么工作

一次暂停的完整过程是这样：

```text
1. 水线监测   交换机持续看某个优先级的入队水位，涨到 XOFF 高水线就触发
2. 发暂停帧   向直连的上游设备（对端交换机或网卡）发 pause 帧：
              「优先级 N，停 t 个时间单位」
3. 上游冻结   上游把该优先级的发送队列冻住，报文停在自己这里，不丢弃
4. 恢复       下游水位降到 XON 低水线，再发一帧恢复，上游继续发
```

三个属性决定了它的能力边界：

| 属性 | 含义 | 解决了什么 | 没解决什么 |
|---|---|---|---|
| **按优先级** | 8 个队列独立暂停、独立恢复 | 只暂停 RoCE 的无损优先级，业务流量不受影响 | 同优先级内的多条流只能一起冻 |
| **逐跳** | 只管直连的上一跳，不是端到端 | 反压沿链路一级级传，不需要全局协调 | 源头感知不到，也管不了源头 |
| **接收方驱动** | 「我快满了，你少发」 | 主动权在接收端，不依赖发送端自觉减速 | 接收端判断失误或配置错误时，没人纠正它 |

第三行（接收方驱动）和 TCP 摆在一起看，差别就出来了。TCP 的拥塞控制是发送方的事：探测到丢包才降速，属于事后反应。PFC 反过来，接收方在队列还没满的时候喊停，属于事前干预。两者对「谁该负责」的假设不同，这也是无损网络里交换机必须参与流控的原因。

水线这个词本身就是个比方：队列是个水箱，XOFF 是上沿，XON 是下沿，涨到上沿就喊上游关阀，落回下沿再让它开阀。后面所有麻烦都出在这个水箱只有一个水面，它分得清优先级，分不清流。

一句话把边界说完：**PFC 管的是「这一跳的这个优先级别丢」，不是「这条流别慢」！** 想让某条流单独减速，得靠 ECN 那一套（第 06 讲）；想让某条流换条路走，得靠自适应路由（第 04 讲附）。拿 PFC 当万能流控使，得到的就是下面这四项代价。

## 队头阻塞

队列按优先级划分，不按流划分。同一优先级的流量共用一条队列，也就共用同一次暂停。回到水箱那个比方：关阀关的是一整个水箱的入口，管不住往里灌水的是哪几路人。

无损队列里跑着两条 RoCE 流：流 A 去往一台消费跟不上的接收端，它的暂停波传回来，队列被冻结；同一时刻流 B 去往另一台完全健康的接收端，因为和 A 同队列，一起被冻住，B 的路径没有拥塞，接收端也在正常收包，它的报文却停在上游队列里发不出去。

这就是队头阻塞（Head-of-Line Blocking）。传统 IDC 里也有这个现象，影响有限，几条流慢一点、重试几次就补上了；无损网络里它变成结构性问题，**受害者是全队列**，队列里有几条流，就有几个受害者。

## 拥塞上游化

暂停逐跳传播，反压一级一级往源头推，最后把流量堆到发送端网卡上，于是**故障现场和根因现场分家**：「A 收不到数据」这个现场，离真正的根因可能隔了好几跳，根因其实是「C 的出口队列堵了」。

单点指标在这种结构里没什么用，它答不出堵在哪、为什么堵。要答这两个问题，得把拓扑、多跳队列状态、路径级流量摆在一起看。设备级看现象，路径级看流量实际怎么走，作业级看哪个训练任务受害，这三种视角后面几讲会反复用到。

## 风暴与死锁

前面两个代价是机制自带的，下面两个是用错时出的后果。

PFC 风暴：某个下游持续喊停，暂停帧沿链路成片传播，大片链路的实际吞吐同时下跌。触发原因常见三种，一块故障或劣化的网卡、一个消费不动的应用进程、某一跳 PFC 配置不一致。它的特征是**丢包率为零、错误计数正常、整片区域一起变慢**。端口利用率可能还落在正常范围，因为链路没断，只是发不出去。

PFC 死锁：多台设备的队列形成环形等待，A 等 B 排空，B 等 C，C 等 A，谁也不放行。结构上跟进程死锁一样，只是资源换成了队列空间。死锁靠 PFC 自己解不开，每一方都在等对方。

工程上的解药是 PFC watchdog：监测到某队列被暂停超时，强制恢复并丢弃该队列的积压，或者打断等待环路。它用允许丢一点，换不永久死锁。

这个取舍要提前说清：无损在工程上是一个**概率承诺，不是绝对保证**。watchdog 介入那一刻，丢包就发生了，观测系统必须能认出这个痕迹。故障的具体形态与定位手段是 [07 讲](07-fault-modes.md) 的内容，这里先把机制想通。

## 经验映射

| 你熟悉的机制 | 对应到 PFC |
|---|---|
| 消息队列的消费者反压 | 逐跳 pause 帧 |
| 缓冲区堆积与背压传导 | 队列水位上涨、暂停波上传 |
| 单个慢消费者拖累整个分区 | 队头阻塞，同队列其他流被冻 |
| 分布式锁形成环路导致的死锁 | PFC 死锁，环形等待 |
| 超时强制回滚、熔断降级 | PFC watchdog |

PFC 和消息队列的消费者反压是同一个机制，作用点从进程间搬到了链路间。运维过 MQ 的人对它的代价也熟悉：反压不消灭拥堵，只是把丢弃换成堆积。堆积在哪、堆到谁、堆多久，这三个问题就是可观测要回答的。

还有一条容易被忽略：PFC 生效期间丢包率几乎不动，端口利用率看不出异常，路径时延却会剧烈膨胀、抖动飙升。传统 IDC 里这个信号常被当成噪声，在无损网络里它是主要线索。

## 判读与实操

五个指标，前三个是主看板：

| 指标 | 位置 | 判读 |
|---|---|---|
| PFC pause 帧收发计数（按优先级） | 交换机端口、网卡 | 是否发生反压，发生在哪个优先级 |
| PFC pause 持续时长或累计等待时间 | 交换机（部分平台支持） | 反压强度，比次数信息量大 |
| 队列水位（瞬时与峰值） | 交换机队列 | 是否贴近 XOFF / XON 水线 |
| 出方向丢弃与队列丢弃 | 交换机 | 无损队列出现丢弃，说明机制已失效或 watchdog 介入 |
| 端口发送队列长度（平均与峰值） | 交换机 | 队头阻塞的间接信号 |

```bash
# 主机侧：pause 与丢弃计数
ethtool -S <ifname> | grep -Ei 'pause|discard|out_of_buffer'

# 主机侧：当前哪些优先级开了 pause
mlnx_qos -i <ifname>

# 交换机侧（CLI 语义示意，命令随平台不同）
show priority-flow-control interface <intf>
show queue-monitor
```

三个信号放在一起读才有意义：

- **pause 计数持续增长，端口利用率却不高**。反压的典型信号，去查是哪个队列、哪条流在喊停。
- **无损队列出现 discard**。机制破裂了，可能是水线配错、watchdog 触发，或者上游没响应 pause。这是事故级信号。
- **单个端口的 pause 计数异常高**。该端口下游消费不动，顺着往下游查：网卡故障、应用卡住、对端配置错误，三者必居其一。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：讲一遍 PFC 的工作原理，必须包含三个词：水线、暂停帧、逐跳。讲完补一句它的本质属于哪类机制。

::: details 参考答案与评分维度

交换机监测无损优先级的入队水位，涨到 XOFF 水线就向直连上游发 pause 帧，要求该优先级停 t 个时间单位。上游冻结该优先级队列，报文留在自己这里不丢弃。下游水位降到 XON 后发恢复帧，流量继续。反压只作用于直连上一跳，靠逐跳传递形成波浪式传播。

本质上属于**接收方驱动的流控**，与消息队列的消费者反压同构，用堆积代替丢弃。

**评分维度**

- 三个关键词说清且因果正确（必需）
- 说出「按优先级」与「只暂停无损队列」（必需）
- 点出「堆积代替丢弃」（加分）
- 把 PFC 说成端到端机制（不通过，属于典型错误）

:::

**必答 Q2**：PFC 防住了丢包，防不住什么？说出两个由它引入的新问题，各用一两句说明成因。

::: details 参考答案与评分维度

1. **队头阻塞**。队列按优先级划分而非按流划分，一条流的目的地堵住，同队列其他流一起被冻。
2. **拥塞上游化**。逐跳反压把拥堵推向源头，症状现场与根因现场分离，定位难度陡增。
3. **PFC 风暴**。下游持续喊停时暂停帧成片传播，大面积吞吐下跌，且不体现为丢包。
4. **PFC 死锁**。环形依赖形成后各方互相等待，只能靠 watchdog 强制打断。

**评分维度**：任意两个各 1 分。说清成因而不是只报名字，给满分。四类全答出加 1 分。

:::

**自测 Q3**：PFC 死锁的解药为什么是 watchdog「允许丢一点」，而不是想办法把死锁彻底消除？

::: details 参考答案与评分维度

环形依赖一旦形成，PFC 自身无法自愈，因为每一方都在等对方。全网瞬时阻塞的代价是万卡停摆，远大于牺牲个别队列流量。工程上因此选 watchdog：检测到队列被暂停超时，强制解除，丢弃积压或打断等待。

这是可用性优先于完整性的取舍。它的直接后果是：无损是概率承诺，不是绝对保证，观测系统必须能识别 watchdog 介入的痕迹。

**评分维度**：说出「无法自愈、代价不对称」（必需）。说出「用局部丢包换全局可用」（必需）。提到无损不是绝对保证（加分）。

:::

**自测 Q4**：一条 RoCE 流的接收端应用消费不动，暂停波逐跳上传。此时三个问题：网络里丢包了吗；沿途去往别处的业务流量受影响吗；沿途同优先级、去往健康目的地的 RoCE 流受影响吗。

::: details 参考答案与评分维度

第一问，不丢。报文堆在沿途队列里，这正是 PFC 的设计目的。

第二问，不受直接影响。业务流量在同端口的其他优先级队列，PFC 按优先级暂停。共享出端口的带宽可能被间接挤压。

第三问，受影响。同优先级队列共享，队头阻塞把它一起冻住。

**评分维度**：三问全对给满分。第三问答错，说明队头阻塞没有理解到位。

:::

## 小结

交换机丢包的原因只有一个，出端口队列涨满。有损网络靠 TCP 重传兜底，无损网络的重传代价太高，于是 PFC 选择提前介入：水位到 XOFF 就向直连上游发暂停帧，上游把报文憋在自己队列里，水位退回 XON 再放行。

三个属性对应三种设计意图。按优先级保证业务流量不被牵连，逐跳保证不需要全局协调，接收方驱动保证不指望发送端自觉。这三样也一并定下了它的边界：同队列内的其他流它管不了，源头它管不了，接收端判断错了也没人纠正。

队列按优先级划分，一条流堵住，全队列遭殃。反压逐跳上传，拥堵被推到源头，症状现场和根因现场于是分家。再严重就是风暴与死锁，后者只能靠 watchdog 用允许丢一点换活性。

::: tip 本课要点

**PFC 把丢包换成堆积，代价是拥堵会传染。**

- 丢包唯一原因：**出端口队列涨满**。PFC 的思路是「满之前让上游停」
- 三个属性：**按优先级、逐跳、接收方驱动**。反过来看，它们也决定了 PFC 管不了同队列内其他流、管不了源头
- 四个代价：**队头阻塞、拥塞上游化、PFC 风暴、PFC 死锁**
- 死锁靠 **watchdog** 用「允许丢一点」换活性。无损是概率承诺，不是绝对保证
- 主看板：**pause 计数与时长、队列水位、无损队列 discard**。PFC 生效时丢包不动、时延暴涨

:::

留一个思考题：如果整张 Fabric 的 XOFF 都设得很保守，水线很低，最先变差的是吞吐还是时延。
