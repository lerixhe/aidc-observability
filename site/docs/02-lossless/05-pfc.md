RDMA 不能丢包，以太网默认会丢包，两者之间需要一个机制把丢包挡在发生之前。这个机制是 PFC（Priority-based Flow Control），标准定义在 IEEE 802.1Qbb。

它解决丢包的方式很直接：队列快满了，就让上游先别发。代价是把丢包换成了堆积，而堆积会沿链路传染给本来无关的流量。

## 交付

- 说清交换机丢包的唯一原因，以及无损网络为什么不能靠重传补救
- 完整复述一次 PFC 暂停的生命周期：XOFF 水线、pause 帧、上游冻结、XON 恢复
- 说出三个关键属性（按优先级、逐跳、接收方驱动）各自解决了什么问题，以及各自没解决什么
- 解释队头阻塞与拥塞上游化怎么让症状现场和根因现场分家
- 在交换机与网卡上找到 pause 计数、队列水线与无损队列丢弃这三类信号

## 交换机为什么会丢包

交换机每个出端口有一组队列，通常 8 个，报文按优先级映射进去，排队，出端口按线速发送。

丢包的原因只有一个：**出端口的发送速率低于入队速率，队列涨满，后到的报文被丢弃**。

有损网络对此的处理是照丢，TCP 自己重传。无损网络不能这么办，03 讲的因果链决定了重传代价太高。所以思路要反过来：在队列涨满**之前**，让上游停手。

PFC 就是把「停手」这个动作标准化了。它的暂停帧只带两个信息：哪个优先级，停多久。

## PFC 怎么工作

一次 PFC 暂停的完整过程是这样：

```text
1. 水线监测   交换机持续看某个优先级的入队水位，涨到 XOFF 高水线就触发
2. 发暂停帧   向直连的上游设备（对端交换机或网卡）发 pause 帧：
              「优先级 N，停 t 个时间单位」
3. 上游冻结   上游把该优先级的发送队列冻住，报文停在自己这里，不丢弃
4. 恢复       下游水位降到 XON 低水线，再发一帧恢复，上游继续发
```

三个属性决定了它的能力边界：

| 属性 | 含义 | 解决了什么 | 没解决什么 |
|---|---|---|---|
| **按优先级** | 8 个队列独立暂停、独立恢复 | 只暂停 RoCE 的无损优先级，业务流量不受影响 | 同优先级内的多条流只能一起冻 |
| **逐跳** | 只管直连的上一跳，不是端到端 | 反压沿链路一级级传，不需要全局协调 | 源头感知不到，也管不了源头 |
| **接收方驱动** | 「我快满了，你少发」 | 主动权在接收端，不依赖发送端自觉减速 | 接收端判断失误或配置错误时，没人纠正它 |

第三行要和 TCP 对照。TCP 的拥塞控制是发送方的事：探测到丢包才降速，属于事后反应。PFC 反过来，接收方在队列还没满的时候就喊停，属于事前干预。两者对「谁该负责」的假设完全不同，这也是无损网络里交换机必须参与流控的原因。

## 代价一：队头阻塞

队列是按优先级划分的，不是按流划分的。同一优先级的流量共用一条队列，也就共用同一次暂停。

设想一个场景：无优先级队列里跑着两条 RoCE 流。流 A 去往一台消费跟不上的接收端，它的暂停波传回来，队列被冻结。流 B 去往另一台完全健康的接收端，因为和 A 同队列，一起被冻住。

B 没有任何问题，它的路径没有拥塞，接收端也在正常收包，但它的报文停在上游队列里发不出去。这就是队头阻塞（Head-of-Line Blocking）。

这个现象在传统 IDC 里也存在，但影响范围有限：几条流慢一点，重试补上。无损网络里它变成结构性问题，因为它的受害者是全队列，而不是某一条流。队列里有几条流，就有几个受害者。

## 代价二：拥塞上游化

暂停是逐跳传播的，反压会一级一级往源头推，最后把流量堆到发送端网卡。

于是出现一个反直觉的现象：故障现场和根因现场不在同一个地方。「A 收不到数据」这句话描述的现场，可能离真正的根因隔了好几跳，而根因是「C 的出口队列堵了」。

::: warning 可观测性难度的来源

**症状现场不等于根因现场。**

监控看到「某条链路时延暴涨」，根因可能在几跳之外，甚至在一个不相干的源端口上。

只看单点指标，回答不了「堵在哪、为什么堵」。要回答这个问题，必须把拓扑、多跳队列状态、路径级流量三样东西关联起来看。

这也是后面反复要用的三种视角：设备级看现象，路径级看流量实际怎么走，作业级看哪个训练任务受害。

:::

## 风暴与死锁

前面两个代价是机制本身的属性，下面两个是机制用错时的后果。

**PFC 风暴**：某个下游持续喊停，暂停帧沿链路成片传播，大片链路的实际吞吐同时下跌。触发原因常见三种：一块故障或劣化的网卡、一个消费不动的进程、某一跳的 PFC 配置不一致。

它的特征很特别：**不丢包，没有错误计数，整张网突然集体变慢**。端口利用率可能还落在正常范围，因为链路没断，只是发不出去。

**PFC 死锁**：多台设备的队列形成环形等待，A 等 B 排空，B 等 C，C 等 A，谁也不放行。和进程死锁是同一套结构，只是资源换成了队列空间。

死锁靠 PFC 自己解不开，每一方都在等对方。工程上的解药是设备侧的 **PFC watchdog**：监测到某队列被暂停超时，强制恢复并丢弃该队列的积压，或者打断等待环路。它用「允许丢一点」换「不永久死锁」。

这个取舍的代价要提前说清：**无损在工程上是一个概率承诺，不是绝对保证**。watchdog 介入那一刻，丢包就发生了。观测系统必须能识别这个痕迹。

两类故障的具体触发场景、现场形态与定位手段，是 [07 讲](07-fault-modes.md) 的内容。这一讲只需要在机制上想通它们为什么会发生。

## 经验映射

| 你熟悉的机制 | 对应到 PFC |
|---|---|
| 消息队列的消费者反压 | 逐跳 pause 帧 |
| 缓冲区堆积与背压传导 | 队列水位上涨、暂停波上传 |
| 单个慢消费者拖累整个分区 | 队头阻塞，同队列其他流被冻 |
| 分布式锁形成环路导致的死锁 | PFC 死锁，环形等待 |
| 超时强制回滚、熔断降级 | PFC watchdog |

::: info 经验映射（IDC → AIDC）

PFC 与消息队列的消费者反压是同一个机制，作用点从进程间搬到了链路间。运维过 MQ 的人对它的代价也熟悉：反压不消灭拥堵，只是把丢弃问题换成堆积问题。

堆积在哪、堆到谁、堆多久，这三个问题就是可观测要回答的。

另一个直接推论：**时延劣化的敏感度在无损网络里是核心技能**。PFC 生效期间，丢包率几乎不动，端口利用率看不出异常，但路径时延会剧烈膨胀、抖动飙升。这恰恰是传统 IDC 里最容易被忽略的信号。

:::

## 判读与实操

五个指标，前三个是主看板：

| 指标 | 位置 | 判读 |
|---|---|---|
| PFC pause 帧收发计数（按优先级） | 交换机端口、网卡 | 是否发生反压，发生在哪个优先级 |
| PFC pause 持续时长或累计等待时间 | 交换机（部分平台支持） | 反压强度，比次数信息量大 |
| 队列水位（瞬时与峰值） | 交换机队列 | 是否贴近 XOFF / XON 水线 |
| 出方向丢弃与队列丢弃 | 交换机 | 无损队列出现丢弃，说明机制已失效或 watchdog 介入 |
| 端口发送队列长度（平均与峰值） | 交换机 | 队头阻塞的间接信号 |

```bash
# 主机侧：pause 与丢弃计数
ethtool -S <ifname> | grep -Ei 'pause|discard|out_of_buffer'

# 主机侧：当前哪些优先级开了 pause
mlnx_qos -i <ifname>

# 交换机侧（CLI 语义示意，命令随平台不同）
show priority-flow-control interface <intf>
show queue-monitor
```

判读三点：

- **pause 计数持续增长，端口利用率却不高**。这是反压的典型信号，去查是哪个队列、哪条流在喊停。
- **无损队列出现 discard**。机制破裂了，可能是水线配错、watchdog 触发，或者上游没响应 pause。这是事故级信号。
- **单个端口的 pause 计数异常高**。该端口下游消费不动，顺着往下游查：网卡故障、应用卡住、对端配置错误，三者必居其一。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：讲一遍 PFC 的工作原理，必须包含三个词：水线、暂停帧、逐跳。讲完补一句它的本质属于哪类机制。

::: details 参考答案与评分维度

交换机监测无损优先级的入队水位，涨到 XOFF 水线就向直连上游发 pause 帧，要求该优先级停 t 个时间单位。上游冻结该优先级队列，报文留在自己这里不丢弃。下游水位降到 XON 后发恢复帧，流量继续。反压只作用于直连上一跳，靠逐跳传递形成波浪式传播。

本质上属于**接收方驱动的流控**，与消息队列的消费者反压同构，用堆积代替丢弃。

**评分维度**

- 三个关键词说清且因果正确（必需）
- 说出「按优先级」与「只暂停无损队列」（必需）
- 点出「堆积代替丢弃」（加分）
- 把 PFC 说成端到端机制（不通过，属于典型错误）

:::

**必答 Q2**：PFC 防住了丢包，防不住什么？说出两个由它引入的新问题，各用一两句说明成因。

::: details 参考答案与评分维度

1. **队头阻塞**。队列按优先级划分而非按流划分，一条流的目的地堵住，同队列其他流一起被冻。
2. **拥塞上游化**。逐跳反压把拥堵推向源头，症状现场与根因现场分离，定位难度陡增。
3. **PFC 风暴**。下游持续喊停时暂停帧成片传播，大面积吞吐下跌，且不体现为丢包。
4. **PFC 死锁**。环形依赖形成后各方互相等待，只能靠 watchdog 强制打断。

**评分维度**：任意两个各 1 分。说清成因而不是只报名字，给满分。四类全答出加 1 分。

:::

**自测 Q3**：PFC 死锁的解药为什么是 watchdog「允许丢一点」，而不是想办法把死锁彻底消除？

::: details 参考答案与评分维度

环形依赖一旦形成，PFC 自身无法自愈，因为每一方都在等对方。全网瞬时阻塞的代价是万卡停摆，远大于牺牲个别队列流量。工程上因此选 watchdog：检测到队列被暂停超时，强制解除，丢弃积压或打断等待。

这是可用性优先于完整性的取舍。它的直接后果是：无损是概率承诺，不是绝对保证，观测系统必须能识别 watchdog 介入的痕迹。

**评分维度**：说出「无法自愈、代价不对称」（必需）。说出「用局部丢包换全局可用」（必需）。提到无损不是绝对保证（加分）。

:::

**自测 Q4**：一条 RoCE 流的接收端应用消费不动，暂停波逐跳上传。此时三个问题：网络里丢包了吗；沿途去往别处的业务流量受影响吗；沿途同优先级、去往健康目的地的 RoCE 流受影响吗。

::: details 参考答案与评分维度

第一问，不丢。报文堆在沿途队列里，这正是 PFC 的设计目的。

第二问，不受直接影响。业务流量在同端口的其他优先级队列，PFC 按优先级暂停。共享出端口的带宽可能被间接挤压。

第三问，受影响。同优先级队列共享，队头阻塞把它一起冻住。

**评分维度**：三问全对给满分。第三问答错，说明队头阻塞没有理解到位。

:::

## 小结

交换机丢包的原因只有一个，出端口队列涨满。有损网络靠 TCP 重传兜底，无损网络的重传代价太高，于是 PFC 选择提前介入：水位到 XOFF 就向直连上游发暂停帧，上游把报文憋在自己队列里，水位退回 XON 再放行。

三个属性对应三种设计意图。按优先级保证业务流量不被牵连，逐跳保证不需要全局协调，接收方驱动保证不指望发送端自觉。三样合起来，代价也一起带进来了。

队列按优先级划分而不是按流划分，于是一条流堵住，全队列遭殃，这是队头阻塞。反压逐跳上传，拥堵被推到源头，于是症状现场和根因现场分家。再严重就是风暴与死锁，后者只能靠 watchdog 用允许丢一点换活性。

::: tip 本课要点

**PFC 把丢包换成堆积，代价是拥堵会传染。**

- 丢包唯一原因：**出端口队列涨满**。PFC 的思路是「满之前让上游停」
- 三个属性：**按优先级、逐跳、接收方驱动**。反过来看，它们也决定了 PFC 管不了同队列内其他流、管不了源头
- 四个代价：**队头阻塞、拥塞上游化、PFC 风暴、PFC 死锁**
- 死锁靠 **watchdog** 用「允许丢一点」换活性。无损是概率承诺，不是绝对保证
- 主看板：**pause 计数与时长、队列水位、无损队列 discard**。PFC 生效时丢包不动、时延暴涨

:::

留一个思考题：如果整张 Fabric 的 XOFF 都设得很保守，水线很低，最先变差的是吞吐还是时延。
