为了确保一次梯度交换里某个优先级的报文不丢，一张成熟的无损网络通常都带着逐跳反压，PFC 也不例外。PFC 用起来非常简单，不同于端到端的拥塞控制，我们无须理解那些参数之间的联动，几条命令就能把它打开。不过也正是因为这种简单，它的模型很不严格，这要求我们不能像使用 TCP 那样来使用它。

PFC 的全称是 **Priority-based Flow Control**，标准写在 IEEE 802.1Qbb。做法不复杂：队列快满了，让上游先别发。翻标准原文，一页纸就能读完，实现也就是一组水线加一帧报文。丢包确实被挡在了外面，代价是堆积，而堆积会顺着链路传染给本来无关的流量。

正因为简单，很多人看一眼就以为懂了。机制确实只有这么点，麻烦全在它的边界上，以及那几条边界在真实拓扑里怎么连锁发作。

## PFC 的基本使用

交换机每个出端口挂着一组队列，常见八个，报文按优先级映射进去排队，出端口按线速往外发。丢包的原因只有一个：**出端口的发送速率低于入队速率，队列涨满**，后到的报文被扔掉。

有损网络对此的处理是照丢不误，TCP 自己重传。无损网络不能这么办，第三讲那条因果链决定了重传代价太高，所以思路要反过来：在队列涨满之前，让上游停手。

每个无损队列上和「停手」有关的东西就三样，形式大概是这样的，命令随平台不同，语义是这么个语义：

```text
switch(config)# interface ethernet 1/1
switch(config-if)# priority-flow-control mode on
switch(config-if)# priority-flow-control priority 3 xoff 2000 xon 800
switch(config-if)# show priority-flow-control interface ethernet 1/1
Port          Prio  RxPause  TxPause    Xoff    Xon
ethernet 1/1     3       17       42    2000    800
```

`xoff` 是高水线，`xon` 是低水线，`RxPause` 与 `TxPause` 是收到和发出的暂停帧计数。三条命令开完之后，一次暂停的完整过程是这样：

```text
1. 水线监测   交换机持续看某个优先级的入队水位，涨到 xoff 就触发
2. 发暂停帧   向直连的上游设备（对端交换机或网卡）发 pause 帧：
              「优先级 3，停 t 个时间单位」，每个单位 512 bit time
3. 上游冻结   上游把该优先级的发送队列冻住，报文停在自己这里，不丢弃
4. 恢复       下游水位降到 xon，再发一帧撤销，上游继续发
```

上面的过程里，所有报文在 pause 到达之前照发不误，收到 pause 之后才冻住，冻多久由帧里那个时间值说了算。因为 PFC 是逐跳的，它不用担心自己停下会牵连这条链路以外的东西，停的只是「往上游要这个优先级」这一件事，能把这条链路上的这个优先级别丢，就是它全部的承诺。

注意 `RxPause` 里那个 17，它就是这一跳正在替你兜底的次数，一次采样里十七次不算多，一分钟上千次就是另一回事了。

## 不丢包

那么 PFC 配上之后，真的就能不丢包吗？

下面看一个特别的例子。

```text
# 上游的出口队列，优先级 3，共享缓冲 12MB，xoff 设在 9MB
# 同一时刻，端口上还有优先级 0 的业务流量在抢这块缓冲
# 队列涨到 9MB，pause 发出去，上游停了
# 可 pause 从发出到生效，对面还在发在途的报文，这段叫 skid
# 在途的量按 400Gbps 与线缆时延算，2 微秒就是 100KB
# 缓冲只剩 3MB，够；只剩 200KB，不够
```

上面这个例子里，PFC 明明配着，报文还是丢了，因为 `xoff` 设得太贴近缓冲上沿，留下一段不够 skid 用的余量，或者同一块共享缓冲被别的优先级吃掉了一大截。是的，**PFC 只保证「我停了之后不再丢」，不保证「我停之前没丢」。**

到这里，你应该明白 PFC 根本不能算端到端无损，它仅仅满足了「逐跳不丢」这件事，而且是有条件的不丢。它有三个属性，每一个都同时是一份承诺和一条限制：

1. **按优先级**。八个队列独立暂停、独立恢复，只暂停 RoCE 的无损优先级，业务流量不受影响。反过来说，同优先级内的多条流只能一起冻。
2. **逐跳**。只管直连的上一跳，不是端到端，反压沿链路一级级传，不需要全局协调。反过来说，源头感知不到，也管不了源头。
3. **接收方驱动**。「我快满了，你少发」，主动权在接收端，不依赖发送端自觉减速。反过来说，接收端判断失误或者配置错误的时候，没人纠正它。

第三条跟 TCP 摆在一起看，差别就出来了。TCP 的拥塞控制是发送方的事，探测到丢包才降速，属于事后反应；PFC 反过来，接收方在队列还没满的时候喊停，属于事前干预。两者对「谁该负责」的假设不同，这也是无损网络里交换机必须参与流控的原因。

水线这个词本身就是个比方：队列是个水箱，xoff 是上沿，xon 是下沿，涨到上沿就喊上游关阀，落回下沿再让它开阀。后面所有麻烦都出在这个水箱只有一个水面，它分得清优先级，分不清流。

一句话把边界说完：**PFC 管的是「这一跳的这个优先级别丢」，不是「这条流别慢」！** 想让某条流单独减速，得靠 ECN 那一套；想让某条流换条路走，得靠自适应路由。拿 PFC 当万能流控使，得到的就是下面这几项代价。

## 恢复

PFC 的撤销不是等队列排空才做的，而是水位落回 `xon` 就做。暂停帧里那个时间值也有讲究，它是「最多停多久」，不是「停多久」。

上游收到一帧「停 65535 个单位」，它就冻 65535 个 512 bit time，到点自己解冻，哪怕下游还没喊恢复。所以低水线的设置要跟这个时间对上：设得太长，队列排空了，阀还关着，白白闲着一段；设得太短，一帧不够用，下游又得补发一帧，于是 pause 帧一帧接一帧，计数看着不高，实际一直在打。

还有一个反向的坑，`xon` 离 `xoff` 太近，队列在两条水线之间来回穿越，pause 和撤销交替发，这叫水线抖动，表现出来是端口利用率上蹿下跳，而丢包率一直是零。

## 队头阻塞

队列按优先级划分，不按流划分。同一优先级的流量共用一条队列，也就共用同一次暂停。回到水箱那个比方：关阀关的是一整个水箱的入口，管不住往里灌水的是哪几路人。

无损队列里跑着两条 RoCE 流：流 A 去往一台消费跟不上的接收端，它的暂停波传回来，队列被冻结；同一时刻流 B 去往另一台完全健康的接收端，因为和 A 同队列，一起被冻住，B 的路径没有拥塞，接收端也在正常收包，它的报文却停在上游队列里发不出去。

这就是队头阻塞（Head-of-Line Blocking）。传统 IDC 里也有这个现象，影响有限，几条流慢一点、重试几次就补上了；无损网络里它变成结构性问题，**受害者是全队列**，队列里有几条流，就有几个受害者。

## 拥塞上游化

暂停逐跳传播，反压一级一级往源头推，最后把流量堆到发送端网卡上，于是**故障现场和根因现场分家**：「A 收不到数据」这个现场，离真正的根因可能隔了好几跳，根因其实是「C 的出口队列堵了」。

单点指标在这种结构里没什么用，它答不出堵在哪、为什么堵。要答这两个问题，得把拓扑、多跳队列状态、路径级流量摆在一起看。设备级看现象，路径级看流量实际怎么走，作业级看哪个训练任务受害，这三种视角后面几讲会反复用到。

## 风暴与死锁

前面两个代价是机制自带的，下面两个是用错时出的后果。

PFC 风暴：某个下游持续喊停，暂停帧沿链路成片传播，大片链路的实际吞吐同时下跌。触发原因常见三种，一块故障或劣化的网卡、一个消费不动的应用进程、某一跳 PFC 配置不一致。它的特征是**丢包率为零、错误计数正常、整片区域一起变慢**。端口利用率可能还落在正常范围，因为链路没断，只是发不出去。

PFC 死锁：多台设备的队列形成环形等待，A 等 B 排空，B 等 C，C 等 A，谁也不放行。结构上跟进程死锁一样，只是资源换成了队列空间。死锁靠 PFC 自己解不开，每一方都在等对方。

工程上的解药是 PFC watchdog：监测到某队列被暂停超时，强制恢复并丢弃该队列的积压，或者打断等待环路。它用允许丢一点，换不永久死锁。这个取舍要提前说清，无损在工程上是一个**概率承诺，不是绝对保证**，watchdog 介入那一刻，丢包就发生了，观测系统必须能认出这个痕迹。

## 用 ECN 分担

上面的机制每生效一次，就要付一次网络读写：pause 帧从下游发出，上游收到，冻结，再等撤销。一条链路上几百条流都在同一个优先级里，暂停的次数多了，链路有相当一段时间是在关着阀过的。

所以工程上通常会把一部分「停手」从硬的换成软的，让 ECN 去承担常态的降速。发送端先减速，队列就涨不到 `xoff`，pause 帧自然少下来，落到 PFC 头上的只剩那些来不及减速的微突发。这跟把一个事务里的多条指令打成一个 pipeline 是一个道理，把多次往返压成一次，只不过这里压的不是指令，是暂停的往返。

## 盯住一条流

考虑一个业务场景，无损队列里跑着一条很要紧的梯度流，我们希望它别被打到暂停。PFC 是悲观的做法，不管谁在发，一律先停；ECN 是乐观的做法，先让发的人自己收一收。

**PFC 是一种悲观的反压，那是不是可以用乐观的方式来处理拥塞？** 可以。交换机在水线越过下限之后，只在报文头上打一个标记，接收端把这条标记回给发送端，发送端自己把速率降下来，整套动作里没有任何一次「停下」。

同一件事在两种配置界面上的写法差别不小。交换机 CLI 里是一行：

```text
switch(config-if)# congestion-control ecn minimum 400 maximum 1600 probability 10 mark
```

同一份东西写成模型化配置，大概是这样：

```yaml
interface:
  ethernet:
    - name: ethernet1/1
      qos:
        congestion-control:
          ecn:
            min-threshold: 400
            max-threshold: 1600
            marking-probability: 10
            action: mark
```

我们常听说命令行比模型化配置省事太多，但是从这个例子里看到 YAML 也没多出几行，大约只是从一行变成七行，多出来的是可校验、可对账、能进版本库。

**注意事项**

ECN 的 `max` 阈值不能压到 `xoff` 之上，两者必须留出一段距离，否则报文先被打了标记、还没来得及降速，队列已经撞上 `xoff`，ECN 就变成了 PFC 的预热器。这个顺序不能反。

## 判读与实操

主看板五个指标，逐个说：PFC pause 帧收发计数，按优先级看，判的是有没有发生反压、发生在哪个优先级；pause 持续时长或累计等待时间，部分平台支持，判的是反压强度，比次数信息量大；队列水位，看瞬时与峰值，判的是有没有贴近 xoff 与 xon；出方向丢弃与队列丢弃，无损队列出现丢弃就是机制已经失效或者 watchdog 介入了；端口发送队列长度，平均与峰值都要，它是队头阻塞的间接信号。

```bash
# 主机侧：pause 与丢弃计数
ethtool -S <ifname> | grep -Ei 'pause|discard|out_of_buffer'

# 主机侧：当前哪些优先级开了 pause
mlnx_qos -i <ifname>

# 交换机侧（CLI 语义示意，命令随平台不同）
show priority-flow-control interface <intf>
show queue-monitor
```

三个信号放在一起读才有意义。pause 计数持续增长而端口利用率不高，是反压的典型信号，去查是哪个队列、哪条流在喊停；无损队列出现 discard，机制破裂了，可能是水线配错、watchdog 触发，或者上游没响应 pause，这是事故级信号；单个端口的 pause 计数异常高，说明该端口下游消费不动，顺着往下游查，网卡故障、应用卡住、对端配置错误，三者必居其一。

还有一条容易被忽略：PFC 生效期间丢包率几乎不动，端口利用率看不出异常，路径时延却会剧烈膨胀、抖动飙升。传统 IDC 里这个信号常被当成噪声，在无损网络里它是主要线索。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：讲一遍 PFC 的工作原理，必须包含三个词：水线、暂停帧、逐跳。讲完补一句它的本质属于哪类机制。

::: details 参考答案与评分维度

交换机监测无损优先级的入队水位，涨到 XOFF 水线就向直连上游发 pause 帧，要求该优先级停 t 个时间单位。上游冻结该优先级队列，报文留在自己这里不丢弃。下游水位降到 XON 后发恢复帧，流量继续。反压只作用于直连上一跳，靠逐跳传递形成波浪式传播。

本质上属于**接收方驱动的流控**，与消息队列的消费者反压同构，用堆积代替丢弃。

**评分维度**

- 三个关键词说清且因果正确（必需）
- 说出「按优先级」与「只暂停无损队列」（必需）
- 点出「堆积代替丢弃」（加分）
- 把 PFC 说成端到端机制（不通过，属于典型错误）

:::

**必答 Q2**：PFC 防住了丢包，防不住什么？说出两个由它引入的新问题，各用一两句说明成因。

::: details 参考答案与评分维度

1. **队头阻塞**。队列按优先级划分而非按流划分，一条流的目的地堵住，同队列其他流一起被冻。
2. **拥塞上游化**。逐跳反压把拥堵推向源头，症状现场与根因现场分离，定位难度陡增。
3. **PFC 风暴**。下游持续喊停时暂停帧成片传播，大面积吞吐下跌，且不体现为丢包。
4. **PFC 死锁**。环形依赖形成后各方互相等待，只能靠 watchdog 强制打断。

**评分维度**：任意两个各 1 分。说清成因而不是只报名字，给满分。四类全答出加 1 分。

:::

**自测 Q3**：PFC 死锁的解药为什么是 watchdog「允许丢一点」，而不是想办法把死锁彻底消除？

::: details 参考答案与评分维度

环形依赖一旦形成，PFC 自身无法自愈，因为每一方都在等对方。全网瞬时阻塞的代价是万卡停摆，远大于牺牲个别队列流量。工程上因此选 watchdog：检测到队列被暂停超时，强制解除，丢弃积压或打断等待。

这是可用性优先于完整性的取舍。它的直接后果是：无损是概率承诺，不是绝对保证，观测系统必须能识别 watchdog 介入的痕迹。

**评分维度**：说出「无法自愈、代价不对称」（必需）。说出「用局部丢包换全局可用」（必需）。提到无损不是绝对保证（加分）。

:::

**自测 Q4**：一条 RoCE 流的接收端应用消费不动，暂停波逐跳上传。此时三个问题：网络里丢包了吗；沿途去往别处的业务流量受影响吗；沿途同优先级、去往健康目的地的 RoCE 流受影响吗。

::: details 参考答案与评分维度

第一问，不丢。报文堆在沿途队列里，这正是 PFC 的设计目的。

第二问，不受直接影响。业务流量在同端口的其他优先级队列，PFC 按优先级暂停。共享出端口的带宽可能被间接挤压。

第三问，受影响。同优先级队列共享，队头阻塞把它一起冻住。

**评分维度**：三问全对给满分。第三问答错，说明队头阻塞没有理解到位。

:::

## 小结

交换机丢包的原因只有一个，出端口队列涨满。有损网络靠 TCP 重传兜底，无损网络的重传代价太高，于是 PFC 选择提前介入：水位到 xoff 就向直连上游发暂停帧，上游把报文憋在自己队列里，水位退回 xon 再放行。

三个属性对应三种设计意图。按优先级保证业务流量不被牵连，逐跳保证不需要全局协调，接收方驱动保证不指望发送端自觉。这三样也一并定下了它的边界：同队列内的其他流它管不了，源头它管不了，接收端判断错了也没人纠正。

队列按优先级划分，一条流堵住，全队列遭殃。反压逐跳上传，拥堵被推到源头，症状现场和根因现场于是分家。再严重就是风暴与死锁，后者只能靠 watchdog 用允许丢一点换活性。故障的具体形态与定位手段是 [07 讲](07-fault-modes.md) 的内容，这里先把机制想通。


## 思考题

为什么 PFC 的水线问题不能靠「把缓冲调大」来解决？

再留一个：如果整张 Fabric 的 xoff 都设得很保守，水线很低，最先变差的是吞吐还是时延。

::: tip 本课要点

**PFC 把丢包换成堆积，代价是拥堵会传染。**

- 丢包唯一原因：**出端口队列涨满**。PFC 的思路是「满之前让上游停」
- 三个属性：**按优先级、逐跳、接收方驱动**。反过来看，它们也决定了 PFC 管不了同队列内其他流、管不了源头
- 四项代价：**队头阻塞、拥塞上游化、PFC 风暴、PFC 死锁**
- 死锁靠 **watchdog** 用「允许丢一点」换活性。无损是概率承诺，不是绝对保证
- 主看板：**pause 计数与时长、队列水位、无损队列 discard**。PFC 生效时丢包不动、时延暴涨

:::

## 参考资料

- [IEEE 802.1Qbb — Priority-based Flow Control](https://standards.ieee.org/ieee/802.1Qbb/4509/)（PFC 帧格式、XOFF / XON 语义、逐跳作用范围的规范定义）
- [IEEE 802.1Qaz — Enhanced Transmission Selection](https://standards.ieee.org/ieee/802.1Qaz/5410/)（ETS 带宽分配，与 PFC 共同构成 DCB 的无损队列模型）
- Guo et al., *RDMA over Commodity Ethernet at Scale*, SIGCOMM 2016（微软在生产 RoCE 集群中观察到的 PFC 反压、队头阻塞与 pause 风暴数据）
- Zhu et al., *Congestion Control for Large-Scale RDMA Deployments*, SIGCOMM 2015（DCQCN 论文，含生产环境 PFC 触发频率与代价的量化）
- [OpenConfig — QoS / Queue models](https://github.com/openconfig/public/tree/master/release/models/qos)（队列水线、丢弃、pause 相关指标模型的公开定义）
- [NVIDIA MLNX_OFED / mlnx_qos 文档](https://docs.nvidia.com/networking/)（主机侧 PFC 配置与 pause 计数器的用法）
