如果要用一句话来描述这一讲，我想应该是：PFC 是抢救，ECN + DCQCN 是治未病。

上一讲的 PFC 是"快满了才喊停"。它的触发条件是队列涨到 XOFF 高水线，**那时候队列已经快满了**，代价很大：冻结整个优先级队列、可能传染、可能死锁。

更好的策略是让拥塞**刚冒头**就通知源端"你发太快了，请降速"，队列根本涨不到 XOFF。这需要两个能力：

1. 交换机能告诉网络"这里开始堵了"：**ECN**
2. 源端网卡收到通知后能主动降速：**DCQCN**

## 学完这一讲，你应该能

- 说清 ECN 的两位标记与交换机的三段水线（Kmin / Kmax）策略
- 完整画出 DCQCN 闭环，并指出 CP / NP / RP 三个角色各自落在哪台设备上
- 解释"PFC 是最后防线、ECN/DCQCN 是主防线"的分工，以及健康网络里 PFC 为什么应该是罕见事件
- 建立三级指标分级：ECN 标记率（领先）→ PFC pause（滞后）→ 丢包（事故确认）
- 与 TCP 拥塞控制对照，说清"信号来源"与"决策位置"的两处根本差别

## 机制拆解

### 0x01 为什么 PFC 不够，要再补一层

拿急诊打比方，PFC 是病危抢救，代价大。日常体检是另一套：拥塞早期就通知源端降速，让队列涨不到 XOFF。

这需要两个能力：**交换机侧的显式标记（ECN）** 与 **网卡侧的闭环降速（DCQCN）**。两者合起来，才是 RoCEv2 完整的拥塞控制。

### 0x02 ECN：在报文里夹一张"此处轻微拥堵"的便签

**ECN（Explicit Congestion Notification）** 是 IP 头里的两个 bit。怎么理解？它相当于在报文上夹一张便签，写着"此处轻微拥塞，收到请降速"。

| 阶段 | 谁做 | 做什么 |
|---|---|---|
| 发送 | 源端网卡 | 给报文打 `ECT` 标记："我能理解拥塞通知" |
| 标记 | 交换机 | 队列低于 `Kmin` 不管；在 `Kmin~Kmax` 之间**按概率打 `CE` 标记**；超过 `Kmax` 通常全标（或交给 PFC） |
| 传递 | 网络 | CE 标记**随报文到达接收端**，便签是写给收件人的 |
| 反馈 | 接收端网卡 | 见到 CE 就回 `CNP` 通知包给源端 |

对比一下有损网络。TCP 的拥塞信号是**丢包**，隐式、事后、粗暴。无损网络的拥塞信号是**CE 标记**，显式、事前、温和。

这是"有损到无损"范式转换的又一处语义翻转：**拥塞从"已经发生的事故"变成"正在发生的、可观测的状态"**。

::: info 为什么标记打在报文上，而不是直接发给源端

因为交换机不知道、也不该关心某条 RDMA 流对应哪台源主机。它只做逐包处理，代价最低。

让接收端把信号折叠成 CNP 回到源端，是"谁最清楚谁反馈"的分工：接收端知道是哪个 QP 收到了 CE，交换机不知道。

这个设计还有个副产品：反馈路径与数据路径解耦。CNP 是独立的控制报文，可以自己带优先级。
:::

### 0x03 DCQCN：收到便签之后，谁降速、怎么降

ECN 只负责标记，降速动作由 **DCQCN**（Data Center Quantized Congestion Notification）完成。

换句话说，DCQCN 相当于把 TCP 的拥塞控制搬进网卡硬件，信号来源从丢包换成了 CE 标记。闭环里有三个角色：

| 角色 | 名称 | 落在哪 | 做什么 |
|---|---|---|---|
| **CP** | Congestion Point | 交换机 | 监测队列水位，按概率打 CE 标记 |
| **NP** | Notification Point | 接收端网卡 | 收到 CE 报文 → 按控制频率回 `CNP` 给源端 |
| **RP** | Reaction Point | 发送端网卡 | 收到 CNP → 按比例降速；一段时间没再收到 → 定时器驱动逐步恢复 |

完整闭环，可以照着画：

```text
① 交换机队列涨过 Kmin        → 给过路报文打 CE 标记
② 接收端网卡解到 CE          → 回 CNP 给源端
③ 源端网卡按 CNP 密度降速    → 拥塞源头的流量被压回去
④ 队列水位回落               → 不再打标 → 源端定时器驱动逐步升速
```

一句话定位：**DCQCN 是主防线，主动降速，治未病。PFC 是最后防线，物理暂停，保命。**

一个调优良好的无损网络里，PFC pause 应该是**罕见事件**。PFC 频繁触发，说明 DCQCN 参数没调好（Kmin/Kmax、降速斜率、CNP 频率、恢复定时器），或者存在异常流量。

### 0x04 和 TCP 拥塞控制对照着记

| 维度 | TCP 拥塞控制 | DCQCN |
|---|---|---|
| 信号 | **丢包**（或时延），隐式猜测 | **ECN 标记**，显式告知 |
| 决策者 | 内核协议栈（软件，慢，吃 CPU） | 网卡硬件（不耗 CPU，微秒级反应） |
| 动作 | 降 cwnd，靠重传兜底 | 降速 + 定时恢复，PFC 只兜底 |
| 粒度 | 每条连接独立感知 | 端网协同，交换机深度参与 |

这套端网协同有个隐含要求：**交换机与网卡的参数要配套调优**。Kmin/Kmax、PFC 水线、CNP 频率、降速系数是联动的，任何一个不匹配，闭环就失效。

所以"批量、一致地改全网设备参数"成了刚需。管控面（Netconf / gNMI 下发）从运维便利，变成了正确性的一部分。

## 经验映射

| 你熟悉的概念 | 在无损网络里的对应 |
|---|---|
| 领先指标 vs 滞后指标 | **ECN 标记率 = 领先**，PFC pause = 滞后，丢包 = 确认 |
| 阈值告警 | 从这里开始要改成"分级 + 传导关系"分析，不再是单点阈值 |
| 实时流处理（Kafka → Flink → 时序库） | 完全复用：这些计数器就是普通时序流 |
| 主动探测（自产自收） | 换成**设备被动上报**（gNMI 订阅），采集模型不同 |
| 路径维度的观测 | 设备计数器是单点维度，需要与拓扑、路径数据关联才能定位 |

**领域语义变了，管道还是你那套。** 你已有的实时链路可以把 ECN / PFC 计数器当成普通时序流处理。增量工作只在两处：数据源的采集方式、跨维度关联分析。

## 判读与实操

### 0x05 三级健康指标（这一讲最重要的产出）

| 层级 | 指标 | 含义 | 处置 |
|---|---|---|---|
| 领先 | **ECN 标记率**（按端口/优先级/队列） | 拥塞正在形成，已被 DCQCN 接管 | 观察趋势；持续升高说明流量模型或参数需要调整 |
| 滞后 | **PFC pause 次数与时长** | DCQCN 没兜住，已经在反压 | 告警加定位到端口 / 队列 / 流 |
| 事故 | **无损队列丢包 / discard** | 机制失效（配置错误、死锁、硬件故障） | 最高优先级，立即定位 |

排障价值在于**传导关系**。

ECN 涨、PFC 跟着涨、然后丢包，说明拥塞在恶化。ECN 不高但 PFC 频繁，说明参数失衡或者存在微突发。PFC 不高却丢包，说明某跳配置错误，比如无损队列没开 PFC。这比单看任何一个数字都更能定位问题层级。

### 0x06 命令与指标位置

```bash
# 主机侧：ECN 标记与 CNP 相关计数（NVIDIA/Mellanox 命名示意）
ethtool -S <ifname> | grep -Ei 'ecn|cnp|np_cnp|rp_cnp'

# 交换机侧：队列 ECN 标记计数与阈值配置
show interface <intf> counters queue            # 每队列的标记/丢弃计数
show qos queue ecn                              # Kmin/Kmax 与标记概率
```

判读要点：

- **ECN 标记率有值，PFC 几乎为 0**。闭环工作正常，这是健康状态。
- **ECN 不高，PFC 很高**。DCQCN 参数有问题（Kmin 过高、降速不足），或者流量微突发超出标记能力，去看队列水线。
- **ECN 与 PFC 都不高，却有丢包**。优先怀疑配置不一致（某跳无损队列没开 PFC）或链路硬件问题。

## 习题

**必答 Q1**："既然 PFC 能保证不丢包，为什么还要 ECN / DCQCN？"先用一句话点破设计哲学，再展开两三点。

::: details 参考答案与评分维度

**一句话**：PFC 是事后抢救，代价大。ECN/DCQCN 是事前预防，尽量不让网络走到需要抢救的地步。

展开四点。

① **代价不对称**。PFC 一触发就冻结整个优先级队列，带来队头阻塞、暂停传播，甚至风暴或死锁。ECN 只改两个 bit，几乎零成本。
② **信号更早**。Kmin 到 Kmax 之间的标记发生在队列远未填满时，源端有充足时间降速。
③ **可观测性更好**。ECN 标记率是连续、可量化的"拥塞热度"指标。PFC 计数只有发生与未发生，信息量低。
④ **闭环可控**。DCQCN 的降速是概率化、渐进的，能避免吞吐剧烈震荡。

**评分维度**：一句话点破"预防 vs 抢救"（必需）。展开两点以上且涉及代价或信号时机（必需）。提到"ECN 标记率是更好的可观测指标"（加分）。
:::

**必答 Q2**：写出 DCQCN 闭环（交换机打标 → … → 源端升速），并指出三个角色各自在哪台设备上。

::: details 参考答案与评分维度

① 交换机（CP）队列涨过 Kmin，按概率给报文打 CE。
② 接收端网卡（NP）解到 CE，回 CNP 给源端。
③ 发送端网卡（RP）收到 CNP，按密度降速。
④ 队列水位回落，交换机不再打标。
⑤ 源端一段时间没收到 CNP，定时器驱动逐步升速。

**评分维度**

- 五步顺序正确（必需）
- CP/NP/RP 与设备对应正确（必需，最容易错的是把 NP 说成源端）
- 能补上"CNP 生成有控制频率，避免反馈风暴"（加分）
:::

**自测 Q3**：无损网络的三层健康指标分级是什么？各自含义与处置？

::: details 参考答案与评分维度

**ECN 标记率**是领先指标。拥塞正在形成，但已被 DCQCN 接管，轻微时属于正常运行的一部分。

**PFC pause 次数与时长**是滞后指标。说明 DCQCN 没兜住，或者参数失衡，需要告警排查。

**丢包 / 无损队列 discard** 是事故确认。机制本身失效（配置错误、死锁、硬件故障），最高优先级。

这三层本质上是一条传导链：拥塞先在 ECN 标记率上冒头，兜不住才落到 PFC，最后失守才是丢包。

排障价值在看 **ECN → PFC → 丢包**的传导关系，比单看任何一个数都更能定位问题层级。

**评分维度**：三层齐全且顺序（领先 / 滞后 / 确认）正确得基本分。能说出传导关系的判读价值得满分。
:::

**自测 Q4**：把 ECN / PFC 指标接入你已有的数据管道，和接入"主动探测质量数据"相比，最大的两个不同是什么？

::: details 参考答案与评分维度

① **数据来源不同**。探测数据是自产自收，主动发、自己收。这些计数器是**设备被动上报**，采集要走 gNMI 订阅或 SNMP 轮询。秒级事件用 SNMP 分钟级会漏（见 [11 gNMI 遥测](../04-telemetry/11-gnmi.md)）。

② **数据维度不同**。探测数据天然带路径维度（五元组 / ECMP 路径），设备计数器是单点维度。要回答"谁堵了、堵住了谁"，必须把设备计数器 × 拓扑 × 路径数据做关联分析。这正是图计算与路径覆盖能力结合的地方（见 [16 AIOps](../05-analysis/16-aiops.md)）。

**评分维度**：两点各 1 分。能指出"关联分析是新增工作量"而不是"管道直接复用就完事"，得满分。
:::

## 小结

这一讲可以压成一句话：**PFC 是抢救，ECN + DCQCN 是治未病。**

PFC 的毛病在于触发得太晚。队列快满了才喊停，一喊停就冻结整个优先级队列，副作用全来了。ECN 换了个思路，队列刚过 Kmin 就在报文上夹张便签，按概率打 CE 标记，让信号随报文走到接收端。

便签到了接收端，得有人把话传回去。接收端网卡看到 CE 就回 CNP，源端网卡收到 CNP 就降速，水位回落再靠定时器慢慢升回来。这三个角色分别是交换机、接收端网卡、发送端网卡，缺一个闭环都不成立。

分工定下来，指标分级也就跟着定了：ECN 标记率看趋势，PFC pause 看告警，丢包看事故。三条指标连起来读，比单看一个数字有用得多。

::: tip 本课要点

**PFC 是抢救，ECN + DCQCN 是治未病。**

- 设计哲学：**PFC 是最后防线（抢救），ECN / DCQCN 是主防线（治未病）**。健康网络里 PFC 应是罕见事件
- ECN 是 IP 头的 2 bit。交换机在 **Kmin~Kmax** 之间按概率打 **CE**，拥塞从"事故"变成"可观测状态"
- DCQCN 三角色：**CP 交换机打标 · NP 接收端回 CNP · RP 源端网卡降速 / 定时恢复**
- 指标三级：**ECN 标记率（领先）→ PFC pause（滞后）→ 丢包（事故确认）**，看传导关系而非单点
- 对比 TCP：信号从丢包变标记，决策从内核变**网卡硬件**。参数要端网配套，管控面是正确性的一部分
:::

留一个思考题：Kmin 设得很低会让 ECN 标记率很好看、PFC 几乎为零，这时候网络真的更健康吗。
