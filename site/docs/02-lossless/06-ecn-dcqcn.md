ECN 是数据中心里最常用的拥塞通知手段之一，顾名思义，它的灵感源于漏斗（funnel）的结构——只不过这个漏斗长在交换机里，装的是还没发出去的报文。

漏斗的容量是有限的，如果出端口一直不往外发，你一直往里灌水，它就会变满，直至再也装不进去。出端口一开，水往下流，流走一部分之后，就又可以继续往里面灌。如果流嘴淌水的速率大于灌水的速率，那么漏斗永远都装不满；如果淌水的速率小于灌水的速率，那么一旦漏斗满了，灌水就需要暂停并等待漏斗腾空。

所以，漏斗的剩余空间就代表着当前还能再收多少，漏斗淌水的速率代表着这条路径能放出去的最大频率。放到报文的世界里还有个更土的名字，叫水位。

水池上挂着两道机关。XOFF 水线是硬闸，水位一到就把上游进水口关死，这就是 PFC。Kmin 到 Kmax 那一段是软闸，还没到关阀的份上，先拎一块牌子告诉上游「慢点倒」，这就是 ECN。

PFC 是最后一道防线，触发条件很硬：队列涨到 XOFF 高水线。到那一刻队列已经快满，暂停不可避免，副作用也就一起跟着来。更好的做法是不让它走到那一步，拥塞刚冒头就让源端把速率降下来，队列永远涨不到 XOFF。

坡道就架在两个水线之间，下面用代码描述一下单个队列的标记规则。

## 标记规则

```py
# coding: utf8

import random

class Queue(object):

    def __init__(self, kmin, kmax, pmax):
        self.kmin = kmin       # 下限，水位到这儿才开始标
        self.kmax = kmax       # 上限，到这儿就该全标了
        self.pmax = pmax       # 上限处对应的标记概率，通常按队列容量折算
        self.depth = 0         # 当前队列水位，字节

    def enqueue(self, size):
        self.depth += size

    def dequeue(self, size):
        self.depth -= size

    def should_mark(self):
        if self.depth < self.kmin:          # 水位还没到下限，不打扰
            return False
        if self.depth >= self.kmax:         # 到上限了，一个一个标
            return True
        p = self.pmax * (self.depth - self.kmin) / (self.kmax - self.kmin)
        return random.random() < p          # 中间这段按概率标，水位越高标得越狠
```

再提供一个 C 版本的：

```c
static inline bool should_mark(struct queue *q)
{
    if (q->depth < q->kmin)
        return false;
    if (q->depth >= q->kmax)
        return true;
    /* 线性插值：水位越高，标得越狠 */
    uint32_t p = (uint64_t)q->pmax * (q->depth - q->kmin) / (q->kmax - q->kmin);
    return (rand() & 0xffff) < p;
}
```

`should_mark` 是这套算法的核心，它在每个报文出队前都会被调用一次，标不标就取决于当时的水位。标不标得准取决于 Kmin、Kmax 与 Pmax 三个值，而这三个值配得对不对，取决于出端口的带宽和队列能开多大。它的开销是一个常量，一次比较加一次随机数，跟这个队列里挤了多少条流没有关系。

按概率标是关键，它让标记率随水位连续变化，源端收到的降速信号也就是连续的，不会因为跨过一个阈值就从「不管」跳到「全标」。

那么问题来了，标记就是说一句话，让谁听见、听见了怎么办？交换机只看得见过路的包，看不见某条流属于哪台机器；源端只看得见自己的发送窗口，看不见下游的水位。把这两头接起来的活，不能只靠交换机。

而且这里有个麻烦：从交换机打标，到接收端回通知，再到源端把速率降下来，这三个动作隔着好几个 RTT，没法原子完成。降得狠一点，吞吐立刻塌下去；降得软一点，队列在反馈到位的这段时间里已经撞上 XOFF。这真是个艰难的选择，我们该如何解决这个问题呢？DCQCN 救星来了！

## DCQCN

DCQCN 是 SIGCOMM 2015 上那篇 *Congestion Control for Large-Scale RDMA Deployments* 给出的方案，它把 TCP 那一套拥塞控制搬进了网卡硬件，信号来源从丢包换成了 CE 标记，于是降速这件事从「协议栈里的一个算法」变成了「网卡固件里的几行状态机」。

它只认一个输入：CNP 的密度。CNP 不是新造的包，它是接收端网卡在解到 CE 标记之后回给源端的一条控制报文。四个量在源端网卡里滚动：

```text
α    = (1 - g) * α + g * F     # 每周期按 CNP 的到达比例 F 平滑一次，g 是平滑系数
rate = rate * (1 - α / 2)      # 收到 CNP，按 α 砍一刀，α 越大砍得越狠
rate = rate + 5%               # 定时器到点，没再收到 CNP，就小步加回来
T    = 55 µs                   # 升速的节奏，两个加号之间至少隔这么久
```

上面四个量是这么配合的：α 记的是「最近有多堵」，它被 CNP 的密度推着走，一段时间没有 CNP 就自己衰减回零；rate 是「现在能发多快」，它被 α 推着往下砍，也被定时器一点点抬上去；T 决定了抬升的节奏。这套设计的好处是它不光滑，还带惯性，一次 CNP 打到头上，rate 是砍一刀，砍完还要等好几个周期才慢慢爬回来。

一场拥塞打完，源端网卡里这组数字大致是这么个走向：

```text
1) rate   = 87 Gbps    # 从 100 砍到 87，砍了 13%
2) α      = 0.26       # 平滑后的 CNP 密度，越小说明越不堵了
3) cnps   = 61         # 上一个周期收回来 61 条 CNP
4) next   = 0.07s      # 距离下一次允许升速还有 70 毫秒
```

字段名随网卡和固件各家不同，意思是这四个。这个实现考虑得很周到，连下次什么时候可以升速都替你算好了，照着定时器加回来就行；如果不想让速率一步跳回去，也可以把那个 5% 调小，代价是恢复得更慢。

闭环里有三个角色，一个都少不了：

```text
① 交换机队列涨过 Kmin        → 给过路报文按概率打 CE 标记（CP）
② 接收端网卡解到 CE          → 按控制频率回 CNP 给源端（NP）
③ 源端网卡收到 CNP           → 按 α 把速率砍一刀（RP）
④ 队列水位回落，低于 Kmin    → 不再打标，CNP 停止
⑤ 源端一段时间没收到 CNP     → 定时器驱动，逐步把速率加回来
```

第 ⑤ 步的恢复是渐进的，不是一步回到原速，降速要快、恢复要慢，否则立刻又会撞上拥塞。第 ② 步的频率控制要单独说：如果每个 CE 报文都回一个 CNP，拥塞严重时反馈报文本身就会变成新的负担，所以实际实现会对 CNP 做限频，比如每 N 个字节或每 N 微秒最多回一个。

标记为什么不干脆由交换机直接通知源端？因为交换机不知道也不该关心某条 RDMA 流属于哪台源主机，它做的是逐包处理，每次只看到当前这个报文，改成追踪流的身份，代价立刻涨上去。让接收端把信号折叠成一个 CNP 送回源端，是「谁最清楚谁反馈」的分工：接收端知道是哪个 QP 收到了 CE，交换机不知道。这个设计还有一个副产品，反馈路径与数据路径解耦，CNP 是独立的控制报文，可以单独设优先级，不受数据流的拥塞影响。

## 和 TCP 对照

显式这两个字是跟 TCP 比出来的。TCP 靠丢包和时延去推测拥塞，猜的成分很大；ECN 是路径上的设备直接告诉源端「我这儿堵了」，不用猜。

两处差别的后果不同：**信号来源从丢包换成标记**，拥塞在造成损失之前就被发现了；**决策位置从内核搬到网卡**，降速可以在微秒级完成，也不占用本就紧张的 CPU 核。代价是灵活性，TCP 的拥塞控制算法可以换、可以调，改的是软件；DCQCN 的参数烧在网卡固件和交换机配置里，改动要过设备厂商的接口，还要保证全网一致。

ECN 的那两个 bit 在 IP 头的老位置，RFC 3168 定的，四种状态：`00` 是本流不支持，`01` 和 `10` 是支持但还没被标，`11` 是这台设备认为此处拥塞。发送端置 `01` 或 `10`，等于跟沿途设备说「堵了你就标，不必丢」，交换机在 Kmin 与 Kmax 之间按概率把它改成 `11`，接收端看见了就回 CNP。

回到水池。入队速率不超过出队速率，水位永远升不到 Kmin，牌子一直不掉下来，这是健康状态。入队速率持续大于出队速率，水位迟早穿过 Kmin，标就开始一个个往外发。水位钉在 Kmax 上不下，说明源端没踩刹车，或者刹车踩得太轻，下一个接手的就只有 XOFF 那道硬闸了。

## 参数是联动的

这套端网协同有一个隐含前提：交换机和网卡的参数要配套。Kmin、Kmax 决定什么时候开始标记，PFC 的 XOFF / XON 决定什么时候兜底，CNP 生成频率决定反馈的快慢，降速系数与恢复定时器决定源端的反应曲线，这几组参数联动，**改一个就要重新校核其他几个**。

举个具体的失衡：Kmin 设得过高，队列要涨到很晚才开始标记，信号来不及传导到源端，队列已经撞到 XOFF，PFC 频繁触发；Kmin 设得过低，标记率长期偏高，源端一直在降速，吞吐上不去。两种失衡到了值班表上都写成同一句话，「最近网络有点慢」。

所以「批量、一致地改全网设备参数」不再只是运维便利，它是这套机制能工作的前提。管控面下发（Netconf、gNMI）在这里不是可选项。

参数摊开是这么几组：Kmin 与 Kmax、CNP 的生成频率、速率增量的更新周期、降速比例、恢复定时器。论文给过一组默认值，但那是特定规模、特定流量模型下压出来的，厂商设备出厂默认又是另一套，两家厂商的默认值对不上是常事。

现场的调参流程基本长这样：先把 Kmin / Kmax 与 XOFF / XON 对齐，保证标记先动、兜底后动；再压测找降速与恢复的拐点，一次只动一组，动完重跑同一份流量；最后把这组值写进配置管理，别让它在下一次固件升级后悄悄回退。抄默认值能把实验跑通，跑不通生产，这句在每篇讲调参的地方都成立，本讲只是第一个。

## 判读与实操

指标分三级，划分依据是时间尺度。

一级是**ECN 标记率**，按端口、按优先级、按队列看。它是领先指标，说明拥塞正在形成、已经被 DCQCN 接管。看的是趋势，持续升高说明流量模型或参数需要调整。

二级是**PFC pause 次数与时长**。它是滞后指标，说明 DCQCN 没兜住，已经进入反压，该告警了，定位要精确到端口、队列、流。

三级是**无损队列丢包与 discard**。这是事故确认，说明机制本身失效，配置错误、死锁、硬件故障都在这一级，处置优先级最高。

单看任何一个数字都定不了位，价值在传导关系上。ECN 涨、PFC 跟着涨、随后丢包，说明拥塞在持续恶化，DCQCN 已经压不住；ECN 不高但 PFC 频繁，说明参数失衡或者存在微突发，标记还没来得及传导，队列已经撞线；ECN 与 PFC 都不高，却有丢包，先怀疑某跳配置错误，比如无损队列没开 PFC。

```bash
# 主机侧：ECN 标记与 CNP 相关计数（命名随驱动版本略有差异）
ethtool -S <ifname> | grep -Ei 'ecn|cnp|np_cnp|rp_cnp'

# 交换机侧：每队列的标记与丢弃计数、ECN 阈值配置
show interface <intf> counters queue
show qos queue ecn
```

指标语义变了，数据管道还是原来那套，ECN 与 PFC 计数器可以当普通时序流处理，采集、存储、查询的链路不用重写。增量工作在两处：采集方式从拉变成推，分析方式从单点阈值变成跨维度关联，这两件事在第四、五篇展开。

## 拓展阅读

**1. 《那两个 bit 空了十七年》**

ECN 在 2001 年就写进了 RFC，之后的十几年里，它在公网上的部署率基本是个笑话：默认关着，开了也多半没人配阈值，网管看着那两个 bit 一直是 `00`，谁也没觉得有问题。直到数据中心把 DCTCP 和 DCQCN 搬上来，大家才发现这两个 bit 原来一直在原位等着，一直没被用。

—— 原来一个字段可以先空着十七年，等的就是一个真正需要它的场景。

笔者表示要重新拾起放弃很久的 RFC 3168。哎，干网络这一行，真是要活到老，学到死啊！😢

::: tip 本课要点

**ECN 提前标记，DCQCN 闭环降速，PFC 只做兜底。**

- 分工的根据是时间尺度：**ECN 在 Kmin 就开始介入，PFC 到 XOFF 才动手**
- ECN 是 IP 头两个 bit：源端置 ECT，交换机在 Kmin 到 Kmax 之间**按概率**打 CE，接收端回 CNP
- DCQCN 三角色：**CP 交换机打标、NP 接收端回 CNP、RP 源端降速与恢复**
- 指标三级：**ECN 标记率（领先）、PFC pause（滞后）、丢包（事故确认）**，看传导关系
- 参数联动：Kmin / Kmax、XOFF / XON、CNP 频率、降速与恢复系数要配套，**管控面是正确性的前提**

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：既然 PFC 能保证不丢包，为什么还要 ECN 与 DCQCN？给出三条理由。

::: details 参考答案与评分维度

**代价不对称**。PFC 一触发就冻结整个优先级队列，带来队头阻塞、暂停传播，最坏是风暴与死锁。ECN 只改两个 bit，几乎零成本。

**信号更早**。Kmin 到 Kmax 之间的标记发生在队列远未填满时，源端有充足时间把速率降下来。

**信息量更大**。ECN 标记率是连续值，能反映拥塞程度和恶化速度，做趋势和告警都好用。PFC 计数只有有无，答不出「有多堵」。

还有一条可以补：闭环可控。DCQCN 的降速是概率化、渐进的，能避免吞吐剧烈震荡。

**评分维度**：三条中答对两条（必需）。其中至少一条涉及时机或代价（必需）。提到「ECN 标记率是更好的可观测指标」（加分）。

:::

**必答 Q2**：写出 DCQCN 闭环的五步，并指出三个角色各在哪台设备上。

::: details 参考答案与评分维度

交换机（CP）队列涨过 Kmin，按概率打 CE。接收端网卡（NP）解到 CE，按控制频率回 CNP 给源端。发送端网卡（RP）收到 CNP，按密度降速。队列水位回落，不再打标。源端一段时间没收到 CNP，定时器驱动逐步升速。

**评分维度**

- 五步顺序正确（必需）
- CP、NP、RP 与设备对应正确（必需，最常见的错误是把 NP 说成源端）
- 补出「CNP 有限频，避免反馈风暴」或「恢复是渐进的不硬切」（加分）

:::

**自测 Q3**：三级健康指标分别是什么，各自的行为？为什么单看一个数字定不了位？

::: details 参考答案与评分维度

**ECN 标记率**是领先指标。拥塞正在形成，已被 DCQCN 接管，轻微时属于正常范围。

**PFC pause 次数与时长**是滞后指标。DCQCN 没兜住，已经进入反压，需要告警。

**丢包与无损队列 discard** 是事故确认。机制本身失效，配置错误、死锁、硬件故障，最高优先级。

三者构成一条传导链。单看一个数字只能说明当前处在哪一层，看不出方向和原因。同样一个 PFC 计数，配上高 ECN 说明拥塞恶化，配上低 ECN 说明参数失衡，处置完全不同。

**评分维度**：三层齐全且顺序正确（必需）。说出传导关系的判读价值（必需）。

:::

**自测 Q4**：把 ECN 与 PFC 指标接进已有的数据管道，与接入主动探测数据相比，最大的两个不同是什么？

::: details 参考答案与评分维度

**数据来源不同**。探测数据自产自收；这些计数器是设备被动上报，采集要走 gNMI 订阅或 SNMP 轮询。秒级事件用 SNMP 分钟级会漏（见 [11 讲](../04-telemetry/11-gnmi.md)）。

**数据维度不同**。探测数据天然带路径维度；设备计数器是单点维度。要回答「谁堵了、堵住了谁」，必须把设备计数器、拓扑、路径数据做关联分析。

**评分维度**：两点各 1 分。能指出关联分析是新增工作量、管道复用不等于工作完成（给满分）。

:::

## 小结

PFC 的毛病在触发时机。队列快满了才喊停，喊停就是冻结整个优先级队列，副作用全跟着来。ECN 换了思路，队列刚过 Kmin 就在报文上打标记，按概率打，让信号跟着报文走到接收端。

标记到了接收端，还得有人把话传回来。接收端网卡回 CNP，源端网卡据此降速，水位回落再靠定时器慢慢加回来。三个角色分别是交换机、接收端网卡、发送端网卡，缺一个闭环不成立。

分工定下来，指标分级也定了：ECN 标记率看趋势，PFC pause 看告警，丢包看事故。三条连起来读，能看出问题处在哪一层、往哪个方向走。

代价在灵活性上。参数烧在固件和交换机配置里，联动的几组值要配套，管控面从运维便利变成了正确性的一部分。

留一个思考题：Kmin 设得很低，ECN 标记率会很好看、PFC 几乎为零，这时候网络真的更健康吗。
