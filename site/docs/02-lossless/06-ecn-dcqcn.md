ECN 的道理，拿水池讲最快。交换机的一个队列就是个水池：入水口接着所有想出去的报文，出水口按线速往外放。入得比出得快，水位就涨；入得比出得慢，水位自己落回去。

水池上挂着两道机关。XOFF 水线是硬闸，水位一到就把上游进水口关死，这就是 PFC。Kmin 到 Kmax 那一段是软闸，还没到关阀的份上，先拎一块牌子告诉上游「慢点倒」，这就是 ECN。

PFC 是最后一道防线，触发条件很硬：队列涨到 XOFF 高水线。到那一刻队列已经快满，暂停不可避免，副作用也就一起跟着来。

更好的做法是不让它走到那一步。拥塞刚冒头，就让源端把速率降下来，队列永远涨不到 XOFF。这需要交换机侧的显式标记（ECN）和网卡侧的闭环降速（DCQCN）。

## 交付

- ECN 的两位标记与交换机的三段水线（Kmin 到 Kmax）分别怎么处理
- DCQCN 闭环里 CP、NP、RP 三个角色各落在哪台设备上
- PFC 与 ECN 的分工为什么由时间尺度决定，以及健康网络里 PFC 为什么应当罕见
- 三级指标：ECN 标记率领先，PFC pause 滞后，丢包是事故确认
- 与 TCP 拥塞控制的两处差别：信号来源与决策位置

## PFC 的问题在触发时机

拿一组典型配置对照就清楚了。ECN 的 Kmin 一般落在队列容量的一两成，XOFF 水线常放在七八成。中间这段水位，就是 ECN 可以反复打标、源端可以反复降速的空间。PFC 只在最后那一段才动，一动手就是冻结整个优先级队列。

时机晚带来两个后果，一个是代价，一个是信息量。

代价上，PFC 一触发就冻结整个队列，连带队头阻塞与暂停传播，最坏情况是风暴或死锁。ECN 只改两个 bit，交换机开销可以忽略。

信息量上，ECN 标记率是个连续值，能反映拥塞的程度和变化趋势。PFC 计数只有发生和未发生，看不出恶化速度。

所以设计上把两者排成两层：**ECN 加 DCQCN 负责常态，PFC 负责兜底**，只在 ECN 没兜住的时候出手。一个调优良好的集群里，PFC pause 应该是罕见事件。

## ECN：把拥塞写在报文里

ECN 三个字母是 Explicit Congestion Notification，显式拥塞通知。显式这两个字是跟 TCP 比出来的：TCP 靠丢包和时延去推测拥塞，猜的成分很大；ECN 是路径上的设备直接告诉源端「我这儿堵了」，不用猜。

它是 IP 头里的两个 bit，RFC 3168 定义。两个 bit 表示四种状态：

| 标记 | 含义 | 谁置位 |
|---|---|---|
| `00`（Not-ECT） | 本流不支持 ECN | 源端 |
| `01` / `10`（ECT(1) / ECT(0)） | 支持 ECN，可以被打标 | 源端 |
| `11`（CE） | 此处拥塞，请降速 | 交换机 |

流程分三段。

发送端置 ECT。源端网卡给报文写上 ECT，等于告诉沿途设备：这条流支持拥塞通知，堵了直接标，不必丢。

交换机按水线打 CE。每台交换机对每个队列配两个阈值 Kmin 与 Kmax：

| 队列水位 | 交换机动作 |
|---|---|
| 低于 Kmin | 不处理，正常转发 |
| Kmin 到 Kmax 之间 | **按概率**打 CE 标记，水位越高概率越大 |
| 超过 Kmax | 全标 CE，或者交给 PFC 兜底 |

按概率打标是关键。它让标记率随水位连续变化，源端收到的降速信号也就是连续的，不会因为跨过一个阈值就从「不管」跳到「全标」。

回到水池。如果入队速率不超过出队速率，水位永远升不到 Kmin，牌子一直不掉下来，这是健康状态。如果入队速率持续大于出队速率，水位迟早穿过 Kmin，标就开始一个个往外发。水位钉在 Kmax 上不下，说明源端没踩刹车，或者刹车踩得太轻，下一个接手的就只有 XOFF 那道硬闸了。

接收端回 CNP。CE 标记跟着数据报文走到接收端，接收端网卡看到 CE，生成一个 CNP（Congestion Notification Packet）发回源端，告诉它哪条流被标了。

标记为什么不直接由交换机通知源端？因为交换机不知道也不该关心某条 RDMA 流属于哪台源主机。它做的是逐包处理，每次只看到当前这个报文，代价最低。

让接收端把信号折叠成一个 CNP 送回源端，是「谁最清楚谁反馈」的分工：接收端知道是哪个 QP 收到了 CE，交换机不知道。这个设计还有一个副产品，反馈路径与数据路径解耦。CNP 是独立的控制报文，可以单独设优先级和标记，不受数据流的拥塞影响。

## DCQCN：三个角色，一个闭环

ECN 只负责标记，降速动作由 DCQCN（Data Center Quantized Congestion Notification）完成。它的做法是把 TCP 那套拥塞控制搬进网卡硬件，信号来源从丢包换成 CE 标记。

闭环里有三个角色：

| 角色 | 全称 | 落在哪 | 做什么 |
|---|---|---|---|
| **CP** | Congestion Point | 交换机 | 监测队列水位，按概率打 CE 标记 |
| **NP** | Notification Point | 接收端网卡 | 收到 CE 报文，按控制频率回 CNP 给源端 |
| **RP** | Reaction Point | 发送端网卡 | 收到 CNP 按比例降速，一段时间没收到再逐步恢复 |

五个步骤走完一圈：

```text
① 交换机队列涨过 Kmin        → 给过路报文按概率打 CE 标记
② 接收端网卡解到 CE          → 按控制频率回 CNP 给源端
③ 源端网卡收到 CNP           → 按 CNP 密度降低发送速率
④ 队列水位回落，低于 Kmin    → 不再打标，CNP 停止
⑤ 源端一段时间没收到 CNP     → 定时器驱动，逐步把速率加回来
```

第 ⑤ 步的恢复是渐进的，不是一步回到原速。降速要快，恢复要慢，否则立刻又会撞上拥塞。

第 ② 步的频率控制要单独说。如果每个 CE 报文都回一个 CNP，拥塞严重时反馈报文本身就会变成新的负担。实际实现会对 CNP 做限频，比如每 N 个字节或每 N 微秒最多回一个。

## 和 TCP 拥塞控制对照

| 维度 | TCP 拥塞控制 | DCQCN |
|---|---|---|
| 信号 | 丢包（或时延），靠推测 | ECN 标记，显式告知 |
| 决策位置 | 内核协议栈，软件 | 网卡硬件 |
| 反应时间 | 一个 RTT 起，还要经过内核调度 | 微秒级 |
| CPU 占用 | 每条连接都要算 | 网卡完成，主机 CPU 不参与 |
| 兜底 | 重传 | PFC |

两处差别的后果不同。**信号来源从丢包换成标记**，拥塞在造成损失之前就被发现了；**决策位置从内核搬到网卡**，降速可以在微秒级完成，也不占用本就紧张的 CPU 核。

代价是灵活性。TCP 的拥塞控制算法可以换、可以调，改的是软件；DCQCN 的参数烧在网卡固件和交换机配置里，改动要过设备厂商的接口，还要保证全网一致。

## 参数是联动的

这套端网协同有一个隐含前提：交换机和网卡的参数要配套。

Kmin、Kmax 决定什么时候开始标记，PFC 的 XOFF / XON 决定什么时候兜底，CNP 生成频率决定反馈的快慢，降速系数与恢复定时器决定源端的反应曲线。这几组参数联动，**改一个就要重新校核其他几个**。

举个具体的失衡。Kmin 设得过高，队列要涨到很晚才开始标记，信号来不及传导到源端，队列已经撞到 XOFF，PFC 频繁触发。Kmin 设得过低，标记率长期偏高，源端一直在降速，吞吐上不去。

所以「批量、一致地改全网设备参数」不再只是运维便利，它是这套机制能工作的前提。管控面下发（Netconf、gNMI）在这里不是可选项。这一点在 [04 讲](../01-paradigm/04-rocev2.md) 讲过，在 [14 讲](../04-telemetry/14-pipeline.md) 还会再遇到。

## 调参的现实

参数摊开是这么几组：Kmin 与 Kmax、CNP 的生成频率、速率增量的更新周期、降速比例、恢复定时器。论文给过一组默认值，但那是特定规模、特定流量模型下压出来的。厂商设备出厂默认又是另一套，两家厂商的默认值对不上是常事。

现场的调参流程基本长这样：先把 Kmin / Kmax 与 XOFF / XON 对齐，保证标记先动、兜底后动；再压测找降速与恢复的拐点，一次只动一组，动完重跑同一份流量；最后把这组值写进配置管理，别让它在下一次固件升级后悄悄回退。

拄默认值能把实验跑通，跑不通生产。这句在每篇讲调参的地方都成立，本讲只是第一个。

## 经验映射

| 你熟悉的概念 | 在无损网络里的对应 |
|---|---|
| 领先指标与滞后指标 | ECN 标记率领先，PFC pause 滞后，丢包是确认 |
| 阈值告警 | 要改成分级加传导关系分析，单点阈值不够 |
| 实时流处理（Kafka 到 Flink 到时序库） | 完全复用，这些计数器就是普通时序流 |
| 主动探测（自产自收） | 换成设备被动上报（gNMI 订阅），采集模型不同 |
| 路径维度观测 | 设备计数器是单点维度，要与拓扑、路径数据关联 |

指标语义变了，数据管道还是原来那套。ECN 与 PFC 计数器可以当普通时序流处理，采集、存储、查询的链路不用重写。增量工作在两处：采集方式从拉变成推，分析方式从单点阈值变成跨维度关联。这两件事在第四、五篇展开。

## 判读与实操

三级指标的划分依据是时间尺度：

| 层级 | 指标 | 含义 | 处置 |
|---|---|---|---|
| 领先 | **ECN 标记率**（按端口、优先级、队列） | 拥塞正在形成，已被 DCQCN 接管 | 看趋势。持续升高说明流量模型或参数需要调整 |
| 滞后 | **PFC pause 次数与时长** | DCQCN 没兜住，已经进入反压 | 告警，定位到端口、队列、流 |
| 事故 | **无损队列丢包与 discard** | 机制失效：配置错误、死锁、硬件故障 | 最高优先级，立即定位 |

单看任何一个数字都定不了位，价值在传导关系上：

- ECN 涨、PFC 跟着涨、随后丢包，说明拥塞在持续恶化，DCQCN 已经压不住。
- **ECN 不高但 PFC 频繁**，说明参数失衡或者存在微突发，标记还没来得及传导，队列已经撞线。
- **ECN 与 PFC 都不高，却有丢包**，先怀疑某跳配置错误，比如无损队列没开 PFC。

```bash
# 主机侧：ECN 标记与 CNP 相关计数（命名随驱动版本略有差异）
ethtool -S <ifname> | grep -Ei 'ecn|cnp|np_cnp|rp_cnp'

# 交换机侧：每队列的标记与丢弃计数、ECN 阈值配置
show interface <intf> counters queue
show qos queue ecn
```

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：既然 PFC 能保证不丢包，为什么还要 ECN 与 DCQCN？给出三条理由。

::: details 参考答案与评分维度

**代价不对称**。PFC 一触发就冻结整个优先级队列，带来队头阻塞、暂停传播，最坏是风暴与死锁。ECN 只改两个 bit，几乎零成本。

**信号更早**。Kmin 到 Kmax 之间的标记发生在队列远未填满时，源端有充足时间把速率降下来。

**信息量更大**。ECN 标记率是连续值，能反映拥塞程度和恶化速度，做趋势和告警都好用。PFC 计数只有有无，答不出「有多堵」。

还有一条可以补：闭环可控。DCQCN 的降速是概率化、渐进的，能避免吞吐剧烈震荡。

**评分维度**：三条中答对两条（必需）。其中至少一条涉及时机或代价（必需）。提到「ECN 标记率是更好的可观测指标」（加分）。

:::

**必答 Q2**：写出 DCQCN 闭环的五步，并指出三个角色各在哪台设备上。

::: details 参考答案与评分维度

交换机（CP）队列涨过 Kmin，按概率打 CE。接收端网卡（NP）解到 CE，按控制频率回 CNP 给源端。发送端网卡（RP）收到 CNP，按密度降速。队列水位回落，不再打标。源端一段时间没收到 CNP，定时器驱动逐步升速。

**评分维度**

- 五步顺序正确（必需）
- CP、NP、RP 与设备对应正确（必需，最常见的错误是把 NP 说成源端）
- 补出「CNP 有限频，避免反馈风暴」或「恢复是渐进的不硬切」（加分）

:::

**自测 Q3**：三级健康指标分别是什么，各自的行为？为什么单看一个数字定不了位？

::: details 参考答案与评分维度

**ECN 标记率**是领先指标。拥塞正在形成，已被 DCQCN 接管，轻微时属于正常范围。

**PFC pause 次数与时长**是滞后指标。DCQCN 没兜住，已经进入反压，需要告警。

**丢包与无损队列 discard** 是事故确认。机制本身失效，配置错误、死锁、硬件故障，最高优先级。

三者构成一条传导链。单看一个数字只能说明当前处在哪一层，看不出方向和原因。同样一个 PFC 计数，配上高 ECN 说明拥塞恶化，配上低 ECN 说明参数失衡，处置完全不同。

**评分维度**：三层齐全且顺序正确（必需）。说出传导关系的判读价值（必需）。

:::

**自测 Q4**：把 ECN 与 PFC 指标接进已有的数据管道，与接入主动探测数据相比，最大的两个不同是什么？

::: details 参考答案与评分维度

**数据来源不同**。探测数据自产自收；这些计数器是设备被动上报，采集要走 gNMI 订阅或 SNMP 轮询。秒级事件用 SNMP 分钟级会漏（见 [11 讲](../04-telemetry/11-gnmi.md)）。

**数据维度不同**。探测数据天然带路径维度；设备计数器是单点维度。要回答「谁堵了、堵住了谁」，必须把设备计数器、拓扑、路径数据做关联分析。

**评分维度**：两点各 1 分。能指出关联分析是新增工作量、管道复用不等于工作完成（给满分）。

:::

## 小结

PFC 的毛病在触发时机。队列快满了才喊停，喊停就是冻结整个优先级队列，副作用全跟着来。ECN 换了思路，队列刚过 Kmin 就在报文上打标记，按概率打，让信号跟着报文走到接收端。

标记到了接收端，还得有人把话传回来。接收端网卡回 CNP，源端网卡据此降速，水位回落再靠定时器慢慢加回来。三个角色分别是交换机、接收端网卡、发送端网卡，缺一个闭环不成立。

分工定下来，指标分级也定了：ECN 标记率看趋势，PFC pause 看告警，丢包看事故。三条连起来读，能看出问题处在哪一层、往哪个方向走。

代价在灵活性上。参数烧在固件和交换机配置里，联动的几组值要配套，管控面从运维便利变成了正确性的一部分。

::: tip 本课要点

**ECN 提前标记，DCQCN 闭环降速，PFC 只做兜底。**

- 分工的根据是时间尺度：**ECN 在 Kmin 就开始介入，PFC 到 XOFF 才动手**
- ECN 是 IP 头两个 bit：源端置 ECT，交换机在 Kmin 到 Kmax 之间**按概率**打 CE，接收端回 CNP
- DCQCN 三角色：**CP 交换机打标、NP 接收端回 CNP、RP 源端降速与恢复**
- 指标三级：**ECN 标记率（领先）、PFC pause（滞后）、丢包（事故确认）**，看传导关系
- 参数联动：Kmin / Kmax、XOFF / XON、CNP 频率、降速与恢复系数要配套，**管控面是正确性的前提**

:::

留一个思考题：Kmin 设得很低，ECN 标记率会很好看、PFC 几乎为零，这时候网络真的更健康吗。
