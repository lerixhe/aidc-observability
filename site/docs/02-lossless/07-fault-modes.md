前面几讲讲的是机制正常工作时的样子。失效的时候，现场完全不同。

先说一处我自己判断错过的。第一次碰上 PFC 风暴，第一反应是配置：整片区域一起慢、不丢包、端口全 up，看着就像某几跳的 PFC 优先级配错了。于是把那几台的 PFC 开关、XOFF / XON 水线、DSCP 映射逐个比对了一遍，全对。

指路的是 pause 计数。受影响的那几台交换机上，只有一个优先级在涨，而且只朝一个方向涨；顺着这个方向逐跳往上查，源头是一台服务器上读写卡住的应用进程，它不再从接收缓冲里取数据，接收缓冲满了就持续喊停，暂停帧一跳一跳往上游传，最后整片区域陪着它等。

配置清单是必要动作，但它从来不是答案。

从那次起，我把四类故障按「看起来像什么」排了一遍，不再按机制分类。四类故障有一个共同点：它们大多不以丢包的样子出现。丢包率可能是零，端口是 up 的，带宽利用率看着也正常，训练却在变慢。习惯盯的那个指标不参与，告警就不会响。

## 交付

- 四类故障的成因、可观测信号、定位缺口
- 每类故障的指纹，比如「断崖超时加丢包率为零」指向死锁
- 路径级探测与设备遥测各自的能力边界，以及为什么必须叠加
- 真实告警到手时的推进顺序：先判类型，再拉设备侧，再沿拓扑收窄
- 周期性尖刺这类现象怎么与训练任务的节奏对齐

## PFC 风暴：配对了也会发生

这一节最容易写成一张配置检查清单：优先级对齐、水线一致、ACL 不误伤。清单本身没错，但它解释不了一件事：配置全对的时候，风暴照样会来。

某个下游持续喊停。触发原因常见三种，一块故障或劣化的网卡、一个消费不动的应用进程、某一跳设备的 PFC 配置错误。暂停帧沿链路逐跳向上游成片传播，大量链路的实际吞吐同时下跌，特征是丢包率为零、错误计数正常、整片区域一起变慢。

路径级探测能看到路径时延剧烈膨胀、抖动飙升，探测包被 pause 压在自己的出端口。多条路径被覆盖时，劣化呈区域性成片分布，而不是零星几点。看不到的是根因在哪台设备、哪个队列，谁最先喊停，是网卡故障还是配置错误。**受害者和肇事者在探测数据里长得一样**。

要补的是设备侧按优先级的 pause 收发计数与队列深度，秒级采集，沿拓扑做多跳关联，找暂停波的源头。源头有个特征：pause 计数异常上涨，自身入流量却正常。

## PFC 死锁：链路没有断

死锁最反直觉的地方在这里：所有链路都是好的，所有端口都是 up 的，所有报文都还在网络里。多台设备的队列形成环形等待，A 等 B 排空，B 等 C，C 等 A，谁也不放行。结构上和进程死锁一样：环路、持有等待、不可剥夺。触发常与配置或拓扑突变有关，比如路由收敛的瞬间、链路翻转、Fabric 配置不一致。watchdog 没配或者失效时，环路不会自愈。

路径级探测看到的是完全超时，时延曲线从正常直接断崖。这里的「不通」与链路 down 不是一回事：报文全卡在队列里，一个没扔，丢包率可能依然为零。探测答不出「不通」和「链路 down」的区别，也答不出环路涉及哪几台设备、watchdog 是否已经介入。

要补的是 watchdog 事件、stuck 队列状态、端口 up 与 down 记录，结合拓扑做环检测。

## incast 丢包：兜得住，但兜住了也慢

AllReduce 同步突发，上万个源在同一瞬间朝同一个目的地汇聚，出口队列在微秒级涨满。DCQCN 能压住其中一部分，极端 incast 下压不住。

分两种情况。PFC 兜底成功，慢但不丢；PFC 水线没配好或者响应不及时，真的丢包，RDMA 粗粒度重传，这一轮集合通信被严重拖慢。

路径级探测看到的是周期性的时延尖刺或丢包，周期与训练步的节奏吻合，这是 incast 最独特的指纹：规律性周期，指向同一个汇聚点。看不到的是哪个任务、哪一次 AllReduce 造成的，缺少流与任务的关联；汇聚设备在尖刺那一瞬间的队列状态也看不到，因为探测是采样的，不是逐包的。还有「可接受的 ECN 降速」和「已经丢包的事故级 incast」这条界线，得靠设备侧数据划。

要补的是汇聚设备的 ECN 标记率、PFC pause、丢包计数秒级遥测，也就是 06 讲的三级指标。再加流与训练任务、Rank 的关联，把「某端口 incast」翻译成「任务 X 的 Rank 12 所在 rail 拥塞」。

## 队头阻塞：网络里什么都没坏

这句话听起来像在推谢，说穿了就是它的本质：同一优先级队列里，流 A 的目的地堵了，暂停波把同队列去往健康目的地的流 B 一起冻住。

网络里没有任何东西坏了，纯粹是共享队列的设计代价。所以它没有报警器，只有受害者的时延曲线。

路径级探测能看到流 B 的路径时延升高，还能确认 B 的整条路径里只有某一段与 A 重叠。设备级监控做不到这一点，它只有单点视角，证明不了「B 慢是因为 A」。看不到的是肇事流 A 是谁，它可能完全不在探测路径上；队列内多条流的交织关系，要逐流遥测才能看穿。

要补的是设备侧的逐队列时延与水线，加路径级探测交叉定位共享段。要证明「A 堵导致 B 慢」，还得做两者时间上的相关性分析。

## 四类故障的指纹

| 故障 | 探测看得到 | 看不到 | 定位要补 |
|---|---|---|---|
| **PFC 风暴** | 时延膨胀，区域性成片劣化 | 根因设备与队列，肇事者身份 | pause 计数（按优先级）加队列深度，多跳关联找源头 |
| **PFC 死锁** | 断崖式超时，**丢包率为零** | 与链路 down 的区分，环路位置 | watchdog 事件、stuck 队列、端口状态、环检测 |
| **incast** | **周期性**尖刺，与训练步同步 | 哪个任务或哪次 AllReduce 肇事，尖刺瞬间队列状态 | ECN、PFC、丢包三级指标秒级遥测，加流与任务关联 |
| **队头阻塞** | 无辜路径时延升高，路径级能证清白 | 肇事流是谁，队列内多流交织 | 逐队列遥测，加路径交叉定位共享段，加时间相关性分析 |

## 路径级与设备级的分工

四类故障走下来，两种手段的边界很清楚。

主动探测的观测对象是**路径**，强项是秒级发现，外加圈定受影响的路径集合。它答不出在哪台设备、哪个队列、为什么。

设备遥测（gNMI 订阅）的观测对象是**队列**，强项是给出根因所需的精度，代价是只能覆盖到设备维度，不知道这些队列支撑的是哪条路径、哪个训练任务。

所以两者必须叠加，平台的职责是把两个视角拼成一条证据链：探测负责快和广，设备遥测负责准和深。

有一处容易走偏。**探测圈出的是受影响的路径集合，不是根因**。把这个集合与拓扑求交集，候选设备立刻缩小一个数量级，设备侧排查范围从全网收到几条路径经过的那几台，这是探测最实际的贡献。有人拿探测结果直接下结论说「就是这台交换机有问题」，那是把范围当成了根因。

## 经验映射

| 有损 IDC 里的直觉 | 在无损网络里要修正的地方 |
|---|---|
| 丢包率涨了就是出事了 | 最常见的故障丢包率为零，要看时延与 pause |
| 链路不通就去查链路 | 「不通但没丢包」是死锁，这个组合在有损网络里不存在 |
| 告警单点定位根因 | 拥塞上游化，症状现场与根因现场分离，必须多跳关联 |
| 看平均值就够 | 微突发被平均值抹平，要看秒级甚至亚秒级的峰值 |
| 网络问题归网络，任务慢归任务 | 必须做流与任务的关联，否则答不出谁受害、谁肇事 |

## 判读与实操

从告警到根因的四步：

```text
① 判类型    看三个特征：丢包率是否为零、是否周期性、是否区域性成片
② 拉设备侧  该路径经过的每台设备：pause 计数（按优先级）、队列水线、ECN 标记、discard
③ 沿拓扑收窄  找第一个「pause 异常上涨但自身入流量正常」的设备，或第一处 discard
④ 做关联    与训练作业计划对齐：受影响的 Rank 属于哪个任务、哪一段并行策略
```

快速分诊表：

| 观测特征 | 初判 | 下一步 |
|---|---|---|
| 时延膨胀、丢包为零、多路径同时劣化 | PFC 风暴 | 逐跳拉 pause 计数，找源头 |
| 断崖超时、丢包为零、路径集合集中 | PFC 死锁 | 查 watchdog 事件与 stuck 队列，做环检测 |
| 周期性尖刺、与训练步同步、指向同一汇聚点 | incast | 查汇聚设备的 ECN、PFC、丢包三级指标 |
| 部分路径温和升高、其余路径正常 | 队头阻塞 | 找共享段，做时间相关性分析 |

```bash
# 主机侧：按优先级看 pause 与丢弃
ethtool -S <ifname> | grep -Ei 'pause|discard|out_of_buffer'

# 交换机侧（CLI 语义示意）
show priority-flow-control interface <intf> counters
show queue-monitor interface <intf>
```

顺序上有一个容易犯的错：一头扎进设备计数器。几千个计数器摆在那里，没有假设就只能一个个试。**先用「是否丢包加是否周期性」把四类故障分层**，再决定拉哪一类数据。

四类故障的指纹与判读器写成了一个可以跑的 lab：

```bash
cd labs/03-fault-inject
make plan       # 四个场景的注入剧本：在哪台节点、为什么、敲什么
make run        # 计划 + 样本摘要 + 判读结论，不需要 Docker
make classify   # 拿样本喂判读器，看它怎么根据四个特征下结论
```

lab 把上面那张分诊表写成了代码。判定顺序本身就是知识：先判丢包（机制层面的分水岭），再判周期（同步突发还是持续劣化），再判 pause 强度（反压有没有接管），最后才看时延（噪声最大）。

四个场景的 `expected/` 锁着判读结论，阈值一改，哪个场景先翻，diff 里看得见。容器拓扑只能造出等效的观测形态，造不出真实 pause 帧，这条边界在 lab 的 README 第 2 节写清了。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：探测平台报警：某个 POD 内 30 多条路径的时延在同一秒集体劣化五倍，丢包率不变。回答三个问题：最可能是四类故障里的哪个，为什么会调取哪三类设备侧数据，沿拓扑怎么收窄根因范围。

::: details 参考答案与评分维度

**类型**。首选 PFC 风暴，多路径同时劣化、不丢包、区域性成片，三个特征都吻合。次选 PFC 死锁的早期阶段，但死锁通常表现为超时而不是五倍劣化。incast 也能造成多路径劣化，但「同一秒、成片、非周期性」更像风暴。

**三类数据**。按优先级的 PFC pause 收发计数、队列水线与深度、ECN 标记率与 discard。第一类确认反压发生并给出方向，第二类确认是否贴近 XOFF，第三类区分机制在工作还是已经失效。

**收窄**。从受影响路径的汇聚方向逐跳往上游找，定位第一个 pause 计数异常上涨、但自身入流量正常的设备，那就是暂停波源头附近。顺带核对这几跳的 PFC 配置是否一致。

**评分维度**

- 类型判断正确且给出理由（必需）
- 三类数据能对应到「是否反压、反压强度、机制是否失效」（必需）
- 收窄策略是「沿拓扑找第一个异常点」而不是「逐台设备看」（必需）
- 提出先验证配置一致性（加分）

:::

**必答 Q2**：只用手头的数据（探测时延与丢包曲线，加设备计数器），怎么区分 PFC 风暴和周期性 incast？给出两个可操作的区分点。

::: details 参考答案与评分维度

**时间形态**。incast 与训练步同步，周期性重复，尖刺只有毫秒级。风暴是持续性劣化，起点明确，结束要等根因消除，通常不呈现严格周期。

**空间形态**。incast 的劣化指向少数汇聚点，也就是 AllReduce 的接收侧，受影响路径集合随时间稳定。风暴呈区域性成片，会沿拓扑向上游蔓延。

**设备侧佐证**。incast 表现为汇聚设备队列瞬时冲高、ECN 标记率高。风暴表现为源头附近的 pause 计数长时间持续上涨，与队列水线并不同步，因为源头可能是消费不动的端口，而不是拥塞端口。

**相关性**。把尖刺时间点与训练作业日志的 step 时间对齐，对得上的就是 incast。

**评分维度**：两个以上可操作区分点，每个都说清看哪个数据、怎么判（必需）。提出与训练日志做时间对齐（加分）。

:::

**自测 Q3**：「路径完全超时加丢包率为零」指向什么故障？为什么丢包率为零反而是重要线索？

::: details 参考答案与评分维度

指向 PFC 死锁，或者永久性暂停。丢包率为零说明报文没有被丢弃，全部卡在队列里等待。这正是 PFC 不丢包属性带来的反作用：它保证了不扔，也保证了能永久堆积。

如果是链路 down，报文在本地就被丢弃，丢包率会飙升。所以「不通但没丢」是无损网络特有的组合，本身就是诊断特征。

**评分维度**：答出死锁（必需）。解释卡住与丢弃的区别（必需）。指出 watchdog 缺失是长期卡死的条件（加分）。

:::

**自测 Q4**：为什么说路径级覆盖在队头阻塞这类故障里特别有价值？

::: details 参考答案与评分维度

队头阻塞的受害者是无辜路径。设备级均值看不出它劣化，路径级探测却能确认该路径除与肇事流共享的那一段之外，其余各段全部正常，把怀疑范围锁到共享段。

设备级监控只有单点视角，证明不了「B 慢是因为 A」这种跨流因果。路径级数据加上时间相关性，才能把这条链补全。

**评分维度**：说出证明清白、锁定共享段（必需）。说出设备级单点视角的局限（必需）。

:::

## 小结

四类故障里，三类不丢包。

PFC 风暴是持续性的区域停摆，不丢包也没有错误计数，只能靠 pause 计数沿拓扑找源头。PFC 死锁最凶险，指纹是断崖超时加丢包率为零，报文全卡在队列里，得靠 watchdog 事件与环检测。incast 有节奏，与训练步同步，要靠三级指标加流与任务的关联才定位得了。队头阻塞最冤，网络一点没坏，纯是共享队列的设计代价，路径级覆盖反而能替受害流证明清白。

四类的排障顺序是共用的：判类型、拉设备侧、沿拓扑收窄、做关联。结论也共用一条：探测负责快和广，设备遥测负责准和深，平台把两者拼成根因。

::: tip 本课要点

**无损网络的故障，大多不以丢包的样子出现。**

- **PFC 风暴**：不丢包但整片变慢。探测见区域性时延膨胀，定位靠 pause 计数沿拓扑找源头
- **PFC 死锁**：断崖超时加**丢包率为零**是指纹。定位靠 watchdog 事件、stuck 队列、环检测
- **incast**：周期性尖刺，与训练步同步。定位靠 ECN、PFC、丢包三级指标加流与任务关联
- **队头阻塞**：无辜路径受累，**路径级覆盖能证明清白、锁定共享段**
- 分工：**探测负责秒级发现与圈定路径集合，设备遥测负责队列级根因**
- 顺序：先判类型（丢包、周期、空间形态），再拉设备三件套，再沿拓扑收窄，最后做任务关联

:::

留一个思考题：watchdog 配得太激进（一暂停就强制恢复），风暴会变少、丢包会变多。这个取舍怎么向业务方解释。
