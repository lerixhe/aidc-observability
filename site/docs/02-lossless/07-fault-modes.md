前面两讲把 PFC 与 ECN 的机制讲完了，但那只是它们正常工作时长的样子。失效的时候，现场完全是另一副面孔，所以本节我们要对着四类真实故障往里看一层，看看这些机制是怎么一步步把人带偏的。

PFC 名字里那个「流控」是最容易误读的地方，它控的不是流，是队列。名字跟行为对不上的那一处，恰好就是所有故障的起点。

先说一处我自己判断错过的。第一次碰上 PFC 风暴，第一反应是配置：整片区域一起慢、不丢包、端口全 up，看着就像某几跳的 PFC 优先级配错了。于是把那几台的 PFC 开关、XOFF / XON 水线、DSCP 映射逐个比对了一遍，全对。

指路的是 pause 计数。受影响的那几台交换机上，只有一个优先级在涨，而且只朝一个方向涨；顺着这个方向逐跳往上查，源头是一台服务器上读写卡住的应用进程，它不再从接收缓冲里取数据，接收缓冲满了就持续喊停，暂停帧一跳一跳往上游传，最后整片区域陪着它等。配置清单是必要动作，但它从来不是答案。

从那次起，我把四类故障按「看起来像什么」重新排了一遍，不再按机制分类。四类还有一个共同点：它们大多不以丢包的样子出现。丢包率可能是零，端口是 up 的，带宽利用率看着也正常，训练却在变慢，习惯盯的那个指标不参与，告警就不会响。

## 最初的想法不是逐跳

最早做无损的那批人是想让发送端自己减速的。发送端看不见下游队列，但可以等一个信号：丢了包就慢下来，这是 TCP 走了三十年的路。问题在频率控制上，它不能反应太猛，一丢包就把窗口砍半，上千条流同时砍，吞吐立刻塌下去；也不能反应太肉，等它慢到队列不涨，队列早就溢出了。

中间那档调不出来。有人试过用自适应算法压着这个频率，把跌落折算成吞吐的损失，压测跑下来有效吞吐只剩正常水平的六成多，这一点非常致命，因为训练集群买的带宽是用完的，不是省出来的。

所以才有了逐跳反压这一套。它在链路层就动手，水位一过 XOFF 就往上游打一帧暂停，不需要端到端协商，也不用为每种流量适配一套减速策略，交换机就在队列旁边，看见满了就喊一嗓子，简单直接。

不过逐跳也是有代价的，代价就是前面说的传染。队列是共享的，一帧暂停冻住的是整个优先级，这一点在下面还要往深里看。

## 逐跳方案其实也相当复杂

刚才说逐跳方案很简单，为什么这里又说它很复杂呢？因为有一点我们开篇时没有想到，这一点非常可怕，它是队头阻塞的全部来历，那就是同一个队列里的流是共享的。

比如无损队列里同时跑着几条梯度流：

```text
$ show queue ethernet1/1 3 depth
Priority 3   depth 8240 / 9000   xoff 8000      ← 已经过了 XOFF

$ show priority-flow-control interface ethernet1/1 counters
Prio 3   TxPause 4127   RxPause 0                ← 一直在喊上游

$ show flow 10.2.3.4:4001 -> 10.8.1.9:4791 rate
rate 0 Gbps                                      ← 这条流的目的地是健康的，也停了
```

前面几行说的是「队列过了 XOFF，这一跳在一直喊停」，最后一行才是要命的地方：那条流的目的地一直在正常收包，它的路径上没有任何一处拥塞，它还是停了，因为它和最堵的那条流共用一个队列。

为什么共享队列是队头阻塞的巨大障碍呢？因为 PFC 想做的其实是「只让该慢的那条慢下来」，而它手上只有队列这个粒度，一按下去就是全队列。想让 B 少慢一点，只能让 A 和 B 分开排队。

那就给每条流单独开一个队列，行不行？这想法不新鲜，改起来犹如在布满地雷的道路上小心翼翼地行走。一台交换机的一个端口只有八个队列，一个端口上跑着的流有几万条；有的芯片把队列做到了三万多（per-QP 队列那一类设计），代价是每一级缓冲都要按队列数切分，切到每条队列只剩几百字节，几百字节连一个 MTU 都装不下，拥塞还没反应过来队列已经满了。

所以主流做法干脆放弃「按流隔离」，把这种队列共享的代价当成设计前提，用 ECN 提前减速把撞线概率压下去，用 AR 把流量摊开，用逐队列遥测把「谁和谁共享」这件事事后还原出来。这套妥协不好听，但它能落地。

## 风暴是怎么长出来的

暂停帧本身很简单，以太网上它是一帧普通的 MAC 控制帧，靠 opcode 认出来，身上只有三样东西：

```c
struct pause_frame {
    uint16_t opcode;      // 0x8808，认这里才知道是暂停帧
    uint16_t priority;    // 哪几个优先级要停，位图
    uint16_t quanta;      // 停多少个 512 bit time
};
```

我们注意到这个帧只有三个字段，为什么需要三个呢？继续往下看就明白了：

```text
opcode  → 决定这帧给谁处理，交换机把它从数据面摘出来交给流控逻辑
priority→ 决定停哪几个队列，一个端口八个队列可以分开停
quanta  → 决定停多久，到点自己解冻，不需要等第二帧
```

三样组合起来才是完整语义：谁该停、停多久、且这个决定由下游做、只对相邻一跳有效。少一样都不成立，比如只有 priority 没有 quanta，上游就不知道停多久，只能等下一帧撤销，一旦撤销帧丢了就是永久暂停。

一帧暂停到达上游之后，事情散落在三处发生。入口的 MAC 认出 opcode，把这一帧交给流控逻辑；流控逻辑按优先级位图去关对应队列的闸门，闸门关掉之后报文还能收，但调度器不再把它取走发送，这就是「停在自己这里、不丢弃」的实际含义；`quanta` 到点或者收到撤销帧，闸门重新打开。

这三个动作散在入口、队列管理、调度器三处，我把它们凑到一句里便于理解：**暂停不是让报文消失，是让报文排队等一个不再来的时刻。**

风暴就是这条链上出现了「一直不撤销」的一跳。源头往往不是拥塞端口，而是一个消费不动的接收端：网卡收得进，应用不取，接收缓冲满了就往上游喊停，上游队列跟着涨，涨到 XOFF 再往它的上游喊停，一帧接一帧，最后整片区域陪着它。这也解释了为什么它会成片，而且丢包率为零。

路径级探测在这种现场能看到什么？路径时延剧烈膨胀、抖动飙升，探测包被 pause 压在自己的出端口，多条路径被覆盖时劣化呈区域性成片分布。看不到的是根因在哪台设备、哪个队列，谁最先喊停。**受害者和肇事者在探测数据里长得一样**，要补的是设备侧按优先级的 pause 收发计数与队列深度，秒级采集，沿拓扑做多跳关联。源头有个特征：pause 计数异常上涨，自身入流量却正常。

## 环形等待

死锁最反直觉的地方在这里：所有链路都是好的，所有端口都是 up 的，所有报文都还在网络里，一个都没扔。

多台设备的队列形成环形等待，A 等 B 排空，B 等 C，C 等 A，谁也不放行。结构上和进程死锁一模一样，三个条件一个不少：环路存在、持有并等待、不可剥夺。PFC 尤其符合第三条，「不可剥夺」是它的设计目的，报文宁可排着也不许丢。

触发常与配置或拓扑突变有关，比如路由收敛的瞬间、链路翻转、Fabric 配置不一致。watchdog 没配或者失效时，环路不会自愈，因为每一方都在等对方先动。

路径级探测看到的是完全超时，时延曲线从正常直接断崖。这里的「不通」与链路 down 不是一回事：报文全卡在队列里，丢包率可能依然是零。探测答不出「不通」和「链路 down」的区别，也答不出环路涉及哪几台设备。

研究完这环等待关系，我开始有点担心主线程——不是主线程，是担心一个更朴素的事：这种环每天都在形成，只是大多数环比这个短、自己散得开。一条流在两个端口之间来回争抢就能凑成一个小环，两端的队列都退不下去，靠 `quanta` 到点强制解冻才散掉。真正能撑成事故的环，得靠拓扑本身有环路，再叠上配置不一致。

要补的是 watchdog 事件、stuck 队列状态、端口 up 与 down 记录，结合拓扑做环检测。

## 周期性尖刺

AllReduce 每算完一轮就来一次同步突发，上万个源在同一瞬间朝同一个目的地汇聚，出口队列在微秒级涨满。DCQCN 能压住其中一部分，极端 incast 下压不住。

分两种情况。PFC 兜底成功，慢但不丢；PFC 水线没配好或者响应不及时，真的丢包，RDMA 粗粒度重传，这一轮集合通信被严重拖慢。

路径级探测看到的是周期性的时延尖刺或丢包，周期与训练步的节奏吻合，这是 incast 最独特的指纹：规律性周期，指向同一个汇聚点。看不到的是哪个任务、哪一次 AllReduce 造成的，缺少流与任务的关联；汇聚设备在尖刺那一瞬间的队列状态也看不到，因为探测是采样的，不是逐包的。

还有一条界线得划清楚：「可接受的 ECN 降速」和「已经丢包的事故级 incast」不是同一件事，它们只差一点点水线，而这只有设备侧的秒级数据分得出来。要补的是汇聚设备的 ECN 标记率、PFC pause、丢包计数三级遥测，再加流与训练任务、Rank 的关联，把「某端口 incast」翻译成「任务 X 的 Rank 12 所在 rail 拥塞」。

## 判读与实操

从告警到根因四步，一步都不能跳。

```text
① 判类型    看三个特征：丢包率是否为零、是否周期性、是否区域性成片
② 拉设备侧  该路径经过的每台设备：pause 计数（按优先级）、队列水线、ECN 标记、discard
③ 沿拓扑收窄  找第一个「pause 异常上涨但自身入流量正常」的设备，或第一处 discard
④ 做关联    与训练作业计划对齐：受影响的 Rank 属于哪个任务、哪一段并行策略
```

特征怎么映到类型：时延膨胀、丢包为零、多路径同时劣化，初判 PFC 风暴，下一步逐跳拉 pause 计数找源头；断崖超时、丢包为零、路径集合集中，初判 PFC 死锁，下一步查 watchdog 事件与 stuck 队列；周期性尖刺、与训练步同步、指向同一汇聚点，初判 incast，下一步查汇聚设备的三级指标；部分路径温和升高、其余路径正常，初判队头阻塞，下一步找共享段。

```bash
# 主机侧：按优先级看 pause 与丢弃
ethtool -S <ifname> | grep -Ei 'pause|discard|out_of_buffer'

# 交换机侧（CLI 语义示意）
show priority-flow-control interface <intf> counters
show queue-monitor interface <intf>
```

顺序上有一个容易犯的错：一头扎进设备计数器。几千个计数器摆在那里，没有假设就只能一个个试。**先用「是否丢包加是否周期性」把四类故障分层**，再决定拉哪一类数据。

四类故障的指纹与判读器写成了一个可以跑的 lab：

```bash
cd labs/03-fault-inject
make plan       # 四个场景的注入剧本：在哪台节点、为什么、敲什么
make run        # 计划 + 样本摘要 + 判读结论，不需要 Docker
make classify   # 拿样本喂判读器，看它怎么根据四个特征下结论
```

lab 把上面那张分诊表写成了代码。判定顺序本身就是知识：先判丢包（机制层面的分水岭），再判周期（同步突发还是持续劣化），再判 pause 强度（反压有没有接管），最后才看时延（噪声最大）。四个场景的 `expected/` 锁着判读结论，阈值一改，哪个场景先翻，diff 里看得见。容器拓扑只能造出等效的观测形态，造不出真实 pause 帧，这条边界在 lab 的 README 第 2 节写清了。

两种手段的分工也在这儿定下来。主动探测的观测对象是**路径**，强项是秒级发现，外加圈定受影响的路径集合，它答不出在哪台设备、哪个队列、为什么。设备遥测的观测对象是**队列**，强项是给出根因所需的精度，代价是只能覆盖到设备维度，不知道这些队列支撑的是哪条路径、哪个训练任务。有一处容易走偏：**探测圈出的是受影响的路径集合，不是根因**，拿它直接下结论说「就是这台交换机有问题」，那是把范围当成了根因。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：探测平台报警：某个 POD 内 30 多条路径的时延在同一秒集体劣化五倍，丢包率不变。回答三个问题：最可能是四类故障里的哪个，为什么会调取哪三类设备侧数据，沿拓扑怎么收窄根因范围。

::: details 参考答案与评分维度

**类型**。首选 PFC 风暴，多路径同时劣化、不丢包、区域性成片，三个特征都吻合。次选 PFC 死锁的早期阶段，但死锁通常表现为超时而不是五倍劣化。incast 也能造成多路径劣化，但「同一秒、成片、非周期性」更像风暴。

**三类数据**。按优先级的 PFC pause 收发计数、队列水线与深度、ECN 标记率与 discard。第一类确认反压发生并给出方向，第二类确认是否贴近 XOFF，第三类区分机制在工作还是已经失效。

**收窄**。从受影响路径的汇聚方向逐跳往上游找，定位第一个 pause 计数异常上涨、但自身入流量正常的设备，那就是暂停波源头附近。顺带核对这几跳的 PFC 配置是否一致。

**评分维度**

- 类型判断正确且给出理由（必需）
- 三类数据能对应到「是否反压、反压强度、机制是否失效」（必需）
- 收窄策略是「沿拓扑找第一个异常点」而不是「逐台设备看」（必需）
- 提出先验证配置一致性（加分）

:::

**必答 Q2**：只用手头的数据（探测时延与丢包曲线，加设备计数器），怎么区分 PFC 风暴和周期性 incast？给出两个可操作的区分点。

::: details 参考答案与评分维度

**时间形态**。incast 与训练步同步，周期性重复，尖刺只有毫秒级。风暴是持续性劣化，起点明确，结束要等根因消除，通常不呈现严格周期。

**空间形态**。incast 的劣化指向少数汇聚点，也就是 AllReduce 的接收侧，受影响路径集合随时间稳定。风暴呈区域性成片，会沿拓扑向上游蔓延。

**设备侧佐证**。incast 表现为汇聚设备队列瞬时冲高、ECN 标记率高。风暴表现为源头附近的 pause 计数长时间持续上涨，与队列水线并不同步，因为源头可能是消费不动的端口，而不是拥塞端口。

**相关性**。把尖刺时间点与训练作业日志的 step 时间对齐，对得上的就是 incast。

**评分维度**：两个以上可操作区分点，每个都说清看哪个数据、怎么判（必需）。提出与训练日志做时间对齐（加分）。

:::

**自测 Q3**：「路径完全超时加丢包率为零」指向什么故障？为什么丢包率为零反而是重要线索？

::: details 参考答案与评分维度

指向 PFC 死锁，或者永久性暂停。丢包率为零说明报文没有被丢弃，全部卡在队列里等待。这正是 PFC 不丢包属性带来的反作用：它保证了不扔，也保证了能永久堆积。

如果是链路 down，报文在本地就被丢弃，丢包率会飙升。所以「不通但没丢」是无损网络特有的组合，本身就是诊断特征。

**评分维度**：答出死锁（必需）。解释卡住与丢弃的区别（必需）。指出 watchdog 缺失是长期卡死的条件（加分）。

:::

**自测 Q4**：为什么说路径级覆盖在队头阻塞这类故障里特别有价值？

::: details 参考答案与评分维度

队头阻塞的受害者是无辜路径。设备级均值看不出它劣化，路径级探测却能确认该路径除与肇事流共享的那一段之外，其余各段全部正常，把怀疑范围锁到共享段。

设备级监控只有单点视角，证明不了「B 慢是因为 A」这种跨流因果。路径级数据加上时间相关性，才能把这条链补全。

**评分维度**：说出证明清白、锁定共享段（必需）。说出设备级单点视角的局限（必需）。

:::

## 小结

四类故障里，三类不丢包。

PFC 风暴是持续性的区域停摆，不丢包也没有错误计数，只能靠 pause 计数沿拓扑找源头。PFC 死锁最凶险，指纹是断崖超时加丢包率为零，报文全卡在队列里，得靠 watchdog 事件与环检测。incast 有节奏，与训练步同步，要靠三级指标加流与任务的关联才定位得了。队头阻塞最冤，网络一点没坏，纯是共享队列的设计代价，路径级覆盖反而能替受害流证明清白。

这也改写了从 IDC 带过来的几条直觉：丢包率涨了才算出事，这一条不成立；「链路不通就查链路」也不成立，因为在无损网络里「不通且不丢」是有专门含义的组合；还有「看平均值就够」与「网络问题归网络、任务慢归任务」，前者被微突发推翻，后者被拥塞上游化推翻。

四类的排障顺序是共用的：判类型、拉设备侧、沿拓扑收窄、做关联。结论也共用一条：探测负责快和广，设备遥测负责准和深，平台把两者拼成根因。

::: tip 本课要点

**无损网络的故障，大多不以丢包的样子出现。**

- **PFC 风暴**：不丢包但整片变慢。探测见区域性时延膨胀，定位靠 pause 计数沿拓扑找源头
- **PFC 死锁**：断崖超时加**丢包率为零**是指纹。定位靠 watchdog 事件、stuck 队列、环检测
- **incast**：周期性尖刺，与训练步同步。定位靠 ECN、PFC、丢包三级指标加流与任务关联
- **队头阻塞**：无辜路径受累，**路径级覆盖能证明清白、锁定共享段**
- 分工：**探测负责秒级发现与圈定路径集合，设备遥测负责队列级根因**
- 顺序：先判类型（丢包、周期、空间形态），再拉设备三件套，再沿拓扑收窄，最后做任务关联

:::
