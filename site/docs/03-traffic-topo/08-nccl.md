分布式训练按并行策略把模型和切开的输入分到上万张卡上，每一步结束时这些卡必须对齐结果。对齐的方式是集合通信（Collective Communication），实现它的库是 NCCL（NVIDIA Collective Communications Library）。PyTorch 这类训练框架底下的网络流量，绝大部分由它生成。

所以智算网络的流量形态不是自然形成的，它是被算出来的。这一篇讲这个编排过程，以及它对监控意味着什么。

## 交付

- 说清集合通信在训练里的位置，以及为什么每一步都必须同步
- 认出四种常用原语及其典型场景：AllReduce、AllGather、ReduceScatter、All-to-All
- 自己把 Ring AllReduce 的传输量算一遍，理解「带宽最优」这个结论从哪里来
- 解释环序为什么决定哪些链路被打满，以及拓扑感知排序在做什么
- 从任务元数据推出预期流量，把「慢」翻译成「哪条该跑满的链路没跑满」

## 训练每一步都在做集合通信

数据并行下，每张卡手里的模型一样、数据不同。一步算完，各自得到一份局部梯度，只有把全局的梯度汇总起来，下一步才能继续。这个汇总就是 AllReduce。

| 原语 | 干什么 | 典型场景 |
|---|---|---|
| **AllReduce** | 各卡持一份，交换归约后每卡都拿到总和 | 每步梯度同步，流量的绝对大头 |
| **AllGather** | 每卡持一片，交换后每卡拿到完整拼图 | 参数分片训练（ZeRO 类）收集完整参数 |
| **ReduceScatter** | AllReduce 的前半程，归约后每卡只留一片 | 与 AllGather 成对出现 |
| **Broadcast / All-to-All** | 一对全发，全体互发 | 初始化、专家并行（MoE）路由 |

AllReduce 是同步的：所有参与的卡到齐才开始，全部完成才结束。这个约束决定了后面所有事情：一轮里最慢的那条路径决定整轮何时结束，一万张卡一起等它。

sync 的边界就是训练步的边界，于是流量呈现出严格周期性的尖刺，周期等于一步的耗时。

## Ring AllReduce 怎么走

最经典的实现是环（Ring）。N 张卡排成环，数据切成 N 块，每张卡在环上接力：把手里的一块发给下一跳，同时从上一跳收一块。

整个过程转两圈。

**第一圈 ReduceScatter**，目标是让每张卡算出一块完整梯度的部分和。走 N-1 步，每步每卡发一块、收一块、就地累加。结束时每张卡手里有一块已经归约完成的结果。

**第二圈 AllGather**，目标是把这些块轮流传一圈，让每张卡都拿到全部。再走 N-1 步，每步每卡转发一块。

两圈合计 2(N-1) 步，每步每张卡发送的数据量是 S/N（S 是梯度总量）。乘起来：

```text
每卡总发送量 = 2(N-1) × S/N ≈ 2S
```

**每张卡的收发量约等于两倍梯度量，与 N 无关**。这是 Ring 成为主流实现的原因：集群从 8 卡扩到 8000 卡，单卡的网络负担不变。

换成常见的做法，每张卡先把梯度发给同一个中心节点归约，再广播回来，单卡发送量是 2S，中心节点的接收量却是 S×N。中心节点是瓶颈，卡数一多就撑不住。环没有中心节点，负担均匀分摊到每张卡身上。

代价是步数。N 张卡的环要转 2(N-1) 步，延迟正比于环长。所以 NCCL 对大消息用 Ring 榨带宽，对小消息用 Tree 压延迟。Tree 每一步能把参与方减半，步数是 O(log N)，代价是链路利用率不如环均匀。

## 环序决定哪些链路被打满

环是一个逻辑结构，它在物理网络上的走法由软件决定，而走法直接决定了流量分布。

同一时刻，环上只有相邻的卡对在互发数据。这是一条独占的、串行的数据通路：哪些链路参与这个环，哪些链路就会被持续打满；没参与环的链路，一条流量都没有。

于是有一件必须做的事：**让环顺着物理拓扑走**。NCCL 启动时会探测本机的 GPU、网卡、PCIe 与 NVLink 布局，据此决定环的顺序，尽量让相邻的通信方在物理上也相邻。

探测得到的信息包括：哪张 GPU 挂在哪块网卡上、网卡挂在哪个 PCIe switch 与 NUMA 节点下、GPU 之间是 NVLink 还是 PCIe。这些信息决定了环该先走机内还是先出网卡。

这一步做得好不好，直接体现在跨机、跨 spine 的流量占比上。环序排错，流量会绕行，把原本不该打满的上联打满。下一讲讲 rail-optimized 拓扑，做的就是这件事。

## 流量矩阵为什么是已知的

这是这一篇对监控者最重要的一个判断。

传统 IDC 的流量由用户请求驱动，来多少、走哪条路，事先算不出来，监控只能被动接收。

智算集群的大流量由训练框架和 NCCL 主动编排。谁和谁通信，由并行策略决定；通信多大，由模型参数量决定；什么时候通信，由训练步的节奏决定。三样都能从任务元数据里推出来。

推论是监控可以做一件传统 IDC 做不到的事：**比对预期与实际**。

某个 DP 组的 8 个 Rank 应该各自通过自己的 rail 打满端口，实际发现 8 条 rail 里只有 7 条达到预期，第 8 条明显偏低。这条信息不需要等训练侧报错，直接指向那条 rail 的链路或网卡。

要算一笔账的话，一个 7B 参数的模型用 BF16 训练，梯度量约 `7 × 10⁹ × 2 B ≈ 14 GB`。每一步同步，一万张卡参与，这个量级的流量每几百毫秒来一次，这就是网络必须做到 200G、400G 线速的原因，也是一点点低效会被放大成整体变慢的原因。

## NCCL 遇到网络异常时会怎样

三种表现，都需要知道。

**环上一个慢点，全环等它。** 集合通信的同步性把木桶效应落到了环这个具体结构上。一条 rail 劣化，环就卡在那一段，整个任务变慢，而不是只有一部分卡变慢。

**NCCL 会重试、降级、换路。** 遇到异常它可能切换算法（Ring 换 Tree）、切换路径、减少通道数。结果是任务变慢，但训练侧不一定有显式报错。

**调试信息有限。** NCCL 会告诉你在哪个通信步阻塞，不会解释网络原因。所以「NCCL timeout」这类工单最后都会落到网络团队，要求网络侧自证清白或者给出根因。

这三条合起来，就是智算网络 SRE 的日常工作形态：训练侧看到的是慢，网络侧要回答为什么慢。

## 经验映射

| 传统 IDC 的监控假设 | 智算网络里的变化 |
|---|---|
| 流量随机、不可预测 | 流量由软件编排，可以预测 |
| 只能被动观测 | 可以做预期与实际的比对，主动发现异常 |
| 单点指标看健康度 | 需要「任务、环、路径、设备」四层映射 |
| 故障定位靠经验 | 定位可以靠编排关系推导：谁本该和谁通信 |
| 网络慢就是网络问题 | 慢也可能是 straggler 在主机侧，要先区分 |

::: info 经验映射（IDC → AIDC）

做过大规模主动探测编排的人，对这件事不陌生：把探测任务铺到全网、按拓扑分组、自动替换坏点，本质是程序化地编排压力与观测。

智算网络把这件事反过来了。训练任务本身就是一张已知的流量压力图，你不需要自己造压力，只需要知道它该长什么样。

从编排观测，到观测被编排的流量，中间差的只是一份任务元数据。

:::

## 判读与实操

看 NCCL 在做什么：

```bash
# 打开 NCCL 调试日志，含算法选择、环拓扑、通道数
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,COLL,NET
# 日志里会出现 ring 或 tree、通道数、使用的网卡

# 主机侧看 NCCL 建立的连接与对端
ss -u -a | grep 4791

# 看 GPU 与网卡的物理亲和，判断环序能不能顺着拓扑走
nvidia-smi topo -m
```

从任务元数据推预期流量：

| 输入 | 能推出什么 |
|---|---|
| 模型参数量、精度 | 每步梯度量级，即每步同步的数据量 |
| 并行策略（DP / TP / PP / EP） | 通信原语组合与通信域大小 |
| NCCL 算法与环排序 | 预期被打满的 rail 与链路集合 |
| 训练步时间戳 | 预期尖刺出现的时刻 |

判读的落点是一句话：**把「慢」翻译成「哪条预期的流量没有兑现」**。

预期该打满的链路没打满，是链路或网卡的问题；预期之外的链路被打满，说明流量绕行或回退，是环序或拓扑的问题。这两种情况的处置方向完全不同。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：什么是 AllReduce？它为什么决定了智算网络的流量形态？覆盖同步性、周期性、带宽规模三点。

::: details 参考答案与评分维度

AllReduce 是集合通信原语。各卡持一份梯度，交换归约后每张卡都拿到总和。数据并行训练每一步结束都要执行一次。

**同步性**。所有卡到齐才开始，全部完成才结束，最慢的那个决定整体节奏，木桶效应落到环这个结构上。

**周期性**。与训练步严格对齐，形成可预测的尖刺。

**带宽规模**。数据量正比于模型参数量，万卡同步意味着持续的 TB 级流量，是集群网络负载的主体。

**评分维度**：三点齐全（必需）。说出「决定了哪些链路被打满」的拓扑含义（加分）。只背定义不讲同步后果（不通过）。

:::

**必答 Q2**：「流量矩阵是已知的」是什么意思？举一个预期与实际比对的例子。

::: details 参考答案与评分维度

传统业务流量由用户行为驱动，事先算不出应该有多少。智算流量由训练框架与 NCCL 按并行策略编排，从任务元数据能推出应该发生什么：哪些卡组通信、走哪些 rail、多大带宽、什么节奏。

例子：某 DP 组 8 个 Rank 应各自通过自己的 rail 打满 400Gbps 参与 AllReduce。实际监控发现 8 条 rail 里只有 7 条达到预期带宽，第 8 条明显偏低。这个差值本身就指向那条 rail 的链路或网卡，不需要等训练侧报错。

**评分维度**：解释「可从元数据推导预期」（必需）。例子给出可量化的预期差（必需）。指出绕行与回退也能这样识别（加分）。

:::

**自测 Q3**：Ring AllReduce 为什么成为主流？它对网络拓扑有什么隐含要求？

::: details 参考答案与评分维度

每卡收发量约为 2 倍梯度量，**不随卡数增长**，所以带宽最优、扩展性好。

隐含要求是环经过的每一段链路都要能持续吃满线速，且环序要与物理拓扑对齐。环序错位会让流量跨机群绕行、争夺共享上联，效率急剧下降。这就是 NCCL 要做拓扑感知排序、集群要做 rail-optimized 拓扑的原因。

**评分维度**：说出带宽最优及其算法来源（必需）。说出环序要与物理拓扑对齐（必需）。能给出「2S 不随 N 变」的算式（加分）。

:::

**自测 Q4**：「NCCL timeout」工单落到网络团队，手上有路径级探测与设备遥测，按什么顺序排查最快？

::: details 参考答案与评分维度

**先做时间对齐**。超时时刻有没有同刻的探测或遥测异常。没有异常，可以较快排除网络侧突发故障，把方向转回主机或框架。

**再看任务相关路径**。从任务元数据确定该任务的 rail 与环覆盖哪些链路，逐段核对设备计数：丢包、ECN、PFC、CRC、光模块误码。

**再看历史形态**。是周期性劣化（慢性拥塞）还是突发（故障、配置变更）。

**最后输出到任务语境**。给受影响 rail、路径集合与根因类型，而不是一堆端口号。

**评分维度**：顺序合理，先自证再定位（必需）。能把网络数据翻译成任务语言（必需）。提到与变更记录对齐（加分）。

:::

## 小结

集合通信是训练每一步的对齐动作，AllReduce 是其中的流量大头。四种原语分工明确，AllReduce 加 ReduceScatter 加 AllGather 覆盖了数据并行与参数分片两条主线。

Ring 能成为主流，靠的是一笔好账：数据切 N 块，两圈共 2(N-1) 步，每卡收发约 2S，与卡数无关。代价是延迟正比于环长，所以小消息改用 Tree。

环在物理网络上怎么走由软件决定，走法决定流量分布。NCCL 探测本机 GPU 与网卡的物理布局来排环，排得好，跨机流量就少。这件事的工程化外壳，就是 rail-optimized 拓扑。

对监控者来说，关键判断是流量矩阵已知。既然能算出预期，就能做预期与实际的比对，把「慢」翻译成「哪条该跑满的链路没跑满」。

::: tip 本课要点

**智算网络的流量由软件编排，所以它可预测。**

- 集合通信是每步的对齐动作，实现是 NCCL。流量大头是 **AllReduce**，另有 AllGather、ReduceScatter、All-to-All
- Ring AllReduce 的账：数据切 N 块，**2(N-1) 步，每卡收发约 2S，与卡数无关**。大消息走 Ring 榨带宽，小消息走 Tree 压延迟
- 环序决定哪些链路被打满。NCCL 做**拓扑感知排序**，集群做 rail-optimized 拓扑，都是为这件事服务
- 流量矩阵**已知**，所以能做「预期 vs 实际」比对。该跑满的没跑满、不该跑满的跑满了，两种情况指向不同问题
- NCCL 遇异常会降级、换路，表现为**慢而无报错**，所以这类工单最后都落到网络侧

:::

留一个思考题：如果训练框架把 AllReduce 改成异步、允许各 Rank 落后一到两步，网络侧的排障难度是变大还是变小。
