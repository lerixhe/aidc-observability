前面几讲把无损网络怎么把丢包挡在发生之前讲完了，但是一直没有提到**训练通信本身是个什么形状**，它并不是一堆点对点的流，而是一组集合操作。

分布式训练把模型切开、分到上万张卡上，每张卡算其中一部分，一步算完，各部分的结果必须合到一起才能算下一步。把结果合起来这个动作叫集合通信（Collective Communication），干这件事的库是 NCCL（NVIDIA Collective Communications Library），PyTorch 这类框架底下的网络流量，绝大部分由它生成。

## 集合通信

集合通信允许一次调用就把全体参与方卷进来，库负责把一次逻辑上的交换拆成多条点对点收发，每条怎么走、什么时候走，都由库自己编。

它是分布式训练的一种解耦方式，把「数据怎么传」从「模型怎么算」里拆出来。有了它，并行策略只负责说清楚「谁跟谁要合一次」，剩下的路径与顺序交给 NCCL。如果是普通的点对点消息，N 张卡两两互相发一次，就得写 N² 条流，谁先谁后还得自己排。

最常见的切法是数据并行，每张卡一份完整模型、一份不同的数据，一步跑完，手上是一份局部梯度，只有把上万份梯度加起来得到全局梯度，下一步才有意义，这个求和叫 AllReduce。除了它，还有三个常客：AllGather 是每卡持一片、交换之后每卡都拿到完整的一份，参数分片训练用它收集完整参数；ReduceScatter 是 AllReduce 的前半程，归约之后每卡只留一片，跟 AllGather 成对出现；Broadcast 和 All-to-All 分别管一对多与全体互发，初始化与专家并行（MoE）的路由用它。

几种并行叠在一起，流量就是这几个原语的组合，走哪些链路也跟着定了。

## AllReduce

为了支持集合语义，NCCL 不能只靠 socket 发消息了，它单独做了一套传输与算法，名字叫 Ring、Tree、CollNet 这一串。我们先用一个现成的压测工具演示一下 AllReduce 跑起来是什么样。

```bash
$ ./build/all_reduce_perf -b 8 -e 8G -f 2 -g 8
```

这张表里 `algbw` 和 `busbw` 两个带宽常常让人看不明白：明明只有一条 AllReduce，怎么有两个带宽，而且差着将近一倍？

`algbw` 是「逻辑带宽」，拿数据量除以耗时，算的是「这么大的梯度多久同步完」；`busbw` 是「总线带宽」，按 Ring 的实际收发量折算，N 张卡每卡要发出去 2(N-1)/N 份数据，八卡就是 1.75 倍。NCCL 拿 busbw 跟网卡线速比，是看这套环有没有跑满；拿 algbw 跟训练步耗时比，是看任务还要等多久。两个数各有各的用处，拿错了就判错。

上面这个过程里，`warmup iters: 5` 的那五次不计入统计，因为建链、注册内存、算环序都要时间。**在生产环境中，我们很少只看一次 AllReduce 的结果**，训练每算完一步就来一次，一秒里能跑好几轮，所以真正要看的是稳定态的 busbw 和它的抖动，而不是第一轮跑出来的那个数。

还有一点值得单独说：压测里的 AllReduce 用的是一个干净的、没有别的流量抢带宽的通信域，生产里一个 GPU 上往往同时挂着数据并行的 AllReduce 和张量并行的 All-to-All，两条流量抢同一块网卡。所以下面的读者不要拿压测数字直接当生产预期。

## 环怎么转

最经典的实现是环（Ring）。N 张卡排成一个环，梯度切成 N 块，每张卡在环上接力：手里的一块发给下一跳，同时从上一跳收一块，收到就地累加。

整个过程转两圈。第一圈 ReduceScatter，目标是让每张卡算出一块完整的部分和，走 N-1 步，每步每卡发一块、收一块、累加一次；第二圈 AllGather，把这些块再轮流传一圈，让每张卡凑齐全部，还是 N-1 步，每步每卡转发一块。

两圈合计 2(N-1) 步，每步每卡发出去的数据量是 S/N，S 是梯度总量，乘起来：

```text
每卡总发送量 = 2(N-1) × S/N ≈ 2S
```

每张卡的收发量**约等于两倍梯度量，跟卡数无关**，8 卡是这样，8000 卡也是这样，加卡不加单卡的网卡负担，这是 Ring 成为主流实现的原因。

代价在步数。N 张卡的环要转 2(N-1) 步，延迟正比于环长，卡越多圈越大。所以 NCCL 的选法是**大消息走 Ring 榨带宽，小消息走 Tree 压延迟**，Tree 每一步把参与方减半，步数是 log N，代价是各条链路上的流量不如环均匀。Tree 的默认切换阈值在几百 KB 量级，这个值可以在环境变量里调。

一句话概括这两个算法：**Ring 省带宽、费时间；Tree 省时间、费带宽。**

## 环序由软件定

上面提到的环，成员顺序由 NCCL 在启动时排定，不是物理连线的形状。

环是逻辑结构，它在物理网络上怎么走全看这个顺序：同一时刻只有环上相邻的卡在互发数据，这是一条串行的通路，哪些链路进了这个环，哪些就被持续打满，没进环的链路一条流量都没有。

所以环的排布要顺着物理拓扑走。NCCL 启动时探测本机的 GPU、网卡、PCIe 与 NVLink 布局，据此排定环里成员的顺序，尽量让相邻的通信方在物理上也相邻。探测的内容包括哪张 GPU 挂在哪块网卡上、网卡挂在哪个 PCIe switch 与 NUMA 节点下、GPU 之间走 NVLink 还是 PCIe，这几样决定了环先走机内还是先出网卡。

如果现在要给集群加一批新机器，环序要不要跟着调整？正常情况下不用，NCCL 每次启动都重新探测一遍，新成员自动按拓扑入环。需要人工干预的是另一种情况：探测不准，或者你想强制某几条 rail 优先，那就得用拓扑文件把关系写死。

排得好不好，直接体现在跨机、跨 spine 的流量占比上。排错了，流量绕行，本来不该打满的上联被打满。下一讲的 rail-optimized 拓扑，做的是给这件事提供物理基础。

## 一条日志的字段

把 `NCCL_DEBUG=INFO` 打开，日志里会出现这样的行：

```text
NCCL INFO Channel 00/04 :    0   1   2   3
NCCL INFO Channel 01/04 :    3   2   1   0
NCCL INFO Ring 00 : 0[0] -> 1[0] via P2P/IPC
NCCL INFO Ring 00 : 7[0] -> 0[0] via NET/IB/0/RoCE
```

那这几个字段是什么含义呢？

**Channel**。它表示并行的通道数，`00/04` 是说一共四条通道、这是第 0 条。多条通道是为了把梯度切成更多块并行转，能把启动与结束的等待摊薄。注意第一条正向、第二条反向，这是 NCCL 的惯用排法，两个方向各排一遍，负载更均衡。

**环的成员序列**。`0 1 2 3` 就是这个环里 GPU 的编号顺序，也是数据传递的顺序，谁在谁后面一目了然。

**transport**。`P2P/IPC` 是机内，走 NVLink 或者 PCIe 共享内存；`NET/IB/0/RoCE` 是出网卡，`0` 是第几块网卡的资源，`RoCE` 说明走的是以太网上的 RDMA 而不是原生 IB。一个环里同时出现这两种，说明它是跨机环：机内几跳靠 NVLink，跨机那一段出网卡。

**方括号里那个 0**。它是 GPU 索引。多卡机器上一个环里同一个 GPU 可能被重复用到，看这个编号才能对上具体是哪张卡。

## 不足

前面把 Ring 的好处说完了，不足还没提。不足就在下面四条，一条比一条难受。

**一、同步屏障**。AllReduce 是同步的，参与的卡到齐才开始，全部完成才结束。集合通信把木桶效应落到了环这个具体结构上，一条 rail 劣化，环就卡在那一段，整个任务变慢，而不是只有一部分卡变慢。

**二、单环串行**。一个 Ring 组里，同一时刻只有相邻的两个成员在传。环上任一段链路打折，整圈的节奏跟着打折，没有第二条路可绕。

**三、降级不报错**。NCCL 遇到异常会换算法（Ring 换 Tree）、换路径、减少通道数。结果是任务变慢，训练侧不一定有显式报错。

**四、日志不解释网络**。NCCL 能告诉你在哪个通信步阻塞，说不出为什么。所以「NCCL timeout」这类工单最后都会落到网络团队，要网络侧自证清白或者给出根因。

正因为这四条，集合通信的问题从来不是「看 NCCL 日志」能解决的。日志负责告诉你时间点和通信域，网络负责告诉你那几条路径上到底发生了什么，两边对得上才叫定位。

## 流量矩阵是已知的

传统 IDC 的流量由用户请求驱动，来多少、走哪条路，事先算不出来，监控只能被动接收；智算集群的大流量由训练框架和 NCCL 编排，谁和谁通信由并行策略定，通信量多大由模型参数量定，什么时候通信由训练步的节奏定，三样都能从任务元数据里推出来。

既然能算出预期，监控就多了一件传统 IDC 做不到的事：**比对预期与实际**。

先算量。一个 7B 参数的模型用 BF16 训练，梯度量约 `7 × 10⁹ × 2 B ≈ 14 GB`。每一步同步一次，一万张卡参与，这个量级的流量每几百毫秒来一次。网络必须做到 200G、400G 线速，原因就在这里。

再看一个具体的判读。某个 DP 组的 8 个 Rank 应该各自通过自己的 rail 打满端口，实际发现 8 条 rail 里只有 7 条达到预期，第 8 条明显偏低。这条结论**不需要等训练侧报错**，直接指向那条 rail 的链路或网卡。

从任务元数据推预期流量，输入是这几样：模型参数量与精度，决定每步梯度量级；并行策略（DP / TP / PP / EP），决定通信原语的组合与通信域大小；NCCL 的算法与环排序，决定预期被打满的 rail 与链路集合；训练步的时间戳，决定预期尖峰出现的时刻。

**预期该打满的链路没打满，先查链路和网卡**；预期之外的链路被打满，说明流量绕行或者回退了，去查环序和拓扑。两种情况的处置方向完全不同。

看 NCCL 在做什么，三条命令够用：

```bash
# 打开 NCCL 调试日志，里面有算法选择、环拓扑、通道数
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,COLL,NET

# 主机侧看 NCCL 建立的连接与对端
ss -u -a | grep 4791

# GPU 与网卡的物理亲和，判断环序能不能顺着拓扑走
nvidia-smi topo -m
```

日志里会出现选了 ring 还是 tree、用了几个通道、走的哪块网卡，三样东西对上了，预期与实际的比对才有依据。

## 补充

近期这一层在动，NCCL 之外出现了另外几条路：SHARP 把归约搬到交换机里做，数据不用绕到端主机再回来；NVLink 域内的 SHARP（NVLS）把归约放到超节点的交换芯片上；还有以内存语义直连的集合通信实现。这些路共同的效果是让「环」不再是唯一答案，尤其是小消息与中等消息。

从此 Ring 不必是唯一答案了，但也别急着把它当成旧技术，跨机、大消息、异构拓扑，它还是最稳的那一条。具体内容请读者阅读第 10 讲超节点那一章。

**必答 Q1**：什么是 AllReduce？它为什么决定了智算网络的流量形态？覆盖同步性、周期性、带宽规模三点。

::: details 参考答案与评分维度

AllReduce 是集合通信原语。各卡持一份梯度，交换归约后每张卡都拿到总和。数据并行训练每一步结束都要执行一次。

**同步性**。所有卡到齐才开始，全部完成才结束，最慢的那个决定整体节奏，木桶效应落到环这个结构上。

**周期性**。与训练步严格对齐，形成可预测的尖峰。

**带宽规模**。数据量正比于模型参数量，万卡同步意味着持续的 TB 级流量，是集群网络负载的主体。

**评分维度**：三点齐全（必需）。说出「决定了哪些链路被打满」的拓扑含义（加分）。只背定义不讲同步后果（不通过）。

:::

**必答 Q2**：「流量矩阵是已知的」是什么意思？举一个预期与实际比对的例子。

::: details 参考答案与评分维度

传统业务流量由用户行为驱动，事先算不出应该有多少。智算流量由训练框架与 NCCL 按并行策略编排，从任务元数据能推出应该发生什么：哪些卡组通信、走哪些 rail、多大带宽、什么节奏。

例子：某 DP 组 8 个 Rank 应各自通过自己的 rail 打满 400Gbps 参与 AllReduce。实际监控发现 8 条 rail 里只有 7 条达到预期带宽，第 8 条明显偏低。这个差值本身就指向那条 rail 的链路或网卡，不需要等训练侧报错。

**评分维度**：解释「可从元数据推导预期」（必需）。例子给出可量化的预期差（必需）。指出绕行与回退也能这样识别（加分）。

:::

**自测 Q3**：Ring AllReduce 为什么成为主流？它对网络拓扑有什么隐含要求？

::: details 参考答案与评分维度

每卡收发量约为 2 倍梯度量，**不随卡数增长**，所以带宽最优、扩展性好。

隐含要求是环经过的每一段链路都要能持续吃满线速，且环序要与物理拓扑对齐。环序错位会让流量跨机群绕行、争夺共享上联，效率急剧下降。这就是 NCCL 要做拓扑感知排序、集群要做 rail-optimized 拓扑的原因。

**评分维度**：说出带宽最优及其算法来源（必需）。说出环序要与物理拓扑对齐（必需）。能给出「2S 不随 N 变」的算式（加分）。

:::

**自测 Q4**：「NCCL timeout」工单落到网络团队，手上有路径级探测与设备遥测，按什么顺序排查最快？

::: details 参考答案与评分维度

**先做时间对齐**。超时时刻有没有同刻的探测或遥测异常。没有异常，可以较快排除网络侧突发故障，把方向转回主机或框架。

**再看任务相关路径**。从任务元数据确定该任务的 rail 与环覆盖哪些链路，逐段核对设备计数：丢包、ECN、PFC、CRC、光模块误码。

**再看历史形态**。是周期性劣化（慢性拥塞）还是突发（故障、配置变更）。

**最后输出到任务语境**。给受影响 rail、路径集合与根因类型，而不是一堆端口号。

**评分维度**：顺序合理，先自证再定位（必需）。能把网络数据翻译成任务语言（必需）。提到与变更记录对齐（加分）。

:::

## 小结

集合通信是训练每一步的对齐动作。AllReduce 是其中流量的大头，AllGather 与 ReduceScatter 覆盖参数分片这条线，All-to-All 覆盖专家并行。

Ring 的算式没几行：数据切 N 块，两圈 2(N-1) 步，每卡收发约 2S，与卡数无关。延迟正比于环长，所以小消息走 Tree。

环在物理网络上怎么走由软件定，走法决定流量分布。NCCL 探测本机的 GPU 与网卡布局来排环，排得好，跨机流量就少。这件事的工程外壳，就是 rail-optimized 拓扑。

对监控来说，最要紧的一条是流量矩阵已知。既然能算出预期，就能做预期与实际的比对，把「慢」定位到某条该跑满却没跑满的链路。

这一讲把流量说清楚了：谁和谁通信、多大、什么时候，都能推。能推，监控就多了一件礼物。但可推不能直接换算成停机时间，一条劣化的 rail 究竟多吃掉多少训练进度，要等第 19 讲讲 MTTR 拆解时才算得清，那一讲会把今天的流量矩阵接到时间账上。

::: tip 本课要点

**智算网络的流量由软件编排，所以它可预测。**

- 集合通信是每步的对齐动作，实现是 NCCL。流量大头是 AllReduce，另有 AllGather、ReduceScatter、All-to-All
- Ring AllReduce 的算式：数据切 N 块，2(N-1) 步，每卡收发约 2S，与卡数无关。大消息走 Ring 榨带宽，小消息走 Tree 压延迟
- 环序决定哪些链路被打满。NCCL 做拓扑感知排序，集群做 rail-optimized 拓扑，为的是同一件事
- 流量矩阵已知，所以能做「预期 vs 实际」比对。该跑满的没跑满、不该跑满的跑满了，两种情况指向不同问题
- NCCL 遇异常会降级、换路，表现为慢而无报错，这类工单最后都落到网络侧

:::
