万卡集群的骨架是 Clos 架构，以太网语境里常叫 Fat-Tree，两层或三层交换机，Leaf 全部上联到 Spine，上联总带宽等于下联总带宽，**1:1 无收拢**。这个形状给出一个承诺：任意两组服务器互访都能吃满线速，也就是**全等分带宽**（full bisection bandwidth）。

```text
        +---------+   +---------+   +---------+   +---------+
        | Spine A |   | Spine B   |   | Spine C |   | Spine D |
        +----+----+   +----+----+   +----+----+   +----+----+
             |             |             |             |
      +------+------+------+------+------+------+------+------+
      |             |             |             |             |
  +---+---+     +---+---+     +---+---+     +---+---+     +---+---+
  | Leaf1 |     | Leaf2 |     | Leaf3 |     | Leaf4 |     | Leaf5 |
  +---+---+     +---+---+     +---+---+     +---+---+     +---+---+
      |             |             |             |             |
   GPU 组1       GPU 组2       GPU 组3       GPU 组4       GPU 组5
```

传统 IDC 的流量以小流为主，几毫秒就排空，3:1 或 4:1 的收拢比是常见的省钱手段，因为同时打满所有上联的概率不高。训练集群不吃这一套：AllReduce 是持续的大象流，一打就是一整个训练周期，任何收拢比都意味着跨组通信排队，而集合通信是同步的，排一次队就是全员等一次。所以 1:1 无收拢在训练集群里是必需项，代价是交换机与光模块数量巨大，布线复杂，成本和运维复杂度随规模线性上升。

Rail-optimized 是 Clos 的一个变种，它是为集合通信量身改过的那一版，改的地方不多，但每一处都贴着 NCCL 的通信规律。

## 一台 GPU 服务器有八条轨道

传统业务服务器一两块网卡就够。GPU 服务器不一样：8 张 GPU 通常各配一块独立网卡（200G 或 400G），每块网卡属于一条 **Rail（轨道）**。

```text
Rail 0 交换机组  --  所有服务器的 网卡0  --  GPU0
Rail 1 交换机组  --  所有服务器的 网卡1  --  GPU1
Rail 2 交换机组  --  所有服务器的 网卡2  --  GPU2
...                                          共 8 条轨道
```

八条轨道说得再白一点：像八条平行车道，每条车道在每栋楼门口都有一站。货从甲楼 3 号门送到乙楼 3 号门，全程走 3 号车道，一趟不用上主干道；换成从甲楼 3 号门送到乙楼 5 号门，就得上主干道横穿一次。

Rail N 指的是所有服务器第 N 块网卡所连的那组接入交换机，同号的卡走同一条道。流量于是分成两种形态：

```text
轨道对齐（rail-aligned）：A.GPU0 到 B.GPU0，全程在 Rail 0 内，不经过 Spine
轨道交叉（rail-crossing）：A.GPU0 到 B.GPU5，必须跨轨道，占用共享上联
```

NCCL 做拓扑感知排序时，会尽量把环排成同 rail 序列，让集合通信的相邻通信方落在同一条轨道里。**轨道对齐的比例越高，跨 spine 的流量越少**，拥塞面也越小。这个比例不是布线时顺带形成的，它是设计目标。

## 轨道定位算法

每张卡属于哪条轨道，是可以算出来的，不需要查表：

```py
def RAIL_SLOT(gpu_index, rails):
    return gpu_index % rails      # 8 卡 8 轨，卡 3 就是 Rail 3

def RAIL_SLOT_FORCED(gpu_index, rails, topo):
    # 拓扑文件里写了强制归属，就按文件来，跳线改了也不认默认算法
    forced = topo.get(gpu_index)
    return forced if forced is not None else gpu_index % rails
```

默认算法是取模，八卡八轨就是一一对应。之所以要留一个强制入口，是因为布线不是永远理想：某台机器的 5 号网卡跳到了 3 号轨的 leaf 上，默认算法就会算错，这时候得用拓扑文件把关系写死，让 NCCL 按真实布线排环。

取模这个规则有个副作用，值得提前知道：**卡号与网卡号的对应关系一旦定了，就改不动了**。换一块网卡、调一次 PCIe 槽位，卡号跟着变，轨道归属跟着变，环序也跟着变。所以 GPU 服务器上那块板的插卡顺序是设计的一部分，不是装配工人可以自由发挥的地方。

## 改道

流量在等价路径之间不均匀，是这一层最常见的事，改道有三种，性质完全不同。

第一种是**重哈希**。ECMP 每来一条新流就重新算一次哈希，落点由五元组决定。它看起来像改道，其实只是随机，两条大象流撞在同一条上联上，谁也没改道，只是运气差。这种「改」不会自己好，也不会自己变坏。

第二种是**自适应路由的偏转**。交换芯片看出口队列，把某个包临时挪到另一条等价路上。这是临时的，下一个包可能就回去了，控制器不刷新任何表项。它对应的是「临时纠正」：这一下避开了拥塞，但路由表的答案没变。

第三种是**双 ToR 切换**。一台接入交换机故障或者要升级，流量整体切到另一台，路由表真的变了，收敛之后新路径成为常态。这种切换要通知所有相关方，**表项需要刷新**。

三种改道在监控上的指纹完全不同：重哈希看不出事件，只有结果不均；AR 偏转会让 `rx_out_of_order` 涨，而路由表不动；双 ToR 切换会让路径集合整体变化一次，LLDP 邻居和 BGP 邻居同时抖一下。把三者当成一回事，就会出现「明明切过去了，流量怎么还走老路」这种争论。

## 变更

把一台机器的轨道从 Rail 3 挪到 Rail 5，或者把一整个平面下的链路整批换掉，是这一层最重的动作，它的单位是「一台机器、一组链路」，不是「一个端口」。

一次变更大致分三步：先给目标机器加上新归属的上联，让它同时挂在两条道上；再验证新路径能不能通、跑不跑得满；最后拆掉老上联。

中间那个「双上联」的阶段是最危险的，也是最容易被忽略的：这台机器此刻有两个身份，NCCL 在两个身份之间可能排出两个不同的环，训练侧看到的是带宽忽高忽低。所以变更要么在任务开始前做完，要么就承认它会影响正在跑的任务。

还有一处要注意：**一次只动一台**。整批机器同时双上联，等于让几百条环同时重排，NCCL 每次重排都要重新建链、重新探测，这个开销在万卡规模上不小。分批做，每批之间留出观察窗口，比一次做完要慢，但出问题时能收得回来。

## 容错

一条链路抖一下就是全体停摆，这个前提在第三讲已经立好，接入层于是做了三层冗余。

**双 ToR** 防的是单台接入交换机故障或者升级维护，流量切到另一台，训练不中断。**双平面**防的是整个交换平面故障，损失部分带宽，集群降速运行，训练继续推进。**计算、存储、带外三张网物理隔离**，各自独立，checkpoint 的流量和管理面的流量不会打到训练上。

三种设计对应三种故障粒度，故障后的状态也不一样：双 ToR 切换之后集群基本全速，双平面掉一个之后集群在降速运行，两者的告警级别和处置动作不是一回事。

降速而不回退，差在量级上：一次 checkpoint 回退的代价是回退时长乘以万卡算力，从几分钟到几十分钟；同期降速运行损失的只是利用率，通常在一两成，两者差一个数量级。工程上宁可牺牲带宽，也不触发回退。

代价是冗余度下降。双平面掉一个平面之后只剩单平面，再有一处故障就没有备份，这类「已降级」状态必须被监控显式记录下来，否则第二次故障会打得措手不及。

## 三级状态

「坏了」这个词在拓扑监控里太粗。按可恢复的程度排，现场其实分三级。

第一级是**端口 down**：链路丢、光模块灭、`Link detected: no`。后果是双 ToR 切换或降速，处置是立即告警、走硬件更换。

第二级是**链路劣化**：CRC 与 FEC 纠正计数上涨、误码增加，端口还是 up。后果是还在跑，但重传与乱序变多，处置是巡检发现、排期更换。

第三级是**队列打满**：pause 持续上涨、ECN 标记率升高、水线贴顶。后果是不丢包也在变慢，处置是查流量与参数，不换硬件。

把第二级当成第一级，会提前换掉一批还能用的模块；把第三级当成第二级，会在光模块上白白花一周。经验上讲，**第一级自己会报警，第二级靠巡检，第三级靠趋势**。

## 确定下线

Clos 是去中心化的，一张 leaf 认为某台机器不可达，并不代表所有观测点都这么认为，所以一条 rail 是不是真的下线，得经过一次协商。

三个观测点各自有话说：链路层的 LLDP 邻居消失，说明对端接口没了；路由层的 BGP 邻居 down，说明三层也不可达；探测侧的路径时延断崖，说明数据面不通。三个信号同时出现，可以判定这条 rail 断；只有探测时延高了、而 LLDP 与 BGP 都好好的，那就是劣化而不是断，判据完全不同。

这套协商比人工「看一眼告警就下结论」慢，但误判率低得多。就像集群里一个节点说「他掉线了」不算数，要大多数节点都认了才算——网络这边也一样，单一观测点不足以宣判。

这话得配一个诚实的补充：**误判不可避免**。探测报某条 rail 时延升高，可能真的是链路，也可能是某个 Rank 在写 checkpoint、CPU 卡住、或者宿主机上另一个任务抢了带宽。先承认误报，再谈缓解：把探测时延与主机侧 CPU、磁盘、任务日志摆在一起对齐，对不上的先存疑。把误判率当成已知成本写进值班手册，比声称「我们的探测很准」有用得多。

## 摸拓扑

三组命令，能把一张网的形状摸出来：

```bash
# 主机侧：GPU 与网卡的物理亲和，判断某张卡走哪块网卡、哪条轨道
nvidia-smi topo -m

# 主机侧：网卡的 PCIe 位置与链路速率，核对是否按设计上联
lspci -tv | grep -i eth
ethtool <ifname> | grep -E 'Speed|Link detected'

# 网络侧：拓扑自动发现的两种来源
show lldp neighbors
show ip bgp summary
```

摸清之后按 rail 维度组织观测：每条 rail 的链路利用率分布看是否均匀，某条显著偏低或偏高都不正常；每条 rail 的 pause、ECN、discard 定位到哪条轨道在反压；跨轨道（经 spine）流量占比应尽量低，升高说明环序与拓扑错位；双 ToR 主备流量是否按设计分流，切换后有没有恢复；平面之间的流量对称不不对称，不对称是单平面劣化的早期信号。

同一个故障在 rail 维度上**通常成组出现**。某条 rail 的多条路径同时劣化，问题几乎一定在这条 rail 或它的上联，而不在若干互不相关的服务器上。

这条论断在实验里能量出来：

```bash
cd labs/05-clos-topo
make run        # 三个实验：流数、hash 口径、同质大象流，不需要 Docker
make topo       # 拓扑与地址表
make deploy     # 真拓扑：2 spine / 4 leaf，需要 Docker 与 containerlab
make collect    # 起流量、采上行计数、算真实分布
```

1:1 无收拢**只保证有两条等价路径，不保证两条都在干活**。第一个实验量流数：八条流时两条上行只用上一条，两千条才贴近均分。第三个实验量的是更硬的一条：五元组完全相同的训练流量，任何 hash 都只选一条路。rail-optimized 拓扑存在的理由就在这里。

## 拓扑要进数据模型

拓扑在传统 IDC 里是排障时才查一次的东西。在智算网络里，它得成为监控数据模型里的实体。

故障定位的第一问变了：从「哪台设备坏了」变成「哪条轨道、哪个平面、哪个环段出了问题」。设备是物理实体，轨道和环段才是与训练任务对应的单位。拓扑要用图结构存，这也是后面做图计算的基础。

流量矩阵已知，加上拓扑，预期就能写成具体断言，比如「任务 X 的环经过 Rail 0、3、5，Rail 3 的链路利用率应接近线速」，这类断言可以持续自动核对。

探测部署策略也跟着变。路径覆盖按 rail 和平面分层设计：每条 rail 独立覆盖，跨平面路径重点覆盖。全网均匀撒点是传统 DC 的做法，在 rail 化的拓扑里会漏掉大量同轨路径。

没有拓扑这一层，手上只剩一堆孤立的端口计数器。计数器能告诉你某个端口在丢包，回答不了谁堵了谁、哪条环受影响、这个端口属于哪个任务的哪一段。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：讲清 rail-optimized。什么是 Rail，rail-aligned 的流量长什么样，它和 NCCL 环排序是什么关系。

::: details 参考答案与评分维度

Rail 是同编号网卡的集合：每台 GPU 服务器的第 N 块网卡都上联到同一组接入交换机，构成第 N 条轨道。

rail-aligned 指通信双方走同编号的 GPU 与网卡，流量在单条轨道内闭合，不经过 Spine。

NCCL 的拓扑感知环排序会尽量把环排成同 rail 序列，让集合通信流量对齐轨道，避免跨轨道争抢共享上联。

**评分维度**：Rail 定义正确（必需）。rail-aligned 形态正确（必需）。指出拓扑迎合通信模式这个目的（必需）。说出错位后果是带宽争抢与绕行（加分）。

:::

**必答 Q2**：双 ToR 加双平面分别防什么故障？故障后集群处于什么状态，全速还是降速？为什么说降速运行好过全体回退？

::: details 参考答案与评分维度

双 ToR 防单台接入交换机故障或升级维护，流量切到另一台，训练不中断，基本全速。双平面防整个交换平面故障，损失部分带宽，集群降速运行但训练继续推进。

降速好过回退的算法是量级差：一次 checkpoint 回退的代价是回退时长乘以万卡算力，几分钟到几十分钟；同期降速损失的只是利用率。两者差一个数量级，所以宁可牺牲带宽也不触发回退。

**评分维度**：两个机制防护对象区分清楚（必需）。状态正确（必需）。代价给出量级（必需）。补出「双平面掉一个之后冗余度下降、需尽快修复」（加分）。

:::

**自测 Q3**：Clos 为什么要做成 1:1 无收拢？不做的话代价是什么？

::: details 参考答案与评分维度

训练流量是持续的大象流，不是偶发突发。任何收拢比都意味着跨组通信排队，而集合通信是同步的，一次排队就变成全员变慢。

代价是交换机和光模块数量、布线复杂度、成本。这是用硬件冗余换带宽与时延的确定性。

**评分维度**：说出大象流加同步是根因（必需）。说出成本代价（必需）。

:::

**自测 Q4**：某条 Rail 的一台接入交换机整体故障，路径级探测与监控平台分别看到什么？

::: details 参考答案与评分维度

探测：覆盖该 rail 的路径成组断崖或劣化。由于双 ToR 与冗余路径，部分路径在切换后自动恢复，呈现「成组故障加成组自愈」的形态。

设备侧：该交换机失联（LLDP 与 BGP 邻居消失），流量在备用路径上重新哈希，其他 rail 与上联的利用率出现跳变。

监控平台的价值在于把「Rail R 的交换机 down」翻译成「任务 X 的环段受影响」，并判断会不会触发 checkpoint 回退。

**评分维度**：说出成组特征（必需）。说出切换导致的路径集合变化（必需）。能翻译成任务影响（加分）。

:::

## 小结

Clos 用 1:1 无收拢换来「任意两组互访都能吃满线速」，代价是硬件数量与布线复杂度。这笔成本躲不掉，因为训练流量是持续的大象流，收拢比在同步场景里等于排队。

一台 GPU 服务器有 8 张卡、8 块网卡、8 条轨道，同号卡走同一条道。NCCL 的环排序顺着轨道排，跨 spine 的流量就被压到最低。轨道按通信规律设计，不是布线时顺带形成的。

接入层有三层冗余：双 ToR 防单台故障，训练不中断；双平面防整个平面，降速继续；三网隔离让 checkpoint、训练、管理面互不抢带宽。判一份故障之前先分清它是端口 down、链路劣化还是队列打满，三级的处置方向完全不同。

对监控来说，拓扑从图纸变成了数据模型里的实体。Rail、平面、环段都是查询维度，冗余切换本身也是需要被观测的事件。

::: tip 本课要点

**Clos 的无收拢、八条轨道、三层冗余，共同决定流量能走哪条路。**

- Clos / Fat-Tree：1:1 无收拢换全等分带宽，本质是硬件换确定性。ECMP 无处不在，是路径覆盖的主战场
- GPU 服务器 8 卡 8 网卡 8 条轨道。rail-aligned 是同轨通信不出轨，NCCL 环排序顺着 rail 走
- 三层冗余：双 ToR 防单台（不中断）、双平面防整平面（降速）、三网隔离防互相抢带宽
- 监控的新维度：Rail、平面、环段。冗余切换与路径重哈希本身就是观测事件
- 探测按 rail 与平面分层覆盖，不做全网均匀撒点

:::

- [NVIDIA NCCL — Topology awareness](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/communicators.html)（NCCL 如何感知拓扑并排序环）
