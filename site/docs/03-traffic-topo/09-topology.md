上一讲说过，环序要顺着物理拓扑排。这一篇讲拓扑本身：万卡集群长什么形状，跟传统数据中心差在哪里，以及这些形状为什么必须进监控的数据模型。

三件事决定了流量能走哪条路：Clos 的无收拢承诺、每台服务器八条轨道、接入层的冗余设计。

## Clos：1:1 无收拢换确定性

万卡集群的骨架是 **Clos 架构**，以太网语境里常叫 Fat-Tree。两层或三层交换机，Leaf 全部互联到 Spine，并且**上联总带宽等于下联总带宽，1:1 无收拢**。

```text
        +---------+   +---------+   +---------+   +---------+
        | Spine A |   | Spine B   |   | Spine C |   | Spine D |
        +----+----+   +----+----+   +----+----+   +----+----+
             |             |             |             |
      +------+------+------+------+------+------+------+------+
      |             |             |             |             |
  +---+---+     +---+---+     +---+---+     +---+---+     +---+---+
  | Leaf1 |     | Leaf2 |     | Leaf3 |     | Leaf4 |     | Leaf5 |
  +---+---+     +---+---+     +---+---+     +---+---+     +---+---+
      |             |             |             |             |
   GPU 组1       GPU 组2       GPU 组3       GPU 组4       GPU 组5
```

这个形状给出的承诺是：任意两组服务器互访都能吃满线速，也就是全等分带宽（full bisection bandwidth）。任意两个节点之间都有大量等价路径，靠 ECMP 分担。

代价在硬件上。交换机和光模块数量巨大，布线复杂，成本和运维复杂度都随规模线性上升。

训练流量决定了这笔钱必须花。传统 IDC 的流量以小流为主，几毫秒就排空，收拢比（比如 3:1、4:1）是个常见的省钱手段，因为同时打满所有上联的概率不高。

训练集群不吃这一套。AllReduce 是持续的大象流，一打就是一整个训练周期，任何收拢比都意味着跨组通信排队。集合通信又是同步的，排队一次就是全员等一次。所以 1:1 无收拢不是富裕，是必需。

::: info 经验映射（IDC → AIDC）

ECMP 在这里的角色和传统 IDC 一样，负责把流量摊到多条等价路径上。

差别在分母与后果。传统 DC 里路径覆盖做到九成已经很强，剩下那一成赌的是概率。训练集群里，没覆盖到的那一成，可能正好承载某个 AllReduce 环的关键一段，一次劣化就是一次全局停顿。

这也是路径级观测在智算网络里比在 IDC 里更值钱的原因。

:::

## 一台 GPU 服务器的八条轨道

传统业务服务器一两块网卡就够。GPU 服务器不一样：8 张 GPU 通常各配一块独立网卡（200G 或 400G），每块网卡属于一条 **Rail（轨道）**。

```text
Rail 0 交换机组  --  所有服务器的 网卡0  --Z--  GPU0
Rail 1 交换机组  --  所有服务器的 网卡1  --Z--  GPU1
Rail 2 交换机组  --  所有服务器的 网卡2  --Z--  GPU2
...                                          共 8 条轨道
```

Rail N 指的是所有服务器第 N 块网卡所连的那组接入交换机。同号的卡走同一条道。

于是流量分两种形态：

```text
轨道对齐（rail-aligned）：A.GPU0 到 B.GPU0，全程在 Rail 0 内，不经过 Spine
轨道交叉（rail-crossing）：A.GPU0 到 B.GPU5，必须跨轨道，占用共享上联
```

把上一讲接上。NCCL 做拓扑感知排序时，会尽量把环排成同 rail 序列，让集合通信的相邻通信方落在同一条轨道里。轨道对齐的比例越高，跨 spine 的流量越少，拥塞面也越小。

这件事的含义可以概括成一句话：**拓扑存在的目的是迎合软件的通信模式**。轨道不是布线时顺手形成的，它是按 NCCL 的通信规律设计的。

## 接入层的三层冗余

03 讲的因果链决定了网络抖一下就是全体停摆，所以接入层做了三层冗余：

| 设计 | 防什么 | 故障后状态 |
|---|---|---|
| **双 ToR** | 单台接入交换机故障或升级维护 | 流量切到另一台，训练不中断 |
| **双平面** | 整个交换平面故障 | 损失部分带宽，降速运行 |
| **计算 / 存储 / 带外三网物理隔离** | checkpoint 与训练抢带宽、管理面被业务打爆 | 各自独立，互不影响 |

三层设计对应三种故障粒度，恢复后的状态也不同。这一点对监控很重要：双 ToR 切换后集群基本全速，双平面故障后集群降速运行，两者的告警级别和处置动作不一样。

「降速运行好过全体回退」这笔账要算清。一次 checkpoint 回退的代价是回退时长乘以万卡算力，从几分钟到几十分钟。同期降速运行损失的只是利用率，通常在一两成。所以工程上宁可牺牲带宽，也不触发回退。

代价是冗余度下降。双平面掉一个平面之后，只剩单平面，再有一处故障就没有备份了。这类「已降级」状态必须被监控显式记住，否则第二次故障会打得措手不及。

::: info 经验映射（IDC → AIDC）

降级、限流、灰度，做稳定性的人对这套不陌生：保住整体活性，牺牲局部性能。

AIDC 的双平面是同一个判断落在物理层上的版本。你需要补的不是这套思想，是把它映射到新拓扑上的词汇：平面、轨道、环段。

:::

## 拓扑要进数据模型

拓扑在传统 IDC 里是排障时翻一翻的图纸。在智算网络里，它必须成为监控数据模型里的实体，理由有四条。

**故障定位的第一问变了。** 从「哪台设备坏了」变成「哪条轨道、哪个平面、哪个环段出了问题」。设备是物理实体，轨道和环段才是与训练任务对应的单位。拓扑要用图结构存，这也是后面做图计算的基础。

**冗余切换本身就是事件。** 双 ToR 切换、路径重新哈希会让流量瞬间换路。路径级探测能立刻发现「路径集合变了」，设备级监控对此毫无察觉，因为两端的计数器都正常。

**预期与实际的断言要落到拓扑上。** 上一讲说流量矩阵已知，加上拓扑，预期就能写成具体断言。比如「任务 X 的环经过 Rail 0、3、5，Rail 3 的链路利用率应接近线速」。这类断言可以持续自动核对。

**探测部署策略随之改变。** 路径覆盖应按 rail 和平面分层设计：每条 rail 独立覆盖，跨平面路径重点覆盖。全网均匀撒点是传统 DC 的做法，在 rail 化的拓扑里会漏掉大量同轨路径。

没有拓扑这一层，手上只剩一堆孤立的端口计数器。计数器告诉你某个端口在丢包，回答不了「谁堵了谁」「哪条环受影响」「这个端口属于哪个任务的哪一段」。

## 经验映射

| 传统 IDC 的拓扑认知 | 智算网络里必须补的维度 |
|---|---|
| 二层三层、VLAN、ECMP | Rail 编号、平面归属、超节点边界 |
| 设备级可用性（up 或 down） | 路径集合是否变化，切换本身是事件 |
| 收拢比是常态设计 | 1:1 无收拢是默认前提 |
| 计算与存储可共用网络 | 三网物理隔离是硬要求 |
| 拓扑用于变更管理 | 拓扑用于实时关联与自动核对 |

## 判读与实操

摸清拓扑的三组命令：

```bash
# 主机侧：GPU 与网卡的物理亲和，判断某张卡走哪块网卡、哪条轨道
nvidia-smi topo -m

# 主机侧：网卡的 PCIe 位置与链路速率，核对是否按设计上联
lspci -tv | grep -i eth
ethtool <ifname> | grep -E 'Speed|Link detected'

# 网络侧：拓扑自动发现的两种来源
show lldp neighbors
show ip bgp summary
```

按 rail 维度组织观测：

| 观测对象 | 说明 |
|---|---|
| 每条 rail 的链路利用率分布 | 是否均匀。某条显著偏低或偏高都异常 |
| 每条 rail 的 pause、ECN、discard | 定位到哪条轨道在反压 |
| 跨轨道（经 spine）流量占比 | 应尽量低。升高说明环序与拓扑错位 |
| 双 ToR 主备流量分配 | 是否按设计分流，切换后有没有恢复 |
| 平面间流量对称性 | 单平面劣化的早期信号 |

判读的落点：**同一个故障在 rail 维度上通常成组出现**。某条 rail 的多条路径同时劣化，问题几乎一定在该 rail 或它的上联，而不在若干互不相关的服务器上。

实验入口，量的是这条论断：

```bash
cd labs/05-clos-topo
make run        # 三个实验：流数、hash 口径、同质大象流，不需要 Docker
make topo       # 拓扑与地址表
make deploy     # 真拓扑：2 spine / 4 leaf，需要 Docker 与 containerlab
make collect    # 起流量、采上行计数、算真实分布
```

1:1 无收拢只保证有两条等价路径，不保证两条都在干活。第一个实验量流数：八条流时两条上行只用上一条，两千条才贴近均分。第三个实验量的是更硬的一条：五元组完全相同的训练流量，任何 hash 都只选一条路。这就是 rail-optimized 拓扑存在的理由。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：讲清 rail-optimized。什么是 Rail，rail-aligned 的流量长什么样，它和 NCCL 环排序是什么关系。

::: details 参考答案与评分维度

Rail 是同编号网卡的集合：每台 GPU 服务器的第 N 块网卡都上联到同一组接入交换机，构成第 N 条轨道。

rail-aligned 指通信双方走同编号的 GPU 与网卡，流量在单条轨道内闭合，不经过 Spine。

NCCL 的拓扑感知环排序会尽量把环排成同 rail 序列，让集合通信流量对齐轨道，避免跨轨道争抢共享上联。

**评分维度**：Rail 定义正确（必需）。rail-aligned 形态正确（必需）。指出拓扑迎合通信模式这个目的（必需）。说出错位后果是带宽争抢与绕行（加分）。

:::

**必答 Q2**：双 ToR 加双平面分别防什么故障？故障后集群处于什么状态，全速还是降速？为什么说降速运行好过全体回退？

::: details 参考答案与评分维度

双 ToR 防单台接入交换机故障或升级维护，流量切到另一台，训练不中断，基本全速。双平面防整个交换平面故障，损失部分带宽，集群降速运行但训练继续推进。

降速好过回退的原因是一笔量级账：一次 checkpoint 回退的代价是回退时长乘以万卡算力，几分钟到几十分钟；同期降速损失的只是利用率。两者差一个数量级，所以宁可牺牲带宽也不触发回退。

**评分维度**：两个机制防护对象区分清楚（必需）。状态正确（必需）。代价给出量级（必需）。补出「双平面掉一个之后冗余度下降、需尽快修复」（加分）。

:::

**自测 Q3**：Clos 为什么要做成 1:1 无收拢？不做的话代价是什么？

::: details 参考答案与评分维度

训练流量是持续的大象流，不是偶发突发。任何收拢比都意味着跨组通信排队，而集合通信是同步的，一次排队就变成全员变慢。

代价是交换机和光模块数量、布线复杂度、成本。这是用硬件冗余换带宽与时延的确定性。

**评分维度**：说出大象流加同步是根因（必需）。说出成本代价（必需）。

:::

**自测 Q4**：某条 Rail 的一台接入交换机整体故障，路径级探测与监控平台分别看到什么？

::: details 参考答案与评分维度

探测：覆盖该 rail 的路径成组断崖或劣化。由于双 ToR 与冗余路径，部分路径在切换后自动恢复，呈现「成组故障加成组自愈」的形态。

设备侧：该交换机失联（LLDP 与 BGP 邻居消失），流量在备用路径上重新哈希，其他 rail 与上联的利用率出现跳变。

监控平台的价值在于把这句「Rail R 的交换机 down」翻译成「任务 X 的环段受影响」，并判断会不会触发 checkpoint 回退。

**评分维度**：说出成组特征（必需）。说出切换导致的路径集合变化（必需）。能翻译成任务影响（加分）。

:::

## 小结

Clos 用 1:1 无收拢换来「任意两组互访都能吃满线速」的承诺，代价是硬件数量与布线复杂度。这笔钱必须花，因为训练流量是持续大象流，收拢比在同步场景里等于排队。

一台 GPU 服务器有 8 张卡、8 块网卡、8 条轨道，同号卡走同一条道。NCCL 的环排序顺着轨道排，跨 spine 的流量就被压到最低。轨道不是布线时顺便形成的，它是按通信规律设计的。

接入层有三层冗余：双 ToR 防单台故障，训练不中断；双平面防整个平面，降速继续；三网隔离让 checkpoint、训练、管理面互不抢带宽。

对监控来说，拓扑从图纸变成了数据模型里的实体。Rail、平面、环段都是查询维度，冗余切换本身就是需要被观测的事件。

::: tip 本课要点

**Clos 的无收拢、八条轨道、三层冗余，共同决定流量能走哪条路。**

- Clos / Fat-Tree：**1:1 无收拢**换全等分带宽，本质是硬件换确定性。ECMP 无处不在，是路径覆盖的主战场
- GPU 服务器 **8 卡 8 网卡 8 条轨道**。rail-aligned 是同轨通信不出轨，NCCL 环排序顺着 rail 走
- 三层冗余：**双 ToR** 防单台（不中断）、**双平面** 防整平面（降速）、**三网隔离**防互相抢带宽
- 监控的新维度：**Rail、平面、环段**。冗余切换与路径重哈希本身就是观测事件
- 探测按 rail 与平面分层覆盖，不做全网均匀撒点

:::

留一个思考题：把轨道数从 8 改成 4、每块网卡带宽翻倍，rail-aligned 的比例会变好还是变差。
