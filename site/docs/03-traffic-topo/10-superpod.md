title: 第10讲 · 超节点与 Scale-up
description: 超节点把一半横向流量私有化到柜内。scale-up 与 scale-out 的语义、带宽、故障表现各不相同，域内故障落在常规监控的盲区里，每一笔取舍都算清省了什么、付出了什么。
---

超节点是一个非常贵的盒子。为了把域内带宽做上去，厂商在里面苦心孤诣加了一堆东西：整柜的铜缆背板、十八个 NVSwitch 托盘、按 GPU 数配平的供电与散热，这些设计也让它的可管理性跟着下降，柜内的连接关系、错误计数、路由策略，全都不在标准网管的口径里。但是毫无疑问这是值得的，尤其像训练这种拿带宽当饭吃的场景。

集群里于是跑着两套网络。一套在机柜之间，规则是报文、队列、PFC 那一套；另一套在机柜内部，讲的是内存地址，没有队列溢出，也就没有 PFC，带宽高一个数量级，故障却表现为训练直接挂死。

两边的差别不止参数。scale-out 的语义是报文（send / recv），经网卡出去，每 GPU 400 Gb/s，约 50 GB/s，存在拥塞与丢包，所以要 PFC、ECN、DCQCN；scale-up 的语义是内存（load / store），直接读写对端 HBM，每 GPU 900 GB/s 到 1.8 TB/s，链路是承诺带宽的点对点通道，基本不存在拥塞。一列要求配置处处一致，另一列要求硬件本身不出错。前面九讲的东西，全部落在第一列。

## 铜缆还是光缆

域内的距离很短，一柜之内，两米封顶。这个距离用铜缆就够了，一根 DAC 铜缆的成本只有同速率光模块的零头，功耗也低一个量级，还不怕灰尘。

代价是距离，铜缆过了两米信号就散，所以柜内的走线必须贴着背板走，不能跨柜。如果你的域就是要跨柜，那只能上光，光模块与端口的账立刻回来，覆盖整个产品周期。

这笔账在一个机柜内算下来，省掉的是几百个光模块的采购与功耗，付出的是走线的自由度。绝大多数超节点都选了铜缆，不是因为它先进，是因为它刚好够用。

## 把交换塞进盒子里

传统 Clos 是个二维结构：每台机器先上 leaf，leaf 再上 spine，任意两点之间至少两跳。这个结构在大规模下是省的，链路总数按 N log N 涨，但它要有交换芯片、要有光模块、要有布线。

如果参与方只有七十二颗 GPU 呢？用二维结构反而浪费，还不如把交换芯片直接铺成一个平面，任意两颗之间一跳直达。这么做省下来的不只是链路，还有每一跳的排队、每一跳的时延、每一跳的配置一致性。

这跟一个集合很小的时候不该用二维哈希表是一个道理：元素少，二维结构本身的开销比数据还大，用一维数组遍历反而快。超节点就是这么个取舍，它用一柜子的铜缆和十八个 NVSwitch 托盘，把七十二颗 GPU 做成了一个一维直连的域。

算一下链路数就知道代价在哪：七十二颗 GPU，每颗十八条 NVLink，加起来是 648 条物理链路。这个数字比机柜之间那几百条光模块链路还多，链路基数一上去，故障频率必然跟着上去。

## 带宽差 18 到 36 倍

H100 一代的 NVLink 双向 900 GB/s，Blackwell 一代做到 1.8 TB/s。同代机器的 scale-out 网卡是每 GPU 400 Gb/s，换算过来 50 GB/s。**域内带宽是域间的 18 到 36 倍**。

这个比例决定工程上的取舍：张量并行（TP）要在每一层交换激活值，通信量大，只能放在域内；数据并行（DP）每步只同步一次梯度，可以跨机柜；专家并行（EP）介于两者之间，看具体实现。并行策略的分层就是这么来的，哪里快，通信密集的活儿就放哪里，超节点出现之后这个分层也在变。

这笔账值不值，得把两边都算上：省下的东西很实在，TP 与部分 EP 不用再跨柜，跨 spine 的流量少一大截；付出的也很实在，这十几倍带宽只能在一个盒子内用，出了柜子立刻掉回 50 GB/s，而你把一大块流量交给了一个常规监控看不见的域。**省下的流量是钱，付出的是可见性，两笔都得认。**

## 域内没有 PFC

PFC 存在的前提是队列会溢出，溢出就丢包，丢包对 RDMA 是灾难。

NVLink 上没有这条链条：链路是点对点的串行通道，多条组成一组，NVSwitch 做全互联交换，发送端和接收端的时间槽固定，带宽是承诺的，**没有排队溢出这个状态**，也就没有需要提前阻止的丢包。逐跳反压在这儿没有作用对象。

NVLink 处在机器内部总线的位置上，像跨 socket 的 UPI 或 AMD 的 Infinity Fabric：程序访问另一颗 CPU 挂的内存走 NUMA 路径，不需要拥塞控制。RoCE 更像跨机器的 RPC，有队列、可能丢包，所以要重传和拥塞控制。

硬件误码照样存在，处理方式和网络不同。NVLink 走**链路层重放**：数据在链路上以 flit 为单位传输，某个 flit 出错，发送端硬件从回放缓冲区里再送一遍。整个过程在芯片内部闭环，耗时纳秒量级，操作系统、网卡、NCCL 都感知不到。高频误码会让重放次数暴涨，光纤脏污、铜缆微弯、金手指氧化都会造成这种情况，重放本身不丢数据，但会吃掉有效带宽，这就是柜内失速那类隐性故障的起点。

这一笔换得很彻底：丢掉的是整套拥塞控制、水线与调参，拿到的是确定性的带宽，代价是那个你熟悉的环境没了，域内没有队列水线可以读。

## 域内的界限

一台超节点能装多少张卡，不是想装多少装多少，它有几个硬上限，超出任何一个就得重新出域：

```text
nvlink-domain-max-gpus    72    # 域内 GPU 上限，超过就要走 scale-out
nvlink-domain-nvswitch    18    # NVSwitch 托盘数，决定全互联的端口规模
nvlink-links-per-gpu      18    # 每颗 GPU 的 NVLink 条数，决定单卡带宽
nvlink-lane-gbps          50    # 单条链路每方向 GB/s 量级，代际翻倍
```

这几条界限不是产品的选项，它们由物理决定：NVSwitch 的端口数决定了能挂多少 GPU，机柜的供电与散热决定了能塞多少托盘，铜缆的长度决定了柜内能拉多远。

所以「把域做大」这条路是有尽头的，接近上限之后，再做大的收益就不如去做 scale-out。下一讲要讲的柜内失速，恰好发生在这个上限附近，因为这时候链路基数最大、余量最小。

接下来看一个具体现象，验证一下「域内带宽是承诺的」这句话是不是真的。

一颗 GPU 上的某条 NVLink 出问题，它的有效带宽会往下掉，但同时**同一颗 GPU 的其他十七条链路一条都不会来分担**，因为时间槽是按链路编号固定分配的，坏掉的那条的时间槽就空在那里。整颗 GPU 的对外带宽是所有链路的最小值，不是平均值。

这就好比电影院里人走了座位还在，下一波观众来了直接坐；而不是谁来了谁抢座。带宽是预留的，不是竞争来的，这个比方不好听，但它解释了一个重要的事实：**域内链路坏了，带宽不会自动补回来，只能等换件**。

## 拓扑由固件拍板

域内的路由、时间槽分配、重放、降速，全部由厂商固件和 NVSwitch 决定。我们在这套东西面前是甩手掌柜，没有交换机的命令行可以敲，也没有队列水线可以调。

能做的只有一件事：看它给出的计数器，然后判断该不该换件。

```bash
# 字段清单随驱动版本变化，先查再采
dcgmi dmon -l | grep -i nvlink

# XID 与 NVLink 相关报错
dmesg -T | grep -i 'xid\|nvlink'
```

域内该看的五个信号：**NVLink 带宽**（每 GPU 每方向），跟拓扑期望值比，掉档比绝对值更有意义；**NVLink 错误与 replay 计数**，看一阶差分，绝对值长期不为零就是链路劣化；**XID 报错码**，区分可恢复与不可恢复，处置前查官方文档；**GPU 温度与降频**，降频会让域内带宽整体下移，容易被误判成链路故障；**NCCL 拓扑与 ring 组成**，确认通信是不是真的在域内。

命令只解决「有没有」，趋势要自己存。replay 计数是累计值，没有时序就判断不出劣化速度，这一点和交换机计数器的处理方式一样。

## NCCL 会自己选路

NCCL 启动时探测拓扑。它读 NVML 的总线信息，看 GPU 与网卡的亲和性，据此决定 ring 与 tree 的成员顺序。

```bash
nvidia-smi topo -m
```

输出是一张亲和矩阵，四种标记：`NV#` 是走 # 条 NVLink，`PIX` 是同一个 PCIe 交换芯片下，`SYS` 是跨 NUMA，`NODE` 是同 NUMA。

再打开 NCCL 的初始化日志，能看到它实际选了什么：

```bash
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,GRAPH ./train 2>&1 | grep -i 'ring\|tree\|nvlink\|via'
```

两份输出对照着看，能回答一个关键问题：**这次训练的 ring 是不是全在域内**。如果部分成员被排到 `SYS` 或跨节点路径上，训练照跑，带宽掉一个数量级，这时候所有网络设备的指标都正常，因为流量根本没走那些链路。

## 超节点把故障搬进了盒子

GB200 NVL72 这类整机的组成很直白：72 颗 GPU、36 颗 Grace CPU、18 个 NVSwitch 托盘，装在一个机柜里，域内全互联。

麻烦在位置上：域内的连接关系不经过任何交换机端口，网管系统按「设备 × 端口」建模，**这些链路没有对应的对象**。于是出现一类故障：不报警，指标全绿，任务在变慢。

另一句话得说在前面：省掉的是跨柜那几百条光模块链路的一半，付出的则是把相当于全网十分之一的链路基数塞进一个盒子，而这些链路在网管里没有对象，链路越多、坏得越频，偏偏这一块最少人看得见。

scale-up 用 load / store 语义，没有逐包头部可以挂遥测元数据，INT 那一套在域内直接失效，因为没有报文可插。域内的可观测入口只有三条：设备固件与带外管理，主要是 NVSwitch 侧的计数器；GPU 驱动侧的指标，走 DCGM 与 NVML；应用侧日志，主要是 NCCL 的报错与降级记录。这三条都不属于标准网络遥测接口，一套采集口径覆盖不了全集群。

## 分界线正在移动

scale-up 的私有总线正在被拉进开放标准。UALink 让多家加速器共用一套域内互联，Ultra Ethernet Consortium 也把 scale-up 列入目标场景。

推动这件事的原因很直接：域内带宽是域间的十几倍，这块带宽如果只由一家厂商提供，整机成本与供应都会被卡住。协议开放之后，采集入口才会标准化，而现在多厂商混部的环境里，域内数据只能按厂商各写一套适配。

存储领域走过同一条路。早期的 SAN 是各家私有管理协议，后来 SMI-S 与 SNIA 标准出来，才有一套统一采集口径。超节点现在处在前面那个阶段，现实的做法是把域内数据抽象成一层内部指标模型。

## 小结

集群里跑着两套网络。scale-out 关心报文与拥塞，所以有 PFC、ECN、DCQCN。scale-up 是 load / store 语义，带宽承诺、时间槽固定，没有排队溢出这个状态，PFC 在这里没有作用对象。

两边带宽差 18 到 36 倍，这个比例决定并行策略怎么分层：通信密集的放域内，同步频率低的跨机柜。

麻烦出在位置上。超节点把一半横向流量私有化到柜内，域内链路不经过任何交换机端口，网管按设备加端口建模，这些链路连对象都没有。故障于是不报警，只表现为任务变慢。域内的观测入口只有三条：固件带外、DCGM 与 NVML、NCCL 日志，都不属于标准遥测。

对从 IDC 过来的人来说，迁移成本低的部分很明确：亲和性思维、拓扑感知、硬件错误分类，这些能力直接可用，缺的是接口与工具链。麻烦的是这些信号不在标准遥测里，传统主机监控的采集面是网卡、磁盘、CPU，域内数据一个都不覆盖。

::: tip 本课要点

**一个集群两套网络：scale-out 讲报文与拥塞，scale-up 讲内存与总线。**

- 语义差别是根：load / store 与 send / recv，前者没有队列溢出，所以没有 PFC
- 带宽量级：域内每 GPU 900 GB/s 到 1.8 TB/s，域间约 50 GB/s，差 18 到 36 倍，决定并行策略分层
- 超节点把一半故障挪进盒子：网管按设备端口建模，看不见域内链路
- 域内信号只有三个入口：固件与带外、DCGM 与 NVML、NCCL 日志
- NCCL 会自己选路。ring 被排到域外时，网络指标全绿，任务变慢

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：某千卡集群接了 4 台超节点，训练任务出现周期性变慢，每次只影响部分任务。交换机侧的 PFC 与 ECN 全部正常。给出排查顺序。

::: details 参考答案与评分维度

先扩大范围，再谈定位。PFC 与 ECN 正常只说明 scale-out 侧没有拥塞，它不覆盖域内。

**第一步看拓扑**。抓一次 NCCL 初始化日志，确认 ring 是否全在域内。新加一批任务之后，成员顺序可能被排到跨节点路径上。

**第二步看域内计数**。采 NVLink 的 replay 与 CRC 一阶差分，按 GPU 与链路拆分。周期性变慢常对应某条链路的偶发重放，而这条链路不会产生告警。

**第三步看降频与温度**。GPU 温度贴顶会整体降频，域内带宽下移，表现和链路故障一样。

**第四步才对时间线**。把任务变慢的时刻与 XID、驱动日志、固件事件对齐。

**评分维度**：先扩大范围再收敛（必需）。提到确认 NCCL 拓扑（必需）。区分降频与链路故障（加分）。直接怀疑交换机配置（不通过）。

:::

**必答 Q2**：为什么 scale-up 域内不需要 PFC？从队列是否存在、丢包后果、重传机制三个方面回答。

::: details 参考答案与评分维度

**队列**。域内链路是点对点固定时间槽，带宽是承诺的。不存在多流争抢同一个出端口队列的溢出状态。

**丢包后果**。内存语义下丢一个 flit 就是数据不一致，硬件用 CRC 与 replay 处理，语义上不暴露给上层，也不存在重传造成尾延迟放大的问题。

**重传机制**。NVLink 有自己的链路层重放，粒度和时机由硬件决定，不依赖端到端拥塞控制。

所以逐跳反压在这个域里没有作用对象。反过来，域内一旦出错，恢复手段是换链路、换托盘，调参数没有用。

**评分维度**：三点都答到（必需）。说出「域内故障靠替换而非调参」（加分）。

:::

**自测 Q3**：把超节点当一台大交换机纳管，会丢哪几类信息？

::: details 参考答案与评分维度

三类。域内链路的连接关系，也就是谁和谁之间有几条 NVLink。链路级错误计数，这些在固件与带外接口里，不在交换机 MIB 里。域内拓扑与训练 ring 的对应关系，这是判断流量是否走域内的唯一依据。

设备建模层面还有一个后果：CMDB 里按机柜、交换机、端口建的三层树，装不下「域」这个概念。域内故障的告警归因会挂到错误的父节点上。

**评分维度**：说出连接关系与链路计数（必需）。提到拓扑与 ring 的对应（加分）。

:::

**自测 Q4**：给域内可观测设计一个最小指标体系，选三个指标并说明理由。

::: details 参考答案与评分维度

一个可用的最小集：NVLink 每 GPU 双向带宽、NVLink 错误与 replay 增长率、NCCL ring 的域内占比。

选择逻辑是覆盖三层。带宽回答性能有没有掉档，错误增长率回答硬件有没有劣化，ring 域内占比回答流量还在不在域内。三个指标分别对应性能、健康、拓扑，缺一层就会出现解释不了的故障。

**评分维度**：三个指标覆盖不同维度（必需）。给出选择逻辑而不是罗列（必需）。

:::

留一个思考题：如果域内带宽只比域间高一倍，今天这套 rail-optimized 拓扑与并行策略分层还成立吗。
