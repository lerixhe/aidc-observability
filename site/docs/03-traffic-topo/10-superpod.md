---
title: 超节点与 Scale-up 网络
description: 超节点把一半横向流量私有化到柜内，PFC 与队列水线在那半边失效。本课讲清 scale-up 与 scale-out 的分界，以及域内故障该看什么信号。
---

如果要用一句话来描述这一讲，我想应该是：同一个集群里跑着两套网络，一套讲报文，一套讲内存地址。

前面九讲的全是机柜之间的那套。交换机、端口、队列、PFC，都是 scale-out 网络里的东西。

从这一讲开始要加一条分界线。**同一个集群里跑着两套物理网络，规则完全相反。** 一套讲报文与拥塞，一套讲内存地址与总线。

## 学完这一讲，你应该能

- 说清 scale-up 与 scale-out 在语义、带宽、故障表现三方面的差别，并给出量级对比
- 解释 NVLink 与 NVSwitch 为什么不需要 PFC，也不需要丢包这个概念
- 认出超节点把故障位置从交换机侧挪到盒子内部之后，传统网管会丢失哪几类信号
- 拿到一台超节点机器时，能用 `nvidia-smi topo` 与 NCCL 的拓扑探测复原域内连接关系

## 机制拆解

### 0x01 两套网络，两套规则

| 维度 | scale-out | scale-up |
|---|---|---|
| 范围 | 机柜之间、集群级 | 机柜内部、域内几十到几百 GPU |
| 协议 | RoCEv2、InfiniBand | NVLink、NVSwitch、专有总线 |
| 语义 | 报文（send/recv），经 NIC | 内存（load/store），直接读写对端 HBM |
| 典型带宽 | 每 GPU 400 Gb/s，约 50 GB/s | 每 GPU 900 GB/s 到 1.8 TB/s，双向 |
| 拥塞与丢包 | 存在，所以要 PFC、ECN、DCQCN | 基本不存在，链路是承诺带宽的点对点 |
| 故障表现 | 时延抖动、pause 上涨、任务变慢 | 训练挂死、单卡掉队、NCCL 报错 |

两边不是同一类东西。带宽差一个数量级还多。

H100 一代的 NVLink 双向 900 GB/s，Blackwell 一代升到 1.8 TB/s。同一代机器的 scale-out 网卡是每 GPU 400 Gb/s，也就是 50 GB/s。

**域内带宽是域间的 18 到 36 倍。** 这个比例直接决定了矩阵切分的方式，也就决定了流量模型。

### 0x02 NVLink 不需要无损，因为它不谈丢包

先说清一件事。PFC 存在的理由是队列会溢出，溢出就丢包，丢包对 RDMA 是灾难。

NVLink 上没有这个链条。链路是定点对点的串行通道，多条组成一组。NVSwitch 做全互联交换。发送端和接收端的时间槽是固定的，带宽是承诺的。**没有"排队溢出"这个状态。**

用熟悉的东西类比一下。NVLink 相当于同一台机器里的内存总线，比如跨 socket 的 UPI，或者 AMD 的 Infinity Fabric。你调 Go 程序访问另一颗 CPU 挂的内存，走的是 NUMA 路径。这条路不会去配拥塞控制。

RoCE 相当于跨机器的 RPC。有网络、有队列、可能丢包，所以要有重传与拥塞控制。

::: warning 内存语义决定了观测手段不同

scale-up 用 load/store 语义，意味着没有 per-packet 的头部可以挂遥测元数据。INT 那一套在域内直接失效，因为你没有"报文"可插入。

域内的可观测入口只有三条：

- 设备固件与带外管理，也就是 NVSwitch 侧的计数器
- GPU 驱动侧指标，走 DCGM 与 NVML
- 应用侧日志，主要是 NCCL 的报错与降级记录

这三条都不是标准的网络遥测接口，也就意味着你没法定一套统一的采集口径覆盖全集群。
:::

### 0x03 超节点把故障位置搬进了盒子

GB200 NVL72 这类整机的组装方式很直白。72 颗 GPU、36 颗 Grace CPU、18 个 NVSwitch 托盘，装在一个机柜里，域内全互联。

这是整机，不是拼装。

规模上去之后，域内链路的数量是配件级的。72 颗 GPU 全互联，链路数远超机柜之间的几百条光模块链路。

链路基数上去，单链路故障率不变，故障频率必然上升。这就是概率。

问题在于位置。域内的连接关系不经过任何交换机端口。网管系统按"设备 × 端口"建模时，这些链路根本没有对应的对象。

这就是这一讲最实用的一句判断：**超节点的一半故障，落在现有监控模型的盲区里。** 这类故障不会报警，只会变成"任务有点慢"。指标全绿，任务照慢。

### 0x04 拓扑感知：NCCL 会自己选路

NCCL 启动时探测拓扑。它读 NVML 的总线信息，看 GPU 与网卡的亲和性，然后决定 ring 与 tree 的成员顺序。

```bash
nvidia-smi topo -m
```

输出是一张亲和矩阵。四个标记值得记住。

- `NV12`：走 12 条 NVLink
- `PIX`：同一个 PCIe 交换芯片下
- `SYS`：跨 NUMA
- `NODE`：同 NUMA

再打开 NCCL 的初始化日志，能看到它实际选了什么。

```bash
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,GRAPH ./train 2>&1 | grep -i 'ring\|tree\|nvlink\|via'
```

这两份输出对照着看，能回答一个关键问题：**这次训练的 ring 是不是全在域内。**

如果部分成员被排到 `SYS` 或者跨节点路径上，训练能跑，但带宽掉一个数量级。这时候所有网络设备的指标都是正常的，因为流量根本没走那些链路。

## 经验映射

| 你已有的概念 | 在超节点里的对应物 |
|---|---|
| NUMA 亲和性与 `numactl` | GPU 与 NVLink 域的亲和性，NCCL 的拓扑探测 |
| 单机内共享内存 | scale-up 域的内存语义通信 |
| 跨机器的 RPC 与重试 | scale-out 的 RDMA 语义 |
| 交换芯片背板与 SerDes 链路 | NVSwitch 托盘与 NVLink 物理通道 |
| 内核日志与 XID 这类硬件报错 | NVLink replay、ECC、XID 错误码 |

迁移成本低的那部分很明确。亲和性思维、拓扑感知、硬件错误分类，你都会。缺的是接口与工具链。

还有一件更麻烦的事：**这些信号不在标准遥测里。**

## 判读与实操

### 0x05 域内该看什么

| 信号 | 来源 | 判读要点 |
|---|---|---|
| NVLink 带宽（每 GPU 每方向） | DCGM / NVML | 与拓扑期望值对比，掉档比绝对值更有意义 |
| NVLink 错误与 replay 计数 | DCGM / NVML | 用一阶差分看，绝对值长期不为 0 就是链路劣化 |
| XID 报错码 | 内核日志 / DCGM | 区分可恢复与不可恢复，13、31、79 这类码要查手册 |
| GPU 温度与降频 | DCGM | 降频会让域内带宽整体下移，误判成链路故障 |
| NCCL 拓扑与 ring 组成 | 应用日志 | 确认通信是否真的在域内 |

```bash
# 字段清单随驱动版本变化，先查再采
dcgmi dmon -l | grep -i nvlink

# XID 与 NVLink 相关报错
dmesg -T | grep -i 'xid\|nvlink'
```

一行命令只能确认存在性。趋势得自己存。

### 0x06 分界线正在移动

scale-up 的私有总线正在被拉进开放标准。UALink 让多家加速器共用一套域内互联。Ultra Ethernet Consortium 也把 scale-up 列入目标场景。

驱动这件事的力量很简单。域内带宽是域间的十几倍。这块带宽如果只由一家厂商提供，整机成本与供应都会被卡住。

对做可观测的人来说，结论不乐观但明确：**协议开放之后，采集入口才会标准化。** 现在的多厂商混部里，域内数据只能按厂商各写一套适配。协议先开放，采集才标准。

::: info 经验映射（IDC → AIDC）

这件事在存储领域发生过一次。早期的 SAN 是各家私有管理协议。后来 SMI-S 与 SNIA 标准出来，才有一套统一采集口径。

超节点现在处在前一个阶段。工具能做的是把"域内数据"抽象成一层内部指标模型，就像当年给各家存储设备写适配层。
:::

## 习题

**必答 Q1**：某千卡集群接了 4 台超节点，训练任务出现周期性变慢，每次只影响部分任务。交换机侧的 PFC 与 ECN 全部正常。给出你的排查顺序。

::: details 参考答案与评分维度

先证伪"正常"的范围。PFC 与 ECN 正常，只说明 scale-out 侧没有拥塞，它不覆盖域内。先证伪，再定位。

第一步看拓扑。抓一次 NCCL 初始化日志，确认 ring 是否全在域内。有人加了一批任务之后，成员顺序可能被排到跨节点路径上。先看这个。

第二步看域内计数。采 NVLink 的 replay 与 CRC 一阶差分，按 GPU 与链路拆分。周期性变慢往往对应某条链路的偶发重放，而这条链路不会告警。

第三步看降频与热。GPU 温度贴顶会整体降频，域内带宽下移，表现出来和链路故障一样。

第四步才对时间线。把任务变慢的时间点与 XID、驱动日志、固件事件对齐。

**评分维度**：先扩大范围再收敛（必需）。提到 NCCL 拓扑确认（必需）。区分降频与链路故障（加分）。直接怀疑交换机配置（不通过）。
:::

**必答 Q2**：为什么 scale-up 域内不需要 PFC。请从队列是否存在、丢包后果、重传机制三个角度回答。

::: details 参考答案与评分维度

- **队列**。域内链路是定点对点固定时间槽，带宽是承诺的。没有"多流争抢同一个出端口队列"的溢出状态。
- **丢包后果**。内存语义下丢一个 beat 就是数据不一致，硬件层面用 CRC 与 replay 处理，语义上不暴露给上层，也不存在"重传造成时延放大"的尾延迟问题。
- **重传机制**。NVLink 有自己的链路层重传与重放，粒度和时机由硬件决定，不依赖端到端拥塞控制。

所以 PFC 这套逐跳反压在这个域里没有对象。反过来说，域内一旦出错，恢复手段靠换链路或换托盘，调参数没用。

**评分维度**：三点都答到（必需）。能说出"域内故障靠替换而非调参"（加分）。
:::

**自测 Q3**：把超节点当一台大交换机纳管，会丢哪几类信息。

::: details 参考答案与评分维度

会丢三类。一，域内链路的连接关系，也就是谁和谁之间走了几条 NVLink。二，链路级的错误计数，这些数据在固件与带外接口里，不在交换机 MIB 里。三，域内拓扑与训练 ring 的对应关系，这是判断"流量是否走域内"的唯一依据。

设备建模层面还有一个后果。CMDB 里按机柜、交换机、端口建的三层树，装不下"域"这个概念。域内故障的告警归因会挂到错误的父节点上，因为那层关系不在网管里。

**评分维度**：说出连接关系与链路计数（必需）。提到拓扑与 ring 的对应（加分）。
:::

**自测 Q4**：如果让你给"域内可观测"设计一个最小指标体系，你会选哪三个指标，理由是什么。

::: details 参考答案与评分维度

一个可用的最小集有三项：NVLink 每 GPU 双向带宽、NVLink 错误与 replay 的增长率、NCCL ring 的域内占比。

选择逻辑是覆盖三层。带宽回答"性能有没有掉档"。错误增长率回答"硬件有没有劣化"。ring 域内占比回答"流量还在不在域内"。三个指标分别对应性能、健康、拓扑三个维度，缺一层就会出现解释不了的故障。

**评分维度**：三个指标覆盖不同维度（必需）。给出选择逻辑而非罗列（必需）。
:::

## 小结

这一讲可以压成一句话：**同一个集群里跑着两套网络，一套讲报文，一套讲内存地址。**

scale-out 关心报文和拥塞，所以有 PFC、ECN、DCQCN。scale-up 是 load/store 语义，带宽是承诺的，时间槽是固定的，没有排队溢出这个状态，所以 PFC 在这里没有对象。两边的带宽差 18 到 36 倍，这个比例直接决定了矩阵怎么切。

麻烦出在位置上。超节点把一半横向流量私有化到柜内，域内链路不经过任何交换机端口。网管按设备加端口建模，这些链路连对象都没有。于是故障不报警，只变成"任务有点慢"。

域内的观测入口只有三条：固件带外、DCGM 与 NVML、NCCL 日志。这不是标准遥测，也定不出统一口径。UALink 这类开放标准出来之后，采集才会跟着标准化，存储领域的 SMI-S 走过同一条路。

::: tip 本课要点

**同一个集群里跑着两套网络，一套讲报文，一套讲内存地址。**

- 一个集群两套网络：**scale-out 讲报文与拥塞，scale-up 讲内存与总线**
- 带宽量级：域内每 GPU 900 GB/s 到 1.8 TB/s，域间约 50 GB/s，差 18 到 36 倍
- NVLink 没有队列溢出状态，所以不需要 PFC，也不谈丢包
- 超节点把一半故障挪进盒子：**网管按设备端口建模，看不见域内链路**
- 域内信号只有三个入口：固件与带外、DCGM/NVML、NCCL 日志
- 一条坑：NCCL 会自己选路。ring 被排到域外时，网络指标全绿，任务变慢
:::

留一个思考题：如果域内带宽只比域间高一倍，今天这套 rail-optimized 拓扑和矩阵切分方式还成立吗。
