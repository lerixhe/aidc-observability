前面九讲讲的是机柜之间的那套网络：交换机、端口、队列、PFC。

集群里还有另一套网络，在机柜内部，规则和前面那套完全不同。它不讲报文，讲内存地址；没有队列溢出，也就没有 PFC；带宽高一个数量级，故障表现却是训练直接挂死。

这一篇划清两套网络的分界，以及超节点给观测带来的那部分盲区。

## 交付

- 说清 scale-up 与 scale-out 在语义、带宽、故障表现三方面的差别，给出量级对比
- 解释 NVLink 与 NVSwitch 为什么不需要 PFC，也没有丢包这个概念
- 认出超节点把故障位置从交换机侧挪到盒子内部之后，常规网管会丢哪几类信号
- 拿到一台超节点机器时，用 `nvidia-smi topo` 与 NCCL 的拓扑探测复原域内连接关系

## 两套网络，规则相反

| 维度 | scale-out | scale-up |
|---|---|---|
| 范围 | 机柜之间，集群级 | 机柜内部，几十到几百 GPU |
| 协议 | RoCEv2、InfiniBand | NVLink、NVSwitch、专有总线 |
| 语义 | 报文（send / recv），经网卡 | 内存（load / store），直接读写对端 HBM |
| 典型带宽 | 每 GPU 400 Gb/s，约 50 GB/s | 每 GPU 900 GB/s 到 1.8 TB/s，双向 |
| 拥塞与丢包 | 存在，所以要 PFC、ECN、DCQCN | 基本不存在，链路是承诺带宽的点对点通道 |
| 故障表现 | 时延抖动、pause 上涨、任务变慢 | 训练挂死、单卡掉队、NCCL 报错 |

第一列的内容前面九讲已经铺开，第二列是新的。两张表并排放着，能看出这不是同一类东西：一边是网络，一边更接近总线。

## 带宽差多少

H100 一代的 NVLink 双向 900 GB/s，Blackwell 一代做到 1.8 TB/s。同代机器的 scale-out 网卡是每 GPU 400 Gb/s，换算过来 50 GB/s。

**域内带宽是域间的 18 到 36 倍。**

这个比例不是宣传数字，它决定了工程上的很多取舍。张量并行（TP）要在每一层做激活值交换，通信量大，只能放在域内。数据并行（DP）每步只同步一次梯度，可以跨机柜。专家并行（EP）介于两者之间，看具体实现。

换句话说，并行策略的分层是由带宽比决定的：哪里快就把通信密集的活儿放哪里。下一讲讲超节点如何改变这个分层，而这一篇先把两边的账面弄清楚。

## NVLink 为什么不需要 PFC

PFC 存在的前提是队列会溢出，溢出就丢包，丢包对 RDMA 是灾难。

NVLink 上没有这条链条。链路是点对点的串行通道，多条组成一组，NVSwitch 做全互联交换。发送端和接收端的时间槽固定，带宽是承诺的。**没有「排队溢出」这个状态**，也就没有需要提前阻止的丢包。

拿已经熟悉的东西对照：NVLink 相当于同一台机器里的内存总线，比如跨 socket 的 UPI 或 AMD 的 Infinity Fabric。程序访问另一颗 CPU 挂的内存走 NUMA 路径，这条路不需要拥塞控制。RoCE 相当于跨机器的 RPC，有网络、有队列、可能丢包，所以需要重传与拥塞控制。

硬件误码照样存在，处理方式和网络不一样。NVLink 走**链路层重放**：数据在链路上以 flit 为单位传输，某个 flit 出错，发送端硬件从回放缓冲区里再送一遍。整个过程在芯片内部闭环，耗时在纳秒量级，上层完全感知不到。

高频误码会让重放次数暴涨。光纤脏污、铜缆微弯、金手指氧化都会造成这种情况。重放本身不丢数据，但会吃掉有效带宽，这就成了下一篇要处理的隐性故障。

::: warning 内存语义决定了观测手段不同

scale-up 用 load / store 语义，没有逐包头部可以挂遥测元数据。INT 那一套在域内直接失效，因为没有报文可插。

域内的可观测入口只有三条：

- 设备固件与带外管理，主要是 NVSwitch 侧的计数器
- GPU 驱动侧指标，走 DCGM 与 NVML
- 应用侧日志，主要是 NCCL 的报错与降级记录

这三条都不属于标准网络遥测接口，也就没法用一套采集口径覆盖全集群。

:::

## 超节点把故障搬进了盒子

GB200 NVL72 这类整机的组成很直白：72 颗 GPU、36 颗 Grace CPU、18 个 NVSwitch 托盘，装在一个机柜里，域内全互联。

链路数量随规模上升得很快。72 颗 GPU 全互联，域内链路的条数远超机柜之间那几百条光模块链路。单链路故障率不变，链路基数上去，故障频率必然跟着上去。

麻烦在位置。域内的连接关系不经过任何交换机端口。网管系统按「设备 × 端口」建模时，这些链路没有对应的对象。

于是出现一类故障：不报警，指标全绿，任务在变慢。这类故障的具体形态（PCIe 协商掉速、NVLink 链路重放、XID 错误码）是 [10b 讲](10b-scale-up-nvlink.md) 的内容。

## NCCL 会自己选路

NCCL 启动时探测拓扑。它读 NVML 的总线信息，看 GPU 与网卡的亲和性，据此决定 ring 与 tree 的成员顺序。

```bash
nvidia-smi topo -m
```

输出是一张亲和矩阵，四种标记的含义：

| 标记 | 含义 |
|---|---|
| `NV#` | 走 # 条 NVLink |
| `PIX` | 同一个 PCIe 交换芯片下 |
| `SYS` | 跨 NUMA |
| `NODE` | 同 NUMA |

再打开 NCCL 的初始化日志，能看到它实际选了什么：

```bash
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,GRAPH ./train 2>&1 | grep -i 'ring\|tree\|nvlink\|via'
```

两份输出对照着看，能回答一个关键问题：**这次训练的 ring 是不是全在域内。**

如果部分成员被排到 `SYS` 或跨节点路径上，训练能跑，带宽掉一个数量级。这时候所有网络设备的指标都正常，因为流量根本没走那些链路。

## 经验映射

| 你已有的概念 | 在超节点里的对应物 |
|---|---|
| NUMA 亲和性与 `numactl` | GPU 与 NVLink 域的亲和性，NCCL 的拓扑探测 |
| 单机内部共享内存 | scale-up 域的内存语义通信 |
| 跨机器的 RPC 与重试 | scale-out 的 RDMA 语义 |
| 交换芯片背板与 SerDes 链路 | NVSwitch 托盘与 NVLink 物理通道 |
| 内核日志与 XID 这类硬件报错 | NVLink replay、ECC、XID 错误码 |

::: info 经验映射（IDC → AIDC）

迁移成本低的部分很明确：亲和性思维、拓扑感知、硬件错误分类，这些能力直接可用。缺的是接口与工具链。

麻烦的一点是这些信号不在标准遥测里。传统主机监控的采集面是网卡、磁盘、CPU，域内数据一个都不覆盖。

:::

## 判读与实操

域内该看的五个信号：

| 信号 | 来源 | 判读要点 |
|---|---|---|
| NVLink 带宽（每 GPU 每方向） | DCGM 与 NVML | 与拓扑期望值对比，掉档比绝对值更有意义 |
| NVLink 错误与 replay 计数 | DCGM 与 NVML | 看一阶差分。绝对值长期不为零就是链路劣化 |
| XID 报错码 | 内核日志与 DCGM | 区分可恢复与不可恢复，处置前查官方 XID 文档 |
| GPU 温度与降频 | DCGM | 降频会让域内带宽整体下移，容易被误判成链路故障 |
| NCCL 拓扑与 ring 组成 | 应用日志 | 确认通信是否真的在域内 |

```bash
# 字段清单随驱动版本变化，先查再采
dcgmi dmon -l | grep -i nvlink

# XID 与 NVLink 相关报错
dmesg -T | grep -i 'xid\|nvlink'
```

命令只解决「有没有」，趋势要靠自己存。replay 计数是累计值，没有时序就判断不出劣化速度，这一点和交换机计数器的处理方式一样。

## 分界线正在移动

scale-up 的私有总线正在被拉进开放标准。UALink 让多家加速器共用一套域内互联，Ultra Ethernet Consortium 也把 scale-up 列入目标场景。

驱动这件事的力量很简单：域内带宽是域间的十几倍，这块带宽如果只由一家厂商提供，整机成本与供应都会被卡住。

对做可观测的人来说，结论不算乐观。**协议开放之后，采集入口才会标准化。** 现在的多厂商混部环境里，域内数据只能按厂商各写一套适配。

::: info 经验映射（IDC → AIDC）

这件事在存储领域发生过一次。早期的 SAN 是各家私有管理协议，后来 SMI-S 与 SNIA 标准出来，才有一套统一采集口径。

超节点现在处在前面那个阶段。工具能做的是把域内数据抽象成一层内部指标模型，类似当年给各家存储设备写适配层。

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：某千卡集群接了 4 台超节点，训练任务出现周期性变慢，每次只影响部分任务。交换机侧的 PFC 与 ECN 全部正常。给出排查顺序。

::: details 参考答案与评分维度

先扩大范围，再谈定位。PFC 与 ECN 正常只说明 scale-out 侧没有拥塞，它不覆盖域内。

**第一步看拓扑**。抓一次 NCCL 初始化日志，确认 ring 是否全在域内。新加一批任务之后，成员顺序可能被排到跨节点路径上。

**第二步看域内计数**。采 NVLink 的 replay 与 CRC 一阶差分，按 GPU 与链路拆分。周期性变慢常对应某条链路的偶发重放，而这条链路不会产生告警。

**第三步看降频与温度**。GPU 温度贴顶会整体降频，域内带宽下移，表现和链路故障一样。

**第四步才对时间线**。把任务变慢的时刻与 XID、驱动日志、固件事件对齐。

**评分维度**：先扩大范围再收敛（必需）。提到确认 NCCL 拓扑（必需）。区分降频与链路故障（加分）。直接怀疑交换机配置（不通过）。

:::

**必答 Q2**：为什么 scale-up 域内不需要 PFC？从队列是否存在、丢包后果、重传机制三个方面回答。

::: details 参考答案与评分维度

**队列**。域内链路是点对点固定时间槽，带宽是承诺的。不存在多流争抢同一个出端口队列的溢出状态。

**丢包后果**。内存语义下丢一个 flit 就是数据不一致，硬件用 CRC 与 replay 处理，语义上不暴露给上层，也不存在重传造成尾延迟放大的问题。

**重传机制**。NVLink 有自己的链路层重放，粒度和时机由硬件决定，不依赖端到端拥塞控制。

所以逐跳反压在这个域里没有作用对象。反过来，域内一旦出错，恢复手段是换链路、换托盘，调参数没有用。

**评分维度**：三点都答到（必需）。说出「域内故障靠替换而非调参」（加分）。

:::

**自测 Q3**：把超节点当一台大交换机纳管，会丢哪几类信息？

::: details 参考答案与评分维度

三类。域内链路的连接关系，也就是谁和谁之间有几条 NVLink。链路级错误计数，这些在固件与带外接口里，不在交换机 MIB 里。域内拓扑与训练 ring 的对应关系，这是判断流量是否走域内的唯一依据。

设备建模层面还有一个后果：CMDB 里按机柜、交换机、端口建的三层树，装不下「域」这个概念。域内故障的告警归因会挂到错误的父节点上。

**评分维度**：说出连接关系与链路计数（必需）。提到拓扑与 ring 的对应（加分）。

:::

**自测 Q4**：给域内可观测设计一个最小指标体系，选三个指标并说明理由。

::: details 参考答案与评分维度

一个可用的最小集：NVLink 每 GPU 双向带宽、NVLink 错误与 replay 增长率、NCCL ring 的域内占比。

选择逻辑是覆盖三层。带宽回答性能有没有掉档，错误增长率回答硬件有没有劣化，ring 域内占比回答流量还在不在域内。三个指标分别对应性能、健康、拓扑，缺一层就会出现解释不了的故障。

**评分维度**：三个指标覆盖不同维度（必需）。给出选择逻辑而不是罗列（必需）。

:::

## 小结

集群里跑着两套网络。scale-out 关心报文与拥塞，所以有 PFC、ECN、DCQCN；scale-up 是 load / store 语义，带宽承诺、时间槽固定，没有排队溢出这个状态，PFC 在这里没有作用对象。

两边的带宽差 18 到 36 倍，这个比例决定了并行策略怎么分层：通信密集的放域内，同步频率低的跨机柜。

麻烦出在位置上。超节点把一半横向流量私有化到柜内，域内链路不经过任何交换机端口，网管按设备加端口建模，这些链路连对象都没有。故障于是不报警，只表现为任务变慢。

域内的观测入口只有三条：固件带外、DCGM 与 NVML、NCCL 日志。都不属于标准遥测，定不出统一口径。UALink 这类开放标准出来之后，采集才会跟着标准化，存储领域的 SMI-S 走过同一条路。

::: tip 本课要点

**一个集群两套网络：scale-out 讲报文与拥塞，scale-up 讲内存与总线。**

- 语义差别是根：**load / store 与 send / recv**，前者没有队列溢出，所以没有 PFC
- 带宽量级：域内每 GPU 900 GB/s 到 1.8 TB/s，域间约 50 GB/s，**差 18 到 36 倍**，决定并行策略分层
- 超节点把一半故障挪进盒子：**网管按设备端口建模，看不见域内链路**
- 域内信号只有三个入口：**固件与带外、DCGM 与 NVML、NCCL 日志**
- NCCL 会自己选路。ring 被排到域外时，网络指标全绿，任务变慢

:::

留一个思考题：如果域内带宽只比域间高一倍，今天这套 rail-optimized 拓扑与并行策略分层还成立吗。
