如果要用一句话来描述这一讲，我想应该是：节点内通信失速不会报警，只会让一万张卡在屏障前静静等它。

上一讲我们划分了 scale-up 与 scale-out 的边界。柜内几百条 NVLink 跑着内存语义，不走交换机，也不发 PFC。

但很多工程师接手大集群后，最痛苦的经历来自盒子内部。**交换机端口全绿，RDMA 没有丢包，NCCL 通信却慢了三倍。**

去机器里查，才发现某颗 GPU 挂载的 NVLink 发生了隐性降速，或者 PCIe 链路协商掉到了 Gen3。这一讲把柜内的观测黑盒彻底拆开。

先在一条能跑的命令上，看一下 GPU 内部互联与错误指标的入口：

```bash
# 查看本地 GPU 间拓扑矩阵与 NVLink 连接状态
nvidia-smi topo -m 2>/dev/null || echo "需在配备 NVIDIA GPU 的机器上执行"
```

你会在矩阵里看到 `NV#`、`PIX`、`SYS` 等连接标记。它直接决定了通信走柜内总线、PCIe 桥还是跨 CPU 慢速通道。

## 学完这一讲，你应该能

- 说出 NVLink 物理层重传、恢复、降级与断连四级错误状态的演进链条
- 解释 PCIe 链路掉速对大模型分布式训练的致命影响
- 熟练判读 GPU XID 错误码，区分硬件损坏、驱动异常与热失控
- 建立一套基于 DCGM 的节点内可观测采集清单，涵盖重传、降级、温度与功率

## 机制拆解

### 0x01 NVLink 链路错误：不丢包，但会重放

在 scale-out 网络里，链路劣化表现为错包、丢弃或者 PFC 反压。

NVLink 没有交换机队列，处理硬件误码靠的是**链路层重放（Link-Level Replay）**。

报文在 NVLink 走的是微小数据块（flit）。数据块出错，发送端硬件直接从微型回放缓冲区里把 flit 再送一遍。

这个动作在芯片硬件内部闭环，耗时通常只有几个纳秒。操作系统、网卡、NCCL 应用层完全感知不到。

你可以把这套排查，类比成排查分布式系统的长尾。一个 worker 卡顿，全局同步一起卡死。这相当于把单点故障的代价，直接放大了一万倍。

你手上已有的主机监控工具，大部分能直接复用。但你必须把轮询周期从分钟级收紧，才能捕捉到纳秒级重放引发的带宽缩水。

但光纤脏污、铜缆微弯、金手指氧化会导致高频误码。**重放频率一旦达到每秒几万次，有效通信带宽就会剧烈缩水。**

NVLink 错误演进通常走四级链条：

1. **Recovery / Replay（可纠正重放）**：硬件自动纠错，带宽微幅抖动，通常无告警。
2. **Link Degradation（链路降级）**：误码率突破水线，固件主动关闭部分通道，带宽对半甚至掉到四分之一。
3. **Flit Error Accumulation（不可纠正累积）**：重传耗尽，硬件触发不可屏蔽中断。
4. **Link Down（链路彻底断开）**：NCCL 无法走 NVLink，被迫降级走跨机网络，时延暴增百倍。

### 0x02 PCIe 协商掉速：无声无息的半身不遂

在单机八卡服务器里，GPU 与网卡之间必须经过 PCIe 交换芯片。

每张 400G 网卡必须跑在 PCIe Gen5 x16 才能打满单向 50 GB/s 的线速。

但 PCIe 链路受到高频干扰、供电微抖或针脚松动时，硬件会触发降速自愈机制：

| PCIe 状态 | 理论单向带宽 | 实际可用带宽 | 对 400G 网卡的影响 |
|---|---|---|---|
| **Gen5 x16** | 64 GB/s | 约 50～55 GB/s | 完美打满 400 Gbps 线速 |
| **Gen5 x8** | 32 GB/s | 约 25 GB/s | 网卡降速 50%，沦为慢节点 |
| **Gen4 x16** | 32 GB/s | 约 25 GB/s | 协议代际协商失败，带宽减半 |
| **Gen3 x16** | 16 GB/s | 约 13 GB/s | 带宽跌去四分之三，集合通信严重落后 |

麻烦在于，**PCIe 协商降速不属于致命错误，机器不死机，训练进程照常启动。**

一个 Rank 的网卡被锁在 Gen4，它的发送带宽就只有正常卡的一半。因为 AllReduce 的木桶效应，整场一万张卡全部降速到这一半。

监控看板上的集群网络流量呈现均匀低水位，运维查断腿也找不到拥塞，真凶只是机箱里一条协商错误的插槽。

### 0x03 故障指纹：读懂 GPU XID 错误

NVIDIA 驱动向内核日志打印的系统事件，统称 **XID 错误**。

它们是定位节点内故障最高效的指纹。但几百种 XID 混在日志里，必须抓出与通信强相关的几组：

| XID 编号 | 核心含义 | 通信故障表现 | 排查动作 |
|---|---|---|---|
| **XID 31** | 显存 ECC 不可纠正错误 | 进程直接崩掉，偶发时导致某卡算力骤降 | 必须下线换卡或运行显存深度巡检 |
| **XID 43** | GPU 驱动停止响应或掉卡 | NCCL 通信挂死，报 connection closed | 检查 PCIe 链路状态、供电模块与固件版本 |
| **XID 79** | GPU 掉电或物理掉线 | 整机脱离拓扑，训练任务整体中断 | 硬件故障，检查机柜供电与母排接触 |
| **XID 92** | 高频降频（Thermal / Power Throttle） | 某卡主频暴跌，成为 AllReduce 木桶短板 | 清理机柜风道、检查进风温度、查散热硅脂 |
| **XID 119** | NVSwitch 物理链路不可纠正错误 | 节点内拓扑破损，NVLink 域通信退化 | 更换机柜 NVSwitch 托盘或内部跳线 |

::: info 经验映射（IDC → AIDC）

这相当于把微观指标从网卡物理层，一路推进到 GPU、插槽、金手指的物理信号完整性上。

传统服务器出问题看 syslog，通常是磁盘坏道、网卡 link down、OOM。

智算运维必须把 **XID、PCIe 协商宽度、NVLink 回放计数** 当作第一等公民。
:::

::: warning 隐性降速的致命代价

节点内慢卡是通信调优最大的盲区。

它不像交换机丢包那样有据可查。它完全在硬件层静默降级，却通过集合通信全局放大。
:::

## 经验映射

| 你熟悉的机制 | 对应到柜内通信 |
|---|---|
| 网卡 CRC 校验与重发 | NVLink Link-Level Replay（硬件微重放） |
| 网卡千兆协商掉到百兆半双工 | PCIe 协商从 Gen5 掉速到 Gen4、链路宽度 x16 掉到 x8 |
| CPU 动态调频与过热降频 | GPU Thermal Throttling（XID 92）引发算力与通信降速 |
| Linux 内核 OOM Killer 日志 | NVIDIA 内核驱动 XID 错误事件 |

推论很明确：**集合通信变慢时，先排除盒子里的慢卡，再怀疑机柜间的网络交换机。**

## 判读与实操

### 0x04 诊断命令与指标抓取

巡检节点内互联与健康状态的核心命令清单：

```bash
# 1. 检查所有 GPU 的 PCIe 协商速度与宽度（重点看 Current Link 与 Target 是否一致）
nvidia-smi -q -d LINK | grep -E "PCIe Generation|Link Width"

# 2. 检查 NVLink 链路误码与硬件回放计数（重点关注 replay 增量）
nvidia-smi nvlink -s -i 0

# 3. 实时追踪内核中的 XID 故障指纹
dmesg -T | grep -i "NVRM: Xid"

# 4. 利用 dcgm-exporter 抓取关键时序指标
curl -s localhost:9400/metrics | grep -E "DCGM_FI_DEV_NVLINK_CRC_FLIT_ERROR_COUNT|DCGM_FI_DEV_PCIE_REPLAY_COUNTER"
```

判读要点：

- `PCIe Link Width` 如果显示为 `x8` 或 `x4`，或者代际低于 `Gen5`，说明插槽松动或总线劣化，必须立即排队报修。
- `NVLink Error` 中的 `DL Replay` 如果持续增加，说明虽然没有断线，通信带宽已经大打折扣。

## 习题

**必答 Q1**：为什么单台服务器内某张网卡的 PCIe 协商掉速，能拖慢上千卡的分布式训练集群。

::: details 参考答案与评分维度

- **带宽受限**：400G 网卡线速需要 PCIe Gen5 x16 的带宽支撑。掉速到 Gen4 之后，主机到网卡的通道带宽折半。
- **通信落后**：该节点上的 GPU 在发送梯度时耗时翻倍，成为本轮通信中的最慢节点。
- **木桶效应**：分布式训练依赖 AllReduce 算法。所有正常节点在完成通信后，必须在全局同步屏障处等待慢节点。最终导致整个集群千卡的算力利用率同时下跌。

**评分维度**：答出 PCIe 带宽减半限制网卡传输（必需）。结合 AllReduce 同步屏障说明全局级联拖垮效应（必需）。
:::

**必答 Q2**：某集群在跑大模型训练时，网络交换机无 pause 无拥塞。但任务每跑两小时就突然出现几分钟的耗时尖刺，现场无丢包。请指出三个可能在节点内部发生的原因与排查手段。

::: details 参考答案与评分维度

- **原因一：GPU 过热或功耗墙降频（XID 92）**。某张卡风道受阻，温度触顶后触发自动降频，算力下降导致无法准时交付梯度。排查：用 `nvidia-smi -q -d PERFORMANCE` 查看状态。
- **原因二：NVLink 高频链路重放（Link Replay）**。线缆在特定发热形变下误码激增，微回放吃满带宽。排查：比对 `nvidia-smi nvlink -s` 前后计数器差值。
- **原因三：显存 ECC 单比特纠错频率过高**。硬件纠正软错误时产生微小停顿，累积形成长尾延迟。排查：用 `dcgm-exporter` 检查 `DCGM_FI_DEV_ECC_SBE_VOL_TOTAL` 指标。

**评分维度**：列出两个以上节点内非网络根因（必需）。给出具体的排查指标或命令（必需）。
:::

**思考题（不给参考答案）**：72 卡液冷机柜里，某托盘温漂引发误码。网管如何在挂死前仅凭端侧遥测定位托盘。

## 小结

这一讲可以压成一句话：**节点内通信失速不会报警，只会让一万张卡在屏障前静静等它。**

超节点把横向流量包裹进机柜，给运维带来的最大挑战是可观测性失明。NVLink 链路重放与 PCIe 降级，在底层避免了报错，却在顶层通过屏障狠狠惩罚训练。

解决柜内可观测，核心是建立覆盖 NVLink Replay、PCIe 协商状态、GPU 降频与 XID 故障指纹的端侧监控矩阵。

::: tip 本课要点

**节点内通信失速不会报警，只会让一万张卡在屏障前静静等它。**

- 故障隐蔽性：NVLink 链路重放与 PCIe 协商掉速不丢包、不死机，但吞吐断崖式下跌
- 木桶效应放大：**单卡带宽折半，通过 AllReduce Barrier 放大为上万张卡同时降速**
- 关键状态核对：PCIe 协商代际与宽度必须对齐，低于基准即属于故障
- 故障指纹归位：抓牢 XID 31 显存损坏、XID 43 掉卡、XID 92 降频与 XID 119 拓扑破损
- 采集体系重构：依赖 DCGM 与主机端日志，把采集探针下沉到插槽、金手指与芯片内部
:::

留一个思考题：如果超节点内部某条 NVLink 发生永久损坏，NCCL 会自动选择降级走哪条备用路径。
