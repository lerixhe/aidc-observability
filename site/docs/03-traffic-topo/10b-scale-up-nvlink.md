`nvidia-smi` 天天在用，多数人只拿它看一张表：哪张卡在忙、温度多少、显存占了多少。这个工具还有几个查询模式，正好对应节点内排查要看的几样东西，GPU 之间的互联关系、PCIe 链路的协商状态、NVLink 的误码与重放计数。

这些数据不经过任何交换机端口，常规网管采集不到。所以节点内的故障形态和机柜之间完全不同：交换机端口全绿，RDMA 没有丢包，NCCL 通信却慢了三倍。

## 交付

- 说出 NVLink 链路错误从重放到断连的四级演进，以及每级的可观测表现
- 解释 PCIe 协商掉速对大模型分布式训练的影响路径
- 判读常用 XID 错误码，区分硬件损坏、驱动异常与热失控
- 建立一份基于 DCGM 的节点内采集清单，覆盖重放、降级、温度与功率
- 拿到一台机器时，用三四条命令复原域内连接关系与链路健康

## 交换机看不到的那一半

[10 讲](10-superpod.md) 说过超节点把一半横向流量私有化到柜内，域内链路不经过交换机端口。网管按「设备 × 端口」建模，这些链路没有对应对象，于是没有告警。

剩下的部分只能从主机侧看。三条入口：GPU 驱动暴露的 NVML 与 DCGM 指标、`nvidia-smi` 的查询子命令、内核日志里的 XID 事件。这一篇讲的就是这三条入口能拿到什么，以及拿到之后怎么判。

## NVLink 的四级错误演进

scale-out 网络里链路劣化表现为错包、丢弃或者 PFC 反压。NVLink 没有交换机队列，处理误码靠**链路层重放**。

数据在 NVLink 上以 flit 为单位传输。某个 flit 出错，发送端硬件从回放缓冲区里把它再送一遍。整个过程在芯片内部闭环，耗时纳秒量级，操作系统、网卡、NCCL 都感知不到。

这个机制的成本很低，所以偶尔一两次重放不影响什么。光纤脏污、铜缆微弯、金手指氧化会造成持续的高频误码，情况就不一样了。

错误演进通常走四级：

| 级别 | 状态 | 可观测表现 |
|---|---|---|
| 一 | **Replay**，可纠正重放 | 硬件自动纠错，带宽微幅抖动，通常无告警 |
| 二 | **Degradation**，链路降级 | 误码率突破水线，固件主动关闭部分通道，带宽掉到一半甚至四分之一 |
| 三 | **不可纠正累积** | 重放耗尽，硬件触发不可屏蔽中断，驱动开始报错 |
| 四 | **Link Down**，链路断开 | NCCL 无法走 NVLink，被迫降级走跨机网络，时延上升一个数量级 |

前两级是隐性故障的藏身处。带宽已经掉了，告警还没响。第三级之后才会出现 XID，第四级才会挂训练。

所以判读的重点在一、二级：replay 计数的增长速率，以及协商出来的链路宽度。

有一点要说清：replay 是累计计数，纳秒级的重放事件不可能靠人工观察捕捉，也没必要捕捉。看的是时间窗口内的差分：同一块卡、同一条链路，replay 每隔几分钟涨几百次，就说明误码率已经超出正常范围。

## PCIe 协商掉速

单机八卡服务器里，GPU 与网卡之间要经过 PCIe 交换芯片。一张 400G 网卡要打满单向 50 GB/s，得跑在 PCIe Gen5 x16 上。

PCIe 链路遇到高频干扰、供电微抖或针脚接触不良，硬件会触发降速自愈。协商结果可以和设计不符：

| 协商状态 | 理论单向带宽 | 实际可用 | 对 400G 网卡的影响 |
|---|---|---|---|
| Gen5 x16 | 64 GB/s | 约 50 至 55 GB/s | 打满 400 Gbps 线速 |
| Gen5 x8 | 32 GB/s | 约 25 GB/s | 网卡带宽减半，变成慢节点 |
| Gen4 x16 | 32 GB/s | 约 25 GB/s | 代际协商失败，带宽减半 |
| Gen3 x16 | 16 GB/s | 约 13 GB/s | 跌去四分之三，集合通信严重落后 |

问题在于降速不属于致命错误。机器不死机，训练进程照常启动，只有带宽变了。

一个 Rank 的网卡被锁在 Gen4，它的发送带宽就是正常卡的一半。AllReduce 是同步的，一万张卡在同一轮里等它，整场训练的算力利用率跟着掉一半。

集群看板上，网络流量呈现均匀的低水位。找不到拥塞，找不到丢包，因为流量根本没发出来。这就是节点内慢卡最难查的地方。

## 先分清是卡、是链路，还是过热

三种情况的表面现象完全一样：某张卡参与的通信变慢。处置方式却各不相同，一个换卡，一个换链路，一个调散热。

分开看三样东西：

| 疑点 | 特征 | 结论 |
|---|---|---|
| 卡 | XID 有记录，ECC 计数在涨 | 换卡或跑显存巡检 |
| 链路 | replay 在涨但 XID 干净，协商宽度掉了 | 换线、换托盘、查接触 |
| 过热 | 温度与功率贴顶，出现降频标记，XID 与 replay 都正常 | 查风道与进风温度 |

排查顺序照这个表从上往下：先看 XID，再看协商状态与宽度，最后看温度与功率。三样都干净，才回头怀疑机柜之间的网络。

## XID 指纹

NVIDIA 驱动往内核日志里打印的系统事件统称 **XID 错误**，是定位节点内故障最直接的线索。几百种编号里，与通信强相关的就那几组：

| XID | 含义 | 表现 | 处置 |
|---|---|---|---|
| **48** | 显存 ECC 不可纠正错误 | 进程崩溃，或某卡算力骤降 | 下线换卡，或跑显存巡检 |
| **43** | GPU 停止处理 | NCCL 挂死，报 connection closed | 查 PCIe 链路、供电、固件版本 |
| **74** | NVLink 相关致命错误 | 域内通信退化，拓扑破损 | 查 NVSwitch 托盘与内部跳线 |
| **79** | GPU 掉卡（fallen off the bus） | 整机脱离拓扑，任务中断 | 硬件故障，查供电与母排接触 |
| **92** | 功耗或温度触发降频 | 某卡主频下跌，成为木桶短板 | 查风道、进风温度、散热 |

XID 编号随驱动与型号演进，同一编号在不同代次上含义可能收紧或扩展。处置之前以官方 XID 文档为准，上表只用来建立直觉。

::: warning 隐性降速的代价

节点内慢卡是通信调优里最大的盲区。

它不像交换机丢包那样有据可查，硬件层静默降级，代价通过集合通信全局放大。

这一类故障的处理优先级应当与网络故障同级，而不是排在其他故障之后。

:::

## 经验映射

| 你熟悉的机制 | 对应到柜内通信 |
|---|---|
| 网卡 CRC 校验与重发 | NVLink 链路层重放（硬件微重放） |
| 网卡从千兆协商掉到百兆半双工 | PCIe 协商从 Gen5 掉到 Gen4，或 x16 掉到 x8 |
| CPU 动态调频与过热降频 | GPU 功耗与温度降频（XID 92） |
| 内核 OOM Killer 日志 | NVIDIA 驱动的 XID 错误事件 |

::: info 经验映射（IDC → AIDC）

传统服务器出问题看 syslog，常见的是磁盘坏道、网卡 link down、OOM。这三类故障都有明确的错误入口，查起来方向清楚。

节点内的故障入口换成了 NVML 计数器、PCIe 协商状态、XID 事件码。查法一样，都是找计数器异常加时间对齐，换的只是数据源。

一个推论：集合通信变慢时，先排除节点内的慢卡，再怀疑机柜之间的交换机。

:::

## 判读与实操

巡检节点内互联的四条命令：

```bash
# 1. PCIe 协商速度与宽度，对比 Current 与 Target 是否一致
nvidia-smi -q -d LINK | grep -E "PCIe Generation|Link Width"

# 2. NVLink 链路状态与误码计数（看 replay 增量，不看绝对值）
nvidia-smi nvlink -s -i 0

# 3. 内核里的 XID 事件
dmesg -T | grep -i "NVRM: Xid"

# 4. DCGM 时序指标，适合长期采集
curl -s localhost:9400/metrics | grep -E "DCGM_FI_DEV_NVLINK_CRC_FLIT_ERROR_COUNT|DCGM_FI_DEV_PCIE_REPLAY_COUNTER"
```

判读三点：

- **`Link Width` 显示 `x8` 或 `x4`，或者代际低于 `Gen5`**。插槽接触或总线劣化，排队报修。
- **`DL Replay` 持续增长**。链路没断，带宽已经在打折。按卡按链路看增长速率，找出增长最快的那条。
- **XID 与时间线对齐**。训练变慢的时刻有没有对应的 XID，有则是硬件或驱动问题，没有则继续往温度、功率、拓扑排。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：为什么单台服务器内某张网卡的 PCIe 协商掉速，能拖慢上千卡的训练集群？

::: details 参考答案与评分维度

**带宽受限**。400G 网卡要打满线速，需要 PCIe Gen5 x16 的通道带宽。掉到 Gen4 或 x8，主机到网卡的带宽折半。

**单点变慢**。该节点上的 GPU 发送梯度耗时翻倍，成为本轮通信的最慢者。

**全局放大**。AllReduce 有全局同步屏障，正常节点完成通信后要在屏障处等它。最终表现为整个集群的算力利用率同时下跌。

**评分维度**：答出 PCIe 带宽限制网卡传输（必需）。结合同步屏障说明全局级联效应（必需）。只答「网卡变慢」而没有全局路径（不通过）。

:::

**必答 Q2**：某集群跑大模型训练，交换机侧无 pause 无拥塞，任务每两小时出现几分钟耗时尖刺，无丢包。指出三个节点内可能的原因与排查手段。

::: details 参考答案与评分维度

**GPU 过热或撞功耗墙降频（XID 92）**。某张卡风道受阻，温度触顶后自动降频，无法准时交付梯度。查 `nvidia-smi -q -d PERFORMANCE`。

**NVLink 高频链路重放**。线缆在特定温度下误码激增，微重放吃掉带宽。对比 `nvidia-smi nvlink -s` 前后计数器差值。

**显存 ECC 单比特纠错频率过高**。硬件纠正软错误产生微停顿，累积成长尾延迟。用 DCGM 看 `DCGM_FI_DEV_ECC_SBE_VOL_TOTAL` 的增长率。

**评分维度**：列出两个以上节点内非网络根因（必需）。每个给出具体指标或命令（必需）。能指出「周期性尖刺要与作业日志对齐」（加分）。

:::

**思考题（不给参考答案）**：72 卡液冷机柜里，某个托盘温漂引发误码。在不挂训练的前提下，仅凭端侧遥测怎么定位到托盘。

## 小结

节点内的故障不进网管的采集面。域内链路不经过交换机端口，数据只在三条通道里：NVML 与 DCGM 指标、`nvidia-smi` 查询、内核 XID 事件。

NVLink 用链路层重放处理误码，重放开销小，不容易被注意到。演进到降级那一级，带宽已经掉了一半，告警还没有。PCIe 协商掉速更隐蔽，机器不死机、进程照常启动，只有带宽变了，而这个变化会通过 AllReduce 的同步屏障放大到全局。

XID 是最直接的线索，几十个编号里记住四五个常用的就够。编号随驱动演进，处置前查官方表。

::: tip 本课要点

**柜内失速不报警，只表现为任务变慢。**

- NVLink 四级演进：**重放 → 降级 → 不可纠正 → 断连**。前两级没有告警，判读靠 replay 增长速率与链路宽度
- PCIe 协商要对齐设计：**Gen5 x16 打满 400G，Gen4 或 x8 直接减半**。降速不触发任何错误
- 木桶效应的落点：**单卡带宽折半，经同步屏障放大为全场降速**
- XID 记四五个够用：**48 显存 ECC、43 停止处理、74 NVLink、79 掉卡、92 降频**。处置前查官方文档
- 排查顺序：**先排除节点内慢卡，再怀疑机柜之间的交换机**

:::

留一个思考题：如果超节点内部某条 NVLink 永久损坏，NCCL 会自动降级走哪条备用路径。
