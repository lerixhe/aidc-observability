在第 10 讲，我们讲到了超节点与域内带宽，也知道域内链路不经过交换机端口，所以在网管里连对象都没有。这一节我们接着往里看一层，讲讲厂商在 NVLink 上给的那套链路层重放与降级机制，它比单纯看链路 up / down 优秀得多，可惜听懂它的人不多。

`nvidia-smi` 天天在用，多数人只拿它看一张表：哪张卡在忙、温度多少、显存占了多少。这个工具还有几个查询模式，正好对应节点内排查要看的几样东西：GPU 之间的互联关系、PCIe 链路的协商状态、NVLink 的误码与重放计数。

我最初也把 `-q` 里那些协商宽度、replay 计数当成给厂商工程师看的数字，直到第一次遇上柜内失速才知道错了：交换机那边干净得像新装的，所有端口全绿，NCCL 却慢了三倍，当时能看的就只有那几个数字。这些数据不经过任何交换机端口，常规网管采集不到，所以节点内的故障形态和机柜之间完全不同。

## 链路的健康度

每一条 NVLink 上都有几个只涨不跌的计数器，磕开一条链路看，是这样：

```text
$ nvidia-smi nvlink -e -i 0
GPU 0: NVIDIA H100 80GB HBM3 (UUID: GPU-xxxxxxxx)
         Link 0: CRC FLIT Error Count: 0
         Link 0: Replay Error Count: 0
         ...
         Link 17: CRC FLIT Error Count: 0
         Link 17: Replay Error Count: 0
```

`CRC FLIT Error Count` 记的是「这条链路上出过多少个错 flit」，`Replay Error Count` 记的是「为了救这些 flit，硬件重放了多少次」。两个都是累计值，从上电那天起单调上涨，跟时间成正比，跟健康程度没关系。

数据在 NVLink 上以 flit 为单位传输，某个 flit 出错，发送端硬件从回放缓冲区里把它再送一遍，整个过程在芯片内部闭环，耗时纳秒量级，操作系统、网卡、NCCL 都感知不到。这个机制的成本很低，偶尔一两次重放不影响什么。光纤脏污、铜缆微弯、金手指氧化会造成持续的高频误码，情况就不一样了。

错误演进通常走四级：

```text
一、Replay，可纠正重放        硬件自动纠错，带宽微幅抖动，通常无告警
二、Degradation，链路降级     误码率突破水线，固件主动关掉部分通道，带宽掉一半甚至四分之一
三、不可纠正累积              重放耗尽，硬件触发不可屏蔽中断，驱动开始报错
四、Link Down，链路断开       NCCL 无法走 NVLink，被迫降级走跨机网络，时延上一个数量级
```

前两级是隐性故障的藏身处：**带宽已经掉了，告警还没响**。第三级之后才会出现 XID，第四级才会挂训练。所以判读的重点在一、二级，看的是 replay 的增长速率和协商出来的链路宽度。

## 绝对值模式

最省事的读法是把计数器原样搬上监控，配一个阈值，超了就报。这个读法有个跟缓存淘汰里 LRU 一样的毛病：它把「历史累积」当成了「当下热度」。

replay 计数从机器上电那天起就在涨，开机半年累积到几百万一点也不奇怪。拿绝对值做阈值只有两种结果：要么设得高到永远不报，要么一上线就全线告警。就像 LRU 会把「刚刚偶然被访问一次的 key」当成热 key 一样，一个只涨不跌的计数器也分不清「过去半年很糟」和「现在正在糟」。

还有一个坑更隐蔽：计数器是定长的。`nvidia-smi` 打出来的这一类计数多半是 64 位，够你用到硬件报废，但交换机上那些 32 位的字节计数、DCGM 里那些 32 位字段就不一定了，绕回零的那一刻，绝对值会从天文数字掉到零，趋势图上像一次「修复」，实际上是折返。判读之前先确认这个字段的宽度，缺一位就能骗你一次。

## 差量模式

差量模式把计数器的读数拆成两样东西记：一是这一段时间里涨了多少，二是这段增量发生在什么时候。

```go
type link struct {
    replay   uint64        // 累计重放，只涨不跌
    prev     uint64        // 上一次采到的值
    ts       int64         // 上一次采样的时刻
    rate     float64       // 衰减后的近期速率，次/秒
}

// 一次采样：算出增量、换算成速率、按间隔衰减旧值、再合并
func (l *link) sample(now int64, cur uint64) float64 {
    gap := now - l.ts
    delta := cur - l.prev
    if delta < 0 { // 计数器折返，按最大值补齐
        delta = ^uint64(0) - l.prev + cur
    }
    inst := float64(delta) / (float64(gap) / 1e9)   // 这一窗口的瞬时速率
    l.rate = decay(l.rate, gap)                      // 旧速率按间隔衰减
    l.rate = l.rate*0.75 + inst*0.25                 // 新老速率加权，别让一次抖峰说了算
    l.prev, l.ts = cur, now
    return l.rate
}

// 指数衰减：两次采样隔得越久，旧的速率掉得越多
func decay(rate float64, gap int64) float64 {
    const halfLife = 300e9 // 半衰期 5 分钟
    return rate * math.Pow(0.5, float64(gap)/halfLife)
}
```

`sample` 是这套判读的核心，每采一次都会调用它一次。能算出多少速率取决于这一窗口涨了多少以及窗口有多长。为什么要衰减、为什么要加权，是因为一次巡检时读到的尖峰不该马上变成「这条链路要换了」；隔了半小时再看，如果它自己又掉回去了，那就是一次抖动，不是劣化。

按这套口径，正常机器的线应该是贴着零的一条细线，出问题的时候是一根明显抬起来又缓慢落下去的包。判据也就变成了两个：抬到多高、落了多久还没落回来。

## 为什么要缓存上一次的读数？

这个问题看着多余，其实不是。`nvidia-smi` 每执行一次都要跟驱动打交道，一次几百毫秒，跨机器批量采集时这个开销不小；DCGM 那边读的是共享内存里的快照，快很多，但它也是快照，不是实时值。

所以要算差量，必须把上一次的读数存在采集侧，不能每次去问「昨天是多少」。这跟 Redis 缓存系统时间戳是一个道理：每一次取时间都要一次系统调用，取一次的代价比用一次贵得多，索性把它缓存起来。

差量口径的全部前提就是这个缓存：采样间隔稳定、时间基准统一、上一次的值存好。三样缺一样，算出来的斜率都在骗人。

## 为什么采样要落在同一个时间基准上？

我们是单线程采集的吗？不是。一台机器上往往同时跑着 DCGM exporter、巡检脚本、临时的人工命令，三个来源都在读同一批计数器，也都想写同一份状态。

写冲突的后果不严重但很烦：两个采集器各自记了「上一次」的值，算出来的增量互相覆盖，图上出现锯齿。解决办法很土，要么只让一个采集器写，要么每次写用一次原子比较交换，谁先到谁生效。

## 那些看着多余的分列计数

`-e` 与 `-c` 这类子命令的输出是按链路来的：一颗 GPU 到每一颗 NVSwitch 各占一列，十几列数字看着冗余，一条总计数不就能判断有没有问题了么？

能判断「有没有问题」，不能判断「问题在哪」。一条链路的老化只体现在它自己那一列上，合并成总数就被平均掉了。这跟交换机上按端口、按队列拆分的道理完全一样：分得细才有定位力，粗的快照只适合看趋势。

## 卡、链路，还是过热

三种情况的表面现象完全一样：某张卡参与的通信变慢。处置方式却各不相同，一个换卡，一个换链路，一个调散热。

**卡**的特征是 XID 有记录、ECC 计数在涨，处置是换卡或跑显存巡检；**链路**的特征是 replay 在涨而 XID 干净、协商宽度掉了，处置是换线、换托盘、查接触；**过热**的特征是温度与功率贴顶、出现降频标记，而 XID 与 replay 都正常，处置是查风道与进风温度。

排查顺序就按这个来，从 XID 查到温度功率，三样都干净，才回头怀疑机柜之间的网络。

## PCIe 掉速：机器不死机，只有带宽变了

单机八卡服务器里，GPU 与网卡之间要经过 PCIe 交换芯片。一张 400G 网卡要打满单向 50 GB/s，得跑在 PCIe Gen5 x16 上。

PCIe 链路遇到高频干扰、供电微抖或针脚接触不良，硬件会触发降速自愈，协商结果可能和设计不符：

```text
Gen5 x16   理论单向 64 GB/s   实际可用 50~55 GB/s   打满 400G 线速
Gen5 x8    理论单向 32 GB/s   实际可用约 25 GB/s    网卡带宽减半，变成慢节点
Gen4 x16   理论单向 32 GB/s   实际可用约 25 GB/s    代际协商失败，带宽减半
Gen3 x16   理论单向 16 GB/s   实际可用约 13 GB/s    跌去四分之三，集合通信严重落后
```

降速不属于致命错误。机器不死机，训练进程照常启动，**只有带宽变了**。

一个 Rank 的网卡被锁在 Gen4，它的发送带宽就是正常卡的一半。AllReduce 是同步的，一万张卡在同一轮里等它，整场训练的算力利用率跟着掉一半。集群看板上，网络流量呈现均匀的低水位，找不到拥塞，找不到丢包，因为流量根本没发出来。节点内慢卡最难查就在这里，处理优先级应当与网络故障同级。

## XID 指纹

NVIDIA 驱动往内核日志里打印的系统事件统称 XID 错误，是定位节点内故障最直接的线索。几百种编号里，与通信强相关的就那几组：

```text
48   显存 ECC 不可纠正错误   进程崩溃，或某卡算力骤降        下线换卡，或跑显存巡检
43   GPU 停止处理            NCCL 挂死，报 connection closed  查 PCIe 链路、供电、固件版本
74   NVLink 相关致命错误      域内通信退化，拓扑破损           查 NVSwitch 托盘与内部跳线
79   GPU 掉卡               整机脱离拓扑，任务中断           硬件故障，查供电与母排接触
92   功耗或温度触发降频      某卡主频下跌，成为木桶短板       查风道、进风温度、散热
```

编号随驱动与型号演进，同一编号在不同代次上含义可能收紧或扩展。处置之前以官方 XID 文档为准，上面这几条只用来建立直觉。

顺带说一句读法的区别，这一点容易搞反：**replay 是计数，看斜率；XID 是事件，看有无**。XID 出现一次就写进内核日志，不会自己消失，也不该做差分，做成趋势图反而会把它埋掉。

## 摸一遍

巡检节点内互联的几条命令：

```bash
# 1. PCIe 协商速度与宽度，对比 Current 与 Target 是否一致
nvidia-smi -q -d LINK | grep -E "PCIe Generation|Link Width"

# 2. NVLink 每条链路的带宽（看是否掉档）
nvidia-smi nvlink -s -i 0

# 3. NVLink 的 CRC 与重放计数（看增量，不看绝对值）
nvidia-smi nvlink -e -i 0

# 4. 内核里的 XID 事件
dmesg -T | grep -i "NVRM: Xid"

# 5. DCGM 时序指标，适合长期采集
curl -s localhost:9400/metrics | grep -E "DCGM_FI_DEV_NVLINK_CRC_FLIT_ERROR_COUNT|DCGM_FI_DEV_PCIE_REPLAY_COUNTER"
```

一套健康的机器，第 2 条命令的输出长这样（型号不同，Link 条数也不同，H100 是 18 条）：

```text
$ nvidia-smi nvlink -s -i 0
GPU 0: NVIDIA H100 80GB HBM3 (UUID: GPU-xxxxxxxx)
         Link 0: 25.781 GB/s
         ...
         Link 17: 25.781 GB/s
```

带宽那几行跟拓扑期望值对一下；错误计数看增减。`CRC FLIT Error Count` 不为零但不再长，说明链路有过误码，已经由重放纠回来；持续增长就是下一步要处理的劣化。

判读三条：`Link Width` 显示 `x8` 或 `x4`，或者代际低于 `Gen5`，说明插槽接触或总线劣化，排队报修；`Replay Error Count` 持续增长，链路没断但带宽已经在打折，按卡按链路看增长速率，找出增长最快的那条；XID 与时间线对齐，训练变慢的时刻有没有对应的 XID，有则是硬件或驱动问题，没有则继续往温度、功率、拓扑排。

## 小结

节点内的故障不进网管的采集面。域内链路不经过交换机端口，数据只在三条通道里：NVML 与 DCGM 指标、`nvidia-smi` 查询、内核 XID 事件。

NVLink 用链路层重放处理误码，重放开销小，不容易被注意到。演进到降级那一级，带宽已经掉了一半，告警还没有。PCIe 协商掉速更隐蔽，机器不死机、进程照常启动，只有带宽变了，而这个变化会通过 AllReduce 的同步屏障放大到全局。

判读的口径要分两半：计数看差量，事件看有无。XID 是最直接的线索，几十个编号里常用的就那么四五个，编号随驱动演进，处置前查官方表。

::: tip 本课要点

**柜内失速不报警，只表现为任务变慢。**

- NVLink 四级演进：重放 → 降级 → 不可纠正 → 断连。前两级没有告警，判读靠 replay 增长速率与链路宽度
- PCIe 协商要对齐设计：Gen5 x16 打满 400G，Gen4 或 x8 直接减半。降速不触发任何错误
- 木桶效应的落点：单卡带宽折半，经同步屏障放大为全场降速
- XID 常用的五个：48 显存 ECC、43 停止处理、74 NVLink、79 掉卡、92 降频。处置前查官方文档
- 排查顺序：先排除节点内慢卡，再怀疑机柜之间的交换机

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：为什么单台服务器内某张网卡的 PCIe 协商掉速，能拖慢上千卡的训练集群？

::: details 参考答案与评分维度

**带宽受限**。400G 网卡要打满线速，需要 PCIe Gen5 x16 的通道带宽。掉到 Gen4 或 x8，主机到网卡的带宽折半。

**单点变慢**。该节点上的 GPU 发送梯度耗时翻倍，成为本轮通信的最慢者。

**全局放大**。AllReduce 有全局同步屏障，正常节点完成通信后要在屏障处等它。最终表现为整个集群的算力利用率同时下跌。

**评分维度**：答出 PCIe 带宽限制网卡传输（必需）。结合同步屏障说明全局级联效应（必需）。只答「网卡变慢」而没有全局路径（不通过）。

:::

**必答 Q2**：某集群跑大模型训练，交换机侧无 pause 无拥塞，任务每两小时出现几分钟耗时尖刺，无丢包。指出三个节点内可能的原因与排查手段。

::: details 参考答案与评分维度

**GPU 过热或撞功耗墙降频（XID 92）**。某张卡风道受阻，温度触顶后自动降频，无法准时交付梯度。查 `nvidia-smi -q -d PERFORMANCE`。

**NVLink 高频链路重放**。线缆在特定温度下误码激增，微重放吃掉带宽。对比 `nvidia-smi nvlink -s` 前后计数器差值。

**显存 ECC 单比特纠错频率过高**。硬件纠正软错误产生微停顿，累积成长尾延迟。用 DCGM 看 `DCGM_FI_DEV_ECC_SBE_VOL_TOTAL` 的增长率。

**评分维度**：列出两个以上节点内非网络根因（必需）。每个给出具体指标或命令（必需）。能指出「周期性尖刺要与作业日志对齐」（加分）。

:::

## 思考

1. 你能尝试用 py 或者 Go 写一个差量判读器么，输入是一台机器 `nvidia-smi nvlink -e` 的历史输出，输出是每条链路的近期速率。
2. 如果一台机器原来按绝对值配阈值，现在整体切成差量口径，想象一下现有的告警规则会产生什么影响，哪些会变多，哪些会变哑。
