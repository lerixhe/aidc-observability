探测能看到路径通不通，看不到队列里堆了多少。这个信息只在设备上，交换机自己门儿清：哪个端口、哪个优先级队列、涨到多少字节。所以后面几讲的数据，都要从设备这边取。

在使用设备数据之前，得先了解它到底能报什么，**排障之前得先知道设备能报什么**。通过 gNMI 订阅，你可以清晰地知道一台交换机内部的一系列运行参数，而不用在出事那一刻现查现找。

一台交换机能报的状态分九大块，每块都有非常多的参数，这九块分别是：

1. 接口计数，流量、错包、丢弃都在这一块。
2. 队列与 QoS，每个队列的发送、丢弃、水线。
3. ECN，标记计数与阈值。
4. PFC，按优先级的 pause 收发与时长。
5. 转发表与邻居，FIB 使用率与 BGP 邻居状态。
6. 光模块与环境，收发光功率、温度、FEC 纠错。
7. 系统资源，CPU、内存、FIB 使用率。
8. 链路聚合与 LLDP，成员端口与对端身份。
9. 告警与日志，硬件告警与异常事件。

gNMI 可以一次性取全量，也可以按块取，按块取就是给路径：

```bash
# 取所有接口的计数
gnmic get --path '/interfaces/interface/state/counters'

# 取某个队列的水线
gnmic get --path '/qos/interfaces/interface[id=eth1]/output/queues/queue[name=3]/state'

# 取邻居与转发表
gnmic get --path '/network-instances/network-instance[name=default]/protocols/bgp'
```

考虑到参数非常繁多，一一说明工作量巨大，下面只挑几块关键的、最常用的讲。如果读者想要了解所有的参数细节，请参考阅读 [OpenConfig 的模型仓库](https://github.com/openconfig/public)。

## 为什么要换成订阅

以前取这个数据的办法是 SNMP 轮询。今天这套办法在智算网络里撑不住，原因不在「慢」，在三个结构性的地方。

**方向是反的。** 数据靠轮询产生，要看得细就得采得密，一万台设备、每台 500 个 OID、60 秒轮一遍，网管侧每秒要发 8.3 万个请求、等 8.3 万个响应；而 PFC 风暴、incast 尖刺是秒级甚至亚秒级事件，一次持续 1.5 秒的风暴在 60 秒轮询下只有一两个采样点，落在两次轮询之间就是彻底看不见。**分钟级的均值永远正常**，这是现场最常见的一句误判。

**模型是平铺的。** MIB 是一堆数字编号，语义全靠人记，要表达「eth1 端口队列 3 的 pause 帧计数」，只能靠厂商自定义分支，同一件事在不同厂商那里编号还不一样。

**一问一答。** SNMP 默认走 UDP 161，每次都要一个网络来回，报文小，RTT 就是全部成本，采样点一多，网管服务器的连接数与处理能力先到顶。

gNMI 把这三样都换了一遍：方向从拉变成推，事件一发生就能被采到；模型从平铺编号变成有结构的路径，维度自己就带上了；长连接代替一问一答，网管的并发压力也降下来。

**gNMI**（gRPC Network Management Interface）是 gRPC 上的网络设备接口，数据用 Protobuf 编码。四个 RPC：`Capabilities` 问设备支持哪些模型和编码，`Get` 读一次，`Set` 写配置，`Subscribe` 建长连接持续收。

`Subscribe` 是这套东西的重点，它有三种取数方式：`sample` 按 `sample_interval` 周期推送，可到毫秒级，适合计数器与水位这类连续量；`on_change` 值变了才推，适合端口 up/down、邻居变化；`poll` 是订阅建立后由采集端触发一次，排障时临时拉一把用。

一条推送长这样，字段是 Protobuf 序列化后的 JSON 视图：

```json
{
  "source": "leaf-01",
  "subscription-name": "queue-stats",
  "timestamp": 1730198749123456789,
  "updates": [
    {
      "Path": "interfaces/interface[name=eth1]/state/counters/out-pfc-pause-frames",
      "values": { "interfaces/interface/state/counters/out-pfc-pause-frames": 1842 }
    }
  ]
}
```

## 这台设备每秒过多少包？

这个信息在接口计数块里。`in-octets` 与 `out-octets` 给流量，`in-errors` 与 `in-discards` 给坏包与丢弃：

```bash
$ gnmic get --path '/interfaces/interface[name=eth1]/state/counters' --encoding json
{
  "in-octets": "1837492837465",
  "out-octets": "1928374655647",
  "in-unicast-pkts": "1837264519",
  "in-errors": "0",
  "in-discards": "0",
  "out-discards": "1284"
}
```

以上，`in-octets` 这个累积值除上时间，就是这一段的平均速率；`out-discards` 那 1284 是这一路真正被扔掉的包，它中 `in-discards` 与 `in-errors` 都是零，说明进来的包没问题，扔在出口。

极限情况下，一张 400G 的端口线速下是每秒钟 4000 亿个比特，也就是 500 亿字节，这些字节换乘包数，小包能到每秒上亿个。这样的一台设备每秒产生的计数变化，靠每分钟问一次是永远跟不上的。

如果 `out-discards` 涨得快，可以按队列拆开看一眼究竟是哪个队列在扔，这一层口径与下一块是连着的。

## 哪个队列在顶？

这个信息在队列块里，按接口、按队列号，每个队列都有自己的一组数：

```bash
$ gnmic get --path '/qos/interfaces/interface[id=eth1]/output/queues/queue[name=3]/state' 
{
  "transmit-pkts": "918273645",
  "transmit-octets": "1283749283746",
  "dropped-pkts": "0",              # 这个队列扔掉多少，无损队列必须为 0
  "max-queue-len": "8256",          # 观测到的最大水线，单位字节
  "ecn-marked-pkts": "48213"        # 被打过 ECN 标记的包数
}
```

这个信息也是比较有用的，通过观察 `max-queue-len` 与队列容量的比例，可以判断这条队列离撞线还有多远。如果发现水线一直贴着上限，接着就可以沿拓扑往上查是哪条流在灌它。

关于队列还有个重要的参数需要观察，那就是 `dropped-pkts`，它表示这个队列因为缓冲耗尽被丢掉的包数，如果这个数字在无损队列上不为零，意味着 PFC 的保护已经失效，或者 watchdog 已经介入过，需要立即定位。

## 缓冲占了多少？

这个信息在队列的上层，硬件缓冲池这一块：

```bash
$ gnmic get --path '/qos/interfaces/interface[id=eth1]/output/queues/queue[name=3]/state/buffer'
```

四样东西值得看：每队列分配的静态缓冲，一般按水线算出来；共享池的已用量，这是全端口抢的那一锅；共享池的水线阈值；以及某个队列是不是已经吃到超出自己那份共享。

如果某个队列长期吃掉远超自己配额的那份共享缓冲，说明这一路的流量模型和当初设计的不一样，要么水线该调，要么流该拆。

## 订阅窗口有多大？

这个信息不在设备里，在你的采集侧，但它决定了断连之后能补回多少东西。

gNMI 是长连接，连接断了，这段时间的数据就断了。重连之后能补回什么，取决于两类数据：计数器可以重连后拉一次现值的，补回来的只是一个点，中间那段峰值永远丢了；水位这类瞬时量连补都补不了，因为「当时的水位」这个值已经不存在了。

所以断连本身要当成一个事件记下来，并且要算清代价。一个 PFC 风暴如果在采集断连的 30 秒里发生，你在图上看到的是风暴前后的两条平线，中间什么都没有，而这个空档在图上看起来和「一切正常」一模一样。

设备侧如果支持 dial-out（由设备主动连采集器），断连期间有的平台会在设备本地缓存一段，这段缓存是环形的，后来的数据覆盖前面的。缓存大小与断连时长乘积决定你能补回多少，超过就只剩一个空洞。

值得单独看的一个指标是重连次数与全量重拉次数。整条订阅重连一次，往往伴随一次全量 `Get`，这个动作对设备 CPU 的冲击比 10 条订阅加起来还大，频繁重连会把设备自己压出问题。

## 采样间隔决定你能看见什么

`sample_interval` 是最该先定下来的参数，它直接决定事故能不能被看见。`labs/06-gnmi-mock` 用一个模拟设备把这件事量了一遍：

```bash
cd labs/06-gnmi-mock
make run
```

信号是一台设备的真实形态：PFC 风暴每 20 秒一次，每次 1.5 秒，速率 400 帧/秒；队列水位从 32 KB 冲到 200 KB；`oper-status` 每 7 秒抖一次，每次 300 毫秒。

```text
① 累积计数器：out-pfc-pause-frames（真实峰值 400 帧/s）
模式            间隔    样本数   观测峰值帧/s   保真度   数据量
SAMPLE         100ms     201         400      100%   28.9 KB
SAMPLE            1s      21         400      100%    3.0 KB
SAMPLE            5s       5         120       30%    734 B
SAMPLE           10s       3          60       15%    439 B
ON_CHANGE      100ms      16         400      100%    2.3 KB
ON_CHANGE         1s       3         200       50%    441 B

② 瞬时水位：queue[3] watermark-bytes（真实峰值 200 KB）
SAMPLE            1s      21         172       86%    3.4 KB
SAMPLE            5s       5          32       16%    820 B

③ 离散状态：oper-status（真实 DOWN 3 次）
ON_CHANGE      任意间隔     7           3      100%    910 B
SAMPLE            1s      21           3      100%    2.7 KB
SAMPLE            5s       5           1       33%    647 B
```

计数器按 `sample` 采，5 秒间隔下观测到的峰值只有真实的 30%，风暴在图上变成一个 120 帧/秒的小鼓包，告警阈值设在 200 帧/秒上就永远不会响。间隔拉到 10 秒只剩 15%。

`on_change` 用在计数器上是错的。计数器的值一直在变，条件永远成立，实际退化成一个间隔不确定的 `sample`，峰值丢掉一半。它适合的是第三种表里的状态量：`oper-status` 用 `on_change`，任意间隔都 100% 召回；用 `sample` 采，间隔超过 300 毫秒的抖动就开始漏。

水位这类 Gauge 比计数器更难，它是瞬时值，`on_change` 只在「值变了」时推，掉回来那一下也会推一次，能捞到尖峰，代价是数据量和突发不可控。要抓准峰值，正解是把间隔压到秒级以下，或者换成设备侧的水线快照与直方图。

## 传什么由模型定

gNMI 只规定怎么传，传什么由数据模型规定，行业主流是 **OpenConfig**，一套厂商中立的 YANG 模型，订阅时按路径指定。路径本身就是维度：接口名、队列号、方向，每一层都是一个标签，时序库要的形状正是这个，`interfaces × queue × direction` 三列标签加一个数值。

OpenConfig 覆盖不到所有厂商特性。PFC pause 的按优先级细分、队列水线直方图、INT 相关计数，常落在厂商私有模型里，以 `openconfig-*` 之外的私有 path 提供。工程上有两件事要做：一是**模型映射层**，内部统一指标名对到各厂商 path，上层不被单家绑定；二是**启动时用 `Capabilities` 探一遍**，设备支持哪些 path 就订阅哪些，不支持的记一条降级日志。多厂商混部的真实工作量全在这两件事上。

两笔账要提前算。**数据量**：点速率等于采样频率乘设备数乘路径数，一万台设备、每台 500 条路径、1 秒一次，就是每秒 500 万个点，不做分级订阅，存储和查询两头都撑不住。**时钟**：跨设备关联要回答「谁先 pause、谁后堆积」，靠时间戳排序，设备间时钟差到秒级，排序结果全乱，上下游关系判断反了也是常事。NTP 在局域网里能把误差压到毫秒级，够做趋势关联；要判微秒级的事件顺序得上 PTP，靠硬件时间戳，误差在亚微秒量级。采集端还要统一打一个接收时间戳，跟设备时间戳一起存，用来事后校验设备时钟有没有漂。

分级订阅按事件时标来定，不按指标好不好看：队列水线、PFC pause、ECN 标记是 0.1 到 1 秒 `sample`，因为事件本身是亚秒级，间隔一大就丢峰值；端口计数（octets、discards、CRC）是 10 到 30 秒 `sample`，趋势分析够用而序列数最多；端口 up/down、邻居、告警状态不限频率走 `on_change`；转发表与拓扑走分钟级或变更触发；排障临时深挖用手动 `poll`。

## 摸一遍

三条命令跑通订阅：

```bash
# 握手：看设备支持哪些模型与编码
gnmic -a <device>:57400 -u <user> -p <pass> --insecure capabilities

# 取值：先用 Get 确认路径存在，再上订阅
gnmic -a <device>:57400 -u <user> -p <pass> --insecure get \
  --path '/interfaces/interface[name=eth1]/state/counters'

# 订阅：sample 模式，每 1 秒推一次队列计数
gnmic -a <device>:57400 -u <user> -p <pass> --insecure subscribe \
  --path '/interfaces/interface[name=eth1]/state/counters/out-pfc-pause-frames' \
  --mode stream --stream-mode sample --sample-interval 1s
```

订阅建不起来，先看这三处：路径在设备上不存在（`Get` 先确认一次，返回 NotFound 就是这个问题）、编码不匹配（`Capabilities` 里支持的 encoding 与客户端要的不一样）、订阅条数超了（有的平台对单会话的订阅数有上限，几十条以内）。三种情况在采集器日志里都长得像「连上了又断开」，只能靠 `Capabilities` 的输出逐个排除。

## 小结

设备上什么都有，问题是怎么拿。SNMP 这套办法失效在三处：拉模式加分钟级，秒级事件系统性漏采；OID 平铺，表达不了端口乘队列的结构；一问一答，采样点一多，网管侧先撑不住。

gNMI 把这套换成 gRPC 加 Protobuf 上的长连接订阅。四个 RPC 里 `Subscribe` 是重点，`sample` 给连续量、`on_change` 给状态量、`poll` 留给排障。传什么由 OpenConfig 那棵 YANG 树定，接口、队列、优先级、方向都成了维度。

采样间隔决定你能看见什么。5 秒间隔下 400 帧/秒的 PFC 风暴只剩 30%，10 秒剩 15%，阈值设在 200 帧/秒就一次都不会触发。计数器必须按秒级 `sample`，状态量必须走 `on_change`。

两件事要提前算：点速率是频率乘设备数乘路径数，分级订阅是可行性前提；时钟不对齐，关联分析出来的因果链会整条错掉。

::: tip 本课要点

**SNMP 是去问设备，gNMI 是设备自己说。**

- SNMP 三处失效：**拉模式分钟级、OID 平铺、一问一答**。1.5 秒的 PFC 风暴在 60 秒轮询下可能一个点都没有
- gNMI = gRPC + Protobuf：`Capabilities` / `Get` / `Set` / `Subscribe`
- 三种取数方式：**`sample`（连续量）、`on_change`（状态量）、`poll`（排障）**。计数器用 `on_change` 是错的
- 保真度是算术题：5 秒 `sample` 下 400 帧/秒的风暴只剩 30%，1 秒才 100%
- OpenConfig 是厂商中立 YANG 树，接口 × 队列 × 优先级 × 方向，直接对时序维度
- 两件事要提前算：**分级订阅**（频率 × 设备数 × 路径数）、**时钟对齐**（NTP 毫秒级，PTP 亚微秒级）

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：SNMP 也能采到 pause 计数，为什么要换成 gNMI？从方向、模型、开销三处答。

::: details 参考答案与评分维度

方向。SNMP 是拉，事件发生后要等下一个轮询周期；gNMI 是推，值一到点就送过来。分钟级轮询下，一次 1.5 秒的 PFC 风暴可能只有一两个样本，落在两次轮询之间就完全看不见。

模型。OID 平铺表达不了「端口 × 队列 × 优先级」这种结构，厂商扩展各写各的；YANG 树自带层级与标签，直接对上时序维度。

开销。SNMP 一问一答，每采一个点要一个网络来回，一万台设备每台 500 个 OID 每分钟一轮就是每秒 8 万多个请求。gNMI 一条长连接推到底，请求开销与采集点数解耦。

**评分维度**：三处都点到本质（必需）。给出量级数字（加分）。只回答「gNMI 更现代、更快」（不通过）。

:::

**必答 Q2**：给一万台交换机做遥测采集，所有指标都 1 秒订阅跑不动。设计一套分级订阅，并说清你按什么给指标分档。

::: details 参考答案与评分维度

按事件时标分档，不看指标重要性。

1. 亚秒到 1 秒 `sample`。队列水线、PFC pause（按优先级）、ECN 标记计数。事件持续几百毫秒到几秒，间隔一放大就丢峰值，序列数可控（端口 × 队列）。
2. 10 至 30 秒 `sample`。端口 octets、discards、CRC。用于趋势与容量分析，序列数最多，降频收益最大。
3. `on_change`。端口、邻居、告警状态。离散事件，周期采样只会浪费带宽，还会漏掉 300 毫秒级的抖动。
4. `poll` 或变更触发。拓扑、转发表。

再叠两个手段：采集侧按序列表做降采样，存「1 秒峰值加 1 分钟均值」两档；排障时对指定端口临时提到亚秒级。

**评分维度**：分档与事件时标挂钩（必需）。给出数据量估算或降采样策略（必需）。提到临时提频（加分）。

:::

**自测 Q3**：为什么计数器不能用 `on_change`，状态量却最好用 `on_change`？

::: details 参考答案与评分维度

计数器的值与时间成正比，任何时刻都在变，`on_change` 的触发条件永远成立，等于退化成一个间隔不确定的 `sample`，而且设备侧的推送抑制会让峰值丢一半。实验里 1 秒间隔的 `on_change` 观测到的 pause 峰值只有 200 帧/秒，真实是 400。

状态量取值是离散的少数几个，变化本身就是事件。`on_change` 每次变化都推，召回 100%，数据量只有周期采样的十分之一。

**评分维度**：说出计数器单调递增、触发条件恒真（必需）。说出状态量变化即事件（必需）。给出实验数字（加分）。

:::

**自测 Q4**：两台设备时钟差 3 秒，跨设备关联分析会得出什么错误结论？工程上怎么防？

::: details 参考答案与评分维度

时间戳排序会把因果关系搞反。B 设备的队列堆积在物理上发生在 A 的 pause 之后，时钟差 3 秒之后，图上看是 B 先堆积、A 后 pause，结论就变成「B 的拥塞反压到了 A」，方向整个相反。

防护手段三条：全网 NTP 严格对齐，要求到毫秒级；判微秒顺序的场景上 PTP，走硬件时间戳；采集端同时记录设备时间戳与接收时间戳，两者的差值就是设备时钟的漂移量，超过阈值就报一条采集侧告警。

**评分维度**：说出顺序反转这个具体错误（必需）。给出 NTP / PTP 的量级（加分）。提到采集端双时间戳校验（加分）。

:::

## 思考

平时你们在使用设备遥测时，还需要查看哪些重要的信息，能不能直接在九块里找到对应的路径？找不到的那些，多半落在厂商私有模型里，那一块的经验比 OpenConfig 文档值钱。

留一个思考题：如果把队列水线从 1 秒改成 100 毫秒订阅，最先撑不住的是采集器带宽、交换机 CPU，还是存储写入。
