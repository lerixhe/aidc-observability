如果要用一句话来描述这一讲，我想应该是：让每一个路过的报文当记录员，自己把账本带到终点。

上一讲解决了"把设备数据采出来"。可设备数据是按端口组织的，你要查的却是某一条流。

问题很具体。训练任务从 A 卡发往 B 卡，路径上有 5 台设备、10 个端口。gNMI 告诉你这 10 个端口都忙，却不告诉你谁在卡这一条流。

INT 补的就是这个缺口。**让报文自己记录经过的每一跳**，路径视角从推断变成实测。

## 学完这一讲，你应该能

- 说出端口视角遥测的三个盲点，以及 INT 各自怎么补
- 讲清 INT 的元数据结构：每跳采什么、怎么封装、怎么上报
- 区分 INT-XD、INT-MX、postcard 三种范式，并判断哪种适合你的芯片
- 算清 INT 的带宽与 MTU 代价，给出可用的采样率区间
- 把一条路径的 P99 时延拆成每跳的排队与转发，指出可疑的那一跳

## 机制拆解

### 0x01 端口视角的三个盲点

| 盲点 | 具体表现 | 后果 |
|---|---|---|
| **不知道是谁** | 端口的队列水线是全流聚合值 | 8 个任务混跑，看不出谁把队列顶满 |
| **不知道哪一跳** | 端到端时延只有一个总数 | 5 台设备里定位不到具体一台 |
| **不知道当时** | 5 秒采样点之外的瞬时尖峰全部丢失 | 微突发在两次采样之间发生并结束 |

三个盲点合起来，就是现场那句抱怨。"设备指标都正常，但这条任务就是慢。"这句话多半就出在这里。

INT 的思路是换主语。让每一个经过的报文当记录员，把每一跳的现场写进它自己的包头。

### 0x02 元数据：每跳写什么

标准字段通常包括五项，加起来 20 到 30 字节。

| 字段 | 宽度 | 判读价值 |
|---|---|---|
| switch ID | 4 字节 | 定位到具体设备 |
| ingress port / egress port | 各 2 到 4 字节 | 还原实际路径，验证 ECMP 是否走偏 |
| hop latency | 4 字节 | 该跳停留时长，队列加转发 |
| queue occupancy | 4 字节 | 出口队列当时的占用水线 |
| egress TX utilization | 4 字节 | 出口链路当时的利用率 |
| timestamp | 8 字节 | 全局时钟对齐后的时刻，跨设备排序用 |

一条 8 跳的路径，元数据合计约 160 到 240 字节。这就是 INT 的第一项成本：**报文变大。**

用熟悉的东西类比一下。INT 相当于在 HTTP 请求头里逐层追加 `X-Forwarded-For` 与各段耗时。调用方拿到的响应带完整链路账本，不用再去查每个服务的监控面板。

区别在于包头空间更紧张。IP 头选项早就名存实亡，所以 INT 走的是自带的封装格式。

::: warning MTU 是第一个会咬人的地方

1500 字节 MTU 下，加上 INT 元数据很容易超限，触发分片或丢弃。分片对 RDMA 流量是灾难。

工程做法两条。一，在数据中心内部启用 9000 字节 jumbo frame，把余量留出来。二，给 INT 封装单独规划 MTU 预算，把"每跳 24 字节乘以最大跳数"提前算进设计，而不是上线后被动发现。
:::

### 0x03 三种范式：谁负责上报

| 范式 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **INT-MX / 报文携带** | 元数据全部写进报文头，跟到终点 | 终点能拿到完整路径，无需额外采集 | 报文膨胀最大，靠 MTU 扛 |
| **INT-XD / 导出上报** | 交换机把元数据打包成 telemetry report，从带外或 UDP 发给采集器 | 不改原始报文长度，上报可聚合 | 上报链路本身要能扛住采样量 |
| **postcard** | 每跳只在本地上报一行"我见过这个流" | 报文几乎零开销 | 关联靠流标识，跨设备拼接难度高 |

多数生产环境走 INT-XD 或 postcard。原因很直接。报文膨胀会影响业务，元数据只是运维数据，不该让业务流量买单。

IETF 把这一套标准化为 IOAM，它定义了 trace option 的封装方式与数据字段。厂商实现时会加私有字段，这也是后面那条坑的来源。

### 0x04 采样率：算一笔账再决定

全量 INT 不现实。1450 字节的报文加 200 字节元数据，带宽开销约 14%，再加上报头上报，成本翻倍。

所以硬件都带采样器。采样率走哈希，典型值 1:1024 到 1:4096。

```text
单口 400 Gb/s，1:2048 采样
→ 每秒约 24 万个采样报文（按 1500 字节均值估算）
→ 每个采样报文带 200 字节元数据 + 60 字节上报头
→ 上报流量约 62 MB/s，约占链路 0.12%
```

0.12% 看起来可以忽略。真正的压力在采集侧。单台设备 32 个端口，集群上千台设备，汇总起来是每秒几十万个 telemetry report。采样端的聚合与降采样必须提前设计。这笔账要在设计阶段算。

**采样率的选择标准只有一个：能不能抓到高频事件。** 一个持续 200 微秒的微突发，1:4096 采样可能整段错过。要抓它得靠采样器之外的机制，比如队列水线触发的快照。

### 0x05 与 gNMI 的分工

| 维度 | gNMI + OpenConfig | INT |
|---|---|---|
| 视角 | 端口、设备 | 流、路径、逐跳 |
| 粒度 | 周期采样，1 到 5 秒 | 事件驱动，报文级 |
| 覆盖 | 全设备全端口 | 仅被采样的报文所经路径 |
| 关联能力 | 弱，靠时间戳与拓扑推断 | 强，同一条流跨设备直接拼接 |
| 部署成本 | 低，软件即可 | 高，依赖芯片与镜像支持 |

两者不是替代关系。gNMI 负责"面"，告诉你全网哪些地方在冒烟。INT 负责"线"，告诉你这条流在哪一跳被卡住。

现场用法是级联。gNMI 告警指出问题端口，再用 INT 定位这个端口上的哪个流、哪一跳。

::: info 经验映射（IDC → AIDC）

这个分工和分布式链路追踪一模一样。Metrics 是聚合的、便宜的、覆盖面广的。Trace 是个体的、贵的、能定位到单次请求的。

会用 Jaeger 或 OpenTelemetry 的人没有学习成本。先看指标找到异常服务，再拉 trace 看那一跳。INT 就是网络层的 trace，交换机是 span。
:::

## 判读与实操

### 0x06 把 P99 拆成每跳

拿到一条 INT 记录，第一步看两个数：跳数、总时长。

```python
# int_parse.py — 玩具实现：按 24 字节一组的元数据解析
import struct

HOP = 24  # switch_id(4) + ports(4) + hop_latency_ns(4) + queue_depth(4) + tx_util(4) + pad(4)

def parse(payload: bytes):
    hops = []
    for off in range(0, len(payload) - HOP + 1, HOP):
        sid, ports, lat_ns, qdepth, tx_util, _ = struct.unpack_from("!IIIIII", payload, off)
        hops.append({
            "switch": f"sw-{sid:04x}",
            "ingress": ports >> 16,
            "egress": ports & 0xFFFF,
            "hop_us": lat_ns / 1000,
            "queue": qdepth,
            "tx_util_pct": tx_util / 10,
        })
    return hops

def worst(hops):
    return max(hops, key=lambda h: h["hop_us"])
```

判读顺序有讲究，看错顺序就会提前下结论。

1. **先看总时长与跳数。** 跳数异常多，说明 ECMP 走了非预期路径，先查拓扑与 hash。
2. **再看逐跳中位数。** 中位数平稳而 P99 高，说明是排队而非转发故障。
3. **然后看 ECN 标记与队列的对应关系。** 某一跳的 queue 高，而 tx_util 不到 60%，说明几股流在抢同一个出端口。问题在上游的负载分布，不在这一跳本身。
4. **最后对齐时间。** 用 timestamp 排序，把 PAUSE 上涨的时刻与 hop latency 抬升的时刻对上。

### 0x07 两个判断，别弄反

**hop latency 高不等于这一跳有问题。** 队列是在这一跳的出口排的，但把队列堆满的流量来自上游。先看出口，再怪上游。判读要看 tx_util 与 queue 的组合：出口利用率接近满、队列还堆着，这才是本跳的问题。

**INT 的记录是采样，不是全量。** 一条流在 5 分钟里只被采到 30 次。这 30 次说明当时的情况，不说明另外几百万个报文。用它看分布形状可以，用它算精确总量不行。

::: warning INT 在 RoCE 上的实现差异

RoCEv2 报文走 UDP 封装，INT 元数据的插入点没有统一标准。常见三条路线。

一是芯片原生支持在特定封装下做，多为自研或特定白盒。二是用 telemetry report 采样后上报。三是借用镜像与探针在旁路还原。

这三条路线拿到的数据保真度不同。第一条能拿到逐跳队列，第二条只能拿到采样点的快照，第三条最粗，常常只有端到端。

选型时要问清一件事：**你的芯片能把元数据插进业务报文，还是只能旁路导出。** 这个答案决定 INT 在你这里能做路径级归因，还是只能做抽样统计。
:::

## 经验映射

| 你已有的做法 | 在 INT 里的对应物 |
|---|---|
| 链路追踪的 trace id 与 span | 流标识加每跳元数据 |
| 采样率与尾延迟的取舍 | 哈希采样率的选择 |
| 日志的采样丢头问题 | telemetry report 上报端的丢弃 |
| APM 的瓶颈定位 | 逐跳 latency 分解 |
| 链路预算与协议开销 | INT 元数据对 MTU 与带宽的占用 |

迁移成本低。真正需要新的经验只有一条：**网络侧的元数据是硬件写的。** 写不写、写多少、写得准不准，都由芯片决定。这一层没有软件兜底，芯片决定上限。

### 0x08 实验入口：按固定步长解析，再逐跳归因

```bash
cd labs/07-int-path
make run     # 四个场景的逐跳判读 + 采样捕获率对照
make test    # 10 个单测，含截断载荷必须报错
```

四个场景对应四种归因：出口拥塞、上游争抢、转发面偏慢、健康。同一套元数据，把"利用率 × 队列 × 停留时长"三个量组合起来才分得开。

采样对照那张表是本实验的重点。**1:4096 下，一次 200 微秒的微突发有近一半概率一次都抓不到。** 这不是实现问题，是采样率的算术后果。

## 习题

**必答 Q1**：某次训练任务的 P99 时延从 1.2 毫秒涨到 9 毫秒，gNMI 显示全部端口 PFC 与 ECN 正常。给出用 INT 定位的操作序列。

::: details 参考答案与评分维度

第一步确认采集在跑。查采样率、上报量、上报端丢弃计数。上报数在事故期间掉到 0，问题就在采集侧。

第二步拉这段时间的 INT 记录，按流标识分组，找出受害流的那一组。

第三步把受害流的记录按 hop latency 排序，看是否集中在某一跳。同时看这一跳的 tx_util 与 queue：利用率不到 60% 而队列高，说明是多股流争抢，问题在上游分布。

第四步用 timestamp 对齐，找同一时刻其他流的记录，确认是否存在跨流的同步突发，也就是 incast 特征。

第五步回到 gNMI 核对这一跳的端口计数与 ECN 标记。两边不一致，说明其中一侧的数据有问题。

**评分维度**：先确认采集自身健康（必需）。按流分组再看逐跳（必需）。用 tx_util 与 queue 的组合做归因（必需）。提到两侧数据交叉验证（加分）。
:::

**必答 Q2**：给一个 200 台交换机的集群设计 INT 方案，写出采样率、上报通道、存储策略，并说明理由。

::: details 参考答案与评分维度

采样率 1:2048 起步，对抓漏的微突发场景再加队列水线触发的快照。理由是开销可控在千分之一量级，同时保留分布形状。

上报通道走独立的采集网络，不用业务链路。每台设备的上报流量按端口数 × 采样率 × 报文大小估算，上限按单设备 100 MB/s 预留。

存储分层。原始 INT 记录保留 3 到 7 天，因为数据量大且价值随时效衰减。逐跳时延的聚合百分位与队列水线保留 90 天，供基线对比。归档只留"受害流"的记录，也就是超过基线的那些。

再加一条：给采集侧做丢弃计数，并监控它。上报端一丢，INT 就成了随机抽样，结论会系统性偏乐观。

**评分维度**：采样率与理由匹配（必需）。上报通道独立（必需）。存储分层且给出保留期（必需）。提到采集侧丢弃监控（加分）。
:::

**自测 Q3**：INT-XD 与 postcard 都避免报文膨胀，两者在归因能力上差在哪。

::: details 参考答案与评分维度

INT-XD 由交换机把一条记录的完整元数据导出，同一次采样在单点就能拿到整条路径的字段，关联成本低。

postcard 每跳只上报自己那一行，需要靠流标识与时间窗在采集端拼接。拼接依赖时钟精度与流标识的唯一性，跨设备时钟漂移会让顺序错乱。

所以 postcard 的开销更小，归因链路更长，容错更差。

**评分维度**：说清两者在关联点上的差别（必需）。提到时钟与流标识的依赖（加分）。
:::

**自测 Q4**：为什么 INT 不能替代 gNMI 做全量监控。

::: details 参考答案与评分维度

覆盖面不同。INT 只覆盖被采样报文经过的路径，没流量经过的端口永远没有记录。而故障常常发生在"没有流量的那半边"，比如一条 rail 上的备用链路。

开销也不同。全量 INT 的带宽与采集端压力都不可接受。

所以两者的定位是级联：gNMI 做面，INT 做线。

**评分维度**：指出覆盖面的空白区（必需）。给出级联用法而不是并列比较（加分）。
:::

## 小结

这一讲可以压成一句话：**让每一个路过的报文当记录员，自己把账本带到终点。**

端口视角有三个天生看不全的地方。不知道是谁、不知道哪一跳、不知道当时。INT 换了主语，让报文自己记：switch ID、进出端口、停留时长、队列水线、出口利用率，每跳二十几字节。

上报方式有三种。全写进包头的膨胀最大，交换机导出的不改原报文，postcard 最省但拼接最费劲。生产环境多数走后两种，因为不该让业务流量替运维数据买单。

采样率是道算术题。1:2048 的开销在千分之一量级，看着无所谓，但 200 微秒的微突发在 1:4096 下有近一半概率抓不到。判读要看 tx_util 与 queue 的组合，hop latency 高不等于这一跳有问题。

::: tip 本课要点

**让每一个路过的报文当记录员，自己把账本带到终点。**

- 端口视角三盲点：**不知道是谁、哪一跳、当时**。INT 换主语，让报文当记录员
- 元数据五项：switch ID、进出端口、hop latency、queue depth、tx util，约 24 字节一跳
- 三种范式：**INT-MX 报文携带**、**INT-XD 导出上报**、**postcard 本地上报**
- 采样率按"能不能抓到高频事件"定，1:1024 到 1:4096 是常见区间
- 判读看 **tx_util 与 queue 的组合**，hop latency 高不代表本跳有问题
- 一条坑：INT 能不能插进业务报文，取决于芯片。旁路导出的方案拿不到逐跳队列
:::

留一个思考题：如果微突发只持续 50 微秒，你会加采样率，还是换一个根本不靠采样的机制。
