---

一个真实场景：训练任务的 P99 时延从 1.2 毫秒涨到 9 毫秒，训练侧报慢。拉 gNMI 数据一看，路径上五台交换机、十个端口，PFC 与 ECN 计数全在正常范围，队列水线也没有明显抬升。

设备指标正常，任务就是慢。端口视角答不了这个问题：**一条流的问题，被摊到了全网几十个端口上。**

INT（In-band Network Telemetry，带内遥测）换了一个记录者：让经过的报文自己写一份逐跳记录，带到终点再读出来。路径从推断变成实测。

## 交付

- 端口视角遥测的三个盲点，各自对应 INT 的哪个字段
- INT 元数据的字段构成、每跳字节数与最大跳数预算
- INT-MX、INT-XD、postcard 三种上报范式，各自适合什么芯片能力
- 采样率与微突发捕获率的定量关系
- 拿到一条 INT 记录后，怎么把总时延拆到具体一跳并给出归因

## 端口视角的三个盲点

| 盲点 | 具体表现 | 后果 |
|---|---|---|
| 不知道是谁 | 端口的队列水线是全流聚合值 | 8 个任务混跑，看不出谁把队列顶满 |
| 不知道哪一跳 | 端到端时延只有一个总数 | 五台设备里定位不到具体一台 |
| 不知道当时 | 5 秒采样点之外的瞬时尖峰全部丢失 | 微突发在两次采样之间发生并结束 |

第 13 讲要处理的光模块劣化，本质也是被这三条挡住：单条链路只占一台 64 端口交换机的 1.5%，聚合指标一摊，什么都看不见。

## 每跳写什么

标准字段五项，加时间戳共 28 字节，按 8 字节对齐算 32 字节。实验里的实现省掉时间戳，取 24 字节一组：

| 字段 | 宽度 | 判读价值 |
|---|---|---|
| switch ID | 4 字节 | 定位到具体设备 |
| ingress / egress port | 各 2 到 4 字节 | 还原实际路径，验证 ECMP 有没有走偏 |
| hop latency | 4 字节 | 该跳停留时长，队列加转发 |
| queue occupancy | 4 字节 | 出口队列当时的占用水线 |
| egress TX utilization | 4 字节 | 出口链路当时的利用率 |
| timestamp | 8 字节 | 全局时钟对齐后的时刻，跨设备排序用 |

一条 8 跳的路径，元数据 220 到 260 字节。这就是 INT 的第一项成本：报文变大。

IP 头选项这条路早就不通，运营商与防火墙对 IP option 的处理五花八门，多数直接丢。所以 INT 自带封装，常见承载是 Geneve、NSH，或者 UDP 封装下的自定义头。承载方式决定 MTU 预算，也就决定了能插几跳。

1500 字节 MTU 下加 200 字节元数据，很容易顶到上限，触发分片。分片对 RDMA 流量是事故，一个 4000 字节的 RDMA 报文被切成三片，任一片丢了整条消息重传。工程上两条路：数据中心内部统一开 9000 字节 jumbo frame，把余量留出来；或者把「每跳 24 字节乘最大跳数」提前算进设计，最大跳数取舍在方案阶段定死，不要上线以后再发现。

## 谁上报

| 范式 | 做法 | 优点 | 代价 |
|---|---|---|---|
| INT-MX（报文携带） | 元数据全写进报文头，跟到终点 | 终点拿到完整逐跳路径，不需要额外采集链路 | 报文膨胀最大，靠 MTU 与 jumbo frame 硬扛 |
| INT-XD（导出上报） | 交换机把元数据打包成 telemetry report，走带外或 UDP 发给采集器 | 原始报文长度不变，上报可聚合、可压缩 | 上报链路要扛住采样量 |
| postcard | 每跳只在本地上报一行「我见过这条流」 | 报文几乎零开销 | 关联靠流标识加时间窗拼接，跨设备时难度高 |

生产环境多数走 INT-XD 或 postcard，理由很直接：报文膨胀影响业务，元数据只是运维数据，不该让业务流量替它占带宽。

IETF 把这一套标准化成 IOAM，在 RFC 9197 里定义了 trace option 的字段与封装语义。厂商实现会加私有字段，这就是为什么不问清芯片能力就不能排方案。

## 采样率是算术题

全量 INT 不现实。1450 字节的报文加 200 字节元数据，带宽开销 14%，再加上独立的上报头，成本接近翻倍。

所以硬件都带采样器，哈希选包，典型值 1:1024 到 1:4096。

```text
单口 400 Gb/s，1:2048 采样
→ 每秒约 24 万个采样报文（按 1500 字节均值估算）
→ 每个报文带 200 字节元数据 + 60 字节上报头
→ 上报流量约 62 MB/s，约占链路 0.12%
```

0.12% 看着可以忽略，真正的压力在采集侧：单台设备 32 个端口，集群上千台设备，汇总起来每秒几十万个 telemetry report。聚合与降采样必须提前设计。

采样率的选择标准只有一条：能不能抓到高频事件。`labs/07-int-path` 把这件事量了一遍：

```bash
cd labs/07-int-path
make run
```

假设一条流 24 万个报文/秒，一次微突发持续 200 微秒，也就是 48 个报文：

```text
采样      突发报文   解析捕获   实测捕获   一次突发全错过
1:256       48       17.1%      17.3%        0.0%
1:1024      48        4.6%       4.8%        6.0%
1:4096      48        1.2%       1.1%       49.5%
元数据开销：5 跳 120 字节，相对 1450 字节报文 8.3%
```

1:4096 下，一次 200 微秒的微突发有大约一半的概率一个报文都采不到。采样率决定的就是这件事，往上翻只是把一半的概率变成五分之一。微突发靠另一套机制抓：队列水线越线触发快照、直方图、或者交换机侧的丢包与暂停事件流。

## 与 gNMI 的分工

| 维度 | gNMI + OpenConfig | INT |
|---|---|---|
| 视角 | 端口、设备 | 流、路径、逐跳 |
| 粒度 | 周期采样，0.1 到 5 秒 | 事件驱动，报文级 |
| 覆盖 | 全设备全端口 | 仅被采样报文经过的路径 |
| 关联能力 | 弱，靠时间戳与拓扑推断 | 强，同一条流跨设备直接拼接 |
| 部署成本 | 低，软件即可 | 高，依赖芯片与镜像支持 |

两者是级联关系。gNMI 负责面，告诉你全网哪些地方在冒烟；INT 负责线，告诉你这条流在哪一跳被卡住。现场用法是 gNMI 告警指出问题端口，再用 INT 定位这个端口上的哪条流、哪一跳。

INT 替代不了 gNMI 的原因在覆盖面。没有流量经过的端口永远没有 INT 记录，而故障常常发生在没流量的那半边，比如某条 rail 上的备用链路。

## 经验映射

| 你已有的做法 | 在 INT 里的对应物 |
|---|---|
| 链路追踪的 trace id 与 span | 流标识加每跳元数据 |
| 采样率与尾延迟的取舍 | 哈希采样率的选择 |
| 日志采样丢头 | telemetry report 上报端的丢弃 |
| APM 的瓶颈定位 | 逐跳 latency 分解 |
| 链路预算与协议开销 | INT 元数据对 MTU 与带宽的占用 |

分布式链路追踪那一套在这里直接可用：Metrics 是聚合的、便宜的、覆盖面广的，Trace 是个体的、贵的、能定位到单次请求的。先看指标筛出异常服务，再拉 trace 看那一跳，网络侧的顺序一模一样，交换机是 span。

要新学的东西只有一条：**网络侧的元数据由硬件写**。写不写、写多少、写得准不准，取决于芯片。这一层没有软件兜底。

芯片的差异在 RoCE 上尤其明显。RoCEv2 报文走 UDP 封装，元数据的插入点没有统一标准，常见三条路线：芯片原生支持在特定封装下逐跳插入，多为自研或特定白盒；只支持 telemetry report 采样上报；或者干脆靠镜像与旁路探针还原。第一条能拿到逐跳队列，第二条只能拿到采样点快照，第三条最粗，常常只有端到端。选型时要问清一件事：**你的芯片能把元数据插进业务报文，还是只能旁路导出。**

## 判读与实操

`labs/07-int-path` 用四个场景把四种归因各摆了一遍：

```bash
cd labs/07-int-path
make run     # 四个场景的逐跳判读 + 采样捕获率对照
make test    # 10 个单测，含截断载荷必须报错
```

```text
定位到第 3 跳（sw-003f）：上游争抢
  场景 upstream     全程   31.4 µs
  #   设备       入    出        停留(µs)    队列KB   利用%   占比   归因
   1  sw-0011  1    8           0.8      12    42.0   2.5%  ok
   2  sw-002a  3    11          0.9      18    51.0   2.9%  ok
  *3  sw-003f  7    2          28.0     640    55.0  89.1%  上游争抢
   4  sw-004c  5    13          0.9      22    55.0   3.0%  ok
   5  sw-005d  9    4           0.8      15    46.0   2.5%  ok
```

第 3 跳的队列堆了 640 KB，出口利用率只有 55%。队列高、出口不满，说明几股流在抢同一个出端口，问题在上游的负载分布，不在这台交换机。同一个停留时长，队列与利用率换一组组合，归因就变成别的：

| 停留时长 | 队列 | 出口利用率 | 归因 |
|---|---|---|---|
| 高 | 高 | 接近打满 | 本跳出口拥塞 |
| 高 | 高 | 不满 | 上游争抢，几股流抢同一出口 |
| 高 | 低 | 低 | 转发面偏慢（查表、ACL、微码） |
| 低 | 低 | 低 | 健康 |

表里的高与低都是相对本路径其他跳说的：同一条记录内部横向比，绝对阈值只作参考。

判读顺序：

1. 先看总时长与跳数。跳数异常多，说明 ECMP 走了非预期路径，先查拓扑与哈希。
2. 再看逐跳中位数。中位数平稳而 P99 高，是排队而非转发故障。
3. 然后看每一跳的队列与利用率组合，按上表归因。
4. 最后对齐时间戳，把 PAUSE 上涨的时刻与 hop latency 抬升的时刻对上。

两个容易弄反的判断。**hop latency 高不等于这一跳有问题**：队列在这一跳的出口排，但把队列堆满的流量来自上游，出口利用率接近打满、队列还堆着，才是本跳的责任。**INT 记录是采样，不是全量**：一条流五分钟里被采到 30 次，这 30 次说明当时的情况，不说明另外几百万个报文，用它看分布形状可以，用它算精确总量不行。

要自己解析时，按固定步长切元数据就够了：

```python
# int_parse.py — 按 24 字节一组的元数据解析
import struct

HOP = 24  # switch_id(4) + ports(4) + hop_latency_ns(4) + queue_depth(4) + tx_util(4) + pad(4)

def parse(payload: bytes):
    hops = []
    for off in range(0, len(payload) - HOP + 1, HOP):
        sid, ports, lat_ns, qdepth, tx_util, _ = struct.unpack_from("!IIIIII", payload, off)
        hops.append({
            "switch": f"sw-{sid:04x}",
            "ingress": ports >> 16,
            "egress": ports & 0xFFFF,
            "hop_us": lat_ns / 1000,
            "queue": qdepth,
            "tx_util_pct": tx_util / 10,
        })
    return hops
```

真实的坑在载荷校验：`len(payload)` 不是 24 的整数倍时直接报错，不要按整数截断后读出一堆垃圾字段。实验里有一个单测专门管这条。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：某次训练任务的 P99 时延从 1.2 毫秒涨到 9 毫秒，gNMI 显示全部端口 PFC 与 ECN 正常。给出用 INT 定位的操作序列。

::: details 参考答案与评分维度

1. 先确认采集自己在跑。查采样率、上报量、上报端丢弃计数。上报数在事故期间掉到 0，问题就在采集侧。
2. 拉这段时间的 INT 记录，按流标识分组，找出受害流那一组。
3. 把受害流按 hop latency 排序，看是否集中在某一跳。同时看这一跳的队列与利用率：队列高、利用率不到 60%，说明多股流争抢，问题在上游分布。
4. 用时间戳对齐，找同一时刻其他流的记录，确认是否存在跨流同步突发，也就是 incast 特征。
5. 回 gNMI 核对这一跳的端口计数与 ECN 标记。两边不一致，说明其中一侧的数据有问题。

**评分维度**：先确认采集自身健康（必需）。按流分组再看逐跳（必需）。用队列与利用率的组合归因（必需）。两侧数据交叉验证（加分）。

:::

**必答 Q2**：给一个 200 台交换机的集群设计 INT 方案，写出采样率、上报通道、存储策略与理由。

::: details 参考答案与评分维度

采样率 1:2048 起步，开销控制在千分之一量级，同时保留分布形状。抓不准的微突发另配队列水线触发的快照。

上报走独立采集网络，不占业务链路。单设备上报上限按端口数 × 采样率 × 报文大小估，200 台设备按每台 100 MB/s 预留。

存储分层。原始 INT 记录留 3 到 7 天，数据量大、价值随时效衰减。逐跳时延的百分位与队列水线聚合留 90 天，供基线对比。归档只留超过基线的「受害流」记录。

再加一条：采集侧必须有丢弃计数并进监控。上报端一丢，INT 就退化成随机抽样，结论会系统性偏乐观。

**评分维度**：采样率与理由匹配（必需）。上报通道独立（必需）。存储分层并给出保留期（必需）。采集侧丢弃监控（加分）。

:::

**自测 Q3**：INT-XD 与 postcard 都不改报文长度，两者在归因能力上差在哪？

::: details 参考答案与评分维度

INT-XD 由交换机导出一条完整记录，同一次采样在单点就能拿到整条路径的字段，关联成本低。

postcard 每跳只上报自己那一行，得靠流标识与时间窗在采集端拼接。拼接依赖时钟精度与流标识唯一性，跨设备时钟漂移会让顺序错乱，缺一跳就断链。

所以 postcard 开销更小、归因链路更长、容错更差。

**评分维度**：说清两者在关联点上的差别（必需）。提到时钟与流标识的依赖（加分）。

:::

**自测 Q4**：一条路径的 INT 记录显示第 4 跳 hop latency 是其他跳的 20 倍，出口利用率 98%，队列 700 KB。归因是什么？如果出口利用率 50%，归因又是什么？

::: details 参考答案与评分维度

第一种是本跳出口拥塞。出口接近打满，队列堆着的报文发不出去，停留时长主要花在排队上，处置方向是分流或扩容。

第二种是上游争抢或本跳转发面偏慢，要再区分。队列高而出口不满，是多股流抢同一出口，往上游查谁在超发；队列低而停留长，才是本跳转发面慢，查 ACL、查表、微码。

**评分维度**：两种情况分开答（必需）。第二种进一步区分（加分）。

:::

## 小结

端口视角有三个天生看不全的地方：不知道是谁、不知道哪一跳、不知道当时。一条流的时延被摊到几十个端口上，所有指标都正常，任务就是慢。

INT 换了记录者。switch ID、进出端口、停留时长、队列水线、出口利用率，每跳二十几字节，跟着报文走到终点。

上报有三种。写进包头的膨胀最大，交换机导出的不动原报文，postcard 最省但拼接最费劲。生产环境多数走后两种，元数据不该占业务带宽。

采样率是一道算术题。1:2048 的开销在千分之一量级，看着无所谓，但 200 微秒的微突发在 1:4096 下有近一半概率一个报文都抓不到。判读要看队列与利用率的组合，hop latency 高不代表这一跳有问题。

::: tip 本课要点

**一条流的问题，端口视角答不了。**

- 端口视角三盲点：**不知道是谁、哪一跳、当时**。INT 让报文自己写逐跳记录
- 元数据五项加时间戳：switch ID、进出端口、hop latency、queue depth、tx util，24 到 32 字节一跳，8 跳 190 到 260 字节
- 三种范式：**INT-MX 报文携带、INT-XD 导出上报、postcard 本地上报**，生产走后者居多
- 采样率按「能不能抓到高频事件」定。1:4096 下 200 微秒微突发约一半概率全错过
- 判读看**队列与利用率的组合**：队列高加出口满＝本跳拥塞，队列高加出口不满＝上游争抢，队列低加停留长＝转发面慢
- INT 能不能插进业务报文，取决于芯片。旁路导出的方案拿不到逐跳队列

:::

留一个思考题：微突发只持续 50 微秒时，你会把采样率翻八倍，还是换成队列水线触发的快照，为什么。
