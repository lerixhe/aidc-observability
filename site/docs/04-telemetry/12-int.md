上一讲我们把数据从设备上取了出来。gNMI 能告诉你每个端口每秒丢了多少包、队列堆到多高、pause 帧发了几千次，一台交换机身上该报的九块东西都能订阅上。但是它回答不了另一个问题：**这条流到底卡在哪一跳。**

现场的样子是这样。训练任务的 P99 时延从 1.2 毫秒涨到 9 毫秒，训练侧报慢，拉 gNMI 数据一看，路径上五台交换机、十个端口，PFC 与 ECN 计数全在正常范围，队列水线也没有明显抬升。

设备指标正常，任务就是慢。你会想到把采样密一点，从 5 秒改成 100 毫秒，反复看了半天，所有端口的曲线都在正常区间里躺着。你又会想到把阈值调低一点，结果全网几百个端口一起告警，什么也定位不了。

端口视角给出的回答是「整条路径都健康」，可这条流确实慢了七八倍。问题出在视角上。端口是设备的一个面，流是穿过去的一条线，一条流慢，摊到每个端口上只是很小的一点增量。**一条流的问题，被摊到了全网几十个端口上。**

这时，INT（In-band Network Telemetry，带内遥测）闪亮登场了，它换了一个记录者：让经过的报文自己写一份逐跳记录，带到终点再读出来，路径从推断变成实测。

## 交付

- 端口视角遥测的三个盲点，各自对应 INT 的哪个字段
- INT 元数据的字段构成、每跳字节数与最大跳数预算
- INT-MX、INT-XD、postcard 三种上报范式，各自适合什么芯片能力
- 采样率与微突发捕获率的定量关系
- 拿到一条 INT 记录后，怎么把总时延拆到具体一跳并给出归因

## 端口视角的三个盲点

| 盲点 | 具体表现 | 后果 |
|---|---|---|
| 不知道是谁 | 端口的队列水线是全流聚合值 | 8 个任务混跑，看不出谁把队列顶满 |
| 不知道哪一跳 | 端到端时延只有一个总数 | 五台设备里定位不到具体一台 |
| 不知道当时 | 5 秒采样点之外的瞬时尖峰全部丢失 | 微突发在两次采样之间发生并结束 |

第 13 讲要处理的光模块劣化，本质也是被这三条挡住：单条链路只占一台 64 端口交换机的 1.5%，聚合指标一摊，什么都看不见。

## INT 是个什么记录者

INT 可以理解成一份随报文走的行程单。报文进第一台交换机，芯片在它头上记一笔：我是谁、你从哪个口进来、从哪个口出去、在这儿待了多少微秒、出口队列当时有多满。下一跳接着记，一路记到终点，采集端把这份行程单读出来，一条路径的全部停留时间就有了。

它不是全量的，它是采样的，这一点决定了怎么读它。

**当 INT 说某一跳慢时，这一跳一定慢；当它说这一跳正常时，可能只是这一段压根没被采到。** 打个比方，当它说这条流在你家三楼停了两百微秒，那是真停过；当它说这一路都很顺畅，你得先看看这一路有没有被抽到过。

这句话是这一讲的总纲。后面两节讲采样率，算的就是「抽到过」的概率；判读那一节讲归因，前提就是你手上那条记录是真的走完了全程。

## 三种上报范式

元数据写进哪里，各家芯片的做法不一样。按写法分三档：

| 范式 | 做法 | 优点 | 代价 |
|---|---|---|---|
| INT-MX（报文携带） | 元数据全写进报文头，跟到终点 | 终点拿到完整逐跳路径，不需要额外采集链路 | 报文膨胀最大，靠 MTU 与 jumbo frame 硬扛 |
| INT-XD（导出上报） | 交换机把元数据打包成 telemetry report，走带外或 UDP 发给采集器 | 原始报文长度不变，上报可聚合、可压缩 | 上报链路要扛住采样量 |
| postcard | 每跳只在本地上报一行「我见过这条流」 | 报文几乎零开销 | 关联靠流标识加时间窗拼接，跨设备时难度高 |

生产环境多数走 INT-XD 或 postcard，理由很直接：报文膨胀影响业务，元数据只是运维数据，不该让业务流量替它占带宽。

IETF 把这一套标准化成 IOAM，在 RFC 9197 里定义了 trace option 的字段与封装语义。厂商实现会加私有字段，这就是为什么不问清芯片能力就不能排方案。

## 注意事项

原理放到下一节，先把三件事说在前面。

跳数预算估小了，关键时刻插不进去。元数据是逐跳累加的，报文从第一跳背到最后，所以设计阶段就要定死「最多几跳」。定 4 跳，结果某条流绕了 6 跳，芯片只能在第 5 跳放弃记录，你手上拿到的是一份断在中间的行程单，前面四跳全对，最后两跳没有，事故恰好出在最后两跳。

MTU 没留余量，会把业务打崩。1500 字节加 200 字节元数据，总长顶到 1700，触发分片。分片对 RDMA 流量是事故：一个 4000 字节的 RDMA 报文被切成三片，任一片丢了，整条消息重传。省下的那点带宽，抵不上一次重传的代价。

只估了采集端，没估上报端的丢弃，这是最常见的一个。上报通道和业务流量抢带宽的时候，交换机先丢的一定是 telemetry report，因为它是低优先级。你的 INT 数据在事故期间掉一半，看着像全网突然健康了，实际上是观测先瞎了。上报端的丢弃计数必须单独埋一个，进监控。

## 每跳写什么

标准字段五项，加时间戳共 28 字节，按 8 字节对齐算 32 字节。实验里的实现省掉时间戳，取 24 字节一组：

| 字段 | 宽度 | 判读价值 |
|---|---|---|
| switch ID | 4 字节 | 定位到具体设备 |
| ingress / egress port | 各 2 到 4 字节 | 还原实际路径，验证 ECMP 有没有走偏 |
| hop latency | 4 字节 | 该跳停留时长，队列加转发 |
| queue occupancy | 4 字节 | 出口队列当时的占用水线 |
| egress TX utilization | 4 字节 | 出口链路当时的利用率 |
| timestamp | 8 字节 | 全局时钟对齐后的时刻，跨设备排序用 |

一条 8 跳的路径，元数据 220 到 260 字节。这就是 INT 的第一项成本：报文变大。

IP 头选项这条路早就不通，运营商与防火墙对 IP option 的处理五花八门，多数直接丢。所以 INT 自带封装，常见承载是 Geneve、NSH，或者 UDP 封装下的自定义头。承载方式决定 MTU 预算，也就决定了能插几跳。数据中心内部统一开 9000 字节 jumbo frame，余量就出来了；1400 字节的小 MTU 环境，八跳就是上限。

实验里用的是定长编码，每跳固定 24 字节，按大端排列：

```text
偏移   字段            宽度
 0    switch id        4
 4    ingress port     2
 6    egress port      2
 8    hop latency      4   （纳秒）
12    queue depth      4   （KB）
16    tx util          4   （基点，10000 = 100%）
20    reserved         4   （时间戳低位，本实验未使用）
```

定长换来的是零歧义解析：不需要长度前缀，也不会因为某个可选字段缺失而整体错位。代价是字段宽度写死，扩展要改版本号。真实实现里这叫「定长 trace option」。

要自己解析，按固定步长切就够了：

```python
# int_parse.py — 按 24 字节一组的元数据解析
import struct

HOP = 24  # switch_id(4) + ports(4) + hop_latency_ns(4) + queue_depth(4) + tx_util(4) + pad(4)

def parse(payload: bytes):
    hops = []
    for off in range(0, len(payload) - HOP + 1, HOP):
        sid, ports, lat_ns, qdepth, tx_util, _ = struct.unpack_from("!IIIIII", payload, off)
        hops.append({
            "switch": f"sw-{sid:04x}",
            "ingress": ports >> 16,
            "egress": ports & 0xFFFF,
            "hop_us": lat_ns / 1000,
            "queue": qdepth,
            "tx_util_pct": tx_util / 10,
        })
    return hops
```

真实的坑在载荷校验：`len(payload)` 不是 24 的整数倍时直接报错，不要按整数截断后读出一堆垃圾字段。实验里有一个单测专门管这条，叫 `TestDecodeRejectsTruncated`。

这条不啰嗦的原因在于它不报错。`len = 25` 的载荷按「整数截断」写，最后一跳会读出 1 个真字节加 23 个零，产出一份看起来完全正常的记录：switch id 是 0、队列 0 KB、利用率 0%。**事故复盘时给你一份假记录，比没有记录更坏。**

## 空间占用估计

元数据的开销可以算得很干净。一条报文背 h 跳，每跳 24 字节，元数据是 24h 字节，相对报文本身的占比是：

```text
开销 = 24h / (1450 + 24h)     # 1450 字节是常见的以太网载荷均值
```

h 取几个值代进去：

1. h = 1，开销 1.6%，可以忽略
2. h = 5，开销 120 / 1570 = 7.6%，实验里按 1450 为分母算成 8.3%
3. h = 8，开销 192 / 1642 = 11.7%
4. h = 16，开销 384 / 1834 = 21%，长路径的代价开始难看

上面的数字是「每个报文都插」的全量口径。真实部署没有全量 INT，都是采样，所以实际开销要再乘采样率，这一乘就是下一节要算的东西。

回到那个常见的误解：既然每跳才 24 字节，多插几跳没关系？错在分母。RDMA 的小消息居多，一次 AllReduce 里 512 字节的报文很常见，这时候 24 字节是它的 4.7%，八跳就是 37%，业务侧直接看得到带宽下降。**开销要按实际报文长度算，不能按 1500 字节的名义 MTU 算。**

## 采样率是算术题

全量 INT 不现实，硬件都带采样器，哈希选包，典型值 1:1024 到 1:4096。

开销先算一遍。单台 32 端口 400 Gb/s 交换机，线速、1500 字节均值，整机包速率约 10.7 亿包每秒，采 1:2048 就是每秒约 52 万条记录。每条记录带 200 字节元数据加 60 字节上报头，一共 260 字节：

```text
上报流量 = 520,000 × 260 B  ≈ 135 MB/s
占整机带宽 = 135 MB/s ÷ 12.8 Tb/s ≈ 0.008%
```

千分之一都不到，看着可以忽略。真正的压力在采集侧：上千台这样的设备，汇总起来每秒几亿条 telemetry report，聚合物与降采样必须提前设计，这一笔账在第 14 讲算。

采样率的选择标准只有一条：能不能抓到高频事件。`labs/07-int-path` 把这件事量了一遍：

```bash
cd labs/07-int-path
make run
```

假设一条流 24 万个报文/秒，一次微突发持续 200 微秒，也就是 48 个报文：

```text
采样      突发报文   解析捕获   实测捕获   连续 60 次全错过
1:256       48       17.1%      17.3%        0.0%
1:1024      48        4.6%       4.8%        6.0%
1:4096      48        1.2%       1.1%       49.5%
元数据开销：5 跳 120 字节，相对 1450 字节报文 8.3%
```

这张表的值都是算得出来的，一条公式就够。哈希采样近似独立同分布，48 个报文每个被采到的概率都是 1/k，一次突发里**至少采到一个**的概率是：

```text
p = 1 - (1 - 1/k)^m      # m 是突发里的报文数，k 是采样分母
```

k = 4096、m = 48 代进去，p = 1 - (4095/4096)^48 ≈ 1.17%，表里那 1.2% 就是这么来的。连续 n 次突发一次都没采到的概率是 (1 - p)^n，n = 60 时 (0.9883)^60 ≈ 49.5%，这就是最后一列那个「一半」。

所以 1:4096 下，一次 200 微秒的微突发有大约一半的概率，一分钟里 60 次，一次都抓不到。这是采样率的算术后果，不是实现得不好。

明白了这张表，你也许会问，这么低的捕获率，有没有办法提高一点？答案是有的，两条路。

**第一条，把采样率往上翻。** 1:4096 提到 1:256，捕获率从 1.2% 涨到 17.1%，代价是上报量涨 16 倍，开销从 0.008% 涨到 0.13%。往上翻只是把「一半抓不到」变成「八成能抓到」，永远到不了 100%。

**第二条，把事件的持续时长放宽。** 实验里第三个可以自己改的参数就是这个：

```bash
go run . -burst-us 2000
```

突发从 200 微秒拉到 2000 微秒，报文数从 48 变成 480，同样 1:4096 的捕获率从 1.2% 涨到 11%，从「基本抓不到」变成「大概能抓到」。这说明一件事：**采样率够不够，取决于你要抓多短的事件，不取决于某个推荐值。**

真遇到 50 微秒级的微突发，正确做法是换机制，不是加采样率：队列水线越线触发快照、直方图、或者交换机侧的丢包与暂停事件流。拿采样去抓 50 微秒的事，翻八倍采样率也只是把概率从 1% 变成 8%。

## 芯片不支持的那批设备

INT 不是软件功能，是芯片功能。手上那批设备不支持，也有替代路线，只是每条都有代价。

1. **只支持 telemetry report 采样上报。** 能拿到采样点快照，拿不到逐跳队列，属于「知道有人在慢，不知道慢在哪一跳」。
2. **镜像加旁路探针。** 交换机把指定端口的流量镜像到探针，探针自己解析。这能拿到报文级证据，代价是镜像本身占端口带宽，探针要按 400G 的量级配置，成本比开 INT 高得多。
3. **硬件探针或智能网卡在端侧打时间戳。** 只能给出端到端，一跳都拆不出来，但至少能回答「是不是网络慢」。
4. **换设备。** 听着粗暴，但在新建集群里，这常常是最省事的答案：选型阶段把 INT 能力写进需求，别等上线以后发现只能镜像。

要问清的问题只有一个：**你的芯片能把元数据插进业务报文，还是只能旁路导出。** 前者能拿到逐跳队列，后者只能拿到采样点快照。

## 与 gNMI 的分工

| 维度 | gNMI + OpenConfig | INT |
|---|---|---|
| 视角 | 端口、设备 | 流、路径、逐跳 |
| 粒度 | 周期采样，0.1 到 5 秒 | 事件驱动，报文级 |
| 覆盖 | 全设备全端口 | 仅被采样报文经过的路径 |
| 关联能力 | 弱，靠时间戳与拓扑推断 | 强，同一条流跨设备直接拼接 |
| 部署成本 | 低，软件即可 | 高，依赖芯片与镜像支持 |

两者是级联关系。gNMI 负责面，告诉你全网哪些地方在冒烟；INT 负责线，告诉你这条流在哪一跳被卡住。现场用法是 gNMI 告警指出问题端口，再用 INT 定位这个端口上的哪条流、哪一跳。

INT 替代不了 gNMI 的原因在覆盖面。没有流量经过的端口永远没有 INT 记录，而故障常常发生在没流量的那半边，比如某条 rail 上的备用链路。

## INT 还能回答什么

除了「这条流卡在哪一跳」，这份逐跳记录还能顺手回答几个问题，现场用得上：

- **ECMP 到底走没走偏。** 进出端口一串下来就是实际路径，和拓扑算出来的预期路径一比，哈希是不是极化一目了然，第 04b 讲那个「八条同五元组」的实验，真机上就是用 INT 验的。
- **队列堆在哪一级。** 队列水线在每一跳都有，螺旋上升还是单点顶满，形态不同，处置方向完全不同。
- **PFC 是不是真的传导了。** 把 INT 的时间戳和 pause 帧的收发时刻对齐，能看出反压走了几跳、在哪一跳断掉。
- **路径 MTU 与黑洞。** 元数据能插进去就说明这条路上每跳都认得这个封装，插不进去的那一跳，就是问题所在。

这几条的共同点是：它们都是「单条流」的问题，端口视角永远答不了。

| APM 的瓶颈定位 | 逐跳 latency 分解 |
| 链路预算与协议开销 | INT 元数据对 MTU 与带宽的占用 |

分布式链路追踪那一套在这里直接可用：Metrics 是聚合的、便宜的、覆盖面广的，Trace 是个体的、贵的、能定位到单次请求的。先看指标筛出异常服务，再拉 trace 看那一跳，网络侧的顺序一模一样，交换机是 span。

要新学的东西只有一条：**网络侧的元数据由硬件写**。写不写、写多少、写得准不准，取决于芯片。这一层没有软件兜底。

芯片的差异在 RoCE 上尤其明显。RoCEv2 报文走 UDP 封装，元数据的插入点没有统一标准，常见三条路线：芯片原生支持在特定封装下逐跳插入，多为自研或特定白盒；只支持 telemetry report 采样上报；或者干脆靠镜像与旁路探针还原。选型时把这三条问清楚，比问「支持不支持 INT」有用得多。

## 判读与实操

`labs/07-int-path` 用四个场景把四种归因各摆了一遍：

```bash
cd labs/07-int-path
make run     # 四个场景的逐跳判读 + 采样捕获率对照
make test    # 10 个单测，含截断载荷必须报错
```

同样是第 3 跳吃掉九成时延，队列与利用率换一组组合，归因就变成别的：

| 停留时长 | 队列 | 出口利用率 | 归因 |
|---|---|---|---|
| 高 | 高 | 接近打满 | 本跳出口拥塞 |
| 高 | 高 | 不满 | 上游争抢，几股流抢同一出口 |
| 高 | 低 | 低 | 转发面偏慢（查表、ACL、微码） |
| 低 | 低 | 低 | 健康 |

表里的高与低都是相对本路径其他跳说的：同一条记录内部横向比，绝对阈值只作参考。实验里的绝对阈值是出口利用率 85%、队列 500 KB、停留 20 微秒，这三个数是模型的设定，真机上要按端口缓冲和业务基线重新定。

判读顺序：

1. 先看总时长与跳数。跳数异常多，说明 ECMP 走了非预期路径，先查拓扑与哈希。
2. 再看逐跳中位数。中位数平稳而 P99 高，是排队而非转发故障。
3. 然后看每一跳的队列与利用率组合，按上表归因。
4. 最后对齐时间戳，把 PAUSE 上涨的时刻与 hop latency 抬升的时刻对上。

两个容易弄反的判断。**hop latency 高不等于这一跳有问题**：队列在这一跳的出口排，但把队列堆满的流量来自上游，出口利用率接近打满、队列还堆着，才是本跳的责任。**INT 记录是采样，不是全量**：一条流五分钟里被采到 30 次，这 30 次说明当时的情况，不说明另外几百万个报文，用它看分布形状可以，用它算精确总量不行。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：某次训练任务的 P99 时延从 1.2 毫秒涨到 9 毫秒，gNMI 显示全部端口 PFC 与 ECN 正常。给出用 INT 定位的操作序列。

::: details 参考答案与评分维度

1. 先确认采集自己在跑。查采样率、上报量、上报端丢弃计数。上报数在事故期间掉到 0，问题就在采集侧。
2. 拉这段时间的 INT 记录，按流标识分组，找出受害流那一组。
3. 把受害流按 hop latency 排序，看是否集中在某一跳。同时看这一跳的队列与利用率：队列高、利用率不到 60%，说明多股流争抢，问题在上游分布。
4. 用时间戳对齐，找同一时刻其他流的记录，确认是否存在跨流同步突发，也就是 incast 特征。
5. 回 gNMI 核对这一跳的端口计数与 ECN 标记。两边不一致，说明其中一侧的数据有问题。

**评分维度**：先确认采集自身健康（必需）。按流分组再看逐跳（必需）。用队列与利用率的组合归因（必需）。两侧数据交叉验证（加分）。

:::

**必答 Q2**：给一个 200 台交换机的集群设计 INT 方案，写出采样率、上报通道、存储策略与理由。

::: details 参考答案与评分维度

采样率 1:2048 起步，单台 32 端口 400G 设备不到 1% 的带宽开销，同时保留分布形状。抓不准的微突发另配队列水线触发的快照。

上报走独立采集网络，不占业务链路。单设备上报上限按端口数 × 采样率 × 报文大小估，这个量级在一百多 MB/s，200 台设备按每台 100 MB/s 预留，采集网要按 20 GB/s 的汇聚来设计，或者按端口分配配额压下来。

存储分层。原始 INT 记录留 3 到 7 天，数据量大、价值随时效衰减。逐跳时延的百分位与队列水线聚合留 90 天，供基线对比。归档只留超过基线的「受害流」记录。

再加一条：采集侧必须有丢弃计数并进监控。上报端一丢，INT 就退化成随机抽样，结论会系统性偏乐观。

**评分维度**：采样率与理由匹配（必需）。上报通道独立（必需）。存储分层并给出保留期（必需）。采集侧丢弃监控（加分）。

:::

**自测 Q3**：INT-XD 与 postcard 都不改报文长度，两者在归因能力上差在哪？

::: details 参考答案与评分维度

INT-XD 由交换机导出一条完整记录，同一次采样在单点就能拿到整条路径的字段，关联成本低。

postcard 每跳只上报自己那一行，得靠流标识与时间窗在采集端拼接。拼接依赖时钟精度与流标识唯一性，跨设备时钟漂移会让顺序错乱，缺一跳就断链。

所以 postcard 开销更小、归因链路更长、容错更差。

**评分维度**：说清两者在关联点上的差别（必需）。提到时钟与流标识的依赖（加分）。

:::

**自测 Q4**：一条路径的 INT 记录显示第 4 跳 hop latency 是其他跳的 20 倍，出口利用率 98%，队列 700 KB。归因是什么？如果出口利用率 50%，归因又是什么？

::: details 参考答案与评分维度

第一种是本跳出口拥塞。出口接近打满，队列堆着的报文发不出去，停留时长主要花在排队上，处置方向是分流或扩容。

第二种是上游争抢或本跳转发面偏慢，要再区分。队列高而出口不满，是多股流抢同一出口，往上游查谁在超发；队列低而停留长，才是本跳转发面慢，查 ACL、查表、微码。

**评分维度**：两种情况分开答（必需）。第二种进一步区分（加分）。

:::

## 小结

端口视角有三个天生看不全的地方：不知道是谁、不知道哪一跳、不知道当时。一条流的时延被摊到几十个端口上，所有指标都正常，任务就是慢。

INT 换了记录者。switch ID、进出端口、停留时长、队列水线、出口利用率，每跳二十几字节，跟着报文走到终点。它的可信度是不对称的：说哪一跳慢，那一跳一定慢；说一路正常，先看看有没有被采到过。

上报有三种。写进包头的膨胀最大，交换机导出的不动原报文，postcard 最省但拼接最费劲。生产环境多数走后两种，元数据不该占业务带宽。

采样率是一道算术题，p = 1 - (1 - 1/k)^m，k 是采样分母，m 是突发里的报文数。1:2048 的开销在万分之一量级，看着无所谓，但 200 微秒的微突发在 1:4096 下有一半概率整分钟都抓不到。判读要看队列与利用率的组合，hop latency 高不代表这一跳有问题。

芯片能不能把元数据插进业务报文，是选型阶段就要问清的一句话。问不清，后面讲的都是别人的机房。

::: tip 本课要点

**一条流的问题，端口视角答不了。**

- 端口视角三盲点：**不知道是谁、哪一跳、当时**。INT 让报文自己写逐跳记录
- 可信度不对称：**说慢一定慢，说正常可能没采到**
- 元数据五项加时间戳：switch ID、进出端口、hop latency、queue depth、tx util，24 到 32 字节一跳，8 跳 190 到 260 字节
- 三种范式：**INT-MX 报文携带、INT-XD 导出上报、postcard 本地上报**，生产走后者居多
- 采样捕获率 p = 1 - (1 - 1/k)^m。1:4096 下 48 个报文的突发只有 1.2%，连来 60 次一半概率全错过
- 判读看**队列与利用率的组合**：队列高加出口满＝本跳拥塞，队列高加出口不满＝上游争抢，队列低加停留长＝转发面慢
- 三个坑：跳数预算估小、MTU 没留余量、上报端静默丢弃
- 芯片能不能插进业务报文，决定后面所有能力

:::

留一个思考题：微突发只持续 50 微秒时，你会把采样率翻八倍，还是换成队列水线触发的快照，为什么。
