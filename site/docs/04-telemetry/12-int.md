上一讲我们把数据从设备上取了出来，gNMI 能告诉你每个端口每秒丢了多少包、队列堆到多高、pause 帧发了几千次，一台交换机身上该报的九块东西都能订阅上，它非常有价值，能解决很多聚合层面的定位需求。

但是如果我们想知道**这条流到底卡在哪一跳**，它就无能为力了，它只提供端口视角的计数，没有逐流逐包的视角。

讲个使用场景，训练任务的 P99 时延从 1.2 毫秒涨到 9 毫秒，训练侧报慢，拉 gNMI 数据一看，路径上五台交换机、十个端口，PFC 与 ECN 计数全在正常范围，队列水线也没有明显抬升。设备指标正常，任务就是慢。

你会想到把采样密一点，从 5 秒改成 100 毫秒，反复看了半天，所有端口的曲线都在正常区间里躺着。你又会想到把阈值调低一点，结果全网几百个端口一起告警，什么也定位不了。你可能又想到抓包，可是抓包只能抓到两端的报文，中间那五跳里发生了什么，报文上不写着。

实际上这不是数据不够密的问题，是视角的问题。端口是设备的一个面，流是穿过去的一条线，一条流慢，摊到每个端口上只是很小的一点增量。**一条流的问题，被摊到了全网几十个端口上。**

这时，INT（In-band Network Telemetry，带内遥测）闪亮登场了，它就是专门解决这种路径级定位问题的。它让经过的报文自己写一份逐跳记录，带到终点再读出来，路径从推断变成实测。它在定位能力上比端口指标强一个量级，只是每一跳要多背二十几个字节，而且只有被采样到的包才背着走。

## INT 是什么？

INT 可以理解成一份随报文走的行程单。报文进第一台交换机，芯片在它头上记一笔：我是谁、你从哪个口进来、从哪个口出去、在这儿待了多少微秒、出口队列当时有多满。下一跳接着记，一路记到终点，采集端把这份行程单读出来，一条路径的全部停留时间就有了。

它不是全量的，它是采样的，这一点决定了怎么读它。当 INT 说某一跳慢时，这一跳一定慢；当它说这一跳正常时，可能只是这一段压根没被采到。打个比方，当它说这条流在你家三楼停了两百微秒，那是真停过；当它说这一路都很顺畅，你得先看看这一路有没有被抽到过。这句话是这一讲的总纲，后面算采样率的算术题，算的就是「抽到过」的概率。

## 基本使用

它输出的是这样一张表，五跳，一跳一行：

```text
定位到第 3 跳（sw-003f）：上游争抢
  场景 upstream     全程   31.4 µs
  #   设备       入    出        停留(µs)    队列KB   利用%   占比   归因
   1  sw-0011  1    8           0.8      12    42.0   2.5%  ok
   2  sw-002a  3    11          0.9      18    51.0   2.9%  ok
  *3  sw-003f  7    2          28.0     640    55.0  89.1%  上游争抢
   4  sw-004c  5    13          0.9      22    55.0   3.0%  ok
   5  sw-005d  9    4           0.8      15    46.0   2.5%  ok
```

五跳里第 3 跳吃了 89.1% 的时延，其余四跳加起来不到 4 微秒，一眼就能看到问题落在哪台设备、哪个入端口、哪个出端口。顺手看一眼它的兄弟场景，同样是第 3 跳吃掉九成时延，结论却完全不同：

```bash
go run . -scenario forwarding
```

```text
定位到第 3 跳（sw-003f）：转发面偏慢
  场景 forwarding   全程   43.4 µs
   3  sw-003f  7    2          40.0      16    40.0  92.1%  转发面偏慢
```

队列 16 KB、出口利用率 40%，这一跳不忙，但是它慢。这两条记录放在一起，把 INT 的用处说清楚了：**停留时长告诉你哪一跳不对，队列与利用率告诉你为什么不对**，一个数看不出结论，三个数组合才有。

似乎很准确啊，两个场景都定位对了。下面我们跑一次采样捕获的对照，看看采样率落到 1:4096 的时候，一条 200 微秒的微突发还能不能被看见：

```bash
make run
```

你会张大了嘴巴发现最后一列写着 49.5%：连续 60 次突发，一次都没采到的概率接近一半。这是怎么回事？如果一条流 24 万个报文每秒，一次微突发持续 200 微秒，里面只有 48 个报文，采样器每 4096 个包才挑一个，48 个包全落在采样缝隙里是极可能发生的事。

原因就在于采样这个动作本身。它跟误判率是一个道理，采样率决定的是「抽到过」的概率，不是你观测得细不细。所以我们要把突发拉长一点再看：

```bash
go run . -burst-us 2000
```

突发从 200 微秒拉到 2000 微秒，报文数从 48 变成 480，同样 1:4096 的捕获率从 1.2% 涨到 11%，从「基本抓不到」变成「大概能抓到」。这说明一件事：**采样率够不够，取决于你要抓多短的事件，不取决于某个推荐值。**

那如何来量这个捕获率呢？一条公式就够。哈希采样近似独立同分布，48 个报文每个被采到的概率都是 1/k，一次突发里至少采到一个的概率是：

```text
p = 1 - (1 - 1/k)^m      # m 是突发里的报文数，k 是采样分母
```

k = 4096、m = 48 代进去，p = 1 - (4095/4096)^48 ≈ 1.17%，实测那一列 1.1% 就是这么来的。连续 n 次突发一次都没采到的概率是 (1 - p)^n，n = 60 时 (0.9883)^60 ≈ 49.5%，这就是最后一列那个「一半」。

```text
采样      突发报文   解析捕获   实测捕获   连续 60 次全错过
1:256       48       17.1%      17.3%        0.0%
1:1024      48        4.6%       4.8%        6.0%
1:4096      48        1.2%       1.1%       49.5%
元数据开销：5 跳 120 字节，相对 1450 字节报文 8.3%
```

明白了这张表，你也许会问，这么低的捕获率，有没有办法提高一点？答案是有的，两条路。

**第一条，把采样率往上翻。** 1:4096 提到 1:256，捕获率从 1.2% 涨到 17.1%，代价是上报量涨 16 倍。往上翻只是把「一半抓不到」变成「八成能抓到」，永远到不了 100%。

**第二条，把事件的持续时长放宽。** 上面那个 `-burst-us 2000` 就是干这个的，从「基本抓不到」变成「大概能抓到」。这条路的代价是你改不了现实，微突发就是那么短。

真遇到 50 微秒级的微突发，正确做法是换机制，不是加采样率：队列水线越线触发快照、直方图、或者交换机侧的丢包与暂停事件流。拿采样去抓 50 微秒的事，翻八倍采样率也只是把概率从 1% 变成 8%。

## 注意事项

原理放到下一节，先把三件事说在前面。

跳数预算估小了，关键时刻插不进去。元数据是逐跳累加的，报文从第一跳背到最后，所以设计阶段就要定死「最多几跳」。定 4 跳，结果某条流绕了 6 跳，芯片只能在第 5 跳放弃记录，你手上拿到的是一份断在中间的行程单，前面四跳全对，最后两跳没有，事故恰好出在最后两跳。

MTU 没留余量，会把业务打崩。1500 字节加 200 字节元数据，总长顶到 1700，触发分片。分片对 RDMA 流量是事故：一个 4000 字节的 RDMA 报文被切成三片，任一片丢了，整条消息重传。省下的那点带宽，抵不上一次重传的代价。

只估了采集端，没估上报端的丢弃，这是最常见的一个。上报通道和业务流量抢带宽的时候，交换机先丢的一定是 telemetry report，因为它是低优先级。你的 INT 数据在事故期间掉一半，看着像全网突然健康了，实际上是观测先瞎了。上报端的丢弃计数必须单独埋一个，进监控。

## INT 的原理

学会了怎么用，下面有必要把原理说一下，不然读者还会继续蒙在鼓里。

元数据写进哪里，各家芯片的做法不一样。按写法分三档：**报文携带**（INT-MX）把元数据全写进报文头跟到终点，终点拿到完整逐跳路径，代价是报文膨胀最大，靠 MTU 与 jumbo frame 硬扛；**导出上报**（INT-XD）由交换机把元数据打包成 telemetry report，走带外或 UDP 发给采集器，原报文长度不变，上报链路要扛住采样量；**postcard** 每跳只在本地上报一行「我见过这条流」，报文几乎零开销，但关联靠流标识加时间窗拼接，跨设备时难度高。

生产环境多数走后两种，理由很直接：报文膨胀影响业务，元数据只是运维数据，不该让业务流量替它占带宽。IETF 把这一套标准化成 IOAM，在 RFC 9197 里定义了 trace option 的字段与封装语义，厂商实现会加私有字段，这就是为什么不问清芯片能力就不能排方案。

标准字段五项，加时间戳共 28 字节，按 8 字节对齐算 32 字节。实验里的实现省掉时间戳，取 24 字节一组：

```text
偏移   字段            宽度
 0    switch id        4
 4    ingress port     2
 6    egress port      2
 8    hop latency      4   （纳秒）
12    queue depth      4   （KB）
16    tx util          4   （基点，10000 = 100%）
20    reserved         4   （时间戳低位，本实验未使用）
```

一条 8 跳的路径，元数据 220 到 260 字节。IP 头选项这条路早就不通，运营商与防火墙对 IP option 的处理五花八门，多数直接丢，所以 INT 自带封装，常见承载是 Geneve、NSH，或者 UDP 封装下的自定义头。承载方式决定 MTU 预算，也就决定了能插几跳。数据中心内部统一开 9000 字节 jumbo frame，余量就出来了；1400 字节的小 MTU 环境，八跳就是上限。

要自己解析，按固定步长切就够了：

```python
# int_parse.py — 按 24 字节一组的元数据解析
import struct

HOP = 24  # switch_id(4) + ports(4) + hop_latency_ns(4) + queue_depth(4) + tx_util(4) + pad(4)

def parse(payload: bytes):
    hops = []
    for off in range(0, len(payload) - HOP + 1, HOP):
        sid, ports, lat_ns, qdepth, tx_util, _ = struct.unpack_from("!IIIIII", payload, off)
        hops.append({
            "switch": f"sw-{sid:04x}",
            "ingress": ports >> 16,
            "egress": ports & 0xFFFF,
            "hop_us": lat_ns / 1000,
            "queue": qdepth,
            "tx_util_pct": tx_util / 10,
        })
    return hops
```

真实的坑在载荷校验：`len(payload)` 不是 24 的整数倍时直接报错，不要按整数截断后读出一堆垃圾字段。实验里有一个单测专门管这条，叫 `TestDecodeRejectsTruncated`。这条不啰嗦的原因在于它不报错：`len = 25` 的载荷按「整数截断」写，最后一跳会读出 1 个真字节加 23 个零，产出一份看起来完全正常的记录，switch id 是 0、队列 0 KB、利用率 0%。**事故复盘时给你一份假记录，比没有记录更坏。**

## 空间占用估计

元数据的开销可以算得很干净。一条报文背 h 跳，每跳 24 字节，元数据是 24h 字节，相对报文本身的占比是：

```text
开销 = 24h / (1450 + 24h)     # 1450 字节是常见的以太网载荷均值
```

h 取几个值代进去：

1. h = 1，开销 1.6%，可以忽略
2. h = 5，开销 120 / 1570 = 7.6%，实验里按 1450 为分母算成 8.3%
3. h = 8，开销 192 / 1642 = 11.7%
4. h = 16，开销 384 / 1834 = 21%，长路径的代价开始难看

上面的数字是「每个报文都插」的全量口径。真实部署没有全量 INT，都是采样，所以实际开销要再乘采样率。

所以回到那个常见的误解：既然每跳才 24 字节，多插几跳没关系？错在分母。RDMA 的小消息居多，一次 AllReduce 里 512 字节的报文很常见，这时候 24 字节是它的 4.7%，八跳就是 37%，业务侧直接看得到带宽下降。**开销要按实际报文长度算，不能按 1500 字节的名义 MTU 算。**

## 跳数超出预算时

当实际路径比预算长，记录不会只丢一点点，它会整段断掉，这一点要单独说，因为它变化得比想象中陡。

预算 4 跳，实际走了 6 跳，第 5 跳芯片就没有位置可写了，后面两跳的元数据一个字段都没有。表现是：前面几跳的数看着都对，最后一段永远缺失。如果事故恰好出在最后两跳，你手上的记录会给出「一路健康」的结论。

更麻烦的是这个现象不稳定。同一条流在不同时刻绕行的跳数可能不一样，于是有的记录是 5 跳，有的记录是 4 跳，看起来像数据质量问题，实际是路径长度在预算边上摆动。

解法只有两个：把预算加大（背更多字节，MTU 也跟着加），或者把 jumbo frame 与封装一起重算一遍。**跳数预算不是配一个数就完了，它要和 MTU、封装方式一起对账。**

## 芯片不支持的那批设备

INT 不是软件功能，是芯片功能。手上那批设备不支持，也有替代路线，只是每条都有代价。

1. **只支持 telemetry report 采样上报。** 能拿到采样点快照，拿不到逐跳队列，属于「知道有人在慢，不知道慢在哪一跳」。
2. **镜像加旁路探针。** 交换机把指定端口的流量镜像到探针，探针自己解析。这能拿到报文级证据，代价是镜像本身占端口带宽，探针要按 400G 的量级配置，成本比开 INT 高得多。
3. **硬件探针或智能网卡在端侧打时间戳。** 只能给出端到端，一跳都拆不出来，但至少能回答「是不是网络慢」。
4. **换设备。** 听着粗暴，但在新建集群里，这常常是最省事的答案：选型阶段把 INT 能力写进需求，别等上线以后发现只能镜像。

要问清的问题只有一个：**你的芯片能把元数据插进业务报文，还是只能旁路导出。** 前者能拿到逐跳队列，后者只能拿到采样点快照。

这中间还有一层差异，在 RoCE 上尤其明显。RoCEv2 报文走 UDP 封装，元数据的插入点没有统一标准，常见三条路线：芯片原生支持在特定封装下逐跳插入，多为自研或特定白盒；只支持 telemetry report 采样上报；或者干脆靠镜像与旁路探针还原。选型时把这三条问清楚，比问「支持不支持 INT」有用得多。

## INT 还能回答什么

除了「这条流卡在哪一跳」，这份逐跳记录还能顺手回答几个问题，现场用得上。

**ECMP 到底走没走偏**：进出端口一串下来就是实际路径，和拓扑算出来的预期路径一比，哈希是不是极化一目了然，04b 那个「八条同五元组」的实验，真机上就是用 INT 验的。**队列堆在哪一级**：队列水线每一跳都有，螺旋上升还是单点顶满，形态不同，处置方向完全不同。**PFC 是不是真的传导了**：把 INT 的时间戳和 pause 帧的收发时刻对齐，能看出反压走了几跳、在哪一跳断掉。**路径 MTU 与黑洞**：元数据能插进去就说明这条路上每跳都认得这个封装，插不进去的那一跳，就是问题所在。

这几条的共同点是：它们都是「单条流」的问题，端口视角永远答不了。

## 与 gNMI 的分工

两者是级联关系，不是替代关系。gNMI 的视角是端口与设备，周期采样 0.1 到 5 秒，覆盖全设备全端口，部署成本低，软件就能干；INT 的视角是流与路径，事件驱动、报文级，只覆盖被采样报文经过的路径，关联能力强，同一条流跨设备可以直接拼接，但要芯片与镜像支持。

现场用法是 gNMI 告警指出问题端口，再用 INT 定位这个端口上的哪条流、哪一跳。INT 替代不了 gNMI 的原因在覆盖面：没有流量经过的端口永远没有 INT 记录，而故障常常发生在没流量的那半边，比如某条 rail 上的备用链路。

## 判读与实操

`labs/07-int-path` 用四个场景把四种归因各摆了一遍：

```bash
cd labs/07-int-path
make run     # 四个场景的逐跳判读 + 采样捕获率对照
make test    # 10 个单测，含截断载荷必须报错
```

同样是第 3 跳吃掉九成时延，队列与利用率换一组组合，归因就变成别的：

```text
停留时长   队列   出口利用率        归因
高        高     接近打满        本跳出口拥塞
高        高     不满            上游争抢，几股流抢同一出口
高        低     低              转发面偏慢（查表、ACL、微码）
低        低     低              健康
```

表里的高与低都是相对本路径其他跳说的：同一条记录内部横向比，绝对阈值只作参考。实验里的绝对阈值是出口利用率 85%、队列 500 KB、停留 20 微秒，这三个数是模型的设定，真机上要按端口缓冲和业务基线重新定。

判读顺序：先看总时长与跳数，跳数异常多说明 ECMP 走了非预期路径，先查拓扑与哈希；再看逐跳中位数，中位数平稳而 P99 高，是排队而非转发故障；然后看每一跳的队列与利用率组合，按上表归因；最后对齐时间戳，把 PAUSE 上涨的时刻与 hop latency 抬升的时刻对上。

两个容易弄反的判断。**hop latency 高不等于这一跳有问题**：队列在这一跳的出口排，但把队列堆满的流量来自上游，出口利用率接近打满、队列还堆着，才是本跳的责任。**INT 记录是采样，不是全量**：一条流五分钟里被采到 30 次，这 30 次说明当时的情况，不说明另外几百万个报文，用它看分布形状可以，用它算精确总量不行。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：某次训练任务的 P99 时延从 1.2 毫秒涨到 9 毫秒，gNMI 显示全部端口 PFC 与 ECN 正常。给出用 INT 定位的操作序列。

::: details 参考答案与评分维度

1. 先确认采集自己在跑。查采样率、上报量、上报端丢弃计数。上报数在事故期间掉到 0，问题就在采集侧。
2. 拉这段时间的 INT 记录，按流标识分组，找出受害流那一组。
3. 把受害流按 hop latency 排序，看是否集中在某一跳。同时看这一跳的队列与利用率：队列高、利用率不到 60%，说明多股流争抢，问题在上游分布。
4. 用时间戳对齐，找同一时刻其他流的记录，确认是否存在跨流同步突发，也就是 incast 特征。
5. 回 gNMI 核对这一跳的端口计数与 ECN 标记。两边不一致，说明其中一侧的数据有问题。

**评分维度**：先确认采集自身健康（必需）。按流分组再看逐跳（必需）。用队列与利用率的组合归因（必需）。两侧数据交叉验证（加分）。

:::

**必答 Q2**：给一个 200 台交换机的集群设计 INT 方案，写出采样率、上报通道、存储策略与理由。

::: details 参考答案与评分维度

采样率 1:2048 起步，单台 32 端口 400G 设备不到 1% 的带宽开销，同时保留分布形状。抓不准的微突发另配队列水线触发的快照。

上报走独立采集网络，不占业务链路。单设备上报上限按端口数 × 采样率 × 报文大小估，这个量级在一百多 MB/s，200 台设备按每台 100 MB/s 预留，采集网要按 20 GB/s 的汇聚来设计，或者按端口分配配额压下来。

存储分层。原始 INT 记录留 3 到 7 天，数据量大、价值随时效衰减。逐跳时延的百分位与队列水线聚合留 90 天，供基线对比。归档只留超过基线的「受害流」记录。

再加一条：采集侧必须有丢弃计数并进监控。上报端一丢，INT 就退化成随机抽样，结论会系统性偏乐观。

**评分维度**：采样率与理由匹配（必需）。上报通道独立（必需）。存储分层并给出保留期（必需）。采集侧丢弃监控（加分）。

:::

**自测 Q3**：INT-XD 与 postcard 都不改报文长度，两者在归因能力上差在哪？

::: details 参考答案与评分维度

INT-XD 由交换机导出一条完整记录，同一次采样在单点就能拿到整条路径的字段，关联成本低。

postcard 每跳只上报自己那一行，得靠流标识与时间窗在采集端拼接。拼接依赖时钟精度与流标识唯一性，跨设备时钟漂移会让顺序错乱，缺一跳就断链。

所以 postcard 开销更小、归因链路更长、容错更差。

**评分维度**：说清两者在关联点上的差别（必需）。提到时钟与流标识的依赖（加分）。

:::

**自测 Q4**：一条路径的 INT 记录显示第 4 跳 hop latency 是其他跳的 20 倍，出口利用率 98%，队列 700 KB。归因是什么？如果出口利用率 50%，归因又是什么？

::: details 参考答案与评分维度

第一种是本跳出口拥塞。出口接近打满，队列堆着的报文发不出去，停留时长主要花在排队上，处置方向是分流或扩容。

第二种是上游争抢或本跳转发面偏慢，要再区分。队列高而出口不满，是多股流抢同一出口，往上游查谁在超发；队列低而停留长，才是本跳转发面慢，查 ACL、查表、微码。

**评分维度**：两种情况分开答（必需）。第二种进一步区分（加分）。

:::

## 小结

端口视角有三个天生看不全的地方：不知道是谁、不知道哪一跳、不知道当时。一条流的时延被摊到几十个端口上，所有指标都正常，任务就是慢。

INT 换了记录者。switch ID、进出端口、停留时长、队列水线、出口利用率，每跳二十几字节，跟着报文走到终点。它的可信度是不对称的：说哪一跳慢，那一跳一定慢；说一路正常，先看看有没有被采到过。

上报有三种。写进包头的膨胀最大，交换机导出的不动原报文，postcard 最省但拼接最费劲。生产环境多数走后两种，元数据不该占业务带宽。

采样率是一道算术题，p = 1 - (1 - 1/k)^m。1:2048 的开销在万分之一量级，看着无所谓，但 200 微秒的微突发在 1:4096 下有一半概率整分钟都抓不到。判读要看队列与利用率的组合，hop latency 高不代表这一跳有问题。

芯片能不能把元数据插进业务报文，是选型阶段就要问清的一句话。问不清，后面讲的都是别人的机房。

::: tip 本课要点

**一条流的问题，端口视角答不了。**

- 端口视角三盲点：**不知道是谁、哪一跳、当时**。INT 让报文自己写逐跳记录
- 可信度不对称：**说慢一定慢，说正常可能没采到**
- 元数据五项加时间戳：switch ID、进出端口、hop latency、queue depth、tx util，24 到 32 字节一跳，8 跳 190 到 260 字节
- 三种范式：**INT-MX 报文携带、INT-XD 导出上报、postcard 本地上报**，生产走后者居多
- 采样捕获率 p = 1 - (1 - 1/k)^m。1:4096 下 48 个报文的突发只有 1.2%，连来 60 次一半概率全错过
- 判读看**队列与利用率的组合**：队列高加出口满＝本跳拥塞，队列高加出口不满＝上游争抢，队列低加停留长＝转发面慢
- 三个坑：跳数预算估小、MTU 没留余量、上报端静默丢弃
- 芯片能不能插进业务报文，决定后面所有能力

:::
