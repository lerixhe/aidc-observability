如果要用一句话来描述这一讲，我想应该是：症状出现在语义层，根因是一颗米粒大的模拟器件。

上一讲四大故障是"机制病"，这一讲讲"硬件病"。

业界公认 AIDC 网络故障的第一来源是光模块与物理层。更重要的是：**这一讲是路径级覆盖能力最直接的价值变现现场**。

## 学完这一讲，你应该能

- 建立规模直觉：为什么万卡集群里"今天坏在哪"比"会不会坏"更接近真实问题
- 区分四种光模块故障模式，并说清"劣化"为什么最难查
- 完整走通"路径级探测发现 → CRC/FEC 定位端口 → DOM 确认模块"的三层信号链
- 理解无损网络里"链路健康"的判据为什么要从"有没有丢"变成"纠错压力有多大"
- 知道探测数据在 RoCE 环境下的误报风险与规避方法

## 机制拆解

### 0x01 为什么坏光模块防不住：规模的暴击

先建规模直觉。一万张 GPU 的集群，按每台 8 网卡加 Clos 多级互联估算，全网有**十万根以上光纤、十几万个光模块**。

而光模块是全网里**唯一的模拟器件加唯一的可插拔部件**，天然最不可靠：

- 激光器老化、温度漂移、灰尘污染（插拔一次污染一次）。
- 搬运、施工、运维人员天天插拔，接触不良常态化。
- 哪怕单个模块年失效率只有千分之几，十几万的基数意味着**集群里每天都有模块在坏**。

光模块相当于整张网的机械硬盘：唯一带活动部件（激光器），唯一可插拔，也最容易坏。运维上对待它的方式也就该一样，也就是靠更换周期与健康度趋势管，不指望它不出事。

### 0x02 四种故障模式：完全失效好查，劣化才要命

| 类型 | 表现 | 难度 |
|---|---|---|
| **完全失效** | 激光器停振、LOS、链路直接 down | 好查，端口 down 立刻暴露 |
| **劣化（最阴险）** | 光功率缓慢漂移 → 误码率上升 → **链路还通，但 CRC 错误持续累积**，FEC 在拼命纠错 | 难，所有"通"的指标都正常 |
| **间歇 flap** | 反复 up/down，路由震荡，触发路径重哈希风暴 | 中，要看历史窗口的聚合 |
| **单 lane 劣化** | 400G 由多条并行 lane 组成，坏一条只降一份带宽且可能不自愈 | 难，端口显示 up，流量悄悄变慢 |

::: warning 关键推理（把前面几讲全串起来）

一条链路劣化后，哈希到它上面的**那几条 ECMP 路径**开始丢包、重传、时延膨胀。到了 RoCE 端侧，表现是 PFC / ECN 异常、训练任务变慢、NCCL timeout。

**症状出现在语义层，根因是一颗米粒大的模拟器件。** 而全网设备级聚合指标（丢包率均值、总流量）会被彻底稀释。一台 64 端口交换机上，一条链路只占 1.5%。

这就是"AIDC 排障先查光模块"这句行话的由来。
:::

### 0x03 黄金组合：三层信号锁一个好模块

**① 路径级探测：发现哪条路径劣化**

坏模块只影响经过它的个别路径。路径级探测会看到"全网几千条路径里，某三条时延或 CRC 相关指标劣化、其余正常"。**设备级聚合监控永远看不到这一步。**

**② 端口级 CRC / FEC 计数（gNMI 遥测）：锁定哪个端口**

把劣化路径集合与拓扑求交集，缩到某台设备的某个端口。核对该端口的 **CRC 错误计数、FEC 纠错计数**是否上涨。

注意：**FEC 纠错上涨时链路还没丢包**，这是劣化前兆，能提前抢修。

**③ 光功率 / 温度遥测（DOM）：确认为什么**

读取模块收发光功率与温度。功率漂移、温度异常，确认模块级根因，换模块，工单闭环。

三层信号的关系相当于撒网、收网、验货：探测撒网，CRC/FEC 收网，DOM 验货。

```text
路径级探测（快、广）        →  CRC/FEC（准、窄）        →  DOM（确因）
「这几条路径不对劲」        「是这个端口」              「这颗模块在漂」
      秒级                        分钟级                      分钟级
```

::: info 经验映射（IDC → AIDC）

这条"路径发现 → 端口定位 → 模块确认"的故事线，对有路径级探测经验的读者几乎是平移。

你已经做透了第一层（路径级探测）。第二层只是多订阅一组 gNMI 计数器，第三层再多订阅一组 DOM 指标。三种数据源拼起来，才能把"全网排障"压缩成"单模块定位"，**这正是已有能力在新场景里最直接的价值证明**。
:::

### 0x04 统计口径的变化

传统 IDC 里，"丢包与时延统计口径"是一套很成熟的东西。在无损网络里这套口径要升级：

| 维度 | 有损网络 | 无损网络 |
|---|---|---|
| 主要的错误信号 | 端口 drop 计数 | **CRC 错误数、FEC 纠错数（已纠正 / 未纠正）** |
| 健康的判据 | 有没有丢 | **纠错压力有多大** |
| 丢包的含义 | 常态，看趋势 | 机制失效，事故级 |
| 需要注意的新陷阱 | — | 探测包走有损队列，不受 PFC 影响，但会受拥塞降速影响 |

最后一行值得展开。**探测包走有损队列**（该丢就丢），所以它不受 PFC 暂停影响，这是它能反映"共享链路真实状况"的原因。反过来，拥塞导致的 DCQCN 降速也会让探测时延波动，需要与"路径劣化"区分。

区分方法有三条。

1. 交叉验证同期 ECN 标记率，同步上涨更像正常拥塞控制。
2. 看形态：拥塞是脉冲式，硬件劣化是单调漂移。
3. 与训练步节奏做时间对齐。

## 经验映射

| 你熟悉的做法 | 在光模块场景里的对应 |
|---|---|
| 端口 up/down 告警 | 只能抓"完全失效"，占比很低 |
| 端口丢包率告警 | 无损网络里丢包约等于 0，几乎失效 |
| 全网巡检式轮询 | 十几万模块轮不过来，必须靠异常驱动 |
| 路径级探测 | ✅ 主力发现手段 |
| 人工登机 `show interface` | 升级为 gNMI 订阅加自动关联 |

结论：光模块场景最能说明"为什么必须做路径级加设备级的组合"，也最能体现监控工程价值。**十万个器件的问题，收敛到某一次具体换件**。

## 判读与实操

### 0x05 读什么

```bash
# 主机侧网卡：物理层错误计数（NVIDIA/Mellanox 命名示意）
ethtool -S <ifname> | grep -Ei 'crc|symbol|fec|phy|corrected'

# 交换机侧：端口物理错误与 FEC 统计
show interface <intf> counters errors
show interface <intf> transceiver detail        # DOM：收发光功率、温度、偏置电流
```

### 0x06 判读阈值思路（不要照抄具体数字）

| 现象 | 判读 | 动作 |
|---|---|---|
| CRC 缓慢上涨、丢包为 0 | 劣化前兆，仍在 FEC 能力内 | 记为观察对象，安排窗口更换 |
| FEC 未纠正块增长 | 劣化加剧，接近丢包 | 提高优先级，尽快更换 |
| 收光功率低于规格下限或持续下降 | 物理层问题（脏、弯折、老化） | 先清洁，再看是否需换件 |
| 单 lane 功率异常而其他正常 | 单 lane 劣化 | 直接按模块更换处理 |
| flap（up/down 反复） | 接触或器件问题 | 优先处理，避免路由震荡 |

### 0x07 自动化的落点

一个可落地的自动流程：**路径劣化告警 → 路径集合与拓扑求交 = 候选端口 → 查 CRC/FEC 与 DOM → 命中规则则自动建工单并附证据**。

人工介入只剩"确认与更换"，这就是把 MTTR 从小时压到分钟的真实路径。

## 习题

**必答 Q1**：完整讲述"一颗劣化光模块"的旅程：从光功率开始漂移，到训练任务变慢，到被定位更换。按时间线描述**每一层监控各自在什么时刻看到了什么**。

::: details 参考答案与评分维度

**时间线**

1. **T+0 起**。光功率缓慢下降，误码率上升，FEC 纠错计数开始增长。此时链路完全正常，只有物理层计数器在动，第三层先有信号。
2. **T+n**。FEC 纠错能力被吃掉一部分，偶发未纠正块，链路出现零星丢包与重传。哈希到该链路的少数 ECMP 路径时延抬升、抖动变大，第一层路径级探测先发现"哪条路径"。
3. **T+n 稍后**。RoCE 侧表现为该路径上的流触发 PFC / ECN 异常，集合通信变慢，NCCL 可能出现超时。设备级聚合指标仍"正常"。
4. **定位**。路径集合与拓扑求交得到候选端口，查 CRC/FEC 锁定端口，读 DOM 确认模块功率漂移，然后换件。

**评分维度**

- 时间线顺序正确，且体现"物理层信号早于业务症状"（必需）
- 三层信号与"快广、准窄、确因"的分工明确（必需）
- 指出聚合指标被稀释、任务侧只看到慢（必需）
- 能补出自动化闭环（加分）
:::

**必答 Q2**："端口 CRC 错误数上涨但丢包数为 0"说明什么？该不该处理？为什么这是最好的抢修窗口？

::: details 参考答案与评分维度

说明物理层已经在劣化（误码率上升），但 FEC 仍能把错误纠正回来，所以还没有表现为丢包。**应当处理**，且应作为主动运维的对象。

这是最好的抢修窗口，理由三条。

① 此时业务无感，更换可以在计划窗口内做，不影响训练。
② 一旦 FEC 纠错能力耗尽转为丢包，就会触发 RoCE 重传、PFC/ECN 异常甚至任务中断。届时只能被动抢修，还可能付出 checkpoint 回退的代价。
③ 从"纠错压力上升"到"开始丢包"通常有可观测的时间差，这个时间差就是运维的提前量。

**评分维度**：说出"FEC 掩盖、即将丢包"（必需）。明确"应主动处理"（必需）。说出提前量的价值与回退代价（加分）。
:::

**自测 Q3**：为什么坏光模块"设备级聚合指标看不见"？请从数量关系上说明。

::: details 参考答案与评分维度

Clos 里两台服务器间有几十条等价路径，一条劣化只污染哈希到它的一小部分流量。从全网角度看，受影响流量占比可能只有千分之几。全网丢包率从 1e-7 涨到 1e-6，依然"远低于告警阈值"。但对走那条路径的 RDMA 流，丢包率是灾难性的。

**平均在长尾分布下会抹平问题**，这正是"路径级观测与设备级聚合"的本质差异。

**评分维度**：给出"单链路占比约 1% 或千分之几"的量级（必需）。指出"对受影响流是灾难，对均值是噪声"（必需）。
:::

**自测 Q4**：路径级探测在 RoCE 网络里如何避免"把正常拥塞降速误报为路径劣化"？

::: details 参考答案与评分维度

多信号交叉验证，三条。

① 同期该路径的 ECN 标记率若同步上涨、而 PFC 与丢包正常，更可能是 DCQCN 在正常工作。
② 用基线模型区分"周期性训练步抖动"与"持续性劣化"。前者与训练步对齐，后者不随节奏消失。
③ 形态差异。劣化是单调漂移，属于物理过程。拥塞是脉冲式。

答出"探测加设备遥测交叉验证"即达标。

**评分维度**：给出至少两种交叉验证手段（必需）。能提到"单调漂移与脉冲"的形态差异（加分）。
:::

## 小结

这一讲可以压成一句话：**症状出现在语义层，根因是一颗米粒大的模拟器件。**

十几万个光模块，唯一的模拟器件，唯一的可插拔件，所以集群里每天都有模块在坏。完全失效好查，端口直接 down。要命的是劣化：链路还通，CRC 在涨，FEC 硬扛着，所有"通"的指标都正常。

三层信号才能闭环。路径级探测先发现哪几条路径不对劲，路径集合与拓扑求交得到候选端口，CRC 与 FEC 确认，DOM 读出功率漂移，最后换件。

口径也跟着换了。以前问"丢没丢"，现在问"纠错压力有多大"。FEC 纠错上涨意味着链路还没丢包，那是最好的抢修窗口，业务无感，计划窗口就能换。

::: tip 本课要点

**症状出现在语义层，根因是一颗米粒大的模拟器件。**

- 规模直觉：万卡集群**十几万光模块**，唯一模拟器件加可插拔件 → **每天都有坏的**，AIDC 故障第一来源
- 完全失效好查（LOS）。**劣化最阴险**：链路通、CRC 涨、FEC 硬扛，单 lane 劣化只降一份带宽
- 症状远在天边：路径劣化 → PFC/ECN 异常 → 任务变慢或 NCCL timeout，**聚合指标被稀释看不见**
- 黄金组合：**路径级探测发现 → CRC/FEC 端口定位 → DOM 确因**
- 口径升级：健康判据从"丢没丢"变成"**CRC / FEC 纠错压力**"。FEC 纠错上涨就是免费抢修窗口
- 探测在 RoCE 下的误报风险：靠 ECN 交叉验证加形态判断（漂移 vs 脉冲）规避
:::

留一个思考题：如果 FEC 纠错计数上涨在换件之后仍然维持，你会先怀疑模块，还是先怀疑清洁度和连接器。
