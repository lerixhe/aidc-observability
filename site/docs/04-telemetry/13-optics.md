07 讲那四类故障，成因在配置与机制。还有一类更底层：器件本身在退。它退化的那几个星期里，链路是通的，指标全绿。只看通不通来判健康，就只能在它开始丢包那天发现问题，那时候抢修窗口已经过完了。

先说规模。一万张 GPU 的集群，按每台 8 块网卡加 Clos 多级互联估算，全网十万根以上光纤、十几万个光模块。这个基数决定了问题不是「会不会坏」，是「今天坏在哪」。

光模块是整张网里唯一的模拟器件，也是唯一的可插拔件。激光器会老化，温度会漂，插一次进一次灰，施工与巡检人员天天插拔。单个模块年失效率按千分之几算，十几万的基数摊下来，**集群里每天都有模块在坏**。

## 交付

- 四种故障模式的区别，以及为什么「劣化」占掉了大部分排障时间
- FEC 在劣化过程中的位置：什么时候在纠错，什么时候开始丢包
- 从路径级探测到 CRC/FEC 到 DOM 的三层信号链，每层的输入输出
- 无损网络里「链路健康」的判据怎么从「有没有丢」换成「纠错压力有多大」
- 探测数据在 RoCE 环境下的误报来源与三条区分手段

## 四种故障模式

| 类型 | 表现 | 排查难度 |
|---|---|---|
| 完全失效 | 激光器停振、LOS、链路直接 down | 低，端口 down 当场暴露 |
| 劣化 | 光功率缓慢漂移，误码率上升，链路还通，CRC 持续累积，FEC 在纠错 | 高，所有「通」的指标都正常 |
| 间歇 flap | 反复 up/down，路由震荡，触发路径重哈希风暴 | 中，要看历史窗口的聚合 |
| 单 lane 劣化 | 400G 由多条并行 lane 组成，坏一条只掉一份带宽 | 高，端口显示 up，流量悄悄变慢 |

四种里最难的是劣化。400G 端口用 KP4 FEC，也就是 RS(544,514)：544 个 10 bit 符号里带 514 个数据符号，能纠 15 个符号错误。链路一开始劣化，误码率从 1e-12 涨到 1e-9、1e-7，FEC 都还能全纠回来，端到端一个包都不丢。要到 pre-FEC BER 逼近 2.4e-4 这个量级，纠错能力吃满，才会出现未纠正块、开始丢包。

这段窗口有多长，取决于老化速率，从几天到几个月都有。它是运维唯一能主动安排的抢修时间。

## 为什么聚合指标看不见

一条链路劣化之后，哈希到它上面的那几条 ECMP 路径开始丢包、重传、时延膨胀。到 RoCE 端侧，表现是 PFC / ECN 异常、训练变慢、NCCL timeout。

问题出在分母。一台 64 端口交换机上，一条链路只占 1.5% 的端口数；放到全网，一条劣化链路污染的流量可能只有千分之几。全网丢包率从 1e-7 涨到 1e-6，离任何合理的告警阈值都还差得远。但对哈希到那条路径上的 RDMA 流，这个丢包率足以让一次 AllReduce 重传几十次。

均值在长尾分布下会抹平问题，这就是「AIDC 排障先查光模块」这句行话的由来：症状在语义层，根因在一颗模拟器件上，而中间的聚合层把因果链剪断了。

## 三层信号链

**第一层，路径级探测，回答「哪条路径劣化」。** 坏模块只影响经过它的个别路径。全网几千条探测路径里，某三条的时延或丢包劣化、其余正常，这个模式设备级聚合监控永远给不出来。

**第二层，端口 CRC / FEC 计数，回答「哪个端口」。** 把劣化路径集合与拓扑求交集，缩到某台设备的某个端口，核对该端口的 CRC 错误计数与 FEC 纠错计数是否在涨。

**第三层，DOM 遥测，回答「为什么」。** 读模块的收发光功率、温度、偏置电流、供电电压，确认功率漂移或温度异常，换件，工单闭环。

```text
路径级探测（快、广）    →   CRC / FEC（准、窄）    →   DOM（确因）
「这几条路径不对劲」        「是这个端口」             「这颗模块在漂」
秒级                        分钟级                     分钟级
```

三层里最容易缺的是第一层。只订阅 CRC / FEC 也能查到坏端口，前提是你知道去查哪台设备的那哪个端口；十几万个端口全量比对，等的是「CRC 已经涨到进告警阈值」，比路径探测晚几天到几周。这些天的差距就是劣化窗口被吃掉的部分。

## 口径要换

传统 IDC 里，丢包与时延的统计口径很成熟。无损网络里这套口径要重写：

| 维度 | 有损网络 | 无损网络 |
|---|---|---|
| 主要错误信号 | 端口 drop 计数 | CRC 错误数、FEC 纠错数（已纠正 / 未纠正） |
| 健康判据 | 有没有丢 | 纠错压力有多大 |
| 丢包的含义 | 常态，看趋势 | 机制失效，事故级 |
| 新增的陷阱 | 无 | 探测包走有损队列，不受 PFC 影响，但受拥塞降速影响 |

表里有一行要展开。探测包一般打有损优先级，该丢就丢，所以它不受 PFC 暂停影响，反映的是共享链路的真实状况；反过来，拥塞引起的 DCQCN 降速也会推高探测时延，跟硬件劣化混在一起看就是误报。

区分手段三条。一是**交叉验证**同期 ECN 标记率，标记率同步上涨更像正常的拥塞控制。二是**看形态**，拥塞是脉冲式，跟着训练步起落，硬件劣化是单调漂移。三是**与训练节奏对齐**，只在与训练同步的时段恶化、其余时段干净的，是拥塞。

## 经验映射

| 你熟悉的做法 | 在光模块场景里的位置 |
|---|---|
| 端口 up/down 告警 | 只能抓完全失效，占比最低的那一类 |
| 端口丢包率告警 | 无损网络里丢包约等于 0，这条告警基本失效 |
| 全网巡检式轮询 | 十几万个模块轮不过来，必须异常驱动 |
| 路径级探测 | 主力发现手段，回答「哪条路径」 |
| 登机敲 `show interface` | 升级为 gNMI 订阅加自动关联 |

路径级探测有经验的人，这条链的迁移成本很低：第一层是现成的，第二层多订阅一组 gNMI 计数器，第三层再订一组 DOM 指标。三种数据源拼起来，才能把「全网排障」压成「单模块定位」。

## 判读与实操

```bash
# 主机侧网卡：物理层错误计数（NVIDIA/Mellanox 命名示意）
ethtool -S <ifname> | grep -Ei 'crc|symbol|fec|phy|corrected'

# 交换机侧：端口物理错误与 FEC 统计
show interface <intf> counters errors
show interface <intf> transceiver detail        # DOM：收发光功率、温度、偏置电流
```

阈值思路，具体数字按模块规格与厂商建议填：

| 现象 | 判读 | 动作 |
|---|---|---|
| CRC 缓慢上涨，丢包为 0 | 劣化前兆，仍在 FEC 能力内 | 记为观察对象，排窗口更换 |
| FEC 未纠正块增长 | 劣化加剧，接近丢包 | 提高优先级，尽快更换 |
| 收光功率低于规格下限或持续下降 | 物理层问题（脏、弯折、老化） | 先清洁，再看是否换件 |
| 单 lane 功率异常，其余正常 | 单 lane 劣化 | 按模块更换处理 |
| flap（up/down 反复） | 接触或器件问题 | 优先处理，避免路由震荡 |

自动化的落点是一条链：**路径劣化告警 → 路径集合与拓扑求交 = 候选端口 → 查 CRC/FEC 与 DOM → 命中规则自动建单并附证据**。人工只剩确认与更换。MTTR 从小时压到分钟，靠的就是把前两步的比对交给机器。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：完整讲一颗劣化光模块的旅程：从光功率开始漂移，到训练任务变慢，到被定位更换。按时间线说清每一层监控在什么时刻看到了什么。

::: details 参考答案与评分维度

1. T+0 起，光功率缓慢下降，误码率上升，FEC 纠错计数开始增长。链路完全正常，只有物理层计数器在动，第三层先有信号。
2. T+n，FEC 纠错能力被吃掉一部分，出现零星未纠正块，链路偶发丢包与重传。哈希到这条链路的少数 ECMP 路径时延抬升、抖动变大，第一层路径级探测先发现「哪条路径」。
3. T+n 稍后，RoCE 侧该路径上的流触发 PFC / ECN 异常，集合通信变慢，NCCL 可能超时。设备级聚合指标仍然显示正常。
4. 定位阶段，路径集合与拓扑求交得到候选端口，查 CRC / FEC 锁定端口，读 DOM 确认功率漂移，换件。

**评分维度**

- 时间线正确，体现「物理层信号早于业务症状」（必需）
- 三层信号的分工清楚（必需）
- 指出聚合指标被稀释、任务侧只看到慢（必需）
- 补出自动化闭环（加分）

:::

**必答 Q2**：「端口 CRC 错误数上涨但丢包数为 0」说明什么？该不该处理？为什么这是最好的抢修窗口？

::: details 参考答案与评分维度

说明物理层已经在劣化，误码率上升，但 FEC 还能把错误纠回来，所以没有表现为丢包。**应当处理**，并且转为主动运维对象。

这是最好的窗口，理由三条。此时业务无感，更换能排在计划窗口，不影响训练。一旦 FEC 纠错能力耗尽转为丢包，就会触发 RoCE 重传、PFC / ECN 异常甚至任务中断，还可能付出 checkpoint 回退的代价。从「纠错压力上升」到「开始丢包」通常有几天以上的时间差，这个差值就是提前量。

**评分维度**：说出「FEC 掩盖、即将丢包」（必需）。明确应主动处理（必需）。给出提前量的价值与回退代价（加分）。

:::

**自测 Q3**：为什么坏光模块在设备级聚合指标里看不见？从数量关系上说明。

::: details 参考答案与评分维度

Clos 里两台服务器之间有几十条等价路径，一条劣化只污染哈希到它的一小部分流量。从全网看，受影响流量占比可能只有千分之几，全网丢包率从 1e-7 涨到 1e-6，依然远低于任何告警阈值。而对走那条路径的 RDMA 流，丢包率已经足以让一次 AllReduce 反复重传。

均值抹平长尾，这就是路径级观测与设备级聚合的本质差别。

**评分维度**：给出「单链路占 1% 或千分之几」的量级（必需）。指出「对受影响流是事故，对均值是噪声」（必需）。

:::

**自测 Q4**：路径级探测在 RoCE 网络里怎么避免把正常的拥塞降速误报成路径劣化？

::: details 参考答案与评分维度

多信号交叉验证，三条。

1. 同期该路径的 ECN 标记率若同步上涨、PFC 与丢包正常，更像 DCQCN 在正常工作。
2. 用基线区分「跟着训练步起落的周期性抖动」与「持续性劣化」。前者随训练节奏出现，后者不随节奏消失。
3. 看形态。劣化是单调漂移，属于物理过程；拥塞是脉冲式。

答出「探测数据与设备遥测交叉验证」即达标。

**评分维度**：给出至少两种交叉手段（必需）。提到单调漂移与脉冲的形态差异（加分）。

:::

## 小结

十几万个光模块，唯一的模拟器件、唯一的可插拔件，所以集群里每天都有模块在坏。完全失效好查，端口直接 down。难的是劣化：链路还通，CRC 在涨，FEC 硬扛着，所有「通」的指标都正常。KP4 FEC 能纠 544 符号块里的 15 个符号错误，pre-FEC BER 到 2.4e-4 量级才吃满，这段窗口就是抢修期。

聚合指标看不见，因为分母太大。一条链路占一台 64 端口交换机的 1.5%，全网丢包率从 1e-7 涨到 1e-6，没有任何阈值会响，而走这条路径的 RDMA 流已经在反复重传。

三层信号才能闭环：路径级探测发现哪几条路径不对劲，路径集合与拓扑求交得到候选端口，CRC 与 FEC 确认，DOM 读出功率漂移，换件。

口径跟着换了。以前问丢没丢，现在问纠错压力有多大。FEC 纠错上涨意味着还没丢包，那是最好的抢修窗口，业务无感，计划窗口就能换。

::: tip 本课要点

**症状在语义层，根因在一颗模拟器件上。**

- 规模：万卡集群十几万光模块，唯一模拟器件加唯一可插拔件，**每天都有坏的**，AIDC 故障第一来源
- 完全失效好查，**劣化最费时间**：链路通、CRC 涨、FEC 硬扛；单 lane 劣化只掉一份带宽
- 看不见的原因在分母：一条链路占 64 端口交换机的 1.5%，全网丢包率涨十倍也够不着阈值
- 三层信号：**路径级探测发现 → CRC / FEC 定位端口 → DOM 确认模块**
- 口径升级：健康判据从「丢没丢」换成「**CRC / FEC 纠错压力**」。FEC 纠错上涨就是免费的抢修窗口
- RoCE 下防误报：ECN 交叉验证、形态判断（漂移对脉冲）、与训练节奏对齐

:::

留一个思考题：换件之后 FEC 纠错计数仍然维持，先怀疑新模块，还是先怀疑清洁度与连接器。
