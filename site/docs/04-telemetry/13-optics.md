链路上的每一个光模块都有寿命，时间一到，它就不亮了。你可以想象每条链路背后都有一个死神，时刻盯着那颗激光器的偏置电流与误码，寿命一到就把它收走。

你还可以进一步站在死神的角度思考，会不会因为同一批模块同时到期，以至于一次收走一片。它们同批采购、同一天上电、在同一个机柜里烤着同样的温度，老化曲线本来就是排着队走的。而且死神也不是一刀切，它在收走之前会先让模块慢慢劣化，误码一点点爬上去，链路还照样通。

这些问题厂商早就想到了，所以在光模块这件事上做得非常小心：FEC 纠错、DOM 读数、告警阈值、寿命预测，一层层加。但再小心，也没法把十几万个模拟器件的寿命排开。

先说规模。一万张 GPU 的集群，按每台 8 块网卡加 Clos 多级互联估算，全网十万根以上光纤、十几万个光模块。单个模块年失效率按千分之几算，十几万的基数摊下来，**集群里每天都有模块在坏**。

## 光模块的健康账本

每个模块内部都有一组寄存器，通过 I2C 读出来，行业里叫 DOM 或 DDM。读的是四样：温度、供电电压、偏置电流、收发光功率。四样各有上下限，越界就报警。

除了这四样，链路两端还有一组物理层计数器：CRC 错误数、FEC 已纠正块数、FEC 未纠正块数。这两组数据来源不同，读法也不同。

网管对它们有两套动作。一套是**定时轮询**，按周期把所有端口扫一遍，这是集中处理；另一套是**惰性读取**，只有某个端口报了告警、或者路径级探测指到它头上，才去把它的寄存器和计数器单独拉一遍，这是零散处理。绝大多数模块的健康状况是定时扫描发现的，惰性读取用来确认。

## 巡检策略

默认的巡检是每分钟一次，但巡检不会遍历所有端口，而是采用一种简单的贪心策略：

1. 从端口清单里随机抽 20 个；
2. 看这 20 个里面有几个增量超阈值；
3. 如果超阈值的比例超过 1/4，就重复步骤 1。

同时，为了保证巡检不会把采集器自身压垮，还加了单轮时间上限：一轮扫描最多跑 25 秒，跑不完就等下一轮。

设想一个大型集群里同一批模块在同一时间开始劣化，会出现怎样的结果？

毫无疑问，巡检会持续抽样、持续命中，直到劣化模块的比例降下去才会恢复常态。这段时间里，路径级探测会看到几条 rail 同时掉速，训练步时一起抬高，值班表上冒出一片「网络有点慢」。导致这种卡顿的另一个原因是 FEC 纠错在吃带宽：纠错不是免费的，纠错越频繁，能用来传数据的余量越少。

当训练侧拿到一个慢步，它如果正好处在劣化蔓延的时段，就会一直等到 NCCL 超时。如果任务侧把超时设得比较短，那么就会出现大量连接因为超时而重建，作业日志里一片异常。而且这时候你还无法从 NCCL 的日志里看出根因，因为日志只会写 timeout，不会写「第 3 跳那颗模块在漂」。

所以运维要注意上电时间与批次：如果有大批量的模块同时到寿，要么分批上电，要么按批次分散备件，而不宜让整批模块在同一个月里一起老化。给老化曲线加一个随机范围，跟上电时间摊开是一个道理。

```py
# 同一批模块分批上电，把老化曲线摊开
for rack in racks:
    power_on(rack, delay=random.randint(0, 30 * 86400))
```

在集群扩容的场景里这个坑尤其深：一次扩容几百台机器，同批模块同天上电，一年后它们会排着队坏。我们这边就曾出现过几次因为同批模块集中劣化导致的步时抬升，通过按批次分散采购与分批上电，总能很好地解决这个问题，希望读者们今后能少犯这样的错误。

## 收割余量的那个角色

你可以把链路想象成一条一直在抖的绳子。抖一下，某个符号就错了，错误发生的频率叫误码率。

FEC 是绳子旁边那个不知疲倦的修补工。每抖错一次，它就补一块，补一次记一笔账。它补得动的那些天，链路是通的、端到端一个包都不丢，你会以为一切正常。

400G 端口用 KP4 FEC，也就是 RS(544,514)：544 个 10 bit 符号里带 514 个数据符号，能纠 15 个符号错误。这 15 个符号的纠错余量，就是它一晚上能干的活。

它一直在收的，是模块的余量。余量收完了，它就从「纠错」变成「放弃」，那时才开始丢包。所以劣化这件事有一条明确的爬坡曲线：

1. **余量充足期。** 误码率从 1e-12 涨到 1e-9，FEC 全纠回来，端到端零丢包，只有 pre-FEC 纠错计数在涨。
2. **余量吃紧期。** 误码率到 1e-7，纠错频繁，偶尔出现未纠正块，链路开始零星丢包，重传变多。
3. **余量耗尽期。** pre-FEC BER 逼近 2.4e-4 这个量级，纠错能力吃满，未纠正块成规模出现，开始稳定丢包。

这三段之间不是断崖，是斜坡。斜坡有多长，取决于老化速率，从几天到几个月都有。它是运维唯一能主动安排的抢修时间，也是这一讲最想让你记住的一件事：**在它还没丢包的时候看见它。**

## 账本要看增量

这是这一讲最实用的一节，也是最多人栽跟头的地方。

端口 CRC 与 FEC 计数都是**累计值**，从设备开机那天开始加，`show` 一次给你一个总数。判据从来不是这个数有多大，是它**每分钟涨了多少**。

现场两个端口摆在一起：

```text
端口 A：CRC 累计 4,120,000，最近三天每分钟增量 0
端口 B：CRC 累计 3,400，最近一分钟增量 200
```

A 的累计值比 B 大一千多倍。看绝对值，A 是必须处理的那个，实际它三个月前就坏过、换过模块、计数没清零而已。B 才是正在退的那颗。

增量也得换算成人话，不然「200」这个数没有体感。一个 400G 端口线速跑 1500 字节的报文，每分钟约 20 亿个包，200 个未纠正块摊进去，包丢失率是 1e-7。

1e-7 这个数写在任何一张监控大盘上都是绿的，告警线通常设在 1e-3 或 1e-4，中间差着三四个数量级。但是换一个分母它就变成另一件事：走这条路径的 RDMA 流，每分钟要重传 200 次。一次 AllReduce 跑两小时，就是两万四千次重传，步时抖动肉眼可见。

**同一个数字，用全网做分母是噪声，用一条流做分母是事故。** 这句是判读光模块的全部心法。

还有一条要记住：差分要看窗口。一分钟的增量有抖动，看五分钟、看一小时，趋势才出来。一次 200 的尖峰可能是机房空调抖了一下，连续六十个五分钟窗口都是单调上升，那就是激光器在退。

## 为什么聚合指标看不见

一条链路劣化之后，哈希到它上面的那几条 ECMP 路径开始丢包、重传、时延膨胀。到 RoCE 端侧，表现是 PFC / ECN 异常、训练变慢、NCCL timeout。

问题出在分母。一台 64 端口交换机上，一条链路只占 1.5% 的端口数；放到全网，一条劣化链路污染的流量可能只有千分之几。全网丢包率从 1e-7 涨到 1e-6，离任何合理的告警阈值都还差得远。但对哈希到那条路径上的 RDMA 流，这个丢包率足以让一次 AllReduce 重传几十次。

均值在长尾分布下会抹平问题，这就是「AIDC 排障先查光模块」这句行话的由来：症状在语义层，根因在一颗模拟器件上，而中间的聚合层把因果链剪断了。

有个现场值得记一下。一个 512 卡的作业，步时在两三周里从 1.9 秒爬到 2.6 秒，抖动也在变大。系统侧的信号只有两条：全网丢包率从 1e-7 涨到 8e-7，几个 leaf 的上联队列水线偶尔冒一下，两条都够不着任何告警线。

真正破案靠的是按 rail 比对吞吐：8 条 rail 里有 3 条掉了两成，其余 5 条干干净净。3 条 rail 的路径集合与拓扑求交，落在 3 个端口上，读 FEC 未纠正块，两个模块在涨，换上以后步时回到 1.9 秒。

这里的数字能对上账，也是它值得记的原因。每个 rail 上的 ring 是并行的，整个 AllReduce 由最慢的那个 ring 决定，带宽掉两成，步时该涨 25%，也就是 1.9 秒变 2.4 秒；实际爬到 2.6 秒，多出来的十几个点是重传和乱序补回来的。**步时涨得比带宽掉得多，说明路径上不只慢，还在丢。**

复盘时最刺眼的一句是：那两个模块的纠错计数已经在涨了三周，第一个星期就有信号，只是没人按月看增量。

## 四种故障模式

完全失效的表现是激光器停振、LOS、链路直接 down，端口 down 当场暴露，排查难度最低。

劣化是光功率缓慢漂移、误码率上升、链路还通、CRC 持续累积、FEC 在纠错，所有「通」的指标都正常，难度最高。

间歇 flap 是反复 up / down、路由震荡、触发路径重哈希风暴，难度中等，要看历史窗口的聚合。

单 lane 劣化最容易被漏掉：400G 由多条并行 lane 组成，坏一条只掉一份带宽，端口显示 up，流量悄悄变慢。

四种里最难的是劣化，因为它的证据全在计数器里，而计数器最容易被读错。

## 三层信号链

**第一层，路径级探测，回答「哪条路径劣化」。** 坏模块只影响经过它的个别路径。全网几千条探测路径里，某三条的时延或丢包劣化、其余正常，这个模式设备级聚合监控永远给不出来。

**第二层，端口 CRC / FEC 计数，回答「哪个端口」。** 把劣化路径集合与拓扑求交集，缩到某台设备的某个端口，核对该端口的 CRC 错误计数与 FEC 纠错计数是否在涨。

**第三层，DOM 遥测，回答「为什么」。** 读模块的收发光功率、温度、偏置电流、供电电压，确认功率漂移或温度异常，换件，工单闭环。

```text
路径级探测（快、广）    →   CRC / FEC（准、窄）    →   DOM（确因）
「这几条路径不对劲」        「是这个端口」             「这颗模块在漂」
秒级                        分钟级                     分钟级
```

三层里最容易缺的是第一层。只订阅 CRC / FEC 也能查到坏端口，前提是你知道去查哪台设备的那哪个端口；十几万个端口全量比对，等的是「CRC 已经涨到进告警阈值」，比路径探测晚几天到几周。这些天的差距就是劣化窗口被吃掉的部分。

## 口径要换

传统 IDC 里，丢包与时延的统计口径很成熟，无损网络里这套口径要重写。

主要错误信号从「端口 drop 计数」换成「CRC 错误数与 FEC 纠错数」，后者分已纠正与未纠正两种；健康判据从「有没有丢」换成「纠错压力有多大」；丢包的含义从「常态，看趋势」换成「机制失效，事故级」。

还有一条新增的陷阱要单说：探测包一般打有损优先级，该丢就丢，所以它不受 PFC 暂停影响，反映的是共享链路的真实状况；反过来，拥塞引起的 DCQCN 降速也会推高探测时延，跟硬件劣化混在一起看就是误报。

区分手段三条。一是**交叉验证**同期 ECN 标记率，标记率同步上涨更像正常的拥塞控制。二是**看形态**，拥塞是脉冲式，跟着训练步起落，硬件劣化是单调漂移。三是**与训练节奏对齐**，只在与训练同步的时段恶化、其余时段干净的，是拥塞。

## 备件与替换

主动替换和被动等告警，是两套完全不同的节奏。

主动的那套靠三层的信号链，看到增量在涨就排窗口换，业务无感；被动的那套等端口 down 或者等 CRC 涨进告警阈值，那时已经在丢包，换来的是抢修窗口和可能的 checkpoint 回退。

这里有个坑跟从库不一样：备用链路的光模块是不发光的，或者发光但没流量。收光功率低、温度正常、纠错计数为零，这些读数看起来都「健康」，其实是因为它压根没在干活。**待机的模块在 DOM 上看起来是最健康的那一颗**，等它被切上来才发现早就是坏的。

所以备件要单独管：同批次采购的备件会一起老化，固件版本也可能跟现网不一致；上电时间、批次号、固件版本这三样要么进资产库，要么在换件的时候重新读一遍，别指望 DOM 告诉你。

还有一条是节奏问题。整批替换看起来很爽快，一次换掉几百颗，代价是同时失去几百颗的纠错余量，窗口里出一次错就是一次事故。分批替换慢一点，但每一批都能回滚。

## 判读与实操

```bash
# 主机侧网卡：物理层错误计数（NVIDIA/Mellanox 命名示意）
ethtool -S <ifname> | grep -Ei 'crc|symbol|fec|phy|corrected'

# 交换机侧：端口物理错误与 FEC 统计
show interface <intf> counters errors
show interface <intf> transceiver detail        # DOM：收发光功率、温度、偏置电流
```

两条命令拿到的是累计值，落进时序库以后才有用。采集侧要做两件事：一是按分钟算一阶差分，把「累计值」转成「增量」；二是把增量除以端口的期望包数，得到丢失率，否则 200 这个数在面板上没有意义。

阈值思路，具体数字按模块规格与厂商建议填。CRC 缓慢上涨而丢包为 0，属于劣化前兆，仍在 FEC 能力内，记为观察对象、排窗口更换；FEC 未纠正块增长，说明劣化加剧、接近丢包，提高优先级尽快更换；收光功率低于规格下限或持续下降，是物理层问题，先清洁再看是否换件；单 lane 功率异常而其余正常，按模块更换处理；flap 反复 up/down，是接触或器件问题，优先处理，避免路由震荡。

自动化的落点是一条链：**路径劣化告警 → 路径集合与拓扑求交 = 候选端口 → 查 CRC/FEC 增量与 DOM → 命中规则自动建单并附证据**。人工只剩确认与更换。MTTR 从小时压到分钟，靠的就是把前两步的比对交给机器。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：完整讲一颗劣化光模块的旅程：从光功率开始漂移，到训练任务变慢，到被定位更换。按时间线说清每一层监控在什么时刻看到了什么。

::: details 参考答案与评分维度

1. T+0 起，光功率缓慢下降，误码率上升，FEC 纠错计数开始增长。链路完全正常，只有物理层计数器在动，第三层先有信号。
2. T+n，FEC 纠错能力被吃掉一部分，出现零星未纠正块，链路偶发丢包与重传。哈希到这条链路的少数 ECMP 路径时延抬升、抖动变大，第一层路径级探测先发现「哪条路径」。
3. T+n 稍后，RoCE 侧该路径上的流触发 PFC / ECN 异常，集合通信变慢，NCCL 可能超时。设备级聚合指标仍然显示正常。
4. 定位阶段，路径集合与拓扑求交得到候选端口，查 CRC / FEC 增量锁定端口，读 DOM 确认功率漂移，换件。

**评分维度**

- 时间线正确，体现「物理层信号早于业务症状」（必需）
- 三层信号的分工清楚（必需）
- 指出聚合指标被稀释、任务侧只看到慢（必需）
- 补出自动化闭环（加分）

:::

**必答 Q2**：「端口 CRC 错误数上涨但丢包数为 0」说明什么？该不该处理？为什么这是最好的抢修窗口？

::: details 参考答案与评分维度

说明物理层已经在劣化，误码率上升，但 FEC 还能把错误纠回来，所以没有表现为丢包。**应当处理**，并且转为主动运维对象。

这是最好的窗口，理由三条。此时业务无感，更换能排在计划窗口，不影响训练。一旦 FEC 纠错能力耗尽转为丢包，就会触发 RoCE 重传、PFC / ECN 异常甚至任务中断，还可能付出 checkpoint 回退的代价。从「纠错压力上升」到「开始丢包」通常有几天以上的时间差，这个差值就是提前量。

**评分维度**：说出「FEC 掩盖、即将丢包」（必需）。明确应主动处理（必需）。给出提前量的价值与回退代价（加分）。

:::

**自测 Q3**：一个端口 CRC 累计 400 万、增量 0，另一个累计 3400、每分钟增量 200。先处理哪个？把 200 这个数换算成对被影响流有意义的口径。

::: details 参考答案与评分维度

先处理第二个。累计值是历史总和，换过模块也不清零，不能作为判据；增量才是当前状态。

换算：400G 端口每分钟约 20 亿个包，200 个未纠正块对应包丢失率 1e-7。全网口径下这是噪声，对走这条路径的 RDMA 流就是每分钟两百次重传，两小时的训练步累计两万多次。

**评分维度**：明确按增量判断（必需）。给出 1e-7 与每分钟重传次数的换算（必需）。指出要看窗口内的趋势而非单点（加分）。

:::

**自测 Q4**：路径级探测在 RoCE 网络里怎么避免把正常的拥塞降速误报成路径劣化？

::: details 参考答案与评分维度

多信号交叉验证，三条。

1. 同期该路径的 ECN 标记率若同步上涨、PFC 与丢包正常，更像 DCQCN 在正常工作。
2. 用基线区分「跟着训练步起落的周期性抖动」与「持续性劣化」。前者随训练节奏出现，后者不随节奏消失。
3. 看形态。劣化是单调漂移，属于物理过程；拥塞是脉冲式。

答出「探测数据与设备遥测交叉验证」即达标。

**评分维度**：给出至少两种交叉手段（必需）。提到单调漂移与脉冲的形态差异（加分）。

:::

## 小结

十几万个光模块，唯一的模拟器件、唯一的可插拔件，所以集群里每天都有模块在坏。完全失效好查，端口直接 down。难的是劣化：链路还通，CRC 在涨，FEC 硬扛着，所有「通」的指标都正常。

FEC 收的是余量。KP4 能纠 544 符号块里的 15 个符号错误，pre-FEC BER 到 2.4e-4 量级才吃满，这段斜坡从几天到几个月不等，它就是抢修期。

计数器只能看增量。累计 400 万增量 0 的端口什么也不用做，累计 3400 每分钟涨 200 的端口要排窗口。200 换算下来是 1e-7 的丢失率，全网看是噪声，一条流看是每分钟两百次重传。

聚合指标看不见，因为分母太大。一条链路占一台 64 端口交换机的 1.5%，全网丢包率涨十倍也够不着阈值。

三层信号才能闭环：路径级探测发现哪几条路径不对劲，路径集合与拓扑求交得到候选端口，CRC 与 FEC 确认，DOM 读出功率漂移，换件。

::: tip 本课要点

**症状在语义层，根因在一颗模拟器件上。**

- 规模：万卡集群十几万光模块，唯一模拟器件加唯一可插拔件，**每天都有坏的**
- 完全失效好查，**劣化最费时间**：链路通、CRC 涨、FEC 硬扛；单 lane 劣化只掉一份带宽
- FEC 收的是余量，三段斜坡：全纠、吃紧、耗尽，**斜坡长度就是抢修窗口**
- **看增量不看累计**。400 万增量 0 不用管，3400 每分钟涨 200 才要管
- 200 块/分钟 = 1e-7 丢失率，全网是噪声，单条流是每分钟两百次重传
- 看不见的原因在分母：一条链路占 64 端口交换机的 1.5%
- 三层信号：**路径级探测发现 → CRC / FEC 定位端口 → DOM 确认模块**
- RoCE 下防误报：ECN 交叉验证、形态判断（漂移对脉冲）、与训练节奏对齐

:::

## 思考

留一个思考题：换件之后 FEC 纠错计数仍然维持，先怀疑新模块，还是先怀疑清洁度与连接器。

这一讲的坑都很小，代价都不小：一次是把存量当现状，一次是把全网当分母，一次是等告警响了才动。希望读者们今后能少犯这样的错误。
