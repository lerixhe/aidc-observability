量级很容易失算。一万台设备、每台 500 条序列、每秒一次，就是每秒 500 万个点。按每点 20 字节算，一天 8.6 TB 原始体积，列存压缩 5 到 10 倍之后还有 0.9 到 1.7 TB，三副本再乘三。一周的数据就能吃掉一个机架的盘位。

从设备到可查询之间隔着五段链路，每段都有自己丢数据的方式，多数还是静默的。这一层没有魔法，只有取舍：留什么、留多久、丢得起什么。

## 交付

- 从设备订阅到可查询的五段链路，以及每段丢数据的具体形态
- 原始、降采样、聚合三档保真度的体积与能回答的问题
- 给定规模算出点速率、日增量与压缩后的存储需求
- 事件时间与处理时间的区别，迟到数据怎么把窗口结果搞偏
- 管道自己的三条 SLO，以及事故期间怎么判断少了的数据是网络丢了还是管道丢了

## 五段链路，五个丢点

```text
设备（gNMI 订阅）
  → 采集器（订阅管理、缓冲、编码）
    → 传输（Kafka 主题，按设备分区）
      → 流处理（解析、聚合、降采样）
        → 存储（列存或时序库）
          → 查询（面板、告警、RCA）
```

| 段 | 丢法 | 表现 |
|---|---|---|
| 设备侧 | 订阅被挤掉、采样缓冲溢出 | 某台设备的数据突然缺失，没有告警 |
| 采集器 | 出口阻塞、本地队列满 | 部分序列断点，日志里刷 error |
| 传输 | 生产端超时、分区不可用 | 一段时间的数据整体空洞 |
| 流处理 | 解析异常抛错、checkpoint 回滚 | 重复或跳过一段窗口 |
| 存储 | 写入失败、合并压力过大 | 查询结果偏少，看不出少了 |

这张表的用处是排查顺序。查询结果异常时从上游往下查，五段各有各的可观测信号，猜不出来。

## 保真度三档

| 档 | 保留什么 | 体积 | 能回答的问题 |
|---|---|---|---|
| 原始 | 每个采样点，原样 | 100% | 微突发、尖峰形态、精确时序 |
| 降采样 | 秒级聚合到分钟，保留 max 与均值两条线 | 约 1/60 | 趋势、容量、基线对比 |
| 聚合 | 只留百分位与峰值的日汇总 | 约 1/3600 | 长期基线、月报、容量规划 |

多数团队只做后两档，然后在第一次微突发事故里发现自己答不出「峰值到底多高」。`labs/08-pipeline` 把这件事压到一分钟能跑完：

```bash
cd labs/08-pipeline
make run     # 四档体积 + 事故窗口查询对照 + 背压丢点
make test    # 14 个单测
```

同一份 1 小时的秒级数据，四档落盘，阈值 400 KB：

```text
二、事故窗口查询（t=2400..3000，共 600 s）
档位         桶数   点数   峰值KB   P99KB   均值KB  告警  短板
raw          600    600    520.0   520.0   213.6   是    完整信息，可定位到秒
1m(max)       10    600    520.0   520.0   213.6   是    峰值保住，时间分辨率降到分钟
1m(mean)      10    600    213.6   213.6   213.6   否    峰值丢失，短时冲顶被摊平
1d(max)        1   3600    520.0   520.0    53.2   是    峰值保住，但答不出哪一分钟
```

`1m(mean)` 那一行的峰值等于均值：520 KB 的短时冲顶被摊平成 213 KB，落在 400 KB 阈值以下，告警直接不响。落盘体积还跟 `1m(max)` 一模一样，白丢了一整个告警。

所以降采样必须保留 `max`，不能用均值代替。同理，监控接口时同时存平均 RT 与 P99，只存均值的话抖动永远不出现在图上。要求再高一点，保留 p99 与水线直方图，能答出「峰值持续了多久」这种问题，均值加 max 两档答不出。

时间序列数据库的 rollup 配成「5 分钟均值」，这是在丢信息，不是压信息。一个 5 分钟内发生、持续 200 微秒的队列尖峰，在均值里贡献接近于零，查询窗口越长，这类尖峰消失得越彻底。

## 容量怎么算

按一万台设备、每台 500 条序列、每秒一次估算：

```text
点速率      = 10,000 × 500 × 1  =  5,000,000 点/秒
每日点数    = 5e6 × 86,400       ≈  4.3e11 点/天
原始体积    = 4.3e11 × 20 B      ≈  8.6 TB/天
列存压缩比  ≈ 5–10 倍（时序数据）
落盘体积    ≈  0.9–1.7 TB/天
```

一周原始数据 6 到 12 TB，还没算索引与副本。三个副本一乘，方案就得回去重做。

保留策略是可行性前提，照下面这张表改就行：

| 数据 | 保留期 | 理由 |
|---|---|---|
| 原始秒级序列（关键端口与队列） | 3 到 7 天 | 事故回溯窗口，价值随时效衰减 |
| 分钟级降采样（含 max 与 p99） | 90 天 | 基线与季度对比 |
| 日聚合 | 1 年以上 | 容量规划与年度复盘 |

「关键端口」得落实成规则：全量原始数据留不下，把 PFC、ECN、队列水线这三类高价值序列单独提保留期，其余降档。

容量驱动是维度乘积，不是设备台数。3000 台服务器、每台 8 个网口、每口 8 个队列，序列数是 19.2 万条端口队列序列；三类指标一起采就是 57.6 万条，点速率 57.6 万每秒。加一个队列维度，量级翻一倍，比加一千台设备影响大得多。

## 背压与静默丢弃

Kafka 与 Flink 都有背压机制，它们保证的是不雪崩，不保证不丢数。

丢不丢，相当一部分由几个配置项决定。`acks=1` 加短超时，网络抖动时会丢一批。消费者落后太多时，如果开了 `auto.offset.reset=latest`，重启后直接从最新位置读，积压全跳过。这两条配置叠在一起，正好在事故期间丢掉最需要的那段数据。

1. **生产端 `acks=all`，重试给足。** 上游的数据补不回来，宁可慢，不能丢。
2. **消费端不做泳道式丢弃，做落盘积压。** 落后了先堆着，扩容消费者再追。
3. **每段埋丢弃计数。** 设备侧订阅被挤、采集器队列溢出、Kafka 生产失败、Flink 反压时长，四个计数器缺一个有盲区。

实验里背压那一段很直观：缓冲 200 点，消费速率从 1 降到 0.1，持续 300 秒。

```text
投递 3528 / 期望 3600 · 整体完整率 98.0%
丢弃 72 点 · 首次丢弃 t=2622 s
事故窗口（t=2400..3000）完整率 88.0% · 窗口内丢弃 72 点
健康窗口（t=0..2400）完整率 100.0%
```

98% 的整体完整率看起来可以接受，丢掉的 72 个点全部落在事故窗口内，事故窗口只剩 88%。只看整体数字，一切正常。

## 事件时间与迟到

窗口按什么时间切，决定结果对不对。

**处理时间**是到达流处理器的时刻，实现简单，结果不可复现，同样的数据重放会得到不同结果。**事件时间**是报文打上时间戳的时刻，结果稳定，但要处理乱序与迟到。

设备时钟有抖动，网络有传输延迟，Kafka 有堆积。三条叠加，一条 10:00:00 的数据可能 10:00:30 才到，按处理时间切窗口就落进了后一个窗口。事故复盘时，30 秒的偏移足以把同一团微突发里的先后顺序排错。

Flink 用水位线（watermark）处理这件事：系统持续声明「我确信某时刻之前的数据到齐了」，窗口等水位线过了再算。工程上有两个决定要提前做。

`allowed lateness` 给足，通常按分钟级给，2 到 5 分钟。给太小，迟到的数据被静默丢弃，而且日志里不一定有痕迹。

水位线别只看单个分区。按设备分区的主题，一台设备卡住就拖慢全局水位线，整个作业的输出都停在那一刻。常见做法是开空闲分区检测（`withIdleness`），把长时间没数据的分区从水位线计算里摘出去。

## 分区键与幂等

同一端口的两条数据顺序颠倒，会得出「ECN 先涨后降」这种假的因果。

分区键选设备 ID 或端口 ID，保证同一实体的数据进同一分区，消费端单线程处理就有序。

写入侧要幂等。ClickHouse 用 `ReplacingMergeTree` 按主键去重，或者 `INSERT` 前按窗口先查一遍。只要开了重试，幂等就不是可选项：至少一次投递必然带来重复，重复可以在查询时用主键去重，缺失没有任何补救手段。

## 经验映射

| 你已有的做法 | 在遥测管道里的位置 |
|---|---|
| 消息队列削峰与积压告警 | Kafka 消费者滞后监控 |
| 幂等消费与去重表 | ReplacingMergeTree 或窗口去重 |
| 流处理的 watermark 与窗口 | Flink 事件时间语义 |
| 服务自身指标（RED、USE） | 管道的延迟、完整率、丢弃计数 |
| 采样与聚合的取舍 | 原始、降采样、聚合三档 |

这套东西对后端没有新概念，新约束只有一条：**数据源是硬件**。你改不了设备的分区策略，也没法给交换机加背压，只能在自己这一侧把缓冲、重试、幂等做厚。

## 判读与实操

管道不监控自己，事故期间就分不清数据少了是网络坏了还是管道坏了。

| 指标 | 定义 | 告警阈值参考 |
|---|---|---|
| 端到端延迟 | 事件时间到可查询时间的差值，按 P99 | 超过采样间隔的 3 倍 |
| 序列完整率 | 实际点数 / 期望点数，按设备与序列统计 | 低于 99.5% |
| 丢弃计数 | 四段丢弃计数之和，按分钟看一阶差分 | 任意非零并持续 3 分钟 |

第二个指标要**按序列统计**，才能看出「某台设备的某类序列整体缺失」，那是设备侧订阅被挤的典型形态。按设备聚合会把它摊平。

```sql
-- 期望点数按 60 秒窗口内每序列应有点数计算（1 秒采样 = 60）
SELECT
    device, port, queue,
    count() AS actual,
    60 AS expected,
    round(count() / 60, 4) AS completeness
FROM telemetry.port_queue
WHERE ts >= now() - INTERVAL 5 MINUTE
GROUP BY device, port, queue
HAVING completeness < 0.995
ORDER BY completeness ASC
LIMIT 20;
```

数据缺失时先看 Kafka 主题的端到端延迟，再看设备侧订阅状态，两者一对照，边界立刻清楚。

```bash
# 主题积压与滞后
kafka-consumer-groups.sh --bootstrap-server <broker> \
  --describe --group telemetry-ingest

# 采集侧：订阅是否被设备重置
journalctl -u gnmic --since '30 min ago' | grep -i 'subscribe\|reset\|overflow'
```

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：某集群 3000 台服务器，每台 8 个网口，每口 8 个队列，采集队列水线、PFC、ECN 三类指标，1 秒一次。估算点速率与一周原始存储。

::: details 参考答案与评分维度

序列数 = 3000 × 8 × 8 = 19.2 万条端口队列序列，三类指标 57.6 万条。

点速率 = 57.6 万 × 1 = 57.6 万点每秒。日点数 ≈ 4.97e10，每点 20 字节约 1 TB 每天，压缩 5 到 10 倍后 100 到 200 GB 每天，一周原始 0.7 到 1.4 TB。

要点在序列数上：真正的成本驱动是维度乘积，端口 × 队列 × 指标，不是设备台数。

**评分维度**：序列数算对并指出维度乘积（必需）。给出压缩后的量级（必需）。提出降档策略而不是全量留存（加分）。

:::

**必答 Q2**：告警提示「某任务时段的数据查询结果为空」。给出从设备到存储的排查顺序，每一步看什么。

::: details 参考答案与评分维度

从上游往下。

1. 设备侧。订阅还在不在，有没有被别的订阅挤掉。看采集器日志里的 subscribe reset。
2. 采集器。本地队列是否溢出，出口是否报错，采样配置有没有被改。
3. Kafka。主题有没有数据写入，消费者组滞后多少，分区是否可用。
4. 流处理。解析是否抛错，checkpoint 是否反复回滚，作业是否重启。
5. 存储。写入失败率，合并任务是否堆积，查询的时间范围有没有写错。

每一步都有可量化信号。先分清是全体缺失还是单设备缺失，这一步能直接定位到对应段。

**评分维度**：顺序从上游到下游（必需）。每步给出可观测信号（必需）。先区分全体与局部（加分）。

:::

**自测 Q3**：降采样为什么必须保留 max，只留均值会漏掉哪类故障？

::: details 参考答案与评分维度

均值会摊平短时尖峰。200 微秒的队列顶满，摊进 5 分钟窗口后贡献接近零，520 KB 的冲顶变成 213 KB 的均值上升。

漏掉的是微突发类故障：incast 尖峰、PFC 瞬时反压、带宽抢占。这几类正是智算网络最常见、也最容易被「指标正常」掩盖的故障形态。

**评分维度**：说清摊平效应（必需）。举出至少一类被漏掉的故障（必需）。

:::

**自测 Q4**：管道用 `auto.offset.reset=latest` 会造成什么后果，什么时候这条配置看起来「没问题」？

::: details 参考答案与评分维度

消费者重启时如果组内没有有效 offset，会从最新位置读起，跳过全部积压。事故期间重启一次，丢掉的正是最需要的那段。

它看起来没问题的时候是稳态：流量正常、消费者不掉线、没有重启、没有积压。问题只在故障叠加时暴露，而那正是最不该丢数据的时刻。

**评分维度**：说清重启跳过积压（必需）。指出问题只在叠加场景暴露（加分）。

:::

## 小结

从设备到查询窗口隔着五段：设备、采集器、传输、流处理、存储。每段都能静默丢数据，排查从上游往下走。

保真度分三档。原始留三到七天，分钟级留九十天，日聚合留一年。降采样必须保留 max，均值会把 200 微秒的冲顶摊平成一条平线，520 KB 变 213 KB，400 KB 的告警阈值一次都不会触发。

量级要按维度乘积算，不是按设备台数。点速率是频率乘设备数乘路径数，一天 4.3e11 个点，压缩后还有 TB 级，三副本再乘三。

管道的口径比业务更保守：至少一次投递，幂等写入，宁可重复不能缺失。管道自己要有三条 SLO，端到端延迟、序列完整率、丢弃计数，否则事故期间分不清数据少了是哪一段的责任。

::: tip 本课要点

**留什么、留多久、丢得起什么，这三件事要在出事之前定下来。**

- 五段链路五个丢点：**设备、采集器、传输、流处理、存储**，排查从上游往下
- 保真度三档：原始 3 到 7 天、分钟级 90 天、日聚合 1 年
- **降采样必须保留 max 与 p99**。均值把 520 KB 的冲顶摊成 213 KB，阈值 400 KB 的告警直接不响
- 容量按维度乘积算（端口 × 队列 × 指标），3000 台设备就能到 57.6 万序列
- 至少一次投递加幂等写入，宁可重复不可缺失
- 管道自身三条 SLO：端到端延迟、序列完整率（按序列统计）、丢弃计数

:::

留一个思考题：只能给管道加一条告警，你选端到端延迟还是序列完整率，为什么。
