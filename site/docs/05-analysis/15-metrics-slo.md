在平时的值守工作中，有时候需要从成千上万条序列里找出真正动了的那几个，再拼出一条能讲给人听的因果链来。这里就有一个问题，如何从海量指标里找出有问题的那个口径？

最直接的做法是这样，一条命令把设备上所有路径都订阅上：

```bash
gnmic -a <device>:57400 -u <user> -p <pass> --insecure subscribe \
  --path '/' --mode stream --stream-mode sample --sample-interval 1s
```

跑起来十分钟，设备 CPU 上去，会话被踢，采集器内存也涨。换一条路，登机敲 `show interface counters`，64 个端口一行一个，八列计数，几百行刷下来，人眼找不到重点。

两个做法都拿到了「全部数据」，也都有两个很明显的**缺点**。

一、没有分页，也没有条数上限，一次拉回来几十万行，采集端还得把这一坨全塞进内存。真实设备上一台交换机光队列计数就是 64 端口乘 8 队列，再乘上指标数，一次全量扫描就是几万行起步。

二、扫描本身要吃设备 CPU，而这台设备正在给训练供数。全量订阅在交换机上就是一次全表遍历，管控面的处理能力本来就不富余，扫描期间转发面抖一下，业务侧看见的是 PFC 涨了、时延跳了，你还不确定这是真故障还是自己扫出来的。

面对这两个显著的缺点该怎么办呢？

办法不是找一个更强的扫描，而是在扫之前把「扫什么」定下来。指标口径这件事有七个性质，值得先摆出来：

1. 复杂度还是 O(n)，但可以分步走，按端口分批、按窗口滚动，不必在一次查询里把全库扫完；
2. `sample_interval` 只是一个提示，设备给的是「尽量」，负载高的时候漏点是常态，返回的点数可多可少；
3. 同扫描一样，它也支持维度筛选，`device`、`port`、`queue`、`priority` 四个标签把范围卡住；
4. 服务器不需要为口径保存状态，口径的唯一状态就是写进指标名和文档的那个定义式；
5. 聚合结果可能会有重复，窗口边界重叠、多副本重试、消息重放，同一个包会被数两次，这点非常重要；
6. 口径改版的过程中如果有数据写入，改动前后的数据能不能对上是不确定的；
7. 单次查询返回的是空的，并不意味着数据没了，而要看序列还在不在更新。

第 5 和第 7 两条最容易骗人。前者让你把一次事故算成两次，后者让你把采集器掉线看成风平浪静，面板上一片 0，看着像天下太平，实际是所有序列都没在涨。所以判据里必须有「序列是否还在更新」这一项，不能只有「值是否超阈值」。

## 按维度筛

在使用之前，让我们先往库里插一批数据。一台 64 端口交换机，每端口 8 个队列、8 个优先级、3 类指标，序列数就是 64 × 8 × 8 × 3 = 12288 条，一千台这样的设备就是 1228 万条。

好，库里现在有了 1228 万条序列，接下来我们找出 PFC 相关的那些。

查询提供了三个参数，第一个是**时间窗口**，第二个是**维度筛选**，第三个是**分组粒度**。第一次查时窗口从最近五分钟开始，然后把返回结果里最早的时间戳作为下一次的起点，一直查到当前时刻为止。

```text
# 第一轮：只取 PFC 这一类，按端口收拢
> query -m pfc_pause_seconds_rate{device="leaf-11"} --start 5m --group port
1) "t=1702"   2) [s1: 0.02  s2: 0.01  s3: 0.31  ... s64: 0.02]

# 第二轮：把 s3 那一列拆到优先级
> query -m pfc_pause_seconds_rate{device="leaf-11", port="s3"} --group priority
1) "t=1702"   2) [p0: 0  p1: 0  p2: 0  p3: 4.82  p4: 0 ...]
```

从上面的过程可以看到虽然你只筛了端口，返回的结果仍然是一串序列。因为这个筛选不是限定返回的序列数，而是限定设备单次参与聚合的维度组合数（约等于）。如果只看端口不拆优先级，一条 4.82 秒的 pause 会被 8 个优先级和 7 个空端口摊薄，看到的只有 0.31。

这件事的结论很直接：**口径的粒度决定了你能看见什么，而不是精度。** 序列数不够细的时候，不是「看得糊一点」，是「看不见」。

## 三个口径

PFC pause 至少有三个可采的量。**帧数**回答反压发生了几次，**时长**回答每次持续多久，**范围**回答波及多大面积。

只报帧数是常见错误。两次事故帧数都是 12 万，恢复代价能差 100 倍。A 场景每帧只 pause 一个 quanta，即 512 bit time，10 Gb/s 链路下约 51.2 微秒，累计 12 万帧，总停顿 6 秒；B 场景每帧 pause 满 65535 quanta，同样 12 万帧，总停顿接近 9 小时。

```text
pause_quanta = 1      → 512 bit × 0.1 ns/bit  ≈ 51.2 µs
pause_quanta = 65535  → 51.2 µs × 65535       ≈ 3.36 s
```

所以口径要成对出现：**帧数回答频率，时长回答代价。** 只看请求次数、不看总耗时，看不出服务在卡。

帧数不为零本身不说明故障。健康网络里 PFC 应该罕见，但不该为零，零可能意味着链路没有瞬时拥塞、水线阈值设得过松、或者流量根本没打满。反过来说，跑满带宽的训练任务有稳定的 PFC 背景值。判断看三个量：变化率、时长分布、受影响端口数，绝对值说明不了什么。

ECN 标记率的分子很清楚，被标记的报文数，麻烦在分母。用该端口发出的全部报文，会被小流稀释；用该端口该优先级发出的报文，最接近真实，但要按优先级拆维度，数据量大；用具 ECN 能力的报文最精确，但要知道对端是否协商了 ECN；用收到 CE 标记的报文则是语义混乱，分子分母混在一起。生产上一般选第二个，并把维度写进指标名：

```text
ecn_mark_ratio{device, port, priority} =
    rate(ecn_marked_packets_total{device, port, priority}[1m])
  / rate(ecn_capable_packets_total{device, port, priority}[1m])
```

口径写死之后跨设备才可比。否则会遇到这种场面：一台设备标记率 3%，另一台 0.1%，差十倍，原因只是两台设备的优先级配置不同。

队列水线有三个数，三个用途。瞬时值用 SAMPLE 1 秒或更细采，回答现在的状态，实时面板用；窗口峰值取 1 分钟内的 max，回答微突发有没有把队列顶满；窗口均值做长期占用与容量规划。面板上放均值，事故复盘用峰值，**队列水线的均值几乎没有诊断价值**。一条链路 99% 的时间队列为空，1% 的时间顶满，均值看起来很温和。队列本身是双峰分布，均值落在两峰之间，既不代表空闲也不代表拥塞。

还有一个单位问题。有的设备报字节，有的报 cell 数，有的报百分比。跨厂商混部先统一单位，否则同一个阈值没法用。

## 分位数为什么不能平均

多个实例的 p99 取平均，得到的数字既不是全局 p99，也不对应任何真实用户。

原因跟分位数本身怎么算出来有关。分位数不是一条可以直接相加的量，它来自一份排序后的分布；你对若干份分布各取一个点再平均，只是把几个「代表性时刻」平均了，原来那份排序信息全丢了。

正确做法是各实例上报直方图桶，聚合时用 `histogram_quantile` 重算：

```text
# 错误：把各端口的 p99 平均
avg(port_latency_p99)

# 正确：聚合直方图后重算
histogram_quantile(0.99,
  sum by (le) (rate(port_latency_bucket[5m]))
)
```

这也是这一讲最像「字典扩容」的一个点：分位数是查表查出来的，桶的边界一旦定了，精度就定了；桶可以相加，分位数不能。

## 桶怎么划

直方图的桶通常是按指数增长的：1 微秒、2 微秒、4 微秒、8 微秒，一直排到秒级。为什么是指数而不是等宽，理由跟字典的数组长度取 2^n 是一个道理：**低位的分辨率要细，高位的分辨率可以粗。**

时延在 5 微秒和 10 微秒之间的差别，对判读来说很要紧；在 5 秒和 10 秒之间的差别，对人来说都是「卡住了」。指数桶自动把这种分布的不均匀吃掉了，代价是高位数上的插值误差大一些，这是可以接受的。

这条设计还有一个副作用值得知道：桶一旦定了就不能随便改。改桶等于改口径，历史数据和新数据不可比，跟口径改版那一条性质是同一件事。

## 同一份数据，三种形状

口径的差别，在事故里才看得出来。`labs/09-slo` 用同一份 30 天的指标流跑了三种算法：

```bash
cd labs/09-slo
make run     # 三种口径的可用率 + 错误预算 + 多窗口燃烧率
make test    # 19 个单测
```

```text
窗口 30 天 · 43200 个一分钟窗口 · 请求 1166378520 条 · 失败 887511 条 · 目标 99.900%

  口径                可用率      差目标 判定       分母口径说明
  时间口径          99.780%   -12.0bp 未达标      分母是分钟数，夜间小流量事故与白天大流量事故权重相同
  事件口径          99.924%     2.4bp 达标       分母是请求数，夜间事故被低流量稀释
  分位口径          99.803%    -9.7bp 未达标      只看时延，完全忽略失败率：失败快也是「达标」
```

三个数都叫可用率，一个达标两个未达标，最宽与最严相差 14 个基点。所以「可用率 99.9%」这句话，不说口径等于没说。

形状的差别来自事故落在什么时段。同一份数据里有五次注入的事故：

```text
  事故                       时段                 持续        坏分钟        坏请求
  夜间大事故（劣化一小时才被发现）   d4 02:00          60 分         60     112376
  白天大事故（PFC 风暴）      d13 14:00         15 分         15     177882
  白天小抖动                d21 10:00          5 分          5       9782
  夜间小抖动                d28 03:00          5 分          5       1500
```

第一行和第二行值得对照着看。夜间那次坏了 60 分钟，白天那次只坏了 15 分钟，时间口径上第一次是第二次的四倍；请求数上第一次只有 11 万，第二次是 17 万。**同一场事故，时间口径说它更重，事件口径说它更轻，两个都没算错。**

这就是分母的意义。运维关心「坏了多久」，因为他要排窗口；业务关心「坏了多少请求」，因为它要算 SLA。两个口径都得有，但必须写清楚用于哪一件事。

第三行那个「分位口径」更值得警惕。它只看时延，一个直接返回错误的请求在时延上看是最优的，失败得越快，越「达标」。

## 写口径，写 SLO

SLI 是好事件占有效事件的比例，SLO 是这个比例的目标值。难点全在「好事件」怎么定义。网络侧有四个候选：带宽达成率，好事件是实际吞吐不低于承诺的 90%；P99 时延，好事件是端口到端口时延低于阈值；序列完整率，好事件是实际点数不低于期望的 99.5%；训练步耗时，好事件是单步耗时不超过基线的 1.1 倍。

第四个最值得投。前三个是手段，第四个是结果。集群好不好，训练任务自己会说话。

SLO 给一个数字就够，但要带窗口：

```text
SLO-1  训练步耗时 P95 ≤ 基线 1.1 倍，30 天滚动窗口，目标 99%
SLO-2  遥测序列完整率 ≥ 99.5%，按天统计，目标 99.5%
SLO-3  故障发现时间 P90 ≤ 3 分钟，按周统计，目标 95%
```

99% 的月度 SLO，允许的不可用时间是 7.2 小时。99.9% 是 43 分钟。99.99% 是 4.3 分钟。千卡集群上一次 PFC 风暴导致的训练中断通常 20 到 60 分钟，含发现、定位、恢复三段，这意味着 99.9% 的月度预算，一个月只够摊一到两次事故。

教你一个把预算讲给老板听的说法：99.99% 一个月给你 4.3 分钟，一次训练中断从发现到恢复按 20 分钟算，你连一次都吃不下。要么把目标改成 99.9%，43 分钟留给交付节点；要么砸钱做冗余、自动切换、跨轨重路由，把单次中断压到分钟级。这个计算的价值不在数字本身，它逼你回答一句：**SLO 订的是承诺，还是期望。**

预算定完，告警按燃烧率来配，不要按绝对值。短窗抓突发，长窗抓趋势，两个窗同时超阈才报：

```text
  窗口              燃烧率         阈值 状态
  5m           200.0×      14.4× 超阈值
  60m           29.6×      14.4× 超阈值
  30m           63.5×       6.0× 超阈值
  360m           3.0×       6.0× 正常
  判定：快烧两窗口同时超阈值 → page（人现在就该看）
```

单看 5 分钟，一次抖动就能把燃烧率打到 200 倍，天天误报；单看 6 小时，刚开始的事故摊进长窗里被稀释成 3 倍，看着正常，等它涨上来已经晚了。快慢两个窗同时超阈值才叫人，这是唯一能同时避开误报与漏报的配法。

## 高基数就是指标世界里的大 key

一条序列就是一个维度组合，组合多了，序列就爆炸。一台 64 端口交换机，每端口 8 个队列、8 个优先级、3 类指标，序列数就是 12288 条，一千台就是 1228 万条。这个数字一进时序库，写入、查询、压缩三头都疼，一次 `count by` 就要扫全表。

如果你观察到指标库的内存与磁盘大起大落，这极有可能是因为高基数导致的，这时候你就需要定位出具体是哪个指标，进一步定位出具体的业务来源，然后再改采集侧的设计。

**那如何定位高基数呢？** 为了避免给线上设备带来卡顿，这就要用到分步查询，对筛出来的每一类指标，先看它下面挂了多少条序列，把序列数最多的前 N 名拿出来：

```bash
# 每台设备上每个路径返回多少条序列（基数探查）
gnmic -a <device>:57400 -u <user> -p <pass> --insecure get \
  --path '/interfaces/interface/state/counters' | jq '.updates | length'

# 时序库侧：每个指标名下的序列数，从上往下排
curl -s 'http://prometheus:9090/api/v1/label/__name__/values' | jq -r '.data[]'
```

基数最大的那几个指标，通常是带队列和优先级两个标签的，它们的诊断价值最高，存储成本也最高。处置办法是限制维度：只对关键端口开队列级订阅，其余端口只留端口级；只对 PFC 与 ECN 保留优先级维度，其余指标打平。

如果你担心这样查会大幅抬升设备 CPU 导致误报，还可以加一个间隔参数，每查一批就歇一会儿，ops 就不会剧烈抬升，代价是扫描时间变长。

**加一个标签，量级翻一倍，比加一千台设备影响大得多。**

做指标治理时，这张表比任何面板都重要。它进 Git，改动走评审。


## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：给一个 PFC 相关事故写三条指标口径，要求能支撑「这是灾难级还是可忽略」的判断。

::: details 参考答案与评分维度

三条分别覆盖频率、代价、面积。

1. `pfc_pause_frames_rate`：pause 帧数的一阶差分，按端口与优先级拆维度，回答反压发生了多少次。
2. `pfc_pause_seconds_rate`：累计 pause 量化值换算成秒后的一阶差分，同维度，回答累计停了多久，这是判断严重度的核心。
3. `pfc_affected_ports_ratio`：有 pause 计数变化的端口数除以端口总数，回答波及多大面积，接近 1 就意味着风暴。

再加一条约束：三条都与上周同期比比值，判断标准是比值超过 2 倍，不是某个固定阈值。

**评分维度**：三条分别覆盖频率、时长、范围（必需）。指出时长是严重度核心（必需）。提出同比或基线对比（加分）。

:::

**必答 Q2**：老板要求「网络可用性 99.99%」，算一遍错误预算，并说明这个目标在千卡集群里意味着什么。

::: details 参考答案与评分维度

99.99% 的月度窗口是 30 天，允许故障 30 × 24 × 60 × 0.0001 = 4.32 分钟。

千卡集群上一次训练中断从发现到恢复通常 20 到 60 分钟。这个目标不允许任何一次完整的训练中断，一个月连一次 5 分钟的故障都吃不下。

结论两条。把目标改成 99.9%，43 分钟预算留给关键的训练窗口与交付节点。或者砸钱做冗余、自动切换、跨轨重路由，把单次中断压到分钟级。

**评分维度**：预算算对（必需）。把预算与单次恢复时间对照（必需）。给出改目标或改架构两条路（加分）。

:::

**自测 Q3**：为什么队列水线的均值几乎没有诊断价值，面板上应该放什么。

::: details 参考答案与评分维度

队列是双峰分布，要么空，要么在短窗口被顶满。均值落在两者之间，既不反映空闲也不反映拥塞。

面板上放窗口峰值与超阈值时长。峰值给最坏情况，时长给这种情况持续了多久。

**评分维度**：说清双峰或摊平效应（必需）。给出峰值与超阈值时长（加分）。

:::

**自测 Q4**：两个团队对同一批数据得出 3% 与 0.1% 两个 ECN 标记率。列出三种可能的口径差异。

::: details 参考答案与评分维度

分母不同，一个用全部报文，一个只算该优先级的报文。维度不同，一个按端口聚合，一个按队列拆开后再算。时间窗口不同，一个用 1 分钟，一个用 5 分钟，拥塞被平滑掉了。

解法是把口径写进指标定义并版本化，争谁对没有意义。

**评分维度**：给出至少两种差异来源（必需）。指出解法是口径治理而非辩论（加分）。

:::

## 小结

全量拉计数器是条死路：一次几十万行，人看不过来，设备还要为这次扫描付出 CPU。换成按维度筛、按窗口滚，七条性质里有两条要特别当心：结果可能重复，返回 0 可能是采集器掉了。

PFC 三个口径缺一不可。帧数看频率，时长看代价，范围看面积。两次事故帧数一样，时长能差一百倍，只报帧数等于没报。ECN 标记率的关键在分母，最常用「该端口该优先级发出的包数」，写进指标名里，跨设备才可比。队列水线的均值几乎没有诊断价值，尖峰永远被摊平，面板上要放窗口峰值和超阈值时长。

同一个故障在不同口径下是两种形状：时间口径说夜间那次更重，事件口径说白天那次更重，两个都对，用哪个取决于你要排窗口还是算赔付。

SLI 最后要落到业务侧，训练步耗时最有意义。错误预算算完再谈承诺，99.99% 一个月只给 4.3 分钟。分位数不能跨实例平均，要聚合直方图后重算。高基数指标就是指标世界里的大 key，一个队列标签能把序列数翻八倍。

::: tip 本课要点

**口径不定，面板就是辩论场。**

- 全量拉计数器两条硬缺陷：**没有分页、扫描自己吃掉设备 CPU**
- 七个性质里最要紧的两条：**聚合结果可能重复、返回 0 可能是采集器掉了**
- PFC 三个口径缺一不可：**帧数看频率、时长看代价、范围看面积**。1 quanta 等于 512 bit time，10 Gb/s 下约 51.2 微秒
- ECN 标记率的分母必须写死，最常用「该端口该优先级发出的包数」
- 队列水线只看均值等于看不见故障，面板放**窗口峰值与超阈值时长**
- 同一份数据三种口径：时间 99.780%、事件 99.924%、分位 99.803%，最宽与最严差 14 个基点
- 燃烧率要快慢两个窗成对看，5 分钟单看天天误报，6 小时单看会漏
- 一条坑：**分位数不能跨实例平均**，要聚合直方图后用 `histogram_quantile` 重算

:::

## 思考

留一个思考题：如果 SLO 只允许保留一个指标，你选训练步耗时的 P95 还是端到端时延的 P99。
