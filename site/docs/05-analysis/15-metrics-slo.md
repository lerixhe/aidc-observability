两个团队对着同一块面板争，一个说「PFC 涨了 300 倍」，另一个说「只有 0.3% 的端口有 pause」。两个人都没说错，他们用的分母不同。

数据到达之前，一切讨论都在这一步打转：同一个计数器拿出来，口径不同，结论相反。这一讲把三个核心指标的口径定下来，再讲 SLI 与 SLO 怎么写。

## 交付

- PFC pause 的三种口径，以及只报帧数为什么会漏掉灾难级事件
- ECN 标记率的分母怎么选，指标定义式怎么写
- 队列水线的瞬时值、峰值、均值各自能回答什么问题
- 把网络指标翻译成业务 SLI，写出带错误预算的 SLO
- 四种常见的口径反模式，包括分位数跨实例平均

## PFC：帧数只是故事的一半

PFC pause 至少有三个可采的量。

| 口径 | 原始字段 | 单位 | 说明什么 |
|---|---|---|---|
| pause 帧数 | out-pfc-pause-frames | 帧 | 反压发生了几次 |
| pause 时长 | pause duration | quanta 或微秒 | 每次反压持续多久 |
| 受影响范围 | 涉及端口数、优先级数 | 个 | 故障波及多大面积 |

只报帧数是常见错误。两次事故帧数都是 12 万，恢复代价能差 100 倍。

A 场景每帧只 pause 一个 quanta，即 512 bit time，10 Gb/s 链路下约 51.2 微秒，累计 12 万帧，总停顿 6 秒。B 场景每帧 pause 满 65535 quanta，同样 12 万帧，总停顿接近 9 小时。

```text
pause_quanta = 1      → 512 bit × 0.1 ns/bit  ≈ 51.2 µs
pause_quanta = 65535  → 51.2 µs × 65535       ≈ 3.36 s
```

所以口径要成对出现：**帧数回答频率，时长回答代价。** 只看请求次数、不看总耗时，看不出服务在卡。

帧数不为零本身不说明故障。健康网络里 PFC 应该罕见，但不该为零，零可能意味着链路没有瞬时拥塞、水线阈值设得过松、或者流量根本没打满。反过来说，跑满带宽的训练任务有稳定的 PFC 背景值。判断看三个量：变化率、时长分布、受影响端口数，绝对值说明不了什么。

## ECN 标记率：分母决定一切

分子很清楚，被标记的报文数。麻烦在分母。

| 分母选项 | 数值形态 | 问题 |
|---|---|---|
| 该端口发出的全部报文 | 被小流稀释 | 大流拥塞时比率很低，看着正常 |
| 该端口该优先级发出的报文 | 最接近真实 | 需要按优先级拆维度，数据量大 |
| 具备 ECN 能力的报文 | 最精确 | 需要知道对端是否协商了 ECN |
| 收到 CE 标记的报文 | 语义混乱 | 分子分母混在一起 |

生产上一般选第二个，并把维度写进指标名：

```text
ecn_mark_ratio{device, port, priority} =
    rate(ecn_marked_packets_total{device, port, priority}[1m])
  / rate(ecn_capable_packets_total{device, port, priority}[1m])
```

口径写死之后跨设备才可比。否则会遇到这种场面：一台设备标记率 3%，另一台 0.1%，差十倍，原因只是两台设备的优先级配置不同。

## 队列水线：瞬时、峰值、均值

三个数，三个用途。

| 形态 | 采法 | 能回答 |
|---|---|---|
| 瞬时值 | SAMPLE 1 秒或更细 | 现在的状态，实时面板用 |
| 窗口峰值 | 1 分钟窗口内的 max | 微突发有没有把队列顶满 |
| 窗口均值 | 1 分钟平均 | 长期占用，容量规划用 |

面板上放均值，事故复盘用峰值。**队列水线的均值几乎没有诊断价值。** 一条链路 99% 的时间队列为空，1% 的时间顶满，均值看起来很温和。队列本身是双峰分布，均值落在两峰之间，既不代表空闲也不代表拥塞。

还有一个单位问题。有的设备报字节，有的报 cell 数，有的报百分比。跨厂商混部先统一单位，否则同一个阈值没法用。

## SLI 怎么写

SLI 是好事件占有效事件的比例，SLO 是这个比例的目标值。难点全在「好事件」怎么定义。网络侧有四个候选：

| SLI | 好事件 | 有效事件 | 适用 |
|---|---|---|---|
| 带宽达成率 | 实际吞吐 ≥ 承诺的 90% | 所有测量窗口 | 容量与 SLA 结算 |
| P99 时延 | 端口到端口时延 ≤ 阈值 | 所有采样 | 拥塞诊断 |
| 序列完整率 | 实际点数 ≥ 期望的 99.5% | 期望点数 | 遥测管道自身 |
| 训练步耗时 | 单步耗时 ≤ 基线的 1.1 倍 | 所有训练步 | 最有业务意义 |

第四个最值得投。前三个是手段，第四个是结果。集群好不好，训练任务自己会说话。

SLO 给一个数字就够，但要带窗口。

```text
SLO-1  训练步耗时 P95 ≤ 基线 1.1 倍，30 天滚动窗口，目标 99%
SLO-2  遥测序列完整率 ≥ 99.5%，按天统计，目标 99.5%
SLO-3  故障发现时间 P90 ≤ 3 分钟，按周统计，目标 95%
```

## 错误预算

99% 的月度 SLO，允许的不可用时间是 7.2 小时。99.9% 是 43 分钟。99.99% 是 4.3 分钟。

千卡集群上一次 PFC 风暴导致的训练中断通常 20 到 60 分钟，含发现、定位、恢复三段。这意味着 99.9% 的月度预算，一个月只够摊一到两次事故。

这个计算的价值不在数字本身，它逼你回答一句：**SLO 订的是承诺，还是期望。** 订成期望没人当真，订成承诺就得配资源。

## 四条口径反模式

| 反模式 | 表现 | 改法 |
|---|---|---|
| 用均值做 SLI | 微突发被摊平，永远达标 | 换成 P95 或 P99 |
| 把「丢包率 0」当健康指标 | 无损网络里它天然为 0 | 换成 PFC 时长与 ECN 标记率趋势 |
| 分母随流量漂移 | 同一指标跨时段不可比 | 分母写进指标定义，版本化 |
| 分位数直接平均 | p99 平均之后没有统计意义 | 存直方图，聚合时重算分位数 |

第四个值得多说两句。多个实例的 p99 取平均，得到的数字既不是全局 p99，也不对应任何真实用户。正确做法是各实例上报直方图桶，聚合时用 `histogram_quantile` 重算。

```text
# 错误：把各端口的 p99 平均
avg(port_latency_p99)

# 正确：聚合直方图后重算
histogram_quantile(0.99,
  sum by (le) (rate(port_latency_bucket[5m]))
)
```

## 一张落地的口径表

做指标治理时，这张表比任何面板都重要。它进 Git，改动走评审。

| 指标 | 定义式 | 维度 | 采集 | 告警基线 |
|---|---|---|---|---|
| pfc_pause_sec | 累计 pause 时长的一阶差分 | device, port, priority | 1 s SAMPLE | 单端口 5 分钟内 > 10 秒 |
| ecn_mark_ratio | 标记包 / 该优先级发出的包 | device, port, priority | 1 s SAMPLE | 1 分钟内 > 5% 且连续 3 个窗口 |
| queue_peak_bytes | 窗口内队列占用最大值 | device, port, priority | 1 s SAMPLE | 达容量 80% 连续 5 分钟 |
| port_latency_p99 | 端口到端口时延的分位数 | device, port | INT 或探针 | > 基线 2 倍 |
| sequence_completeness | 实际点数 / 期望点数 | device, metric | 分钟窗口 | < 99.5% |

## 经验映射

| 你给微服务定 SLO 的做法 | 在智算场景里的对应物 |
|---|---|
| 选指标、定目标、算预算 | 同样三步，指标换成训练步耗时 |
| 超预算冻结变更 | 同样适用，灰度与变更节奏跟着预算走 |
| HTTP P99 与错误率 | 训练步耗时 P95 与 NCCL 超时率 |
| 用户旅程的服务依赖链 | 任务 → Rail → 链路 → 光模块的传导链 |

区别在「用户体验」的载体。IDC 里是 HTTP 的 P99 与错误率，这里是训练任务的每步耗时。网络指标退化成诊断用的中间量，不再是 SLI 本体。选定业务 SLI 之后，网络侧那一堆计数器才有明确的用途：解释业务 SLI 为什么掉了，以及该从哪一层下手。

## 判读与实操

预算定完，告警按燃烧率来配，不要按绝对值。短窗抓突发，长窗抓趋势，两个窗同时超阈才报。

```text
1h 燃烧率 14.4  → 全部预算两天半内耗尽 → 立即处置
6h 燃烧率 6     → 五天耗尽           → 当天处置
3d 燃烧率 1     → 30 天正好用完       → 记录观察
```

实验用同一份 30 天的指标流，跑三个口径：

```bash
cd labs/09-slo
make run     # 三种口径的可用率 + 错误预算 + 多窗口燃烧率
make test    # 19 个单测
```

时间口径算出 99.780%，未达标；事件口径算出 99.924%，达标。两个数都叫可用率，判定相反。

第三个口径更值得警惕：分位口径只看时延，**失败得快也算达标**，一个直接返回错误的请求在时延上看是最优的。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：给一个 PFC 相关事故写三条指标口径，要求能支撑「这是灾难级还是可忽略」的判断。

::: details 参考答案与评分维度

三条分别覆盖频率、代价、面积。

1. `pfc_pause_frames_rate`：pause 帧数的一阶差分，按端口与优先级拆维度，回答反压发生了多少次。
2. `pfc_pause_seconds_rate`：累计 pause 量化值换算成秒后的一阶差分，同维度，回答累计停了多久，这是判断严重度的核心。
3. `pfc_affected_ports_ratio`：有 pause 计数变化的端口数除以端口总数，回答波及多大面积，接近 1 就意味着风暴。

再加一条约束：三条都与上周同期比比值，判断标准是比值超过 2 倍，不是某个固定阈值。

**评分维度**：三条分别覆盖频率、时长、范围（必需）。指出时长是严重度核心（必需）。提出同比或基线对比（加分）。

:::

**必答 Q2**：老板要求「网络可用性 99.99%」，算一遍错误预算，并说明这个目标在千卡集群里意味着什么。

::: details 参考答案与评分维度

99.99% 的月度窗口是 30 天，允许故障 30 × 24 × 60 × 0.0001 = 4.32 分钟。

千卡集群上一次训练中断从发现到恢复通常 20 到 60 分钟。这个目标不允许任何一次完整的训练中断，一个月连一次 5 分钟的故障都吃不下。

结论两条。把目标改成 99.9%，43 分钟预算留给关键的训练窗口与交付节点。或者砸钱做冗余、自动切换、跨轨重路由，把单次中断压到分钟级。

**评分维度**：预算算对（必需）。把预算与单次恢复时间对照（必需）。给出改目标或改架构两条路（加分）。

:::

**自测 Q3**：为什么队列水线的均值几乎没有诊断价值，面板上应该放什么。

::: details 参考答案与评分维度

队列是双峰分布，要么空，要么在短窗口被顶满。均值落在两者之间，既不反映空闲也不反映拥塞。

面板上放窗口峰值与超阈值时长。峰值给最坏情况，时长给这种情况持续了多久。

**评分维度**：说清双峰或摊平效应（必需）。给出峰值与超阈值时长（加分）。

:::

**自测 Q4**：两个团队对同一批数据得出 3% 与 0.1% 两个 ECN 标记率。列出三种可能的口径差异。

::: details 参考答案与评分维度

分母不同，一个用全部报文，一个只算该优先级的报文。维度不同，一个按端口聚合，一个按队列拆开后再算。时间窗口不同，一个用 1 分钟，一个用 5 分钟，拥塞被平滑掉了。

解法是把口径写进指标定义并版本化，争谁对没有意义。

**评分维度**：给出至少两种差异来源（必需）。指出解法是口径治理而非辩论（加分）。

:::

## 小结

PFC 三个口径缺一不可。帧数看频率，时长看代价，范围看面积。两次事故帧数一样，时长能差一百倍，只报帧数等于没报。

ECN 标记率的关键在分母，最常用「该端口该优先级发出的包数」，写进指标名里，跨设备才可比。队列水线的均值几乎没有诊断价值，尖峰永远被摊平，面板上要放窗口峰值和超阈值时长。

SLI 最后要落到业务侧，训练步耗时最有意义，网络指标退成诊断用的中间量。错误预算算完再谈承诺，99.99% 一个月只给 4.3 分钟，一次训练中断都装不下。分位数不能跨实例平均，要聚合直方图后重算。

::: tip 本课要点

**口径不定，面板就是辩论场。**

- PFC 三个口径缺一不可：**帧数看频率、时长看代价、范围看面积**。1 quanta 等于 512 bit time，10 Gb/s 下约 51.2 微秒
- ECN 标记率的分母必须写死，最常用「该端口该优先级发出的包数」
- 队列水线只看均值等于看不见故障，面板放**窗口峰值与超阈值时长**
- SLI 从业务侧选：训练步耗时最有意义，网络指标退为诊断中间量
- 错误预算算完再做承诺，99.99% 等于不允许一次完整中断
- 一条坑：**分位数不能跨实例平均**，要聚合直方图后用 `histogram_quantile` 重算

:::

留一个思考题：如果 SLO 只允许保留一个指标，你选训练步耗时的 P95 还是端到端时延的 P99。
