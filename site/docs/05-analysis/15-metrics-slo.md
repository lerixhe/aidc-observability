如果要用一句话来描述这一讲，我想应该是：口径不写清楚，面板就是辩论场。

上一讲解决了数据怎么到达。这一讲解决数据怎么变成判断。

先说一个常见事故。两个团队对着同一块面板争论，一个说"PFC 涨了 300 倍"，另一个说"只有 0.3% 的端口有 pause"。两个人都没说错，他们用的分母不同。

## 学完这一讲，你应该能

- 说清 PFC pause 的三种口径，并解释只报帧数为什么会漏掉灾难级事件
- 给 ECN 标记率选一个固定分母，并写出完整的指标定义式
- 区分队列水线的瞬时值、峰值、均值，知道各自能回答什么问题
- 把网络指标翻译成业务 SLI，写出带错误预算的 SLO
- 认出四种最常见的口径反模式，包括分位数跨实例平均

## 机制拆解

### 0x01 PFC：帧数只是故事的一半

PFC pause 至少有三个可采的量。

| 口径 | 原始字段 | 单位 | 说明什么 |
|---|---|---|---|
| **pause 帧数** | out-pfc-pause-frames | 帧 | 反压发生了几次 |
| **pause 时长** | pause duration | quanta 或微秒 | 每次反压持续多久 |
| **受影响范围** | 涉及端口数、优先级数 | 个 | 故障波及多大面积 |

只报帧数是常见错误。两次事故，帧数都是 12 万，恢复代价可能差 100 倍。

极端情况是这样的。A 场景每帧只 pause 一个 quint（约 512 比特时间，10 Gb/s 下约 51 微秒），累计 12 万帧，总停顿 6 秒。B 场景每帧 pause 满 65535 quanta，累计 12 万帧，总停顿接近 9 小时。

所以口径要成对出现。**帧数回答频率，时长回答代价，两者不能互相替代。**

用 Go 的话类比一下。帧数相当于请求数，时长相当于总耗时。只看 QPS 不看耗时，看不出服务在卡。

以 10 Gb/s 链路为例，一个 pause quanta 等于 512 bit time，换算下来约 51.2 微秒。

```text
pause_quanta = 1      → 512 bit × 0.1 ns/bit  ≈ 51.2 µs
```

::: warning PFC 的帧数是背压次数，不是异常次数

健康网络里 PFC 应该罕见，但不该为零。零可能意味着三件事：链路没有瞬时拥塞、水线阈值设得过松、流量根本没打满。

反过来说，持续不为零也不一定是故障。集群在跑满带宽的训练任务时，PFC 有稳定背景值。判断要看三个量：变化率、时长分布、受影响端口数。绝对值本身说明不了什么。
:::

### 0x02 ECN 标记率：分母决定一切

ECN 标记率的分子很清楚，被标记的报文数。麻烦在分母。

| 分母选项 | 数值形态 | 问题 |
|---|---|---|
| 该端口发出的全部报文 | 被小流稀释 | 大流拥塞时比率很低，看起来正常 |
| 该端口该优先级发出的报文 | 最接近真实 | 需要按优先级拆维度，数据量大 |
| 具备 ECN 能力的报文 | 最精确 | 需要知道对端是否协商了 ECN |
| 收到 CE 标记的报文 | 语义混乱 | 分子分母混在一起 |

生产上一般选第二个，并把维度写进指标名。

```text
ecn_mark_ratio{device, port, priority} =
    rate(ecn_marked_packets_total{device, port, priority}[1m])
  / rate(ecn_capable_packets_total{device, port, priority}[1m])
```

口径写死之后，跨设备才可比。否则你会遇到这种场面：一台设备的标记率是 3%，另一台是 0.1%，差值十倍，原因只是两台设备的优先级配置不同。

### 0x03 队列水线：瞬时、峰值、均值

三个数，三个用途。瞬时值、峰值、均值分别服务于实时面板、事故复盘、容量规划。

| 形态 | 采法 | 能回答 |
|---|---|---|
| 瞬时值 | SAMPLE 1 秒或更细 | 现在的状态，用于实时面板 |
| 窗口峰值 | 1 分钟窗口内的 max | 微突发有没有把队列顶满 |
| 窗口均值 | 1 分钟平均 | 长期占用，用于容量规划 |

面板上放均值，事故复盘用峰值。**队列水线的均值几乎没有诊断价值。** 一条链路 99% 的时间队列为空，1% 的时间顶满，均值看起来温和得像没跑流量。

还有个单位问题。有的设备报字节、有的报 cell 数、有的报百分比。跨厂商混部时先统一单位，否则同一个阈值没法用。

### 0x04 SLI 怎么写：从网络指标到业务事件

SRE 的框架很简单。SLI 是好事件占有效事件的比例，SLO 是这个比例的目标值。

难点在"好事件"怎么定义。网络侧有四个候选。

| SLI | 好事件 | 有效事件 | 适用 |
|---|---|---|---|
| **带宽达成率** | 实际吞吐 ≥ 承诺的 90% | 所有测量窗口 | 容量与 SLA 结算 |
| **P99 时延** | 端口到端口时延 ≤ 阈值 | 所有采样 | 拥塞诊断 |
| **序列完整率** | 实际点数 ≥ 期望的 99.5% | 期望点数 | 遥测管道自身 |
| **训练步耗时** | 单步耗时 ≤ 基线的 1.1 倍 | 所有训练步 | 最有业务意义 |

第四个最值得投。前三个是手段，第四个是结果。集群好不好，训练任务自己会说话。

写 SLO 时给一个数字就够，但要带窗口。

```text
SLO-1  训练步耗时 P95 ≤ 基线 1.1 倍，30 天滚动窗口，目标 99%
SLO-2  遥测序列完整率 ≥ 99.5%，按天统计，目标 99.5%
SLO-3  故障发现时间 P90 ≤ 3 分钟，按周统计，目标 95%
```

## 判读与实操

### 0x05 错误预算怎么算

99% 的月度 SLO，允许的不可用时间是 7.2 小时。99.9% 是 43 分钟。99.99% 是 4.3 分钟。

对千卡集群来说，一次 PFC 风暴导致的训练中断通常是 20 到 60 分钟，含发现、定位、恢复三段。这意味着 99.9% 的月度预算，一个月只够摊一到两次事故。

这个计算的价值不在数字本身。它逼你回答一个问题：**你的 SLO 订的是承诺，还是期望。** 订成期望就没人当真，订成承诺就要配套资源。

### 0x06 四条口径反模式

| 反模式 | 表现 | 改法 |
|---|---|---|
| 用均值做 SLI | 微突发被摊平，永远达标 | 换成 P95 或 P99 |
| 把"丢包率 0"当健康指标 | 无损网络里它天然为 0 | 换成 PFC 时长与 ECN 标记率趋势 |
| 分母随流量漂移 | 同一指标跨时段不可比 | 分母写进指标定义，版本化 |
| 分位数直接平均 | p99 平均之后没有统计意义 | 存直方图，聚合时重算分位数 |

第四条值得展开。多个实例的 p99 取平均，得到的数字既不是全局 p99，也不对应任何真实用户。正确做法是各实例上报直方图桶，聚合时用 `histogram_quantile` 重算。

```text
# 错误：把各端口的 p99 平均
avg(port_latency_p99)

# 正确：聚合直方图后重算
histogram_quantile(0.99,
  sum by (le) (rate(port_latency_bucket[5m]))
)
```

### 0x07 一张可落地的口径表

做指标治理时，这张表比任何面板都重要。它进 Git，改动走评审。

| 指标 | 定义式 | 维度 | 采集 | 告警基线 |
|---|---|---|---|---|
| pfc_pause_sec | 累计 pause 时长的一阶差分 | device, port, priority | 1 s SAMPLE | 单端口 5 分钟内 > 10 秒 |
| ecn_mark_ratio | 标记包 / 该优先级发出的包 | device, port, priority | 1 s SAMPLE | 1 分钟内 > 5% 且连续 3 个窗口 |
| queue_peak_bytes | 窗口内队列占用最大值 | device, port, priority | 1 s SAMPLE | 达容量 80% 连续 5 分钟 |
| port_latency_p99 | 端口到端口时延的分位数 | device, port | INT 或探针 | > 基线 2 倍 |
| sequence_completeness | 实际点数 / 期望点数 | device, metric | 分钟窗口 | < 99.5% |

::: info 经验映射（IDC → AIDC）

这套做法和你给微服务定 SLO 完全一样。选指标、定目标、算预算，超预算就冻结变更。

区别在于"用户体验"的载体变了。IDC 里是 HTTP 的 P99 与错误率，这里训练任务的每步耗时。网络指标在这里退化成诊断用的中间量，不再是 SLI 本体。
:::

### 0x08 实验入口：三个口径，三个结论

```bash
cd labs/09-slo
make run     # 三种口径的可用率 + 错误预算 + 多窗口燃烧率
make test    # 19 个单测
```

同一份 30 天的指标流，时间口径 99.780%（未达标），事件口径 99.924%（达标）。两个数都叫可用率，判定相反。

第三个口径更值得警惕。分位口径只看时延，**失败得快也算达标**。这个缺陷得知道。

## 习题

**必答 Q1**：给一个 PFC 相关事故写三条指标口径，要求能支撑"这是灾难级还是可忽略"的判断。

::: details 参考答案与评分维度

三条分别覆盖频率、代价、面积。

1. `pfc_pause_frames_rate`：pause 帧数的一阶差分，按端口与优先级拆维度。回答"反压发生了多少次"。
2. `pfc_pause_seconds_rate`：累计 pause 量化值换算成秒后的一阶差分，同维度。回答"累计停了多少时间"，这是判断严重度的核心。
3. `pfc_affected_ports_ratio`：有 pause 计数变化的端口数除以端口总数。回答"波及多大面积"，这个值接近 1 就意味着风暴。

再加一条基线约束：三条都要与上周同期对比，用比值而不是绝对值。判断标准是比值超过 2 倍，而不是某个固定阈值。

**评分维度**：三条分别覆盖频率、时长、范围（必需）。指出时长是严重度核心（必需）。提出同比或基线对比（加分）。
:::

**必答 Q2**：老板要求"网络可用性 99.99%"，算一遍错误预算，并说明这个目标在千卡集群里意味着什么。

::: details 参考答案与评分维度

99.99% 的月度窗口是 30 天，允许故障时间 30 × 24 × 60 × 0.0001 = 4.32 分钟。

千卡集群上一次训练中断从发现到恢复通常 20 到 60 分钟。也就是说这个目标不允许任何一次完整的训练中断，一个月连一次 5 分钟的故障都吃不下。

结论有两条。第一，把目标改成 99.9%，把 43 分钟预算留给真正关键的训练窗口与交付节点。第二，砸钱做冗余、自动切换、跨轨重路由，把单次中断压到分钟级。

**评分维度**：预算算对（必需）。把预算与单次恢复时间对照（必需）。给出改目标或改架构两条路（加分）。
:::

**自测 Q3**：为什么队列水线的均值几乎没有诊断价值，面板上应该放什么。

::: details 参考答案与评分维度

队列是典型的双峰分布。要么空，要么在短时窗口被顶满。均值会落在两者之间，既不反映空闲也不反映拥塞。

面板上该放窗口峰值与超阈值时长。峰值告诉你最坏情况，时长告诉你这种情况持续了多久。

**评分维度**：说清双峰或摊平效应（必需）。给出峰值与超阈值时长（加分）。
:::

**自测 Q4**：两个团队对同一批数据得出 3% 与 0.1% 两个 ECN 标记率。列出三种可能的口径差异。

::: details 参考答案与评分维度

三种可能。分母不同，一个用全部报文，一个只算该优先级的报文。维度不同，一个按端口聚合，一个按队列拆开后再算。时间窗口不同，一个用 1 分钟，一个用 5 分钟，拥塞被平滑掉了。

这一题的标准答案是"把口径写进指标定义并版本化"，不是去争谁对。

**评分维度**：给出至少两种差异来源（必需）。指出解法是口径治理而非辩论（加分）。
:::

## 小结

这一讲可以压成一句话：**口径不写清楚，面板就是辩论场。**

PFC 三个口径缺一不可。帧数看频率，时长看代价，范围看面积。两次事故帧数一样，时长能差一百倍，只报帧数等于没报。

ECN 标记率的关键在分母，最常用"该端口该优先级发出的包数"，写进指标名里，跨设备才可比。队列水线的均值几乎没有诊断价值，因为它永远把尖峰摊平，面板上要放窗口峰值和超阈值时长。

SLI 最后要落到业务侧，训练步耗时最有意义，网络指标退成诊断用的中间量。算完错误预算再谈承诺，99.99% 一个月只给 4.3 分钟，一次训练中断都装不下。还有一个坑要记住：分位数不能跨实例平均。

::: tip 本课要点

**口径不写清楚，面板就是辩论场。**

- PFC 三个口径缺一不可：**帧数看频率、时长看代价、范围看面积**
- ECN 标记率的分母必须写死，最常用"该端口该优先级发出的包数"
- 队列水线只看均值等于看不见故障，面板放**窗口峰值与超阈值时长**
- SLI 从业务侧选：训练步耗时最有意义，网络指标退为诊断中间量
- 错误预算算完再做承诺，99.99% 等于不允许一次完整中断
- 一条坑：**分位数不能跨实例平均**，要聚合直方图后用 `histogram_quantile` 重算
:::

留一个思考题：如果 SLO 只允许你保留一个指标，你会选训练步耗时的 P95 还是端到端时延的 P99。
