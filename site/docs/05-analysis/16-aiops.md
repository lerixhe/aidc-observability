在第 07 讲，我们细致讲过四类故障的排障办法：看 pause 计数按优先级涨不涨，看队列水线和 ECN 标记，几台设备一对比，问题基本就落在某个端口上。那套办法在单台设备、单条链路上够用。

不过在万卡规模下，这种方式是有缺陷的，它不是总能收敛。

一台交换机 down 掉，在集群里会被放大成上千条告警。它自己的 LLDP 与 BGP 邻居批量报警，这是依赖广播；经过它的所有探测路径开始超时、丢包、时延上涨，这是路径广播；受影响的 Rail 上流量偏离、队列水位异常，训练任务变慢与 NCCL timeout，任务视角再报一次，这是视角广播。三个机制乘起来，一个物理故障换来几百上千条告警，**真正有用的信息只有一句：X 设备 down 了**。值班工程师淹在这一千条里，还得自己找出那一句。

不过这种淹没也仅仅在某几类故障下才会发生，而且多数情况下值班的人一眼就能认出是谁挂了，找人这件事并不难。真正把人淹死的，是那几类「源头不响、叶子全响」的故障：一次 PFC 风暴的源头设备自己的计数器看不出异常，全网十几条路径同时劣化；一次光模块劣化，端口是 up 的，只有往返时延在飘。

## 图搜索

为了解决这个问题，业界发明了基于图的根因定位算法，它的流程比较复杂，不过已经有了很多开源的库做了良好的封装，用户拿来即用，比如 networkx。

```py
import networkx as nx

# 拓扑图：设备是节点，链路是边
g = nx.DiGraph()
g.add_edge("spine-01", "leaf-11")
g.add_edge("leaf-11", "gpu-node-07")

# 一次 incident 里的告警节点集
alarm_nodes = {"leaf-11", "gpu-node-07", "leaf-11:s3", "gpu-node-07:eth0"}

# 找共同上游祖先：所有告警节点都能到达的节点
candidates = [
    n for n in g.nodes
    if all(nx.has_path(g, n, a.split(":")[0]) for a in alarm_nodes if a != n)
]

# 打分：覆盖告警多、时间最早、异常量级大者优先
def score(node, alarm_ts, alarm_mag):
    covered = sum(1 for a in alarm_nodes if nx.has_path(g, node, a.split(":")[0]))
    return covered * 2 - alarm_ts.get(node, 99) + alarm_mag.get(node, 0)

print(sorted(candidates, key=score, reverse=True)[:3])
```

为了使用它，需要维护一张完整的拓扑图，这些设备之间通过 LLDP 与 BGP 邻居自动发现，配置数据补齐接口与队列的属性。同很多分布式算法一样，它也使用「多数证据」的机制：一个候选根因要覆盖过半的告警节点才算数，覆盖不到的排到后面去。

不过这套算法还需要考虑拓扑漂移、时钟漂移、告警收敛等很多细节问题，同时因为要拿全网的告警集去图上匹配，意味着单次定位的耗时比人工敲两条命令长得多，快的那条路永远是「我知道大概是哪台」。

三处的输入错一个，结论就错，这一点必须提前说清。**拓扑要准**：配置漂移、静态拓扑表过期、聚合口与子接口的映射写错，都会让图失真，共同祖先直接算错。**事件时间要对齐**：设备间时钟差几秒，传播方向就判反，把下游当上游。**告警要收敛好**：噪声节点进了图，评分被稀释，Top-3 里塞满无关设备。

算法只有三代，选型其实没什么可纠结的。第一代是故障树与人工规则，准，但维护不动，规则数量随拓扑规模爆；第二代是相关性加图搜索，朴素有效，是工程主流；第三代是 Random Walk 与 GNN，学习「故障通常从哪类节点爆发」，还处在前沿探索。第二代的实现不复杂，取 incident 的告警节点集，在图上找共同上游祖先，按「时间最早 + 异常最大 + 覆盖告警最多」打分，输出 Top-3 候选加证据链，一天能写出原型，难的是把它跑准。

## 适用场景

如果你很在乎定位速度，希望半夜被叫起来时不用从一千条里扒那一句，那就应该考虑图上做 RCA。

不过代价也是有的：需要秒级遥测与路径探测两套数据源，需要一张准确并且自动更新的拓扑，需要告警收敛先做到位，还需要值班的人肯信它给的那三个候选，运维上也要特殊对待。这些都是需要考虑的成本，上之前请再三斟酌。

反过来，如果你手上只有几十台设备、一天三五条告警，人工查比任何算法都快，别折腾。**这套东西是为量写的，不是为先进写的。**

四层的建设顺序也是这个道理，一步都跳不得：数据基础（秒级遥测 + 路径探测 + 任务元数据 + 拓扑）、告警收敛（去重、抑制、聚合）、RCA、自动化处置。没有收敛好的告警，RCA 被噪声淹没；没有可靠的 RCA，自动化处置等于自动放大故障。跳一步就得回头补。

处置那一层还有一条独立的风险要说：根因误判时自动隔离正常端口或切换路径，会把小故障变成大故障。兜底四条：动作分级，可逆低危自动、不可逆高危人工审批；执行前写「预期验证」，处置后指标应如何变化，不达预期立即回滚；灰度启用，先部分集群；全量审计加全局熔断开关。

大模型在这套东西里的落点也很明确：告警收敛那一层可以做告警摘要与聚类描述，把 50 条告警写成人话；RCA 那一层可以做历史相似故障检索，辅助给出候选与证据链；处置那层让 Agent 调用工具去查指标、查拓扑、执行预案。边界只有一条：模型负责组织和解释，不负责计算与执行。

## 判读与实操

一个能跑起来的最小闭环是这样：

```text
数据：gNMI 订阅（秒级）+ 探测结果 + 拓扑图（LLDP/BGP 自动发现）+ 任务元数据
收敛：同设备同时间窗的告警折叠成一个 incident；下游告警标记为「疑似派生」
RCA ：incident 节点集 → 图上找共同上游祖先 → 按传播路径打分排序 → 输出候选根因
处置：候选根因 + 置信度 → 低危动作自动、高危动作审批 → 执行后验证 → 不达预期回滚
```

质量指标比算法选型重要，没有这几个数字，任何「我们上了图算法」都无法证明价值。告警压缩比看一千条告警压成几个 incident；根因命中率看人工确认的根因是否在候选 Top-3 内；误报率与漏报率看收敛规则与阈值的效果；处置成功率与回滚率看自动化是否可信；平均定位时长看 RCA 环节对 MTTR 的实际贡献。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：用四层框架做一段陈述：「给万卡集群建智能运维体系，你怎么分层搭建，每层解决什么？」控制在 400 字内。

::: details 参考答案与评分维度

数据基础。gNMI 秒级遥测（队列、PFC、ECN、CRC/DOM）加路径级探测加任务元数据加自动发现的拓扑图。这一层决定后面能不能做，先解决采集分级与时钟对齐。

告警收敛。同设备、同时间窗折叠，按拓扑归并为 incident，下游告警标记为派生，目标是压缩比上一个数量级。

RCA。把网络建成图，用「共同上游祖先加传播路径评分」输出候选根因与证据链。先做朴素图搜索，等数据质量稳了再考虑学习类方法。

处置。分级自动化，低危自动、高危审批，每个动作配预期验证与回滚，并有全局熔断开关。

**评分维度**：四层齐全且职责清楚（必需）。指出依赖顺序与「数据质量决定上限」（必需）。给出至少一个可量化指标（加分）。

:::

**必答 Q2**：用图的语言重新描述「30 多条路径劣化，找 PFC 风暴源点」的排障流程。节点、边、事件标记分别是什么？共同祖先搜索在找什么？

::: details 参考答案与评分维度

节点是交换机与服务器网卡，端口算节点的接口属性，光模块算节点属性。边是物理链路及其上承载的方向性转发关系，含 ECMP 的多条等价边。事件标记里，路径时延异常挂在边上，pause 计数异常挂在节点或接口上，队列水线同理。

共同祖先搜索找的是所有劣化路径在拓扑上的共同上游汇聚点，也就是那个「自身入流量正常、pause 计数最早异常上涨」的节点，它是暂停波最可能的发源方向。

**评分维度**：三类元素定义正确（必需）。共同祖先与暂停波源头的对应关系说清（必需）。提到按时间先后排序而非只看空间祖先（加分，这是避免误判的关键）。

:::

**自测 Q3**：为什么说图计算 RCA 的难点不在算法而在数据质量？

::: details 参考答案与评分维度

三处「垃圾进」。拓扑图失真，配置漂移或静态表过期，公共祖先算错。事件时序乱，时钟未对齐，传播方向判反。告警未收敛，噪声节点污染图，评分被淹没。

图搜索与传播评分本身是成熟工具，输入错则输出错。建设顺序必须是数据 → 收敛 → RCA。

**评分维度**：给出至少两个数据质量问题（必需）。强调顺序（必需）。

:::

**自测 Q4**：自动化处置最大的风险是什么？怎么设计兜底？

::: details 参考答案与评分维度

最大风险是错误处置放大的次生故障。根因误判时自动隔离正常端口或切换路径，把小故障变成大故障。

兜底四条。动作分级，可逆低危自动、不可逆高危人工审批。执行前写「预期验证」，处置后指标应如何变化，不达预期立即回滚。灰度启用，先部分集群。全量审计加全局熔断开关。

**评分维度**：说出误判放大故障（必需）。给出分级与回滚两类机制（必需）。提到熔断、灰度（加分）。

:::

## 小结

万卡规模下，一个物理故障会广播出上千条告警。放大来自三个机制：依赖广播、路径广播、视角广播。真正把人淹死的不是这些，是「源头不响、叶子全响」的那几类，PFC 风暴和光模块劣化都在里面。

四层架构的依赖顺序不能跳：数据基础、告警收敛、RCA、自动化处置。没有收敛好的告警，RCA 被噪声淹没。没有可靠的 RCA，自动化处置等于自动放大故障。

图计算做 RCA 的道理很朴素。网络本来就是一张图，故障沿拓扑向下传播，若干告警节点的共同上游祖先就是根因候选。算法只是把这句话写成程序，难的地方全在数据质量：拓扑要准、时间要齐、告警要收敛干净。

不过这套东西是为量写的。几十台设备、一天三五条告警的环境里，人工查比任何算法都快。

::: tip 本课要点

**一个故障上千条告警，捞出来的只有一句。**

- 告警放大三机制：**依赖广播、路径广播、视角广播**
- 真正难收的是**源头不响、叶子全响**：PFC 风暴、光模块劣化，源头自己的计数器一片正常
- 四层框架：**数据基础 → 告警收敛 → RCA → 自动化处置**，依赖顺序不可跳
- 图 RCA：网络天然是图，**故障沿拓扑向下流，告警的共同上游祖先就是根因候选**，再按时间、量级、覆盖度排序
- 算法三代：故障树（准但难维护）→ 图搜索（工程主流）→ RW / GNN（前沿）
- 难点在数据质量：**拓扑准、时序齐、告警收敛好**。先有质量指标，再谈算法
- 处置风险：误判放大故障 → 分级加预期验证加回滚加熔断

:::
