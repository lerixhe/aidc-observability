前面几讲的输出最后都要落到一个地方：一个能存下几千万条时间线、还能秒级查回来的库。

先把账算出来，心里才有数。一个端口的队列水线，1 秒一个点，一个点按 20 字节算，一天就是 86400 个点、1.7 MB。一个 64 端口的交换机，8 个队列、2 个方向、3 个核心指标（pause 计数、队列水线、ECN 标记），序列数是 64 × 8 × 2 × 3 = 3072 条，一天 5.3 GB。一万台这样的设备，一天 53 TB。

这个数字一摆出来，选型就变成了「哪个引擎能扛住这个形状」，而不是「谁的跑分高」。

## 交付

- 时序库的底层到底是什么，为什么它不是一种特殊的数据结构
- 选型的六个真实维度，以及为什么写入吞吐通常不是决定性的
- 基数为什么是智算遥测的头号杀手，三千万条这个数字是怎么来的
- Prometheus、VictoriaMetrics、ClickHouse、InfluxDB 的适用位置
- 实时链路与离线链路为什么必须并存，以及一套替代 benchmark 的验证方法

## 时序库是什么

很多人第一次接触时序库，会觉得它是某种专门为时间序列设计的特殊数据结构。

其实不是。时序库的内容就是列式文件加倒排索引，两样都普通得很。列存是按列排的文件，同一列的值挨着放，压缩比高，因为一列里的数字量级接近、变化缓慢；倒排索引是「标签值 → 序列 ID 列表」的一张表，查询时先用它把候选序列挑出来，再去列存里扫描。Grafana 上一个 `{device="leaf-01", queue="3"}` 的筛选，走的就是倒排。

时序库跟普通数据库的差别不在存储引擎，在约定：写入的点必须带时间戳、序列必须靠标签区分、查询几乎都是「某段时间内的聚合」。这三条约定决定了引擎长什么样，也决定了它能承受什么、不能承受什么。

所以判断一个引擎能不能用在智算场景，看它的倒排和列存怎么做就够了。倒排驻留内存，基数就是内存；列存按时间分块，乱序写入就是灾难。这一层的理解，比记四个引擎各自的特点有用得多。

## 三千万条序列

智算遥测的数据形状很少见。维度多、写入密、查询双极化、保留期长，还带乱序补点。

| 特征 | 具体表现 | 对存储的要求 |
|---|---|---|
| 维度多 | 设备 × 端口 × 队列 × 优先级 × 方向 × Rail × 平面 | 高基数，标签组合爆炸 |
| 写入密 | 万卡集群核心指标秒级推送 | 持续高吞吐写入，不能有尖峰雪崩 |
| 查询双极化 | 90% 是「最近 5 分钟某端口某队列」的小查询，10% 是「过去 7 天全网趋势」的大聚合 | 既要低延迟点查，也要能跑大聚合 |
| 保留期长 | 故障复盘要看数周前，容量规划要看数月 | 降采样加分层保留 |
| 乱序与补点 | 设备重连后补推、采集器重启后重放 | 能容忍乱序写入与去重 |
| 口径要一致 | 同一指标在实时告警与历史复盘中数值必须自洽 | 聚合语义可解释、可复现 |

第 14 讲那份容量账按每台 500 条序列算，一万台就是 500 万点每秒、一天 8.6 TB。把维度铺满到端口乘队列，每台设备的序列数从 500 涨到 3072，量级就翻了六倍：

```text
10,000 台交换机 × 64 端口 = 640,000 个端点
每端口保留维度：队列(8) × 方向(2) = 16
核心指标：pause 计数 / 队列水线 / ECN 标记 ≈ 3 条

核心时间线 ≈ 640,000 × 16 × 3 ≈ 3,000 万条
点速率     ≈ 3,000 万点/秒
每日原始   ≈ 52 TB
```

三千万条时间线面前，「写入能到百万点每秒」的跑分说明不了可行性。先算时间线数量，再谈吞吐。

## 六个维度

摆在前面的「写入 QPS」通常不是决定性因素。时序引擎的写入能力可以水平扩展，加节点能解决。无法靠加机器绕过的是基数：标签组合一爆炸，倒排索引与元数据先于磁盘把内存吃穿。

所以六个维度里，基数排第一：

1. **基数上限。** 能撑住多少条独立时间线（series）。最容易踩的坑。
2. **写入模型。** 推还是拉、批量大小、是否需要排序键、是否允许乱序。
3. **查询语言与表达力。** PromQL、MetricsQL、SQL、Flux。它决定上层能不能自然表达「按队列分组的 P95」。
4. **降采样与保留策略。** 内建还是自己写作业，能不能保留峰值。这一条常被忽略。
5. **运维复杂度。** 单机还是集群、要不要专职 DBA、扩缩容是否平滑。
6. **生态与成本。** Grafana 兼容性、告警规则复用、存储成本模型。

## 有条件才省

时序库省空间这件事，跟位图省空间是一个道理：把一个维度的取值压成标签、把时间戳压成增量，效率确实惊人。

不过这个方法也是有条件的，那就是标签的取值集合是封闭的、每条序列的写入是均匀的，否则可能得不偿失。反例很好举：把 `trace_id` 或者 `request_id` 放进标签里，每条序列只写一次，倒排索引瞬间比数据本身大十倍，压缩比全部还回去。同样，某个标签一天新增几千个取值，索引重建的速度跟不上，写入会先卡住。

「省」的前提是同一个标签值会被反复用到，一旦它变成一次性用品，省下来的全吐出来还倒欠一笔。

## 一句劝退，一句劝进

这一节略显枯燥，读者要是看得有点蒙，这是正常现象，可以先跳到下一节，用到选型的时候再回来翻。

以我的经验，能把四个引擎的差别讲到「倒排与基数」这一层的工程师不多，多数讨论停在「谁更快」上。你要是能把这份账讲清楚，团队里关于选型的话语权基本就是你的。

## 四个候选

| 维度 | Prometheus | VictoriaMetrics | ClickHouse | InfluxDB |
|---|---|---|---|---|
| 定位 | 采集、告警、短期存储 | 兼容 Prometheus 的高性能长期存储 | 通用列式 OLAP | 时序数据库加生态工具 |
| 典型职责 | 拉取、规则评估、告警 | 替换远端存储、长保留 | 明细大宽表、灵活聚合、关联分析 | 中小规模指标平台 |
| 语言 | PromQL | PromQL 兼容加 MetricsQL | SQL | Flux / InfluxQL |
| 基数耐受 | 低（内存倒排） | 高 | 高（依赖排序键设计） | 中 |
| 乱序写入 | 差 | 好 | 好 | 较好 |
| 降采样 | 需外部（recording rules 或远端） | 内建 downsampling | 需物化视图或作业 | 内建任务 |
| 强项 | 生态与告警规则标准 | 像 Prometheus 但省内存 | 任意维度聚合、join、明细追溯 | 上手快、写入友好 |
| 弱项 | 长期存储与高基数 | 复杂分析受 PromQL 表达力限制 | 运维重、要设计 schema | 超大规模下成本与并发 |

## 口径差异从哪来

同一个指标，两个库查出来不一样，原因基本是三个。

聚合窗口不同。`avg_over_time` 的步长不同，或者一个库存 1 秒采样，另一个只存 1 分钟均值。

降采样丢了峰值。只保留均值会让 PFC 的微突发彻底消失，对智算场景是致命的。

乱序补点被丢弃或覆盖。设备重连补推的数据在一处被接受，在另一处被丢掉。

所以选型时要先答三个问题：**怎么降采样、峰值还在吗、乱序怎么处理。** 这三条比跑分重要。

降采样这一步，和持久化系统里给日志做重写是同一件事：攒得太多的原始数据，按可接受的精度折叠一次，换回存储空间与重放速度。取舍点也一样，折得越狠，能还原的细节越少。区别在于时序数据的细节损失补偿不了，峰值一旦折没，事故复盘时没有任何办法补回来。

## 一处别扭的设计

Prometheus 的保留期是全库一个值，`--storage.tsdb.retention.time=15d`，一刀切。想给 PFC 计数留三个月、给端口流量只留三天，做不到，只能靠 remote write 把热数据分流到另一个库去。

这个设计我到现在也没太想明白。按指标分保留期是监控里最朴素的需求之一，十几万个光模块的 DOM 指标一天就几个数，占不了多少盘，谁也不舍得删；可它与 PFC 计数挤在同一个 retention 里，就得迁就最费空间的那个。

工程上的绕法有两条。一条是开两套 Prometheus，按指标分流，代价是运维翻倍、查询要跨库。另一条是上远端存储，让 VictoriaMetrics 或 ClickHouse 接住长保留，Prometheus 只留最近两周做告警评估。多数生产环境走的是第二条。

## 一条 SQL 问四个问题

位图里有一条指令叫 `bitfield`，一个命令能连着做多个位的读写，不用管道一件件来。

ClickHouse 的定位就是这条指令：同一个查询里既做聚合、又关联拓扑、还算窗口函数，一条 SQL 把一件事问到底。

```sql
-- 一条查询回答四个问题：谁的队列在涨、涨到多少、多久了、属于哪条 rail
SELECT
    q.device,
    q.port,
    q.queue,
    max(q.peak_kb)                                        AS peak_kb,
    countIf(q.peak_kb >= 400)                             AS windows_over,
    round(countIf(q.peak_kb >= 400) / count() * 100, 1)   AS pct_over,
    any(t.rail)                                           AS rail
FROM telemetry.queue_peak_1m AS q
LEFT JOIN topology.port_rail AS t ON q.device = t.device AND q.port = t.port
WHERE q.ts >= now() - INTERVAL 1 HOUR
GROUP BY q.device, q.port, q.queue
HAVING peak_kb >= 400
ORDER BY windows_over DESC
LIMIT 20;
```

四个问题一次答完：峰值为多少、超阈值多少个窗口、占多大比例、这条链路属于哪条 rail。这在 PromQL 里要拆成三段查询再在 Grafana 里拼，在 ClickHouse 里就是一条。

代价也在这一条上。每次这么写，扫描量都不小，得靠排序键把 `ts` 和 `device` 放在前面，不然一条查询拖慢整个集群。

## 实时与离线

| 链路 | 组成 | 回答什么问题 | 时效 |
|---|---|---|---|
| 实时 | gNMI 与探测 → 消息队列 → 流处理 → 时序库 → 大盘与告警 | 「现在发生了什么」 | 秒级 |
| 离线 | 全量落地 → 批处理数仓 → 聚合与挖掘 → 报表与模型 | 「历史上有什么规律」 | 小时 / 天级 |

两条链路不能只留一条。

实时链路要压延迟，会做激进降采样与短保留，细节会丢。离线链路留全量明细，才能回答「上月这类故障的共同特征」。

离线链路是作业制调度，时延分钟到小时，撑不住秒级大盘与告警。

两者共用一套指标口径定义，否则复盘时数字对不上，团队开始互不信任。

## 经验映射

| 你已有的做法 | 在智算场景里的增量 |
|---|---|
| 消息队列 → 流处理 → 明细 OLAP → 大盘 | 可以整体复用，链路同构 |
| 自产自收的指标采集 | 换成设备被动上报（gNMI 订阅），采集侧变成订阅管理加模型映射 |
| HTTP、DB 的指标语义 | 重新定义：PFC、ECN、FEC 这三个是新语义 |
| 缓存与 OLAP 的分层存储 | 实时与离线双链路的同构做法 |

增量就两点：数据源变成设备上报，指标口径要重定义并保证两条链路一致。「实时写入加明细聚合」这套工程能力可以直接搬过来。

## 判读与实操

不要抄别人的 benchmark，按自己的数据形状跑一遍。

```text
① 算时间线数量   设备数 × 端口数 × 队列数 × 优先级 × 方向（× 额外维度）
② 造真实数据形状 用生产采样合成：不只均匀写入，还要有重连补推的乱序与突发
③ 定查询清单     列 top-10 查询（P95 分位数、按队列分组、跨设备对比、7 天趋势）
④ 双口径校验     同一批数据写两个引擎，比较聚合结果是否一致（尤其是峰值）
⑤ 算总账         3 个月与 12 个月的存储与运维成本，而不是单点写入性能
```

第 ④ 步最好照位图那种「零存零取、整存零取」的思路做一遍：同一批点，一条一条写进去查一次，再批量灌进去查一次，两次结果对不上，说明引擎在去重或乱序处理上跟你想的不一样。这一步能省掉后面半年的争吵。

三千万条时间线这个量级下：

- Prometheus 单机基本承载不住，要远端存储或换引擎。
- VictoriaMetrics 与 ClickHouse 可以承载，都需要精细的标签裁剪与分层保留。
- 降采样必须保留峰值（`max` 而非 `avg`），否则微突发消失。

| 现象 | 可能原因 |
|---|---|
| 查询慢但磁盘不大 | 倒排驻留内存超限，触发落盘或高基数惩罚 |
| 写入延迟抖动 | 批量策略或合并（merge）节奏与写入模式冲突 |
| 同一指标两处查询不一致 | 降采样口径或乱序处理不一致 |
| 存储成本失控 | 保留期 × 原始精度 × 维度爆炸，缺分层保留 |

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：有人说「我们用 ClickHouse，写入能到百万点每秒，够用了」。这句话在两个层面上不足以支撑选型结论。

::: details 参考答案与评分维度

写入能力可以水平扩展，基数不能。真正决定可行性的是要存多少条独立时间线，百万点每秒说的是吞吐，没说维度组合。三千万条时间线可能直接把内存吃穿，写入吞吐再高也救不了。

没有说查询形态。时序场景 90% 是最近窗口的点查加少量大聚合，跑分往往是纯写入或纯扫描，与真实混合负载差异巨大。也没交代降采样口径与乱序补点处理，这两点直接决定数据能不能用于复盘。

**评分维度**：两点各 1 分。主动提出先算时间线数量（加分）。指出峰值保留与乱序处理（加分）。

:::

**必答 Q2**：「同一个网络指标，为什么要同时进实时链路和离线链路？」各举一个只适合其中一条链路的分析任务。

::: details 参考答案与评分维度

两者时效与保真取向相反。实时链路要低延迟、短保留、激进降采样，保「现在」。离线链路保留全量明细、作业制调度，保「历史」。

只适合实时：秒级告警。某端口 PFC pause 在 30 秒内突增，需要立刻定位处置。

只适合离线：跨月故障模式挖掘。比如「过去 90 天所有触发 checkpoint 回退的事件，前置 10 分钟的共性指标特征是什么」。需要全量明细与大规模聚合，实时链路承载不了。

**评分维度**：两类任务区分清楚（必需）。说出口径必须一致，否则复盘数字对不上（加分）。

:::

**自测 Q3**：为什么降采样「只保留均值」在智算场景是致命的？

::: details 参考答案与评分维度

智算网络的关键问题恰恰是微突发。PFC pause 与 incast 影响的是亚秒级峰值，不是平均水位。只留均值，1 秒内队列瞬间打满会被抹成温和的平均值，故障特征完全消失，复盘时数据看着一切正常。这等于把可观测做成了自欺。

正确做法是同时保留 max 与 avg，必要时保留分位数与直方图，查询时按用途选。

**评分维度**：说出微突发被均值抹平（必需）。给出保留 max 加 avg 的具体做法（必需）。

:::

**自测 Q4**：团队打算用一套 Prometheus 撑全站。在智算场景下你会提出哪三个质疑？

::: details 参考答案与评分维度

基数。三千万级时间线会让内存倒排爆掉，先算实际数量，再给标签裁剪方案。

长期保留。Prometheus 本地存储撑不住长保留，保留期又是全库一刀切，想按指标分档做不到，得交代远端存储方案。

乱序与补推。设备重连补推、采集器重放的乱序写入怎么处理，会不会被拒导致数据缺口。

再补一条：单一引擎同时承担告警评估与大规模明细查询，两者会不会互相拖累。

**评分维度**：三点各 1 分，且落到具体机制上，不是「性能不够」。

:::

## 小结

一台 64 端口的交换机，把队列和方向都算上，一天 5.3 GB；一万台一天 53 TB，三千万条时间线。这个账先算出来，选型才有的放矢。

时序库的底层不神秘，列存加倒排，判断一个引擎能不能用，看它倒排放在哪、列存怎么分块就够了。真正的杀手是基数，标签组合一爆炸，倒排先于磁盘把内存吃穿，加机器救不回来。

四个候选各有各的位置。Prometheus 管生态与告警，VictoriaMetrics 兼容还省内存，ClickHouse 强在一条 SQL 问四个问题，InfluxDB 上手快。真要选，先答三个问题：怎么降采样、峰值还在吗、乱序怎么处理。

省空间是有条件的，跟位图一样，标签取值得封闭、写入得均匀，把一次性 ID 塞进标签里，省的全吐出来还倒欠一笔。实时链路和离线链路不能互相替代，两条链路口径必须一致，否则复盘时数字对不上。

::: tip 本课要点

**引擎要容忍你的数据形状，跑分不决定可行性。**

- 账先算：一台 64 端口设备一天 5.3 GB，一万台 53 TB，三千万条时间线
- 时序库 = **列存 + 倒排**，倒排驻留内存，基数就是内存
- 六个维度：高基数、密写入、双极化查询、长保留、乱序补点、口径一致，**基数排第一**
- 四个候选的位置：Prometheus 管生态与告警，VictoriaMetrics 兼容省内存，ClickHouse 强在聚合与明细，InfluxDB 上手快
- Prometheus 的保留期全库一刀切，按指标分档得靠远端存储或分流
- 口径三问：**怎么降采样、峰值还在吗、乱序怎么处理**
- 双链路并存：实时管现在、离线管历史，**口径必须一致**
- 验证五步，第 ④ 步「双口径校验」照零存零取的思路做一遍

:::

留一个思考题：预算只够养一套引擎，你会把实时告警也压在 ClickHouse 上，还是把离线分析砍掉。
