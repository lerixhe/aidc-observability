大模型是突然放出来的，一夜之间什么都能答。放到运维场景里，它最大的新特性不是会写脚本，是能调工具：查拓扑、查计数器、翻历史复盘，自己决定先查哪个再查哪个。

做 Agent 的那批人自己也承认，这套循环是照着人干活的样子抄的。工程师排障本来就是这么走的：看一眼现象，猜个方向，查一条数据，发现猜错了，改个方向再查。模型把这条路径变成了一次可以重放的调用序列，论文里叫 ReAct，其实就是「想一步、做一步、看一眼」。

不过它只有一半能用。这一讲讲清楚哪一半能用，怎么用，以及为什么多数团队停在了第一级。

## 结构

一次完整的排障 Agent 是这么攒起来的，一口气说完：有一个任务，比如「任务 X 变慢，网络侧有没有问题」；有一个规划器，决定先查什么，通常是任务元数据、再是拓扑、再是路径探测；有一组工具，每个工具背后是一个稳定的 API，返回的是摘要而不是原始数据；有一个观察环节，把工具返回的东西塞回上下文，供下一轮判断；最后有一个产出，候选根因加证据链。

这五块里，前四块都是现成的工程活，工具写得好不好决定了整个东西的上限。最有意思的是最后一块：**证据链**。

每条结论都要挂上它来自哪次调用、哪个数值，挂不上的只能标成「推测」。这一条不是为了让报告好看，是为了让编造的东西一眼就能看出来。PEL 那种设计保证的是「消息至少被消费一次」，证据链保证的是「结论至少被复核一次」，两件事的动机完全一样。

## 拆开一次故障

工程师实际在做四件事：

| 动作 | 性质 | 适合谁 |
|---|---|---|
| 读大量非结构化文本（告警描述、日志、工单、runbook、历史复盘） | 语言理解 | 模型强项 |
| 凭经验联想「这个报错像上个月那次」 | 检索式记忆 | 模型加 RAG |
| 查一堆系统拼证据（指标、拓扑、任务状态） | 工具编排 | 模型编排、工具执行 |
| 确定性执行（重启进程、下发配置） | 状态变更 | 传统自动化 |

四件事里前三件都能交给模型，第四件不能。这就是分工原则：**理解与编排交给模型，计算与执行交给老系统。**

反着来，让模型算指标、直接执行命令，是所有失败案例的共同起点。

## 不用 Agent 也能用

很多人一上手就要做 Agent。其实不建 Agent 也能用模型，就像消息队列不用消费组也能读一样。

L1 是摘要。把 incident 里的 50 条告警丢给模型，让它写成一段人话：影响面多大、疑似哪个方向、建议先查哪几项。这个用法零风险，纯只读，输出给人看，不需要工具，不需要权限。它唯一的前置条件是告警收敛，也就是第 16 讲要求先做扎实的那一层。

L2 是检索。runbook、历史复盘、配置文档向量化，值班时直接问「这类告警的处置路径是什么」。风险低，但要带出处和版本，不然它会把三年前的处置步骤当成现在的。

绝大多数团队应该先落在这两级。理由很实在：L1 只依赖收敛，L2 只依赖文档资产，两样都是现成的。

## 建一个 Agent

到 L3，事情就变成「建一个消费组」了：得先注册，再指定从哪里开始。

要准备的东西是三样。工具 API 化：拓扑查询、路径查询、设备计数器、runbook 检索，每个都得是稳定的、有权限边界的、返回摘要的接口。工具注册表：读写分开，写操作走白名单加参数校验加审批。状态观察：每次调用都要留痕，谁调的、调了什么、返回了什么。

这三样里最难的是工具 API 化，不是模型调用。多数公司的 AIOps 项目停在 L1，卡住的地方是工具层，不在模型。没有这一层，Agent 只能在聊天窗口里「建议你去查一下」。

## 一次完整的调用

下面是这个循环跑起来的样子，跟工程师手工排障的步骤一模一样，区别只在每一步换成了可执行的工具调用。

```text
输入：「任务 X 变慢，网络侧有没有问题？」
  → 规划：先查任务元数据（哪些 Rank、哪些路径）
  → 调工具：query_task_meta(task) → 8 rail × 64 rank，步时基线 1.9 s
  → 调工具：query_probe_paths(task) → rail 3 的时延 P99 从 0.9 ms 涨到 4.2 ms
  → 观察：rail 3 上的三条路径同时劣化，其余 rail 正常
  → 再推理：三条路径的共同上游是哪几台，需要补查
  → 调工具：query_topology(rail=3) → 共同上游是 leaf-07 与 spine-11
  → 调工具：query_device_counters(leaf-07, 15m) → 端口 12 的 CRC 增量 200/分钟
  → 产出：候选根因 leaf-07 端口 12，证据链 4 条，其中 1 条标推测
  → 人工确认 / 分级处置
```

七次调用里，前六次都是只读。这一点很关键：**Agent 的能力上限由只读工具决定，风险下限由写工具决定。**

规划错了会绕路，工具返回太脏会跑偏，缺验证步骤会自信地给出错结论。三种失效在日志里长得都不像错误，只像「查得慢」。

## 结论的待复核列表

每条结论进一个列表，等人工确认。

这个列表就是 PEL 的翻版：结论被模型读出来、写进报告，这时候它还是「未确认」状态；人工看过、点了头，才算 ack。人工不点头，它就一直在列表里堆着。

为什么要有这个列表？因为模型给结论的速度远快于人的复核速度。一晚上跑一百次，人只看得了十次，剩下九十条如果直接进决策，等于把复核环节悄悄删掉了。列表把这个环节显式化，让「没复核」这件事看得见。

列表里还有一条规则要写死：**推测项不参与处置决策。** 证据链上缺一环的结论可以让它出现在报告里，提示人去补查，但不能触发任何自动动作。

## 上下文太多怎么办

一条消息攒太多，得定长截断。上下文也一样。

一亿个时序点塞不进上下文，塞进去也没有意义。所以工具不许返回原始数据，必须先聚合：「过去 5 分钟该设备 PFC pause 上涨 40 倍，涉及 3 条路径」。模型只吃结论级摘要。

这和探测端先做多维聚合、再上报是同一个做法：把计算下沉到离数据近的地方。谁离数据近，谁负责算。

验收标准可以量化：单次工具调用返回体小于 2KB 且必须含结论。超了就是摘要粒度设计错了，返回原文让模型自己找结论，模型一定找不到。

## 结论没人复核会怎样

待复核列表会一直涨。

一个晚上一百条，一周七百条，报告越写越长约莫就是这个原因。更要紧的是评分会被稀释：列表里塞满没用的推测项，人翻着翻着就都点「已阅」，复核就退化成形式。

处置办法两条。一是按置信度分层，高置信的先看，低置信的批量处理；二是定期清理，一周没人认领的自动归档并记录「未复核」这个事实，而不是悄悄删掉。

## 断了怎么捡回来

模型服务断一次，那次排障的进度就丢了。

好在有工具调用日志。重新接上以后，不要从头再问一遍，而是把已经拿到的证据喂回去，从断点继续。这需要日志里存的不只是「调了什么」，还要存「返回的摘要」。只存调用参数，接回来还得重查一遍，成本翻倍。

断线重连最容易出的问题是重复处置：断之前已经下发了隔离动作，接回来又下发一次。写操作必须带幂等号，这条在 Agent 场景下比在普通服务里更要紧，因为它的「重试」是模型自己决定的。

## 模型挂了怎么降级

它挂的时候，值班的人还在等结论。

降级路径要提前定好：L3 掉到 L2，只给检索问答；L2 掉到 L1，只给告警摘要；L1 也挂了，回到最原始的规则告警。每一级的降级触发条件写清楚，不要等到出事那天现想。

还有一条容易漏：模型版本换一次，行为可能就变了。同一个提示词，上个版本给四条证据，这个版本给两条。所以升级要跟评测回放一起做，回放集不过就不升。

## 多 Agent 编排

多 Agent 的方案听着先进：一个规划 Agent、几个执行 Agent、一个复核 Agent，互相开会。

关于这一点，我并不认同。多 Agent 的调度成本高得离谱，它们在上下文里互相传话，传一次丢一半信息，最后拼出来的结论还不如单 Agent 加五个好工具。你去看那些真在生产的系统，主干基本都是单 Agent 加一批只读工具，所谓「多 Agent」多数是工程上的偷懒，把本该写在工具里的逻辑塞进了提示词。

分工的边界应该画在工具上，不是画在 Agent 上。一个工具一个职责，返回摘要，能幂等重试，这样一个 Agent 就够用了。

## 经验映射

| 你已有的能力 | 在 LLM 落地里的位置 |
|---|---|
| 告警收敛与 incident 归并 | L1 摘要的输入 |
| runbook 与复盘文档积累 | L2 知识库的原料 |
| 指标与拓扑查询 API | L3 工具层的原料 |
| 处置分级与回滚设计 | 权限分级护栏 |
| 用过编码 Agent | 对 Agent 行为与失效模式的直觉 |
| 缺失部分 | 评测回放体系、工具层的摘要粒度设计 |

用过编码 Agent 的人对这套失效模式不陌生：上下文放不下就会瞎猜，工具返回太脏就会跑偏，没有验证步骤就会自信地错。运维 Agent 踩的是同一批坑。

## 判读与实操

| 护栏 | 具体措施 | 验收方式 |
|---|---|---|
| 上下文工程 | 工具返回聚合摘要，附时间窗与口径说明 | 单次调用返回体 < 2KB 且含结论 |
| 证据链 | 每条结论附 `tool_call_id` 与关键数值 | 抽检 20 条结论，能被人工复核 |
| 权限分级 | 读写工具分注册表，写操作需审批工单 | 演练一次越权调用被拒绝 |
| 评测回放 | 30 个历史故障的告警快照加期望结论 | Top-3 命中率与证据完整率 |

评测回放是落地前提，不是可选优化。用历史故障做回放：输入当时的告警，看 Agent 能否得出当时的结论、证据链是否成立。没有回放的 Agent 是玄学。回放集同时也是回归测试集，提示词或工具改动都要跑一遍。

判读几条常见现象：

| 现象 | 判读 |
|---|---|
| Agent 反复调同一工具 | 工具返回不含它需要的信息，摘要粒度错了 |
| 结论正确但证据链缺失 | 提示词未强制引用，或工具没返回可引用的标识 |
| 结论在相似场景间摇摆 | 缺评测回放集，无法回归验证 |
| 人工最终不采纳 | 多数是摘要信息不足，而非模型推理能力不足 |

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：三分钟陈述：「在智算网络监管控平台里落地大模型能力，你分几级、每级做什么、护栏怎么设？」控制在 400 字内。

::: details 参考答案与评分维度

**L1 摘要**。incident 自动摘要，给出影响面、疑似方向与建议排查项。纯只读，输出给人看，先解决值班被淹。

**L2 检索**。runbook、历史复盘、配置文档入 RAG，带出处与版本，回答「这类告警的处置路径」。

**L3 Agent**。工具调用编排，产出候选根因加证据链。工具层必须 API 化并返回聚合摘要。

**护栏**四条。上下文工程，只喂结论级摘要。证据链强制，结论必须引用工具返回值，推测显式标注。权限分级，读写分离、写操作审批。评测回放，用历史故障集做回归。

**评分维度**：三级清晰且风险递增（必需）。护栏至少覆盖证据链与权限（必需）。指出工具层 API 化是 L3 的真门槛（加分）。

:::

**必答 Q2**：「防幻觉的核心，是让编的无处遁形」。展开这句话背后的设计。

::: details 参考答案与评分维度

幻觉是概率模型的固有属性，用提示词说「请不要编造」无法消除，只能降低频率。那等于把可靠性寄托在不可控因素上。

设计换个方向：让编造在结构上无法通过。做法是强制证据链，每条结论必须关联具体工具调用与返回值，没有证据的只能以「推测」出现并明确标注。

模型仍可能编，但编出来的东西一眼可辨，不会伪装成事实进入决策链。再进一步，把关键计算从模型手里拿走，下沉到 SQL 与聚合引擎，模型只决定算什么、解释结果。

**评分维度**：指出幻觉不可消除（必需）。给出结构上无法伪装的做法而非提高模型能力（必需）。提到计算下沉（加分）。

:::

**自测 Q3**：为什么不让模型直接计算指标、直接执行预案？

::: details 参考答案与评分维度

计算方面，模型是概率模型，算术不保证精确，大规模数据也进不了上下文。计算必须下沉到 SQL、代码、聚合引擎，模型只决定算什么。

执行方面，输出具概率性，一次幻觉就是一次生产事故，预案执行通常不可逆。

分工原则：模型管不确定性高的理解与编排，确定性系统管正确性要求高的计算与执行。

**评分维度**：两点都答到（必需）。补出执行需审批与回滚（加分）。

:::

**自测 Q4**：设计一个网络排障 Agent 的工具清单，至少 5 个，标注读写与返回粒度。

::: details 参考答案与评分维度

| 工具 | 类型 | 返回粒度 |
|---|---|---|
| `query_task_meta(task)` | 只读 | 并行策略、Rank 分布、起止时间（结构体） |
| `query_topology(device 或 task)` | 只读 | 邻接关系、所在 rail 与平面（小图） |
| `query_probe_paths(task 或 device)` | 只读 | 受影响路径集合与时延劣化摘要（Top-N，不含原始序列） |
| `query_device_counters(device, window)` | 只读 | 聚合后的 pause / ECN / CRC / 队列摘要，带口径说明 |
| `search_runbook(symptom)` | 只读 | 相似历史故障与处置方案，带出处与时效 |
| `execute_playbook(action, args)` | 写 | 白名单动作加审批工单号加结果回执 |

考察两件事：粒度意识（给模型的都是摘要）与权限意识（读写分离、写操作审批）。

**评分维度**：五个以上工具且读写标注清楚（必需）。返回粒度明确是摘要（必需）。写工具配审批（加分）。

:::

## 小结

这轮新东西借鉴的东西很明确：照着工程师手工排障的流程抄了一个循环，想一步、做一步、看一眼。和它借鉴的对象比，它多出来的是速度和不知疲倦，少掉的是判断力和责任心，所以分工的原则是「理解与编排给它，计算与执行不给它」。

落地分三级。L1 摘要零风险，L2 检索低风险，L3 Agent 中风险要护栏。四条护栏：只喂摘要不喂原始数据、结论必须挂证据、读写权限分级、用历史故障做回放评测。

门槛不在模型，在工具层。拓扑查询、路径查询、设备计数器、runbook 检索，全得变成稳定的、带权限的、返回摘要的接口。

最后一句是这一讲真正想说的：每条结论进待复核列表，人工 ack 了才生效，没 ack 的一直挂着。这个列表让它编的东西无处遁形，也让你知道这一晚上它替你看过多少你还没看的东西。

::: tip 本课要点

**理解与编排给模型，计算与执行给老系统。**

- 分工原则：模型管语言理解与工具编排，传统系统管计算与状态变更，反着来必翻车
- 三级落地：**L1 摘要（零风险）→ L2 RAG 检索（低）→ L3 Agent 工具调用（中，需护栏）**
- Agent Loop：规划 → 调工具 → 观察 → 再推理 → 产出**证据链**，七次调用里六次是只读
- 四条护栏：**上下文工程、证据链强制、权限分级、评测回放**
- 每条结论进**待复核列表**，推测项不参与处置决策
- 真门槛是**工具层 API 化加摘要粒度设计**，这也解释了多数项目为何停在 L1
- 多 Agent 编排的代价大于收益，边界应该画在工具上

:::

留一个思考题：如果 Agent 的候选根因对了但证据链缺一条，你会让它自动处置吗。

- Nygard, *Release It!*（权限分级、熔断与回滚的稳定性模式来源）

这一篇的技术判断很快会过期，模型半年一代。能留下来的大概只有结构那几段：什么该给模型、什么不能给、证据怎么强制。读者要是有不同想法，来仓库开个 issue 一起聊。
