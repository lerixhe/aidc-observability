> 这篇文章的主要部分源于一次内部分享，当时大模型刚被放进运维场景，老钱抢先分析了它在可观测里的落点，事后又对内容做了补充，并整合了几个同事的疑难问题。

大模型是被突然放出来的，一夜之间什么都能答。放到运维场景里，它最大的新特性不是会写脚本，是能调工具：查拓扑、查计数器、翻历史复盘，自己决定先查哪个再查哪个。做 Agent 的那批人自己也承认，这套循环是照着人干活的样子抄的，作者坦言它狠狠地借鉴了工程师手工排障的流程。

一次完整的排障 Agent 是这么攒起来的：有一张任务表，把所有待解的问题串起来，每个问题都有唯一的 ID 和对应的上下文；有一个规划器，决定先查什么，通常是任务元数据、再是拓扑、再是路径探测；有一组工具，每个工具背后是一个稳定的 API，返回的是摘要而不是原始数据；有一个观察环节，把工具返回的东西塞回上下文，供下一轮判断；最后有一个产出，候选根因加证据链。任务是持久化的，模型重启以后，之前的结论还在。

每个会话都有唯一的名称，它就是任务 ID，在我们首次提问时自动创建。

每个会话都可以挂多个消费组，每个消费组会有一个游标 `last_delivered_id` 在上面往前移动，表示当前这个角色已经复核到哪条结论了。每个消费组都有一个会话内唯一的名称，消费组不会自动创建，它需要单独的指令 `xgroup create` 进行创建，需要指定从某条结论 ID 开始消费，这个 ID 用来初始化 `last_delivered_id` 变量。

每个消费组的状态都是独立的，相互不受影响。也就是说同一份结论会被每个消费组都消费到：值班助手看到的是待处置项，复盘助手看到的是证据链，报表助手看到的是命中率。

同一个消费组可以挂接多个消费者，这些消费者之间是竞争关系，任意一个消费者读取了结论都会使游标 `last_delivered_id` 往前移动。每个消费者有一个组内唯一名称，一般就是值班人的名字。

消费者内部会有一个状态变量 `pending_ids`，它记录了当前已经被读出来、但是还没有确认的结论。如果没人确认，这个变量里面的结论 ID 会越来越多，一旦某条结论被确认，它就开始减少。这个变量在官方文档里被称为 **PEL**，也就是 `Pending Entries List`，这是一个很核心的结构，它用来确保人至少复核过每条结论一次，而不会在模型输出之后、处置之前被悄悄跳过。

## 结论 ID

结论 ID 的形式是 `timestampInMillis-sequence`，例如 `1748012345678-5`，它表示当前这条结论是在毫秒时间戳 `1748012345678` 时产生的，并且是该毫秒内产生的第 5 条。ID 可以由系统自动生成，也可以由客户端自己指定，但是形式必须是 `整数-整数`，而且后面产生结论的 ID 要大于前面的。

这一条看着像洁癖，其实是证据链的地基：ID 一旦倒挂，时间线就排不出先后，「先 pause 后堆积」和「先堆积后 pause」会得出完全相反的结论。

## 结论内容

结论内容就是键值对，形如 `candidate=leaf-07:s12`、`evidence=4`、`confidence=0.72`、`speculation=1`，这没什么特别之处。特别之处在最后那个字段，推测项要显式写出来，不能混在证据里。

## 增删改查

1. `ask` 提一个问题，生成一条结论
2. `withdraw` 撤回结论，这里的撤回仅仅是设置了标志位，不影响结论总长度
3. `history` 获取结论列表，会自动过滤已经撤回的
4. `len` 结论数量
5. `del` 删除整个会话

```text
# * 号表示系统自动生成 ID，后面顺序跟着一堆键值对
> ask task-8841 * symptom "step 1.9s -> 2.6s" window 30m
1748012345678-0        # 生成的结论 ID
> ask task-8841 * candidate leaf-07:s12 confidence 0.72
1748012345999-0
> len task-8841
(integer) 2
# - 表示最小值，+ 表示最大值
> history task-8841 - +
1) 1) 1748012345678-0
   2) 1) "symptom"
      2) "step 1.9s -> 2.6s"
      3) "window"
      4) "30m"
2) 1) 1748012345999-0
   2) 1) "candidate"
      2) "leaf-07:s12"
      3) "confidence"
      4) "0.72"
> withdraw task-8841 1748012345678-0
(integer) 1
# 长度不受影响
> len task-8841
(integer) 2
# 被撤回的结论没了
> history task-8841 - +
1) 1) 1748012345999-0
   2) 1) "candidate"
      2) "leaf-07:s12"
      3) "confidence"
      4) "0.72"
```

## 独立消费

我们可以在不定义消费组的情况下进行独立消费，当没有新结论时，甚至可以阻塞等待。系统提供了一个单独的指令 `ask --sync`，可以把这套东西当成普通的问答来用。用 `--sync` 时，我们可以完全忽略消费组的存在，就好比它就是一个普通的聊天窗口。

```text
# 从会话头部读两条结论
> history task-8841 - + count 2
1) ...

# 从尾部读一条，毫无疑问，这里不会返回任何结论
> tail task-8841 count 1
(nil)

# 从尾部阻塞等待新结论到来，下面的指令会堵住
> tail task-8841 block 0 count 1

# 我们在另一个窗口提一个新问题
> ask task-8841 * candidate spine-11 confidence 0.55
1748012500000-0

# 回到前面的窗口，阻塞解除，返回新结论，还显示了等待时间
1) ...
(93.11s)
```

客户端如果想要顺序消费，一定要记住当前读到哪了，也就是返回的结论 ID。下次继续调用时，把上次返回的最后一个 ID 作为参数传进去，就可以继续。

`block 0` 表示永远阻塞，直到结论到来，`block 1000` 表示阻塞 1 秒，1 秒内没有结论就返回 `nil`。

这一级就是上一讲说的 L1 与 L2：不需要建 Agent，也不需要注册消费组，纯只读，输出给人看。

## 创建消费组

到 L3，事情就变成建一个消费组：得先注册，再指定从哪里开始。这一步对应的是把工具 API 化、把权限边界画出来。

```text
# 0-0 表示从头开始复核，适合复盘场景
> xgroup create task-8841 reviewer 0-0
OK
# $ 表示只看新结论，历史结论全部忽略，适合值班场景
> xgroup create task-8841 onduty $
OK

# 获取会话信息
> xinfo stream task-8841
1) length
2) (integer) 3          # 共 3 条结论
3) groups
4) (integer) 2          # 两个消费组
5) first-entry
6) ...
7) last-entry
8) ...

# 获取消费组信息
> xinfo groups task-8841
1) name "reviewer"  consumers 0  pending 0
2) name "onduty"    consumers 0  pending 0
```

## 消费

消费组提供了 `xreadgroup` 指令进行组内消费，需要提供消费组名称、消费者名称和起始结论 ID。它同独立消费一样，也可以阻塞等待。读到结论后，对应的 ID 就会进入消费者的 PEL 结构里，值班的人处置完毕，使用 `ack` 指令通知服务器，这条结论已经被复核，该 ID 就会从 PEL 中移除。

```text
# > 号表示从当前消费组的 last_delivered_id 后面开始读
> xreadgroup GROUP onduty c1 count 1 streams task-8841 >
1) candidate: leaf-07:s12, evidence: 4, confidence: 0.72

> xreadgroup GROUP onduty c1 count 1 streams task-8841 >
1) candidate: spine-11, evidence: 2, confidence: 0.55

# 再继续读取，就没有新结论了
> xreadgroup GROUP onduty c1 count 1 streams task-8841 >
(nil)

# 观察消费组信息
> xinfo groups task-8841
1) name "onduty"  consumers 1  pending 2   # 两条还没 ack

# 看看每个消费者的状态
> xinfo consumers task-8841 onduty
1) name "c1"  pending 2  idle 418715       # 空闲了多少毫秒没读

# 确认一条
> ack task-8841 onduty 1748012345999-0
(integer) 1
> xinfo consumers task-8841 onduty
1) name "c1"  pending 1  idle 668504

# 全部确认，PEL 清空
> ack task-8841 onduty 1748012500000-0
(integer) 1
> xinfo consumers task-8841 onduty
1) name "c1"  pending 0  idle 745505
```

这个 PEL 就是「待复核列表」。为什么要有它？因为模型给结论的速度远快于人的复核速度。一晚上跑一百次，人只看得了十次，剩下九十条如果直接进决策，等于把复核环节悄悄删掉了。列表把这个环节显式化，让「没复核」这件事看得见。

列表里还有一条规则要写死：**推测项不参与处置决策。** 证据链上缺一环的结论可以让它出现在报告里，提示人去补查，但不能触发任何自动动作。

## 上下文太多怎么办

读者很容易想到，要是结论积累太多，上下文岂不是很长，会不会撑爆？`withdraw` 又不会真的删掉结论，它只是给结论做了个标志位。

系统自然考虑到了这一点，所以它提供了一个定长功能。在 `ask` 的指令里提供一个定长长度 `maxlen`，就可以将老的结论干掉，确保上下文不超过指定长度。

```text
> len task-8841
(integer) 5
> ask task-8841 maxlen 3 * candidate leaf-09:s03 confidence 0.61
1748015160273-0
> len task-8841
(integer) 3
```

上下文被砍掉了。如果它在未来可以提供按时间戳清理结论的规则那就更加完美了，但是目前还没有。

真正落地时，这条约束要落成一个数字：**单次工具调用返回体小于 2KB 且必须含结论**。超了就是摘要粒度设计错了，返回原文让模型自己找结论，模型一定找不到。一亿个时序点塞不进上下文，塞进去也没有意义，所以工具不许返回原始数据，必须先聚合：「过去 5 分钟该设备 PFC pause 上涨 40 倍，涉及 3 条路径」，模型只吃结论级摘要。

这和探测端先做多维聚合、再上报是同一个做法：把计算下沉到离数据近的地方。谁离数据近，谁负责算。

## 结论没人确认会怎样

每个消费者结构里保存了未确认的结论 ID 列表，如果模型给了结论、人也看了、但没点确认，PEL 就会不断增长，如果有很多消费组的话，这个列表占用的内存（以及信任）就会放大。

一个晚上一百条，一周七百条，报告越写越长约莫就是这个原因。更要紧的是评分会被稀释：列表里塞满没用的推测项，人翻着翻着就都点「已阅」，复核就退化成形式。

处置办法两条。一是按置信度分层，高置信的先看，低置信的批量处理；二是定期清理，一周没人认领的自动归档并记录「未复核」这个事实，而不是悄悄删掉。

## PEL 如何避免结论丢失

在客户端读取结论时，系统把结论回复给客户端的进程中，浏览器或者终端突然断开了连接，这条结论就丢失了。但是 PEL 里已经保存了发出去的结论 ID。待客户端重新连上之后，可以再次收到 PEL 中的结论 ID 列表。不过此时 `xreadgroup` 的起始 ID 不能为 `>`，而必须是任意有效的 ID，一般设为 `0-0`，表示读取所有未确认的结论以及 `last_delivered_id` 之后的新结论。

这一条对应的是值班交接：**接班的人不能只接新任务，得把上一班没确认的结论捞回来。** 交接清单如果只写「今晚新发生的事」，那三条还没确认的推测就永远消失了。

断线重连还有一个更容易出事的点：重复处置。断之前已经下发了隔离动作，接回来又下发一次。写操作必须带幂等号，这条在 Agent 场景下比在普通服务里更要紧，因为它的「重试」是模型自己决定的。

## 高可用

这套东西的高可用是建立在主从复制基础上的，跟其它数据结构的复制机制没有区别。不过模型服务挂掉的时候，值班的人还在等结论，所以降级路径要提前定好：L3 掉到 L2，只给检索问答；L2 掉到 L1，只给告警摘要；L1 也挂了，回到最原始的规则告警。每一级的降级触发条件写清楚，不要等到出事那天现想。

还有一条容易漏：模型版本换一次，行为可能就变了。同一个提示词，上个版本给四条证据，这个版本给两条。所以升级要跟评测回放一起做，回放集不过就不升。

## 分区

这套结构没有原生支持分区的能力，如果想要使用分区，那就需要分配多个会话，然后在客户端使用一定的策略把问题发到不同的会话里。

你也许会认为专门的 AIOps 平台要先进很多，它是原生支持多维度的。关于这一点，我并不认同。记得那些平台也存在标签映射策略么，因为它也是通过客户端的规则把不同的数据塞进不同的维度里的。另外它还支持动态增加维度的能力，但是这种调整也是很蹩脚的，它不会把已经存进去的内容重新打标，不会重新组织历史数据。这种简单的动态调整能力，通过增加新的会话就可以做到。

多 Agent 的方案也一样听着先进：一个规划 Agent、几个执行 Agent、一个复核 Agent，互相开会。关于这一点，我并不认同。它们在上下文里互相传话，传一次丢一半信息，最后拼出来的结论还不如单 Agent 加五个好工具。**分工的边界应该画在工具上，不是画在 Agent 上。**

## 小结

这套东西借鉴了工程师手工排障的流程，它弥补了纯规则引擎不能读文本、不能联想的缺陷。但是它又不同于那些专门的平台，它能做的只是理解与编排，计算与执行不能交给它。

落地分三级。L1 摘要零风险，L2 检索低风险，L3 Agent 中风险要护栏。四条护栏：只喂摘要不喂原始数据、结论必须挂证据、读写权限分级、用历史故障做回放评测。

门槛不在模型，在工具层。拓扑查询、路径查询、设备计数器、runbook 检索，全得变成稳定的、带权限的、返回摘要的接口。多数公司停在 L1，卡住的地方就在这里。

最后一句是这一讲真正想说的：每条结论进待复核列表，人工 ack 了才生效，没 ack 的一直挂着。这个列表让它编的东西无处遁形，也让你知道这一晚上它替你看过多少你还没看的东西。

如果读者稍微研究过那些开源 Agent 框架，就会发现它们真正稳的部分其实是工具注册与回放评测，这点极可能是作者们意识到模型能力半年一代，能留下来的只有结构。这只是本人的猜测，未必是实际情况。如果读者有什么不同的想法，可以在评论区一起参与讨论。

::: tip 本课要点

**理解与编排给模型，计算与执行给老系统。**

- 分工原则：模型管语言理解与工具编排，传统系统管计算与状态变更，反着来必翻车
- 三级落地：**L1 摘要（零风险）→ L2 RAG 检索（低）→ L3 Agent 工具调用（中，需护栏）**
- Agent Loop：规划 → 调工具 → 观察 → 再推理 → 产出**证据链**，七次调用里六次是只读
- 四条护栏：**上下文工程、证据链强制、权限分级、评测回放**
- 每条结论进**待复核列表**，推测项不参与处置决策
- 真门槛是**工具层 API 化加摘要粒度设计**，这也解释了多数项目为何停在 L1
- 多 Agent 编排的代价大于收益，边界应该画在工具上

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：三分钟陈述：「在智算网络监管控平台里落地大模型能力，你分几级、每级做什么、护栏怎么设？」控制在 400 字内。

::: details 参考答案与评分维度

**L1 摘要**。incident 自动摘要，给出影响面、疑似方向与建议排查项。纯只读，输出给人看，先解决值班被淹。

**L2 检索**。runbook、历史复盘、配置文档入 RAG，带出处与版本，回答「这类告警的处置路径」。

**L3 Agent**。工具调用编排，产出候选根因加证据链。工具层必须 API 化并返回聚合摘要。

**护栏**四条。上下文工程，只喂结论级摘要。证据链强制，结论必须引用工具返回值，推测显式标注。权限分级，读写分离、写操作审批。评测回放，用历史故障集做回归。

**评分维度**：三级清晰且风险递增（必需）。护栏至少覆盖证据链与权限（必需）。指出工具层 API 化是 L3 的真门槛（加分）。

:::

**必答 Q2**：「防幻觉的核心，是让编的无处遁形」。展开这句话背后的设计。

::: details 参考答案与评分维度

幻觉是概率模型的固有属性，用提示词说「请不要编造」无法消除，只能降低频率。那等于把可靠性寄托在不可控因素上。

设计换个方向：让编造在结构上无法通过。做法是强制证据链，每条结论必须关联具体工具调用与返回值，没有证据的只能以「推测」出现并明确标注。

模型仍可能编，但编出来的东西一眼可辨，不会伪装成事实进入决策链。再进一步，把关键计算从模型手里拿走，下沉到 SQL 与聚合引擎，模型只决定算什么、解释结果。

**评分维度**：指出幻觉不可消除（必需）。给出结构上无法伪装的做法而非提高模型能力（必需）。提到计算下沉（加分）。

:::

**自测 Q3**：为什么不让模型直接计算指标、直接执行预案？

::: details 参考答案与评分维度

计算方面，模型是概率模型，算术不保证精确，大规模数据也进不了上下文。计算必须下沉到 SQL、代码、聚合引擎，模型只决定算什么。

执行方面，输出具概率性，一次幻觉就是一次生产事故，预案执行通常不可逆。

分工原则：模型管不确定性高的理解与编排，确定性系统管正确性要求高的计算与执行。

**评分维度**：两点都答到（必需）。补出执行需审批与回滚（加分）。

:::

**自测 Q4**：设计一个网络排障 Agent 的工具清单，至少 5 个，标注读写与返回粒度。

::: details 参考答案与评分维度

`query_task_meta(task)` 只读，返回并行策略、Rank 分布、起止时间；`query_topology(device 或 task)` 只读，返回邻接关系与所在 rail、平面；`query_probe_paths(task 或 device)` 只读，返回受影响路径集合与时延劣化摘要，Top-N，不含原始序列；`query_device_counters(device, window)` 只读，返回聚合后的 pause / ECN / CRC / 队列摘要并带口径说明；`search_runbook(symptom)` 只读，返回相似历史故障与处置方案，带出处与时效；`execute_playbook(action, args)` 写，白名单动作加审批工单号加结果回执。

考察两件事：粒度意识（给模型的都是摘要）与权限意识（读写分离、写操作审批）。

**评分维度**：五个以上工具且读写标注清楚（必需）。返回粒度明确是摘要（必需）。写工具配审批（加分）。

:::
