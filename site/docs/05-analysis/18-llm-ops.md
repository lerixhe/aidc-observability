如果要用一句话来描述这一讲，我想应该是：理解与编排交给模型，计算与执行交给老系统。

上一讲给了大模型在 AIOps 四层里的三个落点，这一讲展开其中最关键的形态：**Agent**。

它到底怎么干活、为什么适合运维、以及哪些地方绝不能让它碰。

## 学完这一讲，你应该能

- 拆解一次故障处理中工程师实际在做的事，判断哪些环节适合交给大模型
- 说清三级落地的风险递增曲线，并指出自己团队应该先落在哪一级
- 画出一个网络排障 Agent 的 Loop（规划、调工具、观察、再推理、产出证据链）
- 掌握四条护栏，尤其是"上下文工程"与"证据链强制"的具体做法
- 理解为什么评测回放是落地的工程前提，不是可选优化

## 机制拆解

### 0x01 为什么运维天然适合 LLM（但不是万能）

拆开一次故障处理，工程师实际在做什么：

| 动作 | 性质 | 适合谁 |
|---|---|---|
| 读大量非结构化文本（告警描述、日志、工单、runbook、历史复盘） | 语言理解 | **LLM 强项** |
| 凭经验联想"这个报错像上个月那次" | 检索式记忆 | **LLM 加 RAG** |
| 查一堆系统拼证据（指标、拓扑、任务状态） | 工具编排 | **LLM 编排、工具执行** |
| 确定性执行（重启进程、下发配置） | 状态变更 | **传统自动化**，轮不到 LLM |

结论是分工原则：**"理解与编排"交给 LLM，"计算与执行"交给传统系统。**

反着来，也就是让 LLM 算指标、直接执行命令，几乎是所有失败案例的共同起点。两边的分工相当于把"想"和"做"拆成两个进程，各管一端。

### 0x02 三级落地场景（由浅入深，风险递增）

| 级别 | 场景 | 风险 | 前置依赖 |
|---|---|---|---|
| **L1 · 摘要** | incident 自动摘要：把 50 条告警写成人话（影响面、疑似方向、建议排查项） | 零（只读、输出给人看） | 告警收敛已做好 |
| **L2 · 检索** | RAG 知识库：runbook、历史复盘、配置文档向量化，值班时问答 | 低（答案可能过期，需带出处） | 文档资产与版本管理 |
| **L3 · Agent** | 工具调用闭环：自主决定调什么工具、拼证据、产出"候选根因加证据链" | 中（幻觉风险，需护栏） | 工具 API 化、权限分级 |

L3 的 Agent Loop：

```text
输入：「任务 X 变慢，网络侧有没有问题？」
  → 规划：先查任务元数据（哪些 Rank / 哪些路径）
  → 调工具：query_topology() / query_probe_paths() / query_gnmi_counters()
  → 观察结果：某 rail 的 pause 计数异常上涨
  → 再推理：补查该 rail 的 CRC/DOM 与相邻端口
  → 产出：候选根因 + 证据链（每条结论引用具体工具返回值）
  → 人工确认 / 分级处置
```

::: info 经验映射（IDC → AIDC）

这套模式你在哪见过？**就是日常在用的编码 Agent**：理解需求 → 规划 → 调工具（读文件、跑命令）→ 观察 → 再推理 → 产出。

Agent Loop 相当于你的手工排障流程，只是每一步都换成了可执行的工具调用。

用过 Agent 写代码的人，天然懂运维 Agent 该怎么设计、会怎么翻车。上下文放不下就会瞎猜，工具返回太脏就会跑偏，没有验证步骤就会"自信地错"。

这份直觉在运维团队里仍然稀缺，也是面试时最能体现差异化的部分。
:::

### 0x03 四条护栏

1. **上下文工程。** 绝不能把原始数据喂给 LLM。一亿个时序点塞不进上下文，塞进去也没有意义。
   正确做法是工具先把数据**聚合摘要**（"过去 5 分钟该设备 PFC pause 上涨 40 倍，涉及 3 条路径"），LLM 只吃结论级摘要。
   这与"探测端先做多维聚合、再上报"是同一个架构思想：**把计算下沉到离数据近的地方**。

2. **证据链强制。** 所有结论必须引用工具返回值（可核查），引用不上的陈述显式标记为"推测"。
   防幻觉的核心是**让编的无处遁形**，不是求模型别编。只要结论必须挂证据，幻觉就从"隐蔽的错误"变成"显式的空缺"。

3. **权限分级。** 只读工具随便调。写工具走白名单加参数校验加人工审批。这是上一讲"处置分级加回滚"在 LLM 场景下的落地。

4. **评测回放。** 用历史故障做回放测试，输入当时的告警，看 Agent 能否得出当时的结论、证据链是否成立。
   没有评测的 Agent 是玄学。回放集同时也是回归测试集，任何提示词或工具改动都要跑一遍。

::: warning 一个容易忽略的成本

L3 Agent 的成本主要在**工具 API 化**，不在模型调用费。拓扑查询、路径查询、设备计数器、runbook 检索，全要变成稳定的、有权限边界的、返回摘要的接口。

没有这层，Agent 只能在聊天窗口里"建议你去查一下"。这也解释了为什么很多公司的 AIOps 大模型项目停在 L1：不是模型不行，是工具层没做。
:::

## 经验映射

| 你已有的能力 | 在 LLM 落地里的位置 |
|---|---|
| 告警收敛与 incident 归并 | L1 摘要的输入 |
| runbook 与复盘文档积累 | L2 RAG 的知识库 |
| 指标与拓扑查询 API | L3 工具层的原料 |
| 处置分级与回滚设计 | 护栏 3（权限分级） |
| 使用编码 Agent 的经验 | 对 Agent 行为与失效模式的直觉 |
| 缺失部分 | 评测回放体系、工具层的摘要粒度设计 |

## 判读与实操

### 0x04 一个可直接落地的护栏清单

| 护栏 | 具体措施 | 验收方式 |
|---|---|---|
| 上下文工程 | 工具返回聚合摘要，附带时间窗与口径说明 | 单次调用的返回体 < 2KB 且含结论 |
| 证据链 | 每条结论附 `tool_call_id` 与关键数值 | 抽检 20 条结论，能被人工复核 |
| 权限分级 | 读写工具分注册表，写操作需审批工单 | 演练一次越权调用被拒绝 |
| 评测回放 | 30 个历史故障的告警快照加期望结论 | Top-3 命中率与证据完整率 |

### 0x05 判读要点

| 现象 | 判读 |
|---|---|
| Agent 反复调同一工具 | 工具返回不含它需要的信息，摘要粒度错了 |
| 结论正确但证据链缺失 | 提示词未强制引用，或工具没返回可引用的标识 |
| 结论在相似场景间摇摆 | 缺评测回放集，无法回归验证 |
| 人工最终不采纳 | 多数情况是摘要信息不足，而非模型推理能力不足 |

## 习题

**必答 Q1**：三分钟陈述："如果让你在智算网络监管控平台里落地大模型能力，你分几级落地、每级做什么、护栏怎么设？"控制在 400 字内。

::: details 参考答案与评分维度

分三级落地，逐级增加风险与依赖。

**L1 摘要**。incident 自动摘要，给出影响面、疑似方向与建议排查项。纯只读，输出给人看，先解决"值班被淹"。

**L2 检索**。runbook、历史复盘、配置文档入 RAG，带出处与版本，回答"这类告警的处置路径"。

**L3 Agent**。工具调用编排，产出候选根因加证据链。工具层必须 API 化并返回聚合摘要。

**护栏**四条。① 上下文工程，只喂结论级摘要。② 证据链强制，结论必须引用工具返回值，推测显式标注。③ 权限分级，读写分离、写操作审批。④ 评测回放，用历史故障集做回归。

**评分维度**：三级清晰且风险递增（必需）。护栏至少覆盖证据链与权限（必需）。能指出"工具层 API 化是 L3 的真门槛"（加分）。
:::

**必答 Q2**：有句话叫"防幻觉的核心，是让编的无处遁形"。展开解释这句话背后的设计思想。

::: details 参考答案与评分维度

幻觉是概率模型的固有属性，用提示词"请不要编造"无法消除，只能降低频率。这是把可靠性寄托在不可控因素上。

工程设计换个方向：让"编造"在结构上不可能通过。做法是**强制证据链**。每条结论必须关联具体工具调用与返回值。没有证据的结论只能以"推测"形式出现，而且明确标注。

这样模型仍可能编，但编出来的东西一眼可辨，不会伪装成事实进入决策链。本质上，这是给每一条结论都装上审计回溯点。

再进一步，把关键计算从模型手里拿走，下沉到 SQL 与聚合引擎。模型只负责"决定算什么"和"解释结果"，可编造的空间从源头缩小。

**评分维度**：指出幻觉不可消除（必需）。给出"结构上无法伪装"的思路而非提高模型能力（必需）。提到"计算下沉"（加分）。
:::

**自测 Q3**：为什么不让 LLM 直接计算指标、直接执行预案？

::: details 参考答案与评分维度

**计算**。LLM 是概率模型，算术不保证精确，且大规模数据进不了上下文。计算必须下沉到 SQL、代码、聚合引擎，LLM 只决定"算什么"。

**执行**。输出具概率性，一次幻觉就是一次生产事故，且预案执行通常不可逆。

分工原则：LLM 管不确定性高的"理解与编排"，确定性系统管正确性要求高的"计算与执行"。

**评分维度**：两点都答到（必需）。能补充"执行需审批与回滚"（加分）。
:::

**自测 Q4**：设计一个"网络排障 Agent"的工具清单：至少 5 个工具，标注每个是只读还是写、返回什么粒度的数据。

::: details 参考答案与评分维度

| 工具 | 类型 | 返回粒度 |
|---|---|---|
| `query_task_meta(task)` | 只读 | 任务的并行策略、Rank 分布、起止时间（结构体） |
| `query_topology(device 或 task)` | 只读 | 邻接关系、所在 rail 与平面（小图） |
| `query_probe_paths(task 或 device)` | 只读 | 受影响路径集合与时延劣化摘要（Top-N，不含原始序列） |
| `query_device_counters(device, window)` | 只读 | 聚合后的 pause / ECN / CRC / 队列摘要（带口径说明） |
| `search_runbook(symptom)` | 只读 | 相似历史故障与处置方案（带出处与时效） |
| `execute_playbook(action, args)` | **写** | 白名单动作加审批工单号加结果回执 |

考察点两个：**粒度意识**（给 LLM 的都是摘要）加 **权限意识**（读写分离、写操作审批）。

**评分维度**：五个以上工具且读写标注清楚（必需）。返回粒度明确是摘要（必需）。有一个写工具配审批（加分）。
:::

## 小结

这一讲可以压成一句话：**理解与编排交给模型，计算与执行交给老系统。**

拆开一次排障，工程师做四件事：读大量非结构化文本、凭经验联想、查系统拼证据、确定性地执行变更。前两件是语言理解，第三件是工具编排，第四件是状态变更。前三个 LLM 能帮上大忙，第四个绝对不能交给它。

落地分三级。L1 摘要零风险，L2 检索低风险，L3 Agent 中风险要护栏。护栏四条：只喂摘要不喂原始数据、结论必须挂证据、读写权限分级、用历史故障做回放评测。

真正的门槛不在模型，在工具层。拓扑查询、路径查询、设备计数器、runbook 检索，全得变成稳定的、带权限的、返回摘要的接口。没有这层，Agent 只能在聊天框里建议你去查一下。

::: tip 本课要点

**理解与编排交给模型，计算与执行交给老系统。**

- 分工原则：**"理解与编排"给 LLM，"计算与执行"给传统系统**，反着来必翻车
- 三级落地：**L1 摘要（零风险）→ L2 RAG 检索（低）→ L3 Agent 工具调用（中，需护栏）**
- Agent Loop：规划 → 调工具 → 观察 → 再推理 → 产出**证据链**
- 四条护栏：**上下文工程（喂摘要不喂原始数据）· 证据链强制 · 权限分级 · 评测回放**
- 真门槛不是模型，是**工具层 API 化加摘要粒度设计**，这也解释了多数项目为何停在 L1
- 防幻觉的正确方向：**让编的无处遁形**。求模型别编是伪命题
:::

留一个思考题：如果 Agent 的候选根因对了但证据链缺一条，你会让它自动处置吗。
