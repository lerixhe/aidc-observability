description: MTTR 是四段时间的和。拆成发现、定位、恢复、验证，逐段给出可优化的抓手与自动化的边界。
---

我们天天都在看 MTTR 这个数，久而久之以为它就是一个减法：出事时间减去恢复时间。看板上一个数字，月底考核一次。

但是这个数字背后的四段时间，多数团队从来没有真的拆开过，这一节我们把它们拆开，每一段都配一条能直接敲的命令。

## 先拆一次

```text
MTTR = MTTD（发现）+ MTTI（定位）+ MTTR_p（恢复）+ MTTV（验证）
```

千卡集群的一次典型事故，从第一声告警到训练恢复正常 40 分钟，里面大概 8 分钟在发现，20 分钟在定位，10 分钟在恢复，2 分钟在验证。

| 段 | 典型占比 | 主要手段 | 常见浪费 |
|---|---|---|---|
| 发现 | 20% | 告警、异常检测、业务监控 | 聚合窗口太长、告警被抑制规则吞掉 |
| 定位 | 50% | 拓扑、日志、INT、RCA 图 | 各层数据口径不一，人要手工对齐 |
| 恢复 | 20% | 隔离、切换、回滚 | 权限流程、变更审批串行 |
| 验证 | 10% | SLI 对比基线 | 只看告警消失，不看性能回到基线 |

**定位吃掉一半时间。** 这个比例在多数团队身上成立，而多数团队优化的是发现。

拿最近五次事故各填一行，分布就出来了。填完你大概会发现两件事：定位段最长，恢复段最容易自动化，而预算全花在发现段的工具采购上。

## 发现段：先看任务，不看设备

设备侧告警的延迟来自三个地方。**聚合窗口**，1 分钟窗口的均值告警最快也要 1 分钟才响。**阈值宽度**，阈值要压住噪声，通常设在明显异常的位置，劣化早期不响。**抑制规则**，同一设备的告警收敛到一条，响应时间被上游告警拖住。

训练任务本身没有这三个延迟，每个 step 都在打时间戳，直接看步耗时分布，漂移能在秒级被看见。

```text
$ grep -E 'step_time|elapsed' train.log | tail -5
step 1840  step_time_ms 380.2
step 1841  step_time_ms 379.8
step 1842  step_time_ms 520.4
step 1843  step_time_ms 521.1
step 1844  step_time_ms 519.7
```

一次跳变，三行就知道，接着看它是不是全体变慢：

```text
$ grep -E 'rank .* step .* time' nccl_debug.log | tail -8
rank 0  allreduce  p50 190.2 ms
rank 8  allreduce  p50 188.7 ms
rank 16 allreduce  p50 191.4 ms
rank 24 allreduce  p50 189.9 ms
```

这组数字说明两件事：中位数整体在涨，不是个别慢节点；集合通信占比从 24% 涨到 36%，问题在网络或通信调度，不在算力。

步耗时本身没有绝对好坏，判据是它与基线的比值。所以第一周采集的核心产出是基线，不是告警。基线要按任务类型分开存，不同模型、不同卡数、不同并行策略的步耗时不可比，混在一起算等于没有基线。

## 定位段：定界、缩小、确认

定位有固定三步，每一步都有一条命令对应，敲完三步基本就能指到具体端口。

### 定界

问的是哪一层：任务、主机、网络、光层。

| 层 | 数据源 | 定界信号 |
|---|---|---|
| 任务 | 训练日志、步耗时分解 | 是否全体变慢，是否集中在某些 rank |
| 主机 | NCCL 日志、DCGM | 是否有单卡降频、XID、NVLink 重放 |
| 网络 | gNMI 计数器、INT | PFC 时长、ECN 标记率、路径时延分解 |
| 光层 | 光功率、lane 级 CRC、FEC 纠正 | 单 lane 劣化、FEC 纠正率抬升 |

先排主机单卡，一条命令：

```text
$ nvidia-smi --query-gpu=index,clocks_throttle_reasons.active --format=csv
index, clocks_throttle_reasons.active
0, 0x0000000000000000
1, 0x0000000000000000
2, 0x0000000000000004
```

第三张卡的 `0x4` 是「因功耗上限降频」，这张卡在拖慢整个 ring。这个字段比看温度有用，温度高不等于降频，降频一定有个原因位，先看原因再谈散热。

再看有没有硬件事件：

```text
$ dmesg -T | grep -iE 'Xid|nvlink.*error' | tail -3
[Mon Oct 21 10:04:12 2024] NVRM: Xid (PCI:0000:3b:00): 79, pid=0, GPU has fallen off the bus
```

看到 Xid 79 就不用往下查网络了，卡和主板之间已经掉线，这时候拔网线查交换机纯属浪费时间。

### 缩小

在全网里找到具体设备、端口、链路，这一步最耗人，因为它要求把拓扑、时间线、指标三者对齐，而这三样通常躺在三个系统里。

```text
$ gnmic -a leaf-07:57400 -u admin -p *** --insecure get \
    --path '/interfaces/interface[name=eth1]/state/counters/out-pfc-pause-frames'
{
  "updates": [
    { "Path": "interfaces/interface[name=eth1]/state/counters/out-pfc-pause-frames",
      "values": { "out-pfc-pause-frames": 184271 } }
  ]
}
```

一个数没有意义，要的是增量，同一端口隔一分钟再拉一次，差值是 3200 帧，这就是「这个端口正在喊停」的证据。

路径级的证据用实验室里的那条命令：

```text
$ cd labs/07-int-path && go run . -scenario upstream
定位到第 3 跳（sw-003f）：上游争抢
   3  sw-003f  7    2          28.0     640    55.0  89.1%  上游争抢
```

五跳里第 3 跳吃掉 89% 的时延，端口号直接给出来了。RCA 图在这里的作用是把可能性排序，把最可疑的三个候选放到人前面，省掉「挨个端口翻一遍」的那半小时。

### 确认

三角验证，三个独立证据指向同一处才算确认。

```text
证据一  gnmic 拉 pause 计时增量       eth1 每分钟涨 3200 帧
证据二  INT 逐跳记录                  第 3 跳排队 28 µs，占比 89%
证据三  同一时刻其他流                rail 3 上另外两条路径同时劣化
```

三个来源不同结论才可信，三条都指向 eth1，就可以动手了。

## 恢复段：动作阶梯

处置动作按影响面排阶梯，低阶先上，别一上手就重启。

| 阶 | 动作 | 影响 | 可逆 | 建议 |
|---|---|---|---|---|
| 1 | 标记嫌疑端口，加重观测 | 无 | 是 | 自动 |
| 2 | 调整 ECMP 权重或路由，避开嫌疑链路 | 局部流量迁移 | 是 | 自动，带速率限制 |
| 3 | drain 端口，把链路摘除 | 该链路流量转移，容量降一档 | 是 | 自动或人确认 |
| 4 | 从 checkpoint 重启任务 | 回退到上一个 checkpoint | 损失算力时间 | 人确认 |
| 5 | 换硬件、重启设备 | 服务中断 | 否 | 人执行 |

自动化的分界线在第 3 阶与第 4 阶之间，判断标准只有一条：**动作可逆且影响局部，就可以自动。**

第 1 阶的命令很安全，只是把观测压实：

```text
$ gnmic -a leaf-07:57400 -u admin -p *** --insecure subscribe \
    --path '/interfaces/interface[name=eth1]/state/counters/out-pfc-pause-frames' \
    --mode stream --stream-mode sample --sample-interval 100ms
```

第 3 阶的 drain 就不一样了。敲下去之前先看一眼同 rail 还有几条活链路，容量余量够不够：

```text
$ show interface ethernet 1/1 | grep -E 'link|rate'
Ethernet1/1  is up  400G
```

**下面这条命令会把整条链路的流量摘走，敲之前先确认容量兜底在哪里。** 摘错了不是一条链路的事，是同 rail 上几十个 rank 一起变慢：

```text
$ interface ethernet 1/1 shutdown
```

## 验证段：假恢复

恢复动作做完、告警消失之后，有两种假象会跟着出现。

**流量绕开了问题，问题还在。** drain 端口之后告警消失，但那条链路的硬件没修。临时路由一旦回切，故障立刻复现。

**指标回绿但性能没回。** NCCL 把 ring 重组到跨节点路径上，PFC 与 ECN 全部正常，因为流量不走那些链路了。步耗时比基线高 30%，谁也没报警。

验证要看**业务 SLI 是否回到基线**，不是看告警是否消失。

```text
$ ./all_reduce_perf -b 8 -e 128M -f 2 -g 8 | tail -4
  8388608    16777216  float  sum  1234.56  1359.12  0.00  0  0  0.00
 # Avg bus bandwidth    : 268.41
```

总线带宽回到基线值的 ±5%，才算网络侧真的恢复了。跑一次一分钟，省掉的是两周后重来一遍。

```text
验证三问：
1. 受害任务的步耗时是否回到基线 ±10%
2. NCCL ring 是否回到域内或原路径
3. 被处置的设备或链路，故障根因是否已确认并登记
```

第三问常被跳过。跳过它的后果是同一颗光模块两周后再炸一次，而所有人都以为已经修过。

## 一次事故的时间账

| 时刻 | 事件 | 分段 |
|---|---|---|
| 10:00 | 任务步耗时从 380 ms 涨到 520 ms | 发现起点 |
| 10:06 | 值班看到步耗时告警 | 发现结束，6 分钟 |
| 10:09 | 确认全体 rank 同步变慢，排除单卡 | 定界 |
| 10:18 | INT 显示第 3 跳排队，定位到具体端口 | 缩小 |
| 10:23 | 三项证据对齐，确认该端口 PFC 风暴 | 确认，定位结束 17 分钟 |
| 10:26 | drain 端口，流量绕开 | 恢复 |
| 10:31 | ring 重组完成，步耗时回到 390 ms | 验证，5 分钟 |

总计 31 分钟：发现 6、定位 17、恢复 3、验证 5。优化收益最大的是定位段，最容易被自动化的却是恢复段。

## 每段一个抓手

| 段 | 单一最有效动作 |
|---|---|
| 发现 | 把训练步耗时纳入 SLI，按任务类型建基线 |
| 定位 | 统一四层数据的时间戳与设备命名，让对齐成本归零 |
| 恢复 | 把可逆动作写成带速率限制的 runbook，砍掉审批串行 |
| 验证 | 恢复后强制跑一次基线对比，结果写进事故记录 |

第二项听着最不技术，收益最大。定位慢，多数时候卡在数据对不上：设备名三套叫法、时间戳两个时区、端口号两套编号，真缺数据的场合反而少。

这些命令没有一条是新东西，`nvidia-smi`、`dmesg`、`gnmic`、`all_reduce_perf`，全是手边现成的。MTTR 压不下去，通常不是缺工具，是这四条命令从来没被写进同一张纸上。

## 经验映射

| 你已有的做法 | 在 MTTR 拆解里的位置 |
|---|---|
| 服务排障的分层定位 | 定界、缩小、确认三步 |
| 变更管理与审批流 | 动作阶梯与权限分界 |
| 金丝雀与回滚 | 可逆动作优先，不可逆动作人确认 |
| 事故复盘模板 | 每段耗时归因，而不是只写「已恢复」 |
| 灰度与基线对比 | 验证段的三问 |

方法论全是旧的，新增的约束只有一条：**网络侧的处置粒度过粗。** 服务可以灰度 1% 流量，网络只能整条链路摘除或整台设备重启，所以动作阶梯的每一阶都要先想好容量兜底在哪。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：某集群 MTTR 是 45 分钟，老板要求压到 20 分钟。给出拆解方案与三处最可能的收益点。

::: details 参考答案与评分维度

先拆再加。拿最近五次事故各填一行四段耗时，没有这个数据就不要承诺数字。

典型分布是发现 8、定位 25、恢复 10、验证 2。据此找收益点：

1. 定位段。统一设备命名与时间戳，把四层数据对齐从人工变成查询，通常能砍掉定位时间的一半。
2. 发现段。训练步耗时纳入 SLI，按任务类型建基线，发现从 8 分钟降到 2 到 3 分钟。
3. 恢复段。可逆动作（标记、改权重、drain）做成带速率限制的自动化，砍掉审批串行。

验证段不要压。压掉验证换二次事故，代价远大于省下的 2 分钟。

**评分维度**：先拆解再谈目标（必需）。三处收益点与段对应（必需）。明确不压验证段（加分）。

:::

**必答 Q2**：设计一套自动化处置流程，要求能在无人值守时安全运行。写出动作清单与每步护栏。

::: details 参考答案与评分维度

动作清单按可逆性分三层。

自动执行：标记嫌疑端口、加重采样、生成时间线快照、通知值班。

带护栏自动执行：ECMP 权重微调（单次改动不超过 10%，10 分钟内最多两次）、drain 端口（要求同 rail 至少还有一条健康链路，且集群整体容量余量 ≥ 15%）。

必须人确认：任务重启、设备重启、固件升级，以及任何不可逆操作。

护栏四条。速率限制，任何自动动作有频次与幅度上限。熔断，连续两次自动动作没有改善就停下来等人。审计，每次动作写操作日志与触发依据。回滚预案，可逆动作必须记录原始配置。

**评分维度**：按可逆性分层（必需）。给出至少两条具体护栏（必需）。提到熔断或审计（加分）。

:::

**自测 Q3**：为什么「告警消失」不能作为恢复完成的判据。

::: details 参考答案与评分维度

告警看的是被监控对象，不是用户体验。drain 一条链路后，这条链路的计数器归零，告警自然消失，硬件问题还在。或者流量被路由绕开，ring 重组到跨节点路径，网络指标全绿而步耗时仍高于基线。

判据是业务 SLI 回到基线，并确认根因已登记。

**评分维度**：指出告警与用户体验脱钩（必需）。举出绕开或重组两种形态（加分）。

:::

**自测 Q4**：定位段最耗时的环节通常是什么，怎么把它变成可工程化的能力。

::: details 参考答案与评分维度

最耗时的是数据对齐：设备命名不统一、时间戳不同源、端口编号两套体系，人要手工拼接四层数据。

工程化做法是把对齐做成数据模型的一部分。设备用统一资产 ID 做主线，时间统一打采集端时间戳并保存时钟偏差，端口用拓扑里的稳定标识。对齐之后，定位从查三个系统变成一个查询。

**评分维度**：点出数据对齐（必需）。给出统一标识与时间戳方案（必需）。

:::

## 小结

一次 40 分钟的事故，8 分钟在发现，20 分钟在定位，10 分钟在恢复，2 分钟在验证。定位吃掉一半时间，可多数团队天天优化的是发现。

发现段看任务不看设备，设备告警受制于聚合窗口、阈值宽度、抑制规则，训练步耗时不受这三样限制，每个 step 都在打时间戳。

定位段三条命令：`nvidia-smi` 看降频位，`dmesg` 看 Xid，`gnmic` 看 pause 增量，最后用 INT 的逐跳记录锁定端口。恢复按可逆性排阶梯，可逆且影响局部的可以自动。验证段跑一次 `all_reduce_perf`，总线带宽回不到基线就是假恢复。

::: tip 本课要点

**分段才谈优化，MTTR 是四段时间的和。**

- 四段之和：**发现 + 定位 + 恢复 + 验证**。典型占比 20 / 50 / 20 / 10，定位最长
- 发现段：`nvidia-smi --query-gpu=clocks_throttle_reasons.active` 与 `dmesg | grep Xid` 先排主机
- 定位三步：定界（哪一层）、缩小（哪台哪口）、确认（三个独立证据）
- 自动化分界线：**可逆且局部可自动，不可逆必须人确认**
- 一条坑：假恢复。告警消失不等于性能回基线，验证段的三问不能省
- 每段抓手：发现建基线、定位统一标识、恢复砍审批串行、验证对比基线

:::

留一个思考题：定位段的数据全都齐了但还是慢，你会先怀疑工具，还是先怀疑团队不知道怎么问问题。
