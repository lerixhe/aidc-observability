第 04 讲留下一个问题没答：InfiniBand 天生无损、免调优，为什么还要在以太网上费力做无损？

读者们可思考过那个场面：凌晨三点，一条链路开始劣化，训练任务挂在原地不动，值班的人被叫起来，先要判断是哪条路径出了问题，再想办法把流量绕开，中间还得确认容量够不够。一个小时的活儿，天亮了才算完。如果是一个万卡集群，这样的事故足以上新闻了。

所以必须在两条路线里选一个，让这类故障发生时有人兜着：要么硬件天生把无损做到位，要么软件把无损补上。两条路线就是两个阵营，它们的差别不在于谁更快，在于「无损这件事由谁来保证」。

我们可以把 InfiniBand 那一套看成机器自带的心脏：Subnet Manager 一直在跳，拓扑、LID、路由都归它管，节点掉线它重算路径，链路恢复它算回去，应用侧无感。它一般由一到两台节点跑着，一台挂了另一台顶上。

它负责持续监控节点的健康，当某条链路挂掉时，自动重算一条可用路径；客户端不需要知道地址，因为它从来不用地址，它用的是 LID 和 QP，路由由交换机和 SM 维护。当链路发生故障时，在途的报文可能会重传，但连接不需要重建。如此应用程序将无需重启即可自动完成路径切换。

以太网那边没有这颗心脏。链路挂了就是挂了，流量靠 ECMP 重新哈希，哈希到哪条是随机决定的，好不好只能看运气；配置错了没人纠正，因为根本没有一个实体在管配置。所以以太系的「高可用」是攒出来的：PFC 兜住不丢、ECN 兜住不堵、watchdog 兜住死锁，三样都得人配得对。

## 无损也不是绝对不丢

IB 的无损不靠丢包之后重传补救，也不靠阈值报警，它靠信用。发送端在发之前先问接收端「你还有多少缓冲」，接收端按自己剩余的空间发回信用额度，发送端有多少信用就发多少，发完就停。这个过程是硬件逐跳完成的，不经过软件，所以它不存在「阈值设多少合适」这个问题。

SHARP 是另一层红利。它把集合通信的归约计算下沉到交换机里做，比如 AllReduce 的求和，数据不必全走到终点再算，路径中间就被合并了，回程流量大幅减少。这是专用硬件的红利，标准以太网交换芯片做不了这种定制计算。

以太网这边只能「提前刹车」凑出无损，PFC 在链路快满时发暂停帧，ECN 在队列越过阈值时给报文打标记，DCQCN 收到标记就按比例降速，三样协同。配好了以后效果确实像 IB：端到端一个包不丢，应用不用改，运维不用管。

不过好话说完了，代价得摊开。这套无损是「尽力而为地不丢」，而且自己造出了三种故障模式：反压沿着链路往回走，同优先级的其他流一起吃暂停，这是队头阻塞；反压会成环，三台交换机互相顶住，pause 在环路里转圈，这是 PFC 死锁；反压会扩散，一台叶交换机的拥塞能在几秒内传导到整张网上，源头反而看不出来。

所以有两个关键参数要先定。

```text
xoff 水线   高一点 → 缓冲更安全，反压更容易触发
            低一点 → 反压少，缓冲容易打穿

watchdog 超时  短一点 → 死锁恢复快，正常大流量会被误杀
               长一点 → 环路要转很久才有人救
```

第一个参数控制「宁可多停还是宁可多丢」，第二个参数控制「多快认定它是死锁」。这两个参数没有普适最优值，跟集群规模、流量模型、芯片缓冲都相关，这就是「调优」两个字的实际含义。

## 两边的手边工具

接下来我们看看两边怎么查。IB 这边，工具是随栈一起来的：

```text
$ ibstat
CA 'mlx5_0'
        State: Active
        Physical state: LinkUp
        Rate: 400
        Base lid: 12
        SM lid: 1
$ perfquery 12 1
PortSelect:......................1
PortXmitData:....................184467
PortRcvData:.....................912043
```

`ibstat` 看端口状态，`perfquery` 看端口计数器，`ibdiagnet` 一把扫全网的拓扑、路由、错误、SM 状态，报告直接给到端口号。三个命令都是随包来的，不用自己写。

RoCE 这边，同样的信息要自己拼：网卡侧走 `ethtool`，交换机侧走 gNMI，两台设备两套词汇，中间还要一个拓扑库把它们对上。

```text
$ ethtool -S ens1f0 | grep -iE 'pause|crc|discard'
rx_pause_ctrl_phy: 12841
tx_pause_ctrl_phy: 39217
rx_crc_errors_phy: 0
```

有个问题是，**链路切换时，客户端如何感知路径变了**？通过分析 NCCL 的行为，我发现它在建立通信域的时候，就已经把集合通信的路径与算法挑好了：`NCCL_IB_HCA` 决定用哪几张网卡，GID index 决定走 IPv4 还是 IPv6 封装，拓扑探测决定环怎么排。

如果某条链路挂掉，QP 上的在途报文会重传，重传成功就继续走老路，因为路由已经由交换机重新算过了；重算后的路径如果绕远了，连接也不会重建，任务继续跑，只是变慢。这一层很聪明，也很讨厌：**它让一次路径变更变得无声无息**。

但是这样还不够。如果是规划好的迁移，链路并没有挂，而老的连接已经建好了在用，没有新连接需要建立，那这些连接是不是一直切换不过去？

继续往下看，还有个点也做了控制。NCCL 遇到超时会放弃当前通信域，重新初始化一遍，那时候才会重新读环境变量、重新探测拓扑、重排环序。所以在主动迁移之后，老连接会一直跑在旧路径上，直到某一次超时把它们全部打掉重来。

迁移之后，之前配好的 `NCCL_IB_HCA` 可能指向已经不通的网卡，所有新连接都会失败。如果没有连接失败，虽然旧路径还能凑合跑，但带宽已经掉档，所以即使不重建也不会崩，只是慢一个量级。

## 换路线时谁最疼

想知道两个阵营差在哪，看一次故障的定位链就够了。IB 出问题，`ibdiagnet` 跑一遍，符号错误在哪台、哪口、哪条链路，报告直接给到端口号。RoCE 出问题，你得先知道去问谁：gNMI 看 pause 增量，INT 看逐跳排队，拓扑库查共同上游，时序库比对基线，四样东西四套口径，人肉对齐。

再追人这一层。IB 的运维要会看报告，RoCE 的运维要会写查询。前者是把结论读出来，后者是把数据拼出来。这就是为什么以太系集群的平台上总有一支团队在做采集、存储、定位这条链路，而 IB 集群里通常没有。

不过这样还不够。RoCE 世界里，工具链自己也要维护：采集器会掉线、口径会漂移、拓扑会过期，这些都是软件系统的老问题，得有人长期养。这一层的成本，在选型时通常被算在「人力」里，很少被算进「总拥有成本」。

## 国内为什么选以太系

第一是供应链自主。IB 绑定单一供应商，以太系可白盒自研加多厂商竞争，对超大规模自建集群是战略级考量。第二是成本曲线，万卡以上规模，单位带宽成本以太网显著更低，带宽演进节奏也更快，换代不用等专有体系。第三是运维体系延续，既有数据中心几乎全是「以太网加自研管控」，人才、工具链、经验全部可延续，换 IB 等于另起炉灶。第四是软件定义的红利，以太系可定制：rail 优化、遥测深度、自研协议配合，把网络变成自己的竞争力，而不是买来的黑盒。

前三条是成本与供应链，第四条是技术偏好。换个说法，选 RoCE 等于把网络当成自研系统的一部分，而不是一个采购项。

## 一条被忽略的因果

**正因为选了 RoCE**，PFC / ECN / DCQCN 的调优、全 Fabric 配置一致性、故障定位才变得极其复杂，这些复杂度必须靠平台软件填上。

换句话说，「网络可观测、自动化平台」这类岗位，很大程度上是「选 RoCE」这条技术路线的产物。

IB 世界里很多能力是硬件自带的：无损靠信用机制默认成立，拥塞控制内置且参数少，定位工具随厂商一起来。以太系世界里，同样的能力要自己写代码解决，平台软件接过了硬件本该做的事。

这条因果比背参数有用。它解释了一个运维岗为什么需要懂数据管道、时序存储、图上的根因定位：这些东西在这条路线上是必需品，算不上加分项。

有一条动态不能忽略：IB 阵营自己也在向以太网形态靠拢，面向 AI 的以太网 Fabric 方案，用自适应路由与拥塞控制补以太网的短板。「以太网不适合 AI」这个论断已经过时，方向上的分歧收敛成了「谁的软件栈更成熟」。

## 判断自己在哪边

路线之争在任何团队里都会出现。谈的时候分三层，不站队，把判断落在自己负责的范围内。

技术层要公平。IB 的优势是天生无损、免调优、在网计算，小规模快速起步很省心；RoCE 的优势是生态开放、成本、可定制，代价是把无损的复杂度从硬件转交给运维和平台。工程层讲动态，万卡以上规模，供应链安全与单位带宽成本会把天平压向以太系，而且方向已经收敛，差异在软件栈成熟度，不在物理层。个人层讲匹配，以太系把复杂度交给平台，这正是可观测与自动化平台存在的理由。

判断自己所在环境属于哪边，问四个问题就够：是否需要在交换机上配 PFC 水线与 ECN 阈值，是则 RoCE 世界，平台复杂度高；是否有专门的管控面做配置一致性校验，是则 RoCE 世界，且已经踩过坑；是否有秒级遥测订阅与队列级指标，是则 RoCE 世界，可观测已上正轨；是否存在「链路正常但训练变慢」的排查需求，那是 RoCE 世界的典型工作。

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：用技术、工程、个人三层把「IB vs RoCE 之争」讲一遍，给出你的判断。

::: details 参考答案与评分维度

技术层：IB 是专用网络，无损由硬件信用机制保证，基本免调优，还有 SHARP 在网计算，小规模起步省心。RoCE 跑在标准以太网上，无损靠 PFC / ECN / DCQCN 软硬协同，复杂度从硬件移到运维与平台，换回开放生态与成本优势。

工程层：万卡以上规模，供应链自主、单位带宽成本、既有运维体系延续三方面都指向以太系。IB 阵营自己也在推以太网形态的方案，方向上已经收敛，真正的差异在软件栈成熟度。

个人层：以太系把无损复杂度交给平台软件，这正是网络可观测与自动化平台存在的理由。路径级观测、实时数据管道、设备遥测这些积累，正是这个位置需要的。挑战是补齐无损语义，机会是这套能力在以太系里价值更大。

**评分维度**：三层齐全（必需）。技术层公平、不贬低 IB（必需）。工程层说出「方向收敛或软件栈成熟度」（加分）。个人层具体而非泛泛表忠心（加分）。

:::

**必答 Q2**：「网络自动化、可观测平台这个岗位，是选择 RoCE 的产物」，解释这条因果链。

::: details 参考答案与评分维度

选了 RoCE 之后，无损不再由硬件默认保证，要靠 PFC / ECN / DCQCN 参数在每一跳一致配置。配置错了链路依然「正常」，故障表现为隐性的性能劣化。

于是需要四件事：秒级设备遥测，看到队列与 pause；全 Fabric 配置一致性校验，防一跳配错；端网关联与根因定位；自动化下发与回滚，人改不过来。

这些全是软件工作，平台团队因此成为刚需。

**评分维度**：讲清「硬件保证变软件保证」的转移（必需）。串起至少三个由此产生的工作（必需）。对比 IB 世界里这些能力由硬件自带（加分）。

:::

**自测 Q3**：SHARP 是什么？它为什么能减少网络流量？

::: details 参考答案与评分维度

SHARP 把集合通信的归约计算（比如 AllReduce 的求和）下沉到交换机执行。数据不必全部汇聚到终点再算，路径中间就被归约合并，回程与后续链路的流量大幅减少。

这是专用硬件的红利，标准以太网交换芯片不易做这类定制计算。

**评分维度**：说出「交换机侧归约」（必需）。说出流量减少的机制（必需）。指出这是 IB 的专属优势（加分，体现评价公平）。

:::

**自测 Q4**：有人追问「传统 IDC 不也是以太网吗，有什么本质区别」，怎么接？

::: details 参考答案与评分维度

接法：网络形态确实同源（以太网、Clos、ECMP、QoS），变的是运维语义整体升级。

有损变无损：从「丢包重传」到「PFC / ECN 前置避免丢包」。轮询变订阅：从分钟级 SNMP 到秒级 gNMI。设备为中心变任务为中心：从「哪台设备坏了」到「哪个任务的哪条环受影响」。

所以硬件相近，平台软件的复杂度差别巨大，要补的是领域语义，不是从零学网络。

**评分维度**：承认同源（必需）。给出至少两项语义升级（必需）。把结论落在「补语义而非从零」（加分）。

:::

## 小结

IB 是专用网络，无损靠硬件信用机制天生成立，还带 SHARP 在网计算，插上就通，代价是封闭和贵。RoCE 跑在标准以太网上，无损要靠 PFC、ECN、DCQCN 三个东西在每一跳配得一模一样，配错了链路照样通，训练悄悄变慢。

而且以太系的无损不是免费的，它自己造出了三种故障模式：队头阻塞、反压成环、反压扩散。三种都得靠参数和 watchdog 兜着，这就是「调优」两个字的实际含义。

国内厂商选以太系有四个理由：供应链自主、成本曲线、运维体系延续、软件定义红利。这四条合起来，是把网络当自研系统的一部分，不是当采购项。

这条因果比参数有用：正因为选了 RoCE，无损的复杂度才从硬件落到软件上。于是有了秒级遥测、配置一致性校验、端网关联定位、自动化下发回滚这些活，也就有了平台岗位。

::: tip 本课要点

**选 RoCE 是拿运维复杂度换供应链自由度。**

- IB：专用网络、**硬件信用无损、免调优**、SHARP 在网计算、封闭且贵
- RoCE：标准以太网、**复杂度落在运维与平台**、开放生态、成本低、演进快
- 无损不等于不丢：**队头阻塞、反压成环（PFC 死锁）、反压扩散**，靠 XOFF 水线与 watchdog 兜
- 国内选以太系四理由：**供应链自主、成本曲线、运维延续、软件定义红利**
- 核心因果：**选了 RoCE → 无损靠平台软件补 → 可观测与自动化平台岗位存在的原因**
- 方向已收敛：IB 阵营也在做以太网 AI Fabric，差异转到软件栈成熟度

:::
