排障这件事经常遇到一种局面：所有指标都正常，任务就是慢。

比如一次训练，步耗时从 380 毫秒涨到 520 毫秒，你去翻面板，PFC 正常、ECN 正常、丢包为零、CRC 为零，四块面板全绿，你再看一眼阈值，全都离告警线差着三四个数量级。（这里说的「正常」，指的是每个单点值与各自阈值的关系，而这个故障的全部证据在趋势里，不在取值里。）

这个时候就要使用到端到端排障这一套。它把前面二十讲的东西全串起来，很多同学每一样都单独知道，也大致知道该看哪些指标，但是具体到一根线串下来的顺序，往往并不完全正确。

案例是构造的，每一层的数字都取自真实故障的典型形态，可以直接拿去核对自己的集群。背景是一个 512 卡训练任务，rail-optimized 拓扑，每台服务器 8 块网卡对应 8 条 rail，RoCEv2 加 PFC 与 ECN 全开。

```text
10:00  步耗时从 380 ms 涨到 520 ms，P50 与 P99 同步抬升
10:00  全部 512 个 rank 都变慢，没有明显的掉队者
10:00  NCCL allreduce 从 90 ms 涨到 190 ms，占比 24% → 36%
10:00  DCGM 无降频、无 XID、NVLink 无重放
10:02  全网 PFC 与 ECN 侧：只有 rail-3 的 leaf-7 上行口有异常
10:05  该端口 10 分钟内累计 pause 时长 42 秒，ECN 标记率 0.4% → 3.8%
10:08  该端口 CRC 从 0 涨到每分钟 12，FEC 纠正率从 1e-9 升到 4e-6
10:11  DOM 读数：lane 2 光功率 -8.9 dBm，其余 lane 在 -2.4 dBm 附近
10:15  drain 该端口，流量绕开
10:20  步耗时回到 390 ms，ring 恢复到原路径
```

这 20 分钟里没有任何一个单点指标是「超阈值报警」的，全长都在正常范围的上沿。能定案，靠的是一阶差分与四源对照。

## 第一刀：先分全体还是个别

判据只有两个。全体 rank 同步变慢，指向共享资源，网络、共享存储、调度，下一步走网络层；个别 rank 变慢，指向该主机，单卡、单网卡、单链路，下一步走主机层。

这个案例是全体同步变慢，网络层优先。如果只有 4 个 rank 慢，先去查那台机器，那一刀能省掉后面全部工作。

再看集合通信占比。占比从 24% 涨到 36%，说明时间被通信吃掉，算力没有退化，GPU 侧的问题先排除。

```bash
# 从训练日志算每步耗时与通信占比
python3 - <<'PY'
import re
pat = re.compile(r'step\s+(\d+).*?step_time:\s*([\d.]+)ms.*?allreduce:\s*([\d.]+)ms')
rows = [tuple(map(float, m.groups())) for m in pat.finditer(open('train.log').read())]
recent = rows[-200:]
p50 = sorted(r[2] for r in recent)[len(recent)//2]
share = sum(r[3] for r in recent) / sum(r[2] for r in recent)
print(f'allreduce_p50={p50:.1f}ms  comm_share={share:.1%}')
PY
```

但是有个问题：第一刀切完方向指向网络，可网络侧是几百台设备、几千个端口，从哪儿看起？

## 第二刀：主机层排除单卡与域内

于是我们先别急着翻交换机，慢的成因里有一半在主机侧，而且主机侧的证据成本最低。主机层要排除三样：降频、XID、NVLink 重放。

```bash
nvidia-smi --query-gpu=index,temperature.gpu,clocks_throttle_reasons.active --format=csv
dmesg -T | grep -i xid | tail
dcgmi dmon -l | grep -i nvlink
```

三项都干净，说明 GPU 与域内网络没有劣化。

但是以上逻辑还有问题。这一刀还漏了一个东西：NCCL 的 ring 组成有没有变。ring 是流量的实际路线图，它一变，后面所有网络指标都对不上号。域内重组就是这种情形，ring 被重组到跨节点路径，表现是全体变慢，而网络计数器干干净净。

```bash
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,GRAPH ./train 2>&1 | grep -i 'ring\|via'
```

ring 也还在原路径上，主机侧彻底排除。到这里，剩下的可能只有一个：某条链路上有东西在慢，而所有阈值告警看不见它。

## 第三刀：网络层从面到线

gNMI 负责面，告诉你哪台设备的哪个端口在冒烟；INT 负责线，告诉我们哪一跳在卡。一个看趋势，一个看因果。

案例里唯一的异常信号落在 rail-3 的 leaf-7 上行口。判读顺序是固定的：**PFC 时长**先看，不看帧数，42 秒每 10 分钟意味着这条链路 7% 的时间在反压；**ECN 标记率**看斜率，0.4% 到 3.8% 是十倍级上升，说明拥塞在被压制而不是被解决；**队列峰值**看有没有顶满，顶满加长时间 pause 就是风暴前兆；**CRC 与 FEC** 看一阶差分，CRC 从 0 到每分钟 12，这个绝对值在阈值体系里微不足道，在趋势上是第一阶段证据。

```text
现场经验值（同一端口，10 分钟窗口）
PFC pause 时长        < 1 s      正常
                      1–10 s     关注
                      > 10 s     严重，需处置
ECN 标记率             < 1%       正常（跑满带宽时 1–2% 也常见）
                      > 3%       持续存在即异常
```

但是这里有个岔路。PFC 异常只能说明这个端口在反压，说明不了它为什么反压。可能是上游流量打得太猛，也可能是这条链路的物理层在丢东西，逼着上层重传。两种成因的处置方式完全不同：前者要分流，后者要换件。区分它们的钥匙在下一层。

## 第四刀：光层找到那个 lane

劣化阶段的标志是 FEC 在硬扛。链路上不丢包，因为前向纠错把错误都纠回来了，代价是纠错余量被吃掉，pre-FEC BER 抬高，极端情况下芯片会降 lane 或降速率。

DOM 给出决定性证据：lane 2 的光功率 -8.9 dBm，其余 lane 在 -2.4 dBm 附近。单 lane 掉 6 dB，已经超出抖动范围，这是劣化。

```bash
# 读 DOM（厂商命令不同，这是通用形态）
show interfaces transceiver detail
# 关注每 lane 的 rx power、tx bias、温度
```

四个证据到这里齐了：业务层全体变慢、主机层干净、网络层单端口 pause 与 ECN 异常、光层单 lane 劣化。四条独立来源指向同一处。

不过 CRC 涨不能单独定案。脏端面、光纤弯折、连接器松动、对端芯片问题，都会表现为 CRC 上升。下结论要三个证据：DOM 的 lane 级读数、FEC 纠正率的斜率、更换后的对比。前两个是定位，第三个才是确认。

说到这里你可能会想到那一堆 RCA 平台。它们确实能做这件事，只是一套流程要装图模型、要对齐时钟、要喂历史告警，实现极为复杂，一般的团队要费很大的精力才可以搞懂。而眼前这一套只需要四样现成的数据源加一次一阶差分。为了治理这个乱象，我们把它固定成一条规则：**四源对照加一阶差分，四个来源指向同一处才定案。** 从此以后那些复杂的定位流程可以休息了，至少在单个 incident 上是这样。

## 处置顺序

| 顺序 | 动作 | 原因 |
|---|---|---|
| 1 | drain 该端口 | 影响局部、可逆、立刻见效 |
| 2 | 观察 ring 重组与步耗时 | 确认绕开后业务恢复 |
| 3 | 换模块或清洁端面 | 根治，需要停机窗口 |
| 4 | 回切验证并登记根因 | 不回切就不算确认修复 |

第二步容易被跳过，跳过的后果是以为「drain 之后好了」，任务其实在跨 rail 的次优路径上跑着，性能只是没坏到报警。第四步更容易被跳过，而且更贵。

## 时间对不齐问题

上面这套流程不能解决时间对齐问题。如果在采集与处置之间隔得太久，以至于基线已经过期，就会出现问题：你拿四周前的基线做对比，那台设备的流量形态早就变了，一阶差分算出来的斜率全是别人的故事。

为了避免这个问题，端到端排障不要用于跨月的历史对比。如果真的偶尔出现了，数据出现的小波错乱可能需要人工介入解决。

```py
tag = collect_ts_now()          # 采集时刻，跟证据一起存
if evidence.is_fresh(tag, max_age=4 * 3600):
    conclude(evidence)
    archive(evidence, tag)      # 假想的归档指令
```

有一个稍微安全一点的做法，是给每份证据打上采集端的接收时间戳，处置时先比对它与设备时间戳的偏差，偏差超过阈值就重新采一遍，确保你比较的不是两份不同时代的数据。

但是比对时间戳和重新采样不是一个原子动作，任何一键脚本也做不到，这需要在采集侧就埋好双时间戳。

这也不是一个完美的方案，它只是相对安全一点，因为如果你真的超时了，当前这条链路的形态早就翻篇了，别人也会乘虚而入。

## 重复处置

重复处置是指两个流程在同一个端口上同时下手：值班的手工 drain 一次，自动化规则又 drain 一次，设备上前一个动作的回滚把后一个动作的现场抹掉了。

分布式锁那篇里讲过可重入的代价：要支持同一个线程多次加锁，就得在客户端包一层引用计数，还要考虑计数的过期时间，代码复杂度继续升高。排障流程也一样，要支持多个流程同时对同一端口动手，就得在处置层做一个带所有权与租约的锁，还得处理租约过期后的接管。

笔者不推荐做可重入的自动处置，它加重了平台的复杂性，在流程设计上把处置动作收敛到一条单行道完全可以不用它：所有自动处置走同一个执行器，同一端口同一时刻只允许一个动作，后来的排队。

## 小结

第一刀按「全体还是个别慢」切。全体同步变慢走网络，个别 rank 慢走主机。这一刀下去，一半可能性已经排除。

四层各有自己的决定性证据。业务层看通信占比有没有上升，主机层看有没有降频、XID、NVLink 重放，网络层看 PFC 时长与 ECN 标记率的斜率，光层看 lane 级光功率。四条来源不同，指向同一处，才算确认。

处置按止血、止损、根治的顺序。drain 端口可逆、影响局部，先做。换模块要停机窗口，后做。最后一定要回切验证，不回切就等于把「临时绕开」当成「已修好」。

以上还不是端到端排障的全部。这个案例最不完美的部分是 10:20 之后的那段：指标变绿只是第一步，让同一颗模块不用再炸第二次，才算真的修完。下一讲把整门课收一下，说说你会了什么、还差什么。

::: tip 本课要点

**没有一个指标超阈值，定案靠一阶差分与四源对照。**

- 第一刀按「全体还是个别的慢」切：全体走网络，个别走主机
- 四层决定性证据：业务看通信占比、主机看降频与 XID、网络看 PFC 时长与 ECN 斜率、光层看 lane 级 DOM
- **所有指标都在阈值内也能定案**，靠的是斜率与跨源对照
- PFC 异常只说明在反压，成因要靠光层区分拥塞与劣化
- 处置顺序：drain 止血、观察绕开、换件根治、回切验证
- 一条坑：不回切验证，等于把「临时绕开」当成「已修复」

:::

## 习题

::: tip 怎么做题

先自己写答案，三行也算，再展开对照，最后按「评分维度」逐条自评。

:::

**必答 Q1**：给下面这组数据，判断问题在哪一层，并说明依据。

```text
步耗时      P50 从 380 ms 涨到 500 ms
rank 分布   只有 8 个 rank 变慢，集中在同一台服务器
通信占比    24% → 26%
DCGM        该服务器 GPU 温度 79℃ 正常，无 XID
NCCL 日志   allreduce 在该 rank 上耗时是其他 rank 的 4 倍
网络侧      该服务器 8 个网口的 PFC 与 ECN 均正常
```

::: details 参考答案与评分维度

问题在主机层，更可能在该服务器的 PCIe 或本地总线，不是网络。

依据两条：慢的 rank 集中在一台机器上，网络问题通常让整条 rail 或整条路径受害，不会只挑一台机器的 8 个 rank；该机器的 8 个网口指标都正常，网络侧证据缺失。

下一步看三处：该机器的 PCIe 带宽与错误计数、NIC 与 GPU 的亲和性（`nvidia-smi topo -m` 看 `PIX`、`PHB`、`SYS`）、CPU 侧是否有 NUMA 错配。通信占比只从 24% 涨到 26%，说明瓶颈在数据搬运链路，不在网络拥塞。

**评分维度**：定位到主机层并给出「集中在一台机器」这条依据（必需）。排除网络的理由基于端口指标（必需）。提出 PCIe 或亲和性方向（加分）。

:::

**必答 Q2**：把 checklist 压缩成 5 步，说清砍掉哪些以及为什么可以砍。

::: details 参考答案与评分维度

五步版本：全体还是个别变慢，决定走网络还是主机；通信占比是否上升，决定是通信还是算力；哪个端口 PFC 与 ECN 异常，做面的定位；逐跳时延是否集中在一跳，做线的定位；CRC、FEC、DOM 三级确认，锁定硬件确因。

砍掉主机层细查与 NCCL ring 检查。理由：如果第 2 步显示通信占比上升，主机层问题一般伴随 XID 或降频，先看 PFC 面板成本更低；ring 检查放到第 3 步无异常时再做，作为兜底。

风险要说清：五步版会漏掉「域内重组」这类没有网络异常的慢任务。

**评分维度**：五步覆盖定界、缩小、确认（必需）。说清砍什么以及风险（必需）。承认压缩有代价（加分）。

:::

**自测 Q3**：为什么这个案例里「丢包率为 0」完全不能作为排除网络的依据？

::: details 参考答案与评分维度

无损网络靠 PFC 与重传维持零丢包。零丢包是设计结果，不是健康指标。

真实的损失换成了别的东西：反压时长、纠错压力、带宽降档。这些都不体现为丢包，只体现为时延和有效吞吐。

**评分维度**：说清零丢包是设计结果（必需）。指出损失转化为时延与纠错压力（加分）。

:::

**自测 Q4**：PFC 上涨但 CRC 与 FEC 完全正常，下一步做什么。

::: details 参考答案与评分维度

先排除光层，把方向转向拥塞与配置。

流量分布：是否某个 ECMP 分支热点化，看 INT 的逐跳时延与出口利用率。水线配置：是否 XOFF 阈值过低导致容易触发 pause。上游突发：是否新上任务改变了流量形态。

再补一条：看 PFC 是否集中在同一优先级队列，这能把范围从链路缩到某类流量。

**评分维度**：排除光层并给出至少两个方向（必需）。提到按优先级拆维度（加分）。

:::
