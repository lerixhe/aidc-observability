上一课确立了结论：AI 训练网络要压丢包、压 MTTR。本课回答「为什么」的第一层——**为什么连 TCP 都不要了，非要绕过内核**？

理解了这一层的动机，后面的 PFC、ECN 你会自己推导出来，不需要背。

## 本节目标

- 说清一个包走内核协议栈的三笔代价，并解释它们在什么条件下才「致命」
- 用木桶效应解释：为什么同步训练只关心**尾延迟**，而不是平均延迟
- 复述 RDMA 的三大能力（内核旁路 / 零拷贝 / CPU 卸载），并对应到它们各自砍掉的那笔代价
- 推导出完整因果链：同步训练 → 微秒级稳定时延 → RDMA → 丢包恢复代价大 → 必须无损网络 → PFC / ECN
- 知道在机器上怎么确认「它真的在用 RDMA」，而不是只看网卡型号

## 机制拆解

### 内核协议栈的三笔代价

一个 TCP 包从网线进来，要经过这样一条路径：

```text
网卡硬件中断 → 软中断（ksoftirqd）→ 内核协议栈（IP + TCP 状态机、校验、拥塞控制）
            → 数据拷贝到应用缓冲区 → 上下文切换唤醒应用
```

这条路径有三个代价。日常业务里它们都被摊薄了，所以无感；在同步训练里全是致命的：

| 代价 | 具体表现 | 什么时候致命 |
|---|---|---|
| **时延与抖动** | 单次收发包几十微秒起步，且尾延迟不可控 | 软中断排队、CPU 调度、锁竞争会让个别包慢出几个数量级 |
| **CPU 消耗** | 协议栈处理吃 CPU 核 | 200Gbps 线速下单核跑不过来，需多核分摊——而 GPU 服务器的核是稀缺资源 |
| **内存拷贝** | 内核缓冲区 → 应用缓冲区 | 每秒数十 GB 的梯度收发，拷贝既费时又占内存带宽 |

<Aside type="note" title="经验映射（IDC → AIDC）">
你在有损网络里排障时大概见过这样的现场：业务进程 CPU 飙高、某个核的软中断打满，接口时延立刻抖起来。这不是网络设备的问题，而是**主机协议栈路径**的问题。

关键区别在于：在业务网络里，这类抖动会被大量并发请求和重试机制摊平；在同步训练里，它会被木桶效应放大到全局。同一个现象，两种严重度。
</Aside>

### 为什么这对同步训练是致命的

回忆上一课：上万张卡齐步走，**最慢的 Rank 决定所有人的节奏**。由此产生两个硬约束：

1. **平均快没用，尾延迟才致命**。一次 AllReduce 里可能有上万条并发流，只要千分之一的包慢了，整个集合通信就被拖住。内核协议栈的调度抖动正好批量制造这种尾延迟。
2. **CPU 核要留给计算**。训练机器配高核数 CPU 是为了喂 GPU（数据预处理、dataloader、任务编排），不是为了跑协议栈。每秒几十 GB 的梯度收发若走内核，几十个核全搭进去。

结论：需要一条**时延低且稳、不吃 CPU、不做多余拷贝**的传输路径。这就是 **RDMA**（Remote Direct Memory Access，远程直接内存访问）。

### RDMA 的三大能力

| 维度 | TCP 路径 | RDMA 路径 |
|---|---|---|
| 调用方式 | 系统调用陷入内核 | **内核旁路**：用户态直接操作网卡队列（QP），零系统调用 |
| 数据移动 | 内核缓冲区 ←→ 应用缓冲区拷贝 | **零拷贝**：网卡 DMA 直接读写应用内存，跳过内核缓冲区 |
| 传输层处理 | 由 CPU 执行协议栈 | **CPU 卸载**：可靠传输、乱序处理在网卡硬件里完成 |
| 典型时延 | 几十 µs，抖动大 | 1–2 µs 量级，且稳定 |
| CPU 参与度 | 重 | 仅发起，不搬运 |

编程视角的变化只有一句：应用声明「把这段内存的内容写到对面机器的那段内存」，投递一个 Work Request 进网卡队列，剩下的全交给硬件。CPU 全程是发起者，不是搬运工。

<Aside type="note" title="经验映射（IDC → AIDC）">
一个便于记忆的类比：RDMA 之于 TCP，相当于把「每发一个包都起个子进程、经过三层代理」改成「用户态引擎直接驱动网卡发包」——**把控制路径上的中间层全部砍掉，让数据面直达硬件**。

换个角度：优化序列化格式是在省「每一比特」，RDMA 是在省「每一个包的必经之路」。前者是常数优化，后者是量级优化。
</Aside>

### 代价：RDMA 把「不丢包」变成了硬前提

天下没有免费的午餐。RDMA 拿到微秒级时延的办法，是把中间层全砍掉——其中就包括 TCP 那套精细的丢包恢复机制。

RDMA 的重传是**粗粒度的（类似 Go-Back-N）**：丢一个包，可能要从很早的位置整段重传；而且恢复期间这次内存操作整体挂起。换句话说，丢包的代价不是「补一个包」，而是「打断一次正在进行的传输并重来」。

<Aside type="caution" title="完整因果链（这一课的核心）">
把上一课和本课连起来：

**同步训练要求微秒级稳定时延**（木桶效应）→ 内核协议栈做不到 → **上 RDMA** → RDMA 的丢包恢复代价极大 → **所以网络必须从机制上保证不丢包** → 这就是「无损网络」的由来 → 于是有了 PFC 与 ECN（见 [PFC](../02-lossless/05-pfc/)、[ECN + DCQCN](../02-lossless/06-ecn-dcqcn/)）。

被问到「为什么 AI 网络要无损」时，答案就是这条因果链，而不是一句定义。
</Aside>

## 经验映射

| 你已有的认知 | 在 RDMA 场景下要改成 |
|---|---|
| 「丢包率」是核心日常指标 | 变成**极端事件信号**：日常看 PFC pause、ECN 标记率、队列水线 |
| 服务器慢 → 登录看 CPU / 软中断 | 基本失效：数据面不过 CPU，根因通常在网络设备侧或链路 |
| 抓包分析（tcpdump）是万金油 | RDMA 流量大多是 RoCEv2 UDP 封装，抓包只能看外层，语义要靠设备遥测 |
| 靠重传 + 重试兜底 | 重传代价被同步放大，兜底思路不成立 |

对你的监控体系的直接影响是：**观测重心从主机侧转向设备侧遥测与路径级观测**（见 [gNMI + OpenConfig 遥测](../04-telemetry/11-gnmi/)）。这也是为什么智算网络的可观测工程，大量工作发生在交换机上而不是服务器上。

## 判读与实操

机制课也要有可验证的动作。在一台装了 RDMA 网卡的机器上：

```bash
# 1. 确认设备与端口状态（看到 ACTIVE 才说明链路与协议都起来了）
ibv_devices
ibv_devinfo | grep -E 'hca_id|state|link_layer|active_speed'

# 2. 实测带宽与时延（perftest 包，需两端一起跑）
ib_write_bw -d mlx5_0 --report_gbits    # 服务端先起，客户端指过去
ib_write_lat -d mlx5_0                  # 看小消息时延，典型值 1–3 µs

# 3. 看网卡侧的拥塞与丢包计数（RoCE 场景的关键计数器）
ethtool -S <ifname> | grep -Ei 'pause|ecn|discard|out_of_buffer'
```

判读要点：

- **时延对比**：同样 64B 小消息，`ib_write_lat` 是 1–3 µs 量级；TCP 路径通常是几十 µs。差距不在峰值带宽，而在**时延与其稳定性**。
- **`out_of_buffer` / `discard` 增长**：说明接收侧缓冲不足，是丢包前兆，比端口丢包率更早出现。
- **`pause` 计数上涨**：说明上游在反压，网络已经进入无损机制的工作区间，需要拿到 pause 的**按优先级、按端口**分布才能定位（下一模块的主题）。

## 练习

**必答 Q1**：用你自己的话回答：「AI 训练直接用 TCP 不行吗？TCP 也能跑通。」至少给出两个理由，并说明它们与「同步训练的木桶效应」之间的关系。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

两条主线：

① **时延与抖动**——TCP 本身能跑通，但协议栈路径（中断、软中断、调度、拷贝）带来几十微秒的时延和不可控的尾延迟。同步训练里上万条流并行，最慢的那条决定整个 AllReduce 的完成时间，尾延迟被木桶效应放大成全局停顿。

② **CPU 与内存带宽**——线速收发梯度要走协议栈就要占用大量 CPU 核与内存带宽，而这些资源本该喂 GPU；同时内核↔应用的拷贝在高吞吐下成为瓶颈。

换句话说：TCP 的「能跑通」建立在**异步、可容忍抖动**的假设上；同步训练把这两个假设都推翻了。

**评分维度**

- 明确指出「能跑通 ≠ 能满足同步训练的时延/抖动要求」（必需）
- 说出木桶效应或尾延迟放大机制（必需）
- 提到 CPU / 内存拷贝成本（必要但不充分）
- 只回答「TCP 慢、RDMA 快」而没有解释为何在同步训练中致命（不通过）
</details>

**必答 Q2**：完成因果链并解释：同步训练要求（ ① ）稳定 → 内核协议栈做不到 → 上（ ② ）→ 它的丢包恢复代价大 → 所以网络必须（ ③ ）→ 于是有了 PFC / ECN。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**：① 微秒级低时延（含尾延迟）；② RDMA；③ 从机制上避免丢包（无损）。

解释要点在于**顺序不可颠倒**：不是因为「无损听起来更好」才做无损，而是因为选了 RDMA 这条路径，丢包代价被放大到不可接受，才必须在前端把丢包概率压到极低。理解了顺序，才能理解为什么无损网络的所有机制（PFC、ECN、水线阈值）本质上都是**在丢包发生之前介入**。

**评分维度**：三空全对得基本分；能讲出「顺序/因果关系」得满分；能进一步指出「无损机制是预防而不是恢复」加 1 分。
</details>

**自测 Q3**：RDMA 三大能力分别砍掉了内核路径的哪笔代价？

<details>
<summary>参考答案与评分维度</summary>

**内核旁路**砍掉系统调用与上下文切换（时延抖动的主要来源）；**零拷贝**砍掉内核→应用缓冲区的内存拷贝（时延 + 内存带宽）；**CPU 卸载**砍掉协议栈的 CPU 消耗（把核留给计算）。三者合力把单包时延压到 1–2 µs 且稳定。

**评分维度**：三条各 1 分，能对应到「时延 / 带宽 / CPU」三类资源得满分。
</details>

**自测 Q4**：某训练任务变慢，你还能像以前一样登录机器看 CPU 和软中断来排障吗？为什么？

<details>
<summary>参考答案与评分维度</summary>

基本失效。RDMA 数据面不经过 CPU，主机侧 CPU/软中断指标与传输性能几乎解耦；慢的根因大概率在网络设备侧（队列堆积、PFC pause、ECN 降速、单路径劣化）或对端与中间链路。

所以智算网络的可观测必须建设**设备侧遥测（gNMI 秒级订阅）+ 路径级观测**，并把「按训练任务归因」作为一等公民——这也是后续 M4、M5 的主题。

**评分维度**：答出「主机侧排障失效」得基础分；能给出替代观测手段（设备遥测 / 路径级 / 按任务归因）得满分。
</details>

## 本课要点

<Aside type="tip" title="本课要点">
- 内核路径三笔代价：**时延抖动（尾延迟）、CPU 消耗、内存拷贝**
- 同步训练的木桶效应 → 平均快没用，**尾延迟致命**；CPU 核要留给喂 GPU
- RDMA 三大能力：**内核旁路、零拷贝、CPU 卸载**，时延 1–2 µs 量级且稳定
- 因果链：同步训练 → 微秒级稳定 → RDMA → 丢包恢复代价大 → **必须无损网络** → PFC / ECN
- 可观测语义：数据面不过 CPU，主机侧排障失效，重心转向**设备侧遥测 + 路径级观测**
- 动手验证：`ibv_devinfo` 看状态、`ib_write_lat` 看时延、`ethtool -S` 看 pause / discard 计数
</Aside>
