因果链走到这里已经很清楚了：RDMA 不能丢包 → 以太网默认会丢包 → 必须有个机制兜底。这个机制就是 **PFC**。

学完本课你要能答出三件事：它的原理、它的反压本质、以及它「治丢包但引入新病」的代价。

## 本节目标

- 用一句话说清交换机丢包的**唯一**原因，并解释为什么无损网络不能靠重传补救
- 完整复述一次 PFC 暂停的生命周期（XOFF 水线 → pause 帧 → 上游冻结 → XON 恢复）
- 说出 PFC 的三个关键属性（按优先级、逐跳、接收方驱动）各自解决了什么问题
- 解释队头阻塞（HoL）与拥塞上游化如何让「症状现场 ≠ 根因现场」
- 明白 PFC 的本质是「把丢包问题换成堆积问题」，从而知道观测对象要跟着换

## 机制拆解

### 病因：交换机为什么会丢包

交换机每个出端口有一组队列（通常 8 个，按优先级对应）。报文进交换机 → 查表决定出端口与队列 → 排队 → 出端口按线速发送。

**丢包只有一个原因：出端口的发送速率 < 入队速率，队列涨满，后来的报文只能被丢弃。**

有损网络对此的处理是：扔了就扔，TCP 自己重传。无损网络不能这么办（上一课的因果链），所以思路必须反过来——**在队列涨满之前，别让上游再发了**。这就是 PFC（Priority-based Flow Control，IEEE 802.1Qbb）。

### PFC 的机制：按优先级的逐跳反压

一次 PFC 暂停的完整生命周期：

1. **水线监测**：交换机持续监测某优先级入口队列的水位，涨到 `XOFF` 高水线即触发。
2. **发暂停帧**：向**直连的上游设备**（对端交换机或网卡）发一个 PFC pause 帧，内容很朴素——「优先级 N 的流量，停 `t` 个时间单位」。
3. **上游憋住**：上游设备冻结该优先级的队列，报文在**上游队列里堆着**，不丢。
4. **恢复**：下游水位降到 `XON` 低水线 → 再发一帧「N 恢复」，上游继续发。

三个关键属性，每一个都是抽问点：

| 属性 | 含义 | 解决了什么 |
|---|---|---|
| **按优先级** | 8 个队列独立暂停/恢复 | 只暂停 RoCE 的无损优先级，普通业务不受影响（逻辑隔离） |
| **逐跳（hop-by-hop）** | PFC 只管直连的上一跳，不是端到端 | 让反压能沿链路一级级传，无需全局协调 |
| **接收方驱动** | 「我快满了，你少发」 | 主动权在接收端，不依赖发送端自觉减速 |

<Aside type="note" title="经验映射（IDC → AIDC）">
用分布式系统的话说：**PFC 就是把消息队列的「消费者反压」搬到了交换机的每一条链路上**——下游消费不动，逐级往上游喊停，报文在中间各级的缓冲区（队列）里堆积而不丢弃。

运维过消息队列的人都熟悉这套机制的代价：**反压不会消灭拥堵，只是把「丢包问题」换成了「堆积问题」**。堆积在哪、堆到谁、堆多久——这正是可观测要回答的问题。
</Aside>

### 代价一：暂停会传染，堵住无辜流量

逐跳反压 + 队列共享带来两个「病」：

- **队头阻塞（Head-of-Line Blocking）**：同一优先级队列里混着多条流。流 A 的目的地堵了，暂停波传回来，**同队列中去往健康目的地的流 B 也被一起冻住**——B 明明没去堵的地方，也跟着慢。一个受害者拖累一队人。
- **拥塞上游化（backpressure wave）**：暂停逐跳往源头传，最终把流量堆到**发送端网卡**。于是故障现场出现在离根因很远的地方——「A 收不到数据」的真凶可能是「C 的队列堵了」。

<Aside type="caution" title="无损网络可观测性难度的根源">
**症状现场 ≠ 根因现场。**

你监控到「某条链路时延暴涨」，根因可能在几跳之外、甚至在一个完全不相干的源端口上。只看单点指标永远回答不了「堵在哪、为什么堵」——必须把**拓扑、多跳队列状态、路径级流量**关联起来看。

这也是本项目后面要反复用到的三种视角：设备级（现象）、路径级（流量实际路径）、作业级（哪个训练任务受害）。
</Aside>

### 代价二：PFC 风暴与 PFC 死锁

- **PFC 风暴**：某个下游（一块故障网卡、一个消费不动的进程、某一跳配置错误）持续喊停 → 暂停帧沿链路成片传播 → 大面积链路实际吞吐暴跌。特征：**不丢包、无明显错误计数，但整张网突然集体变慢**。
- **PFC 死锁**：多台设备互相等待对方排空队列，形成**环形依赖**（A 等 B、B 等 C、C 等 A），谁也不放行，暂停状态永久卡死。

死锁的解药是设备上的 **PFC watchdog**：监测到某队列被暂停超时，强制恢复并丢弃该队列积压（或打断等待环路）——**用「允许丢一点」换「不永久死锁」**。这个权衡值得记住：可用性优先于完整性，是分布式系统的通用思路。

这两类故障的详细机理与真实触发场景，是 [07 无损网络四大典型故障](../02-lossless/07-fault-modes/) 的正课。本课只需在机制上想通「为什么会有这两种病」。

## 经验映射

| 你熟悉的机制 | 对应到 PFC |
|---|---|
| 消息队列的消费者反压 | 逐跳 pause 帧 |
| 缓冲区堆积 / 背压传导 | 队列水位上涨与暂停波上传 |
| 单个慢消费者拖累整个分区 | 队头阻塞（同队列无辜流被冻） |
| 分布式锁环路导致的死锁 | PFC 死锁（环形依赖） |
| 超时强制回滚的「熔断」 | PFC watchdog |

一个直接的推论：**你已有的「时延劣化敏感度」在无损网络里是核心技能**。PFC 生效时丢包率几乎不变，但路径时延会剧烈膨胀、抖动飙升——这正是传统 IDC 里最容易被忽略、而在 AIDC 里最值钱的信号。

## 判读与实操

### 要看的指标

| 指标 | 位置 | 判读 |
|---|---|---|
| PFC pause 帧收发计数（按优先级） | 交换机端口 / 网卡 | 是否发生反压、发生在哪个优先级 |
| PFC pause 持续时长 / 累计等待时间 | 交换机（部分平台支持） | 反压强度，比次数更有信息量 |
| 队列水位（瞬时 / 峰值） | 交换机队列 | 是否贴近 XOFF / XON 水线 |
| 出方向丢弃 + 队列丢弃 | 交换机 | 无损队列出现丢弃 = 机制已失效或 watchdog 介入 |
| 端口发送队列的平均/峰值长度 | 交换机 | 队头阻塞的间接信号 |

### 命令示例

```bash
# 主机侧（Mellanox/NVIDIA 网卡）：pause 与丢弃计数
ethtool -S <ifname> | grep -Ei 'pause|prio.*pause|discard|out_of_buffer'

# 主机侧：当前 PFC 配置（哪些优先级开了 pause）
mlnx_qos -i <ifname> --show

# 交换机侧（以通用 CLI 语义示意，实际命令随平台不同）
show priority-flow-control interface <intf>       # PFC 状态与计数
show queue-monitor                              # 队列水线与丢弃
```

判读要点：

- **pause 计数持续增长但端口利用率不高** → 典型反压信号，去查是哪个队列、哪条流在喊停。
- **无损队列出现 discard** → 机制破裂（水线配错、watchdog 触发、上游没响应 pause），这是事故级信号。
- **单个端口的 pause 计数异常高** → 该端口下游消费不动（网卡故障、应用卡住、或对端交换机配置错误），顺着往下游查。

## 练习

**必答 Q1**：用自己的话讲一遍 PFC 的工作原理，必须包含这三个词：**水线、暂停帧、逐跳**。讲完补一句「它的本质是什么机制」，用你在分布式系统里的经验做类比。

<details>
<summary>参考答案与评分维度</summary>

**参考答案（结构示意）**

交换机监测无损优先级的入队水位，涨到 XOFF 水线就向直连上游发 pause 帧，要求「优先级 N 停 t 个时间单位」；上游冻结该优先级队列、报文在自己队列里堆积而不丢弃；下游水位降到 XON 后发恢复帧，流量继续。反压只作用于直连上一跳，靠逐跳传递形成波浪式传播。

本质是**接收方驱动的流控/反压**：与消息队列的消费者反压同构，把「丢弃」换成「堆积」。

**评分维度**

- 三个关键词都说清且因果正确（必需）
- 能说出「按优先级」与「只暂停无损队列」（必需）
- 类比贴切且点出「堆积代替丢弃」（加分）
- 把 PFC 说成端到端机制（扣分，属典型错误）
</details>

**必答 Q2**：PFC 防住了丢包，但它防不住什么？说出至少两个由 PFC 引入的新问题，各用一句话说明成因。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

1. **队头阻塞**——同优先级队列里的流共享队列，一条流的目的地堵住，同队列其他流一起被冻。
2. **拥塞上游化**——逐跳反压把拥堵推向源头，症状现场与根因现场分离，定位难度陡增。
3. **PFC 风暴**——下游持续喊停时暂停帧成片传播，大面积吞吐暴跌，且不体现为丢包。
4. **PFC 死锁**——环形依赖时各方互相等待，暂停状态永久卡死，只能靠 watchdog 强制打断。

**评分维度**：任意两个各 1 分；能说清成因（不是只报名字）得满分；能补出风暴/死锁中任一项加 1 分。
</details>

**自测 Q3**：为什么 PFC 死锁的解药是 watchdog「允许丢一点」，而不是把死锁彻底修好？

<details>
<summary>参考答案与评分维度</summary>

环形依赖一旦形成，靠 PFC 自身机制无法自愈（每一方都在等对方），而全网瞬时阻塞的代价（万卡停摆）远大于牺牲个别队列的流量。工程上因此选择：watchdog 检测队列被暂停超时 → 强制解除（丢弃积压或打断等待）→ 保住网络整体活性。

这是「可用性优先于完整性」的经典权衡——和分布式系统里的超时熔断同构。同时它意味着**「无损」在工程上是一个概率承诺，不是绝对保证**，观测系统必须能识别 watchdog 介入的痕迹。

**评分维度**：说出「自愈不可能 / 代价不对称」（必需）；说出丢的是局部换全局可用（必需）；提到「无损不是绝对保证」加 1 分。
</details>

**自测 Q4**：一条 RoCE 流的接收端应用消费不动，暂停波逐跳上传。此时：① 网络里丢包了吗？② 沿途去往别处的普通业务流量受影响吗？③ 沿途同优先级、去往健康目的地的 RoCE 流受影响吗？

<details>
<summary>参考答案与评分维度</summary>

① 不丢——报文堆在沿途队列里，这正是 PFC 的设计目的。
② 不受（直接）影响——普通业务走有损队列，PFC 按优先级暂停；但共享出端口的带宽可能间接被挤压。
③ **受影响**——同优先级队列共享，队头阻塞把它一起冻住。这是本课 4.3 的核心结论。

**评分维度**：三问全对得满分；第 ③ 问答错说明没理解队头阻塞，建议重读本节。
</details>

## 本课要点

<Aside type="tip" title="本课要点">
- 丢包唯一原因：**出端口队列涨满**。PFC 的思路是「满之前让上游停」——**按优先级、逐跳、接收方驱动**
- 机制四步：**XOFF 水线 → 发 pause 帧 → 上游冻结该优先级队列 → XON 恢复**
- 本质类比：反压机制——**把丢包问题换成堆积问题**，堆积就是新的观测对象
- 两个新病：**队头阻塞**（同队列无辜流被冻）+ **拥塞上游化**（症状现场 ≠ 根因现场）
- 风暴与死锁本课只记结论，[07 课](../02-lossless/07-fault-modes/) 展开；watchdog 用「允许丢一点」换「不永久死锁」
- 判读主指标：**PFC pause 计数与时长、队列水位、无损队列的 discard**
</Aside>
