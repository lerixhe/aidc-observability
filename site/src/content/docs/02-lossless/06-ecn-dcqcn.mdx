上一课的 PFC 是「快满了才喊停」。它的触发条件是队列涨到 XOFF 高水线——**那时候队列已经快满了**，代价很大（冻结整个优先级队列、可能传染、可能死锁）。

更好的策略是：拥塞**早期**就通知源端「你发太快了，请降速」，让队列根本涨不到 XOFF。这需要两个能力：

1. 交换机能告诉网络「这里开始堵了」——**ECN**
2. 源端网卡收到通知后能主动降速——**DCQCN**

## 本节目标

- 说清 ECN 的两位标记与交换机的三段水线（Kmin / Kmax）策略
- 完整画出 DCQCN 闭环，并指出 CP / NP / RP 三个角色分别落在哪台设备上
- 解释「PFC 是最后防线、ECN/DCQCN 是主防线」的分工，以及健康网络里 PFC 为什么应该是罕见事件
- 建立三级指标分级：ECN 标记率（领先）→ PFC pause（滞后）→ 丢包（事故确认）
- 与 TCP 拥塞控制对照，说清「信号来源」与「决策位置」的两处根本差别

## 机制拆解

### 为什么 PFC 不够，要再补一层

拿急诊打比方：PFC 是「病危抢救」，代价大；那「日常体检」是什么？

答案是在拥塞早期就通知源端降速，让队列涨不到 XOFF。这需要两个能力：**交换机侧的显式标记（ECN）** 与 **网卡侧的闭环降速（DCQCN）**。两者合起来才是 RoCEv2 完整的拥塞控制。

### ECN：在报文里带一张「此处轻微拥堵」的便签

**ECN（Explicit Congestion Notification）** 是 IP 头里的两个 bit：

| 阶段 | 谁做 | 做什么 |
|---|---|---|
| 发送 | 源端网卡 | 给报文打 `ECT` 标记：「我能理解拥塞通知」 |
| 标记 | 交换机 | 队列低于 `Kmin` 不管；在 `Kmin~Kmax` 之间**按概率打 `CE` 标记**；超过 `Kmax` 通常全标（或交给 PFC） |
| 传递 | 网络 | CE 标记**随报文到达接收端**——便签是写给收件人的 |
| 反馈 | 接收端网卡 | 见到 CE 就回 `CNP` 通知包给源端 |

对比有损网络：TCP 的拥塞信号是**丢包**（隐式、事后、粗暴）；无损网络的拥塞信号是**CE 标记**（显式、事前、温和）。

这是「有损 → 无损」范式转换的又一处语义翻转：**拥塞从「已经发生的事故」变成「正在发生的、可观测的状态」**。

<Aside type="note" title="为什么标记打在报文上，而不是发给源端">
因为交换机不知道（也不该关心）某条 RDMA 流对应哪台源主机——它只做逐包处理，代价最低。让接收端把信号折叠成 CNP 回到源端，是「谁最清楚谁反馈」的分工：接收端知道是哪个 QP 收到了 CE，交换机不知道。

这个设计还有个副产品：反馈路径与数据路径解耦，CNP 是独立的控制报文，可以自己带优先级。
</Aside>

### DCQCN：收到便签之后，谁降速、怎么降

ECN 只负责标记，降速动作由 **DCQCN**（Data Center Quantized Congestion Notification）完成。闭环里有三个角色：

| 角色 | 名称 | 落在哪 | 做什么 |
|---|---|---|---|
| **CP** | Congestion Point | 交换机 | 监测队列水位，按概率打 CE 标记 |
| **NP** | Notification Point | 接收端网卡 | 收到 CE 报文 → 按控制频率回 `CNP` 给源端 |
| **RP** | Reaction Point | 发送端网卡 | 收到 CNP → 按比例降速；一段时间没再收到 → 定时器驱动逐步恢复 |

完整闭环（可以照着画）：

```text
① 交换机队列涨过 Kmin        → 给过路报文打 CE 标记
② 接收端网卡解到 CE          → 回 CNP 给源端
③ 源端网卡按 CNP 密度降速    → 拥塞源头的流量被压回去
④ 队列水位回落               → 不再打标 → 源端定时器驱动逐步升速
```

定位一句话：**DCQCN 是主防线（主动降速，治未病），PFC 是最后防线（物理暂停，保命）。**

一个调优良好的无损网络里，PFC pause 应该是**罕见事件**。如果 PFC 频繁触发，说明 DCQCN 参数（Kmin/Kmax、降速斜率、CNP 生成频率、恢复定时器）没调好，或者存在异常流量。

### 和 TCP 拥塞控制对照着记

| 维度 | TCP 拥塞控制 | DCQCN |
|---|---|---|
| 信号 | **丢包**（或时延），隐式猜测 | **ECN 标记**，显式告知 |
| 决策者 | 内核协议栈（软件，慢，吃 CPU） | 网卡硬件（不耗 CPU，微秒级反应） |
| 动作 | 降 cwnd，靠重传兜底 | 降速 + 定时恢复，PFC 只兜底 |
| 粒度 | 每条连接独立感知 | 端网协同，交换机深度参与 |

这套端网协同有个隐含要求：**交换机与网卡的参数要配套调优**。Kmin/Kmax、PFC 水线、CNP 频率、降速系数是联动的，任何一个不匹配都会让闭环失效——这也是「批量、一致地改全网设备参数」成为刚需的原因，管控面（Netconf / gNMI 下发）从运维便利变成了正确性的一部分。

## 经验映射

| 你熟悉的概念 | 在无损网络里的对应 |
|---|---|
| 领先指标 vs 滞后指标 | **ECN 标记率 = 领先**，PFC pause = 滞后，丢包 = 确认 |
| 阈值告警 | 从这里开始要改成「分级 + 传导关系」分析，不再是单点阈值 |
| 实时流处理（Kafka → Flink → 时序库） | 完全复用：这些计数器就是普通时序流 |
| 主动探测（自产自收） | 换成**设备被动上报**（gNMI 订阅），采集模型不同 |
| 路径维度的观测 | 设备计数器是单点维度，需要与拓扑、路径数据关联才能定位 |

一句话总结：**领域语义变了，管道还是你那套。**你已有的实时链路可以把 ECN / PFC 计数器当成普通时序流处理；真正的增量工作在「数据源的采集方式」与「跨维度关联分析」两处。

## 判读与实操

### 三级健康指标（本课最重要的产出）

| 层级 | 指标 | 含义 | 处置 |
|---|---|---|---|
| 领先 | **ECN 标记率**（按端口/优先级/队列） | 拥塞正在形成，已被 DCQCN 接管 | 观察趋势；持续升高说明流量模型或参数需要调整 |
| 滞后 | **PFC pause 次数与时长** | DCQCN 没兜住，已经在反压 | 告警 + 定位到端口/队列/流 |
| 事故 | **无损队列丢包 / discard** | 机制失效（配置错误、死锁、硬件故障） | 最高优先级，立即定位 |

排障价值在于**传导关系**：ECN 涨 → PFC 涨 → 丢包，说明拥塞在恶化；ECN 不高但 PFC 频繁，说明参数失衡或存在微突发；PFC 不高却丢包，说明某跳配置错误（比如无损队列没开 PFC）。**比单看任何一个数字都更能定位问题层级。**

### 命令与指标位置

```bash
# 主机侧：ECN 标记与 CNP 相关计数（NVIDIA/Mellanox 命名示意）
ethtool -S <ifname> | grep -Ei 'ecn|cnp|np_cnp|rp_cnp'

# 交换机侧：队列 ECN 标记计数与阈值配置
show interface <intf> counters queue            # 每队列的标记/丢弃计数
show qos queue ecn                              # Kmin/Kmax 与标记概率
```

判读要点：

- **ECN 标记率有值但 PFC 几乎为 0** → 闭环工作正常，这是健康状态。
- **ECN 不高、PFC 很高** → DCQCN 参数（Kmin 过高 / 降速不足）或流量微突发超出标记能力，需要看队列水线。
- **ECN 与 PFC 都不高、却有丢包** → 优先怀疑配置不一致（某跳无损队列没开 PFC）或链路硬件问题。

## 练习

**必答 Q1**：「既然 PFC 能保证不丢包，为什么还要 ECN / DCQCN？」——用一句话点破设计哲学，再展开两三点。

<details>
<summary>参考答案与评分维度</summary>

**一句话**：PFC 是事后抢救，代价大；ECN/DCQCN 是事前预防，尽量不让网络走到需要抢救的地步。

展开：

① **代价不对称**——PFC 一触发就冻结整个优先级队列，带来队头阻塞、暂停传播，甚至风暴/死锁；ECN 只改两个 bit，几乎零成本。
② **信号更早**——Kmin 到 Kmax 之间的标记发生在队列远未填满时，源端有充足时间降速。
③ **可观测性更好**——ECN 标记率是一个连续、可量化的「拥塞热度」指标；PFC 计数只有「发生/未发生」，信息量低。
④ **闭环可控**——DCQCN 的降速是概率化、渐进的，能避免吞吐剧烈震荡。

**评分维度**：一句话点破「预防 vs 抢救」（必需）；展开 ≥2 点且涉及代价或信号时机（必需）；提到「ECN 标记率是更好的可观测指标」（加分）。
</details>

**必答 Q2**：写出 DCQCN 闭环（交换机打标 → … → 源端升速），并指出三个角色各自在哪台设备上。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

① 交换机（CP）队列涨过 Kmin，按概率给报文打 CE；
② 接收端网卡（NP）解到 CE，回 CNP 给源端；
③ 发送端网卡（RP）收到 CNP，按密度降速；
④ 队列水位回落，交换机不再打标；
⑤ 源端一段时间没收到 CNP，定时器驱动逐步升速。

**评分维度**

- 五步顺序正确（必需）
- CP/NP/RP 与设备对应正确（必需，最容易错的是把 NP 说成源端）
- 能补上「CNP 生成有控制频率，避免反馈风暴」（加分）
</details>

**自测 Q3**：无损网络的三层健康指标分级是什么？各自含义与处置？

<details>
<summary>参考答案与评分维度</summary>

**ECN 标记率**——领先指标，拥塞正在形成但已被 DCQCN 接管，轻微时属于正常运行的一部分；
**PFC pause 次数/时长**——滞后指标，说明 DCQCN 没兜住或参数失衡，需要告警排查；
**丢包 / 无损队列 discard**——事故确认，机制本身失效（配置错误、死锁、硬件故障），最高优先级。

排障价值在看 **ECN → PFC → 丢包的传导关系**，比单看任何一个数都更能定位问题层级。

**评分维度**：三层齐全且顺序（领先/滞后/确认）正确得基本分；能说出传导关系的判读价值得满分。
</details>

**自测 Q4**：把 ECN / PFC 指标接入你已有的数据管道，和接入「主动探测质量数据」相比，最大的两个不同是什么？

<details>
<summary>参考答案与评分维度</summary>

① **数据来源不同**：探测数据是自产自收（主动发、自己收），这些计数器是**设备被动上报**——采集要走 gNMI 订阅或 SNMP 轮询（秒级事件用 SNMP 分钟级会漏，见 [11 gNMI 遥测](../04-telemetry/11-gnmi/)）。

② **数据维度不同**：探测数据天然带「路径」维度（五元组/ECMP 路径），设备计数器是**单点维度**。要回答「谁堵了、堵住了谁」，必须把设备计数器 × 拓扑 × 路径数据做关联分析——这正是图计算与路径覆盖能力结合的地方（见 [16 AIOps](../05-analysis/16-aiops/)）。

**评分维度**：两点各 1 分；能指出「关联分析是新增工作量」而不是「管道直接复用就完事」得满分。
</details>

## 本课要点

<Aside type="tip" title="本课要点">
- 设计哲学：**PFC 是最后防线（抢救），ECN / DCQCN 是主防线（治未病）**；健康网络里 PFC 应是罕见事件
- ECN：IP 头 2 bit；交换机在 **Kmin~Kmax** 之间按概率打 **CE**；拥塞从「事故」变成「可观测状态」
- DCQCN 三角色：**CP 交换机打标 · NP 接收端回 CNP · RP 源端网卡降速 / 定时恢复**
- 指标三级：**ECN 标记率（领先）→ PFC pause（滞后）→ 丢包（事故确认）**，看传导关系而非单点
- 对比 TCP：信号从丢包变标记，决策从内核变**网卡硬件**；参数要端网配套 → 管控面是正确性的一部分
</Aside>
