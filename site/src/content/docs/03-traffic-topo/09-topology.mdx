## 机制拆解

### Clos / Fat-Tree：用“无收拢”换规模

万卡集群的底层骨架是 **Clos 架构**（以太网语境常叫 Fat-Tree）。两层或三层交换机，**Leaf（接入）全互联到 Spine（核心）**，并且**上联总带宽 = 下联总带宽（1:1 无收拢）**。

```text
        +---------+   +---------+   +---------+   +---------+
        | Spine A |   | Spine B |   | Spine C |   | Spine D |
        +----+----+   +----+----+   +----+----+   +----+----+
             |             |             |             |
      +------+------+------+------+------+------+------+------+
      |             |             |             |             |
  +---+---+     +---+---+     +---+---+     +---+---+     +---+---+
  | Leaf1 |     | Leaf2 |     | Leaf3 |     | Leaf4 |     | Leaf5 |
  +---+---+     +---+---+     +---+---+     +---+---+     +---+---+
      |             |             |             |             |
   GPU 组1       GPU 组2       GPU 组3       GPU 组4       GPU 组5
```

这个形状的承诺：**任何两组服务器互访都能吃满线速**（full bisection bandwidth）。任意两个节点之间都有**大量等价路径（ECMP）**。

代价同样明确：交换机与光模块数量巨大、布线复杂、成本高。本质是**用硬件堆料换带宽与时延的确定性**。1:1 无收拢相当于给每条路径预留了专用车道，不用抢。训练流量是持续性大象流，任何收拢比都意味着跨组通信排队。集合通信又是同步的，一次排队就是全员变慢。

<Aside type="note" title="经验映射（IDC → AIDC）">
老朋友又出现了：**ECMP**。传统 IDC 里，两台服务器之间的流量被哈希散到若干条等价路径上。万卡 Clos 里路径数指数级增长，“如何选点、如何防 hash 极化”直接变成核心工程问题。

与传统 DC 的差别在量级与后果。传统 DC 覆盖 90% 链路已经很强。智算场景里，未覆盖的那 10% 恰好可能承载某个 AllReduce 环的关键一段，一次劣化就是一次全局停顿。
</Aside>

### 一台 GPU 服务器的网络面貌：多网卡多 Rail

传统业务服务器一两块网卡就够。GPU 服务器不同：**8 张 GPU 通常各配一块独立网卡**（200G/400G），每块网卡属于一个 **Rail（轨道）**。

```text
Rail 0 交换机  --  所有服务器的 网卡0 (GPU0)
Rail 1 交换机  --  所有服务器的 网卡1 (GPU1)
Rail 2 交换机  --  所有服务器的 网卡2 (GPU2)
...                                 共 8 条轨道
```

- **Rail N** = 所有服务器第 N 块网卡所在的那个接入交换机组。它相当于把“第 N 块网卡”打成一条专用通道，同号卡走同一条道。
- **rail-aligned（轨道对齐）**：服务器 A 的 GPU0 主要与服务器 B 的 GPU0 通信，同 Rail 内交换，**不出轨道**。

```text
轨道对齐：  A.GPU0 <--> B.GPU0     全程在 Rail 0 内，不跨轨道   ✅
轨道错位：  A.GPU0 <--> B.GPU5     必须跨轨道抢共享带宽        ❌
```

把上一课接上：**NCCL 拓扑感知的环排序，就是让通信环顺着 rail 走**。RDMA 流量 rail 对齐后，大部分流量在 Rail 内完成，跨轨道（经 Spine）的流量被压到最少。

这就是“轨道”存在的意义：**用拓扑结构去迎合软件的通信模式**。

### 双 ToR 双平面：为“训练不能停”设计的冗余

第一课讲过：网络抖一下 = 全体训练停摆。所以接入层做了激进冗余，典型设计有三层：

| 设计 | 防什么 | 故障时状态 |
|---|---|---|
| **双 ToR** | 单台接入交换机故障或升级 | 流量走另一台，训练**不中断** |
| **双平面** | 整个交换平面故障 | 损失部分带宽，**降速运行** |
| **计算 / 存储 / 带外三网物理隔离** | checkpoint 与训练抢带宽、管理面被业务打爆 | 各自独立，互不影响 |

<Aside type="note" title="经验映射（IDC → AIDC）">
“降速运行好过全体回退”这个哲学，做稳定性的人都熟：降级、限流、灰度，本质都是**保住整体活性、牺牲局部性能**。

AIDC 的双平面就是同一哲学在网络物理层的表达。你已有稳定性思想，缺的是把已有思想映射到新拓扑上的词汇。
</Aside>

### 拓扑对监控意味着什么

拓扑不只是画在 PPT 上的图，它**必须成为监控数据模型里的实体**。四个直接后果：

1. **故障定位的第一问变了**。从“哪台设备坏了”升级为“哪条 Rail、哪个平面、哪个环段”。拓扑必须作为一等公民入库，用图结构存，这是后面图计算的基础。
2. **冗余切换本身是观测事件**。双 ToR 切换、路径重哈希会让流量突然换路。路径级探测能立刻发现“路径集合变了”。设备级监控对此毫无察觉。
3. **“预期 vs 实际”落到拓扑**：上一课说流量矩阵已知，加上拓扑就能写成具体断言。比如“任务 X 的环经过 Rail 0/3/5，Rail 3 的链路利用率应接近线速”。断言可以持续自动核对。
4. **探测部署策略随之改变**。路径覆盖应按 Rail / 平面分层设计，每条 Rail 独立覆盖、跨平面路径重点覆盖，而不是全网均匀撒点。

<Aside type="caution" title="这条结论值得单独记">
在传统 IDC 里，拓扑是排障时**查一下**的资料。在智算网络里，拓扑是**数据模型的一部分**，相当于数据表里的外键。没有拓扑，你只有一堆孤立的端口计数器，无法回答“谁堵了谁”“哪条环受影响”。
</Aside>

## 经验映射

| 传统 IDC 的拓扑认知 | 智算网络里必须补充的维度 |
|---|---|
| 二层/三层、VLAN、ECMP | **Rail 编号、平面归属、超节点边界** |
| 设备级可用性（up/down） | **路径集合是否变化**（切换本身是事件） |
| 无收拢不常见（多为收拢设计） | 1:1 无收拢是默认前提 |
| 计算/存储可共用网络 | **三网物理隔离**是硬要求 |
| 拓扑用于变更管理 | 拓扑用于**实时关联与自动核对** |

## 判读与实操

### 摸清拓扑的三条命令

```bash
# 主机侧：GPU-NIC 的物理亲和（判断某张卡走哪块网卡、哪条 Rail）
nvidia-smi topo -m

# 主机侧：网卡的 NUMA/PCIe 位置与速率，核对是否按设计上联
lspci -tv | grep -i eth
ethtool <ifname> | grep -E 'Speed|Link detected'

# 网络侧：BGP/LLDP 邻居关系（拓扑自动发现的两种来源）
show lldp neighbors
show ip bgp summary
```

### 按 Rail 维度组织观测

| 观测对象 | 说明 |
|---|---|
| 每条 Rail 的链路利用率分布 | 是否均匀；某条 Rail 显著偏低或偏高都异常 |
| 每条 Rail 的 pause / ECN / discard | 定位到“哪条轨道在反压” |
| 跨轨道（经 Spine）流量占比 | 应尽量低；升高说明环排序与拓扑错位 |
| 双 ToR 主备流量分配 | 是否按设计分流；切换后是否恢复 |
| 平面间流量对称性 | 单平面劣化的早期信号 |

判读要点：**同一个故障，在 Rail 维度上通常表现为“成组出现”**。某条 Rail 的多条路径同时劣化，几乎可以确定问题在该 Rail 或它的上联，而不是在若干互不相关的服务器上。

## 练习

**必答 Q1**：讲清“rail-optimized”。什么是 Rail？rail-aligned 的流量长什么样？它和 NCCL 环排序是什么关系？

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

Rail 是“同编号网卡的集合”：每台 GPU 服务器的第 N 块网卡都上联到同一组接入交换机，构成第 N 条轨道。rail-aligned 指的是通信双方走**同编号 GPU/网卡**，流量在单条轨道内闭合，不经 Spine。NCCL 的拓扑感知环排序会把环尽量排成同 rail 序列，从而让集合通信流量对齐轨道、避免跨轨道争抢共享上联。

**评分维度**：Rail 定义正确（必需）。rail-aligned 形态正确（必需）。指出“拓扑迎合通信模式”的目的（必需）。能说出错位的后果（带宽争抢/绕行）（加分）。
</details>

**必答 Q2**：“双 ToR + 双平面”分别防什么故障？防住之后集群处于什么状态（全速/降速）？为什么说“降速运行好过全体回退”？

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

双 ToR 防单台接入交换机故障或升级维护：流量切到另一台，训练不中断、基本全速。双平面防整个交换平面故障：损失部分带宽，集群降速运行但训练继续推进。

“降速好过回退”的原因：一次 checkpoint 回退的代价是“回退时间 × 万卡算力”，几分钟到几十分钟。短暂降速只是同一段时间内的算力利用率下降，量级远小。所以工程上宁可牺牲带宽，也不触发回退。

**评分维度**：两个机制的防护对象区分清楚（必需）。状态（不中断 vs 降速）正确（必需）。代价对比给出量级（必需）。能补充“双平面也会降低冗余度、需尽快修复”（加分）。
</details>

**自测 Q3**：Clos 为什么要做成 1:1 无收拢？如果不做代价是什么？

<details>
<summary>参考答案与评分维度</summary>

训练流量是持续性大象流而非偶发突发，任何收拢比都意味着跨组通信排队。集合通信是同步的，一次排队就变成全员变慢。

代价：交换机、光模块、布线数量大幅增加，成本与运维复杂度上升。这是“堆料换确定性”：用硬件冗余买时延与带宽的确定性。

**评分维度**：说出“大象流 + 同步”是根因（必需）。说出成本代价（必需）。
</details>

**自测 Q4**：某条 Rail 的一台接入交换机整体故障，路径级探测与监控平台分别会看到什么？

<details>
<summary>参考答案与评分维度</summary>

探测：覆盖该 Rail 的路径成组断崖或劣化。由于双 ToR / 冗余路径，部分路径在切换后自动恢复，呈现“成组故障 + 成组自愈”的指纹。

设备侧：该交换机失联（LLDP/BGP 邻居消失），流量在备用路径上重哈希，其他 Rail 与上联的利用率出现跳变。

监控平台的价值：把“Rail R 交换机 down”翻译成“任务 X 的环段受影响”，并评估是否会触发 checkpoint 回退。这才是任务为中心的表达。

**评分维度**：说出“成组”特征（必需）。说出切换导致的路径集合变化（必需）。能翻译成任务影响（加分）。
</details>

## 本课要点

<Aside type="tip" title="本课要点">
- Clos / Fat-Tree：**1:1 无收拢**换全等分带宽，本质是堆料换确定性。ECMP 无处不在，是路径覆盖的主战场
- GPU 服务器 **8 卡 8 网卡 8 条 Rail**。rail-aligned = 同轨道内通信不出轨，NCCL 环排序顺着 rail 走
- 冗余三件套：**双 ToR**（防单台故障）· **双平面**（防整平面，降速好过回退）· **三网物理隔离**
- 监控新增一等维度：**Rail / 平面 / 环段**。冗余切换与路径重哈希本身就是观测事件
- 探测部署按 Rail 分层覆盖，不做全网均匀撒点
</Aside>
