前面反复说到一句话：“探测看得到路径，看不到队列，要补设备遥测”。本课讲设备遥测怎么拿。

这也是 M4“遥测数据面”的第一课，它是后面 INT、光模块、数据管道三课的地基。

## 本节目标

- 说出 SNMP 轮询撑不住智算网络的三个结构性原因，而不只是“粒度不够”
- 区分 gNMI 的四个 RPC，尤其是 `Subscribe` 的三种模式及其各自适用的数据
- 理解 YANG / OpenConfig 的作用：把“队列 0 的 pause 计数”表达成厂商中立的结构化路径
- 能设计一套分级订阅策略（什么指标、什么频率、什么模式），并说明数据量权衡
- 知道时钟对齐为什么是跨设备关联分析的前提

## 机制拆解

### SNMP 为什么撑不住智算网络

传统数据中心里这套很常见：网管系统按分钟级定时发 `SNMP GET`，设备回 OID 计数器。三个结构性问题：

| 问题 | 具体表现 | 后果 |
|---|---|---|
| **拉模式 + 分钟级** | 数据靠轮询产生，采样越密、网管压力越大 | PFC 风暴、incast 尖刺是秒级/亚秒级事件，分钟轮询看到的只有“平均值永远正常” |
| **OID 平铺无结构** | MIB 是一堆数字编号，语义弱、厂商扩展混乱 | 难以表达“某端口某优先级队列的 pause 计数”这种多维结构 |
| **响应式思维** | 设备明明知道自己的队列在涨，却只能等人来问 | 信息在源头，权力在采集端，天然滞后 |

### gNMI：把订阅思想搬进交换机

**gNMI**（gRPC Network Management Interface）= 基于 gRPC 的网络设备接口。四个核心 RPC：

| RPC | 作用 |
|---|---|
| `Capabilities` | 设备支持哪些模型与编码（握手时问一句“你会什么”） |
| `Get` | 读取状态/配置 |
| `Set` | 写入配置——**管控面的入口**（批量、一致地下发参数） |
| **`Subscribe`** | 流式遥测，设备**主动持续推送**，而不是等人来拉 |

`Subscribe` 有三种模式，是抽问点：

| 模式 | 行为 | 适用数据 |
|---|---|---|
| `SAMPLE` | 按 `sample_interval`（可到秒/亚秒）周期推送 | 计数器、队列水位等连续量 |
| `ON_CHANGE` | 值变了才推 | 端口 up/down、邻居变化、告警状态 |
| `POLL` | 订阅建立后由采集端按需触发 | 排障时临时拉一把 |

<Aside type="note" title="经验映射（IDC → AIDC）">
这套东西对后端/基础设施背景的读者几乎没有学习成本：**gNMI = gRPC + Protobuf**。`Subscribe` 就是 server streaming；数据模型用 YANG 定义、Protobuf 编码，就是设计 RPC 协议的那套手艺。

“设备协议栈”换了一门语法，但底层仍是你熟悉的长连接、序列化、流控与重连管理。真正的缺口只有一个：**在一台真实（或模拟）交换机上把它跑通**。
</Aside>

### OpenConfig：让“队列 0 的 pause 计数”全世界说同一种话

gNMI 只定义**怎么传**，**传什么**由数据模型定义。行业主流是 **OpenConfig**，即 Google 主导的厂商中立 YANG 模型集。订阅时按路径指定：

```text
/interfaces/interface[name=eth0]/state/counters/in-octets
/interfaces/interface[name=eth0]/state/counters/out-errors
/qos/interfaces/interface[id=eth0]/output/queues/queue[name=3]/state/...
/network-instances/network-instance[name=default]/afts/...   # 转发表/邻居，拓扑发现用
```

三个关键点：

- **结构化多维**：接口 × 队列 × 优先级 × 方向，天然带标签，正是时序库需要的维度设计。
- **厂商中立**：白盒交换机（SONiC）与商用设备混部时，同一套模型采集，这才是“商用/白盒混管”的前提。
- **你要的关键指标就在这棵树上**：端口 CRC / 丢包计数、队列深度、PFC pause 收发（按优先级）、ECN 标记计数（部分在厂商扩展里）。上一模块定位根因要的那三类数据，全靠订阅这棵树。

<Aside type="caution" title="厂商扩展的现实">
OpenConfig 覆盖不了所有厂商特性：PFC pause 的按优先级细分、队列水线直方图、INT 相关计数，常落在厂商私有模型里（例如以 `openconfig-*` 之外的私有 path 提供）。

工程上要做两件事：① **建立模型映射层**（内部统一指标名 → 各厂商 path），避免上层被厂商绑定；② **Capabilities 探测**，采集器启动时按设备能力决定订阅哪些 path。这两点是“多厂商混部”的真实工作量所在。
</Aside>

### 对照表

| 维度 | SNMP | gNMI + OpenConfig |
|---|---|---|
| 方向 | 拉（轮询） | **推（订阅流）** |
| 粒度 | 分钟级 | **秒 / 亚秒级** |
| 模型 | MIB / OID 平铺 | **YANG 结构化树** |
| 传输与编码 | UDP + ASN.1/BER | **gRPC(TLS) + Protobuf** |
| 连接 | 一问一答 | 长连接多路复用，断线自动重订阅 |
| 配置下发 | 弱（SET 语义粗糙） | **强（Set + 事务性语义）** |

## 经验映射

| 你已有的组件/技能 | 在采集链路里的位置 |
|---|---|
| gRPC / Protobuf 服务开发 | gNMI 客户端与模型映射层 |
| 长连接管理、断线重连、背压 | 采集器的订阅管理（这正是 gnmic 的核心） |
| Kafka / Flink / ClickHouse | 数据管道与存储，完全复用 |
| 时序维度设计 | 接口 × 队列 × 优先级 × Rail 的标签体系 |
| 探测频率与开销的权衡 | 采样频率 × 设备数 × 路径数的数据量权衡 |

整条采集链路里没有陌生组件：**交换机(gNMI) → 采集器集群 → Kafka → Flink → ClickHouse → Grafana**。你需要的增量知识是设备侧的模型与语义，不是管道技术。

## 判读与实操

### 用一个命令跑通订阅（gnmic）

```bash
# 1. 握手：看设备支持哪些模型与编码
gnmic -a <device>:57400 -u <user> -p <pass> --insecure capabilities

# 2. 取值：先用 Get 确认路径存在
gnmic -a <device>:57400 -u <user> -p <pass> --insecure get \
  --path '/interfaces/interface[name=eth1]/state/counters'

# 3. 订阅：SAMPLE 模式，每 5 秒推一次队列计数
gnmic -a <device>:57400 -u <user> -p <pass> --insecure subscribe \
  --path '/interfaces/interface[name=eth1]/state/counters/in-octets' \
  --mode stream --stream-mode sample --sample-interval 5s
```

### 分级订阅策略（一课的实际产出）

| 数据类别 | 典型频率 | 模式 | 理由 |
|---|---|---|---|
| 队列水线、PFC pause、ECN 标记 | 1–5 s | SAMPLE | 秒级事件；是根因定位的核心数据 |
| 端口计数（octets、discards、CRC） | 10–30 s | SAMPLE | 趋势分析够用，量级大 |
| 端口 up/down、邻居、告警状态 | — | ON_CHANGE | 离散事件，等待变化即可 |
| 转发表/拓扑相关 | 分钟级或变更触发 | POLL / ON_CHANGE | 变化不频繁 |
| 排障临时深挖 | 手动 | POLL | 按需 |

### 两个必须提的工程细节

1. **数据量爆炸**：采样频率 × 设备数 × 路径数。一万台设备 × 每台 500 条路径 × 1 秒 = 500 万点/秒，在没有降采样的情况下存储与查询都会崩。分级订阅属于可行性前提，并非可选优化。
2. **时钟对齐**：跨设备关联分析（谁先 pause、谁后堆积）的前提是 NTP / PTP 校时。时钟漂移会把因果链变成乱序拼图，**看起来有结论，实际是错的**。

## 练习

**必答 Q1**：“SNMP 也能采到 pause 计数，为什么要上 gNMI？”从**方向、粒度、模型**三个角度回答，各用一句话点破本质。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

- **方向**：SNMP 是拉，事件发生后要等下一个轮询周期；gNMI 是推，设备在变化发生时就推送，本质差别是“信息在源头”还是“信息在采集端”。
- **粒度**：分钟级轮询会系统性漏掉秒级/亚秒级事件（PFC 风暴、incast 尖刺），且对“平均值永远正常”无能为力。
- **模型**：OID 平铺无法表达“某端口某优先级队列”这种多维结构；YANG 树天然带标签与层级，直接对上时序维度模型。

**评分维度**：三个角度都点到本质（必需）；能补出“Set / 管控面”与“厂商中立混管”（加分）；只回答“gNMI 更现代/更快”（不通过）。
</details>

**必答 Q2**：给一万台交换机做遥测采集，不能所有指标都 1 秒订阅。设计一套分级订阅策略并说明理由。

<details>
<summary>参考答案与评分维度</summary>

**参考答案（要点）**

按“事件时标 × 数据量 × 定位价值”三维分级：

1. **秒级 SAMPLE**：队列水线、PFC pause（按优先级）、ECN 标记计数。它们是根因定位的核心，且维度数相对可控（端口 × 队列）。
2. **10–30 s SAMPLE**：端口 octets、discards、CRC，用于趋势与容量分析，量级最大。
3. **ON_CHANGE**：端口/邻居/告警状态。离散事件，无需周期采样。
4. **POLL / 变更触发**：拓扑与转发表类数据。

再叠加两个工程手段：**采集侧预聚合**（在 Flink 里做降采样与峰值保留，存“1s 峰值 + 1min 均值”两档），以及**按需提升频率**（排障时对特定端口临时升到亚秒级）。

**评分维度**：分级明确且理由与事件时标挂钩（必需）；提到数据量估算或降采样策略（必需）；提到临时提频/按需深挖（加分）。
</details>

**自测 Q3**：`Subscribe` 三种模式分别用在什么数据上？选错的后果是什么？

<details>
<summary>参考答案与评分维度</summary>

`SAMPLE` 用于连续计数器与队列水线；`ON_CHANGE` 用于离散状态（端口 up/down、邻居）；`POLL` 用于排障时临时拉取。

选错的后果：计数器用 `ON_CHANGE` → 只推变化，丢失平稳水位基线，趋势分析没数据；状态用 `SAMPLE` → 浪费带宽且可能错过变化瞬间；全部用 `POLL` → 退化回 SNMP 老路。

**评分维度**：三种模式与数据对应正确（必需）；说出至少一种选错的后果（必需）。
</details>

**自测 Q4**：为什么“多设备时钟对齐”是跨设备根因关联分析的前提？不做会怎样？

<details>
<summary>参考答案与评分维度</summary>

跨设备关联的本质是**时间相关性**：A 设备 pause 上涨 → B 设备队列堆积 → C 路径时延膨胀，靠时间戳排序还原传导链。

若设备间时钟差达秒级，事件顺序完全错乱，“上游 / 下游”无法判定，关联分析会输出看似有理其实错误的结论，比没有结论更危险。所以需要 NTP 严格对齐（要求更高的场景用 PTP），并在存储时保留采集端统一打点时间作为交叉校验。

**评分维度**：说出“时间相关性 = 关联分析的基础”（必需）；说出错误结论比无结论更危险（加分）；提到采集端统一打点/NTP/PTP（加分）。
</details>

## 本课要点

<Aside type="tip" title="本课要点">
- SNMP 三宗罪：**拉模式分钟级、OID 平铺、等人来问**，秒级事件系统性漏采
- gNMI = gRPC + Protobuf：`Capabilities` / `Get` / `Set` / **`Subscribe`**；三模式 **SAMPLE（连续）/ ON_CHANGE（状态）/ POLL（排障）**
- OpenConfig = 厂商中立 YANG 模型树，结构化多维（接口 × 队列 × 优先级），白盒与商用混管的前提
- 采集链路：**设备 → gnmic → Kafka → Flink → ClickHouse → Grafana**，与现有数据管道完全同构
- 工程两细节：**分级订阅**（频率 × 设备数 × 路径数的权衡）+ **时钟对齐**（关联分析的前提）
- 厂商扩展要建**模型映射层 + Capabilities 探测**，否则被单一厂商绑定
</Aside>
