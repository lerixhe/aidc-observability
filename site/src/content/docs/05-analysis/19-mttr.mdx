MTTR 常被当成一个数字贴在看板上。这个数字的用处有限，因为它掩盖了最重要的问题：慢在哪一段。

千卡集群的一次典型事故，从第一声告警到训练恢复正常，40 分钟。里面大概 8 分钟在发现，20 分钟在定位，10 分钟在恢复，2 分钟在验证。

**定位吃掉一半时间。** 这个比例在多数团队身上成立，而多数团队优化的却是发现。

## 本节目标

- 把 MTTR 拆成发现、定位、恢复、验证四段，并用自己集群的一次真实事故填这张表
- 认出比设备指标更早的业务信号，说明为什么训练任务本身是最灵敏的探针
- 用定界、缩小、确认三步描述定位过程，并说明每步需要什么数据
- 给处置动作按可逆性分级，划出可自动执行与必须人确认的界线
- 说清“假恢复”的两种形态，以及验证环节为什么不能省

## 机制拆解

### MTTR 是个和

```text
MTTR = MTTD（发现）+ MTTI（定位）+ MTTR_p（恢复）+ MTTV（验证）
```

四段之和才等于用户感知的时长。不分段就只有一个模糊的数字，改哪个环节都靠猜。

| 段 | 典型占比 | 主要手段 | 常见浪费 |
|---|---|---|---|
| 发现 | 20% | 告警、异常检测、业务监控 | 聚合窗口太长、告警被抑制规则吞掉 |
| 定位 | 50% | 拓扑、日志、INT、RCA 图 | 各层数据口径不一，人要手工对齐 |
| 恢复 | 20% | 隔离、切换、回滚 | 权限流程、变更审批串行 |
| 验证 | 10% | SLI 对比基线 | 只看告警消失，不看性能回到基线 |

第一件要做的事不是买工具，是拿最近五次事故各填一行。填完你会发现自己优化错了地方。

### 发现：业务信号比设备信号更早

设备侧告警的延迟来自三个地方。聚合窗口、阈值宽度、抑制规则。

- **聚合窗口**：1 分钟窗口的均值告警，最快也要 1 分钟才响。
- **阈值宽度**：阈值要压住噪声，通常设在明显异常的位置。于是劣化早期不响。
- **抑制规则**：同一设备的告警收敛到一条，响应时间被上游告警拖住。

训练任务本身没有这三个延迟。每个 step 都在打时间戳，直接看步耗时分布，漂移能在秒级被看见。

```text
# 一次真实的判读形态（示意数字）
基线       step_time_p50 = 380 ms
事故期间   step_time_p50 = 520 ms
           step_time_p99 = 2.1 s
           nccl_allreduce_p50 = 190 ms（基线 90 ms）
```

这组数字说明两件事。全体的中位数都在涨，说明不是个别慢节点。集合通信占比从 24% 涨到 36%，说明问题在网络或通信调度，不在算力。

用熟悉的东西类比一下。这相当于服务 RT 报警之前，先看网关的 P99。越靠近业务，信号越早，语义越清楚。

<Aside type="caution" title="业务信号需要基线，否则没有判据">
步耗时本身没有绝对好坏，要看与基线的比值。所以第一周采集的核心产出是基线，不是告警。

基线要按任务类型分开存。不同模型、不同卡数、不同并行策略的步耗时不可比。混在一起算基线，等于没有基线。
</Aside>

### 定位：定界、缩小、确认

定位不是“看图找问题”，它有固定三步。

**第一步，定界。** 问的是哪一层：任务、主机、网络、光层。四个数据源各切一刀。

| 层 | 数据源 | 定界信号 |
|---|---|---|
| 任务 | 训练日志、步耗时分解 | 是否全体变慢，是否集中在某些 rank |
| 主机 | NCCL 日志、DCGM | 是否有单卡降频、XID、NVLink 重放 |
| 网络 | gNMI 计数器、INT | PFC 时长、ECN 标记率、路径时延分解 |
| 光层 | 光功率、lane 级 CRC、FEC 纠正 | 单 lane 劣化、FEC 纠正率抬升 |

一刀切下去就排除掉一半可能。比如全体 rank 同步变慢，可以先把主机与单卡问题排除。只有特定 rail 上的 rank 慢，网络与光层优先。

**第二步，缩小。** 在全网里找到具体设备、端口、链路。

这一步最耗人，因为它要求把拓扑、时间线、指标三者对齐。RCA 图在这里的价值就是把“可能性”排序，把最可疑的三个候选放到人前面。

**第三步，确认。** 三角验证，三个独立证据指向同一处才算确认。

比如怀疑一条链路：PFC 时长在这一跳上涨、INT 显示这一跳排队、同一时刻其他流也在这条路径上慢。三个证据来源不同，结论才可信。

<Aside type="note" title="经验映射（IDC → AIDC）">
这套三步和线上服务排障一模一样。定界相当于判断是接入层、应用层还是数据库层。缩小相当于从全集群追到某个 Pod。确认相当于把日志、指标、链路追踪三者对齐。

差别在于网络侧的“日志”很少，证据主要靠计数器与带内遥测。所以三角验证里，时间线对齐的权重比服务排障时更高。
</Aside>

### 恢复：动作阶梯与可逆性

处置动作按影响面排一个阶梯。低阶先上，别一上手就重启。

| 阶 | 动作 | 影响 | 可逆 | 建议 |
|---|---|---|---|---|
| 1 | 标记嫌疑端口，加重观测 | 无 | 是 | 自动 |
| 2 | 调整 ECMP 权重或路由，避开嫌疑链路 | 局部流量迁移 | 是 | 自动，带速率限制 |
| 3 | drain 端口，把链路摘除 | 该链路流量转移，容量降一档 | 是 | 自动或人确认 |
| 4 | 从 checkpoint 重启任务 | 回退到上一个 checkpoint | 损失算力时间 | 人确认 |
| 5 | 换硬件、重启设备 | 服务中断 | 否 | 人执行 |

自动化的分界线在第 3 阶与第 4 阶之间。判断标准只有一条：**动作可逆且影响局部，就可以自动。**

drain 端口可逆，且有容量兜底，可以自动。重启任务不可逆，会丢掉当前步的算力，必须人确认。

### 验证：假恢复比没恢复更糟

恢复动作做完，告警消失，两种假象会出现。

**假象一，流量绕开了问题，问题还在。** drain 端口之后告警消失，但那条链路的硬件没修。临时路由一旦回切，故障立刻复现。

**假象二，指标回绿但性能没回。** NCCL 把 ring 重组到跨节点路径上，PFC 与 ECN 全部正常，因为流量不走那些链路了。步耗时比基线高 30%，谁也没报警。

所以验证必须看**业务 SLI 是否回到基线**，不是看告警是否消失。

```text
验证三问：
1. 受害任务的步耗时是否回到基线 ±10%
2. NCCL ring 是否回到域内或原路径
3. 被处置的设备或链路，故障根因是否已确认并登记
```

第三个问题常常被跳过。跳过它的后果是同一颗光模块两周后再炸一次，而所有人都以为已经修过。

## 判读与实操

### 一次事故的时间账

拿一次真实事故填表，比看任何方法论都有效。

| 时刻 | 事件 | 分段 |
|---|---|---|
| 10:00 | 任务步耗时从 380 ms 涨到 520 ms | 发现起点 |
| 10:06 | 值班看到步耗时告警 | 发现结束，6 分钟 |
| 10:09 | 确认全体 rank 同步变慢，排除单卡 | 定界 |
| 10:18 | INT 显示第 3 跳排队，定位到具体端口 | 缩小 |
| 10:23 | 三项证据对齐，确认该端口 PFC 风暴 | 确认，定位结束 17 分钟 |
| 10:26 | drain 端口，流量绕开 | 恢复 |
| 10:31 | ring 重组完成，步耗时回到 390 ms | 验证，5 分钟 |

总计 31 分钟。发现 6、定位 17、恢复 3、验证 5。优化收益最大的是定位段，而最容易被自动化的却是恢复段。

### 每段一个抓手

| 段 | 单一最有效动作 |
|---|---|
| 发现 | 把训练步耗时纳入 SLI，按任务类型建基线 |
| 定位 | 统一四层数据的时间戳与设备命名，让对齐成本归零 |
| 恢复 | 把可逆动作写成带速率限制的 runbook，砍掉审批串行 |
| 验证 | 恢复后强制跑一次基线对比，结果写入事故记录 |

第二项听起来最不技术，实际收益最大。定位慢，多数时候不是缺数据，是数据对不上：设备名三套叫法、时间戳两个时区、端口号两套编号。

## 经验映射

| 你已有的做法 | 在 MTTR 拆解里的位置 |
|---|---|
| 服务排障的分层定位 | 定界、缩小、确认三步 |
| 变更管理与审批流 | 恢复段的动作阶梯与权限分界 |
| 金丝雀与回滚 | 可逆动作优先，不可逆动作人确认 |
| 事故复盘模板 | 每段的耗时归因，而不是只写“已恢复” |
| 灰度与基线对比 | 验证段的三问 |

方法论全是旧的。新增的只有一件事：**网络侧的处置动作粒度更粗。** 服务可以灰度 1% 流量，网络只能整条链路摘除或整台设备重启。

## 练习

**必答 Q1**：某集群 MTTR 是 45 分钟，老板要求压到 20 分钟。给出你的拆解方案与三处最可能的收益点。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

先拆再加。拿最近五次事故各填一行四段耗时，没有这个数据就不要承诺数字。

典型分布是发现 8、定位 25、恢复 10、验证 2。据此找收益点：

1. **定位段**：统一设备命名与时间戳，把四层数据对齐从人工变成查询。这一项通常能砍掉定位时间的一半。
2. **发现段**：把训练步耗时纳入 SLI，按任务类型建基线。发现从 8 分钟降到 2 到 3 分钟。
3. **恢复段**：把可逆动作（标记、改权重、drain）做成带速率限制的自动化，砍掉审批串行。

验证段不要压。压掉验证会换来二次事故，代价远大于省下的 2 分钟。

**评分维度**：先拆解再谈目标（必需）。三处收益点与段对应（必需）。明确不压验证段（加分）。
</details>

**必答 Q2**：设计一套自动化处置流程，要求它能在无人值守时安全运行。写出动作清单与每步的护栏。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

动作清单按可逆性分三层。

**自动执行**：标记嫌疑端口、加重采样、生成时间线快照、通知值班。

**带护栏自动执行**：ECMP 权重微调（单次改动不超过 10%，10 分钟内最多两次）、drain 端口（要求同 rail 至少还有一条健康链路，且集群整体容量余量 ≥ 15%）。

**必须人确认**：任务重启、设备重启、固件升级、任何不可逆操作。

护栏有四条。一是速率限制，任何自动动作都要有频次与幅度上限。二是熔断，连续两次自动动作没有改善就停下来等人。三是审计，每次动作写操作日志与触发依据。四是回滚预案，可逆动作必须记录原始配置以便恢复。

**评分维度**：按可逆性分层（必需）。给出至少两条具体护栏（必需）。提到熔断或审计（加分）。
</details>

**自测 Q3**：为什么“告警消失”不能作为恢复完成的判据。

<details>
<summary>参考答案与评分维度</summary>

因为告警看的是被监控对象，而不是用户体验。drain 一条链路后，这条链路的计数器归零，告警自然消失，但硬件问题还在。或者流量被路由绕开，ring 重组到跨节点路径，网络指标全绿而步耗时仍高于基线。

判据要看业务 SLI 是否回到基线，并确认根因已登记。

**评分维度**：指出告警与用户体验脱钩（必需）。举出绕开或重组两种形态（加分）。
</details>

**自测 Q4**：定位段最耗时的环节通常是什么，怎么把它变成可工程化的能力。

<details>
<summary>参考答案与评分维度</summary>

最耗时的是数据对齐：设备命名不统一、时间戳不同源、端口编号两套体系，导致人要手工拼接四层数据。

工程化做法是把对齐变成数据模型的一部分。设备用统一资产 ID 做主线，时间统一打采集端时间戳并保存时钟偏差，端口用拓扑里的稳定标识。对齐之后，定位从“查三个系统”变成一个查询。

**评分维度**：点出数据对齐（必需）。给出统一标识与时间戳的方案（必需）。
</details>

## 本课要点

<Aside type="tip" title="本课要点">
- **MTTR 是和不是数**：发现 + 定位 + 恢复 + 验证，分段才谈优化
- 典型占比：定位约占一半，多数团队优化的却是发现与恢复
- 业务信号更早：**训练步耗时按任务类型建基线**，比设备告警快一个量级
- 定位三步：定界（哪一层）、缩小（哪台哪口）、确认（三个独立证据）
- 自动化分界线：**可逆且局部可自动，不可逆必须人确认**
- 一条坑：假恢复。告警消失不等于性能回基线，验证块不能省
</Aside>
