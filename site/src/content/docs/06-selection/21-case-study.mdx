前面二十课各讲一层。这一课把它们接起来，走一遍完整流程。

案例是构造的，但每一层的数字都来自真实故障的典型形态。**你可以拿同样的表格去核对自己的集群。**

## 本节目标

- 用“全体同步变慢”与“个别 rank 变慢”两个判据，第一刀就切掉一半可能
- 在任务、主机、网络、光层四层各说出一个决定性的证据，并知道它的采集入口
- 把一次 40 分钟的排障写成可复用的 checklist，含每步的判据与止损点
- 说清处置动作的顺序原因，以及验证为什么必须看业务 SLI 而不是告警

## 机制拆解

### 案例：所有指标都正常的那 40 分钟

背景：一个 512 卡训练任务，rail-optimized 拓扑，每台服务器 8 网卡对应 8 条 rail。RoCEv2 加 PFC 与 ECN 全开。

```text
10:00  步耗时从 380 ms 涨到 520 ms，P50 与 P99 同步抬升
10:00  全部 512 个 rank 都变慢，没有明显的掉队者
10:00  NCCL allreduce 从 90 ms 涨到 190 ms，占比 24% → 36%
10:00  DCGM 无降频、无 XID、NVLink 无重放
10:02  全网 PFC 与 ECN 侧：只有 rail-3 的 leaf-7 上行口有异常
10:05  该端口 10 分钟内累计 pause 时长 42 秒，ECN 标记率 0.4% → 3.8%
10:08  该端口 CRC 从 0 涨到每分钟 12，FEC 纠正率从 1e-9 升到 4e-6
10:11  DOM 读数：lane 2 光功率 -8.9 dBm，其余 lane 在 -2.4 dBm 附近
10:15  drain 该端口，流量绕开
10:20  步耗时回到 390 ms，ring 恢复到原路径
```

这份时间线里没有任何一个单点指标是“超阈值报警”的。全长都在正常范围的上沿。

### 第一刀：任务层，先分清全体还是个别

判据只有两个。

| 现象 | 指向 | 下一步 |
|---|---|---|
| **全体 rank 同步变慢** | 共享资源：网络、共享存储、调度 | 网络层优先 |
| **个别 rank 变慢** | 该主机：单卡、单网卡、单链路 | 主机层优先 |

这个案例是全体同步变慢，所以网络层优先。如果只有 4 个 rank 慢，先去查那台机器。

再看集合通信占比。占比从 24% 涨到 36%，说明时间被通信吃掉，算力没有退化。这个判断很关键：它把 GPU 侧的问题先排除了。

```bash
# 从训练日志算每步耗时与通信占比
python3 - <<'PY'
import re
pat = re.compile(r'step\s+(\d+).*?step_time:\s*([\d.]+)ms.*?allreduce:\s*([\d.]+)ms')
rows = [tuple(map(float, m.groups())) for m in pat.finditer(open('train.log').read())]
recent = rows[-200:]
p50 = sorted(r[2] for r in recent)[len(recent)//2]
share = sum(r[3] for r in recent) / sum(r[2] for r in recent)
print(f'allreduce_p50={p50:.1f}ms  comm_share={share:.1%}')
PY
```

### 第二刀：主机层，排除单卡与域内

主机层要排除三样：降频、XID、NVLink 重放。

```bash
nvidia-smi --query-gpu=index,temperature.gpu,clocks_throttle_reasons.active --format=csv
dmesg -T | grep -i xid | tail
dcgmi dmon -l | grep -i nvlink
```

这个案例里三项都干净。意思是 GPU 与域内网络（NVLink）没有劣化。第 10 课的判断在这里派上用场：如果域内 ring 被重组到跨节点路径，也会出现全体变慢，而网络计数器正常。

所以这一刀还要多看一眼：**NCCL 的 ring 组成有没有变**。ring 相当于流量的实际路线图，它一变，后面所有网络指标都对不上号。

```bash
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,GRAPH ./train 2>&1 | grep -i 'ring\|via'
```

### 第三刀：网络层，从面到线

gNMI 负责面，告诉你哪台设备的哪个端口在冒烟。INT 负责线，告诉你哪一跳在卡。这个分工相当于监控与链路追踪的关系，一个看趋势，一个看因果。

案例里唯一的异常信号落在 rail-3 的 leaf-7 上行口。判读顺序是固定的。

1. **PFC 时长**先看，不看帧数。42 秒 / 10 分钟意味着这条链路有 7% 的时间在反压。
2. **ECN 标记率**看斜率。0.4% 到 3.8% 是十倍级上升，说明拥塞在被压制而不是被解决。
3. **队列峰值**看有没有顶满。顶满加长时间 pause 就是风暴前兆。
4. **CRC 与 FEC** 看一阶差分。CRC 从 0 到每分钟 12，这个绝对值在阈值体系里微不足道，在趋势上是第一阶段证据。

```text
现场经验值（同一端口，10 分钟窗口）
PFC pause 时长        < 1 s      正常
                      1–10 s     关注
                      > 10 s     严重，需处置
ECN 标记率             < 1%       正常（跑满带宽时 1–2% 也常见）
                      > 3%       持续存在即异常
```

### 第四刀：光层，找到那个 lane

劣化阶段的标志是 FEC 在硬扛。链路上不丢包，因为前向纠错把错误都纠回来了。代价是纠错压力上升，pre-FEC BER 抬高，极端情况下芯片会降 lane。本质上，硬件在用电与重传换可用带宽。

DOM 读数给出决定性证据：lane 2 的光功率 -8.9 dBm，其余 lane 在 -2.4 dBm 附近。**单 lane 掉 6 dB，这不是抖动，是劣化。**

```bash
# 读 DOM（厂商命令不同，这里是通用形态）
show interfaces transceiver detail
# 关注：每 lane 的 rx power、tx bias、温度
```

四个证据到这里齐了：业务层全体变慢、主机层干净、网络层单端口 pause 与 ECN 异常、光层单 lane 劣化。四条独立来源指向同一处。

<Aside type="caution" title="单凭 CRC 涨不能定案">
CRC 上涨的原因不止光模块。脏端面、光纤弯折、连接器松动、对端芯片问题，都会表现为 CRC 上升。

下结论要三个证据：DOM 的 lane 级读数、FEC 纠正率的斜率、以及更换后的对比。前两个是定位，第三个才是确认。
</Aside>

### 处置顺序：先止血，再止损，最后根治

| 顺序 | 动作 | 原因 |
|---|---|---|
| 1 | drain 该端口 | 影响局部、可逆、立刻见效 |
| 2 | 观察 ring 重组与步耗时 | 确认绕开后业务恢复 |
| 3 | 换模块或清洁端面 | 根治，需要停机窗口 |
| 4 | 回切验证并登记根因 | 不回切就没确认修复 |

第二步容易被跳过。跳过它的后果是以为“drain 之后好了”。任务其实在跨 rail 的次优路径上跑着，性能只是没坏到报警。

## 判读与实操

### 一份可打印的 checklist

| 序 | 检查 | 命令或数据源 | 判据 | 耗时段 |
|---|---|---|---|---|
| 1 | 全体还是个别的慢 | 训练日志、步耗时分布 | 全体同步 → 网络优先 | 发现 |
| 2 | 通信占比是否上升 | 日志里的 allreduce 耗时 | 占比上升 → 通信问题 | 定界 |
| 3 | GPU 是否降频或报错 | `nvidia-smi`、`dmesg` | 干净则排除算力 | 定界 |
| 4 | ring 是否还在原路径 | NCCL 日志 | 变了 → 域内或拓扑问题 | 定界 |
| 5 | 哪个端口 PFC 异常 | gNMI 订阅、面板 | pause 时长 > 10 s / 10 min | 缩小 |
| 6 | ECN 标记率斜率 | 同上 | 涨十倍且持续 | 缩小 |
| 7 | 逐跳时延 | INT | 集中在一跳 → 该跳出口拥塞 | 缩小 |
| 8 | CRC 与 FEC 趋势 | 端口计数器 | 一阶差分上升 | 确认 |
| 9 | lane 级光功率 | DOM | 单 lane 偏离 > 3 dB | 确认 |
| 10 | 处置与验证 | drain、换模块 | 步耗时回基线 ±10% | 恢复 |

十步里有五步在定界与缩小。这和上一课的时间账一致：定位是大头。

### 三条贯通全程的原则

**先看趋势再看阈值。** 这个案例里所有指标都在阈值内。能发现问题的是斜率。斜率就是变化速度，比绝对值敏感一个量级。

**先定界再缩小。** 直接从全网找“哪个端口有问题”，会在几百个候选里迷路。先切成四层，候选立刻少一个数量级。

**证据来自不同来源。** 同一份数据用两种聚合方式看，不算两个证据。

### 实验入口：十步剧本与两条路径的时间账

```bash
cd labs/11-case-study
make run        # 最优路径与蛮干路径各走一遍，看 MTTR 差多少
make steps      # 完整剧本：十步，每步的判据都写出来
make live       # 十步里哪几步能在容器拓扑里复刻
```

两条路径面对同一份数据。最优 40 分钟，蛮干 79 分钟。
差距不在查得快慢，在方向：等阈值告警、跳过定界、凭 CRC 单证据换件。

剧本把每一步的耗时归到发现/定界/缩小/确认/恢复五段。
排出来你就看见上面那张十步表的重量：**定界与缩小占四成以上。**
优化也该按这个比例投人。

## 练习

**必答 Q1**：给下面这组数据，判断问题在哪一层，并说明依据。

```text
步耗时      P50 从 380 ms 涨到 500 ms
rank 分布   只有 8 个 rank 变慢，集中在同一台服务器
通信占比    24% → 26%
DCGM        该服务器 GPU 温度 79℃ 正常，无 XID
NCCL 日志   allreduce 在该 rank 上耗时是其他 rank 的 4 倍
网络侧      该服务器 8 个网口的 PFC 与 ECN 均正常
```

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

问题在主机层，比较可能是该服务器的 PCIe 或本地总线，而不是网络。

依据有两条。一是慢的 rank 集中在一台机器上，网络问题通常是整条 rail 或整条路径受害，不会只挑一台机器的 8 个 rank。二是该机器的 8 个网口指标都正常，网络侧证据缺失。

下一步看三处。该机器的 PCIe 带宽与错误计数、NIC 到 GPU 的亲和性（`nvidia-smi topo -m` 看 `PIX`、`PHB`、`SYS`）、以及 CPU 侧是否有 NUMA 错配。通信占比只从 24% 涨到 26%，说明瓶颈在数据搬运链路上，不在网络拥塞。

**评分维度**：定位到主机层且给出“集中在一台机器”这个依据（必需）。排除网络的理由基于端口指标（必需）。提出 PCIe 或亲和性方向（加分）。
</details>

**必答 Q2**：把 checklist 压缩成 5 步，说明砍掉哪些以及为什么可以砍。

<details>
<summary>参考答案与评分维度</summary>

**参考答案**

五步版本：

1. 全体还是个别变慢（决定走网络还是主机）
2. 通信占比是否上升（决定是通信还是算力）
3. 哪个端口 PFC 与 ECN 异常（面的定位）
4. 逐跳时延是否集中在一跳（线的定位）
5. CRC、FEC、DOM 三级确认（硬件确因）

砍掉的是主机层细查与 NCCL ring 检查。理由：如果第 2 步显示通信占比上升，主机层问题一般会有 XID 或降频伴随，先看 PFC 面板成本更低。ring 检查可以放到第 3 步无异常时再做，作为兜底。

风险要说清：五步版会漏掉“域内重组”这类无网络异常的慢任务。

**评分维度**：五步覆盖定界、缩小、确认（必需）。说清砍什么以及风险（必需）。承认压缩有代价（加分）。
</details>

**自测 Q3**：为什么这个案例里“丢包率为 0”完全不能作为排除网络的依据。

<details>
<summary>参考答案与评分维度</summary>

无损网络靠 PFC 与重传机制维持零丢包。零丢包是设计结果，不是健康指标。

真实损失换成了别的东西：反压时长、纠错压力、带宽降档。这些都不体现为丢包，只体现为时延与有效吞吐。

**评分维度**：说清零丢包是设计结果（必需）。指出损失转化为时延与纠错压力（加分）。
</details>

**自测 Q4**：如果 PFC 上涨但 CRC 与 FEC 完全正常，你的下一步是什么。

<details>
<summary>参考答案与评分维度</summary>

先排除光层，把方向转向拥塞与配置。三个方向：

一是流量分布，是否某个 ECMP 分支热点化，看 INT 的逐跳时延与出口利用率。二是水线配置，是否 XOFF 阈值过低导致易触发 pause。三是上游突发，是否 collector 或存储侧的新任务改变了流量形态。

再补一条：看 PFC 是否集中在同一优先级队列上，这能把范围从链路缩小到某类流量。

**评分维度**：排除光层并给出至少两个方向（必需）。提到按优先级拆维度（加分）。
</details>

## 本课要点

<Aside type="tip" title="本课要点">
- 第一刀按“全体还是个别”切：全体 → 网络，个别 → 主机
- 四层各有决定性证据：业务看通信占比、主机看降频与 XID、网络看 PFC 时长与 ECN 斜率、光层看 lane 级 DOM
- **所有指标都在阈值内也能定案**，靠的是一阶差分与四源对照
- 处置顺序：drain 止血、观察绕开、换件根治、回切验证
- 验证看业务 SLI 回到基线 ±10%，不看告警消失
- 一条坑：不做回切验证，等于把“临时绕开”当成“已修复”
</Aside>
